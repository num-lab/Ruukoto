# Agent Note: Concluding work calls yield the round and are recognized from persisted facts

Status: implemented
Archived: 2026-11-10

## Problem

Personal `background_work` calls that conclude arrangement (report/append/cancel/cancel_delegation/close, plus the authority errors that already instruct the model to end the round) previously returned an ordinary tool result. The model then had to produce prose echoing the result before the run could end, which wasted a provider round and produced tool-call-only or empty assistant answers that callers treated as missing answers. The Personal assistant plan needs a durable main handoff: conclude work, end the run without sealing too early, and keep later owner inputs as distinct runs without fabricating history or successful settlement.

## Decision

[Bounded main coordination](2026-11-03-personal-coordination-cutoff.md) supersedes the earlier upstream-gate requirement: normal arrangements retain this afterTool behavior, queries compose model answers, and exceptional overruns fail honestly with exact-work cancellation. Upstream general yield remains an optional simplification. [Host report publication](2026-11-04-personal-report-publication.md) supersedes model-only report initiation with explicit host provenance while retaining legacy verification. [Foundation integration](../bug-fix/2026-11-04-personal-foundation-integration.md) rejects unexplained empty local answers.

An arrangement-only `background_work` batch yields the round through a host `afterTool` hook, not through the tool's own result. The tool returns plain outputs for `delegate`, `append`, `cancel`, `cancel_delegation`, `close` and `report`; the hook reads the persisted assistant batch and, when every call in it is one of those arrangement actions, returns the same result with `control.terminate: true`. Any query or non-`background_work` call in the batch vetoes this hook's termination decision. A yielded arrangement batch ends the input; a query-containing batch may compose an answer or perform further authorized calls, including error repair, within the round budget. The authority errors `work_tool_inactive`, `work_source_ambiguous`, `work_source_invalid` and `work_tool_coordination_cutoff`, whose text already tells the model to end the round, still carry tool-side `control.terminate`. Pi durable settles the tool result as `{ kind: "model", entryId, control }` in the persisted tool task record either way, so the yield is reconstructible from durable records, not transient live state. The model-facing description mirrors the same contract: sibling calls in one batch cannot see identifiers returned by each other, freshly returned `work`/`delegation` ids are prerequisites usable only from a later batch, arrangement-only batches yield to the host after execution, and query-containing batches continue to prose or further calls.

A `cancel` action commits the durable cancellation intent, fires `abortTask` on the target's invocation without awaiting its join — a held invocation must not block the owner answer — and returns a registration fact ("已登记取消，停止仍须核实") rather than a stopped one; physical stopping stays a separately observable record. An `append` action reports the persisted admission outcome. Low-level `appendPersonalWork` retains terminal refusal; for safely completed work, the model-facing tool may explicitly register linked follow-on work in the same idle identity and report `continued`. If continuation is unavailable or refused, the handoff reports 未接纳 or the actual error instead of claiming the requirement was appended.

`personalWorkHandoff(tx, answerEntryId, limit?)` recognizes a yielded answer by persisted facts: every call slot's `pi.tool` task result must be terminal `kind: "model"` with `control.terminate === true`; any call without that control means unexplained, while model text parts no longer veto recognition — a batch can carry prose before its calls and still yield. Task lookup is scoped by `input.assistant === answer` inside each `pi.tool` task's input, because provider call IDs repeat across assistant entries and an unscoped match would read another entry's outcome. When recognized, the owner-facing text joins the model's own pre-call prose with facts derived from the persisted call arguments and results (delegation/work/agent ids) — e.g. "已委派分析；本轮以工具调用让出：已登记委托 N 的最终汇总安排…" — so a refused call can never hide behind a claim the model wrote first: an `isError` tool result is reported as "调用 X 未生效：…", and a normal result carrying the persisted refusal (the `accepted: false` append outcome) reports as 未接纳 — neither is ever flattened into a success claim. The optional `limit` (the IM receipts pass their 3900-character send budget) bounds the returned string: pre-call prose truncates or drops first, and when the factual body itself exceeds the budget — a large arrangement batch whose accepted-call result JSON alone overflows — the body is rebuilt as an exact aggregate ("共 N 项调用，X 项已生效，Y 项未生效或未接纳") followed by refusal facts in full and accepted calls in compact form, detail truncating on fact boundaries; a refusal's existence can never be cut by successful result payloads. `answer()` in personal-harness consults the handoff whenever the assistant message carries toolCall parts, not only when text is empty; unexplained empty or whitespace-only text throws `answer_missing`, as does a genuinely missing assistant entry. The `/input` status path in personal-control and the Telegram/QQ receipts apply the same recognition before their error/canned paths. Report tasks already reject textless answers as `unanswered`, so a yielded report-attempt round cannot masquerade as a report body.

Pi 1.3.0/1.4.0 exposes no general post-tools round yield: `control.terminate` requires unanimity across every tool slot. Handled arrangement refusals still receive `afterTool` termination, while unavailable or intercepted slots without termination control can prevent a yield; the input may recover within its finite budget. `control.handoff` ends the run but appends a `pi.reset` boundary that drops prior context. `afterTools` is `void` and cannot request termination. This handoff uses the supported all-slot control rather than rewriting native run state to invent successful settlement. The later [cutoff coordinator](2026-11-03-personal-coordination-cutoff.md) instead preserves failed outcomes and owns the final-boundary commit that advances parked owner inputs after cancellation registration. A general upstream yield remains an optional simplification; `test/personal-handoff.test.ts` proves the existing control and recognition contract against the minimal Pi fixture and assembled host.

## Alternatives considered

- `control.handoff` on concluding calls: ends the round, but the persisted `pi.reset` cuts model context — later owner input would lose the conversation. Rejected; it changes history visibility rather than yielding.
- Rewriting `LiveDoc` or replaying the generation to fabricate successful round completion: risks corrupting run accounting. Rejected; the later cutoff coordinator retains native failed outcomes while owning queue progression.
- Forging a model report call for host reporting: a forged call is unverifiable against `modelCall` recovery checks. Explicit host provenance and retained legacy model-report verification are owned by the later report-publication decision.
- Recognizing yield from `LiveDoc` or transient run state: works only in-process. Persisted tool-task results carry `control`, so recognition survives restart and works in `/input` status and recovery paths.
- Yielding whenever `delegate` appears in the batch: repeated delegation across rounds is legitimate arrangement, and per-call yields would let an arrangement-only batch that ends early still veto. The batch-level rule supersedes this: one batch may compose several arrangements, then yields — a `delegate`-only batch concludes like any other arrangement batch, and the round budget in [bounded main coordination](2026-11-03-personal-coordination-cutoff.md) bounds how many further batches the same input may attempt.

## Consequences

Conclusion-oriented rounds no longer spend a provider call on mandatory echo prose, and every consumer of a done input (`answer()`, `/input` status, Telegram receipts, report answer extraction) sees honest handoff facts or its empty-answer failure handling. Mixed rounds continue through model-written answers within the four-round budget; exceptional cutoff preserves committed effects and advances later owner inputs after exact cancellation registration. Each `followUp` retains its own requestId/source. Crash between admission and tool-result commits replays the tool safely under its original idempotency keys; crash after a yielded round reopens with work/report intact and recovery-verified. The accepted cutoff and publication decisions supply M0/M1 behavior without requiring a general upstream yield.
