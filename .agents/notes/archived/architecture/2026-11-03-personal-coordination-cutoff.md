# Agent Note: Bounded main coordination migrates waiting tools to children and cuts off overrun inputs

Status: implemented
Archived: 2026-11-10

## Problem

The main Personal conversation carried the waiting business tools (`read_file`, `write_file`, `http_request`, `web_search`, `read_artifact`, `list_files`, `search_files`) whose operations can hold approvals or slow effects for minutes. While such a call waited, the run owned the only main generation, so later owner inputs queued behind business waiting the model could have delegated. Separately, an arrangement loop could spend unlimited provider rounds issuing `background_work` calls without ever converging to an answer, and no durable fact bounded how many tool batches one owner input may commit. Issue #37 requires the main agent to stay responsive: waiting business work must live in SubAgents, coordination must be bounded per owner input, an over-budget input must stop without executing further effects, and only the work that exact input admitted or appended may be cancelled.

## Decision

Waiting business tools are migrated to child agents. `personalMainToolNames` removes them from every main model request (wire `toolsAdded` and the recorded payload alike), while `personalReadTool` refuses their main-conversation execution with `personal_tool_main_ineligible` before admission — an ordinary handled tool error that still lets hooks observe the call. Child conversations keep the full family, so `background_work` delegation remains the production path for waiting work; the refusal message says so.

One owner input may commit at most `PERSONAL_MAIN_TOOL_ROUNDS` (four) persisted tool-call batches. Rounds are entry-derived, not run-derived: `personalCoordinationTailRounds` counts `pi.assistant` entries containing `toolCall` parts after the latest user-model entry, so the count survives reopen and successor generations, and multi-input runs measure the newest input's window. Window boundaries are submission placements — `pi.user` entries and other input kinds — while `pi.compaction` summaries carry a user-role message yet are host writes, so they stay inside the owning input's window and never reset its budget. At request time a tail of exactly four returns an empty tool list, so a compliant model can only answer in prose; a tail above four throws `coordination_rounds`, faulting the request. Independently, the work-tools `beforeTool` hook blocks every main tool call once the tail exceeds the bound, so a noncompliant model that emits calls on an empty tool offer persists the batch but executes no effect.

A host-side coordinator (`startPersonalCoordination`) drives the cutoff from outside the generation invocation: a `LiveDoc` watch enqueues every run input, a commit subscription enqueues submissions settling `unanswered`, and an open-time sweep rescans persisted `unanswered` inputs, so an abort or crash mid-coordinate is retried rather than lost. Events landing while an input's evaluation is in flight coalesce into a dirty-marked recheck instead of being dropped — the in-flight read may already be stale — and a failed stage retries a bounded number of times in-process before the input stays unevaluated for the reopen sweep or the next event. The sweep logs and retries a failed page a bounded number of times instead of silently dropping leftovers, and `close()` is idempotent — the harness-terminal unlock path and an explicit `close()` share one stop, so the watcher can never keep the profile's storage alive across a reopen.

Evaluation counts that input's batches up to the next user entry; above the bound it commits the cutoff intent first — `ruukoto.coordination` doc keyed by the owner `requestId`, holding the submission id and exact cancellation targets — then waits out the owning run before the completion commit: each round it re-resolves the submission and the `LiveDoc` run owner, and aborts the current generation only while the record is still a run input, so a rollover that hands the run to a later owner input is never aborted and a stale captured generation is never retried. The `abortTask` join is intentionally not awaited — a non-cooperative invocation must not block the cutoff; the abort mark is committed inside `abortTask` and physical death is observed by re-polling the submission. Once the record is no longer placed, one atomic commit rescans admissions around the abort, registers `requestPersonalWorkCancel` on each live target — terminal targets are skipped and already-flagged works are not re-requested — writes the `cancelled` member with the refs actually registered, and appends the `ruukoto.coordination-cutoff` marker entry via `tx.appendEntry`. The marker is a host entry append inside the completion commit, never a queue submission: a write submitted post-settle still joins the public queue and can wedge behind a later live run that faults without a boundary, where a fixed submission key would keep returning that stuck record on reopen. The doc's `marker` member makes the append replay-safe across retries and reopen, so a crash between intent and completion finishes exactly once — no request key is needed. Intent alone never reads as completion: consumers distinguish `cancelled === undefined` (intent persisted, registration unfinished) from a populated list, so "cancel requested" is never claimed before the requests were actually registered. Separately, a run that faults or aborts ends without a `final` boundary, so `queued` submissions would sit in the inbox forever — nothing else places them. Queue progression is therefore a coordinator duty, serialized on the same chain as cutoff evaluation so an over-budget input's cancellation registration is durable before later owner inputs advance: each attempt first drains every pending evaluation, deferred mark and the still-running open sweep, then scans persisted `unanswered` submissions for settles whose events were never enqueued — only records that could still need evaluation count, meaning placed inputs; terminal entryless records (a queued input withdrawn through public `submission.abort()`, or a revoked report/question input) are finished by definition and non-input submissions are never candidates, so the sweep cannot spin on records the evaluator can never accept — and returns without advancing while any are found. Only then does one Session commit place the queue itself: it rewrites any live-spelling input modes parked before the barrier's early return, re-reads the barrier inside the transaction, checks `LiveDoc` for a live run and `InboxDoc` for items, and applies the same `final` boundary admission would — every queued write lands first (a stale head target settles `unanswered`), then the first steer and first follow-up in ID order across parked and legacy live spellings — and starts a `GenerationTask` for the placed inputs, mirroring `startRun`. The barrier read and the placement share the commit, so a settle committed before it is held and one committed after finds the queue already placed or its own item queued — there is no check-then-place window, nothing polls, and the fixed-key `ruukoto.coordination-progress` write no longer exists. Every failure inside an attempt — the unanswered sweep or the placement commit — is contained by one bounded in-process retry: nothing rejects the shared chain (which `close()` also awaits), and beyond the bound the next commit event or the reopen sweep resumes it. Evaluation failures have their own bounded retry, but an input that exhausts it is deferred rather than erased: the coordinator's own sweeps never restart its attempt count, yet a paused retry is not a completed cancellation registration — the deferred record still holds the barrier, so queued successors cannot advance past an unfinished cutoff. A genuine later event or a reopen clears the mark and resumes recovery.

The same registration-before-advancement invariant applies to every route that can run a boundary, so admission itself carries the barrier rather than checking it beforehand: every main-input submission goes through the coordinator's `admit`, whose single Session commit decides queue-vs-place. `admitMainInput` mirrors Pi Durable's `admitSubmission()` for `type: "input"` under the host's fixed `one-at-a-time` queue modes — a known requestId dedupes without writing, `whenBusy: "reject"` on a live run throws `ConversationBusy`, boundary reads (inbox plus the head marker) precede the commit's first table write as upstream `prepareBoundary` requires, a busy or non-empty queue pushes the inbox item, an idle non-empty queue runs the same final boundary in-commit, and an idle empty queue appends the entry and starts the generation — except that `held` queues the draft instead of placing it or advancing anything. An in-commit barrier alone cannot stop foreign commits, though: native automatic background compaction admits its summary write through upstream `admitSubmission`, whose idle-with-items path runs its own `final` boundary — and any other upstream boundary (a write submission, a reset, a live run's `postTools` or `final`) selects queued items the same way. Queued owner inputs therefore carry parked inbox modes (`ruukoto.parked-steer` / `ruukoto.parked-followUp`) the upstream selector set — exactly `steer`, `followUp`, `write` — can never match, so no commit this module does not own can place them; withdrawal paths (`submission.abort`, `withdrawQueuedInputs`) treat every non-write item as an input and stay unaffected, and consumers see the upstream spelling through `personalUnparkMode`. Every commit this module owns first rewrites any live-spelling input items parked — covering native submits that bypass `admitInput` and queues persisted before parking — and the open sweep runs the same pass once for leftovers. `held` reads the coordinator's coordination state inside the transaction: an evaluable settle is `pending` synchronously at its commit's adoption (commit listeners dispatch synchronously after adoption), settles that precede the listener are covered until the open sweep finishes, a dirty recheck keeps its record pending through the backoff, and a deferred record holds until a genuine event resumes it — paused recovery is still unfinished registration. Because commits serialize on the Session line, the check can never be stale: a settle committed before the admission is held, and one committed after finds the input already queued behind it — there is no read-then-submit window, nothing waits or polls, so task abort and `close()` have nothing to deadlock on, and the IM platform mutex is never held past the admission commit, keeping same-channel controls and revocation responsive. The shared `admitInput` injection covers `p.submit`/`answer()` (which also covers `/inputs`), the Telegram/QQ receipt task, the delegation-report and question-answer tasks, and scheduler runs targeting the root conversation; before the coordinator finishes starting — early open-time tasks — the same primitive runs with `held: () => true`, which always queues and never places. A submission admitted while held then advances through the coordinator's own boundary commit once registration is durable.

Exact-work targets come from persisted admissions only: `ruukoto.analysis-admission` entries whose `source.submissionId` is the input's, and `ruukoto.work-note-admission` entries whose `source.kind === "input"` carries its `submissionId`. Delegations instructed by other inputs, queries, rejected appends and calls never admitted are never targets. Works already terminal are skipped, works already flagged are not re-cancelled, and physical stopping stays unverified until observed — cancellation, stopping, effect and result facts remain distinct records.

Consumers report the cutoff factually: `answer()` throws `input_coordination_cutoff` with the persisted registration count instead of a bare `input_unanswered`, and `/input` status returns the same text on a non-done record; both look up the doc by `requestId` first and fall back to the `submission:<id>` key so requestId-less cutoffs stay visible. Telegram and QQ receive the same notice through the original-entry receipt path: a cut-off input settles `unanswered` with no assistant entry, and the fence-faulted settle can win the race against the coordinator's intent commit, so the receipt task waits on the durable fact rather than a wall-clock window — while the input's persisted batch count still exceeds the bound the intent is provably pending (the coordinator owns landing it through retries, dirty re-evaluations and the reopen sweep), and the loop ends when the cutoff record resolves under either doc key or the count no longer reads over-budget; never a fabricated model answer. It then sends `personalCoordinationCutoffText` through the ordinary delivery pipeline with the original source/generation and send-uncertainty checks; an input unanswered for any other reason still records `unanswered`. Inside the same serialized commit, `personalToolSource` refuses new work admissions for a cut-off `sourceRequestId` with `work_tool_coordination_cutoff`, so no admission can slip between the intent write and the fence; the host `p.work` paths (`delegatePersonalWork`, `personalWorkNoteSource`, `appendPersonalWork`) apply the same persisted fence, because a placed-but-cut-off input still reads `active` until the settle lands. Open-time recovery validates the doc family's shape/version — including `targets` element fields and `submission` — and refuses a malformed `coordination_record_invalid` archive rather than guessing; a `null` cutoff is rejected, never treated as absent.

## Alternatives considered

- Abort the run inside the tool execution when the bound is exceeded: a tool call cannot retract its own already-persisted batch or sibling calls in the batch, and the model-facing answer would have to be fabricated. The host cutoff aborts after the fact with durable intent, and the persisted marker states what actually happened.
- Count rounds on the submission record or `LiveDoc` run inputs: submission bounds cannot separate one input's batches from a later input's inside a shared run, and live state is lost on reopen. Entry counting reconstructs the same answer from durable history on every path.
- Let the ineligible-tool refusal itself stop the round: a refusal is one call's error, while the batch and run remain live; it cannot cancel admitted work or bound batches that contain no business tool at all.
- Cancel every running work on cutoff: simpler, but unrelated delegations from other owner inputs would be destroyed by a batch they never instructed. Targets are matched to the exact `submissionId` of admitted records.

## Consequences

Main requests stay tool-complete for coordination (questions, background work, MCP, memory, skills) while never offering waiting business tools; delegated children execute them under the original input's frozen permission and source. A compliant model over-arranging simply receives an empty tool offer and answers in prose; only a persisted fifth batch triggers the durable cutoff, so ordinary runs are undisturbed. Over-budget inputs settle `unanswered` honestly, their marker records exactly which work was asked to stop, and retrying the same request reproduces the same cutoff text rather than re-coordinating. The empty tool list at the bound also removes `ask_user` for that one request, so a model cannot trade arrangement calls for a question at the limit. `test/personal-coordination.test.ts` is the mandatory `@earendil-works/pi-durable` upgrade gate named by the pre-push skill: an upgrade must keep the empty-inbox marker producing no new model request, the doc-guarded marker landing exactly once under completion-commit replay, the mirrored `admitSubmission`/`applyBoundary`/`startRun` semantics (requestId dedupe, busy `reject`, boundary reads before the first table write, writes-before-users ordering, stale-head settling), queued successors placed by the coordinator's own boundary commit after a boundary-less fault, successors held — by progression and by the in-commit admission barrier on every new-submission route — while any cancellation registration is pending, including through a deferred retry-exhausted input, the parked inbox modes keeping queued inputs unselectable to a native automatic-compaction write that lands mid-hold, an idle-with-queued admission placing the earlier queue first, and the real-SIGKILL reopen landing one marker and one cancellation pass. Accepted residual risks: in a multi-input run a later input settles `unanswered` alongside the offender without being marked; queued inputs stranded by a run that ended without a boundary are placed by the coordinator's next scheduled progression attempt — which waits for every pending evaluation and a fresh unanswered sweep before committing the boundary itself — not by the run's own completion, so between the fault and that attempt the queue reads stalled; and a caller that bypasses `admitInput` on the root conversation (`p.main.submit`) leaves its item in a live spelling until the next coordinator commit re-parks it, so an upstream boundary interleaving that window could still place it ahead of a pending registration — production entry paths are all wired through `admitInput`, so the residual needs an out-of-contract caller plus a boundary commit landing inside the window.
