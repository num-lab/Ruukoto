# Agent Note: Admit complete Personal attachments and assign immutable work scope

Status: implemented
Archived: 2026-11-10

## Problem

[Issue #48](https://github.com/num-lab/Ruukoto/issues/48) requires the owner to attach files in Desktop or Telegram, delegate their processing, and receive the requested result. The existing Personal image receiver rejects every media input on a text-only model and does not compare the completed download with its declared length. Desktop has a native picker for Coding but no Personal upload entry. Child artifact access is scoped to a conversation, which cannot distinguish two assignments reusing one child.

## Decision

Desktop and Telegram save complete bytes in the existing private immutable artifact store. Inbound members retain their name, MIME, length, hash, platform file identity, original input, and owner source. A combined input contains at most four files or images, each at most 8 MiB. Empty ordinary files are valid. Supported visual inputs remain JPEG, PNG, and WebP; only visual members require model image support. A failed download, invalid member, or incomplete upload rejects the complete input, including its text, before model admission.

Desktop's native host snapshots the selected ordinary files using a non-following, nonblocking descriptor, then verifies the same file and complete size. It uploads at most 64 KiB of original bytes per authenticated request without raising Personal's 128 KiB request limit. Upload identity and metadata remain fixed; exact chunk replay and completion are idempotent. `/desktop/inputs` admits the original body and the complete selected references. The separate attachment-bearing route makes older backends reject a new client instead of silently treating attachments as unknown fields in a text request. Native drafts retain their references, selection failure, and identity across reload; only an explicit discard or replacement clears a failed selection. A proven attachment rejection before admission releases the matching pending submission and leaves its draft failed for correction. A lost response or request-association conflict retains the original request and staged references for inspection.

Telegram documents use the existing verified bot `getFile` path and owner-private entry. Download validation compares platform size, HTTP length when present, and actual complete bytes; names and MIME are validated without silently truncating names. Media field presence prevents malformed attachment messages from falling through to text or approval parsing. Single files admit after complete staging. Telegram albums arrive as separate updates without a final-member marker, so an issued Send/Discard choice fixes the collected revision and member set before staging. The choice binds the original owner, chat, bot, generation, display, and opaque token. A timeout may coalesce the display but cannot admit an album. The original media message key remains the business input identity; a callback records selection authority separately. Stale choices and late members cannot enlarge an admitted input.

Recovery verifies complete originals before resuming a ready input, including the window after a committed Telegram receipt and before submission. Admitted inputs waiting behind Main retain their exact inbox content and submission even before a user entry exists. A withdrawn queued input retains its original bytes and unanswered submission, but never becomes eligible for a work grant. Desktop timeline, live events and complete-content pages project the verified original Telegram caption and attachment metadata; model history keeps the reconstructible attachment descriptors.

Main receives reconstructible attachment descriptors and visual references. It uses an explicit list of artifact references when delegating or appending a work instruction. The host verifies each attachment's admitted origin against the current owner entry and persists an immutable grant bound to that work and instruction. Earlier files remain selectable after ordinary clarification or an answer to Main's saved question from the same native profile or original IM account and generation. A business answer retains its verified source and permission; it does not approve an operation. Seeing another entry's descriptor in shared main history does not authorize selecting it. The assigned child receives only those references, with original and note inputs reconstructed from persisted grants.

Active attachment reads and publication resolve the exact work, including a reused child's current assignment. Historical output verification resolves the retained grant belonging to the original publication. A later work without a grant cannot read or publish an earlier attachment or cause the host to restore its visual bytes in a new model request. Attachment-derived artifact and history pages retain their work tag through later history reads; both recorded request input and actual provider payload apply the same withholding. History and previous reasoning remain intact; this scope controls new payload restoration and artifact access, not retroactive confidentiality. A required attachment extension makes older executables reject profiles containing these new semantics, and canonical child configuration retains it and the attachment reader after reopening.

Requested originals and generated files use the existing `publish_output`, validated report coverage, authenticated Desktop delivery, and original-owner Telegram send ledger. Attachment admission grants read access to selected immutable bytes, not write permission, control authority, other work's library, or another recipient. Business operations and delivery keep their independent outcomes; an unknown send or failed download does not repeat a successful operation.

Main's attachment delegation schema names direct `publish_output` registration for an explicitly requested unchanged file. The requested name and selected artifact travel in the work instruction; returning a file does not require a base64 answer, manual hash calculation, another read, or a business write. This guidance lives in the current tool schema so prior admitted attachment descriptors retain their immutable identity.

Admitted originals, unresolved submissions, and new native staging remain retained. No cleanup UI or quota system is added. Existing legacy image expiry applies only after establishing that no submission references the staged bytes. Filesystem publication and durable admission remain separate commits; an unreferenced private file can survive a failed commit without becoming a model input.

## Alternatives considered

- Reuse the complete Coding attachment ledger: it already supports bounded snapshots, but its task and core SQLite ownership do not match Personal durable. Reuse the native picker and immutable artifact primitives while retaining Personal source records.
- Grant access to the selected local path: simpler transfer, but later reads can observe changed content and expose neighboring files. Snapshot the selected bytes instead.
- Seal Telegram albums after a quiet interval: avoids a confirmation button, but a late fifth or failed member can arrive after text has executed. An explicit choice defines the input boundary.
- Give the child all main artifacts: reduces parameter passing, but opens other inputs and assignments. Persist only Main's selected immutable references.
- Add a new attachment output sender: makes inbound and outbound files look symmetrical, but duplicates the accepted publication and unknown-send rules. Extend original eligibility in the existing output path.

## Consequences

Uploads, source checks, work grants, and reconstruction add bounded metadata and verification work. Complete originals remain available after an edit or delivery failure, while indefinite unbound staging can accumulate disk usage. Ordinary files are byte-readable; no PDF/Office parser, transcription service, or video understanding is introduced. Telegram multi-file submission needs one confirmation because its API cannot establish album completeness. Native dialogs, configured models, real Telegram transfers, and Linux execution need acceptance beyond offline fixtures.
