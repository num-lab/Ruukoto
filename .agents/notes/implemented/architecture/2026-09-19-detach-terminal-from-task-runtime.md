# Agent Note: The backend owns tasks; the terminal owns interaction

Status: implemented

[Single-product cutover](2026-11-10-single-product.md) supersedes this note’s Personal, dual-product and legacy-import scope. Retained software-work constraints below remain active; retired-product mechanisms and evidence are historical, not current commands, compatibility requirements or acceptance passes.

[User queue controls](../feature/2026-10-30-coding-user-queue.md) changes manual pause, resumption and continuation entries; [report delivery](../feature/2026-10-30-coding-report-delivery-boundary.md) replaces internal-report FIFO. Those decisions own the changed dispatch contracts. Client disconnection still leaves backend execution running, and persistent acceptance remains unchanged.

Original identifier: ADR 0002. [Late-response cleanup](../bug-fix/2026-10-24-tui-exit-late-response.md) adds animation cleanup after client exit without changing detached backend ownership. [Coding message control](../feature/2026-10-28-coding-message-control.md) extends queue ordering and guidance.

This note owns backend/client lifetime for the sole software-work runtime. Core profile bootstrap now owns storage activation and layout/instance binding; old Personal runtime and protocol details are historical.

## Problem

The owner requires tasks to continue after closing the terminal. TUI is also only one entry: project maintenance, QQ and Telegram need to submit and inspect work. If TUI owns the execution loop, closing it kills tasks and each new entry needs its own executor. Tasks need an owner independent of every interaction entry.

Two failures must then remain distinct. Losing a client connection does not affect the task; a backend or server crash interrupts execution, potentially after an external operation has taken effect. Automatic replay could repeat that side effect.

## Decision

- **The backend owns execution; clients may disconnect and reconnect.** One backend schedules tasks and persists state/events, with a separate Pi SDK instance per conversation. TUI is an authenticated local client; it creates no SDK session, loads no model credentials and directly reads neither backend SQLite nor session JSONL.
- **Daily startup is on demand.** On macOS/Linux development machines, ordinary TUI entry starts an absent backend. TUI exit and terminal loss neither stop it nor cancel tasks; `ruukoto stop` explicitly stops it.
- **Managed development is different.** `npm run dev` owns its process group and stops its backend/UI on exit. Development frontends never independently spawn a backend; [development launcher](../process/2026-10-09-dev-launchers.md) owns that contract.
- **Tasks serialize within a conversation and may run concurrently across conversations.** New messages become persisted `queued` tasks before FIFO dispatch, not volatile SDK follow-ups. Concurrent tasks must not conflict on working directories: realpath plus device/inode identity covers symlinks and mount aliases, and an occupied directory leaves the task queued. [SubAgent work copies](2026-10-04-subagent-worktrees.md) owns claims. Conversation serialization does not serialize the entire assignment: SubAgents execute in their own conversations under [work delegation](2026-10-03-work-delegation-subagent-task.md).
- **Interruption is explicit.** Control `interrupt` ends current execution and persists owner pause; `cancel` cancels selected work. TUI exposes `/interrupt`, `/cancel` and `/resume-queue`; later input creates a new task, never an executable continue. `/quit` exits the client, not the backend.
- **Shared-runtime restart preserves records and requires owner-directed continuation.** One startup transaction marks old `running`/`awaiting_confirmation` tasks `interrupted` with `backend_restart`, makes pending approvals `stale`, and preserves queued order while pausing affected conversations with the same reason. The owner explicitly uses `resume-queue` (`resume_queue` on control). [SubAgent restart recovery](2026-10-05-subagent-restart-recovery.md) owns queued-delegation exceptions; [runtime documentation](../../../../docs/modules/runtime.md) describes recovery order.
- **Unknown external effects are never replayed automatically.** The tool ledger records unconsumed approvals as known not executed, interrupted reads as incomplete without write effect, and host-family results by their original host-operation IDs. Other potentially effective operations become `effect_unknown` and emit `task.tool_effect_unknown`. Recovery replays neither model calls nor tools. `continue` creates a new task with `resumes_task_id`, new submission authority and no inherited approval. Confirmation is the normal restricted choice; the owner may explicitly select full access, and the current submission/default-mode policy governs the new task. Continuation fabricates neither tool results nor a verbatim replay of old input. Unknown effects require owner verification or an explicit decision to execute again.
- **Disconnect, restart and shutdown are different events.** Disconnect removes subscriptions only. Reconnect restores observation without approving, continuing, resuming queues or starting another backend. Explicit stop first rejects new submissions and pauses dispatch, then interrupts active tasks, stops tools and persists before closing; queued input remains. Process signals and control `stop` share shutdown. TUI distinguishes connection state from interruption reasons and labels unknown effects as unknown, not safely retryable failures.

## Coding on-demand startup

Ordinary TUI startup requests on-demand startup through `packages/control/src/ensure-backend.ts`. Bare `ruukoto`, workspace paths and `--session` share it; demo/help/read-only discovery does not bootstrap or connect. Managed development only connects to its launcher-owned backend.

- **Probe and reuse.** A connectable socket is not readiness. Owner authentication followed by a valid `ping` response with `pong: true` and `stopping: false` establishes a reusable backend, without fetching a snapshot/subscribing. Probe and client share token precedence: `RUUKOTO_OWNER_TOKEN`, then `RUUKOTO_OWNER_TOKEN_FILE`, then control-directory `owner.token`. No token means no credential to try, not an exception.
- **Do not spawn after a definitive rejection.** Authentication rejection proves a backend exists and asks the owner to check the token; protocol mismatch reports both versions and upgrade guidance, not token changes. Stopping or invalid readiness responses likewise do not authorize a second instance. Transport loss, timeout or absent credentials do not prove the backend still exists: check the socket again, guide the owner if still connectable, and spawn only if unreachable.
- **Detach.** Spawn the fixed `apps/ruukoto/bin/ruukoto.mjs server` with the complete raw child profile environment. Append output to `ProfilePaths.spawnLogPath`; the child’s lifetime is independent of TUI.
- **Converge concurrent starts.** Core preparation/activation and the backend instance lock admit one winner. A lock-race loser’s own exit code, not shared log text, identifies contention; probe the expected activated instance until ready. Missing/malformed ownership or unverifiable process identity rejects rather than treating an ownerless lock as stale.
- **Fail explicitly before entering the connection state machine.** A non-lock early child exit followed by failed readiness probes in the grace window reports startup failure and the log tail written since this attempt began. Missing-model output adds `ruukoto config` guidance. Deadline expiry is separately labeled a timeout and does not kill a process that may still be the initializing winner. All startup failures exit nonzero.
- **Spawn once per TUI startup.** Later disconnections use backoff reconnect only. Reopen TUI if an unavailable backend must be started again. Normal restart recovery still runs: interrupted facts, paused queues and unknown effects do not become execution authority merely because a client starts or reconnects.
- **Use the current product execution policy.** Coding now defaults to and accepts only `native` for restricted execution. The old `container` default and `RUUKOTO_EXECUTION_BACKEND=local` escape are superseded by [native execution](2026-10-10-native-execution-sandbox.md). Full access uses the launching account without a task sandbox under [full-access semantics](../feature/2026-10-12-full-access-current-account.md); no legacy backend override is needed.
- **Manual operation shares the same lock.** `ruukoto server --data-dir ... --agent-dir ...` runs in the foreground and rejects a duplicate instance just like an on-demand start. After replacing a checkout during upgrade, stop the old backend; the next TUI starts the new code.

## Alternatives considered

- **Run the execution loop inside TUI.** Pi's interactive model was the owner's experience reference; a single process avoids connection recovery, event synchronization and daemon management. It fails the requirement that tasks survive terminal exit and serve other entries, so TUI uses backend task APIs instead. Original provenance: offline `.scratch/personal-agent/spec.md` round 2 and `.scratch/personal-agent/issues/04-tui.md`.
- **Use SDK follow-ups as the input queue.** The SDK already supplies a queue, avoiding host scheduling code. Its in-memory lifetime loses accepted inputs and order on restart and cannot expose a persisted paused queue for the owner. Persist requests first, then dispatch FIFO. Provenance: offline `.scratch/personal-agent/issues/02-runtime.md`, implementation step 2.
- **Restart the backend automatically during reconnect.** This could recover from a crash without reopening TUI, but connection loss is not authorization for another launch, and reconnect storms could repeatedly spawn. Startup remains an explicit entry action. Provenance: offline `.scratch/agent-direction/issues/02-coding-daemon.md`.
- **Serialize starts with another client lock.** It would avoid racing backend children, but duplicates arbitration already guaranteed by the backend instance lock. Let losers exit with a dedicated code and reuse the winner.
- **Add spawning/failure/retry states inside TUI.** The owner could repair startup without leaving the interface, but a nonzero exit with the relevant log tail and recovery guidance supplies the needed capability without another UI state machine. Reopen after repair.

## Consequences

Tasks survive terminal/client loss, and new entries share backend execution rather than building their own loops. Restart preserves interruption, queue order and uncertainty without repeating potentially committed side effects. Coding does not require a preinstalled service unit.

Separate processes require connection recovery and event synchronization. Persisted events have monotonic sequence numbers; handshake supplies a consistent snapshot/cursor, replay fills from that cursor, and clients deduplicate or resynchronize gaps. Submission retains a client `request_id`; after a lost response, original-key verification/retry resolves to the original task rather than creating another. See [control](../../../../docs/modules/control.md).

Backend management needs an instance lock, explicit stop, readiness probes and failure classification. The ordinary Coding backend consumes resources after TUI exit until stopped, including during upgrades. Shared-runtime crash recovery also costs owner intervention: continue interrupted tasks, resume paused queues and verify uncertain effects. These costs enforce non-replay rather than silently completing work.

An unavailable backend is not automatically restarted during an open TUI. `spawn.log` is shared; a byte offset excludes earlier output but concurrent terminals' output inside the same startup window can still appear in the tail. Exit classification does not depend on that text. Strict per-attempt log isolation would require separate log files.

## Verification

- `verification/foundation/test/04-sessions.test.ts` drives two sessions concurrently in one host, checking independent subscriptions/history/state. `git show 28c033f7:verification/foundation/test/06-rpc.test.ts` retains historical cross-process Pi exploration; the product did not adopt that RPC design and [test reduction](../testing/2026-10-24-test-suite-reduction.md) removed it from the active suite.
- `test/04-crash-recovery.test.ts` kills a real backend child with SIGKILL and checks an external marker count: restart retains interruption, leaves queues paused and adds no effect. State assertions alone cannot prove non-replay.
- `test/02-idempotency-reconnect.test.ts` and `test/12-reconnect-pending.test.ts` cover one task per lost-response input, gap-free replay, and terminal authentication/protocol failures.
- `test/72-on-demand-backend.test.ts` starts real bin/backend processes with files, sockets and SQLite, stubbing only the model. It covers entry gating, single-instance convergence/reuse, failure logs, token/protocol rejection, detached lifetime and reopening the same task without duplicate submission.
- The offline `.scratch/agent-direction/smoke-02.sh` exercised production-default `runTui` through a PTY: first launch, TUI exit without stopping the backend, reuse, explicit stop followed by relaunch, and nonzero failure without model configuration. It is historical evidence, not a retained executable or current acceptance claim.
