# Agent Note: 任务由后台进程持有，终端只负责交互

Status: implemented

原编号：ADR 0002

## 问题

拥有者要求关闭终端后任务仍然继续执行。交互入口也不止 TUI：项目维护与 QQ、Telegram 等 IM 入口同样要提交和查看任务。如果执行循环由 TUI 进程持有，关闭终端就会终止任务，每加一个入口还要各自持有一套执行。任务需要一个独立于任一交互入口的持有者。

任务独立于终端之后，有两类故障需要分开处理。交互连接断开时，任务本身没有受到影响；后台进程或服务器异常重启时，运行中的任务确实中断了，其中已经发出的外部操作是否生效无法确定，自动重放可能把同一副作用再做一遍。

## 决定

- **任务由后台进程持有，交互入口可以断开并重新连接。** 单个后台进程负责调度、任务状态与事件，每个会话使用独立的 pi SDK 实例驱动。TUI 是独立客户端：只经本机 Unix socket 加拥有者令牌连接后台，不创建 SDK 会话、不加载模型凭据、不直接读取后台数据库或 JSONL。任务生命周期独立于任一交互入口（TUI、CLI、IM 入口与 GitHub 事件来源）。
- **运行位置按产品区分，任务与交互终端分离的原则两个产品相同。** 运行位置分为开发机器与个人服务器，产品划分见[两个 Agent 产品](2026-10-02-two-agent-products.md)。
  - ruukoto 运行在专用 Linux 服务器上，后台由显式 `server` 或 systemd（`ruukoto-backend.service`）管理。它的 TUI 只连接已运行的后台，从不拉起后台：后台不在时，能取到令牌就进入有上限的退避重连，取不到令牌（例如后台从未启动、`owner.token` 还没生成）就打印指引并以 1 退出。
  - ruukoto-code 运行在开发机器上（macOS 与 Linux），首次打开 TUI 时按需拉起本机后台，无需预置服务单元。退出 TUI、终端断开都不停止后台，也不取消任务；只有显式停止（`ruukoto-code stop`）才结束后台。后台崩溃后保留记录并提示恢复，不自动重放结果未知的操作。拉起规则见下文「ruukoto-code 按需拉起后台」。
  - 开发入口（`npm run dev`、`npm run code`）是例外：后台由开发启动器管理，退出 TUI 或配置中心、Ctrl+C 或关闭终端时停止本次启动的整组开发进程，开发前端不自行拉起后台。规则见[开发启动入口](../process/2026-10-09-dev-launchers.md)。日常入口仍按上一条执行。
- **不同会话并行执行，同一会话串行处理任务。** 每个会话一次只执行一个任务。新消息默认排队：先持久化为 `queued` 任务，再按 FIFO 调度，不使用 SDK 的易失 follow-up 队列。不同会话并行以工作目录不冲突为前提：任务开始时占用其工作目录（按 realpath 与 dev/ino 识别，覆盖符号链接与挂载别名），目录已被占用的任务留在队列里等待释放，占用规则见[SubAgent worktree](2026-10-04-subagent-worktrees.md)。同一会话串行不等于整项工作串行：SubAgent 在各自的子会话里执行，见[工作委托与 SubAgent 任务](2026-10-03-work-delegation-subagent-task.md)。
- **提供明确的中断操作。** 控制面 `interrupt` 结束运行中或等待确认的任务并记为 `interrupted`；`cancel` 取消排队或活动任务。TUI 对应 `/interrupt [taskId]`、`/cancel <taskId>`、`/continue [taskId]` 与 `/resume-queue`，每个操作绑定具体的任务或会话。退出客户端与停止后台不共用一个操作：TUI 的 `/quit` 只退出客户端，停止后台是单独的 `stop` 命令。
- **后台或服务器异常重启后，恢复已保存的记录，把未完成的任务标为中断，由拥有者决定是否继续。** 启动恢复在一个事务内把原 `running`、`awaiting_confirmation` 任务定为 `interrupted`（原因 `backend_restart`），其未决确认请求标为 `stale`，失效的批准不得再执行。排队任务保留顺序，所在会话暂停自动调度（暂停原因 `backend_restart`），由拥有者用 `resume-queue`（控制面 `resume_queue`）显式恢复。SubAgent 排队委派任务的恢复另有规则，见[SubAgent 重启恢复](2026-10-05-subagent-restart-recovery.md)。逐步的恢复顺序见 [任务运行时](../../../../docs/modules/runtime.md)「后台崩溃恢复」。
- **不自动重放执行结果不明的外部操作。** 启动恢复按工具操作账本补记结果缺失的操作：审批未消费的记为已知未执行（批准不跨重启执行），只读工具记为未完成且无写入效果，宿主工具族按宿主操作 ID 核实账本；其余可能已产生外部效果的记为 `effect_unknown`，并发 `task.tool_effect_unknown` 事件。恢复不重放任何模型调用或工具操作。拥有者继续时，`continue` 创建带 `resumes_task_id` 的新任务：默认请求确认，旧批准不继承（拥有者可显式重新选择完全访问），不补造工具结果，也不原样重放旧输入。结果不明的操作须先由拥有者核实，或由拥有者明确决定再次执行。
- **交互连接断开与后台执行故障是不同事件。** 客户端断开只移除事件订阅，不取消任务，也不触发恢复。重连只恢复观察，不发送 `resume_queue`、批准或继续，也不再次拉起后台；只有后台重启才走上一条的恢复路径。停止后台也不等于断开客户端：`stop` 先拒绝新任务并暂停调度，再中断活动任务、回收工具进程、落盘后关闭，排队输入保留；进程信号与控制面 `stop` 走同一条关闭路径。TUI 分别显示任务的中断原因与连接状态，结果不明的操作标为「效果未知」，不显示成可以安全重试的失败。

## ruukoto-code 按需拉起后台

只有日常 ruukoto-code 的 TUI 入口按需拉起（`packages/control/src/ensure-backend.ts` 的 `tuiSpawnsBackendOnDemand`，且没有开发重载状态标记）。`ruukoto-code`、`ruukoto-code <路径>` 与 `--session` 都经过这一步；`--demo` 不连后台，也不拉起。ruukoto 不在此列：服务器上的后台由 systemd 与专用后台账户管理，TUI 不越权启动它。

- **探测与复用。** socket 可连且令牌认证握手通过才算后台在运行，此时直接复用，不启动第二个实例。探测与客户端使用同一令牌来源：`RUUKOTO_OWNER_TOKEN` → `RUUKOTO_OWNER_TOKEN_FILE` → 控制目录 `owner.token`；都取不到时视为没有可试的凭据，不抛错。
- **后台明确拒绝时不拉起。** 令牌认证不通过说明后台其实在运行，给出令牌核对指引；协议版本不兼容显示版本与升级指引，不核对令牌，也不拉起（不兼容版本不是拉起能解决的问题）。传输中断、超时或无凭据不算后台在运行的证据：重判一次 socket，仍可连就给令牌核对指引，不可连才拉起。曾经连上过不代表后台仍在。
- **拉起。** 拉起的是 detached 并 unref 的 `server` 子进程，标准输出与错误追加到 `<controlDir>/spawn.log`；就绪后打印一行提示并进入界面。拉起的后台与 TUI 生命周期无关。
- **并发拉起。** 两个终端同时打开时，由后台实例锁 `<dataDir>/runtime.lock` 收敛为单个实例，不另设客户端锁。败于锁竞争的进程以 `INSTANCE_LOCK_EXIT_CODE`（42）退出；TUI 只按本进程子进程的退出码归属判定，不读共享 spawn.log 的内容做分类，继续探测到胜者就绪后按复用进入（不算本进程拉起）。无法核实持锁身份（例如 `ps` 不可用）不算锁竞争，以普通退出码 1 按启动失败给出人工处理指引，锁原样保留；遗留锁（PID 已死、PID 被无关进程回收、`owner.json` 缺失或损坏）按安全规则接管。
- **失败状态明确。** 拉起失败一律打印错误并非零退出，不进入连接状态机。服务进程以非实例锁原因提前退出、宽限窗口后探测仍不通过 → 「后台启动失败」，附本次启动写入的 spawn.log 尾部；尾部是未配置可用模型时，提示先运行 `ruukoto-code config`。到期限仍未就绪 → 等待超时，单独标注，不杀进程（胜者可能仍在就绪途中）。
- **只在 TUI 启动时拉起一次。** 运行中断线按退避重连，重连只恢复观察，不会再次拉起后台；后台不可用需要再拉起时，重开 TUI。
- **拉起即正常后台启动。** 异常中断后的恢复照常执行（标记 `interrupted`、暂停队列、效果未知不重放），拉起与重连都不构成重新执行授权。拉起的后台沿用产品默认执行后端：ruukoto-code 为 `container`；需要 `local` 时在环境中显式设置 `RUUKOTO_EXECUTION_BACKEND=local`，生效时打印无隔离警告。
- **手动后台与升级。** `ruukoto-code server --data-dir … --agent-dir …` 前台运行，与按需拉起共用同一实例锁，谁在运行谁生效，重复启动被拒绝。升级替换检出后经 `ruukoto-code stop` 停下，下次打开 TUI 以新代码拉起。

## 备选方案

- **由 TUI 进程直接持有执行循环** — 这是 pi agent 交互模式的形态，拥有者也以 pi agent 为体验参考；任务与界面同进程，不需要处理连接恢复、事件同步与后台进程管理。不选，是因为关闭终端就会终止任务，不满足拥有者「关闭终端后任务仍应继续」的要求；之后加入的项目维护与 QQ 入口也要求任务生命周期独立于任一交互入口。TUI 因此只经后台任务接口交互，不在 TUI 内持有执行循环。（见原决定；[personal-agent spec](../../../../.scratch/personal-agent/spec.md) 第 2 轮回答；[personal-agent issue 04](../../../../.scratch/personal-agent/issues/04-tui.md) 目标）
- **用 SDK 自带的 follow-up 队列承载排队消息** — SDK 已提供排队，宿主不必自建队列。不选，是因为该队列只在内存中，后台重启即丢失已接受的输入，也无法在重启后保留顺序、暂停调度并交给拥有者恢复。新消息先持久化为任务请求，再由宿主按 FIFO 调度。（见 [personal-agent issue 02](../../../../.scratch/personal-agent/issues/02-runtime.md) 实施计划第 2 条）
- **运行中断线时自动重新拉起后台** — 后台在 TUI 打开期间崩溃，可以不用重开 TUI 就恢复。不选，是因为连接丢失不是重新执行授权，拉起应当是拥有者打开界面的明确动作；自动重拉还会在重连风暴里反复拉起。拉起只发生在 TUI 启动时一次，后台不可用时重开 TUI 即可。（见 [agent-direction issue 02](../../../../.scratch/agent-direction/issues/02-coding-daemon.md)「取舍说明」）
- **另设客户端锁串行化并发拉起** — 客户端先抢锁再拉起，可以避免多个后台进程竞跑。不选，是因为后台实例锁已经保证同一数据目录只有一个后台，再加一把客户端锁只是重复仲裁；竞跑的败者以专用退出码退出，TUI 等胜者就绪后复用即可。（见 agent-direction issue 02「实现方式」）
- **在 TUI 内扩展「拉起中」「拉起失败」状态并原地重试** — 拉起失败时拥有者不必离开界面。不选，是因为失败即退出已经足够：错误信息附 spawn.log 尾部与修复提示，修复后重开 TUI 即可，额外的状态机没有带来新能力。（见 agent-direction issue 02「取舍说明」）

## 后果

- **收益**：关闭终端或断开连接不影响任务执行；TUI、CLI、IM 入口与 GitHub 事件共享同一套任务生命周期，新增入口不需要自带执行循环。后台重启后，中断事实、排队顺序与结果不明的操作都保留下来，不会把可能已生效的外部操作再执行一遍。ruukoto-code 不需要预置服务单元，打开 TUI 即可使用。
- **代价：连接恢复与事件同步。** 客户端与后台分属两个进程，需要一套恢复机制：持久事件带单调序号，握手返回一致的快照与序号并按游标补发，客户端按序号去重、发现缺口时重新同步；提交携带客户端保存的 `request_id`，应答丢失后重试返回原任务。协议细节见 [控制面](../../../../docs/modules/control.md) 与[控制面协议图解](../../../../docs/visual/control-protocol.html)。
- **代价：后台进程管理。** 需要实例锁防止两个后台写同一数据目录，需要独立的停止路径，ruukoto-code 还需要拉起、探测与失败分类。ruukoto-code 的后台在退出 TUI 后继续占用资源，直到显式 `ruukoto-code stop`；升级替换检出后也要先停下后台。
- **代价：恢复需要人工介入。** 后台重启后任务不会自动完成：中断的任务要由拥有者 `continue`，暂停的队列要 `resume-queue`，结果不明的操作要拥有者核实。这是不重放原则的直接代价，换来的是不重复产生副作用。
- **已知上限**：运行中后台崩溃时，TUI 只会退避重连，不会自动恢复后台，需要重开 TUI。spawn.log 是共享追加日志，启动失败时附带的日志尾部只按字节偏移截取本次启动写入的段落，同一窗口内其他终端的并发输出仍可能混入；失败分类只看本进程子进程的退出码，不受此影响。要严格隔离，需改为每次拉起写独立日志文件。

## 验证

- `verification/foundation/test/04-sessions.test.ts` 在同一宿主进程里并行驱动两个会话，断言事件可分别订阅、历史与状态互不串用；`verification/foundation/test/06-rpc.test.ts` 验证跨进程驱动 pi 并从事件流还原回复。
- `test/04-crash-recovery.test.ts` 用真实后台子进程加 SIGKILL 制造崩溃，以外部标记计数为断言：重启后中断事实保留、排队任务不自动启动、标记计数不增加。不重放是关于副作用次数的保证，只看状态字段证明不了。
- `test/02-idempotency-reconnect.test.ts` 与 `test/12-reconnect-pending.test.ts` 覆盖应答丢失后同一输入只对应一个任务、重连补发无缺口、认证失败与协议不兼容时停止重连。
- `test/72-on-demand-backend.test.ts` 拉起真实 bin 后台进程（真实文件、socket 与 SQLite，只有模型打桩），覆盖门控、并发拉起收敛为单实例、已运行不重复拉起、启动失败附日志尾部、令牌不符与协议不兼容不拉起，以及关闭客户端不停止后台、重开看到同一任务且不重复提交。
- [smoke-02.sh](../../../../.scratch/agent-direction/smoke-02.sh) 在 pty 下走真实 `runTui` 生产默认路径：首次拉起、关闭 TUI 后台不停、再开复用、`ruukoto-code stop` 后重开再度拉起、无模型配置时非零退出。
