# Agent Note: Complete tool execution inside a worker and a task-scoped execution unit

Status: implemented

Original identifier: ADR 0004.

The container and dedicated-execution-account design below is historical. [Personal native execution](2026-10-12-personal-native-sandbox.md), [Coding native execution](2026-10-10-native-execution-sandbox.md), and [current-account full access](../feature/2026-10-12-full-access-current-account.md) supersede those launchers: both formal restricted product entries accept native only; Docker workers, image configuration, and the container type are retired. The complete-worker, bounded-protocol, approval-consumption, and verified-stop principles remain. Original deployment parameters and validation are preserved as rationale, not current setup instructions.

## Problem

[Explicit access modes](../feature/2026-09-19-explicit-access-modes.md) require technical constraints on file, command, network, and credential access. Model-driven read/edit/write/bash tools can run arbitrary shell descendants. Running them in the backend exposes its identity, model credentials, database, and control plane. Replacing only the upstream low-level file operations is insufficient: pi `0.85.1` called host `fs.access` through `resolveReadPathAsync()` before custom `ReadOperations`.

Reusing a restricted environment across tasks also carries temporary mounts, environment, surviving processes, and one-operation grants into later tasks. The identity used for full access determines whether commands can read owner authentication material. Reusable approvals or replaceable approved arguments defeat authorization; silent backend fallback makes a supposedly restricted task unrestricted.

## Decision

### Continuing execution principles

- Put complete upstream coding-tool execution, including path resolution and shell descendants, inside `packages/agent/src/tool-worker/`. Keep SDK session orchestration, model calls, approvals, and persistence in the backend. Do not resolve tool paths in the host before delegation. The original worker accepted only read/edit/write/bash; [controlled file search](../feature/2026-10-21-controlled-file-search.md) extends that list. Unknown names are rejected. The worker accepts calls and returns data, receives no approval/mode/control-plane authority, and loads no executable project-discovered extensions.
- Pass structured arguments, never shell-interpolate them into launcher commands. Backend model credentials and network access do not become restricted project-shell capabilities. Restricted workers receive a minimal environment without credentials, SSH agent, proxies, or `RUUKOTO_*` control variables. Full-access environment inheritance now follows the current-account decision instead.
- Use newline-framed JSON on stdio (`tool-worker/protocol.ts`): host `init`, `tool_call`, `abort`, `shutdown`; worker `ready`, `data`, `result`, `fatal`. `MAX_FRAME_BYTES` is 4 MiB; `DATA_CHUNK_BYTES` is 512 KiB and payload chunks are base64. Writes use backpressure and calls have deadlines. The host-generated operation ID, `opId`, is the correlation identity; model-generated SDK call IDs are only upstream tool arguments.
- Declare host tools `executionMode: "sequential"`. Raw output is associated by tool name with its current call; concurrent same-name calls would cross streams. Capture raw bash output through `BashOperations.onData` and file content through Operations wrappers before upstream truncation. Persist task artifacts before producing bounded model views with artifact references.
- Stop and verify the entire execution unit, not merely the launcher CLI or shell parent. Keep directory occupancy and report `task.tool_process_unreaped` (or `mode_switch_unverified`) when exit cannot be established. Register startup occupancy before readiness so cancellation covers startup too. Crashes do not prove descendants exited; restart recovery retains interrupted-task occupancy. [Unverified worker stop](../bug-fix/2026-10-11-preserve-unverified-worker-stop.md) owns result caching, propagation, terminal state, and recovery.
- Consume structured approvals once through a SQLite conditional update (`Store.consumeApproval`): task active, saved/current permission versions both equal the expected version, and approval unused. `consumed_at` means execution began. Execution arguments come entirely from the immutable approved request, not a new model/worker payload bearing its approval ID.
- Run approved `request_file_access` and `http_request` operations in the trusted executor (`execution/approved-ops.ts`), not by widening the worker. File operations `lstat` every component, reject symlinks, open with `O_NOFOLLOW`, and verify `fstat` dev/ino against the approved object. Writes also recheck the original sha256; changes require a new request. Backend data, service credentials, and control-plane directories remain excluded. HTTP follows no redirects and performs no retries, pins the approved resolved address against DNS rebinding, and injects credentials only for the configured target-host binding. Approving one request never gives shell general network access.
- Fail explicitly with `execution_unavailable` when a required execution backend or identity is unavailable; never silently run as the backend or choose another backend. `local` uses a current-account process group with no isolation, warns accordingly, and is a development/test injection, not evidence of restriction.

### Original task-container design

Confirm and auto-review shared one restricted Linux container per task; Plan tasks used auto-review. The trusted image was `ruukoto-worker`, configured by `RUUKOTO_WORKER_IMAGE` with default `ruukoto-worker:latest`, built from `deploy/worker-image/` with pi `0.85.1` and no privileged entry point. These paths and variables are retired historical configuration.

Containers used non-root `--user <uid>:<gid>` (default 1000:1000). Native Linux bind mounts did not map UIDs, so `RUUKOTO_CONTAINER_UID/GID` selected the owner's IDs for workspace writes. They dropped all capabilities, enabled `no-new-privileges`, used a read-only root, a separate `--tmpfs /tmp:rw,nosuid,size=64m`, and `--network none`.

Only the workspace, explicitly granted paths (`:ro` for read-only grants), and host-pinned read roots such as bounded SubAgent sources and shared Git directories were mounted. Mounts retained the host absolute path, also used as cwd; parents outside mounts were empty. This kept prompts, historical paths, and `request_file_access` consistent. No host credentials, SSH agent, proxies, control socket, or container-management socket were passed. Secrets already inside mounted project files were not hidden.

Container names were `ruukoto-task-<taskId>-<backend pid in base36>`, with same-name residue removed before startup. Workers were reused only within a task, keyed by task ID, mode, and grants; changed mode/grants required verified stop before replacement. One-operation approvals did not mutate mounts or become reusable shell authority. Workspace files persisted. Stop used `docker kill`, `docker rm -f`, and a successful listing proving the name absent; listing failure did not prove exit. The cgroup covered `setsid` and signal-ignoring descendants. The historical managed registry tracked `process_group`, `container`, `systemd_unit`, and `starting` identities.

The original full-access design ran outside containers under a dedicated execution account, separate from owner and backend and in neither account's groups. `createSystemdLauncher` used `systemd-run --pipe --wait --uid --gid --unit ruukoto-exec-<taskId> --property KillMode=control-group`. Root-owned fixed-argument sudo wrappers (`ruukoto-exec-launch.sh`, `ruukoto-exec-stop.sh`) were callable only by the backend; both `RUUKOTO_EXEC_LAUNCH_SCRIPT` and `RUUKOTO_EXEC_STOP_SCRIPT` had to be configured. Direct `systemd-run` was code-injected only, not environment-enabled. Project commands never ran as root or received a generic privileged launcher. Workspace ACLs granted entry without group membership; absent ACLs produced EACCES. This account had its existing OS permissions, not all owner files or isolation from its own files.

Originally, missing full-access entry configuration was rejected at submit/mode-switch time before task creation; Docker availability was discovered at worker launch, so an enqueued task's first tool call could fail without executing. Current entry behavior follows the successor decisions, not these retired checks.

### Historical platform evidence and successors

macOS containers ran in Docker Desktop's Linux VM through the real launcher, image, and `ToolWorkerHost`. VM mount permissions allowed uid 1000 to write despite host permission bits; inode numbers changed across the VM. LaunchSpec therefore omitted macOS workspace/read-root dev/ino and the worker checked paths, while host `taskWorkspaceFor` rechecked directory identity. Workspaces had to be in Docker file sharing (normally `/Users`, `/private`, `/tmp`). The proposed macOS dedicated full-access account/sudo wrapper was never deployed or verified and failed closed when absent.

SubAgent/worktree host-fixed bash used temporary confirm workers with host-pinned write/read/Git scope and `safe.directory`, not extra account privileges; see [worktrees](2026-10-04-subagent-worktrees.md) and [integration](../feature/2026-10-05-integrate-worktree-results.md). Native launchers retain the shared worker/protocol/approval/ledger/lifecycle but own host toolchains, real dev/ino, physical protection, per-unit TMPDIR, and macOS unverified-descendant occupancy.

Two old negative probes must not be reused as platform conclusions: Seatbelt rules require real paths (`/tmp` is not `/private/tmp`), and Ubuntu userns profiles match the formal bwrap executable path, not a temporary extracted binary. Corrections remain in [macOS isolation](../../../../verification/foundation/results/native-macos-report.md), [launchd](../../../../verification/foundation/results/native-macos-launchd.md), and [Linux startup](../../../../verification/foundation/results/native-linux-report.md) reports. Probes do not replace integrated product acceptance.

Normal bash remains temporary. [Coding session background processes](../feature/2026-10-21-coding-background-processes.md) use independent executions that outlive the originating task; the personal portion of [the background-lifecycle proposal](../../proposed/feature/2026-10-14-bash-background-lifecycle.md) remains proposed.

## Alternatives considered

- **Replace only low-level Operations.** Upstream factories and the Gondolin example support this with no worker protocol, but the verified upstream pre-Operations path lookup still runs outside restriction. Move the complete tool instead.
- **Run the whole pi session through `pi --mode rpc` inside restriction.** Foundation probes proved cross-process driving and response reconstruction, but this would place model credentials/network beside project shell, while the restricted container had no network. Separate tool execution from session orchestration.
- **Reuse containers per session.** This saves startup time, but leaks temporary mounts, environment, descendants, and one-use capabilities between tasks. Use task-scoped units.
- **Run full access as the owner.** The original proposal separated owner and backend UIDs and made the owner's toolchain available. A same-UID `test -r` on a 0600 `owner.token` still succeeded, proving impersonation possible. That motivated the historical dedicated account; the later current-account decision explicitly revises this trust choice rather than claiming the old guarantee remains.
- **Fall back to the backend when configuration is missing.** Tasks keep working, but expose backend data and credentials while appearing restricted. Fail closed.
- **Add the execution account to the owner's group.** Easier than per-workspace ACLs, but potentially exposes authentication material and violates the original identity split. ACLs were chosen. Submission-time permission preflight was also rejected because the backend cannot determine another UID's access reliably.
- **Temporarily enable shell networking or inject generic credentials after HTTP approval.** Existing scripts could run unchanged, but domain/port restrictions do not constrain methods or side effects on that service. Execute one fixed method/target/headers/body in the trusted executor; unsupported needs remain explicit limits or require owner-selected tools/full access.
- **Retry the whole denied script with greater privilege.** Fewer interruptions, but earlier workspace or external effects may already have happened. Return the denial and require a new concrete operation instead.
- **Mount at `/workspace` and translate paths.** A stable container layout is attractive, but mode-dependent prompts invalidate caching/history, granted paths remain unresolved, and routing cannot translate arbitrary bash source. Preserve host paths.
- **Use Landlock, bubblewrap, systemd sandboxing, Gondolin micro-VMs, OpenShell, or Docker Sandboxes initially.** These could avoid a container runtime or better preserve the host environment, but were unverified on 2026-09-19. Containers met the then-known requirements without premature backend abstraction. Native successors now own the revised choice for both products.
- **Use macOS `sandbox-exec` instead of Docker Desktop.** Built-in tooling was attractive; the 2026-10-02 rejection relied on an invalid path-alias probe and was corrected on 2026-10-08. Only the native decision's actual descendant-verification limits remain relevant.

Historical offline provenance: `.scratch/personal-agent/foundation-findings.md`, issues `03-tools-and-access.md`, `23-container-full-access.md`, `28-container-same-path-mount.md`; `.scratch/agent-direction/issues/03-execution-boundary-proof.md`, `26-native-sandbox.md`, and `native-agent-comparison.md`. These records are not current task or deployment entry points.

## Consequences

Complete path resolution and shell execution inside restriction protect backend data and credentials. Task-scoped units prevent environment/capability inheritance; immutable once-consumed approvals prevent substituted or replayed operations; explicit startup failure avoids false safety claims. The protocol and pre-truncation capture require maintenance, and sequential calls sacrifice same-turn concurrency.

Historical costs included Docker/image startup and cleanup, Docker Desktop VM differences, three identities, fixed privileged wrappers, and workspace ACLs. The historical account-isolation guarantee and undeployed macOS full-access limitation do not describe current full access. Native limitations belong to the successor note. `local` remains unisolated; cached stop results never substitute for real backend exit verification.

## Verification

Original regression references were `test/07-real-tools.test.ts` for real read/edit/check/fix execution, artifacts, detached clients, startup cancellation, and fail-closed launch; `test/08-approvals.test.ts` for one-use file/HTTP approvals, symlink/object/content/protected-path rejection, redirect/credential boundaries, permission-version and terminal-task rejection, and pinned DNS; and the then-current `test/10-access-modes.test.ts` / `test/73-desktop-execution.test.ts` for retired container/systemd configuration. Those historical assertions must not be presented as current full-access behavior.

Real container evidence came from `verification/foundation` Linux probes and the historical `scripts/linux-isolation/container-worker-smoke.mts`: network denial, invisible host paths, non-root/read-only/capability limits, same-path mounts, stopped descendant heartbeats, and removed containers. The historical tx run used `ruukoto-exec` and received `Permission denied` reading the owner token. These require real backends and cannot be proved by model stubs or local workers.

Current interface regression references are `test/10-access-modes.test.ts`, `test/73-desktop-execution.test.ts`, `test/100-worker-stop.test.ts`, and `test/101-native-linux-scope.test.ts`, with integrated SDK/SubAgent/worktree evidence in the native decision. No runtime, container, or platform tests are rerun by this documentation migration.
