# Agent Note: Main application data uses a separate database, controlled tools, and destructive-change approval

Status: implemented

Original identifier: ADR 0009.

[Personal durable application data](2026-10-18-personal-durable-app-data.md) owns personal wiring, native provenance, and two-database receipt recovery. This note retains the data-store contracts and the original shared-runtime consumer rules. [Current-account full access](../feature/2026-10-12-full-access-current-account.md) supersedes earlier general account, environment, approval, and derived-task authorization rules where specified there.

## Problem

The owner requires main to decide whether todos, reminders, habits, and other personal records need structure, and to declare that structure rather than use host-prebuilt business tables. Non-destructive changes can run automatically; dropping tables/fields and bulk migrations require confirmation, with provenance and versions for every change. These records are neither runtime metadata nor long-term preferences, conventions, decisions, and experience. Exposing schema changes in core `ruukoto.db` would expose tasks, approvals, events, and credential bindings; keeping everything in conversation or memory would not provide recoverable structured data.

The original requirement is recorded in the historical offline `.scratch/daily-agent/spec.md` items 8-9 and issue `02-main-data.md`, not a current task entry point.

## Decision

1. Store application data in `<dataDir>/agent-data/main.db`, using `node:sqlite`, WAL, `synchronous=FULL`, and foreign keys. Create its directory with 0700 inside the protected data root. The shared Runtime manages open/recovery/close through `initAppData`; storage lives in `packages/agent/src/app-data/store.ts`. Register the stable application-instance ID in core `meta` as `app_data.main_instance_id`. Recovery verifies file existence and identity first. A registered but missing, mismatched, or corrupt database disables the capability and records `app_data.unavailable`; never create an empty substitute or replace the binding. The databases have no shared transaction and are not joined with `ATTACH`.
2. Expose six controlled tools: `app_data_define_table`, `app_data_migrate`, `app_data_query`, `app_data_insert`, `app_data_update`, and `app_data_delete`. In the shared assembly only the main session category has `ToolCategory.app_data`; assembly, activation, pre-send checks, and invocation agree. Every invocation rechecks the host task/session/project/main binding. An unavailable database supplies no tools. Storage-boundary validation covers names, types, size, relationships, and versions; tool JSON schemas are hints, not enforcement. SQL identifiers come only from the validated catalog and remain quoted; values are bound parameters.
3. Keep host storage-format version 1 separate from main's `schema_version` and change `revision`. Each write atomically commits business/schema changes, version increments, and an append-only audit receipt keyed by unique `hostOpId`. Audit, constraint, or disk-write failure rolls back the business change. A repeated operation returns its original result for identical normalized parameters and conflicts for different parameters.
4. Use the existing approval bridge for table/field/unique-index removal, multi-row writes, and row rewrites. `ApprovalScope.kind = app_data_change` fixes database instance, task and operation IDs, table, operation kind (`drop_table`, `drop_field`, `drop_unique_index`, `multi_row_write`, `rewrite_rows`), schema/revision, normalized parameter digest, affected count/IDs/row versions, and before/after schema definitions. After approval, recheck main identity, task state, permission version, and application versions; any change invalidates approval, which cannot grow to cover newly appeared rows. Consume once and execute the immutable saved arguments. No application transaction or write lock remains open while waiting.
5. The original shared design treats destructive application changes as an explicit full-access exception: their personal-data impact is independent of execution privileges. Auto-review's `classifyForReview` does not handle `app_data_change`, so it sends this scope to the owner without a review-model call, rather than copying MCP's full-access bypass. Current full-access precedence is owned by the linked successor, not inferred from this historical exception.
6. Provide bounded structured queries, not arbitrary SQL, JOINs, or aggregates. Page by `_id`; AND filters support scalar comparisons, null checks, and bounded membership. Host constants limit default/max rows to 50/100, output to 64 KiB, candidate scanning to 1,000 rows / 1 MiB, and total duration to 2 seconds (`QUERY_LIMITS`, `QUERY_TIMEOUT_MS`). Each query starts a fixed read-only child entry with `process.execPath` (`node --import tsx query-child.ts`); timeout kills it with SIGKILL and waits for exit. Writes remain in the host. The child provides terminable computation, not a complete OS sandbox.
7. Before generic unknown-effect recovery, reconcile missing application-write results against receipts: receipt means committed; consumed approval with no receipt in a verifiable database means uncommitted; missing/corrupt/unverifiable database means `effect_unknown`. Never replay a write. `appDataOpCheck` and the shared tool-operation ledger use the same classifier for stop and restart: all approvals unconsumed means known not executed; `app_data_query` has no write effect and a missing result is a read interruption; remaining writes use receipts. Scan terminal tasks too. A failed core result write triggers immediate operation-ID reconciliation; if that also fails, restart retries reconciliation. Conditional `tool_ops` updates and events share a core transaction, preventing duplicate recovery publication.

## Storage and validation

- Host-owned `app_meta` holds storage/schema versions, revision, and instance ID; `app_tables` holds validated business definitions/indexes and creation/update revisions; `app_audit` holds unique `op_id` receipts matching core tool-operation IDs. Receipts include host-assigned task/session/agent/time, schema/revision, reason, normalized operation, affected scope, bounded result, and schema before/after `definitions`. Internal tables are not freely queryable/writable business tables.
- Distinguish initialization from existing-file validation. Missing `app_tables`, `app_audit`, or format-version metadata in an existing database is `storage_corrupt`, never a reason to recreate tables: an empty replacement audit table could falsely prove an old write uncommitted. Newer formats yield `storage_version_too_new`. A crash after first file creation but before core registration can resume by registering the existing file's own ID only if no binding exists.
- Names match `[a-z][a-z0-9_]{0,47}`; reject `sqlite_`, `app_`, reserved `_id`/`_version`, and duplicates. Types are `text`, `integer`, `real`, `boolean`, `json`, `datetime`. Validate/encode before writes: safe JS integers, finite reals, validated UTC ISO datetimes, serializable JSON with byte/depth limits, and distinct missing/null/type handling rather than SQLite coercion.
- Host-maintained `_id` is a monotonic non-reused integer; `_version` is the row version. Relations point only to registered tables' `_id` in the same application space and use `ON DELETE RESTRICT ON UPDATE RESTRICT`. Dependents must be handled explicitly, never cascaded.
- Ordinary/unique indexes reference existing scalar fields only, without expressions or partial indexes. Constraint failures such as duplicate values roll back index creation. Dropping an ordinary index is automatic; dropping uniqueness is destructive because it weakens a constraint.
- Every write has a nonempty `reason`. Define-table requires `expected_schema_version`; an existing table conflicts rather than hiding a different definition behind `IF NOT EXISTS`. Migrate accepts an expected version and bounded structured `add_field` (nullable only), `add_index`, `drop_index`, `drop_field`, `drop_table`, or `rewrite_rows` (explicit IDs and expected row versions). The whole call is one transaction and one revision increment; no SQL, transformation scripts, implicit coercions, or arbitrary expressions.
- Insert is atomic for the batch and returns host row IDs/versions and database versions; one invalid row rejects the batch. Update/delete require explicit IDs and expected row versions, never unconditional whole-table writes. Insert/update/delete check optional `expected_schema_version` when supplied.
- Table creation, nullable-field addition, index creation, ordinary-index removal, bounded insert, and versioned single-row update/delete are automatic. Multi-row update/delete and rewrites require approval. One destructive step makes an entire mixed migration approval-bound, including unique-index removal in a multi-table migration. Rejection, cancellation, mode switch, invalidation, or restart never executes an old request.
- Check expected schema versions inside transactions, row versions for update/delete, and the original schema/revision again after destructive approval. Return identifiable conflicts with current versions; do not overwrite or silently recompute/retry. Successful schema operations advance schema version; transactions with actual changes advance revision; failure advances neither.
- `LIMITS` is host-owned: 64 business tables; 32 fields, 8 indexes, 4 fields/index, and 10,000 rows/table; 16 KiB/field, 32 KiB/row, 64 KiB/write arguments, 100 rows or 16 migration steps/call, and 1 KiB/reason. Update/rewrite limits cover the full merged row. Measure actual UTF-8/JSON bytes. Limit rejection changes neither data, row versions, revision, nor audit.

## Query contract

`mode` is `schema`, `rows`, or `changes`. Schema pages discover tables or read one definition/indexes/relations/current versions without relying on remembered conversation. Rows query business records. Changes pages inspect audit records or look up an `op_id` receipt. All are paginated and byte-bounded.

Rows support projection and AND operators `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `is_null`, `not_null`, `in` (at most 100 values), ordered by `_id`. Iterate candidates after `_id > cursor`, accumulating bytes row by row rather than first collecting `.all()`, then filter/project inside that window. Version read and scan share one read transaction.

Results contain `scanned`, `complete`, `next_cursor`, `schema_version`, and `revision`. Cursors bind table, query digest, and versions; changes between pages cause a cursor conflict and require a fresh query. Candidate/row-budget truncation advances to the last processed candidate, so empty sparse windows still progress. If output bytes leave matching rows unreturned, advance only through the last returned position so those rows remain for the next page. A projected record above 64 KiB is `record_too_large` and requires a narrower projection, avoiding an empty-page loop. Explicitly excessive requests are rejected; legitimate exhausted pages say `complete=false` rather than claiming completeness.

`query-child.ts` opens the database read-only and revalidates the host's structured request. Its environment retains only PATH and the database path, not owner token, model credentials, or core handles; IPC requests/responses/stderr are bounded. The 2-second budget includes startup, execution, and collection. Timeout/cancellation kills and waits; Runtime close reaps pending queries. Process `exit` can precede trailing stdout, so no-response settlement waits for stdio `close`; valid trailing output must not be lost. Timeout still waits for exit without extending the original computation budget.

## Ordering and related decisions

Core records intent and consumes approval if needed; application storage commits data plus receipt; core records result plus event. These are separate transactions. A committed application write whose core result failed is never relabeled unexecuted or automatically repeated.

Execution and rejection leave `task.tool_intent` / `task.tool_result`. Identity, validation, budget, and timeout failures additionally record `app_data.rejected` with source class, tool name, and code, not oversized input or entire private records. Structured todos/reminders/habits belong here; preferences/conventions/decisions/experience remain in MemoryStore. Records do not become memory or control instructions automatically.

The [scheduler](2026-09-24-scheduler-outbox.md) reads bounded row-field references `app_data:<instance ID>/<table>#<row>.<field>` without prebuilding reminder tables. The historical [personal instance import](2026-10-05-personal-instance-import.md) copied the entire database plus WAL with sha256 verification and its core instance binding; it is not the new durable entry's import policy.

## Alternatives considered

- **Prebuilt todos/reminders/habits tables:** simpler validation/migration/integration, but the owner explicitly chose main-defined structure. Extend narrow scheduler reads for actual needs instead.
- **A namespace inside core:** could co-commit business writes and operation records, but would expose core schema evolution and security-sensitive tables. Independent storage accepts receipt-based recovery instead.
- **Open via core `Db`:** reuses WAL/FULL/foreign-key setup, but its constructor installs the complete core schema and migrations. Use `DatabaseSync` directly, without extension loading or model-selected database paths/SQL.
- **`ATTACH ruukoto.db`:** makes both databases visible to one connection/transaction, but violates the requirement that application tools cannot reach core tasks, approvals, events, or credentials. Keep explicit staged commits and reconciliation.
- **In-process `Promise.race` or SQLite `timeout`:** avoids child startup, but synchronous `DatabaseSync` cannot be interrupted by a promise and its timeout bounds lock waiting, not query execution. This was also constrained by the then-supported Node 22.19 API; current Node requirements have since changed.
- **Arbitrary SQL/JOIN/subqueries/aggregates or a generic optimizer:** more expressive, but cannot pre-bound scanning or accept unvalidated identifiers. Declared indexes serve constraints and future demonstrated needs, not a new optimizer.
- **`WHERE ... LIMIT N` as scan control:** simple SQL limits returned rows, not examined rows under sparse matches. Bound candidates first.
- **Cascading foreign keys:** convenient cleanup, but silently turns one deletion into a multi-row write that bypasses approval. Use RESTRICT.
- **Copy MCP's full-access bypass:** consistent with the original general mode semantics, but the original owner requirement separately confirmed destructive application changes. Later mode-policy revisions must be explicit, as in the linked successor.
- **Conversation as the only business database:** no new storage, but cannot independently rediscover schema and structured records after restart.

## Consequences

Core schema stays independent of business evolution and inaccessible through application tools; newer/corrupt storage fails rather than resets. Every write has an atomic local receipt, allowing stop/crash/result-failure reconciliation without replay. Legacy coding/chat/QQ and ordinary development sessions do not gain this API; retired roles/groups are archives, and main SubAgent read-only tools do not include it. Data grants, grantedPaths, and full access do not implicitly broaden this API's identity scope.

Costs are child startup latency, cross-database recovery windows, and the original destructive-change interruption. Missing/unverifiable application storage leaves unresolved writes `effect_unknown` and disables the capability. Query expressiveness and host size limits are deliberate. The read-only child and API checks are not file isolation; protected data roots and the [execution boundary](2026-09-20-tool-worker-per-task-container.md), with its native successors, protect the file. Local workers cannot prove cross-account isolation.

## Verification

`test/28-main-data.test.ts` maps to real store/query-child/Runtime paths: restart/binding, version conflicts, RESTRICT, atomic rollback, hostOpId idempotence, hostile names/limits, sparse paging, real timeout termination, main-only tools and forged identities, destructive approval across the original three modes, approval-time version changes, inaccessible core/internal tables, audit rollback, receipt recovery, missing/corrupt/mismatched storage, and refusal to recreate missing audit tables. Fault injection (`AppDataStore.faultNextWrite`, core result failure, deleting an audit table before reopen) is necessary for dual-store windows and verifies table bytes/receipts/results/events, not just task status. `test/64-tool-op-ledger.test.ts` covers classifier order; `test/62-tool-availability.test.ts` covers categories. This migration does not rerun these runtime tests or claim current full-access semantics from historical assertions.
