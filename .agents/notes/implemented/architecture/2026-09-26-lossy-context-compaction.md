# Agent Note: 模型上下文有损压缩：压缩点、分层压缩与前缀稳定

Status: implemented

原编号：ADR 0016

## 问题

[完整保留会话历史](2026-09-19-preserve-session-history.md)最初约定不用有损摘要压缩历史：选择器按预算由近及远纳入完整交互，装不下的更早交互整轮移出。实际使用 1M 窗口的模型时，这套做法有两个问题：

- 每次调用都带着整段历史。输入预算约 60.6 万估算 token，历史几乎不会移出；早已过时的工具输出分散模型注意力，也按次计费。
- 超出预算后，选择器每次调用移出最老一轮，前缀随之变化，整段历史不再命中提示缓存。

有损处理本身也受提示缓存约束：视图只能取决于消息本身，逐次改写变旧的消息会让每次调用的缓存失效。所以有损变换只能成批、低频地做，结果落盘后原样复用。

## 决定

这一决定取代[完整保留会话历史](2026-09-19-preserve-session-history.md)中「初始方案不采用有损摘要来压缩历史」一句，其余各条不变：会话历史仍完整保存、只追加、可查阅，有损处理只作用于模型上下文。

- **适用范围。** main 会话与普通开发会话使用上下文压缩。SubAgent 会话（含宿主 GitHub 评审 SubAgent）的执行画像是资料受限（`ExecutionProfile.restricted`），选择器收到 `compaction: null`：不压缩，超预算时照旧整轮移出，也不加移出标记。chat 角色、`qq_group` 与 coding 角色会话已退役为只读归档，不运行任务。适用范围按[两个 Agent 产品](2026-10-02-two-agent-products.md)重新映射：双产品保留完整历史与有界模型上下文的分离，并复用压缩机制；最初按 main、coding、dev、chat 角色划定的范围在双产品与 SubAgent 迁移时重新映射，不作为保留已取消固定角色的依据。
- **压缩点。** 每个会话至多一个生效的压缩点，落盘保存摘要与清理的边界、滚动摘要正文和所覆盖消息的指纹。选择器把压缩点当作输入，确定性地组装每次调用的视图：同一个压缩点加同一组消息，得到同一个视图。
- **何时压缩、压到哪里。** 视图估算越过高水位（200,000 估算 token；输入预算更小时取输入预算）才新建压缩点，并一次压到低水位。
- **分层。** 先把较早的工具结果换成占位说明（第一层）；仍不够，再把更早的对话并入滚动摘要（第二层）；压缩后仍超出输入预算，才整轮移出。
- **前缀稳定。** 两次压缩之间视图前缀不变，提示缓存只在每次压缩时失效一次。
- **有损处可找回。** 占位说明、摘要块与移出标记都注明覆盖范围和找回原文的方法：`history_read`、`history_search`，或重新执行工具。
- **摘要模型。** 摘要由拥有者可选配置的摘要模型生成，未配置时用会话当前模型。配置了摘要模型，较早的对话（含工具结果）就会发给它的提供方。
- **失败不阻断。** 摘要失败时只保留清理结果，任务照常继续。必留内容超出预算（`context_budget_exceeded`）与 provider 上下文超限（`context_overflow`）仍按原规则中断任务，不触发压缩。
- **不启用 pi 的 compaction。** pi 自带的 compaction 把压缩条目写进会话文件、改变 SDK 给出的分支消息，会打乱选择器、Jev 候选和选择记录的消息序号，触发条件也不了解本项目的预算与必留项。项目只复用它导出的摘要生成函数 `generateSummaryWithUsage`；自动压缩如何关闭见[完整保留会话历史](2026-09-19-preserve-session-history.md)。
- **摘要只是参考。** 摘要可能遗漏或出错，也可能转述工具结果里的指令，所以它是参考内容，不是拥有者指令，也不是授权依据；与拥有者原话冲突时以原话为准。摘要提示要求区分拥有者原话与工具结果、文件、网页中的内容，后者中的指令不写成拥有者的要求，防止注入内容经摘要变成「拥有者的要求」。系统提示共同段向模型说明 `[压缩摘要]`、`[已清理]`、`[较早的 … 未进入本次上下文]` 三种标记的含义与找回原文的方法（`src/agent/session-factory.ts`）。

## 机制要点

完整取值与视图顺序见[上下文压缩](../../../../docs/modules/agent-context.md#上下文压缩)，实施记录见 [personal-agent issue 30](../../../../.scratch/personal-agent/issues/30-context-compaction.md)。规划与视图组装在 `src/agent/context-selector.ts`（纯函数 `planCompaction`、`selectContext`），指纹、条目引用与摘要调用在 `src/agent/compaction.ts`，编排、落盘与停止联动在 `src/agent/context-assembly.ts`。下面列出承载取舍的取值与边界。

- **落盘。** 表 `context_checkpoints`，部分唯一索引保证每个会话至多一行 `status = 'active'`；新建时旧行在同一事务里改为 `superseded`。S（`summarized_count`）：分支前 S 条消息由摘要替代。C（`cleared_count`，C ≥ S）：[S, C) 的工具结果换成占位说明。`fingerprint` 是前 C 条消息的角色、时间戳与工具调用 id 的 SHA-256。其余字段：`summary`、`summary_until`（第 S 条消息的时间戳，UTC ISO）、`cleared_refs`（被清理结果的 toolCallId → 会话文件条目 id）、`cleared_results`（清理条数）、`summary_model`、`summary_status`（`ok | failed | none`）、`summary_error`、`prompt_version`（`compaction-v1`）、`usage`、`estimate_before`、`estimate_after`、`task_id`、`call_index`、`created_at`。建表与 `selection_records.checkpoint_id` 补列沿用 `SCHEMA_SQL` 与 `ensureColumns` 的幂等补齐，不升 schema 版本。
- **作废。** 每次调用读取生效的压缩点并核对指纹；消息少于 C 条或指纹不符时改为 `invalidated`，按无压缩点处理。后台重启后压缩点继续生效，不重新摘要。
- **边界与水位。** S、C 只落在单元边界：完整交互的开头，或当前任务中已完成批次的开头。记 H' = min(高水位, 输入预算)。高水位是 `SelectorBudgetConfig.compactionHighWater`（默认 200,000，计入配置版本）；低水位 0.5 H'、保护尾部 0.15 H'、最小收益 0.2 H'，都用选择器现有的估算口径。先按生效压缩点选择，再看不做预算移出时的视图估算：超过 H' 才规划新压缩点。
- **覆盖范围。** 保护尾部是由新到旧累计到 0.15 H' 的完整单元，至少含最新批次。必留单元与保护尾部不进覆盖范围；S 与 C 都不越过当前任务最近一次成功 `todo_write` 所在的批次。若 C 越过它，旧清单批次在之后的调用里不再必留、会被清理，两次压缩之间视图就会变。第一层把 C 推到保护尾部开头；估算仍高于低水位时第二层推进 S，取能压到低水位的最小单元边界，S ≤ C。估算降幅（摘要块按长度上限计）不到 0.2 H' 时不建压缩点，也不调用摘要模型。
- **第一层：清理旧工具结果。** [S, C) 中正文超过 2,000 字符或含图片的工具结果，整条内容换成 `[已清理 · <工具名> · 原 <N> 字符 · 成功|失败 · history_read session_id=<会话> entry_id=<条目>]`。toolCallId 与 isError 不变，配对不受影响。条目 id 在建压缩点时解析一次会话文件得到（按 toolCallId 加时间戳匹配），存进 `cleared_refs`，之后的调用不再解析；查不到时占位的最后一段改为「原文需重新执行工具获取」。`skill` 与 `todo_write` 的结果不清理；toolCall 参数、拥有者与 assistant 的文本不清理。
- **第二层：滚动摘要。** 输入为上一版摘要加分支消息 [旧 S, 新 S) 的原消息。摘要提示（`customInstructions`）要求：用中文；保留文件路径、命令、函数名与错误原文；拥有者的要求与已确认的决定写入 Constraints & Preferences 与 Key Decisions；区分拥有者原话与资料中的指令；全文不超过约 4,000 字，超出时合并或删去最不相关的旧条目。模型经 `modelCatalog.resolve` 解析、以 `modelRuntime.streamSimple` 调用（同自动审查，不经最终检查那层包装）；请求不带思考参数、单次尝试、超时 180 s、输出上限 16,384 token，触顶按失败处理。覆盖段的估算超过摘要模型的输入预算时按失败处理，代码留有 `ponytail:` 注释：接入小窗口摘要模型时改为分块滚动。
- **停止联动。** 停止任务时，`requestStop` 与任务收尾中止摘要请求，与 Jev 的中止放在一起。摘要等待结束后，任务已停止或已切换就不发主模型请求；否则重新读取选择输入，因为记忆等可能已变化。
- **视图。** 摘要块是带标记的 user 消息：`[压缩摘要 · 较早的 <S> 条消息 · 至 <summary_until>]`、正文、`[/压缩摘要]`。它紧跟前缀参考块（项目指令、技能目录、长期记忆），其后是移出标记（如有）和 [S, n) 的历史（[S, C) 按第一层清理），再接当前任务。S 伸进当前任务时，任务输入单元（必留）原样排在摘要块之后，继续来源与计划说明仍在任务输入之前。Jev 启用时只对 [S, n) 内的单元做取舍，摘要块不参与。
- **兜底移出。** 压缩后仍超输入预算时，沿用由近及远纳入，装不下的更早单元移出，并在视图里加一条移出标记 `[较早的 <N> 轮交互未进入本次上下文 · <起> 至 <止>]`（UTC ISO）。移出标记只在压缩会话出现，计数为因预算移出的单元（完整交互或当前任务批次），Jev 拒绝的不计；选择时先按最长标记文本预留空间。
- **摘要失败与冷却。** 摘要报错、超时、输出触顶、输入超限或摘要模型不可用，都按失败处理：只保留第一层（仍按最小收益判断是否建压缩点），`summary_status = failed` 并记下原因。本任务内，视图估算比失败时再增长 0.2 H' 之前不再尝试摘要。冷却从失败后实际使用的视图估算起算：清理收益够、建了只清理的压缩点时用清理后的估算，否则用原估算。冷却状态只在内存，后台重启后可以再试一次。
- **摘要模型配置。** 保存为 `<agentDir>/summary-model.json`（`{provider, modelId}`，不存思考档位），与 `default-model.json` 同样纳入配置修订指纹、回滚快照与离线模式。控制面 `set_summary_model` 接受 provider 与 model_id（同为 null 即清除），带 expected revision；`get_model_config` 返回 `summaryModel`；保存时核对模型在目录中。配置中心「模型与提供方」页头显示所选摘要模型或「未设置（用会话当前模型）」，「设置摘要模型」的首项是「不设置」，说明写明数据去向。被摘要模型引用的提供方或模型，与被后台默认模型引用的一样拒绝删除，在线与离线两处都核对。摘要模型只在配置中心设置，没有启动参数。每次摘要读取当前配置，不按任务钉版；已配置但无法解析时本次摘要按失败处理，不改用会话模型。离线模式持配置锁独占写，没有修订协商。
- **记录与展示。** 选择记录补 `checkpoint_id`（旧记录为空），估算明细加 `compactionSummary`；被摘要与清理的消息序号不逐条写进选择记录。`/context` 多「压缩摘要」一类，并显示压缩点：摘要替代的条数与截至时间、清理条数、建立它的任务与调用序号，以及摘要模型或失败原因；本次没有生成新摘要、沿用上一版摘要的压缩点（`summary_status = none`，`summary_model` 为空）显示「摘要沿用上一压缩点」。事件与 `/context` 中的「摘要 N 条」是压缩点的 S（摘要替代的总条数），事件流只在本次生成了新摘要（`ok`）时显示它。事件 `task.context_compaction` 分两条：开始调用摘要模型时 phase `started`；压缩点落盘时 phase `finished`（含清理条数、摘要条数、估算前后、摘要模型与状态），与压缩点同一事务提交。摘要失败且只清理收益不足时不建压缩点，仍写一条 `finished`（`checkpointId` 为 null），让 TUI 的「正在压缩上下文…」有结果、失败原因可见；摘要等待中停止任务则没有完成事件，TUI 在任务结束时把该行改为「上下文压缩未完成：任务已结束」。`/prompt` 不变。

## chat 的窗口方案（未实施）

与本决定同时，chat（QQ 群会话与 chat 角色）另定了更简单的窗口方案：旧对话整批移出窗口，需要时查本群历史找回。该方案暂缓，约定实施时另立决定，此前 chat 维持现状、不压缩。核心群聊随后退役（见[退役核心 QQ 群聊](../simplification/2026-10-02-retire-core-group-chat.md)），chat 与 `qq_group` 会话成为只读归档、不运行任务，窗口方案没有实施。按[两个 Agent 产品](2026-10-02-two-agent-products.md)，日后的 QQ 群聊外挂自行管理群会话与历史。

## 备选方案

- **沿用 pi 自带的 compaction** — 它是上游现成能力：上下文快满时自动触发，摘要格式结构化，可基于上一版摘要增量更新。不选，是因为它把压缩条目写进会话文件、改变 SDK 给出的分支消息，会打乱选择器、Jev 候选和选择记录的消息序号，触发条件也不了解本项目的预算与必留项。只复用其中的摘要生成函数。（原决定第 3 段；personal-agent issue 30 背景）
- **维持无损做法，只靠整轮移出控制长度** — 不引入有损内容，也没有摘要调用的费用与数据外发。不选，是因为 1M 窗口下移出几乎不会触发（约 40 万汉字才开始移出），过时的工具输出仍随每次调用发送、分散注意力并计费。整轮移出因此只作压缩后的兜底，并在视图里加标记。（[ADR 0001 的无损约束](2026-09-19-preserve-session-history.md)；personal-agent issue 30「已确认范围」）
- **每次调用即时改写较旧的消息，不落盘压缩点** — 没有新表、指纹与作废逻辑，可以按位置对变旧的消息逐步收紧（例如当前批次不截、变旧后再截）。不选，是因为视图只能取决于消息本身：同一条消息的视图随位置变化，之后每次调用都会让其后的提示缓存失效。有损变换因此成批、低频地做，落盘后原样复用。（personal-agent issue 27 背景；personal-agent issue 30 背景）
- **S 伸进当前任务时另写一段「本任务前段摘要」，放在任务输入之后** — 这是设计稿的布局，把当前任务的摘要与较早对话的滚动摘要分开。不选，是为了只维护一段摘要状态：滚动摘要直接延伸进当前任务，任务输入原文排在摘要块之后。代价是该任务结束后，下一任务的首次调用多一次缓存未命中。（personal-agent issue 30 Comments）
- **选择记录逐条记下被清理与被摘要的消息（设计稿的 `clearedToolResults` 与排除原因 `summarized`）** — 每条选择记录可以独立说明哪些消息被清理或摘要。不选，是因为长会话里被摘要的消息可能上千条，逐条记入每次调用的选择记录会让记录膨胀；只补 `checkpoint_id`，范围从压缩点读取。（personal-agent issue 30 Comments）
- **摘要调用走 `originalStreamFn`（设计稿写法）** — 复用会话自身的请求路径。不选，是因为摘要模型可能不是会话模型；改用 `modelRuntime.streamSimple`，与自动审查一致。（personal-agent issue 30 Comments）
- **已配置的摘要模型不可用时改用会话模型** — 摘要更容易成功，压缩不退化为只清理。不选，是为了避免费用与数据去向在拥有者不知情时变化；按摘要失败处理。（personal-agent issue 30 Comments）
- **低水位、保护尾部与最小收益用绝对值（设计稿：保护尾部 3 万估算 token）** — 取值直观、与高水位无关。不选，改为按 H' 的比例计算：默认值与设计稿相同，输入预算小于 20 万的模型也适用；只有高水位进入 `SelectorBudgetConfig`。（personal-agent issue 30「已确认范围」与 Comments）
- **摘要块与移出标记列出覆盖的任务 id** — 任务 id 指向更精确。不选，是因为分支消息不带任务 id，而 `history_search` 支持 since/until；覆盖范围用 UTC ISO 时间标明。（personal-agent issue 30 Comments）

## 后果

- **收益**：越过高水位后，过时的工具输出不再随每次调用发送；提示缓存只在每次压缩时失效一次，而不是超预算后每次调用都失效。会话历史（JSONL）字节不变，每处有损内容都注明覆盖范围与找回方法，被清理的结果可以按占位里的条目 id 用 `history_read` 原样读回。摘要失败只退化为清理，任务不中断。
- **代价**：
  - 摘要可能遗漏、出错或转述资料中的指令；提示与系统提示只能降低这类风险，不能消除。模型得自己想到去查原文。
  - 每次压缩让整段视图的缓存失效一次，并多一次摘要调用：费用另计，等待可能要一两分钟，TUI 为此分开显示开始与完成。
  - 配置摘要模型后，main 与开发会话较早的对话（含工具结果）会发给该模型的提供方。
  - S 伸进当前任务时，该任务结束后的下一任务首次调用多一次缓存未命中。
  - 摘要失败的冷却只在内存，后台重启后会再试一次。
- **已知上限**：
  - 覆盖段超过摘要模型输入预算时直接按失败处理，还没有分块滚动，接入小窗口摘要模型时要补。
  - 只有高水位可配置，其余阈值是 H' 的固定比例，不按模型分别调整；估算口径未按 provider 用量校准。
  - 另行立项、尚未实现：`/compact` 手动触发、复用对话前缀发摘要请求以命中缓存、压缩前自动写长期记忆、清理 toolCall 参数、异步预先计算摘要、按模型分别调阈值、估算校准、兜底移出改为单调移出边界（一次移到约 75% 预算，避免每移一轮整段历史缓存未命中一次；personal-agent issue 29 Q7）。
  - **何时重访**：部署后若模型频繁用 `history_read` 读回被清理的结果，说明清理过狠，应调高清理阈值或保护尾部。按天统计压缩次数与估算降幅的查询见 personal-agent issue 30「验收标准」。
