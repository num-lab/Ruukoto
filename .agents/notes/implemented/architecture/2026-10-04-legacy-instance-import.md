# Agent Note: Import legacy development data offline at the destination

Status: implemented

Original identifier: ADR 0022

## Problem

After [product separation](2026-10-02-two-agent-products.md) and [legacy workspace organization](2026-10-03-legacy-workspace-org-attribution.md), ordinary development sessions still shared the personal product's data directory with role-bound sessions, QQ groups, application data, schedules, and IM configuration. Organization mapping changes display ownership within one instance; it does not copy data across instances. Import therefore uses a separate preview, owner-confirmed plan, and apply flow, with plan-derived request identity and durable receipts.

## Decision

`apps/ruukoto-code/src/legacy-import.ts` and `ruukoto-code legacy-import` own the destination-side operation. Schema v28 originally introduced `instance_imports` and `instance_import_items`.

- Import is offline and Code-only, not a control-plane operation. `preview --from <source> [--plan file]`, `apply --plan file`, `revert <importId>`, and `list` hold the destination instance lock; preview and apply require its backend stopped. The owner starts it afterward and clients obtain fresh snapshots rather than relying on import-time broadcasts or cache repair.
- The source is always read-only. Refuse a live source backend or an unverifiable lock-holder identity. Copy `ruukoto.db` and its WAL sidecars into a temporary 0700 directory, operate on that copy, and delete it when the command finishes. Opening the source with a read-only SQLite connection is insufficient: WAL access can create `-shm`/`-wal` sidecars. Error paths must also leave every source file unchanged.
- Import only allow-listed ordinary dev sessions from selected source projects and their one-level SubAgents. Exclude role-bound sessions, QQ groups, and main data. Preserve row IDs so JSONL, `result_ref`, memory `source_refs`, and artifact references need no rewrite. A destination ID not proven by the ledger to belong to this source is a conflict, never an overwrite. Previously imported items from the same source are skipped. `TABLE_POLICY` explicitly imports or excludes every table with a reason; an unclassified new table rejects import.
- Keep incomplete history and invalid identities honest. Rewrite the stored session-file path to the destination `sessions/` directory and hash each available source file before import. Missing or damaged history is reported, not replaced with an empty file. Preserve the four project-root fields only when local realpath/dev/ino match strictly and no destination workspace owns the root. Otherwise clear them, preserve their original values and conflicts in the receipt, and retain a legacy source project. Organization mapping follows the existing mapping rules: preserve it, point to a same-root destination workspace, or clear it for later `project migration-preview`. An invalid session cwd remains browsable but existing identity checks refuse execution.
- Never replay imported work. Queued tasks become canceled; running/awaiting-confirmation tasks become interrupted with migration provenance. Operations that may have started without a recorded result, and their tasks, become effect-unknown; an operation blocked by unconsumed approval is known not executed. Pending and approved-but-unconsumed approvals become stale. Session full-access defaults downgrade to confirm. Imported SubAgents are closed using independent `closed_at`/`closed_by` fields, and their work directories are not copied. Starting the destination must not run old tasks or consume old approvals.
- Fail closed on cross-instance provenance. Import a project memory only when every version's sources are in the imported set or are owner notes. Import personal memories only when explicitly selected in the plan as owner-authorized publication. Other bodies remain at source and are listed as unresolved, not copied. Import data grants, including revoked state, only when both projects are imported; a grant crossing the instance boundary is recorded as inactive provenance in the receipt, not in `data_grants`. Never copy agentDir files (models/auth/default-model/credentials/skills) or QQ/Telegram tables. Preview names and differences without reading secret values. Jev configuration without its named destination credential binding is imported disabled for owner rebinding.
- Apply inserts all rows, ledger items, and the receipt in one destination transaction. Its revision hashes canonical full-row import data, file hashes, and destination conflict state. Source or destination drift after preview returns `revision_conflict`. The same request key and parameters return the original receipt; different parameters return `request_conflict`. Before copying, back up the destination with `VACUUM INTO` at `<dataDir>/migration/<importId>/target-before.db`. Copy via temporary names and rename; skip an existing same-hash file and reject a different one. An interruption before the transaction can resume with the same plan; a failed transaction rolls back together.
- Revert deletes only ledger-owned rows, event ranges, and hash-verified copied files, retaining a reverted receipt. New destination tasks, events, sessions, grants, organization references, or memory versions block revert and are individually reported: they are new facts, not migration debris. Product identity and the destination backup survive revert. Whole-database restore is a separate manual, backend-stopped operation described in the usage guide.

### Current compatibility limits

The original import upgraded a source snapshot and copied MCP configuration with missing-credential disabling. [Instance-scoped MCP](../simplification/2026-10-24-code-instance-mcp.md) supersedes those parts: source and existing destination must use the current storage format; old authorization/configuration is not converted, and MCP services and credentials remain instance-local. Current `TABLE_POLICY` and `rejectWorkflowImport` also reject unsupported source-bound execution state rather than silently dropping it. The historical v28 introduction is not a promise to accept a v28 database today.

Typed row transforms from an independent snapshot connection handle task closing, mode downgrade, paths, and disabled configuration; one destination transaction preserves atomic insertion without per-table CASE SQL. This does not claim database/file atomicity: file copy precedes the transaction and the ledger plus original plan provide recovery.

Online import, a TUI/config-center UI, incremental synchronization, agentDir import, effective cross-instance grants, and a generic bidirectional migration framework are out of scope. New source data is reported and may be imported again. The [personal direction](2026-10-05-personal-instance-import.md) has its own decision. [History preservation](2026-09-19-preserve-session-history.md) and [context compaction](2026-09-26-lossy-context-compaction.md) still apply: preserve history bytes and migrate checkpoints/selection records without rewriting the conversation.

## Alternatives considered

- Online control-plane import avoids downtime and reuses authentication, but adds event/cache consistency work. The owner selected offline import under the destination lock and reconnect-based snapshot recovery.
- ATTACH plus INSERT...SELECT provides a compact cross-database path, but its task closing, permission downgrade, path rewrite, and configuration disabling require error-prone per-table CASE expressions. Typed transforms retain the same transaction guarantees and history-byte fidelity.
- Read-only SQLite access to the source avoids copying first, but can create WAL sidecars. A copied snapshot is necessary for the stronger no-source-writes promise.

## Consequences

Imported data retains its IDs, source identity, and history bytes, with verifiable receipts and conditional revert. Both backends must stop; invalid cwd data is read-only, and import cannot restore cross-instance authority or missing credentials. Source changes are not synchronization, and new destination facts cannot be erased by revert.

Historical issue 21 evidence, formerly `.scratch/agent-direction/issues/21-migrate-coding-instance.md`, is offline provenance rather than a maintained task entry. It reported test/85 7/7, targeted regressions 123/123, and typecheck passing. Full npm test was 918/919: test/32 also failed on an isolated baseline because of its worktree-directory-name prerequisite. The historical smoke ran 7/7 on macOS and Linux via `ssh tx`, using real CLI/processes/SQLite/files/locks and a simulated model. A representative real-data preview/apply/start/read/revert copied 49 byte-identical files and left the source unchanged. That source had no personal memories/grants; those rules had logic-test coverage only. Test/81 once failed concurrently and passed 9/9 in isolation. These are historical results, not fresh validation of current format restrictions.

[Current-account full access](../feature/2026-10-12-full-access-current-account.md) governs account/environment, approval exemption, and derived authority; it does not remove the import-specific downgrade and non-replay rules.
