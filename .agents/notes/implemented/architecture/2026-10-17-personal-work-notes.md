# Agent Note: 个人追加说明由原工作按轮次接纳

Status: implemented

## 问题

[后台工作](2026-10-17-personal-background-work.md)只等待首次 Submission，随后停止子会话并释放占用。直接向长期子会话 steer 或 followUp，会在原回答结束后被收尾 abort 丢弃，或在身份复用后混入另一工作。[迁移方案](../../proposed/architecture/2026-10-17-personal-pi-durable.md)要求追加只属于当前工作，取消和恢复仍维持单工作占用。

## 决定

追加先在原工作 document 保存正文、宿主稳定键与来源，不直接 admission。原 WorkTask 在当前回答完成后顺序提交已接纳说明，每条使用原工作与追加键派生的请求键。每次收齐子会话后台执行后，最终事务重查取消和追加数；仍有新说明就继续原工作，否则与终态一起释放占用。追加与最终事务串行，因此不需要另一份运行状态或 closing 标志。完成结果指向最后接纳说明的回答，历史仍由原生记录持有。

接纳复核占用、活动任务、取消、原入口与同来源未知服务操作；正文不能改变原权限。模型变更仍要求当前唯一拥有者输入。Telegram 只接原已送达工作菜单的直接回复；CLI 用现有 pending 机制及独立 `pending-work-` 文件名前缀保留原工作及请求键（旧 CLI 不扫描，旧程序持锁时拒绝未知文件），丢失应答后只核实原键。新增扩展名让旧程序拒绝新记录，独立 `/work/notes` 接口使旧后台拒绝新 CLI 的追加而不会误投主聊天。恢复从最后已 admission 的轮次重接原键，不从首次回答重放 abort 在途追加；恢复前验证追加与来源、工具动作/参数及原生提交关系。任一轮失败停止后续说明，不能返回旧成功回答。

## 既有笔记审计

按追加说明、后台工作、Telegram 来源与最终回报检索 active notes。[模型工作](2026-10-17-personal-model-work.md)、[宿主控制](2026-10-17-personal-work-controls.md)、后台工作及迁移总方案部分重叠，各保留决定并互链。旧共享工作流的 owner input/final delivery 与 Coding 状态机仍适用原底座，不搬入个人实现；没有完全吸收或需要归档的记录。

## 备选方案

- 直接 steer：更及时进入当前生成，但空工具分析的最终边界可能先结束原 Submission，再开下一轮；原工作收尾会中止已接受说明。选择明确的轮次间顺序处理。
- 每条追加独立后台工作：更容易复用现有 Task，但会改变占用与取消归属，并可能把另一项工作塞入长期会话；保留同一 WorkTask。
- 追加时停止接纳的持久 closing 标志：方便提前冻结，但又增加故障恢复状态；追加不直接 admission，最终事务可复查列表并决定继续或结束。

## 验证

见[窄工单](../../../../.scratch/personal-pi-durable/issues/12-work-notes.md)的原键恢复、收尾竞争、取消与来源隔离用例；模型输入保留追加正文与完整工具定义。

## 后果

当前模型回答结束前追加不会进入生成，界面须说明时机。长工作会使同一业务 document 增长；先沿既有规模保留简单列表，有实际增长证据再优化。整项工作汇总、外部工具权限、真实 IM/模型与产品体验仍需后续验收。
