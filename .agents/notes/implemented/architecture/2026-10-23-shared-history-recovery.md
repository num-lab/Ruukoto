# Agent Note: 双端共用会话历史恢复

Status: implemented

## 问题

TUI 的 `app.ts` 与 Desktop 的 `code-state.ts` 各自持有历史窗口任务查询、任务详情与事件分页、缺失正文补读、请求代次和在途去重。修改恢复规则需要维护两份实现；桌面已独立修复首次显示时 trace 闪开，说明显示时序不能简单统一。

Desktop 还有已复现的旧代次失败路径：历史页已返回、list_tasks 尚在等待时安装新实例快照，旧查询随后失败，loadHistory 的降级 catch 仍会安装旧历史页。外层 run 丢弃旧错误，无法撤回已经安装的旧数据。探针观察到新实例的空 sessionViews 被旧会话及正文重新填入，readError 仍为空。

## 决定

新增 `packages/view/src/history-recovery.ts` 的 HistoryRecovery，集中任务窗口查询、任务详情和事件恢复、正文分页、恢复代次、任务游标与在途读取。它使用注入的只读请求能力，不打开连接或文件；ViewState 与 EventFlow 继续只安装输入，不主动请求。模块面向 Coding 的共享控制协议，正式个人 durable 不接入。

已有两个 adapter 是 TUI 的 ControlConnection 请求与 Desktop bridge 请求。共享模块只消费 list_tasks、get_task、read_task_events、read_history_entry 的具名类型；不依赖客户端错误类、Node、Electron 或完整 UI 对象。传输的 entry_not_found 由 adapter 按具名错误类型和 code 判别，其他失败保留给所属客户端展示；不解析 message。

### 共同读取与客户端展示

共享模块提供重置恢复代次、查找并安装窗口任务状态、恢复单项任务、补读单条正文，以及查询任务是否仍有缺失正文待确认的能力。并发任务恢复由调用方用已有 Promise.all 串联，不另加一个只转发的批量入口。任务和正文循环、游标、代次守卫和去重只保留一份。

read_history 的单次请求、历史页安装和显示阶段仍归客户端：TUI 先装历史并显示，再以全部已加载条目查任务；Desktop 先按本页条目查任务状态，再安装历史，最后补任务事件和已加载窗口的截断条目。Desktop 保留 settle 合并重绘、检查器刷新和通知；TUI 保留滚动锚点、输入历史补种、待办刷新及终端通知。客户端只串联共同能力，不再自行实现任务/正文分页。

正文读取保留两个实际策略：TUI 每页 48 KiB，只续读 assistant；Desktop 每页 64 KiB，续读所有角色。它们作为正文读取的页大小与续读角色条件传入，不以客户端名分支，不扩为通用恢复配置框架。共享的完成判定同时用于识别已完整加载条目和选择是否继续取页，避免调用处再复制判断。

缺失正文的 pending 事实随共享读取代次保存，Desktop 的 historyReady 只读取该事实以控制 trace：已在历史页中的条目补全不阻止收起，页外缺失条目在成功安装前始终未就绪；失败或 entry_not_found 不冒充成功，重置代次后丢弃旧事实。呈现 trace 的规则与动画留在 Desktop。TUI 不消费该就绪查询。

### 失败与代次

每次新快照都同步重置共享恢复代次和游标；客户端已有 generation 继续管理读历史页、滚动、命令、标签和其他独立请求，不由共享模块接管。所有异步恢复成功、失败降级及 finally 清理都必须核实自己所属代次，旧请求不能写新投影、清理新请求或改变新 pending 状态。

同一历史恢复从读页开始固定代次，窗口任务查询、客户端装页、任务事件与条目补读沿用它；阶段之间也可能换代，后续入口不得重新捕获最新代次来继续旧工作。实时单条补读或独立任务刷新才从当前代次开始。Desktop 的 read 持有错误呈现与检查器收尾，run 仅为历史页与摘要去重；任务和正文在途请求只由共享模块持有。旧 read/settle 的 finally 不在新代次触发检查器补种、diff 读取或重绘；新快照同步将 quiet 与 dirty 清零，旧恢复窗口不能压住新代次绘制。

修复 Desktop 的失败降级：只有当前代次的 list_tasks 失败才能先安装已读历史页，再展示错误；旧代次的成功与失败一律不安装，不恢复旧会话，也不污染新错误状态。这保留现行可用性降级，只补齐其遗漏的代次守卫。

任务详情 seq 只用于安装详情，不作为任务事件读取起点；任务事件初次从 0 开始，单任务各页串行、不同任务可并发。完整正文以 UTF-8 字节推进，首页从 0 开始，续页必须连续且总字节数稳定，满足完整性后才安装完整条目；异常返回具名 history_discontinuous 错误。TUI 的有效响应和续读范围不变，同时沿用 Desktop 现有的完整性要求，避免共用实现削弱校验。

条目暂未落盘可延后补读，其他条目错误按客户端原方式报告后继续处理后续缺失条目；不得把一个条目失败变成整个任务恢复链静默中断。任务状态/详情/事件读取失败仍由当前调用场景处理，保持 TUI 的分类提示和 Desktop 的 readError。

共享模块保留一个投影变更通知和一个单条补读失败通知通道。每页事件安装后可通知 TUI 渐进刷新，Desktop 继续用 settle 合并；通知不是逐阶段安装钩子，不把刷新、检查器和错误格式拆成多组回调。

## 备选方案

- 将读取直接放入 ViewState：调用最短，但破坏纯投影的职责与现有浏览器验证，连接和生命周期也会随之混入；采用独立模块。
- 在 control 包实现读取编排：贴近操作协议，但安装投影需要反向依赖 view 或注入大量细碎写回函数；view 已依赖 control 类型，放在 view 保持现有依赖方向。
- 共用一个固定首屏流水线：能再减少客户端串联，但会改变 TUI 渐进显示或破坏 Desktop 的 trace 恢复；保留两个真实展示时序。
- 只抽取无状态分页函数：文件会变短，但代次、游标和去重仍散落两端，旧失败污染的风险也不能集中审查；共同状态应随恢复职责迁移。

## 验证

`test/history-recovery.test.ts` 覆盖两种正文策略、UTF-8 多页、同任务和条目读取去重、事件游标从零开始、跨阶段换代、旧成功/失败与请求清理、未就绪事实及异常页拒绝。`test/37-view-browser.test.ts` 在无 Node 全局的 VM 中实际执行中文与 emoji 多页恢复。TUI 与 Desktop 的集成回归保留各自显示时序、滚动、命令历史、子会话与标签恢复。

`test/41-desktop-stream.test.ts` 覆盖同实例和跨实例的旧 list_tasks 迟到失败，验证旧正文、会话和错误不能重新出现，旧 finally 不触发检查器或重绘；当前代次失败仍显示历史并报错。另一条客户端用例核实单条正文损坏后仍安装后续条目，并保留失败条目的未就绪事实。撤去失败降级代次守卫的负向验证会重现旧正文覆盖与旧会话复活。

验收记录与具体命令见[工单](../../../../.scratch/history-recovery/issues/01-share-recovery.md)。真实 Electron/MyGo 与真实模型不作为这些确定性测试的已验证范围。

## 后果

两端共用任务窗口、详情、事件和正文恢复规则，原长文件只串联读取与显示阶段；没有改变控制协议、JSONL、schema、消息排序或图形样式。代价是维护独立恢复对象及其代次，客户端仍需守住本端历史页与显示收尾的代次；仅重置共享对象不足以保证安全。

只移动分页循环而保留两套状态会增加理解成本；反过来把首屏顺序、滚动和重绘并入共享策略会扩大接口。提取以共同恢复事实为界，客户端串联保持短而显式。

view 包的独立读取编排需要同步职责文档，但不获得创建连接的能力。所有请求仍由已有可信 transport 发出，不新增任意读取路径或自动重试。TUI 对不连续/总量变化响应的处理会更严格，这属于失败路径的完整性校验，正常正文范围和大小策略不变。
