# Agent Note: Personal file operations run on one worker thread

Status: implemented

## Problem

Personal `read_file`/`write_file` preparation, revalidation and execution ran synchronous `fs` scans and content hashing on the host event loop, some of it inside or adjacent to durable Session transactions. A slow or large target could starve the main loop and lengthen every co-resident transaction, violating the Personal responsiveness gate that an unrelated Session commit or control request must still complete while file I/O is outstanding.

## Decision

`PersonalFileIo` (personal-file-io.ts) is the host-side interface for file operation I/O. `openPersonalFileIo` starts exactly one Node `worker_threads` Worker running the bundled `worker/personal-file-worker.mjs` (built from personal-file-worker.ts by `npm run build:worker`). The worker receives immutable `prepare`/`execute` messages and calls the unchanged `preparePersonalFile`/`executePersonalFile` from personal-tool-io.ts. It is a compute relocation, not a security boundary: the host still owns admission, authorization snapshots, source/configuration/permission version checks, directory claims, effect/stop observation and durable records; the worker only runs trusted preparation, revalidation and execution.

The worker is created with `execArgv: []` so a host started with `--eval`, `--import` or `--input-type` does not pass illegal flags to a file-based worker. It is `unref`'d while idle so an idle harness does not pin the process, `ref`'d while any dispatch is pending so an in-flight file write cannot be silently abandoned by event-loop drain, and `unref`'d again once the last pending job settles. Worker `error`/`exit` rejects every pending dispatch: startup/module failures surface as `file_io_worker_failed`, a worker that ends before answering is `file_io_worker_lost`, and a missing bundle is `file_io_worker_unavailable` at open. Replies return structured `PersonalError` code/message; `bytes` arrives as `Uint8Array` through structured clone and is converted back to `Buffer` on the host.

In `personal-tools.ts` the ordering is: admission `prepare` (worker) → admission commit (origin, parameters, prepared request, approval state) → `review` plus optional revalidation `prepare` (worker) → wait for approval → final revalidation `prepare` (worker) → a single short `api.commit` that rechecks origin/permission versions and the unconsumed decision, acquires the directory claim for writes and records the start entry → `execute` (worker) → artifact publish → `observe` commit (effect, stop fact, claim release only when resolved). The same-file type/device/inode/content-hash checks remain inside `executePersonalFile` immediately before writing, so a path, ancestor, inode, content or symlink change between validation and execution still fails closed. Content hashing streams bounded 64 KiB chunks (approved-ops.ts `hashFdContent`), never a whole-file buffer.

A dispatched write whose reply is lost stays `effect_unknown` with the start entry and directory claim preserved; it is never replayed and its completion is never inferred from lost IPC. Once the worker exits the client is dead permanently — every later dispatch rejects `file_io_worker_lost` until the harness is reopened; respawning a worker behind an in-flight seam was rejected because a silent executor swap mid-window would weaken the unknown-effect guarantee, and a fresh harness open re-runs admission and revalidation anyway. `personalTools` accepts an injected `fileIo` (also forwarded through `openPersonalHarness`), so tests can stall, lose or stub the seam; `close()` terminates the worker during harness shutdown and after `updateWebSearch` rebuilds.

## Alternatives considered

- Keep synchronous calls but move them out of transactions: removes the transaction-length problem only; a multi-second disk scan still blocks the event loop and every queued provider/control request behind it. The gate requires the main loop itself to stay responsive.
- Detached subprocess per operation: matches read-only file search but pays process spawn per file op and complicates request/result identity; a fixed worker thread keeps one cheap IPC peer and the immutable-request model. The read-only kill assumptions of the subprocess path are not carried over — writes retain unknown effects on worker loss instead of assuming a killed process proved stop.
- Async `fs.promises` in the host: avoids a worker, but `restrictedResolve`, `/proc/self/fd` pinning and same-fd identity checks are deliberately synchronous; rewriting them async changes the security-critical section. Moving unchanged synchronous code to a worker keeps verified semantics.
- Await the worker inside `api.commit`: would satisfy correctness trivially but holds the Session transaction for the whole I/O window, which the gate explicitly does not count as isolation. Durable writes happen only in the short recheck/consume/observe commits.

## Consequences

File operation stalls no longer block the main event loop or lengthen durable transactions; `test/personal-file-io.test.ts` proves an unrelated commit completes during a stalled worker request, that worker loss mid-dispatch keeps `effect_unknown` plus the directory claim without replay, and that re-dispatch after worker death rejects instead of hanging. All callers of `personalTools`/`openPersonalHarness` that relied on synchronous prepare/execute keep working because every file effect still passes through the same prepared request and observation contract; the host-side crash-after-dispatch semantics are unchanged. `packages/agent` approved-ops hashing is now chunked for both products. Development must run `npm run build:worker` before exercising file tools; a missing bundle fails closed with `file_io_worker_unavailable`.
