# Agent Note: Concluding work calls yield the round and are recognized from persisted facts

Status: implemented

## Problem

Personal `background_work` calls that conclude arrangement (report/append/cancel/cancel_delegation/close, plus the authority errors that already instruct the model to end the round) previously returned an ordinary tool result. The model then had to produce prose echoing the result before the run could end, which wasted a provider round and produced tool-call-only or empty assistant answers that callers treated as missing answers. The Personal assistant plan needs a durable main handoff: conclude work, end the run without sealing too early, and keep later owner inputs as distinct runs — without mutating `LiveDoc`, fabricating history or forking the dependency.

## Decision

An arrangement-only `background_work` batch yields the round through a host `afterTool` hook, not through the tool's own result. The tool returns plain outputs for `delegate`, `append`, `cancel`, `cancel_delegation`, `close` and `report`; the hook reads the persisted assistant batch and, when every call in it is one of those arrangement actions, returns the same result with `control.terminate: true`. Any query call (`list`/`result`/`progress`) or non-`background_work` call in the batch vetoes termination and the run continues — arrangement composition is legal within one batch, never across batches, so a yielded `delegate` cannot be followed by more arrangement in a later batch. The authority errors `work_tool_inactive`, `work_source_ambiguous`, `work_source_invalid` and `work_tool_coordination_cutoff`, whose text already tells the model to end the round, still carry tool-side `control.terminate`. Pi durable settles the tool result as `{ kind: "model", entryId, control }` in the persisted tool task record either way, so the yield is reconstructible from durable records, not transient live state. The model-facing description mirrors the same contract: sibling calls in one batch cannot see identifiers returned by each other, freshly returned `work`/`delegation` ids are prerequisites usable only from a later batch, arrangement-only batches yield to the host after execution, and query-containing batches continue to prose or further calls.

A `cancel` action commits the durable cancellation intent, fires `abortTask` on the target's invocation without awaiting its join — a held invocation must not block the owner answer — and returns a registration fact ("已登记取消，停止仍须核实") rather than a stopped one; physical stopping stays a separately observable record. An `append` action reports the persisted admission outcome: when `appendPersonalWork` records `accepted: false` (for example the original work is already terminal), the tool result states the refusal as 未接纳 instead of returning a success-shaped result that reads as appended.

`personalWorkHandoff(tx, answerEntryId, limit?)` recognizes a yielded answer by persisted facts: every call slot's `pi.tool` task result must be terminal `kind: "model"` with `control.terminate === true`; any call without that control means unexplained, while model text parts no longer veto recognition — a batch can carry prose before its calls and still yield. Task lookup is scoped by `input.assistant === answer` inside each `pi.tool` task's input, because provider call IDs repeat across assistant entries and an unscoped match would read another entry's outcome. When recognized, the owner-facing text joins the model's own pre-call prose with facts derived from the persisted call arguments and results (delegation/work/agent ids) — e.g. "已委派分析；本轮以工具调用让出：已登记委托 N 的最终汇总安排…" — so a refused call can never hide behind a claim the model wrote first: an `isError` tool result is reported as "调用 X 未生效：…", and a normal result carrying the persisted refusal (the `accepted: false` append outcome) reports as 未接纳 — neither is ever flattened into a success claim. The optional `limit` (the IM receipts pass their 3900-character send budget) bounds the returned string: pre-call prose truncates or drops first, and when the factual body itself exceeds the budget — a large arrangement batch whose accepted-call result JSON alone overflows — the body is rebuilt as an exact aggregate ("共 N 项调用，X 项已生效，Y 项未生效或未接纳") followed by refusal facts in full and accepted calls in compact form, detail truncating on fact boundaries; a refusal's existence can never be cut by successful result payloads. `answer()` in personal-harness consults the handoff whenever the assistant message carries toolCall parts, not only when text is empty; unexplained empty text still returns the empty answer, and a genuinely missing assistant entry still throws `answer_missing`. The `/input` status path in personal-control and the Telegram/QQ receipts apply the same recognition before their error/canned paths. Report tasks already reject textless answers as `unanswered`, so a yielded report-attempt round cannot masquerade as a report body.

Pi 1.3.0/1.4.0 exposes no general post-tools round yield: `control.terminate` requires unanimity across every tool slot of the round, so a mixed round with an invalid or unavailable call vetoes termination and the run continues — accepted work stays placed, never polled by the tool itself. `control.handoff` ends the run but appends a `pi.reset` boundary that drops prior context, so it is a context cut, not a yield. `afterTools` is `void` and cannot request termination, and `LiveDoc`/generation internals are private. The implementation therefore only requests the supported bounded yield on conclusion-oriented calls; the general host-forced yield remains an upstream contract request (a post-tools round yield that settles current inputs done without all-slot unanimity and without a reset entry). `test/personal-handoff.test.ts` proves both directions against the minimal pi fixture and the assembled host.

## Alternatives considered

- `control.handoff` on concluding calls: ends the round, but the persisted `pi.reset` cuts model context — later owner input would lose the conversation. Rejected; it changes history visibility rather than yielding.
- Mutating `LiveDoc` or replaying the generation to force round end: violates the private-state boundary and risks corrupting run accounting. Rejected.
- Host-arranged reporting (forging a report call): the issue permits it only with explicit provenance while retaining model-report verification; a forged call is provably unverifiable against `modelCall` recovery checks. Rejected; report stays model-initiated with its existing verification.
- Recognizing yield from `LiveDoc` or transient run state: works only in-process. Persisted tool-task results carry `control`, so recognition survives restart and works in `/input` status and recovery paths.
- Yielding whenever `delegate` appears in the batch: repeated delegation across rounds is legitimate arrangement, and per-call yields would let an arrangement-only batch that ends early still veto. The batch-level rule supersedes this: one batch may compose several arrangements, then yields — a `delegate`-only batch concludes like any other arrangement batch, and the round budget in [bounded main coordination](2026-11-03-personal-coordination-cutoff.md) bounds how many further batches the same input may attempt.

## Consequences

Conclusion-oriented rounds no longer spend a provider call on mandatory echo prose, and every consumer of a done input (`answer()`, `/input` status, Telegram receipts, report answer extraction) sees honest handoff text or the genuine empty-answer error. Mixed rounds keep the documented upstream behavior: the run continues and committed effects are retained; the run never starves because the tool task itself is already terminal. Later owner inputs are unaffected — each `followUp` is its own durable run with its own requestId/source. Crash between the admission commit and the tool-result commit replays the tool safely (idempotent requestIds, `replay: "safe"`); crash after the yielded round reopens with work/report intact and recovery-verified. M1 remains gated on the upstream general yield for cases where a non-concluding mixed round would need a host-forced end.
