# Agent Note: Personal file I/O uses bounded, independently owned jobs

Status: implemented

## Problem

The [shared-worker decision](2026-11-02-personal-file-io-worker.md) moved synchronous file checks off the host event loop but still serialized unrelated jobs and left the client permanently unusable after worker loss. A result lost after a dispatched write must not justify replay, replacement of its identity or release of its claim. [Issue #38](https://github.com/num-lab/Ruukoto/issues/38) requires independent new jobs within bounded capacity, with real stopping evidence and safe profile exclusion.

## Decision

`PersonalFileIo` owns one fixed worker per prepare, revalidate or execute job. Workers run the existing same-fd identity/content/protected-root checks and 64 KiB hashing without rewriting their security-critical synchronous code. Prepared requests are immutable data; no worker stays reserved through an approval wait. Each worker receives one message, returns one identity- and phase-validated reply, closes its port and exits. `execArgv: []` prevents inherited host eval/import flags. Live workers remain referenced until exact exit.

Capacity is four occupied slots per canonical profile, shared across managers for the lifetime of the process. Occupancy includes unused execute reservations, starting workers and workers whose stopping is unverified. A reservation releases locally if it never starts; a created worker releases only on its exact exit. A validated one-job result proves the operation stopped, but does not prove its thread exited or free its capacity. Four OS-stuck workers exhaust availability until actual exits, verified original-host termination or filesystem repair. There is no pool, waiting queue, unbounded replacement or automatic retry.

Every tool-associated job has a version-1 admission before worker creation, including UUID, tool/work/source/generation, phase, access, immutable input and digest, deadline and original host PID/start identity/incarnation. A per-job sequence records starting and dispatch intents, verified no-dispatch/release, one logical settlement, termination requests, validated results, exact exits and verified host termination. Lifecycle entries are the authority; documents project their exact contents and order. Preparation results retain their immutable request. Execution completion retains effect/code and captured-byte length/digest without duplicating all output bytes in Session storage.

The lifecycle owner serializes evidence callbacks even for injected recorders. A valid reply claims its first outcome synchronously, before awaiting evidence, so its later exit cannot turn it into a lost response. Delivery waits for required result and settlement persistence. Deadline/cancel/error that arrives first remains the logical outcome; a later valid result can add stopping evidence, never rewrite the old uncertain write as success. Every awaited pre-start/pre-post step rechecks settlement, cancellation, deadline and namespace fencing. Failure to record evidence fences existing reservations and new dispatch, terminates exact workers and retains unacknowledged receipts in memory.

Tools reserve execute capacity after approval and revalidation, before the short authorization/claim/start commit. The execute-job admission binds the operation's single attempt, including a reservation that never reaches consumption. Capacity denial before consumption is terminal, `started: false` and known not executed; the approved decision remains history but the old key/card can never become actionable when capacity frees. Initial preparation denial also has a durable attempt without inventing a ToolAdmission or approval. Recovery never prepares, reserves or dispatches the original failed attempt again. A verified successful auto-review read revalidation settled before its review claim is not an execution attempt; pending human decisions survive restart and execution still requires fresh post-approval revalidation. New independently authorized operations use fresh preparation and the approval required by normal policy.

Tool observations and job-linked stop evidence derive stopping from validated completion, exact exit, verified original-host termination or verified never-started release, not file kind, timeout or a human string over a known live worker. Starting/preparation jobs participate in source readiness, work collection and settings blockers before ToolAdmission exists. Exact active-tool exclusion prevents self-blocking without excluding sibling operations. An unknown write keeps its claim after worker exit until independent effect resolution; late stopping after that resolution releases the claim in the same transaction.

Healthy shutdown establishes the canonical admission fence even before the first job, requests cancellation/termination and flushes exact lifecycle receipts while Session storage remains usable, then closes storage and releases the profile lock; only checked reconciliation clears the fence. Unverified stopping or evidence flush beyond grace rejects close while keeping Session/control/lock for inspection and retry. Unexpected Session failure signals cleanup without calling the closed Session; exact exits and unacknowledged receipts remain in the process registry. Same-process reopen cannot reset live capacity or infer host termination. Recovery replays exact retained events idempotently, and a foreign original host is stopped only after a verified OS identity change or nonexistence, never a null identity lookup alone. Persistence fencing clears only after exit and successful receipt reconciliation.

New file ToolAdmissions carry `fileIoVersion: 1`; new job documents and entries are explicitly versioned. Completed legacy file history retains its original verification branch. Unfinished legacy file operations reject activation with `file_io_legacy_pending` so old work must be completed or recovered with the original version. A stored job identity must match its index entry and document key before recovery. Legacy test inputs are portable captured storage fixtures from the baseline, not a copied application tree or a runtime dependency on historical Git objects.

## Deadlines and Evidence

The internal defaults are 120 seconds per job and 5 seconds termination grace. Legitimate-storage measurements on 2026-11-03 used Node 24.15.0, fully allocated and fsynced 1/64/512 MiB files and two samples across preparation, revalidation, read execution, write preparation and overwrite execution. The maximum observed phase was 243.246125 ms on Darwin arm64 (read revalidation) and 406.287421 ms on Linux arm64 (read preparation). These frozen local-storage observations justify a conservative initial wait, not a universal throughput guarantee or an old-file size limit. Tests override deadlines/grace to exercise the same lifecycle quickly; product configuration cannot change them.

Maintained tests distinguish real synchronous FIFO stalls and exact worker/host exits from IPC-injected races. They retain file identity/content/symlink/permission/protected-root negatives, exercise separate preparation/revalidation/execution progress with another actual operation, and check original approval replay, capacity exhaustion, shutdown and strong-crash windows. Raw logs and timing captures remain outside the repository; issue comments own acceptance evidence.

## Alternatives considered

- Retain the single cached, permanently dead worker: it minimizes spawn and identity management, but one synchronous stall blocks all file operations and later independent jobs cannot recover after loss.
- Reusable pool, waiting queue or unlimited replacement workers: amortizes spawn or hides transient capacity loss, but a queue couples unrelated work to stuck jobs and replacements conceal live stop-unverified workers. The fixed four-slot refusal makes the availability limit explicit.
- Rewrite the synchronous checks with host `fs.promises`: avoids a worker, but changes same-fd ordering, `/proc/self/fd` directory pinning and protected-root checks. Moving the existing trusted executor preserves those verified semantics.
- Managed process per job: offers a stronger isolated execution identity if Node thread evidence proves inadequate on a supported platform. The current one-job worker supplies exact result/exit evidence and honestly retains OS-stuck occupancy; extra process management is not required for that contract. Reconsider it if real-platform evidence cannot establish the documented lifecycle.

## Consequences

Unrelated jobs can recover without reopening while spare capacity exists. The cost is per-phase worker spawn, durable lifecycle records and a finite fault-tolerance bound: four stuck threads can leave file I/O unavailable while ordinary main/control interaction continues. Worker termination never resolves unknown write effects, and replacing a service never proves the original host stopped.

This decision partially supersedes the cached-client and permanently-dead dispatch portions of the previous worker note. Its no-replay, trusted-bundle, same-file and out-of-transaction guarantees remain; its idle-client ref/unref cycle does not. The [general-tool authorization](2026-10-17-personal-tools-access-artifacts.md) and [background directory claims](../feature/2026-10-21-personal-background-processes.md) decisions retain their ownership and effect rules, extended with job evidence. Coding/native worker decisions remain separate; no shared executor behavior or dependency changes are introduced.
