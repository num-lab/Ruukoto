# Agent Note: Native recovery choices bind original operations and preserve separate facts

Status: implemented

## Problem

The file milestone projects one-shot ordinary decisions into the desktop timeline, while other operation families and recovery choices remain in local management. Reusing broad shutdown or current default permissions for recovery would change the original execution's authority. Requiring freeform evidence for every owner effect statement also makes a simple business decision depend on an unverified text field.

## Decision

Native desktop cards derive actions from each family's canonical records. A versioned action request fixes the operation, admission, displayed occurrence and one stable request key. The action index stores only immutable intent and outcome; family approval, question, effect, stopping and resource records remain authoritative. Paired native credentials identify the actor when the authenticated remote entry supplies them. Client bodies cannot choose an actor. IM-origin affirmative choices remain in the original entry; existing native administrative cancellation, original-record checks and exact cleanup remain available.

Terminal cards retain prior recovery facts without a display ledger. Original command and application-data observations, failed inspection-stop receipts and Cua pending-stop records preserve occurrences after automatic reconciliation establishes the final result. Each history matches the original admission and execution identity. Healthy completions, successful first stops, ordinary running processes and healthy full-access MCP calls do not create recovery cards or approvals.

Synchronous decisions and answers mutate their canonical records in the action-admission transaction. The host gathers every required table read before the first write. Claim resolution prepares a write-only family setter before appending the action and claim. Long recovery registers a background task and fixes the original executor binding plus any current pause or observation. Only one unresolved action may occupy a card. Execution rechecks the original binding and current action eligibility; a lost response is inspected by the same key. Interrupted started actions retain uncertainty without replay. Failures finish the action receipt even when a dependency throws an untyped error.

Owner success or failure is an immutable claim with source, time, card, action and optional fixed-check reference. It uses the family's existing resolution field while retaining the original unknown result. Legacy evidence records keep their original representation and verification. A claim establishes neither stopping nor delivery. Application-data recovery uses its original audit receipt rather than a human settlement. Ordinary MCP keeps explicit end-with-unknown and its original-source prohibition. Cua claims do not replace its stop, fresh observation and exact acceptance sequence.

Fixed checks inspect original receipts or a known target selected from the original record. An application-data audit receipt can establish commit; a command receipt establishes that execution returned. A HEAD request uses the original URL, pinned address and credential digest. Service inspection uses the original machine, service and configuration. Current URL or service observations never establish the old write's effect, execute the old write or acquire current default permissions. Check intent and bounded result are retained separately from the claim.

Cleanup targets one original browser session, command execution, file job, inspection, process or Cua CLI launch. File cleanup drains one job without sealing its profile namespace. Cua reserves the original recovery resource while stopping captured CLI launches and keeps the Linux sandbox running. Stopping the recorded whole sandbox requires its own explicit native choice; the existing legacy management choice remains. Unknown stopping retains the original resource and directory occupancy.

This extends [desktop canonical decisions](../../implemented/feature/2026-11-04-personal-desktop-file-loop.md) and partially supersedes mandatory freeform service evidence in [service recovery](2026-10-17-personal-service-recovery-controls.md), while retaining its original identity and two-fact settlement. [M2 execution](2026-11-04-personal-m2-execution.md), [Cua recovery](2026-10-23-cua-official-mcp.md) and [file jobs](2026-11-03-personal-file-io-jobs.md) retain authority and stopping semantics. Other delivery and business-data notes remain separate.

## Alternatives considered

- A second pending-decision store simplifies UI queries but duplicates family state and can disagree after cancellation or recovery. Derive cards and allowed actions from the existing records.
- Reuse whole-profile shutdown for recovery: existing cleanup is straightforward, but stops unrelated jobs and broadens a card's effect. Drain the exact recorded execution.
- Store generated evidence text for an owner choice: avoids new fields, but invents evidence and loses source/card/check provenance. Preserve claims as their own immutable facts.
- Re-run the old write to infer its outcome: may produce a clear result, but repeats unknown effects under potentially different authority. Inspect fixed records and known targets only.

## Consequences

Native recovery remains available while main handles other input, with bounded original checks and honest effect/stopping results. Retained action and claim records add validation and page-size costs. A dependency failure or unverified stopping can require another explicit choice; it never releases another execution or fabricates success. Representative native and isolated Linux evidence belongs in [Issue #42](https://github.com/num-lab/Ruukoto/issues/42).
