# Agent Note: 固定范围的新闻计划由宿主采集，动态正文复用通知 outbox

Status: implemented

原编号：ADR 0015

## 问题

daily-agent issue 07 要求 main 管理定时新闻、确认新增来源，并避免新闻采集读取个人资料。推送要带可访问的来源 URL，同一摘要里不重复同一来源；搜索服务不可用时不能伪造新闻事实。

[调度器与通知 outbox](../architecture/2026-09-24-scheduler-outbox.md) 第 5 条只批准固定正文：审批时正文已知，获批后原样发送。新闻正文要到每次到期采集后才知道，审批时无法固定。若让模型任务去搜索并撰写正文，任务会装配会话历史、项目资料、应用数据与记忆，采集就可能接触并外发私人上下文，模型也可能补写搜索结果里没有的事实。

## 决定

- **新闻计划复用调度计划、调度运行和 outbox。** main 通过已有的 `schedule_create` 以 `action=news` 提议固定关键词、来源域名、时间窗口与时间规则（`news: { keywords, domains, time_range }`）：关键词 1–5 个、每个不超过 200 字符；来源域名必须明确给出，只接受公开域名，不接受 IP、本机或私有域名；`time_range` 为 `day`（原定时刻前 24 小时，缺省）或 `week`（前 7 天）。新闻计划不接受自由正文、资料引用、接收者或唤醒指令。
- **宿主直接采集，不新增搜索服务。** 到期后宿主按已批准的参数直接调用现有的 Tavily 搜索接口：原 Web Search 工具与新闻采集共用结构化的 `searchTavily`，不新增搜索服务或依赖。每个关键词一次 `topic=news` 搜索，每次最多 5 条结果。main 项目的 Web Search 必须启用，创建计划、确认提交、采集与发送前都会核对；`purpose=tavily_search` 的凭据须允许 main 项目使用。
- **采集不接触私人上下文。** 采集过程不创建模型任务，不装配历史、项目资料、应用数据或记忆工具，也不自动写入长期记忆。
- **正文只来自搜索服务。** 宿主按来源与发布时间过滤、按 URL 去重后，把搜索摘要合并为一条通知。摘要使用服务返回的文本，保留其来源，不生成额外事实。首版不进行模型改写，也不逐条抓取网页，以降低私人上下文泄漏与无依据补写的风险。
- **审批批准的是采集范围。** 这是[调度器与通知 outbox](../architecture/2026-09-24-scheduler-outbox.md) 第 5 条「批准固定正文」的特定扩展：`notification` 审批新增 `mode=news`（`ApprovalScope.mode` 为 `schedule | once | news`），批准的是固定关键词、来源域名（含子域）、搜索窗口、时间规则、摘要模板、目标及配置版本与持续范围。审批记录的正文是宿主生成的策略说明，写明关键词、来源、窗口、摘要来源与「搜索失败不编造或发送新闻」。
- **审批不因访问模式放宽。** TUI 把这类审批明确显示为「动态新闻推送」。完全访问和自动审查模式仍须 owner 确认：完全访问不跳过通知审批，自动审查的确定性策略把 `notification` 范围直接转给拥有者，见[显式访问模式](2026-09-19-explicit-access-modes.md)与[自动审查模式](2026-09-22-auto-review-mode.md)。
- **范围变化即重建。** 新增来源随整个计划一起确认，不单独追加。任何关键词、来源或时间变化，都要取消原计划后重建、重新审批；同一 `create_key` 换了参数会以同键异参冲突拒绝，新增来源不能复用旧批准。
- **每次正文由宿主固定。** 获批计划的每次正文由宿主采集后固定；模型不能选择接收者，也不能自行换键发送。
- **只扩展 schema，不建业务表。** schema v18 仅扩展 `schedules.action`（CHECK 为 `'wake_main','notify','news'`），并在 `schedule_runs.news_result` 保存有界采集快照与状态，不建立固定新闻业务表。v17 升级保留旧计划、调度运行与发送账本，旧运行的 `news_result` 为空。
- **运行键与漏过周期沿用调度器规则。** 每次到期仍用原运行键，未完成运行吸收漏过周期，已完成的窗口不重复搜索。快照、固定正文与 outbox 操作同事务提交。
- **只在一次摘要内合并。** 多关键词结果合并在该次摘要内去重，不合并不同授权范围的计划。
- **窗口与过滤由宿主再次核对。** 采集窗口以原定时刻为截止，起点为截止前 24 小时或 7 天。缺少可解析发布时间、在窗口外、或不匹配批准域名（含子域）的结果不进入摘要。来源 URL 保留完整的 HTTP(S) 链接，不截断；域名在宿主再次校验，带用户名、密码或端口的 URL 丢弃。
- **失败不产生新闻正文。** 搜索失败、限流和结果未知都保存采集状态，并登记一条失败的发送记录：此时尚未向平台发送，所以 outbox 操作标为 `failed`，错误代码以 `news_` 开头（如 `news_rate_limited`、`news_timeout`）。任一关键词的搜索失败，本窗口整体按失败处理：已取得的结果留在快照里供核查，但不发送，也不自动重试。
- **重启不重搜。** 重启时遗留的 `searching` 变为 `unknown`（错误代码 `backend_restart`），不自动重搜同一窗口；已登记、尚未开始的 `pending` 采集可以继续。
- **外发沿用 [Telegram owner 入口](2026-09-24-telegram-owner-entry.md) 的规则。** 平台明确限流时可以退回同一操作，等待后再领取；只有实际发送结果未知才是 `effect_unknown`，不得换键重发。
- **取消中止采集。** 取消计划会中止在途采集，并取消尚未开始的 `pending` 采集；取消后返回的采集结果不能登记发送。

## 采集快照与通知

`schedule_runs.news_result` 是一次运行的采集快照，`status` 取下列值：

| 状态 | 含义 | 发送记录 |
|---|---|---|
| `pending` | 已登记，尚未开始采集 | 无 |
| `searching` | 已领取，正在搜索 | 无 |
| `completed` | 全部关键词搜索成功 | `pending` 操作，正文为该次摘要 |
| `failed` | 搜索服务明确失败（限流、服务错误、畸形响应等） | `failed`，`news_<错误代码>` |
| `unknown` | 结果不明：超时、连接失败、停止时中止或后台重启（`timeout`、`unavailable`、`canceled`、`backend_restart`） | `failed`，`news_<错误代码>` |
| `canceled` | 计划已取消，或领取时计划或目标已变化（`schedule_canceled`、`target_or_schedule_changed`） | 无 |

- **快照内容**：窗口起止，每次查询的关键词、查询时间与服务请求 ID，以及每条结果的 URL、标题、发布时间、查询时间、摘要（不超过 500 字符）和 `summarySource=tavily_search.content`。快照每次最多 32 KiB，超限时后续结果不保存，并标记 `truncated`。
- **URL 去重**：只忽略片段与常见跟踪参数（`utm_*`、`fbclid`、`gclid`），保留可能决定文章身份的其他参数。
- **通知正文**：注明来源是 Tavily 搜索摘要、未经独立核实；每条给出标题、发布时间、摘要与完整 URL。正文受单条通知上限（2,000 字符 / 8 KiB）约束，放不下的条目不展示，并注明省略条数；完整记录在 `schedule_query` 查看。窗口内没有符合条件的结果时，仍发送一条说明没有结果的通知。
- **采集循环**：新闻在独立循环中串行采集，一次运行最多 5 次有界搜索，不占用 main 会话，也不阻塞发送循环。

## 保证范围

- 搜索服务的引用不等于独立核实；来源页面后续失效、搜索服务漏收，都不在可保证的范围内。
- 延迟采集仍受 Tavily 相对查询时间的窗口限制：停机后补采可能缺少旧新闻，宿主不推断、不补造漏过的新闻。

## 备选方案

- **由模型改写或撰写摘要** — 模型能把多条搜索摘要整理成更易读、更连贯的正文。不选，是因为改写需要模型任务，而模型任务会装配会话历史、项目资料与记忆，采集就可能接触并外发私人上下文；模型还可能补写搜索结果里没有的事实。正文由宿主按快照固定，审批才能约束每次发出的内容。（见原决定第 1、5 段，daily-agent issue 07 Comments）
- **逐条抓取来源网页** — 能核实链接可达，拿到原文而不只依赖搜索摘要。不选：首版与模型改写一同不做，以降低私人上下文泄漏与无依据补写的风险；代价是来源页面后续失效、搜索服务的引用未经独立核实，都不在保证范围内。（见原决定第 5 段，daily-agent issue 07 Comments）
- **新建固定的新闻业务表** — 新闻条目字段固定（URL、标题、发布时间），独立成表便于按条目查询。不选，是因为 daily-agent 规格只允许调度器拥有固定的运行记录与发送账本，不预建业务表；采集结果是某次运行的有界快照，挂在 `schedule_runs.news_result` 上，就能与该次运行的固定正文、发送操作同事务提交。（见原决定第 3 段，[daily-agent spec](../../../../.scratch/daily-agent/spec.md)「运行模型」与已确认决策第 8 条）
- **把不同新闻计划的结果批量合并成一条推送** — daily-agent 规格把新闻列为可批量汇总的低优先级事件，合并能减少对拥有者的打扰。不选，是因为每个计划的批准各自固定关键词、来源、目标与持续范围，跨计划合并会让一条通知超出任何单一批准的范围；合并只在一次运行的多个关键词之间进行。（见原决定第 3 段，daily-agent spec 已确认决策第 11 条，[daily-agent issue 07](../../../../.scratch/daily-agent/issues/07-news.md)「实现范围」）

## 后果

- **收益**：新闻采集不调用模型，也不读取会话、项目资料、应用数据或记忆，私人上下文不会进入新闻推送。每条推送内容都来自搜索服务并带完整来源 URL，搜索失败时不发出新闻事实。审批范围在确认时完整可见，增加来源或改关键词必须重新确认。复用调度运行与 outbox，沿用到期补登、一个逻辑键至多一个操作、结果未知不换键重发的既有保证，不另建表或服务。
- **代价**：摘要是搜索服务的原文，可读性受限，也未经独立核实。任一关键词失败，或重启时正在采集，该窗口就没有新闻摘要，只留失败记录。任何范围调整都要取消重建并重新审批。
- **已知上限**：去重只在一次摘要内进行；窗口相互重叠时（如每日计划配 7 天窗口），同一条目可能在相邻摘要里重复出现。快照与通知各有大小上限，超出部分只标注不展示。采集是串行的，多个新闻计划持续积压时需要有界并发。
- **何时重访**：要引入模型改写或网页抓取时，必须重新论证私人上下文的隔离与无依据补写的防护，作为新决定另写一篇。

## 验证

- `test/50-news-migration.test.ts`：v17 → v18 保留调度计划、运行与发送事实，允许新闻动作并补空快照；覆盖旧 CHECK、全部旧数据、索引、外键与失败整体回滚，`integrity_check` / `foreign_key_check` 通过。
- `test/51-news.test.ts`：main 审批与持续范围、重复参数幂等、新增来源不能复用批准、目标变化使批准失效；URL 去重、来源与时间过滤、隐私隔离（不调用模型、不写记忆）；限流、服务失败、畸形响应、超时与部分失败；重启时 `pending` 继续、`searching` 记 `unknown`；取消与 Web Search 禁用。
- 运行：`npx tsx --test test/50-news-migration.test.ts test/51-news.test.ts`。所有搜索与发送都用本地模拟服务；真实 Tavily 与 Telegram/QQ 收发没有验收（daily-agent issue 07 Comments）。
