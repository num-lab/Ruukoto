# Agent Note: 按改动面选检查，取代收尾跑全量

Status: implemented

## 问题

仓库的三处指示（根 `AGENTS.md`、`docs/development.md`、`README.md`）都要求「修改过程中跑 `check:static` 与相关测试，收尾运行 `npm run check`」。全量 `check` 要构建 worker、跑 lint 与两套类型检查，再跑应用与基础验证的全部离线测试：macOS 167 秒、Linux 495 秒、1024 个用例。每批改动不论多小都要付这个代价，而其中绝大多数用例与本次改动无关。

同时，agent 没有判断「这次该跑什么」的依据：`docs/development.md` 的映射表只回答「某个位置常用哪些测试」，不回答「哪种改动需要哪一级证据、什么时候才该升级到全量」。结果两种偏差都会出现：小改动跑全量浪费，或改动跳跃了本该跑的定向用例。

## 决定

引入证据阶梯：默认按改动面选最小检查集，全量只在三种情况跑。

### change-scope

`scripts/change-scope.ts` 报告一次改动相对 merge base 的显式范围，输出带 `formatVersion` 的 JSON：已提交、暂存、未暂存、未跟踪四类路径，以及解析后的 base／head／merge base 提交号。入口是 `npm run change-scope -- --base <ref>`。

基点必须由调用方核实后传入。脚本不猜测、不抓取基点；引用有歧义、未解析到恰好一个提交、或与终点没有唯一共同祖先时，都以非零退出并给出原因。路径按 NUL 分隔解析，含非 ASCII 与空格的文件名不受影响。

### 提交前检查 skill

`.agents/skills/pre-push-checks/SKILL.md` 给出改动面到命令的映射表，覆盖 `src/` 各区、`test/`、`.agents/notes/`、`docs/`、`AGENTS.md` 与 skills、`scripts/`、`verification/` 两个目录、`deploy/`、`package.json`。它不再重复 `docs/development.md` 已有的「位置 → 测试文件」表，而是链接过去，只补上「哪种改动对应哪一级证据」。

明确写入的四条：

- 没有默认的本地全量基线；每处行为改动都要有最窄的、会因该回归而失败的检查。
- 全量只在拥有者明确要求、诊断 CI 失败、或改动确实横跨全仓时跑。
- 已通过的检查不因为「接下来要提交」而重跑。
- `.scratch/` 的工单与证据不改行为，不需要跑检查。

映射表保留一条与直觉相反、但属本仓库刻意做法的说明：只断言落盘布局的用例（直读 SQLite、裸 SQL）是有意为之，不得以「测试只应测行为」为由改写。

### 指示层改写

三处指示改为「按改动面选最小检查集」并链接 skill；`docs/development.md` 仍保留全量 `check` 的命令说明，供 CI 与显式复跑使用。pre-commit 钩子继续只跑 `check:static`（约 8 秒），未改动。

## 备选方案

- **保持全量，只优化耗时** — 不必判断改动面，规则最简单。否：耗时来自用例数量与子进程启动，单点优化到不了「每批改动都付得起」的量级，且判断该跑什么的问题原样留着。
- **全量留给 CI，本地只跑 pre-commit** — 最省本地时间。否：CI 四组矩阵要等远端，行为改动缺本地反馈会以更长的回路暴露回归；本仓库多数改动没有 feature 分支的并行验证。
- **按改动文件自动跑对应测试** — 不必人判断。否：测试与源码路径不是一一对应（`test/01`–`05` 覆盖 `src/runtime/` 与 `src/core/` 交叉面），自动映射会给出看似精确实则漏项的集合，比让人按表选更危险。
- **把映射表写进 AGENTS.md** — 一处可见。否：表有二十行，会把根文件推成操作手册；根 `AGENTS.md` 是常驻指示层，详细映射属于 skill 与开发说明。
- **`change-scope` 自动推断 base（如 `origin/main`）** — 少一个参数。否：基点取决于当前分支的真实 PR 或栈父级，猜错会让范围失真；要求显式传入并在合并基点后重跑，是唯一的可靠做法。
- **输出人类可读的文本而非 JSON** — 直接可读。否：版本化 JSON 能被后续脚本与其他 skill 消费，且格式变化可检出。

## 后果

默认路径从 167 秒降到定向用例的量级（单个测试文件通常数秒）；`check:static` 仍作为提交前的机械门禁。收益是反馈回路变短、且「跑什么」有了可查的依据，而不是每次重新判断。

代价与遗留：

- 选择证据的责任转移到改动者身上。选错集合（太窄）会让回归漏到 CI 才暴露。缓解靠 skill 的映射表按「改动面」而非「文件」组织，并保留「跨模块契约变化时加调用方用例」的要求。
- `change-scope` 需要显式基点，agent 每次要确认当前分支的真实基点；基点判断错误时范围失真。缓解靠「合并基点后重跑」的要求与脚本对歧义引用的拒绝。
- 映射表会随目录结构漂移。它链接 `docs/development.md` 的表而非复制，减少了重复，但新增 `src/` 区时两处都要更新；本批未加门禁校验该表与目录的一致性，漂移明显时再评估。
- 本批只改指示与新增脚本，未改任何现有测试或删除任何检查；全量 `check` 的命令与 CI 入口保持不变。

## 测试

- `npm run change-scope -- --base main` 输出合法 JSON，四类路径与三个提交号齐备。
- 缺 `--base`、基点引用不存在两种情况均以退出码 1 失败并给出原因。
- `npm run check:static` 通过（lint、类型检查、笔记门禁）。
