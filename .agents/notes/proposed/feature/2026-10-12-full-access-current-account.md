# Agent Note: 完全访问使用启动账户且不请求审批

Status: proposed

方案已确认，尚未实施。本篇记录两个产品统一的完全访问语义及其授权传播；当前行为仍以代码和 implemented 笔记为准。

调度业务由[通用定时任务提案](2026-10-12-generic-scheduled-tasks.md)统一为独立任务执行，删除新闻与定时固定通知路径。本篇定义创建时模式及共享免审批行为，不再为退役动作适配审批或兼容记录。

## 问题

拥有者选择完全访问，是要让 Agent 使用自己运行应用时已有的文件、网络和工具权限。当前 native/container 后端却要求专用执行账户与受保护的启动、停止脚本；部署还拆分拥有者、后台与执行账户，增加账户、ACL 和启动入口配置。完全访问在应用数据、通知、服务管理及结构化文件和 HTTP 操作上仍会等待审批，委派和私聊又固定回到请求确认，因此同一个模式在不同路径上含义不同。

原三账户设计保护后台数据库、模型凭据和拥有者令牌，确实提供隔离。这里选择取消完全访问对这项隔离的承诺，以启动账户的已有权限作为完全访问范围，减少使用和配置成本。

## 方案

### 执行账户与权限

- ruukoto 与 ruukoto-code 的 `full_access` 都直接使用启动应用后台的系统账户。移除专用后台账户、专用执行账户及其启动入口要求，不通过容器、Seatbelt、bubblewrap 或其他任务沙箱限制文件与网络访问。
- 保留后台进程和终端分离的运行方式，保留控制面令牌认证、IM 拥有者校验、任务归属与输入校验。完全访问不自动取得 root 或其他账户权限，也不让未经认证的入口选择模式。
- 同账户完全访问进程可以读取、修改该账户有权限的后台数据、凭据和拥有者令牌，也可能据此调用控制面。入口认证和资料 API 校验不能再被描述为对该任务的隔离；不以路径黑名单重新包装一套完全访问沙箱。
- `confirm`、`auto-review` 与 Plan 的受限执行规则继续生效；缺少它们需要的隔离能力仍明确失败，不能静默改用完全访问。新会话默认模式与各会话身份的工具分工沿用现有规则，不因完全访问扩充 main 或 SubAgent 的工具集。

### 无操作审批

完全访问下所有已开放工具均免操作审批，覆盖编码工具、结构化文件访问、HTTP、MCP 写工具、破坏性应用数据变更、通用调度任务中的工具操作、一次外发和服务管理。任务不进入等待人工审批，不调用自动审查，也不把完全访问记作一次人工批准或长期操作授权。模型仍可询问缺失的信息；权限说明和工具描述不得要求它为已经获得完全访问授权的操作重复申请权限。

免审批只移除操作授权等待。执行前仍核实任务活动状态、权限版本、目标、配置修订、产品能力及凭据绑定，保留操作参数快照、幂等认领、事务内状态与事件、效果未知判定及不自动重放规则。MCP 允许列表、服务白名单和资料 API 归属校验继续限制对应接口，不能据此声称无沙箱命令无法经其他路径访问同账户资源。

服务管理可继续使用受保护的固定 helper 与 OS 授权，调用账户改为实际启动账户。它们只属于启用系统服务管理的前置，不是完全访问的启动条件；OS 权限不足就返回失败，不转应用审批，不弹密码，也不自动授予 sudo 权限。

### 环境继承

完全访问继承后台启动时的用户环境，包括 PATH、HOME、代理、SSH agent 和工具凭据，只清除用于内部控制通信的 Ruukoto 变量。不要继续复用仅保留 PATH/HOME/LANG/LC_ALL/TMPDIR 的开发环境过滤。工作副本所需的宿主固定 Git 环境仍按原用途传入，不增加用户环境配置入口，也不把环境值写入诊断和操作记录。

### 授权来源与传播

| 触发来源 | 新任务的模式 |
| --- | --- |
| 拥有者提交或继续普通任务 | 本次明确选择；未指定时取会话默认模式 |
| 已绑定拥有者的 QQ／Telegram 私聊 | 创建任务时取主会话默认模式 |
| 主 Agent 委派、继续旧工作或复用 SubAgent | 取实际发起任务的有效访问模式 |
| 工作内协作消息与结果触发的主 Agent 汇总 | 沿用触发它的任务授权，不重新读取会话当前默认值 |
| 定时计划触发执行 | 使用创建计划时保存的访问模式 |
| GitHub 等其他外部事件 | 使用入口原有的明确权限约束，不继承会话默认完全访问 |

宿主负责保存并传递模式来源，消息正文、模型参数与 SubAgent 身份不能自行提升权限。延迟消息与结果恢复投递仍沿用原触发来源的授权，不因接收方正好空闲、切换模式或复用 Agent 而取得另一项工作的权限。

同一项工作可以在不同用户轮次继续。新一轮按本次发起任务确定新委派的模式，SubAgent 不永久绑定第一次获得的完全访问；既有任务继续携带各自的模式，不能用工作首次模式或工作最近模式反向改写它们。单次批准和限定的长期操作授权不随模式传播。

工作副本创建、改动汇总等为任务服务的临时执行也使用实际发起任务的有效模式，避免主任务完全访问时仍因固定 confirm 入口要求沙箱。工作副本、只读或修改工具分工、来源核实和成果保留仍由原有工作规则负责；完全访问下不再宣称工作副本构成 OS 文件隔离。

### 模式切换与停止

- 会话默认模式只影响之后创建的任务，不改写已有任务和定时计划。拥有者以新模式继续旧工作时，新派发任务采用本次模式，已经运行或排队的任务保持各自已保存的授权。
- 现有显式任务模式切换仍只作用于指定任务，按工具边界执行，不级联改写其他任务、SubAgent 或定时计划。需要立即收紧整项工作时，先停止整项工作，再按新模式重新委派；不能把切换会话默认模式当作已撤销在途执行。
- 完全访问无需额外配置进程管理入口即可启动。停止时回收归属明确的执行进程；发现残留或无法核实停止时，如实报告并保留相关目录占用和现场，不把主 PID 退出等同于整个执行已停止。
- 主动脱离管理的进程、另行提权的进程和外部服务不承诺随任务停止。保留既有停止结论传播、取消和效果未知处理，具体平台监督方式由实现及真实验收确定，不能把无沙箱回收描述为对抗逃逸的安全保证。

### 直接替换

项目处于快速迭代期，直接删除旧身份要求及相关配置、专用执行启动器、启停脚本、部署步骤和兼容分支。不提供旧配置别名、旧协议适配、旧任务或定时计划字段回填、过渡期双路径；尤其不执行“为旧计划补 confirm”的迁移方案。

服务管理仍需要的 helper、策略与 OS 授权按当前账户改造，不因清理执行账户脚本而删掉服务管理能力。此次记录不授权对实际机器执行账户删除、数据清空或文件归属变更。存储若有变化，仍遵循 SCHEMA_VERSION 单调递增与拒绝更新版本数据库的仓库约定。

## 备选方案

- 保留专用执行账户并简化配置：能继续隔离后台凭据和拥有者令牌，沿用现有 Linux 回收证据；仍要求另一账户、权限配置与启动链，不符合完全访问使用日常账户能力的目标。
- 只移除沙箱，保留应用数据、通知与服务审批例外：能分别约束破坏性修改和外发；同一完全访问模式仍会停下等审批，语义不统一，因此选择全部工具免操作审批并保留执行校验。
- 所有任务动态跟随会话当前模式：规则表面简单，切换后各入口一致；会改变既有定时计划、在途子任务与迟到消息的授权，选择按触发来源保存到新任务。
- 复用 local 启动器而不处理环境与停止：代码改动最少；代理、SSH agent 和工具凭据被过滤，原进程组退出也不能证明脱离后代退出，不能直接作为完整方案。
- 为旧账户部署、配置和定时计划提供兼容过渡：既有实例升级成本低；快速迭代期明确接受直接替换，不维护兼容入口、数据回填和双路径。

## 验收标准

1. macOS 与 Linux 的全新配置均可在未设置执行账户启停脚本、未创建专用账户的情况下运行完全访问。实际进程 UID、用户环境、工作区外读写及联网均符合启动账户权限；用临时虚拟凭据和数据证明可见性，不以模拟 launcher 代替真实执行。
2. 覆盖文件、HTTP、MCP、应用数据、普通通知及服务工具的免审批路径：零审批等待、零自动审查，授权来源准确可查。配置变更、任务停止、重复调用、结果未知与事务失败仍产生正确结果；通用定时任务使用同一免审批机制，不保留新闻授权的特殊路径。
3. 覆盖委派、继续旧工作、复用 Agent、协作消息延迟投递、结果汇总及工作副本临时执行；模式来源正确，既有任务不被会话切换改写，单次批准与长期授权不继承。
4. 已绑定拥有者私聊取主会话模式，身份不匹配仍拒绝。定时计划跨会话模式切换和后台重启仍使用创建模式；GitHub 等外部事件不被会话完全访问提升。
5. 两平台实际验证正常停止、后代进程与无法核实停止：观察不到退出证据时保留占用；单列主动脱离进程与外部服务的限制，不把任务取消写成外部效果撤销。
6. 请求确认、自动审查和 Plan 的受限执行、审批及工具约束通过定向回归。旧完全访问入口要求和误导性提示在代码、部署、界面、文档及测试中清理完成，无兼容回填路径。
7. 实现时按改动面运行静态检查及相关现有用例，包括访问模式、审批闸门、工具账本、MCP、应用数据、通用调度、IM、服务管理、SubAgent／worktree／消息、停止和原生执行；真实 Linux 验收使用 `ssh tx`。测试记录区分模拟与真实平台证据，不预填通过结论。

## 风险

完全访问操作的误删、凭据读取、外发及后台状态修改都落在启动账户的权限范围内，工具 API 校验不能阻止自由命令绕过；这是已接受的信任范围。用户环境也可能携带代理和工具凭据，不能再宣称 worker 环境不含凭据。

停止只对归属明确且能核实的进程负责；残留可继续修改文件或占用资源，核实失败会阻塞后续目录使用。若以后要求完全访问仍隔离后台身份，或确定回收所有逃离后代，必须重新讨论隔离部署与平台能力，不能靠加强提示词或路径过滤宣称达成。

会话降权不会撤销既有任务和定时计划。界面与文档必须区分会话默认、任务实际模式和计划保存的模式，避免把选择新默认误解为整项工作已收紧。

直接替换不保证旧部署和旧存储可继续使用；本篇没有授权自动清空现有数据或删除实际系统账户。无沙箱运行、环境继承与回收能力均待实现后验证，本次文档检查不能作为运行行为已交付的证据。
