# Agent Note: Coding 消息队列重排与运行中引导

Status: proposed

## 问题

Code 当前把每条用户输入登记为 Task，再按创建时间串行执行；拥有者不能调整待执行顺序，也不能在同一任务内补充纠正。只调用 SDK steer 会把已接纳输入留在内存，且当前上下文选择把最后一条 user 当作当前任务，可能使原始要求退出必留范围。

产品约定由[规格](../../../../.scratch/coding-message-control/spec.md)持有，步骤与证据由[工单](../../../../.scratch/coding-message-control/issues/01-queue-and-guidance.md)持有。本篇拟部分扩展[后台持有与 FIFO](../../implemented/architecture/2026-09-19-detach-terminal-from-task-runtime.md)、[用户附件来源](../../implemented/architecture/2026-10-16-owner-attachments.md)和[等待解除](../../implemented/architecture/2026-10-14-agent-wait-and-report-ownership.md)，尚不改变它们描述的当前行为。

## 方案

复用 Task 作为持久输入回执，增加明确的队列顺序与引导路由。正文、附件、请求键、模型／权限选择、继续与问题回答来源保持原样。新引导和排队转引导都以同一源 Task 表示输入；路由决定该输入进入目标 Task，还是回退为独立执行，不另建一份正文副本或并行会话。

### 队列顺序与兼容

为 Task 保存待执行顺序，为 Session 保存队列修订；没有显式重排时仍为原 FIFO。所有新入队来源共用顺序分配，普通重排只置换拥有者输入已有位置，内部汇总保留宿主管理位置。回退引导按接纳序号组成一个队首批次，后到的回退排在此前尚未执行的回退之后。顺序、修订和事件同事务提交；入队、出队、取消、路由改变也推进队列修订，客户端不能拿旧列表覆盖新事实。

`runQueueLoop` 在异步目录核实之后、真正置 running 的事务内，重查 Task 仍 queued、没有待引导路由且仍为可执行队首。重排不能恢复暂停队列。握手、查询、事件补发与共享 view 全部读取同一顺序，不再用创建时间推断执行顺序。

基线 schema 为 53、控制协议为 43；实施时以实际检出版本为准递增。新格式必须升级 schema，因为旧程序不认识待引导路由，可能把源 queued Task 独立执行。沿用[Code 库严格版本切换](../../implemented/simplification/2026-10-24-code-instance-mcp.md)：新数据目录从空档案开始，旧 SQLite、JSONL、产物与凭据原地保留，不修改、不移动、不删除，不提供 v53 加法迁移或旧配置转换。旧程序拒绝新 schema，新程序拒绝全部旧 schema；拒绝前不能先写新表或版本号。若以后需要原地延续旧会话，须由拥有者重审既有决定，不能由实施者暗加兼容。

### 引导路由与执行归属

新增小型 `task_guidance` 表，至少保存稳定引导 ID、同会话源／目标 Task、接纳次序、幂等动作键及参数摘要、阶段、实际 JSONL entry 与首次包含它的请求快照引用。阶段只表达实际可证事实：待接入、已归入目标历史、已回退、接入前撤销；是否被某次请求选入另由快照关联证明，不把任何准备阶段称为模型已读。同源输入至多一个未收束路由，历史动作回执保留，同键同参返回原结果，同键异参拒绝。

接纳事务核实普通 Code 会话、拥有者来源、目标仍可接入、源仍 queued 与附件／来源完整性；保存路由后才排 SDK、失效未消费审批和解除等待。源 Task 在待接入期间仍为 queued，但被普通调度排除。进入目标 JSONL 后，其独立执行意图以 `canceled/converted_to_guidance` 收束，绝不伪造独立 completed 或拥有者主动取消；TaskView、查找、历史与问题回执由可信路由给出实际输入去向，不显示一条额外取消气泡。已接入的输入不能再独立回退执行。

目标进入收尾前封闭接入。尚未进入目标历史的引导、以及封闭后到达的引导，解除执行路由并让原源 Task 按队首批次独立执行；不换原请求键，不改变原模型、模式、授权、附件或继续关系。取消仍待接入的源 Task 时撤销路由并移除 SDK 中对应输入；已接入历史的输入不能靠取消一个排队 Task 撤回。普通停止、占用与重启恢复规则优先于队首调度。

### SDK、历史与消费证据

通过公开的 `sdk.agent.steer` 排入带稳定引导 ID 和附件引用的原生 user 消息，并采用 SDK 的 all 消费方式，在下一安全边界按次序读取当时待处理输入；不按文本、时间或数组下标猜消息身份。先用窄 SDK 契约检查核实元数据保留、批次消费及收尾行为，禁止依赖私有字段或改 vendor。

SDK 的 user `message_end` 回调早于 JSONL append，只用来装配引用，不能据此登记落盘或已读。下一次请求发送前先核实实际 JSONL entry、当前任务归属、附件、选择记录和 prompt 快照，再登记对应路由事实；必需记录失败阻断发送。发送是否获得有效响应沿已有请求与响应事实判断，不把保存快照或发出请求说成模型已接受。

JSONL 是消息历史唯一权威副本，与 SQLite 不承诺原子。恢复先按引导 ID 对照日志，再核实路由和请求快照：未落入目标历史的输入可回到普通队首；已落历史的输入属于被中断的目标任务，不能再追加相同 user 条目或作为新任务自动重发；缺失或冲突引用暂停受影响会话并报告，不能猜测。日志已写、SQL 未更新时只补可证关联；SQL 声称已接入但实际日志缺失时拒绝自动执行。

SDK abort 不会清空 steering 队列；目标停止／收尾时必须清除该任务的残余内存路由，再依据持久状态决定回退。重复同文消息通过不同引导 ID 区分，内存清理结果不充当消费账本。

### 完整输入、上下文与授权

当前任务的必留输入由原始要求加本任务已接入的全部引导组成；`context-selector` 不再把最后一条 user 等同于整个当前任务。Jev 相关性输入、预算、压缩与继续恢复使用同一输入集合，选择记录与实际请求可重建。不能因 user 分组错误把原始要求或引导前的本任务工具轨迹降成别的任务；工具结果的既有有损清理与预算策略保留，不能承诺无界上下文，也不能把其他 Task 的输入无条件并入。

继续输入和拥有者问题回答也保留完整输入语义：原 `resumesTaskId`、继续来源与附件链不变；问题回答保留原唯一 `continuationTaskId`、问题版本与答案回执。转引导时复用原输入装配，把必要宿主来源作为可重建记录与对应引导绑定；查询及答案卡通过路由解析实际执行目标，不改写原关联，也不把它当作又一次回答。分支与离线导入须携带可验证的原输入、路由及附件来源；归档导入的未完成路由不得自动执行。

输入身份和执行目标分开投影：Task ID 用于执行分组，用户气泡以源 Task／稳定引导 ID 及实际 entry 去重，不能沿用“一 Task 一 user”的 `input:<targetTaskId>` 合并规则。原要求、两条同文引导和答案输入分别保留；答案卡按具体源输入绑定，不能把目标 Task 内全部 user 替换成同一答案。`find_task` 和问题回答回执仍返回原源 Task 身份，真实执行目标由额外路由字段说明，不破坏现有提交核实。

队列创建顺序、执行顺序与聊天接入顺序各有证据：队列显示持久待执行顺序，普通输入聊天位置取实际开始事件，运行中引导取实际 JSONL 接入位置；不能用源 Task 的 createdAt 排聊天。实时、事件回放、历史补读与冷恢复按稳定输入身份合并并恢复同一接入次序，不先插旧气泡再靠时间重排。

引导图片／文件继续绑定源 Task 的不可变产物，通过同会话可信路由开放给目标当前输入，扩展现有仅从 task.attachments 与继续链恢复的限定；不复制产物、不接受任意其他 Task 产物或本机路径。每条引导独立绑定引用，不能复用单个 pending 附件变量串到别条消息。

当前任务保持既有模型、权限和来源身份；源输入携带的模式、路径授权或继续来源不能升级目标 Task。新增引导只改变拥有者要求，不新增资料／工具资格，已消费资料仍按原规则逐次复核。回退独立执行采用原源 Task 的选择，不采用届时的会话默认。

### 审批与等待

持久接纳引导后，事务内失效目标未消费的 pending／approved 审批，再定向解除等待；批准消费与失效由同一数据库状态裁决，已消费的操作继续。接入屏障持续到该批引导被纳入下一模型请求，旧 assistant 工具批次随后才到达的待审批或尚未消费操作不能绕过屏障先执行。已开始的操作不强停，明确保存其原效果事实。

复用 agent wait 与后台进程 wait 的仅解除等待入口，不走整个 Task 的 requestStop，不取消 SubAgent、工作流或后台进程，不丢目录让出／重取及报告认领规则。返回模型的工具结果准确说明收到新引导、原待审批操作未执行或仅结束等待，不冒充拥有者逐项拒绝，不声称后台已停止。实际新增模型可见措辞实施时按 agent-facing-text 核对快照；本轮不虚构模型调用证据。

普通 Code 主会话的普通 submit 不再因当前任务在 agent／process wait 就解除等待并执行 `requestStop(owner_input)`；移除该入口原来的自动中断行为，普通 Enter 始终排队。只有显式引导走上述仅解除等待路径；其他会话与宿主来源保持各自资格，不借此新增打断权。实现时同步旧 wait 笔记的有效事实。

## 既有笔记审计

按 queue／FIFO／steer／followUp／等待／附件／上下文及 db.ts 的版本门锚点检索 proposed、implemented 与 rejected，rejected 未命中相关笔记。后台持有与 FIFO、附件、等待归属三篇部分重叠并互链，本提案扩展顺序、可信输入来源与解除等待方式，并以显式引导替代普通 Code submit 的等待中断；后台持有、历史唯一副本、不重放、原权限与报告规则保留。[通用 wait](../../implemented/feature/2026-10-25-code-wait.md)的工具名称及后台生命周期保留；[持久问题](../../implemented/feature/2026-10-21-coding-owner-questions.md)的唯一回答关系保留。[Code 严格版本切换](../../implemented/simplification/2026-10-24-code-instance-mcp.md)继续生效并互链，不翻转其迁移禁令。其余命中的个人 durable、IM、后台生命周期提案和桌面样式与此决定无关；没有完全吸收、删除或归档的笔记。

## 备选方案

- 只用 SDK steer／follow-up：接口最少、原生支持轮次间输入；队列易失、abort 后可能残留，无法承诺已接纳消息恢复和唯一执行，因此只把它作为执行载体。
- 中断当前 Task 再以 continue 模拟引导：能复用已有停止路径；会强停工具、改变任务身份与审批，不符合本次已确认语义。
- 新建覆盖所有入口的 owner-input 体系：彻底分离输入和执行，概念整齐；本次会连带改附件 Task 外键、普通提交、问题回答及宿主入口，新增范围过大，保留 Task 加路由。
- 把路由与顺序全写在 meta、保持 schema 版本：可复用 JSON 状态；旧程序仍会误执行待接入 Task，且生命周期、回执和查询变成另一套手工索引，采用正规表及明确升级。
- 先取消排队 Task 再复制正文引导：容易接线；丢失继续、问题回答、附件及请求身份，且回退可能产生第二份任务，保留同一输入回执。
- v53 到新版本的加法迁移：可以原地保留已有会话，格式变化也较局部；现有拥有者决定明确删除兼容并要求重审后才能恢复迁移，本功能未获翻转授权，沿用严格拒绝与新数据目录，保留旧档案。

## 验收标准

规格 R1–R9 实施后均须有会捕获回归的定向证据。重点是任意重排和目录核实竞争、输入与事件同事务、重复请求、同文多条带附件引导、多 user 气泡身份与接入次序、完整原要求与继续／答案来源、审批消费竞争、旧批次后续审批、普通发送不解除等待而显式引导保持同一 Task、SDK 残余清理、自然收尾回退队首 FIFO、日志和 SQL 各崩溃窗口、暂停不被回退唤醒、分支／导入，以及旧 schema 原样拒绝。具体文件与证据阶梯见工单，不能以源码调研代替运行证据。

桌面与 TUI 均需实际交互验收，真实模型确认纠正进入下一请求且未重复执行；缺前提时保持待验收，不记通过。

## 风险

最大风险是混淆持久接纳、历史接入、请求选择与模型实际接受，或让回退消息同时留在 SDK。跨存储恢复、原任务必留输入、特殊输入来源和审批消费屏障必须先于客户端接线完成。持久路由也扩大历史与 view 的投影责任，不能只改调度器。沿用严格 schema 切换的代价是现有实例不能原地使用此能力，必须建立新数据目录，旧会话不会自动出现在新实例；原档案与未核实外部效果须保留并在原版本核实。
