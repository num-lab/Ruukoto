# Change-Scoped Checks

Every behavior change needs the narrowest regression check that fails without the fix. Expand to affected callers and cross-module contracts; CI owns exhaustive coverage and the platform matrix. Use the [development workflow](../development-workflow/SKILL.md) for independent review and acceptance. Parallel implementations defer checks until the integration owner has combined the changes.

## 1. Establish Changed Scope

Use `npm run change-scope -- --base <ref>` to include committed, staged, unstaged and untracked changes relative to the merge base. Read the effective Issue requirements and affected code before choosing tests. Name files in targeted commands, rather than relying on numeric ranges or running the full suite by habit. [Development](../../../docs/development.md#daily-feedback) maps features to tests.

## 2. Select Evidence

Build required native/worker/script assets before their consumers. Tests are offline by default; [external acceptance](../../../docs/development-acceptance.md) owns explicit model configuration and actual platform/client requirements.

Maintained [desktop](../../../verification/desktop-demo/README.md) and [settings](../../../verification/desktop-settings/README.md) demos have their own checks. Exercise changed interactions, light/dark appearance and sizes; frozen baselines stay unchanged and demo evidence does not certify Electron/MyGo.

## 3. Static Checks and Report

Pre-commit runs `npm run check:static`; do not repeat unchanged checks solely for the commit. Report only commands actually run, their results and unavailable prerequisites. Missing real-model, native-host or Linux evidence remains a gap, not a skip/pass. Keep auditable acceptance in the Issue/PR and raw evidence outside the repository. Acceptance does not grant commit, deployment, service or account-change permission.
