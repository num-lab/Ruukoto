# Change-Scoped Checks

Every behavior change needs the narrowest check that fails for its regression. Expand only to affected callers/contracts; CI owns exhaustive coverage and the platform matrix. Run full `npm run check` only when the owner asks, while diagnosing CI failure, or when a repository-wide change has no narrower credible set. [Timing records](../../../docs/development-baselines.md) explain its cost.

Do not repeat a passing check merely because a commit is next. Evidence applies to the content actually checked; changes invalidate only affected conclusions. Author checks do not replace [independent review](../development-workflow/SKILL.md#4-independent-review-and-rework).

## 1. Inspect Scope

```sh
git status --short --branch
npm run change-scope -- --base <verified-reference>
```

Verify the baseline yourself. The command neither guesses nor fetches it. Its versioned JSON reports committed paths relative to merge base and staged/unstaged/untracked paths in the current checkout. Rerun after merging a changed baseline and reassess actual combined impact.

## 3. Static Checks

Pre-commit already runs `npm run check:static` (lint, types, notes and docs); do not manually repeat unchanged checks solely for the commit. The hook's actual result still must pass. [Development](../../../docs/development.md#commits-and-ci) owns hook and CI setup.

## 4. Report

Report only commands actually run and their results. Name missing prerequisites and the evidence they prevent; keep complete auditable conclusions in the Issue/PR and tell the owner what changed, why, and any required action.
