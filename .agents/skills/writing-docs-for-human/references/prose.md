# 按需阅读：docs 行文与去泄露自检

> SKILL.md「落笔红线」与「写完自检」的展开。写或改 `docs/` 任一篇时对照。

## 读者与视角

人类读者要知道**现在怎么运作**，不是它怎么演变来的。每段自问：一个刚加入的维护者
只读这段，能不能判断当前行为？

- 用现在时陈述事实（「调度器每分钟扫描一次 outbox」），不用变更叙事
  （「现在改成每分钟」「不再使用轮询」「旧实现是……」）。
- 删会话与提交痕迹：`本 PR`、`上一 commit`、`后续会`、`评审时决定`、`v2` 一律不留；
  真正未做的能力写进对应的模块文档并标明当前边界，不写「即将支持」。
- 不写自证正确（「这样转是安全的，因为…」），改为陈述使之安全的约束。
- 过程复述（「先 X 再 Y」的调试经过、测试走读）不进 docs；只留非显然的契约与失败条件。

## 一个事实只讲一次

- 命令与配置只在 `docs/usage.md` 出现一次；模块文档讲机制，不复述命令。
- 模块文档之间互相引用，不复制对方的段落。
- 理由、被否方案、代价只写在 `.agents/notes/`；docs 的「设计依据」只放链接和一句话说明。

## 术语与检索性

- 领域概念按根目录 `CONTEXT.md` 的词写；同一概念全篇用同一个词。
- 机制名、工具名、状态名、表名、事件名原样保留（含大小写下划线），它们是读者的检索入口。
- 用 must / may / never 一类明确的时序与强制语，别用「建议」「一般来说」糊过去。
- 代码路径写成 `src/agent/skills.ts` 这样的仓库相对路径；不要写本机绝对路径。

## 图

只画两类，用 Mermaid：

- 状态机用 `stateDiagram-v2`：状态、迁移条件、终态。
- 跨模块时序用 `sequenceDiagram`：参与者、消息、返回。

其余示意用表格或文字；示意图不进 docs。
