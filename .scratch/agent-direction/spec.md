# Ruukoto Agent 方向调整：已确认规格

状态：产品方向访谈完成，Q1—Q19 均已由拥有者确认。本文是后续实施的产品依据；代码迁移、平台隔离选型与部署验收尚待实施。

决策日期：2026-10-02。架构取舍见 [ADR 0017](../../docs/adr/0017-two-agent-products.md)，术语见 [CONTEXT.md](../../CONTEXT.md)。

## 两个产品及运行边界

| 属性 | ruukoto-code | ruukoto |
| --- | --- | --- |
| 定位 | Coding Agent，重心是 Agentic coding | Personal Agent，处理多样化个人事务并持续拓展能力 |
| 运行位置 | 开发机器，首期支持 macOS 与 Linux | 专用 Linux 服务器 |
| 主要交互 | TUI | 绑定拥有者的 QQ 私聊、Telegram 等 IM |
| 会话组织 | 多个工作区，每个工作区多个用户会话 | 唯一持续主会话，跨 IM 入口共享 |
| 任务协作 | 主 Agent 与一层 SubAgent | main 与一层 SubAgent |

两个产品在同一仓库复用适用代码，可以独立安装、运行和升级；一端关闭或两端失联时，另一端仍能完成本地任务。共享信息暂时无法同步只影响其新鲜度，不使本地执行依赖另一端。

ruukoto-code 的工作区对应拥有者选择的实际根目录，可以包含多个仓库。用户界面采用工作区 → 会话；临时 Git worktree 是所属工作区的执行副本。现有 Project 关系在迁移时映射，不把迁移前的存储层次继续作为产品层次。

首次启动 ruukoto-code 时按需拉起本机后台，关闭 TUI 后任务继续，显式停止才结束后台。后台异常中断后保留记录并提示恢复，由拥有者决定继续；结果未知的操作不自动重放。

ruukoto 的单会话约束拥有者与 main 的持续对话，不限制内部工作上下文的数量。main 可以委派长任务后继续回应新消息；完整会话历史保留，模型上下文通过既有压缩和按需检索机制控制长度。

## 工作委托、任务与 SubAgent

工作委托是拥有者交给主 Agent 的一项工作，可跨越多轮对话，包含主 Agent 和多个 SubAgent 的执行任务。任务是某个 Agent 的一次具体执行，具有独立状态、结果与授权范围；Agent 身份和上下文可以跨任务保留。这些是领域关系，不要求直接照搬旧 Task 表的存储结构。

两个产品均支持一层 SubAgent。SubAgent 不直接与拥有者交互，也不能创建自己的 SubAgent；它可以与主 Agent 及当前参与同项工作的其他 SubAgent 通信。跨用户会话、工作区或两台机器的直接 Agent 通信暂不加入，消息本身不扩大工具或资料权限。

SubAgent 完成任务后默认进入空闲，保留身份和上下文。主 Agent 可以继续补充原工作，也可以在同一用户会话内将其复用于另一项独立工作；复用后按当前工作重新确定同级通信资格，不延续旧工作的协作关系。与原上下文无关的工作可以新建 SubAgent。

主 Agent 在不再需要后续协作时可以显式关闭 SubAgent，拥有者也可以关闭。任务完成、退出 TUI 和空闲超时均不自动关闭；关闭后保留历史与产物。保留身份不要求空闲时持续调用模型或保留运行中的工具进程。

每次后续委派建立新的任务记录，前一次任务的完成、失败或取消结果不被改写。任务重新确定工具、工作目录、资料范围和有效授权，前一次任务的单次批准不延续。工作目录与 worktree 的生命周期独立于 Agent 身份，复用时须核对实际文件状态。

取消整项工作委托时，停止属于它的活动与排队子任务，不影响其他工作；迟到结果保留供查阅，不重新启动已取消的工作。SubAgent 身份仍可按复用规则用于后续工作，未汇总的改动和产物不得因为取消、工具进程退出或 Agent 关闭而丢弃。

同一份工作文件保持单一写入者。并行编码时，各 Agent 使用独立 Git worktree，由主 Agent 汇总修改并验证；非 Git 目录的写任务串行。独立上下文或不同当前目录不能单独证明不存在共享文件写入冲突。

## IM 交互与操作授权

QQ 私聊和 Telegram 共享主会话。已接收委托完成或失败后，由 main 汇总并自动回复原入口、原拥有者；多个 SubAgent 的结果统一汇报。需要审批时及时通知，普通进度按需提供，不广播到其他入口。

原回复目标停用或绑定变化时不改发到其他入口，暂时离线则等待，发送效果未知不自动重试。原委托最终汇报的授权不扩大为任意主动外发；定时通知及其他外发继续遵循各自明确的授权范围。

Personal Agent 使用专用账户，按明确授权管理整台服务器，绑定的拥有者私聊能够完成审批。平台身份本身不等于通用控制面身份；审批身份、操作及范围仍由宿主核实。

拥有者可以为具体操作和目标保存可查看、可撤销的长期授权，例如允许重启指定服务。范围外操作仍需审批，不默认授予任意 root 操作的长期权限；已存在的审批例外不因角色退役自动放宽。

Coding Agent 在 macOS/Linux 上均提供有技术约束的受限模式，另设拥有者显式选择的完全访问模式。所需执行边界缺失时拒绝启动受限任务，不静默降级；具体技术须经本机和 Linux 验证后选定。

## 共享与外挂边界

共享内容先限于明确选定的个人偏好与通用经验。Agent 可以提出候选，由拥有者确认发布或修改跨端偏好；本端记忆的正常积累不依赖另一端在线。项目约定保留所属范围，完整历史、日程和任务进度不默认同步。

共享记忆不自动开放其来源历史或产物。同步方式、版本冲突、撤销传播及离线副本处理在共享功能阶段定义；本次不承诺这些能力已实现。

去掉固定 coding 角色，其编码、委派与 GitHub 评审职责迁移到新产品和通用 SubAgent 模型。去掉核心 chat 角色，QQ 群聊改为独立可选程序，可以留在同一仓库，自行管理群会话、历史及发送状态，通过有限接口向 ruukoto 提供结果。停用外挂不影响主会话，外挂不属于 SubAgent 层级。

正式 QQ 外挂、跨端记忆、邮件及 GitHub comment 对话在首期三个场景之后安排。具体协议与功能细节在对应阶段确认，不作为首期必须交付的能力。

## 首期验收场景与顺序

以下把已确认的使用目标具体化为检查场景，不代表已经通过实际验收。

1. **本地仓库修改与测试。** 在开发机器上通过 ruukoto-code 打开工作区、建立会话并完成一次代码修改和检查；可使用多个工作区与会话。关闭 TUI 后任务继续，重新连接能查看结果；个人服务器离线不阻止执行。macOS/Linux 的受限模式必须有实际边界，缺少能力时明确拒绝。
2. **通过 IM 管理服务器。** 拥有者通过绑定私聊请求检查指定服务并按授权执行管理操作；需要审批时可在 IM 完成。限定目标的长期授权有效时可执行其范围内操作，范围外仍需审批；结果回原入口，开发机器离线不影响服务器侧任务。
3. **长任务期间持续响应与协作。** main 委派长任务后继续回应新消息；多个 SubAgent 在同项工作内协作，最终汇报自动送回原入口。SubAgent 任务完成后仍可接受原工作或新工作的委派，只有显式关闭才结束身份的可用状态；取消整项工作停止其子任务，不波及其他工作。

并行写入隔离、批准不跨任务延续、重新绑定后不改发、结果未知不重放及历史完整保存，随相关场景一并验证。

## 现有基础与实施缺口

以下为本次访谈核实的代码事实，与目标行为分别管理：

- 当前仅提供 ruukoto 命令；`npm run dev` 与 `~/.ruukoto-dev/` 是开发本项目的隔离实例，不是新 Coding Agent 产品。
- 当前 AgentRoleId 只有 main/coding/chat，dev 是普通开发会话类别。coding 与 dev 的工具类别相同，但 coding 还承担固定委派和 GitHub PR 评审流程，删除角色必须迁移职责。
- 当前 coding 委派进入固定持久角色会话，已有父子任务、幂等、结果、事件与恢复基础，尚无动态 SubAgent 或同级通信。
- QQ 私聊与 Telegram 已共享 main；现有外部入站固定 confirm，审批仍依赖拥有者控制面，IM 审批尚待实现。绑定配置和失效校验在两平台的入站路径并不完全一致，迁移须分别核实。
- 当前 main 没有文件、命令和通用 MCP 工具；服务器管理需要调整实际工具及执行权限边界。
- 当前 local 后端以当前账户启动工具进程，没有操作系统级文件与网络隔离；confirm/full_access 共用 local 启动器，不能作为已实现的 macOS 受限模式。
- 已有多开发会话与按目录归属入口，但 Project 可包含不同目录，尚不是目标工作区模型。现有目录占用覆盖整项任务、不区分读写，不能简单让父任务持锁等待需取得同一锁的子任务。
- 已有完整历史保存、历史查询、有损上下文压缩、记忆来源与版本管理。个人共享记忆目前仅在同一实例内有效，尚无跨实例同步。
- 现有子任务唤醒不自动外发，IM 用户可能只收到“已委派”；原委托异步最终汇报需要实现新的明确发送范围。
- GitHub 当前只处理 PR webhook 和固定 coding 只读评审；邮件及 GitHub comment 通用对话尚未实现。群聊仍与核心 Runtime、资料范围和发送状态耦合，尚未成为独立外挂。

依据：`src/core/types.ts`、`src/agent/tool-availability.ts`、`src/agent/delegation-tools.ts`、`src/agent/execution/launchers.ts`、`src/runtime/orchestrator.ts`、`src/runtime/runtime.ts`、`src/control/workspace.ts`、`src/core/memory.ts`、`src/agent/host-tools.ts`、`src/github/webhook.ts`、`src/tui/index.ts`、`src/dev.ts`，以及 `test/39-coding-delegation.test.ts`、`test/40-qq-private.test.ts` 与相关 ADR。

## 迁移依据与后续工作

迁移保留现有历史、产物和来源关系，记录旧角色、项目与新归属的映射；取消 coding/chat 角色不表示删除历史。工作区迁移不能隐式扩大资料授权范围。

旧方向在 [personal-agent 规格](../personal-agent/spec.md) 与 [daily-agent 规格](../daily-agent/spec.md) 中保留为历史。ADR 0017 明确修订 ADR 0002 的运行位置、ADR 0011/0012 的审批入口与异步回复范围，以及 ADR 0013/0014 的固定角色路径；ADR 0003 的技术权限边界和 ADR 0016 的历史与上下文分离原则继续有效。

下一步实施需要先验证 macOS 的受限执行能力，形成两个产品入口、工作区映射、通用 SubAgent、IM 授权与旧数据迁移的具体方案；随后按上述三个场景交付。隔离技术、存储变更、切换与回退步骤属于工程实施决定，本次不假定为已验证。

拥有者要求 Ruukoto Agent 包含 ruukoto-code 与 ruukoto 两个工具，分开部署和交互；去掉固定 coding，群聊从核心 chat 剥离，main 可使用一层 SubAgent。通过 grill-with-docs、grilling、domain-modeling 与项目要求的 ponytail 核对现状并记录决策。

### 2026-10-02：第一轮 Q1—Q7

拥有者答复“全部按照你的建议”，确认独立运行、单主会话与内部工作上下文、双端一层 SubAgent、有限共享范围、专用账户及 IM 审批、macOS/Linux 和首期三个使用场景。

### 2026-10-02：第二轮 Q8—Q17

拥有者答复“Q10 SubAgent完成任务后不能立即关闭，主Agent依然可以继续委托任务；其余按照建议”。因此，原先任务完成后关闭 SubAgent 的建议被否定，改为保留身份与上下文供继续委托，其余九项建议采纳。

### 2026-10-02：第三轮 Q18—Q19

拥有者答复“全部按照你的建议”，确认同一主 Agent、同一用户会话内可把 SubAgent 复用于另一项工作，并按当前工作重新确定同级通信资格；任务结束默认空闲，由主 Agent 或拥有者显式关闭，不因任务完成、退出 TUI 或空闲超时自动关闭，历史与产物保留。
