# browser 与 bash 模型可见文本审计报告

两个工具都有会让模型调错的文本，最严重的两处如下。

1. **bash 的后台进程会被静默杀掉。** 调用一结束，工作进程就整组回收；描述没写这一点。
2. **open 失败一次，浏览器就冻结。** 页面打不开时，宿主会自动把浏览器置为「不可用并暂停」。接下来的错误文本让模型去做它做不到的事，最后模型多半会 close 再 start，丢掉页面状态。

这两条串起来，正好撞上典型任务「在 bash 里起服务，再用浏览器访问」。后面的发现按工具分组。

审计范围：被审主体是 `snapshot-tools.json` 里的两份定义。结果与错误文本来自 `browser-tools.ts`（下称 BT）、`browser-manager.ts`（下称 BM）、`tool-router.ts.L320-420.txt`（下称 TR）、`tool-worker-worker.ts.L85-155.txt`（下称 TW）。行号都是这些文件里的行号。

## 一、browser

**B1 参数没有任何描述，各动作接受哪些字段只写在校验代码里**
1. 文本位置：快照 `browser.parameters` 的 11 个属性都只有 `type`，没有 `description`。描述只列了动作名，没写各动作吃哪些参数。对应的白名单在 BT L25-29（`ACTION_FIELDS`），多传就拒，见 BT L47：`动作 ${action} 不接受 ${key}`；必填项在 BT L51-52、L64、L68。
2. 规则：J1。
3. 误调举例：
   - `{action:"wait", text:"加载完成"}` 或 `{action:"wait", url:...}`，想等文字或等跳转，会被拒，因为 wait 只收 `ms`。
   - `{action:"scroll", ref:"e5", direction:"down"}` 想滚动某个元素，会被拒。
   - `{action:"screenshot", ref:"e3"}` 想截元素图，会被拒。
   - `{action:"open", url, ms:3000}` 会被拒。
   - `{action:"wait"}` 不带 ms，会被拒（L64）。

   每次被拒都多一轮往返。错误文本只说「不接受 X」，不列出可用字段，模型还可能再猜错一次。

**B2 取值范围、枚举与默认值不可见**
1. 文本位置：
   - `direction` 在快照里只是 `{"type":"string"}`，合法值 `up/down/left/right` 只在 BT L60，错误文本「滚动方向无效」也没给出合法值。
   - `pixels ≤ 100000`、`ms ≤ 25000`、`index ≤ 10000` 只在 BT L61-63。
   - `pixels` 默认 500 只在 BT L161。
   - `key` 的格式（如 `Enter`、`Control+a`）没有说明。
2. 规则：J1。
3. 误调举例：`direction:"bottom"` 或 `"end"` 被拒，错误里没有合法值，只能再猜。等服务启动时写 `{action:"wait", ms:30000}` 被拒。`press` 的键名写成 `"enter"`、`"Ctrl-A"` 这类格式，结果不确定。另外，`press` 失败属于写动作的失败，会落入 B6 的冻结路径。

**B3 open 和 tabs new 的 url 必须是 http/https 绝对地址**
1. 文本位置：BT L54-58：`网页 URL 无法解析`、`网页 URL 只支持 http/https`。快照里 `url` 没有描述。
2. 规则：J1。
3. 误调举例：想测本地 HTML 时发 `{action:"open", url:"file:///…/index.html"}`；或者省掉协议写 `localhost:3000`（会被 URL 解析成协议 `localhost:`）。两种都被拒。也可能先发 `about:blank`，同样被拒。

**B4 attach 的 url 是本机 CDP 端点，不是网页地址；start 与 attach 的区别没写**
1. 文本位置：描述里只有 `start/attach/open` 一串动作名。实际要求在 BM L183-251：必须是 loopback、要带端口、不能带 query 和 hash；ws 形式还必须是 `/devtools/browser/<UUID>`。错误文本如 BM L186「附接需要显式本机 loopback HTTP 或 WebSocket CDP 地址」、L206「CDP discovery 返回非成功应答；不跟随重定向」、L247「CDP 地址必须指向带 UUID 的浏览器端点」。
2. 规则：J1；J2（「CDP discovery」「附接」都是描述里没定义过的术语）。
3. 误调举例：把 attach 理解成「附到一个页面上」，发 `{action:"attach", url:"http://localhost:3000"}`，得到「CDP discovery 返回非成功应答」，看不懂。模型也不知道该先 start，之后可能把 attach 和 open 混着试好几轮。

**B5 tabs 的组合约束与 index 的含义不可见**
1. 文本位置：BT L66-71。switch 和 close 必须带 index；只有 new 能带 url；list 和 new 不能带 index。index 从 0 还是从 1 开始没写；tabs list 返回什么也没写，结果是 BT L166 把第三方数据原样 JSON 透传。
2. 规则：J1；J5（没有承诺 list 结果里会给出 index）。
3. 误调举例：`{action:"tabs", operation:"switch", url:"…"}` 按 url 切换，被拒。`{action:"tabs", operation:"close"}` 想关当前标签，被拒，因为缺 index。`{action:"tabs", operation:"new", index:1}` 被拒。index 从 0 还是 1 猜错，就会切到或关掉错误的标签。

**B6 写动作一失败，浏览器就冻结；错误文本给出的下一步在这个状态下做不了**
1. 文本位置：
   - BM L119-120：任何非只读动作失败（`!isReadOnly(args)`），包括 open 遇到连接被拒、导航失败，都被定为 `outcome_unknown`，文本是「浏览器动作结果未知；已暂停自动化，请核实当前页面，不能重复旧动作」。
   - BM L176、L154 是超时和应答丢失时的同类文本。
   - BM L614-617：execute 的 catch 把绑定置为 `unavailable`。
   - BT L169-171：再自动 pause，把 pauseTaskId 记为当前任务。
   - 描述里只有一句「结果未知时不重发」。
2. 规则：J2；J3；J4。
3. 模型的路径：「请核实当前页面」只能靠 snapshot 或 screenshot 来做。但这时绑定状态是 `unavailable`，不是 `paused`，所以 BM L608 会拒绝，文本是「浏览器连接不可用，本次动作未发送；请先核实原执行并显式关闭」。
   - 模型如果试 resume，BT L129 拒绝：「人工暂停后需要拥有者的新消息」。
   - 剩下唯一能走的路是 close 再 start，这会丢掉页面和登录状态，也等于绕过了宿主想要的「等拥有者核实」。

   真正可行的下一步是：结束本轮，请拥有者核实页面并回复一条新消息；在新任务里先 resume。BM L590 允许从 unavailable 状态 resume，但没有任何文本说出这条路。描述既没交代 unavailable 状态的存在，也没交代宿主会自动进入这个状态；「已暂停自动化」又和实际的 unavailable 对不上，违反 J3。「不能重复旧动作」只是禁令，没配正面的下一步，违反 J4。

   新任务里同样会出错：模型往往先 snapshot，得到 L608 的「请先……显式关闭」，照做就把拥有者刚核实过的页面关掉了。

**B7 暂停态的错误文本只说「等待」，不说怎么等；在新任务里还说错了下一步**
1. 文本位置：BM L607「浏览器正在人工操作，等待拥有者的新消息继续」；BT L129「人工暂停后需要拥有者的新消息；先前排队的任务不能恢复自动化」；BM L590「人工操作后需拥有者的新消息继续，不能由原任务自行恢复」；描述「新消息的新任务才能 resume」。
2. 规则：J2；J3。
3. 误调举例：
   - 在 pause 的同一任务里，模型会用 `wait` 加 `snapshot` 轮询，或者反复 resume。L607 只说「等待」，没说「结束本轮，宿主收到拥有者新消息后会开新任务」。
   - 在拥有者回复后的新任务里，模型直接 snapshot 或 click，得到 L607，被告知「等待拥有者的新消息」。可是新消息已经到了，这时正确的下一步是 resume。模型会再次结束本轮去等，任务就卡死了。
   - 描述没写 paused 状态下哪些动作还能用（status、close、resume）。「新消息的新任务」「先前排队的任务」是内部术语，模型无法判断自己当前是不是这样的任务。

**B8 pause 的结果没给模型转交拥有者所需的指引；dashboard 地址埋在一大段管道字段里**
1. 文本位置：描述写「人工登录先 pause，密码由拥有者在窗口或 dashboard 输入」。pause 的结果是 BT L126、L166 的 `JSON.stringify(BrowserBinding)`，dashboard 地址在 BM L475 生成。
2. 规则：J5；J2。
3. 后果：描述没说 dashboard 地址在哪、要不要发给拥有者，也没说是否有可见窗口（BM L517：macOS 默认有头，其他平台无头）。模型可能不给拥有者任何地址，只说「请在窗口里登录」；在无头的 Linux 上，拥有者根本看不到窗口。模型也可能把 `cdpUrl` 误当成该转交的地址。

**B9 status、start、attach、pause、resume、close 返回整个内部绑定对象**
1. 文本位置：BT L123-134、L166 直接 `JSON.stringify(data)`。字段见 BM L32-55：
   - 标识与路径：`sessionId`、`generation`、`profileDir`、`socketDir`、`cliSession`、`cdpUrl`、`targetId`、`lockDir`；
   - 进程：`chrome/daemon/dashboard` 下的 `{pid,pgid,processIdentity}`；
   - 标志位：`*Pending`、`pauseTaskId`、`pauseAfterSeq`、`outcomeUnknown`、`failureCode`、`headed`。
2. 规则：J5。
3. 误调举例：模型在 bash 里拿这些字段做多余的事，例如 `kill <daemon.pid>`、`ls <socketDir>`、`curl <cdpUrl>/json`。遇到 `stop_unverified`（见 B11）时，模型尤其会用 bash 按 pid 杀进程，这正是宿主要求「须拥有者核实」想避免的。另外，`state` 的五个取值和 `failureCode` 的含义在描述里都没定义，模型无法据此决定下一步。没启动时 status 返回 `null`，也没告诉模型下一步是 start。

**B10 snapshot 只取交互元素，描述没说**
1. 文本位置：BT L161、L139 发的都是 `["snapshot","-i"]`；描述只写「snapshot」。
2. 规则：J5（结果里有什么，要和描述承诺的一致）；J1。
3. 后果：按 agent-browser 的约定，`-i` 只列交互元素；这一点材料里没有直接证据。测试页面时模型想核对正文（例如「Hello world」是否渲染出来），会反复 snapshot、scroll，再 snapshot，找不到文字，最后才想到截图。工具里也没有读取当前 URL 或标题的动作，模型可能用 open 重载页面来「确认地址」，而 open 是写动作，失败就会触发 B6。

**B11 close 失败后没有任何可执行动作，文本也没写停下**
1. 文本位置：BT L133「浏览器停止未核实；保留绑定，须拥有者核实（stop_unverified）」。随后 start 和 attach 走 BM L417「原浏览器未核实关闭，不能新开实例；请先查看状态并显式关闭」，又把模型指回 status 和 close。
2. 规则：J2；J3。
3. 误调举例：status 和 close 来回循环，或者用 bash 自己找进程去杀（pid 从 B9 的结果里拿得到）。文本应该明写：停下，向拥有者报告。另外，BM L417 在状态是 unavailable 时也会出现，「请先查看状态」让模型多调一次 status。

**B12 「核实」类错误文本像是交给模型的任务，其实是拥有者或宿主的工作**
1. 文本位置：
   - BM L399「请准备当前平台 agent-browser v0.39.1 官方原生程序并配置宿主路径」；
   - BM L409「请先准备 Chromium 并配置宿主可执行文件路径；模型任务不会自动安装或提权」；
   - BM L535「请核实系统沙箱与日志准备」；
   - BM L100、L103「请检查原进程后再继续」；
   - BM L296「请核实目录后继续」；
   - BM L610「请先核实停止；不会自动重建实例」；
   - BM L120「请核实当前浏览器连接」。
2. 规则：J2；J4（「不会自动安装」是禁令，没有配正面的下一步）。
3. 后果：模型在完全访问下有 bash，会照着去做：下载 agent-browser、`brew install chromium`、`chmod 700` 目录、`ps` 加 `kill`。L409 虽然写了「模型任务不会自动安装」，但没说模型该停下报告，读起来反而像「那我来装」。这些文本应该改成：停下，把原因转告拥有者。

**B13 描述里写了装配条件**
1. 文本位置：描述「仅完全访问的拥有者 main/普通开发会话」。
2. 规则：J8。
3. 后果：模型会先花一轮确认自己是否处于「完全访问的拥有者 main」会话，或者在不确定时拒绝调用。工具既然可见，这个条件已经成立。同一类问题还有 BT L86 的 access_denied 文本「浏览器仅开放当前完全访问的拥有者会话」，它在任务被取消或不再 running 时也会出现（BT L85）。模型会误以为是身份不对，于是去向拥有者确认权限，而真正的原因是任务已经结束。

**B14 身份或权限变化的错误没有下一步**
1. 文本位置：BT L112「浏览器调用身份或权限已变化」；BT L119 直接把审批的 `auth.text` 作为错误抛出，内容不在材料里。
2. 规则：J2。
3. 后果：文本没说重试是否有意义、是否该停下。模型可能原样重试，甚至换动作重试。

**B15 截图失败与截图结果**
1. 文本位置：
   - BT L152「截图超过 8 MiB；原文件已保留，可改用视口截图」：「原文件已保留」既没给路径，也没有工具能用；「视口截图」没点出对应的参数是 `full:false`，或者干脆不传 `full`。
   - BT L159 的成功结果「截图产物 ${id}（${字节}；${contentHash}）」里，sha256 对模型没有用处。
   - BT L174「请检查数据目录空间与权限」要求模型去查宿主的数据目录。
2. 规则：J2；J5。
3. 误调举例：模型去找那个「原文件」，或者用 bash 查看数据目录、执行 `df`。结果里那串 64 位哈希白占上下文，模型还可能把它当成引用标识，在后续调用里使用。

**B16 生命周期副作用没写**
1. 文本位置：
   - 浏览器跨任务持有（BM L299 注释）；
   - 守护进程闲置 1 小时后退出，被监督进程回收（BM L323、L756）；
   - resume 会换一个新的 generation，旧引用全部作废（BM L594 附近）；
   - close 会结束自己启动的 Chromium，但保留资料目录（cookie 和登录态都还在）；
   - start 只打开 about:blank；
   - 无头还是有头取决于平台。

   描述里这些都没有。
2. 规则：J7。
3. 误调举例：模型每个新任务都先 start 一次，属于多余调用。闲置超过一小时后，模型直接用旧引用 click，得到「浏览器尚未启动或已回收」，这时模型才知道浏览器已被回收。resume 之后用旧引用 click，被 stale_ref 拒绝一次（L138 的文本会让模型重新取快照，所以只多一次调用）。模型也不知道 close 之后登录态还保留，可能让拥有者重新登录。

**B17 内部术语与错误码后缀**
1. 文本位置：BT L138「引用未由当前代次 snapshot 提供」里的「代次」；BT L173 给每条错误追加「（code）」，例如 `（browser_not_ready）`、`（outcome_unknown）`。描述里没定义过这些术语和代码。
2. 规则：J2。
3. 后果：危害较轻，但模型可能把错误码当成要查的东西，或者转述给拥有者。在 B6 那种场景里，`outcome_unknown` 这个码也没对应任何描述里写过的状态。

**B18 重复 pause 时的文本误导**
1. 文本位置：BM L581。已经暂停后再 pause，会得到 `browser_busy`「请等待当前浏览器动作结束后进入人工操作」。
2. 规则：J2。
3. 后果：模型以为还有动作在途，于是 wait 之后再 pause，反复空转。正确的结论是「已在人工操作中，结束本轮」。

## 二、bash

**S1 后台进程在调用结束时被整组杀掉，描述没写**
1. 文本位置：TW L121-126 用 `detached: true` 让命令自成进程组；TW L142-146 在主 Shell 退出后对整组执行 `killTrackedChild`（注释「主 Shell 退出后仍核实原组，后台子进程不能丢失停止归属」）。快照描述只写了「在工作区执行 bash 命令（在任务执行边界内；输出完整捕获为产物）」。
2. 规则：J7。
3. 误调举例：「在 bash 里起服务，再用浏览器访问」时，模型写 `npm run dev &` 或 `nohup python -m http.server 8000 &`，bash 立即返回，看起来成功了。服务其实已被杀掉。接着 `browser open http://localhost:8000` 连不上，open 是写动作，按 B6 的路径直接冻结浏览器，要拥有者发新消息才能恢复。模型还会以为是服务启动慢，重复 sleep、curl、重启服务，多出好几轮调用。描述应该写明后台进程不跨调用存活，并给出可行做法。可行做法本身取决于宿主有没有长驻进程机制，材料里没有，见第三节。

**S2 timeout 的默认值、上限和超时后的行为没写**
1. 文本位置：快照 `timeout` 只写了「超时秒数」。宿主侧还有 `WORKER_CALL_TIMEOUT_MS`（TR L386），超时走 TR L417「工具执行失败：${message}」；中止时整组回收（TW L138-140）。
2. 规则：J1；J7。
3. 误调举例：模型在前台跑服务，或跑 `npm run dev` 这类不会自己退出的命令，不设 timeout，一直阻塞到宿主上限，最后只拿到一句不透明的「工具执行失败：…」。或者模型设了超过宿主上限的 timeout，以为能等那么久。超时后模型也不知道进程已被杀、已产生的输出有没有保留，只好重跑。

**S3 没有 stdin，也没有 TTY**
1. 文本位置：TW L125 `stdio: ["ignore", "pipe", "pipe"]`；描述没写。
2. 规则：J1；J7。
3. 误调举例：运行 `npx create-vite my-app`、`npm init`、不带 `-m` 的 `git commit`、`ssh` 这类需要交互的命令，会立即遇到 EOF 而失败，或者行为异常。模型会改参数重试几轮，才意识到要加非交互参数（`-y`、`--yes`、`-m`）。

**S4 每次调用都是新 Shell，cd 和环境变量不跨调用保留；起始目录没写清**
1. 文本位置：TW L121 每次都 `spawn` 一个新 Shell，cwd 由上游传入。描述只说「在工作区执行」。
2. 规则：J7。
3. 误调举例：前一次 `cd packages/app`，后一次直接 `npm test`，结果在错误的目录下执行；`export FOO=1` 也不会延续到下一次调用。

**S5 每次结果都无条件追加产物提示**
1. 文本位置：TR L401-408。stdout 和 stderr 只要有输出，就各追加一行「[完整正文已捕获：artifact ${id}（${bytes} 字节，bash stdout）——需要更多内容时用 read_artifact 工具按偏移查询]」，不管上游结果是否已经包含了全部输出。
2. 规则：J6；J5（产物 id 和字节数只有在确实截断时才对下一步有用）。
3. 后果：一次只输出几十字节的 `ls` 也会附带一两行提示。模型很快学会忽略它；真截断时反而错过，或者在没截断时多调一次 read_artifact 去「看完整内容」。另外：
   - 上游 bash 工具本身可能已带截断提示或临时文件路径，材料里没有它的结果格式。如果确实如此，两层提示叠在一起，指向两个不同的去处。
   - 提示里的 `read_artifact` 是否就是 `ARTIFACT_TOOL_NAME`（TR L326）的实际值、这个工具是否随 bash 一起装配，材料里都无法确认。如果名字不符或工具不可见，就违反 J2（指向不存在的动作）。

**S6 「任务执行边界」是没有定义的术语**
1. 文本位置：快照描述「在任务执行边界内」。
2. 规则：J1；J2。
3. 后果：模型不知道边界管什么：网络、工作区以外的路径、提权、哪些命令会被拒。可能先试 `curl` 外网、写 `~/.config`、`sudo` 碰壁，也可能过度保守，不敢做该做的事。快照是完全访问会话，这个短语在这里是否还有实际限制，也无法判断。

**S7 执行环境不可用：没有下一步，只有禁令**
1. 文本位置：TR L339「执行环境不可用：${err.message}（不回退到其他执行方式）」。
2. 规则：J2；J4；J5（`err.message` 是内部错误原文）。
3. 误调举例：模型原样重试 bash，或者改用其他工具绕过去（例如用 http_request 代替 curl、用 write 写脚本）。「不回退到其他执行方式」说的是宿主自己不回退，还是禁止模型换工具？模型读不出来。文本应该写明：停下，向拥有者报告。

**S8 输出捕获失败与执行失败的文本**
1. 文本位置：TR L394、L415「输出捕获失败，执行已停止：${captureFailed}」，其中 `captureFailed` 是磁盘写入的原始错误，可能带内部路径，例如 ENOSPC 加产物路径；TR L417「工具执行失败：${message}」，可能是 `aborted by host` 或工作进程超时的原文。
2. 规则：J2；J5。
3. 误调举例：文本没说命令是否已部分执行、副作用是否已经发生，模型会直接重跑。对 `git push`、数据库迁移这类非幂等命令，重跑可能造成重复副作用。磁盘写满时，模型还可能用 bash 去删文件「腾空间」。

**S9 完全访问下每次 bash 都要审批，拒绝时的文本不可见**
1. 文本位置：TR L341-346：`full_access` 时每次都走 `approvals.request`，拒绝就返回 `grant.text`；TR L349 的 `verifyTask` 文本也不在材料里。
2. 规则：未覆盖，无法判断是否违反 J2 或 J3。
3. 说明：如果审批会阻塞，或者拒绝后不再允许同类调用，描述里需要有对照（J3）。材料不足以给出具体误调。

## 三、未覆盖项与跨工具说明

- **系统提示与完整工具列表**：材料里没有。B6、B7、B13、S5、S6 是否会被「模型调用前必然读到的其他文本」抵消，例如系统提示里已经写了暂停流程、产物工具的用法、执行边界的定义，无法核对。按 SKILL 第 3 步，这些条目在拿到完整快照前只能算暂定成立。
- **事件流里的真实结果**：没有。snapshot、open、tabs list 的数据格式（BT L166 原样透传 agent-browser 的数据），以及上游 bash 结果的格式（截断提示、退出码的呈现方式），都只能从源码推断。
- **其他身份的快照**：同一份 browser 定义会装配给 main 和 dev 两种身份，但只给了 dev 会话的快照，无法核对 J8 关于按身份分叉的部分。
- **未见文本**：审批拒绝的 `auth.text` / `grant.text`、`verifyTask` 文本、`ARTIFACT_TOOL_NAME` 的实际值、`WORKER_CALL_TIMEOUT_MS` 的取值。
- **S1 的修复取决于宿主能力**：如果宿主不支持跨调用的长驻进程，「bash 起服务、浏览器访问」这条典型任务就根本走不通，描述应该直说。如果支持，描述要写出用法。材料不足以判断是哪一种。
- **与文本无关但会影响后果的实现问题**：BT L136-140 校验引用时只检查新快照里有没有同名 key，不检查它是否还指向原来那个元素。重新编号后，旧引用可能点到别的元素上。这不属于文本审计的范围，只做提示。

## 四、SKILL.md 本身难以套用的地方

1. **第 3 步的排除条件依赖完整快照。** 「模型调用前必然读到的其他文本已写明正确做法的，不成立」，需要系统提示和兄弟工具描述才能判定。在只摘两个工具的审计里，这条排除既无法执行，也无法确认成立。SKILL 没说在这种情况下条目该记成「暂定」还是「不成立」。
2. **J2 默认错误文本只给模型看。** 很多 BM 文本（「请准备 Chromium」「须拥有者核实」）实际上同时给模型和拥有者看，可能还会上屏或进日志。SKILL 没说同一串文本服务两类读者时怎么写：拆成两份，还是以模型为准、另附转交给拥有者的内容。
3. **J5 没覆盖第三方数据原样透传。** browser 的大部分结果是 agent-browser 返回值的 `JSON.stringify`。宿主是否有义务裁剪第三方字段，「实现管道」是否包括第三方的内部字段，规则没说。
4. **J6 只讲截断提示。** bash 的产物提示既是指针，也承担截断提示的作用。上游工具可能已有自己的截断提示，这时宿主的追加属于「重复」还是「无条件」，J6 没给判断方法，需要上游结果格式才能定。
5. **多动作合一的工具，J1 的「使用点」难定位。** browser 把 18 个动作塞进一个工具，参数又被多个动作共用（url 对 attach 是 CDP 端点，对 open 和 tabs 是网页地址）。约束该写在参数描述、动作说明，还是拆成多个工具，J1 没给取舍依据。
6. **错误码算不算内部术语。** J2 禁止使用未定义的内部术语，但宿主系统性地给错误文本追加 `（code）`。这些代码是否属于这类术语，SKILL 没说。
7. **跨工具的副作用缺少对应条款。** 第 2 步要求把配合使用的工具串起来走，但 J1-J8 都是单工具视角的规则。bash 回收后台进程，导致 browser open 失败、浏览器冻结，这类跨工具连锁只能分别套 J7 和 J2/J3。没有一条规则直接要求描述交代「本工具的副作用会让哪个兄弟工具的哪一步落空」。
8. **量化一节对盲审不适用。** 它依赖 TUI 的 `/prompt` 和 `selection-records`，盲审材料里没有，只能跳过。
