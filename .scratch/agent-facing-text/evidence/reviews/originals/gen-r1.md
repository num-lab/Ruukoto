# SubAgent 工具族模型可见文本审计报告

**审计前提**：快照来自 ruukoto-code 开发实例，是一次新会话首轮的调用（开发会话、完全访问、没有历史失败）。我只读了 `/tmp/aft/gen/` 下的三份文件。很多结果和错误文本是 `deps.delegate`、`close`、`cancelWork`、`message`、`integrate`、`verifyHost` 和 `messageStateText` 在 runtime 层产生的，不在这份源码里，所以涉及它们的路径只按描述审，不对它们的具体文本下结论。

## subagent_delegate

**D1：继续既有工作时只给 work_id 必然被拒，修改工作还会收到误导性提示（J1、J2）**
- **文本位置**：
  - 快照描述写「补充原工作用 work_id（修改继续沿用首次钉定的写入目标）」。
  - `mode` 参数写「仅首次委派可指定」。
  - 源码 249 行 `const mode = params.mode ?? "analyze"`，278–279 行 `if (mode === "analyze" && readPaths === null && materials === null) throw new Error("必须指定分析对象：开发会话用 read_paths，main 会话用 materials")`。
- **会做错什么**：
  - 模型按描述继续修改工作，调用 `subagent_delegate({request:"再补一处测试", key:"k2", work_id:"w1"})`，mode 被默认成 analyze，于是被拒。
  - 错误文本让它补 read_paths，模型就会改成 `subagent_delegate({..., work_id:"w1", read_paths:["src"]})`。这等于把修改工作当分析工作重发，runtime 怎么处理在材料里看不到。
  - 如果模型改为补 `mode:"modify", target:"..."`，又违背了「仅首次委派可指定」。
  - 继续分析工作也一样：只给 work_id 会被拒。描述里「读范围与资料按本次重新确定」只写在 sub_agent_id 复用那一句下，没写在 work_id 继续上，所以每次继续都至少多一次失败调用。

**D2：modify 不能带 read_paths 或 materials，这条约束只在校验里（J1）**
- **文本位置**：源码 261–262 行 `"mode=modify 时不指定 read_paths 或 materials（写入目标包含自己的资料路径）"`。快照的 `mode`、`target`、`read_paths` 描述都没提。
- **会做错什么**：模型想给修改任务附参考资料，会调用 `subagent_delegate({mode:"modify", target:"packages/agent", read_paths:["docs/architecture.md"], ...})`，被拒后再去掉 read_paths 重试，多一次往返。

**D3：分析委派必须带 read_paths，但这一点不在使用点（J1）**
- **文本位置**：
  - 快照 `required` 只有 `["request","key"]`。
  - 描述只说「开发会话用 read_paths 指定资料路径」，没说分析时必填。
  - 源码 278 行负责拒绝。
- **会做错什么**：模型调用 `subagent_delegate({request:"梳理仓库的错误处理约定", key:"a1"})`，被拒后补 read_paths 再调。

**D4：把会话资格和模型无法影响的限制写进描述（J8）**
- **文本位置**：
  - 描述里有「开发会话用 read_paths…；main 会话用 materials…」「受限模式要求父工作区内或父任务已授予」「不能委派下级」。
  - `mode` 参数里有「dev 与 main 均可发起；计划模式与 SubAgent 自身不能发起」。
  - `materials` 参数整条是「仅限 main 会话」，连同四种 kind 的结构一起，出现在这次开发会话的快照里。
  - SubAgent 子会话根本不装配这个工具（源码 67 行）。
- **会做错什么**：
  - 模型不一定知道自己处在「开发会话」还是「main 会话」。它可能调用 `subagent_delegate({..., materials:[{kind:"text", text:"..."}]})`，被 272 行拒绝（「开发会话不能指定 materials」）。
  - 这些条目每次调用都占用注意力。

**D5：非 Git 直接写入时，父任务这一轮不结束，子任务就不会开始；描述和委派结果都没说（J3、J7）**
- **文本位置**：
  - 快照描述写「非 Git 目录直接写入并与父会话串行」。
  - 源码 319 行的委派结果写「直接写入 ${wt.path}（与父会话按目录占用串行）」。
  - 真正的下一步只在 416 行出现，而且只有调 `subagent_result` 碰上排队状态才看得到：「等待本会话释放目录，请结束本轮」。
- **会做错什么**：模型委派之后会在本轮反复调 `subagent_result({work_id:"w1"})` 等结果。它看不到「必须结束本轮」这一进入与退出条件，直到读到 416 行；如果它改用别的方式等待，子任务就一直排队。

**D6：调用何时返回写了，结果怎么送达、要不要轮询没写（J7）**
- **文本位置**：
  - 快照描述写「子任务入队后立即返回，结果完成后经宿主通知，用 subagent_result 读取」。
  - 源码 327 行结果写「完成后宿主会通知」。
  - 实际送达方式见源码注释 18 行：开发会话在下一次模型调用时由宿主注入资料。
  - 截止时间到了会怎样也没写。
- **会做错什么**：
  - 模型不知道通知会自动出现在后续调用里，会在同一轮循环调用 `subagent_result({work_id:"w1"})` 轮询，多出若干次调用。
  - 截止时间过了之后，它也不知道任务会被终止还是只标记，无从决定要不要 `subagent_cancel`。

**D7：委派结果附带分支名和基线提交，诱导模型绕过 subagent_integrate（J5）**
- **文本位置**：源码 317 行 `副本基于提交 ${wt.baseCommit.slice(0, 12)}（分支 ${wt.branch}）`。
- **会做错什么**：模型拿到分支名后，可能直接用 shell 执行 `git diff <base>..<branch>` 或 `git merge <branch>`，而不是调用 `subagent_integrate({work_id})`。这会绕过冲突保护，或者多出几次 shell 调用。结果里真正有用的只有「父工作区未提交的改动不在副本内」这一事实。

**D8：work_id 的前提条件散在别的工具描述里（J1）**
- **文本位置**：
  - 「取消后不能沿该工作继续委派」只写在 `subagent_cancel` 描述里。
  - 「关闭后新委派被拒绝」只写在 `subagent_close` 描述里。
  - `subagent_delegate` 的 `work_id` 参数描述两者都没提。
- **会做错什么**：模型对一个已取消的工作，或 SubAgent 已关闭的工作，调用 `subagent_delegate({work_id:"w1", read_paths:[...], ...})`，被 runtime 拒绝后再新建工作。

**D9：拒绝委派的错误文本没有下一步，而且用的是内部术语（J2、J3）**
- **文本位置**：源码 239 行 `"只有拥有者任务、独立调度运行或宿主保存来源授权的工作唤醒可以委派 SubAgent"`。按源码头注释 8–10 行，回报唤醒轮次只放行 close、cancel、integrate。
- **会做错什么**：
  - 模型在宿主因子任务回报而唤醒的那一轮里想继续委派，调用 `subagent_delegate({work_id:"w1", ...})` 被拒。
  - 错误没说当前该停下报告拥有者，还是等下一轮。「宿主保存来源授权的工作唤醒」这类词模型也无法对应到自身状态，可能换参数重试。
  - 描述也没写这个阻塞状态：进入条件、仍可用的 close、cancel、integrate、退出方式都缺。

## subagent_result

**R1：「artifact_id 见结果中的产物列表」所指的列表不存在（J1、J2）**
- **文本位置**：
  - 快照描述写「part=artifact 按字节分页读该任务的产物（artifact_id 见结果中的产物列表）」。
  - 源码 395–422 行 `part=result` 的输出只有工作行和任务行（状态、父任务、截止、摘要），没有任何产物列表。
  - `artifact_id` 参数没有描述。
- **会做错什么**：
  - 模型先调 `subagent_result({work_id:"w1"})` 找产物，找不到。
  - 接着可能调 `subagent_result({work_id:"w1", part:"artifact"})`，被 454 行拒绝（「产物不存在或不属于该任务的执行」），或者猜一个 id。
  - 除非 runtime 写的摘要里恰好带了产物 id，否则这条路走不通。

**R2：artifact 分页的 length 范围没写（J1）**
- **文本位置**：
  - 快照只写了 reply 的范围「length 为 256–16384」。
  - artifact 的 4–65536 限制只在源码 457–458 行。
  - `offset` 和 `length` 参数没有描述。
- **会做错什么**：模型照搬 reply 的上限，或者调用 `subagent_result({work_id:"w1", part:"artifact", artifact_id:"a1", length:100000})`，被拒后重调。

**R3：总览说是「供挑选继续或复用对象」，却缺少挑选所需的事实（J1）**
- **文本位置**：
  - 源码 374–376 行，总览每条只有 SubAgent 状态、当前工作、名下工作 id 列表、最近任务。
  - 每项工作是否已取消、是分析还是修改（能否汇总）都没有。
- **会做错什么**：
  - 模型从「名下工作」里挑一个去继续，比如 `subagent_delegate({work_id:"w2", ...})`，结果它已被取消，被拒。
  - 或者对分析工作调用 `subagent_integrate({work_id:"w2"})`。
  - 要避免这些，就得先对每项工作逐个调 `subagent_result({work_id})`，多出 N 次调用。

**R4：结果里混入实现管道标识，模型可能拿错 id（J5）**
- **文本位置**：
  - 源码 399 行「发起任务 ${work.originTaskId}」。
  - 402 行「直接父任务 ${t.parentTaskId}」。
  - 340 行和 397 行把 `closedBy`、`canceledBy`（形如 `agent:<任务ID>`）原样输出。
- **会做错什么**：这些都是父会话任务的 id，模型从来不需要引用。但它们和工作内任务 id 并列出现，模型可能误把发起任务 id 当成 `task_id` 调用 `subagent_result({work_id:"w1", part:"reply", task_id:"<originTaskId>"})`，被 443 行拒绝。

## subagent_close

**C1：有活动任务时只给了「由拥有者取消」，漏掉模型自己能做的动作（J4、J2）**
- **文本位置**：快照描述写「有活动任务时拒绝（等任务结束或由拥有者取消）」。
- **会做错什么**：模型自己就可以调 `subagent_cancel({work_id})` 停掉该工作的活动任务，再关闭。按现有文本，它会停下来请拥有者取消，或者反复重试 `subagent_close({sub_agent_id:"s1"})`。即使出于设计不想让模型自己取消，文本也应写明这一点。

## subagent_cancel

**X1：「仍在停止中」没有说明何时结束、何时能复用（J7）**
- **文本位置**：
  - 源码 521 行 `${running} 个任务仍在停止中`。
  - 525 行同一结果里写「SubAgent 未关闭…」。
  - 快照描述写「空闲未关闭的 SubAgent 可复用于其他工作」，但没说取消调用返回时任务不一定已经停下。
- **会做错什么**：模型取消后立刻调用 `subagent_delegate({sub_agent_id:"s1", read_paths:[...], ...})` 复用，此时 SubAgent 还没空闲，被拒。它也不知道该等多久，或该查什么状态（应该是 `subagent_result` 总览里的状态）。

**X2：描述里有模型无法据此行动的内部语义（J8）**
- **文本位置**：快照描述写「效果未知的已有操作只标记、不重放」。
- **影响**：模型据此做不了任何决定，每次调用都占注意力。这一条影响较轻。

## subagent_message

**M1：主 Agent 和 SubAgent 共用一份描述，主 Agent 看到的默认行为对它不成立（J8、J1）**
- **文本位置**：
  - 快照描述写「省略 to_sub_agent_id 发给主 Agent；…（…主 Agent 发送时必填）」。
  - 参数写「省略 = 发给主 Agent；发送方为主 Agent 时必填」。
  - schema 的 `required` 不含它。
  - 源码 106 行注释写明普通会话和 SubAgent 子会话「共用同一定义」。
- **会做错什么**：在这次快照的开发会话里，模型就是主 Agent。它读到「省略 = 发给主 Agent」这一首要说明，可能调用 `subagent_message({work_id:"w1", key:"m1", text:"..."})` 不带接收方，被 runtime 拒绝后补上 `to_sub_agent_id` 重发。

**M2：消息投递会触发一次新的执行任务，这只在「接收方正忙」时说明（J7）**
- **文本位置**：快照描述写「接收方正忙时消息登记为待投递，由宿主机在其当前任务结束后投递为对方的一次执行任务」。接收方空闲时会怎样没写。
- **会做错什么**：
  - 模型不知道给空闲 SubAgent 发消息是否也会立即开出一次执行任务，也不知道这次任务的回答是否要用 `subagent_result({work_id, part:"reply"})` 读取。
  - 它可能对同一补充指示既发 `subagent_message`，又发 `subagent_delegate({work_id, ...})`，造成重复执行。

## subagent_integrate

**I1：「可比较副本与当前工作区」，但模型拿不到副本位置，也没有工具做这件事（J2）**
- **文本位置**：
  - 源码 566 行「如需重新核对，可比较副本与当前工作区；副本原样保留」。
  - 同类表述还有快照描述的「双方成果都保留供处理」、573 行「冲突或验证失败都能找回」。
- **会做错什么**：没有任何结果给过副本路径，委派结果只给了分支名，见 D7。模型要么用 shell 猜测执行 `git worktree list`、`git diff <branch>`，要么反复调 `subagent_result` 找副本位置。冲突后该怎么「处理」或「找回」也没给出可执行的动作。

**I2：结果和描述里有实现管道（J5、J8）**
- **文本位置**：
  - 快照描述写「宿主经工具工作进程取副本相对基线的完整差异」。
  - 源码 572 行写「基线 ${baseCommit}，汇总时父 HEAD ${parentHead…「读取失败」}」。
- **会做错什么**：
  - 「工具工作进程」、基线和 HEAD 哈希对下一步没有用。
  - 「父 HEAD 读取失败」还会让模型以为汇总有问题，进而多调 shell 执行 `git rev-parse HEAD` 去排查。

## 族内共用错误

**G1：模型无法处理的宿主错误没有说明该停下（J2）**
- **文本位置**：
  - 源码 139 行和 181 行「工具调用缺少宿主任务上下文」。
  - 183 行「身份校验失败：${problem}」。
- **会做错什么**：这类错误模型用任何工具都修不好，但文本没说「停止并报告拥有者」。模型很可能用相同参数重试同一个调用。

## SKILL.md 本身难以套用的地方

1. **只给了一份快照，按身份和状态装配的规则核不了。** 步骤 1 只要求写清前提。但 J3、J8 的很多问题只在别的身份下出现，比如 main 会话、回报唤醒轮次、受限模式、SubAgent 子会话。skill 没要求为每种装配身份各取一次快照，审计者只能从源码推断，这和「不读源码下结论」冲突。
2. **一份定义同时装配给多种身份时，J1 和 J8 方向相反。** 「仅限开发会话」按 J8 是模型无法影响的资格，应删掉；可如果模型不知道自己是哪种会话，它又是 J1 要求写在使用点的前提。skill 没给出裁决，比如「按身份分别装配描述」。
3. **J5 只管「多余」，不管「缺失」。** 结果里缺了下一步所需的事实时（R1 的产物列表、R3 的取消状态和工作模式）没有直接对应的规则，我只能借 J1 或 J2 归类。
4. **「模型要引用的标识只留一个」在多实体工具族里有歧义。** 这组工具确实需要 work_id、sub_agent_id、task_id、artifact_id 四种标识。不清楚这条是指每个实体只留一种标识，还是每条结果只留一个 id。
5. **J6 只管截断提示。** 结果末尾无条件附加的操作指引（如 327 行、573 行）算不算噪音，规则没覆盖。
6. **步骤 1 要从事件流取结果原文，这次材料里没有。** 大量结果和错误文本来自 runtime（冲突提示、幂等冲突、复用资格、`messageStateText`），既不在快照里，也不在给定源码里。凡是依赖它们的路径，比如汇总冲突后、同 key 异参后的下一步，这次都没法审。
