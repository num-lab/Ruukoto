## 待拥有者裁决

- **D1 的根因该怎么修**：要么修实现（继续修改工作时不再要求 read_paths），要么只改文本（如实写出"继续修改工作要补任意 read_paths"）。我判断应该修实现，但这超出了文本审查的范围。
- **D4 / M1 / D9 的会话身份信息**：同一份定义同时装配给 dev 和 main 时，模型是否能从系统提示里可靠地知道自己是哪种会话？手头材料只有一份 dev 快照，没法判定（`session-factory.ts:57` 的 dev 提示没提 read_paths）。如果模型确认不了身份，"仅限 X 会话"这类说明就该改成按身份分别装配不同的描述。
- **X2 的处理方式**：改写还是删除，取决于"效果未知的操作"实际指什么。手头材料不足以判断它对模型有没有行动价值。

## 审查者对 SKILL.md 的 6 条意见

1. **单一快照核不了按身份装配的规则：确实是缺陷。** 步骤 1 只要求"写清前提"，没要求按装配身份各取一份快照。D4、M1、D9 的判定都受影响；main 会话独有的文本（materials 路径、唤醒轮次）也会漏报。
2. **同一定义装配给多种身份时 J1 与 J8 方向相反：确实是缺陷。** D4、M1 两条误报都直接出自 J8 的"会话资格……不写进描述"。规则应该区分两种情况：整个工具的装配资格（可删）和同一定义内按身份分叉的参数约束（要保留，或者拆开装配）。
3. **J5 只管多余、不管缺失：确实是缺陷。** R1、R3 都只能借 J1 立论，而 J1 的字面是"输入约束"。缺少决策所需事实的结果目前没有对应规则，这是漏报源。
4. **"标识只留一个"在多实体工具族里有歧义：确实是缺陷。** 结果里的 work、SubAgent、task 三类 id 分别被不同工具引用，三者都必须保留。按字面执行会诱发"删掉必需 id"的误报。应该改成"每个实体只留模型要引用的那一个标识"。
5. **J6 没覆盖无条件附加的操作指引：基本不算。** J6 管的是宿主向工具结果追加的截断提示。工具结果里固定写死的指引（327、573 行）由 J5、J8 管辖，这类情况已经有规则可依，不会因此误报或漏报；最多是 J6 的意图值得在 J5 里加一句交叉引用。
6. **材料里没有事件流结果原文：不是规则措辞缺陷，主要是这次的取材问题。** 不过它暴露了一处小矛盾：前言说"不读源码下结论"，步骤 3 又允许以"产生它的源码行"为位置。而从未在会话里触发过的错误路径不可能出现在事件流里，这类路径只能审源码。建议在步骤 1 里明写这一例外。
