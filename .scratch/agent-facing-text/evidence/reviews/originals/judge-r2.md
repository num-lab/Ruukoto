## 逐条判定

### D1 delegate：work_id 续委派只带 request/key 被拒 — **部分成立（偏误报）**

位置属实：快照 `subagent_delegate.required = ["request","key"]`，`read_paths` 描述只写「最多 16 个」；`subagent-tools.ts:278–279` 确有 `mode === "analyze" && readPaths === null && materials === null → 必须指定分析对象`。规则适用：J1 成立，续委派这条路径上「每次调用都要重新给 read_paths/materials」确实只在校验代码里，描述没写。

但预期误调不成立：拒绝文本同时点名了两个合法参数与两种身份的对应关系（「开发会话用 read_paths，main 会话用 materials」），模型在同一条错误里拿到下一步，重发一次即成功——**一次可恢复的往返，不是被卡死的错误调用**。按 SKILL.md 第 3 步「模型在调用前必然读到的其他文本已写明正确做法的，也不成立」，这条栽在第三步，而规则措辞（J1「只在校验代码里拒绝，等于模型看不见」）只要求「描述里没写」即可命中，诱发了「描述缺口＝真问题」的误判。审查者没有区分「未见过的约束」与「被拒绝后自解释的约束」。D1 若保留，只应作为 J1 的措辞缺口记录，而不是独立发现。

### D2 delegate：「work_id 续修改」这条路径不可达 — **真问题（本轮最硬的一条）**

三处属实且互相咬合：

- `subagent-tools.ts:249` 续委派不带 mode 时 `mode = params.mode ?? "analyze"`；
- 快照 `mode` 描述与源码 223 行：「仅首次委派可指定」，`runtime/subagents.ts:347` 还硬拒 `work_id && mode !== undefined`；
- 于是工具层 278–279 要求 `read_paths/materials`，而描述里 `read_paths` 只说「开发会话用」、`materials` 只说「main 会话用」，没有一个字说**续修改工作也必须回填一项**。

预期误调成立且措辞误导：模型只传 `work_id` 续修改，拿到的是「必须指定分析对象：开发会话用 read_paths」——它正在续一项**修改**工作，却被要求补一个分析对象；而模型任何「补 mode=modify」的自救尝试都会被 `runtime/subagents.ts:347` 拒（原文「work_id 沿用工作原有模式，不能指定 mode」）。补救路径（补 read_paths，然后 runtime 照 `reusedWork.writeTarget` 继续修改）能从 `test/83-subagent-worktrees.test.ts:592` 的 `delegateFromActiveTask({workId, readPaths: null})` 反推出来，但那条路绕过工具层——**面向模型的路径上只有一条会被两条不同错误文本轮流拒绝的路**。这是 SKILL.md 意义上的硬缺陷（J1 命中；错误文本本身也踩 J2「不用描述里没定义过的内部术语指代状态」，把修改工作叫成「分析对象」）。

### D3 delegate：modify 与 read_paths/materials 互斥未写 — **真问题**

位置属实：快照 `mode`/`target`/`read_paths`/`materials` 四处描述均无互斥语；`subagent-tools.ts:261–263` 确实硬拒 `mode=modify` 附 `read_paths`。规则适用：J1 的「互斥组合写在该参数描述或该动作的说明里」正是为这种组合写的。

误调成立且比 D3 摘要说的更强：描述把 `read_paths` 说成「开发会话用 read_paths 指定资料路径」——工具差异按会话类型划分，模型的第一直觉是「dev 会话就要带 read_paths，顺手明确一下范围」。这条与 D2 同源：**首次 modify 不许给、续 modify 必须给**，同一个参数在同一种工作里要求相反，而两处约束都不在描述里。D2、D3 应合并成一条「续修改工作的资料参数语义不可推断」的发现。

### D4 delegate：结果无条件断言「宿主会通知」+ 416 才说「请结束本轮」— **部分成立**

位置属实：`subagent-tools.ts:327` 每次成功委派都追加「子任务已在后台执行；完成后宿主会通知，完整结果用 subagent_result 按 work_id 读取」；416 行「等待本会话释放目录，请结束本轮」只在 `part=result` 命中「本会话持有该 direct 写入目录」这一个分支出现。

判定按三块拆：

- 「同轮反复 `subagent_result` 轮询」——部分成立。dev 会话的结果注入发生在**下一次任务开始**（`parent-delivery.ts:200` 只认 `kind === "dev"`，注入块由 `driver.ts:711` 在任务开始取），同轮内轮询永远读不到；而 `part=result` 的总览/摘要确实会随子任务推进变化，模型有「再等等」的读物。但这条路径下**描述里承诺的「宿主会通知」在 dev 会话里确实不是本轮的**，模型没有别的依据知道要收手；J7「调用什么时候返回、跨调用保不保保留」恰是这条该覆盖的规则。
- 「327 行口头断言 + 416 行状态条件依赖」——不构成 J6 违反。J6 管的是宿主**追加在结果上的**无条件说明；327 行是工具执行返回值的一部分，且是首次委派后唯一告知 `workId/taskId` 的位置，有条件可退。
- 「同轮在副本上动手、等不到 direct 任务」——真问题，且审查者没写。327 行的「后台执行」对 `kind = "direct"` 是字面误导：`subagent-tools.ts:319` 已经说明它「与父会话按目录占用串行」，即父任务不结束子任务根本不会启动，而模型无法从「后台执行」推出这一点。

### D5 delegate：239 行拒绝文本含未定义术语、无下一步 — **真问题**

位置属实：`subagent-tools.ts:239` 原文「只有拥有者任务、独立调度运行或宿主保存来源授权的工作唤醒可以委派 SubAgent」。规则适用：J2 明写「不用描述里没定义过的内部术语指代动作或状态」——「独立调度运行」「宿主保存来源授权的工作唤醒」两个概念在快照的六个工具描述与三份系统提示（`session-factory.ts:44–88`，`dev`/`main`/`subagent`/`workflow`）里都查不到，模型既判断不了自己是否属于其中之一，也没有任何动作可以改变这个判定。

预期误调可信：`subagents.ts:194–201` 的 `ownerOriginated` 允许 `scheduled` 会话、`agentId === "main"` 且带来源授权的父任务等情形，但模型读到这段拒绝后唯一的显性线索是「换 key / 换 sub_agent_id」——这些都会撞上同一条判定（归属与身份与 key 无关），最坏结果是模型改判成「本环境不能用 SubAgent」而对拥有者报告能力缺失。这一条的措辞责任在 runtime 层，但模型看到的就是它。附带：描述确实没写「SubAgent 自身与宿主 GitHub 评审不能发起」，J1 的同类命中（`subagents.ts:327–328、356`）。

### R1 result：描述承诺「产物列表」，结果里没有 — **真问题**

位置属实到无可辩驳：描述（快照与 `subagent-tools.ts:351`）写「part=artifact 按字节分页读该任务的产物（**artifact_id 见结果中的产物列表**）」，而 `part=result` 的产出（`subagent-tools.ts:399–406`）只有「工作 / SubAgent / 发起任务 / 任务 id、状态、直接父任务、截止、摘要」；`part=reply`（451 行）与 `part=artifact`（469 行）都只回自己那一页；总览（374–377）是 Agent 行。全仓搜「产物列表」只有这句描述与 `delegation-tools.ts:106` 的平行措辞，没有任何代码生成过它。

规则适用：J5 后半段「描述承诺结果里会有的事实（例如下一步要用的标识、可供挑选的状态），结果里要真的有」——这条措辞几乎是为本条目写的。

误调成立：产物 id 的真实来源是 `task.resultRef.artifactIds`（`orchestrator.ts:600`），而展示它的只有 `coding_result` 的 `part=result`（`delegation-tools.ts:169`），其描述首句是「读取本会话旧 coding 子任务（**固定 coding 已退役，只读历史**）与 SubAgent 执行任务的结果；新工作用 subagent_result」——模型按指引走，反而拿不到列表。审查者写的两个预期误调（猜 id 被 454 拒、非缺省任务未提示补 task_id）里，前者成立，后者是 R3 的同义重复。

### R2 result：artifact_id / offset / length 无描述、上限只能在错误里拿到 — **真问题（低烈度，J1）**

位置属实：快照三个属性确实只有 `type`，无 `description`；`subagent-tools.ts:456–458` 的 `offset ≤ byteCount`、`length ≤ 65536`、`length ≥ 4` 只在越界时报错。J1 命中无争议。

`length:100000` 被拒后错误文本（`intParam` 的「必须是 0–65536 的整数」）直接给出上限，属可恢复往返，所以烈度低——但 J1 的字面（「每个动作的输入约束（必填项、取值范围…）写在该参数描述或该动作的说明里」）本来就不因可恢复而豁免，D1 与本条的区别只在于：这里模型**没有任何别的文本**能推出取值范围（`part=reply` 的 256–16384 写在描述里，反而强化了「分页长度是有讲究的、artifact 这边是不是也一样」的错误类比）。

### R3 result：多任务 id 并列，取错 id 被拦 — **真问题**

位置属实：`part=result` 同时输出 `work.id`、`agent.id`、`work.originTaskId`（399 行）、每个任务的 `t.id` 与 `t.parentTaskId`（402 行）。规则适用：J5「每个实体只留模型后续要引用的那一个标识」——`part=result` 输出「发起任务」与「直接父任务」，正是该条针对的管道字段。

误调成立但烈度中等：`task_id` 传成工作 id 会落到 443 行的「任务不属于工作 X 或不提供 task_id 时尚无执行」（同一 `?? null` 分支），错误文本没有指向真实原因；传成 `parentTaskId` 同样落 454 行的「产物不存在或不属于该任务的执行」。两者都可恢复。判定为真问题，但应归到「结果里列了模型后续不需要引用的标识」这一条，而不是审查者摘要里的「拿父任务 id 当 task_id」。

### C1 close：描述「等任务结束或由拥有者取消」— **误报**

位置属实，规则不适用。`subagent_close` 描述「有活动任务时拒绝（等任务结束或由拥有者取消）」与 `subagents.ts:680` 的拒绝文本一致，而该分支在 cancel 之后仍然可达：`cancelTask` 对 running 任务走 `driver.requestStop`（`runtime.ts:3695`），`subagents.ts:521` 保留了「N 个任务仍在停止中」，此时任务仍是 `running`，close 依旧被拒。

审查者漏掉的是**同轮就有的合法动作**：`subagent_cancel` 本身就在模型的工具列表里（快照第 4 个工具），而 `session-factory.ts:57` 的 dev 系统提示原文写着「不再需要的工作用 subagent_cancel 取消（已取消的工作不能继续委派）；不再需要后续协作时用 subagent_close 关闭」——两句话相邻，顺序就是先 cancel 后 close。按第 3 步「模型在调用前必然读到的其他文本（系统提示、兄弟工具描述…）已写明正确做法的，也不成立」，这条不成立。J2/J4 也不适用：「由拥有者取消」是**状态事实的陈述**（谁有权终止子任务），不是要模型去做的动作，描述没有要求模型请拥有者代为取消。

### X1 cancel：描述未写停止是异步的 — **部分成立**

位置属实：快照 `subagent_cancel` 描述通篇无「停止是异步」；`subagents.ts:521` 确有「N 个任务仍在停止中」这个只在收尾未完成时出现的分支。J7 适用（跨调用状态、调用何时算真的结束，模型从结果推断不出）。

误调不成立：`cancelWork` 在事务外 `await Promise.allSettled(prepared.stopping.map(...))`（`subagents.ts:768–769`）后才返回，调用方语境下它是**等到底**的；「仍在停止中」只在极窄的未回收窗口出现，且结果里那句本身就是模型拿到的唯一新信息。所以「立即 close/复用被拒」不是描述缺口导致的必然误调，而是那个窗口下的真实竞争结果，模型重试一次即可。

规则措辞的责任：J7 列的是「调用结束时被清理的资源、调用什么时候返回、跨调用保不保留」，本条的「停止」既不是资源也不是返回值，是**外部进程的停止进度**，覆盖得比较勉强。审查者把它套上来，规则与发现的错配比描述本身更值得记。

### M1 message：同一定义装配给父会话与子会话，主 Agent 必填项靠推理 — **部分成立（实为误报）**

事实核对：属实且比审查者说的更明确——`subagent-tools.ts:67` 里 main/dev 装配六个工具（含 `subagent_message`），`sub_agent` 只装配 `subagent_message`；`session-factory.ts:65`（main）与 `:57`（dev）的系统提示都提到 `subagent_message`。

但规则与误调都不成立：描述原文「省略 to_sub_agent_id 发给主 Agent；指定则发给该 SubAgent（…；**发送方为主 Agent 时必填**）」——这句话把身份与约束并列写在同一句里，是 J8 说的「让模型能确认自己的身份」的一种写法（身份由「谁是发送方」这一模型自明的事实给出，不需要运行时自省）。runtime 的拒绝文本（`subagents.ts:856`「主 Agent 发送时必须指定接收的 SubAgent（to_sub_agent_id）」）与之逐字对应。

误调不成立：审查者设想的路径是「主 Agent 不填接收方被拒后查 id 重发」——但主 Agent 不填的依据来自哪里？描述写的是「省略 = 发给主 Agent」，这句话对主 Agent 而言是**语义上说不通**的（不能发给自己），模型据此就能推出必填。J8 的措辞（「模型会花推理判断一个已成立的条件」）确实容易被读成「任何需要推理的地方都算」，这是本条误报的诱因；但 J8 的意图是防「工具可见即已满足的装配条件被写进描述」，与本条相反——这里缺的不是装配条件，是**写给子会话的默认值被父会话误读**，而描述已经把它标出来了。

### I1 integrate：「双方成果都保留供处理」但副本路径从未给出 — **部分成立（原表述偏误报，真问题在另一半）**

事实核对推翻了审查者的核心断言：「副本路径从未给出」不成立——`subagents.ts:1084–1087` 的冲突拒绝文本原文含「父工作区原改动与副本成果 **${target.path}** 都保留，未写入任何字节。冲突明细：…。待处理：由你或拥有者在父工作区核对差异后手动处理，或让 SubAgent 继续修正后再汇总」，冲突场景正是模型唯一需要去比对副本的场景，路径与两条出路都在那里。

但同一件事在**成功与幂等两条路径上没有做到**：`subagent-tools.ts:566`（`state: "already"`）只写「如需重新核对，可比较副本与当前工作区；副本原样保留」，573 行（success）同样只说「副本原样保留（取消/关闭都不删除），冲突或验证失败都能找回」——两处都不给分支名或路径。dev 会话手上有 bash，副本分支是 `ruukoto/work-<workId>`（`work-copy.ts:158`），可从 `git worktree list` 找到（默认用户配置按 `glob` 的 dev 会话确实有 bash），所以「找不到」不成立；但 main 会话的系统提示明写「**你没有编码工具**」（`session-factory.ts:65`，其工具面是 `subagents + app_data + notification` 一类），对它而言「可比较副本与当前工作区」确实是描述里没有工具能完成的事——这才是 J2「不要求模型做它无法用任何工具完成的事」的正中靶心，而审查者把它写成了主结论的附属。

判定：真问题应改写为「`state=already` 与汇总成功的结果文本要求模型自行核对副本，但这两条路径是 main 会话唯一会看到的，且没有工具可用；冲突路径已有 `target.path`，可见作者知道该给什么」。审查者摘要里的「git diff/worktree list 找副本，多次调用拿不到改动」是误报。

### 未列为发现的项

- **integrate 在子任务未结束时**：`subagents.ts:1074` 的拒绝文本「工作有活动任务 X：等该执行结束后再汇总」给出确定状态与下一步；`subagent_tools` 描述虽未写此约束（J1 的轻微命中），但补不出一条会因此失败的误调。审查者的放过是对的。
- **mode 描述中「计划模式与 SubAgent 自身不能发起」**：属实（`subagents.ts:333` 与 327–328），但模型无法在调用前知道自己在计划模式（`planMode` 由宿主置位），写完也无从行动——放过是对的，属于 J8 该排除的噪音。
- **审查者漏掉的两处**（供参考，非本次判定项）：327 行「后台执行」对 `kind === "direct"` 的字面误导（见 D4 第三块）；`subagent_result` 描述只写 `part=messages` 与 `part=reply` 的部分语义，而 `part=result` 在「非 Git 写入排队等待父释放」时会插入一句「请结束本轮」——这句话所在分支的触发条件描述里没有，模型无法预判自己会不会读到它。

## 待拥有者裁决

1. **D1/D2/D3 是否合并计一条。** 三条都落在 `subagent-tools.ts:257–280` 的同一段校验上，根因是「续委派必须重申资料参数」这条约束没有落点。按 SKILL.md 一条发现对应一个文本位置的口径，分三条会重复计分；按“模型会做错的调用”口径，只有 D2 的路径会连续失败。需要拥有者定「同一段校验多条发现如何计」。
2. **D4 的烈度判据。** 「dev 会话同轮轮询读不到结果」是真实的模型行为，但描述要不要为此写一句「结果在本次任务结束后注入」，取决于本仓是否接受把 driver 的生命周期写进工具描述——`parent-delivery.ts` 的注释把 dev 与 main 的送达差异写得很清楚，模型看到的却没有。属产品取舍。
3. **D1 里「可恢复的单次往返」算不算 J1 命中。** 本报告的判法（不算）与 SKILL.md 第 3 步措辞（只要「写不出具体误调」才不成立，而 D1 写得出来）不一致；两者谁优先，本材料判不了。

| 1 | 第 3 步排除条件依赖系统提示，缺材料时口径未定 | **不是规则缺陷，是任务材料问题。** 第 3 步原话就是「系统提示、兄弟工具描述、引出该状态的上一条结果」，把系统提示列为必读；真正的问题是本次材料只给了 `snapshot-tools.json` 的 `tools` 字段，没有 systemPrompt。C1、M1 两条误报都源于审查者没去读 `session-factory.ts` 的系统提示，属于自身失误。 |
| 2 | 模型自己要用的内部路径卡在 J5 与 J2 之间 | **是真缺陷。** 副本路径既是「内部路径」（J5 禁）又是「模型核对冲突要用的地址」（J5 只豁免了「要转交给拥有者的地址」），I1 的判定完全取决于这句怎么读。建议 J5 把「模型自己的下一步要用」与「要转交给拥有者」并列为例外。 |
| 3 | J8 以推理成本为动机，与第 3 步「必须写具体误调」冲突，纯描述噪音一律不成立 | **部分是真缺陷。** J8 举的两种后果里，「据此拒绝调用」是具体误调，「花推理判断一个已成立的条件」确实只到「浪费」的层级，而第 3 步要求写得出具体误调——两条规则对同一句话要求不同证据标准。但「一律不成立」说过头了：M1 的误报不是 J8 判出来的，是审查者自己把 J8 用错了位置。 |
| 4 | 结果里无条件追加的固定句无规则直接覆盖 | **不是必要补充。** 覆盖它的正是 J5 前半段与 J6 的合并读法：结果要给决策下一步所需的事实，模型会把它当背景忽略的固定句就是「非决策所需」。真正缺的不是规则，是 J6 只写了「宿主追加的提示」而没写「工具自己追加在结果里的固定句」——属于措辞收窄，可以补一句，但不是会导致误报或漏报的缺陷（无实例）。 |
| 5 | J8「让模型能确认自己的身份」未给判断标准 | **不是会导致误报漏报的缺陷。** 判断标准与 J1「写在使用点」是同一套：身份信息必须在模型**调用前**可读的文本里。审查者以此为 M1 辩护，恰恰说明按字面读这条会过度触发——但这是 J8 的性质（正向建议），不是措辞漏洞；真要改，改成「身份相关的参数约束要写在参数描述自身」即可，与本条意见方向一致但落点不同。 |
| 6 | 拒绝文本多在 runtime 层跨包，审计边界未划 | **是真缺陷。** 第 3 步的「没触发过的路径从源码取并注明」没说去哪个包取；至少 D5、R1、I1、X1 四条的真伪完全取决于 `packages/runtime/src/subagents.ts` 里的文本，而该文件不在被审对象目录内。建议在第 1 步或第 3 步写明：跨层错误文本也算被审文本，取不到就标「未覆盖」。 |

**净评：** 6 条里 2 条（#2、#6）指出的是会导致实际漏报的规则缺陷，#3 指出的证据标准冲突成立但结论夸张，#1 归错因，#4、#5 属于可以写得更细但不影响判定准确性的收窄。反过来，**本轮 13 条发现里有 5 条（D1、D4 部分、C1、M1、I1 的主结论）的失准源于审查者没查系统提示、没查 runtime 错误文本原文**——这两件事都不需要改 SKILL.md，只需要材料里补上 systemPrompt 快照与 runtime 层拒绝文本清单。
