# 模型可见文本的编写标准

Status: resolved

## 目标与边界

为「宿主写给模型看的文本」立一份编写标准与审计方法，让下一次工具描述出缺口时能在评审阶段被发现，而不是靠真实会话里模型连续误调来暴露。

范围是产品运行时进入模型上下文的文本：工具名、描述、参数 schema 与参数描述，返回给模型的结果与错误文本，系统提示与参考块里宿主写定的措辞，宿主向工具结果追加的提示。

非目标：

- 不改任何工具描述、参数 schema 或错误文本。按它审出的差异另开工单，见「下一步」。
- 不覆盖面向开发者 agent 的 `.agents/skills/`、`AGENTS.md`。这类文档由 [prose-standard](../../../.agents/skills/prose-standard/SKILL.md) 与全局 `writing-for-agents` 覆盖。
- 不新增门禁脚本。判断是语义的，机械检查会退化成关键词扫描。
- 不修改 bash 工具描述（宿主在 `tool-router.ts` 定义）；本轮只把它作为审计对象。

### 交付物

1. `.agents/skills/agent-facing-text/SKILL.md`

   frontmatter 的 `name` 为 `agent-facing-text`，`description` 写触发条件：写或改模型可见的工具定义、参数 schema、工具结果与错误文本、系统提示措辞时使用。正文三段：

   - **审计步骤**：从 prompt 快照取出模型实际看到的工具定义与错误文本，逐条核对，而非只读源码。被审对象是模型看到的那份文本。

### 硬规则清单（J1–J8）

下列为规则的一般陈述，可直接作为 `SKILL.md` 的底稿；与本次案例的对应关系只在下文案例表里出现。

- **J1 动作前提写在使用点。** 每个动作的输入约束写在该参数描述或该动作的说明里，不能只靠校验代码拒绝。
- **J2 错误文本给出当前状态下真实可执行的下一步。** 本状态下已关闭的能力不写进提示。没有可执行动作时明写「停下来报告拥有者」；不写模型无法用任何工具完成的要求，也不用内部术语指代动作。
- **J3 阻塞状态要在描述里有对照。** 工具存在会冻结自动化的状态时，说明进入条件（包括宿主自动进入的情形）、本状态下哪些动作仍可用、退出方式与谁能触发退出。同一机制服务多个用途时，描述不能只写其中一个。
- **J4 禁令要配正面的下一步。** 写清楚此时的正确做法，以及该禁令在什么范围内有效、换了什么条件后不再适用。
- **J5 结果只含决策下一步所需的事实。** 进程标识、内部路径、连接端点、内部版本号这类实现管道不进结果；模型需要引用的标识只留一个。
- **J6 宿主追加的提示只在真的截断时出现。** 无条件追加的说明是噪音。
- **J7 写模型看不见的生命周期副作用。** 调用结束时会被清理的资源、调用何时返回、跨调用会不会保留，模型无法从结果里推断，要在描述里写明。
- **J8 描述只写模型能据此行动的内容。** 装配条件、会话资格这类工具可见即已满足、模型也无法影响的限制不写进描述。

### 工程验收方法

1. **盲审。** 实施者从一次新开、无失败记录的 ruukoto-code 普通开发会话的 prompt 快照中摘出 browser 与 bash 的工具定义，连同产生模型可见结果与错误的源码（`browser-tools.ts`、`browser-manager.ts`、`tool-router.ts` 的结果追加段）交给独立审查者。审查者只读 `SKILL.md` 及上述材料，不读 `references/cases.md`、本工单、诊断、原会话与本工单的审查记录，出报告。实施者把报告与案例表比对，记录命中与遗漏；不把比对结果告诉该审查者。
   - 证据记录交给审查者的 `SKILL.md` 的 SHA-256。
   - 交付前检查：`SKILL.md` 中不出现案例标识 `file://`、`http/https`、`outcome_unknown`、`browser_not_ready`、`browser_paused`、`resume`、`socketDir`、`cdpUrl`、`核实原执行`、`artifact`、`nohup`、`main/dev`。检查命令与输出写进证据。
2. **补规则后重审。** 有遗漏时回 `SKILL.md` 补规则，不往 `cases.md` 加案例。补的规则同样只写一般陈述，并重跑第 1 步的标识检查。`SKILL.md` 每改一次，盲审与泛化审都按新哈希重跑：盲审换一个新的独立执行上下文，泛化审用第 3 步的同一材料。通过条件：第 1、3、4、5、6、8、9、10 条全部命中，第 2 条归入 J7。补规则最多两轮；两轮后仍有遗漏，保留待验收，把遗漏项与已试规则整理成一个问题交拥有者决定，不降低命中要求。
3. **泛化审。** 被审对象是 SubAgent 工具族（`subagent-tools.ts`）：两个产品都装配，取同一份 ruukoto-code 普通开发会话 prompt 快照里的定义，连同产生其结果与错误的源码；实施者把文件清单写进证据。审查者同第 1 步，照 `SKILL.md` 审，每条发现写明三项：模型实际看到的文本位置（快照中的工具与字段，或源码行号）、对应规则、模型据此会做错什么（具体的错误调用或多余调用）。缺任一项的发现直接记为不成立。
   - **判定者**：独立实现审查者，不由实施者或出报告的审查者兼任；按上述三项逐条判定真问题或误报，有争议的条目整理给拥有者。
   - **误报的处理**：追溯到引发误报的规则措辞，在 `SKILL.md` 改成一般陈述，然后按第 2 步重跑。
   - **通过条件**：判定后没有未处理的误报，并且改过规则后，用同一材料复审一次，不再产生新的误报。泛化审不衡量召回率：被审工具族没有已知缺陷清单，召回率由盲审衡量；也不要求必须发现真问题。
   - **真问题的去处**：写进报告，留给后续修复工单，本轮不修。
4. 两次审查都只出报告，不修改工具文本。

### 记录方式

工程验收逐项对应要求与证据，写清审查者角色、日期、被审内容、命中数与遗漏项，以及未覆盖项。产品验收不适用：本任务没有主观体验取舍，skill 的效果由上述盲审与泛化审证明。没有可用的独立审查者时保存待审状态，不自行补一个通过结论。

验收后按 Q11 的结论另开工单：按 skill 审 browser 与 bash 的模型可见文本，把上述两次审查报告作为输入。
