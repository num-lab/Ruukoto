## 一、隐藏内部回报输入

沿 `getWorkflowDeliveryRun(store, taskId)` 的真实持久绑定派生输入用途，在任务与历史返回视图提供同一种宿主分类。禁止根据 `[工作流最终回报]` 文本、请求键前缀或前端猜测分类；拥有者输入相同文字仍正常显示。

历史页依据既有 `ruukoto_task_start/end` 标记关联原任务，分支历史核实 `branchSource.taskIds`。分类随首屏和每页历史返回，先于 `seedInputHistory`；`Runtime.readHistoryEntry` / `TuiApp.loadEntry` 的单条补读同样带分类，覆盖 `EventFlow.task/addHistory`、输入框 ↑ 历史、sticky prompt、重连和历史翻页。缺少可信绑定时按普通消息保留，不能用正文猜测隐藏。历史标记损坏按现有历史错误处理，不静默丢消息。

保持 JSONL、上下文选择与压缩语义；诊断历史和工作流日志仍可追溯原文。当前 SDK 的 custom_message 虽可设 display:false，但仓库的历史读取、检索和上下文分组未完整支持，本次不切换消息存储形态。控制视图新增字段同步协议与调用方，按仓库版本规则处理。

## 二、等待工具与调度

工具暂名 `agent_wait`，置于共享宿主工具能力；可用于两个产品中已有查询/管理目标资格的主 Agent，不向普通 SubAgent、工作流步骤或无工具汇总身份开放。参数为有界的类型化目标列表与可选等待时限，任务目标固定 taskId，工作流固定 runId；一次调用至多 20 个目标，默认 60 秒、上限 300 秒。边界由宿主校验，拒绝空列表、自等、重复目标、跨来源或失去读取资格的对象。目标不存在明确报错，不跳过。

本轮多目标仅支持同来源会话、同原始发起任务/拥有者事件、同钉版回复目标及代次的一组结果；SubAgent 依据 work.originTaskId，工作流依据 source.taskId 和原事件归组，定时来源还须同 schedule_run。整批校验，跨来源组合明确拒绝并提示分别处理；同一父轮后续调用也不能混入第二报告来源。此限制不影响一次发起多个子任务/工作流后共同等待，不建设跨来源合并报告能力。

采用提交后事件驱动，先订阅、再读持久事实，结束时清理订阅、计时器与 AbortSignal。返回包含原因、逐目标当前状态和已登记的有界结果/产物引用；正常原因区分 result、attention、timeout 和 interrupted。任务终态与 resultSummary 登记齐备才可返回结果；工作流返回固定 terminalVersion 的最终事实快照，不等待 `delivery.reported`，并保留停止未核实和效果未知字段。部分成功、失败、取消、中断都是结果，不转为成功。

任一目标出现结果即返回；人工问题、工具审批、暂停或需要核实的停止也可提前返回 attention，即使工作流整体仍为 running。新的等待调用可针对剩余目标继续等待。超时只关闭本次等待，不结束原任务、不撤销工作；未完成状态持续可见，不靠模型反复查列表轮询。

### 安全让出与恢复

等待登记包含调用任务、SDK 调用标识、固定目标、到期时间、状态与中断原因，状态和事件同事务保存。任务仍承担原工作，等待不是 completed，也不是放宽授权。Driver 在明确工具边界进入等待阶段，禁止同任务并行启动其他工具或新模型请求；当前其他调用必须先完成，受管执行单元须安全停止并核实，才能释放目录占用。不能安全让出时返回明确原因或进入现有待核实路径，不释放占用、不谎称已等待成功。

停止与恢复覆盖原生受限、完全访问及宿主工作副本执行；不能只释放三个子 Agent 名额，因为父目录才是已发现的互等点。让出后唤醒等待目录的队列。恢复涉及工作目录的输入装配或业务工具前，按既有规则重新取得所需目录，重核会话身份、原权限版本、资料授权、目录身份和取消状态。等待恢复中的占用竞争保持可中断；未取得时展示“等待执行资源”，不能绕过占用或忙循环。

仅在工具返回前重取目录仍不足以保证聊天：非 Git 子任务可能持有同目录长时间运行或等待审批。因此新增内部对话阶段，result、attention、timeout 与可信新输入可在未取得工作目录时处理，包括任一结果已到但另一目标仍持目录的情况。此阶段只从已记录会话、固定结果与已核实参考快照装配模型输入，不读取当前工作目录文件、不启动工具 worker；显式允许 `agent_wait` 及不访问工作目录的宿主状态/结果查询，取消等控制仅在逐项证明无需目录且沿原授权时开放。其余工具默认禁用，包括项目读写、bash、MCP、workcopy 与未分类工具；工具清单、发送前检查、调用门和执行入口一致收窄，阶段及模型可见说明进入记录。这是内部资源阶段，不新增拥有者访问模式。

Runtime 新任务领取、Driver 初始化和上下文装配必须支持上述阶段，不能先执行旧的整 Task 抢目录或 worker 初始化再声称可聊天。包括 `ContextAssembly.loadPinnedContext/loadProjectInstructions`、Driver 的技能加载与无条件 `planMcp`：此阶段不现场读取项目指令/技能文件、不启动 MCP，只使用已持久且仍获授权的快照；必要输入缺快照时显式记录和呈现资料缺口，不偷偷丢掉指令或读取被占用文件。原身份与来源权限画像继续钉版，资源阶段只进一步收窄能力；在同一 Driver 内更新阶段、SDK 工具集合与选择记录，不在旧 prompt 未退出时重建 SDK 写入者。转回业务执行须经过唯一资源取得入口，尚未取得时业务工具明确返回资源未取得，模型仍可解释等待原因并继续等待，不能让隐藏工具名绕过调用门。单会话仍只有一个 Driver 和一个历史写入者；后台同目录子执行不因主聊天而被取消。

Runtime 在新拥有者输入已通过身份/原入口校验并成功提交后撤销本次等待资格，结束旧轮的等待执行并让队列处理新消息；重复请求、内部回报和普通事件不触发。不得走整项工作取消路径。晚到的结果不能再次恢复旧 Driver，后台任务继续按原授权运行。既有一会话一个 Driver 和一个 JSONL 写入者保持成立；不得在旧 Driver 未退出时启动同会话新 Driver。

用户新消息打断后不自动恢复旧的任意模型执行；本次等待返回/中断事实落盘，结果送达责任退回持久补报路径。用户可在新轮明确继续等待。后台重启沿现有普通任务 interrupted 规则终止旧内存等待，先恢复占用核实和未完成送达，不自动重放原工具或业务步骤。新消息打断与后台重启都不把后台工作标为成功或隐式取消。

### 唯一消费与报告归属

结果进入会话记录、结果已供模型使用、最终总结完成是三个阶段。为 SubAgent 结果和工作流终态代次登记独立的消费/报告认领事实，复用现有父级送达入口，避免另建一套通知器。工作流按 `(runId, terminalVersion)` 仲裁报告归属；记录等待父任务认领与既有独立汇总两种归属，不能把普通父任务写入现有 `delivery.taskId` 冒充无工具汇总身份。

活动等待登记后，终态报告路由在同一事务核实等待资格：可交给等待父轮时先登记预留；若已有独立汇总仅排队未开始，可通过持久 CAS 转交并撤销其待运行资格；已经开始或完成汇总则不再授予新的最终报告权，等待结果携带已有报告归属。等待对象即使先于订阅完成也按同一规则处理。

工具结果先写入会话记录，以 SDK call/entry 标识核实，再在下一次模型请求接受该结果时记录消费。SQLite 与 JSONL 不宣称原子；崩溃后按已有消息标记补记，未证明进入模型不能当作送达。普通 dev 的下轮注入与 main 的 wake 共用这份消费依据，不能再注入同一已消费结果。

认领或消费结果时，把目标来源及步骤结果的资料依赖闭包持久绑定到父轮，独立于 `delivery.taskId`。等待返回后每次模型请求、最终回复登记和实际 outbox 发送都重核这份来源集合；不能只在第一次恢复时核实。撤销、来源换代或权限失效拒绝后续使用和发送，按事实释放认领或记 undelivered，不把旧结果换到新来源。此扩展需接入 Runtime 的模型请求核实、ParentDelivery 以及 channels 的发送前复核；普通 owner_reply 路径也受被合并报告依赖约束。

正常父轮可继续检查和执行已授权后续步骤；其最终回答按认领的目标集合完成报告登记，适用 IM 仍沿原事件、原目标代次和稳定发送键登记。多个工作流由同一父轮汇总时只发送一份该轮总结，每个运行链接同一报告，不逐个发送相同正文。普通父轮的 owner_reply 与工作报告在结果事务内共用报告/发送槽：先确定认领集合和来源相容性，再由 `recordInboundTerminal/wakeTerminal` 共同登记一个 outbox 操作，不能先按当前事件发送，再按原工作后缀另发一份。当前父轮普通回复目标与原报告目标必须一致且代次有效，否则拒绝接管；原事件关联保留，后台补报仍按原来源核实。调度来源由原 schedule_run 汇总拥有者回报，不新增直接外发。

新输入、显式中断、权限变化、父轮失败或重启都先仲裁报告是否已完成：已记录最终回复/外发操作的只补关联事实；尚未完成的释放认领，原 `sweepWorkflows`/父级送达按原键补报。普通 dev 的 SubAgent 现只在下一任务注入，不能直接沿用为自动补报：为曾被等待覆盖而未完成报告的普通子任务登记持久补报资格和稳定键，结果提交与恢复巡检按该资格补建无工具汇总任务，即使新消息轮已结束也会送达。未经过等待的普通委派保持现行规则；取消工作仍阻止唤醒。模型正文已落盘但任务结果未登记时按已有任务边界核实，不能先盲目再生成；无法确认时保留可见的待核实状态与原文，不能以成功或新发送键掩盖不确定性。失败或未知发送不自动重发，不改发到最新入口。

新增普通子任务补报的内部输入也从其持久补报资格派生用途，接入 09 的任务/历史隐藏分类；它没有 workflow.delivery.taskId，不能只沿工作流绑定判断。内部提示不进入聊天、置顶及 ↑ 历史，最终 assistant 总结仍显示。

### 先验证的三个机制

10 先用最小离线 Runtime/Driver 用例证明：父等待时真实修改工作流及非 Git 子任务可执行；新输入与结果同到时只有一个继续执行者；父轮接管、失败回退与原汇总竞争时没有双重报告。特别验证非 Git 子任务持同目录且等待审批时，attention 与新输入仍能在受限对话阶段处理，项目工具仍被拒绝、项目指令/技能不偷读、MCP 不启动；Coding 新输入轮先结束、普通子任务随后结束时会自动补报。报告负例覆盖首次恢复之后、第二次请求或实际外发之前撤销资料，跨来源批次拒绝，普通 owner_reply 与同来源多个工作报告共用一份 outbox。必须覆盖真实目录占用、工具停止和会话记录，不以计时器替身冒充这些保证。任一机制与已确认目标不相容时退回方案审查，不交付只读目标专用等待或仅完成通知来降低要求。

## 三、侧栏与请求状态

扩展当前 TUI 组件布局，宽屏给侧栏独立空间，焦点切换有可见提示；键盘动作沿现有约定，Esc 返回一层，在根层关闭；窄屏采用现有独立窗口形态并保留所在层与选择。窗口关闭、客户端断开不改变后台运行。工作清单悬浮层与侧栏同时打开时布局不遮住输入和当前操作。

列表依运行 ID 保持选中项，事件到达后重新查询持久事实，不把客户端状态当权威。运行状态建议映射为 `○ 排队`、`▶ 运行中`、`? 待回答/审批`、`Ⅱ 已暂停`、`✓ 成功`、`! 部分失败`、`× 失败`、`■ 已取消`；颜色为辅助，文字始终存在。另列“停止待核实”“效果未知”“回报待送达”等事实；不为 attention 新造运行终态。

启动时固定展示名称和简短任务说明，命名定义沿所选名称，临时脚本要求模型提供名称；时刻取宿主创建时间。说明取显式简短描述，不把任意参数 JSON 自动展开为列表摘要，避免泄露业务数据。扩展 launch 摘要、持久记录、控制视图、工具 schema、导入映射及 fixtures；已有无标题记录使用“未命名工作流＋时间”作为明确回退，详情保留 ID。不得读当前定义名称覆盖历史身份。沿仓库 schema/协议兼容策略执行，不趁机引入自动迁移。

UI 在用户确认业务动作时生成稳定请求键并钉定参数及版本，发送前复用 `packages/control/src/pending-requests.ts` 的 `PendingRequestStore` 保存未决请求，扩展现有操作枚举和恢复分派，不另建日志。沿用原子写、0600、完整参数与 instanceId；写入失败不发送，损坏记录保留，新数据库实例只展示待核实、不向新库重发。原键与核实状态不依赖命令输入历史。连续点击读取同一未决操作，明确拒绝后才可依据新事实生成下一次操作。

应答丢失时只读核实：启动沿原键 find；答复/控制读取原回执，必要时为现有控制账本补按键查询。确认未接收才允许同键重试，结果未知则保留待核实；过期版本显示最新状态并让用户重新确认业务动作。图标、日志、错误和进度注记都指向可选择的详情层，不再生成带 ID 的 TUI 命令教程。保留安全恢复需要的核实内容，但用问题、选择和说明呈现。
