# 工作流交互与等待改进规格

本规格补充[原工作流规格](spec.md)，依据 2026-10-14 拥有者发起的 grill-me 讨论及 Q1–Q9 确认。交付入口为[执行计划](experience-plan.md)；本轮建立方案、工单与设计规范，产品实现另按工单推进。原规格的权限、后台运行、三个共享并发名额、人工回答与唯一回报要求继续有效。

## 已确认要求

| 编号 | 要求 | 验收依据 |
| --- | --- | --- |
| E1 | 面向人的交互通过选择与逐步引导完成，不要求手输无规律 ID、版本、摘要或请求键；作为全局设计原则，本次落实工作流 TUI。 | 从 `/workflow` 完成启动、查看、答复及控制，全程只选择对象、动作和业务内容。机器 CLI/API 保留标识符接口；现有 IM 交互另列后续。 |
| E2 | 两产品共用的 `/workflow` 打开常驻侧栏，主聊天保留，可切换焦点；返回逐层退出，窄终端可展开为独立窗口。 | 键盘完成列表→详情→操作→返回，侧栏打开时仍可聊天，缩放与关闭不取消后台工作。 |
| E3 | 默认展示当前会话的活动运行和最近结果，另有历史与已保存定义启动入口。 | 历史及长列表可续读；定义选择→填写业务参数→启动；查看步骤、日志、问题，执行答复、暂停、恢复、取消和预算调整。脚本编辑继续通过文件或 Agent。 |
| E4 | 用名称、发起时间、简短任务说明辨认运行，临时脚本由 Agent 提供简短名称；状态采用图标与文字。 | 同名同时运行可区分，ID 仅在诊断详情可见；八种运行状态有明确表示，部分失败不算成功，取消与停止核实分别呈现。 |
| E5 | 内部“工作流最终回报”输入不出现在普通聊天、输入历史和置顶用户要求中；用户仍看到最终总结。 | 实时、重连、翻页与会话分支均不泄出内部提示；真正的用户同文输入仍显示。原文及模型输入仍可追溯，不改写既有 JSONL。 |
| E6 | 两产品主 Agent 共用一个等待工具，等待一个或多个明确的 SubAgent 任务或工作流。任一目标有可消费结果、需要人工介入或等待超时即返回事实。 | 固定任务/运行身份，不等待 SubAgent 关闭或动态追逐其最新任务；返回每个目标的状态，未完成与已完成明确区分。 |
| E7 | 等待期间可随时发送新消息并打断本次等待，后台工作继续；正常等待结束后主 Agent 继续检查结果或后续步骤。 | 新消息及时进入处理，未取消原后台任务；超时只结束本次等待，Agent 可再次等待；界面可辨认等待对象与尚未完成的工作。 |
| E8 | 结果消费与最终报告有唯一、可恢复的归属。主 Agent 正常等待后继续处理，最后给一份最终答复；被打断后仍有后台补报。 | 等待返回与原唤醒路径不重复消费、总结或外发；完成/新输入竞争、重启与报告失败不丢失结果或制造重复报告。 |
| E9 | 等待安全让出执行资源，恢复工作目录访问前重新取得并核实；待人工、暂停、停止未核实或效果未知均不得冒充成功。 | 真实修改工作流、非 Git 修改子任务在父等待期间有进展；资源未安全停止不释放；子任务持目录等待审批时主聊天仍能处理输入，但不能访问该目录；恢复业务执行前权限、目录身份和占用再次有效。 |
| E10 | TUI 稳定请求键、版本与应答丢失核实由程序负责。 | 重复点击、断线、重启、版本变化后不误操作；未知提交保存原请求并核实，不换键重做，不要求用户填写协议参数。 |

## 交互路径

```text
/workflow
  ├─ 当前会话：活动运行 / 最近结果
  │    └─ 运行详情：状态、等待原因、步骤、回报状态
  │         ├─ 步骤 / 日志 / 结果
  │         ├─ 回答问题
  │         └─ 暂停 / 恢复 / 取消 / 调整预算
  ├─ 历史 → 运行详情
  └─ 启动工作流 → 已保存定义 → 业务参数 → 确认启动
```

“最近结果”是有界列表，全部历史经分页查看；本次不增加跨工作区或全实例管理视图。输入校验、提交结果与可采取的下一步在当前操作层显示。启动参数沿定义现有 JSON 能力提供编辑与错误定位，不承诺为任意脚本推导表单；业务问题已有选项或约束时据其生成选择/输入界面。

等待工具是模型能力，侧栏是拥有者观察与控制入口。工具完成、SubAgent 本次任务完成、工作流结束和最终报告送达是不同事实；界面不能用一个“完成”混称。多个目标采用任一可消费结果返回，其余目标继续等待或由主 Agent 处理；无需加入未要求的任意组合等待策略。

多个目标限定为同原始工作来源、同回复目标及代次，定时来源须同调度运行；本次不合并不同来源委托的最终报告。原来源与已消费资料持续受每次模型请求和发送前核实，拥有者授权不会因进入等待而扩大。这个工程边界保留原工作流来源约束，不减少一次发起多个后台任务共同等待的能力。

## 范围与现有交付

本次实现工单为 08–11；[12 IM 后续](issues/12-im-progressive-controls.md)只登记目标，QQ/Telegram 的逐步交互方案尚未确定。机器 CLI 保留脚本化能力，TUI 的旧长命令不再作为常规操作入口或错误恢复指引。不建设流程图编辑器、插件平台、跨实例工作流中心或其他入口的全面改造。

原 [06](issues/06-library-and-ui.md) 的工程结果不证明本次交互通过；原 [07](issues/07-acceptance.md) 的旧证据按原范围保留，真实 IM 和拥有者体验缺口继续存在。新增方案只部分取代“文本窗口＋用户填写请求键”的交互选择，以及“所有终态都另建独立汇总任务”的送达选择；安全与审计要求不降低。
