## 目标与边界

逐项验收[规格 A1–A12](../spec.md)，核实[实施计划第九节](../implementation-plan.md#九验收与检查)的组合行为。各实施单已负责最窄回归，本单不代替其验证，也不把模拟结果记成真实模型或 IM 通过。

## 验收步骤

1. 汇总 02–06 的实际实现与证据，重新判断合并后的改动面；因总体跨全部共享运行链路，执行一次完整 `npm run check`，对失败查明原因，不能直接归为环境抖动。
2. macOS/Linux 与两个 Node 版本验证实际构建的脚本 worker、权限边界和停止；Linux 经 `ssh tx`，保存命令与环境。
3. 六输入批量样例故意制造一个失败项，核实并发、独立验证、覆盖清单和最终状态；故障注入覆盖恢复、未知效果、取消、预算、人工回答和结果送达的竞争。
4. 真实模型用例以 `RUN_MODEL_CHECK=1` 显式运行；普通应用测试仍离线。个人产品通过实际绑定 IM 验证等待期间继续聊天、回答绑定与唯一最终回报；编码产品验证 TUI 进度、代码汇总及后续检查。
5. 独立实现审查者从规格、当前源码与原始证据逐项核对，必要时亲跑最窄负例；拥有者验收交互与报告体验。发现方案错误退回方案，不降低原验收标准。

## 交付条件

依赖 [06](06-library-and-ui.md) 完成，所有工程要求有对应证据、独立实现审查无阻断，适用产品验收通过。凭据、真实平台或目标环境缺失时明确未验收及恢复条件，不用“不适用”代替。

完成后同步实际行为文档、决定状态与总工单；未核实的副作用和停止状态不能被验收记录抹掉。提交、合并、部署、发布仍按拥有者授权执行，本单不额外授予这些操作。
