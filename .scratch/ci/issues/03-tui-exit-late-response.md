# 修复 TUI 退出后迟到应答重启动画

Status: ready-for-human

## 目标与边界

由[测试精简](02-reduce-test-suite.md)的 Linux 挂住诊断发现，按其“产品缺陷另立关联局部修复”要求处理。恢复既有退出契约：客户端释放动画资源，后台任务继续；不改权限、协议、持久化和超时，不做产品重构。恢复已有明确清理约定，走局部修复流程并独立审查。

## 实现与证据

`TuiApp.quit` 已标记 exiting 并停止旧计时器；晚到的 continue 结果经 submitText→notify→refreshAll 再次创建 80ms 引用计时器。连接关闭后状态停留在 running，文件进程无法退出。`tickTiming` 在 exiting 时返回；[决定](../../../.agents/notes/implemented/bug-fix/2026-10-24-tui-exit-late-response.md)记录归属与备选。

在 oracle-4c24g 的原 `28c033f7` 上，continue 接收后延迟应答 500ms、模型回包 1500ms，实际任务 running 时退出：Node 22.19 与 24.15 均测试体通过但 20 秒监护超时（124），句柄栈指向该计时器；单行修复后同一窄场景的测试进程分别约 7.38/9.2 秒正常退出。该机制可解释旧 CI 的 32-dev 存活进程；旧日志没有句柄栈，不能证明历史那一次必由同一条应答触发。

正式回归不使用上述固定延时，复用 `test/32-dev.test.ts` 的继续/重载用例，以 Promise 门控制两个阶段，保留原草稿、会话、继续目标断言，新增退出后计时器为空与后台继续完成。macOS Node 24.15 定向 1/1，通过，完整进程 6.881 秒；独立撤去 guard 时同一窄例以实际 80ms 引用计时器非空失败（退出 1），恢复后 1/1 通过（退出 0），进程分别 6.928/6.215 秒；原四格结果待补。
