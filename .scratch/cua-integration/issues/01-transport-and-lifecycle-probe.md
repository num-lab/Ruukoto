# 01 验证 Cua 传输、目标认领与生命周期

Status: ready-for-agent

## 目标与边界

为[规格](../spec.md#接入结构)选择并证明一条实际可交付的接入路线，覆盖 R1–R4、R6–R7 的外部前提。拥有者已确认双产品、本机 Mac + Linux 沙箱和现有 MCP 权限；本单的计划创建不授权本轮安装、系统权限或生产操作。实验只使用隔离测试桌面及无真实账号的应用。

本单不开放产品电脑工具，不引入云服务或完整通用网关。技术理由见[提案](../../../.agents/notes/proposed/architecture/2026-10-22-cua-integration.md)。

## 方案

1. 选择 Cua Driver、Cua CLI/沙箱镜像及桥接的固定正式版本，保存来源、tag/制品哈希、许可证、OS/架构及 Node 22.19/24.15 兼容条件。先审对应版本的配置和重试源码，再运行。Supergateway 是首个候选，不假定其 main 文档等于所选 release。
2. 在 `.scratch/cua-integration/probes/` 编写可重复的最小探针；先模拟 stdio 计数服务测桥接，再分别测真实 macOS Driver 和 Linux 桌面沙箱。记录确切工具 schema、响应样本、图片大小，经过现有 compileMcpSchema 与工具数量/页数限制。
3. 验证配置身份与传输：本机和 Linux 的 HTTPS 端点、证书信任、Bearer 缺失/撤销拒绝、固定源拒绝重定向；服务不公开匿名控制。Linux 镜像无需真实账号，模型调用无需沙箱创建权限。
4. 分别模拟 Code 按任务连接、Personal 每调用重连；执行截图→元素点击→截图，验证 transport lease、显式 session 和窗口引用。比较保留连接与逐调用连接，选择能满足 R4 的最小方案，写出连接由谁持有、何时关闭及重启后如何核实。
5. 证明目标身份与认领：两个客户端、URL 别名、不同凭据及第二桥接对同一目标争用；沙箱参数覆盖到第二目标必须在执行前拒绝。将认领/状态/暂停/解除的 wire 参数、宿主注入身份、认证与持久化位置写入本单证据供 03 消费。缺现成能力则先提交最窄适配设计并独立复审，不凭内存锁宣布通过。
6. 动作被执行后丢弃应答，覆盖 reset、超时、取消、网关 502/503、网关自行生成的 JSON-RPC error、响应超限/截断及网关/Driver/后台退出；测试应用提交计数为一次。记录原 JSON-RPC id、HTTP session/SSE 游标和下游执行身份的对应关系；验证只读原回执、保留未知、结束证明与解除占用。没有原结果恢复能力时明确阻断写工具路线，不能把“永远冻结且没有核实入口”作为完整交付。
7. 保存 `evidence/01-probe.md` 与脱敏机器证据；不提交密钥、用户桌面截图或账户资料。结论必须是带版本/协议的通过，或指明失败机制与待修方案。将后续文件和测试范围据实写回 03–05，并做受影响方案复审。
