# main 应用数据空间

## 目标

让 main agent 按需建立待办、提醒、习惯或其他个人数据结构，同时保护 ruukoto 核心数据库。

## 实现范围

- 独立应用数据数据库或等效 namespace，不开放核心 `ruukoto.db`。
- `define_table`、`migrate`、`query`、`insert`、`update`、`delete` 受控工具。
- 表、字段、索引和 schema 版本由 main 提议并持久化；工具验证名称、类型、大小和关系。
- 非破坏性迁移自动执行；删除表、删除字段和批量重写要求拥有者确认。
- 每次 schema/data 变更保存来源任务、agent、版本、时间和理由。
- 查询限制：最大耗时、返回行数、返回字节数和单次扫描范围。
- main 应用数据与 MemoryStore 分工：偏好、约定、决策、经验仍进入长期记忆。

## 验证

- main 能创建不同结构的表并跨重启读写；
- 迁移版本冲突不会静默覆盖；
- 破坏性操作进入确认；
- 核心任务、审批、事件和凭据表无法被应用数据工具访问；
- coding/chat 默认无法查询 main 数据；
- 大查询、恶意表名、超大字段和超时被拒绝并留下事件。

## 实施计划

计划日期：2026-09-23。依赖 [issue 01](01-orchestration.md) 已交付并修复评审问题。本计划基于当前代码，以下接口和限额是本工单的工程默认方案，尚未实施；状态保持 `ready-for-agent`。

### 1. 建立独立存储与角色边界

- 新增 `<dataDir>/agent-data/main.db`，由 Runtime 管理打开、恢复和关闭，沿用 `node:sqlite`，不增加数据库依赖。目录权限为 `0700`，数据库及辅助文件受后台账户保护，包含在已有 `protectedRoots()` 数据目录范围内。
- 新增 `src/agent/app-data/store.ts`。直接使用 `DatabaseSync` 建立应用数据库；不复用 `new Db(dataDir, "main.db")`，因为 `src/core/db.ts` 的构造器会执行完整的核心 schema 和迁移。连接不开启扩展加载，不接受模型提供的数据库路径或 SQL。
- 写连接设置 WAL、`synchronous=FULL` 和外键约束。首次建立应用库后，把它的稳定实例 ID 登记到核心库已有 `meta` 表；启动恢复前先核对文件存在及实例 ID。已登记但文件丢失、身份不符或损坏时，不自动创建空库，不据此把旧操作判为未提交；保留未知效果并报告应用数据不可用。首次初始化跨库失败可恢复，但不能覆盖既有实例绑定。
- 应用库只包含宿主维护的元数据、schema 目录、追加审计记录及 main 声明的业务表。区分存储格式版本、main 管理的 `schema_version` 和每次变更递增的 `revision`。存储格式过新或迁移失败时明确停止应用数据能力，不重建或清空旧库。
- 在 `ToolCategory` 中新增 `app_data`，仅 main 的角色定义包含它。`Orchestrator.ensureRoles()` 当前会跳过已有角色行，需补充幂等升级：只为既有 main 更新工具清单，保留其 Project、Session、工作目录和模型绑定。
- `Driver` 在装配、发送前检查和调用门中纳入六个应用数据工具。普通开发会话即使 `roleAllows()` 默认放行也不得获得这些工具；执行入口每次重新核实宿主任务、会话、项目与 main 角色绑定。模型参数不接受 agent、project、权限模式或文件路径。
- coding/chat/QQ 会话默认无法调用这些工具；现有资料授权、`grantedPaths` 和完全访问模式不扩大应用数据 API 范围。文件系统隔离仍以 [ADR 0004](../../../docs/adr/0004-tool-worker-per-task-container-exec-account.md) 的容器或独立执行账户为准，local 后端不能作为跨账户隔离的验证依据。

### 2. 固定六个工具的结构化契约

新增 `src/agent/app-data/tools.ts`，沿用 TypeBox、`defineTool` 和宿主注入的 `taskId/sessionId/projectId/hostOpId`。模型侧统一使用 `app_data_` 前缀，避免与其他工具重名；所有写入必须带非空 `reason`。

- `app_data_define_table`：声明表名、字段、索引及关系，携带 `expected_schema_version`。表已存在时报冲突，不用 `IF NOT EXISTS` 掩盖不同定义。
- `app_data_migrate`：携带预期版本和有界的结构化操作列表。首版支持增加可空字段、增加索引、删除索引、删除字段、删除表及按明确行 ID 批量重写字段值。整次调用在一个事务内完成。任意 SQL、脚本转换、隐式类型转换和任意表达式不进入首版。
- `app_data_query`：`mode: schema | rows | changes`。`schema` 分页发现表或读取单表定义、索引、关系和当前版本，保证重启后不依赖会话记忆恢复结构；`rows` 查询业务数据；`changes` 分页查阅本空间的审计记录或按操作 ID 核实提交结果。内部元表不成为可自由查询的业务表。
- `app_data_insert`：按声明的 schema 插入记录，返回宿主分配的行 ID、行版本及数据库版本；批量插入原子提交，不静默忽略非法行。
- `app_data_update`、`app_data_delete`：使用明确行 ID 与预期行版本，不接受无条件全表写入。单行操作可直接执行，多行操作进入确认；批量重写也可由 `migrate` 提交，复用同一验证和执行逻辑。

schema 校验放在存储边界，工具 JSON schema 只承担输入提示，不能代替执行时验证：

- 名称限 `[a-z][a-z0-9_]{0,47}`；拒绝 `sqlite_`、`app_`、内部字段保留名及重复名称。SQL 标识符只能来自已验证的目录，仍统一引用；所有数据值使用绑定参数。
- 字段类型限 `text/integer/real/boolean/json/datetime`，使用严格表和必要约束。整数限 JavaScript 安全整数，浮点数必须有限；日期校验后统一为 UTC ISO；JSON 必须可序列化且受字节和嵌套深度限制。缺省、空值和类型错误分别处理，不依赖 SQLite 自动强制转换。
- 每表固定内部 `_id` 和 `_version`，由宿主维护；`_id` 使用单调、不复用的整数主键。关系只能指向同一应用空间中已登记表的 `_id`。外键启用并固定 `RESTRICT`，禁止级联写入，以免一次单行删除隐式变成批量删除。删除被引用对象前必须显式处理关系；首版拒绝无法安全处理的迁移。
- 普通索引与唯一索引只能引用存在的标量字段，不支持表达式或部分索引。增加索引遇到重复数据等约束错误时整次回滚。删除普通索引自动执行，删除唯一索引按削弱数据约束的操作确认。
- 初始上限：64 张业务表、每表 32 个业务字段、8 个索引、每索引 4 个字段、每表 10,000 行；单字段 16 KiB、单行 32 KiB、单次写入参数 64 KiB、100 行或 16 个迁移步骤，理由最多 1 KiB。按 UTF-8/JSON 实际字节检查，超限不执行；这些值集中定义为宿主常量，模型不可调大。

所有写入在事务内检查 `expected_schema_version`；更新和删除再检查行版本，破坏性 schema 操作再检查预期 `revision`。版本不一致返回可识别的冲突和当前版本，不自动覆盖或在后台重算后重试。一次成功的 schema 操作递增 schema 版本，一次有实际变更的事务递增 revision，失败不推进版本。

### 3. 实现能兑现的查询预算

首版采用主键游标分页，不开放任意 SQL、JOIN、子查询、聚合、正则或全表排序。`rows` 支持选择字段以及有界的 AND 条件，运算限标量比较、空值检查和有限集合匹配；按内部 `_id` 排序。已声明索引用于约束及后续真实需求，首版不另写通用查询优化器。

- 先按 `_id > cursor` 读取固定候选窗口，再在窗口内过滤和投影。不能把 `SELECT ... WHERE 任意条件 LIMIT N` 当作扫描上限：少量命中也可能扫描整表。
- 默认最多返回 50 行，硬上限 100 行、64 KiB；单次最多检查 1,000 个候选行、1 MiB 候选数据。使用 `iterate()` 逐行累计大小，并按单行硬上限为下一次读取预留预算，达到预算立即停止，不先 `.all()` 收集全部记录。单页的版本读取与行扫描放在同一只读事务中。
- 返回 `scanned/complete/next_cursor/schema_version/revision`。游标绑定表、查询参数摘要和版本，只推进到最后已处理的位置；字节上限前未返回的匹配行必须留给下一页。单条投影记录无法容纳时明确拒绝并要求缩小投影，避免空页死循环。跨页数据发生变化时返回游标冲突，调用方重新查询。
- `schema` 与 `changes` 也分页并遵守返回字节限制。请求显式超过限额时拒绝；合法分页耗尽本次扫描或结果预算时返回 `complete=false`，不能把部分结果描述为完整结果。
- 新增 `src/agent/app-data/query.ts`，同时提供查询入口和只读子进程执行路径。每次查询启动一个固定入口的 Node 子进程，只打开 `main.db` 的只读连接；宿主传入已经验证的结构化参数，子进程再次校验。IPC 请求、响应和错误输出均有界，不传 owner token、模型凭据或核心数据库句柄。
- 查询总时限初值 2 秒，覆盖子进程启动、执行和结果收集。超时或任务取消后终止子进程并等待退出，再返回错误；关闭 Runtime 时回收在途查询。子进程仅查询，所有写事务留在宿主，避免后台崩溃后遗留继续提交数据的 writer。

项目最低支持 Node `22.19`；该版本的 `DatabaseSync` API 同步执行，`timeout` 只是数据库锁等待上限。因此不使用同进程 `Promise.race` 充当查询截止，也不依赖较新 Node 才有的 SQLite API。[依据：Node 22.19 SQLite 文档](https://nodejs.org/download/release/v22.19.0/docs/api/sqlite.html#class-databasesync)。只读子进程用于终止超时计算，不将它描述为完整的操作系统权限沙箱。

### 4. 接入破坏性操作确认

复用 `Driver.awaitApproval()`、`Store.consumeApproval()`、控制面 `respond_confirmation` 和现有 TUI 待审批界面，不新增一套审批队列。宿主数据工具通过窄回调使用审批桥，不向模型暴露控制面。

- 创建表、增加可空字段、增加索引、受限插入和带版本的单行更新/删除自动执行。删除表、删除字段、删除唯一索引、多行更新/删除及批量重写必须等待拥有者确认；混合迁移只要包含一项此类操作，整次确认后执行。
- 新增 `ApprovalScope.kind: app_data_change`，固定应用数据库身份、任务与操作 ID、表和操作类别、schema/revision、规范化参数摘要及受影响数量。行操作固定准确的 ID 和行版本；schema 操作固定旧定义、新定义或明确差异。TUI 展示范围、数量、版本和理由，完整参数继续通过现有分页详情读取。
- 获批后重新检查 main 身份、任务状态、权限版本和应用数据版本；任何变化都使原请求失效，不能把批准扩大到新出现的行。批准仅消费一次，执行参数取自批准记录的不可变快照。
- `auto-review` 对此范围直接转拥有者，不调用审查模型。`full_access` 也需要本工单规定的破坏性数据确认。这是相对 [ADR 0003](../../../docs/adr/0003-enforce-explicit-access-modes.md) 通用“无需逐次确认”语义的特定例外，依据是本工单和 [daily-agent 规格第 9 项](../spec.md) 的明确要求；实施时新增 ADR 记录例外并同步说明，不能照搬 MCP 的 full_access 放行分支。
- 拒绝、取消、模式切换、批准过期和后台重启均不执行旧请求。确认期间不持有应用库事务或写锁。

### 5. 让变更、审计与恢复相互对应

- 每次写入在同一个 `main.db` 事务内提交业务/schema 变更、版本递增和追加审计回执。记录 `hostOpId`、任务/会话/agent、schema 版本、revision、时间、理由、规范化操作、受影响范围和有界结果摘要；身份与时间由宿主填写。schema 变更保留前后定义，数据修改保留操作及目标引用，不在本工单实现完整数据时光机。
- `hostOpId` 唯一；同操作重复执行先查回执，同参数返回原结果，异参返回冲突。审计写入失败、约束失败或磁盘写入失败必须回滚业务变更；不能为了继续服务而丢弃审计。
- 核心库先记录工具意图，必要时消费批准，应用库再提交，核心库最后记录工具结果和事件。两库没有共同事务，不使用 `ATTACH ruukoto.db` 拼接，也不宣称它们原子提交。
- 扩展 `Runtime.recover()` 在现有未知效果判断前核实未落结果的应用数据操作，并覆盖 Driver 的中止/结果写入失败路径。有回执则补记已提交结果；批准已消费但无回执、且应用库正常可核实时，记录未提交；应用库丢失、损坏或无法核实则保留 `effect_unknown`。只读查询不应被误标成产生未知写入效果。
- `main.db` 已提交但核心结果写入失败时，立即按操作 ID 核实并保留真实状态；不能报成“未执行”或自动再次写入。重启只补记结果和事件，不自动重放修改。恢复补记沿用现有 `tool_ops` 条件更新，在同一核心事务中写事件，重复恢复不重复发布。
- 正常执行和拒绝均留下既有 `task.tool_intent/task.tool_result` 记录；调用门拒绝、校验失败、预算超限和超时补充可识别的 `app_data.rejected` 事件，包含宿主来源、操作类别和错误码，不把无限长输入或整条个人数据复制进额外事件正文。成功事件以审计 revision/操作 ID 引用应用库记录。
- 应用数据保存待办、提醒、习惯等结构化记录；偏好、约定、决策、经验继续使用 `MemoryStore`。工具描述明确这一分工，应用记录不自动提升为长期记忆或控制指令。

### 6. 按依赖顺序交付并验证

1. 完成独立存储、schema 校验和事务审计。用新建表、约束失败和重开数据库的小范围测试验证 CRUD、版本冲突、关系和原子回滚；先完成这些不变量，再接模型。
2. 完成有界查询和只读子进程。验证稀疏命中仍最多扫描预算内行数、空页能继续、UTF-8 字节限制、游标不漏行、超时真实终止进程。通过受控测试挂点制造执行阻塞，并检查同期控制面请求仍能应答。
3. 接入 Runtime/Driver 与角色升级。检查 mock 模型实际收到的工具清单，并主动调用执行入口验证：只有可信 main 会话可访问；coding/chat/QQ/普通开发会话及伪造身份不能读取；已有 main 角色重启后获得工具且身份不变。
4. 接入审批和 TUI 范围展示。覆盖自动操作、删除表/字段、批量重写、三种权限模式下的确认、拒绝、重复批准、陈旧版本、模式切换与取消。批准前零变更，批准后范围固定且最多执行一次。
5. 补齐双库恢复测试：消费批准后未提交、应用库提交后核心结果缺失、审计插入失败、核心结果写入失败、正常重启、重复恢复、已登记应用库丢失、身份不符和不可读。核对实际表内容、审计回执、工具结果和事件，不仅检查任务状态。
6. 收尾验证核心边界与文档。尝试 `tasks/confirmations/events`、凭据路径、SQLite 元表、保留名称、恶意标识符、超大字段和超限查询，必须拒绝并留下对应记录；以 `PRAGMA integrity_check` 和 `foreign_key_check` 检查应用库，核实核心库中预置的任务、审批和事件未被应用数据操作改变。

测试以新增 `test/28-main-data.test.ts` 为主，复用现有 mock 模型和临时目录设施；按需更新 `test/27-orchestration.test.ts` 的工具清单/升级断言及 `test/14-tui-app.test.ts` 的审批展示检查。验证命令为 `npx tsx --test test/28-main-data.test.ts test/27-orchestration.test.ts test/14-tui-app.test.ts`，完成后执行 `npm run typecheck` 与一次 `npm test`。涉及 Linux 容器或专用执行账户的文件读取隔离，在 `ssh tx` 上按现有部署方式验证；未执行的真实环境检查必须在交付记录中明确列出。

实现落点除三个新增模块和测试外，集中在 `src/runtime/runtime.ts`、`src/runtime/orchestrator.ts`、`src/agent/driver.ts`、`src/core/types.ts`、必要的 `src/core/store.ts` 恢复辅助方法及 TUI 展示。核心库不因业务 schema 变化而升级；应用格式版本独立演进。实施时更新 `docs/runtime.md`，按 `domain-modeling` 约定补充应用数据术语和相应 ADR，最后在本工单追加实现事实、迁移说明与验证结果。

本工单不预建待办、提醒或 outbox 业务表，不实现调度器、消息入口、跨角色数据授权界面或通用 SQL 引擎。[issue 03](03-scheduler-outbox.md) 后续通过带版本的应用记录/快照引用对接触发器，届时按实际读取需求扩展窄接口，不提前增加固定业务字段。
