# 调度器与通知 outbox

## 目标

提供持久的时间触发、通知发送和重启恢复能力，不依赖内存定时器或分布式消息中间件。

## 实现范围

- SQLite 持久化的调度运行记录和发送操作账本；单进程调度循环。它们是运行时基础设施，不是 main 的 `todos`、`reminders`、`habits` 或 `outbox_messages` 业务表。
- 一次性、每日、每周触发；使用 IANA 时区。
- 任务到期时创建稳定幂等键；重复唤醒不会重复建任务。
- 重启后恢复未处理计划；错过时间只补发一次并标记延迟。
- outbox 状态：pending、sending、sent、failed、effect_unknown、canceled。
- 发送目标、正文和操作 id 在发送前固定；结果未知不自动换 id 重发。
- main 自己定义的业务数据通过 scheduler 注册触发，通过发送操作账本排队；普通事件只落事件表。发送正文可引用任务、产物或 main 应用数据快照，不要求预设业务字段。

## 验证

- 进程重启不丢失到期提醒；
- 同一幂等键最多产生一次可见发送；
- 发送失败、超时和结果未知可查询；
- 时区和每日/每周重复规则跨夏令时边界不发生明显漂移；
- 调度器不会阻塞现有编码任务队列。

## 实施计划

计划日期：2026-09-23。[issue 01](01-orchestration.md) 已交付；[issue 02](02-main-data.md) 目前只有实施计划，应用数据快照接口须在其完成后接入。本计划中的接口、限额和时间策略属于拟实施方案，状态保持 `ready-for-agent`，实现顺序仍为 `01 → 02 → 03 → 04`。

### 1. 确定职责与交付边界

- 调度器作为现有 Runtime 内的宿主组件运行，沿用数据实例锁和 SQLite。内存定时器只负责唤醒扫描，触发规则、下一次时间、运行记录和发送状态以数据库为准；进程退出后不靠重建内存定时器猜测漏过的工作。
- 每个计划固定一种动作：`wake_main` 通过编排器创建 main 任务；`notify` 把已批准的固定正文放入发送账本，直接发送，不为每次提醒启动模型。需要临时生成内容时使用 `wake_main`，其任务不会自动继承外发授权。
- 普通内部状态变化使用 `Store.appendEvent()`，不登记为需要派发的入站事件。当前 `Orchestrator.registerInboundEvent()` 会唤醒角色，不能把每条运行、发送或失败记录都送入该入口。
- 本工单交付平台无关的发送账本、一个宿主注入的发送函数及模拟发送验证；真实 Telegram 路由、凭据、限流应答和 owner 回复接入归 [issue 04](04-telegram-owner.md)。无可信目标时不能创建外发操作；已有固定目标暂时离线或发送器未加载时，未领取的操作保留 `pending` 并显示等待原因。
- 现有 `qq_outbox` 的 `pending` 同时表示未发和在途，重启全部转 `unknown`，且没有业务幂等唯一键。本工单新增公共账本，不直接套用其恢复和取消实现；QQ 链路在后续实际接入时再迁移，避免影响既有群回复行为。

### 2. 持久化计划、运行与发送操作

在核心 `ruukoto.db` 中新增三张运行时基础设施表，由 `src/scheduler/store.ts` 提供窄读写方法，纳入现有 `Db` 迁移与 `Store.withTx()`。当前核心 schema 为 v11，实施时按当时最新版本递增。表中不预设待办、习惯或提醒业务字段，main 也不能通过应用数据工具直接读写这些核心表。

- `schedules` 保存计划 ID、宿主 main 身份、创建任务/操作、创建幂等键和参数摘要、时间规则、固定动作及来源快照、`next_due_at`、已处理的时间范围、当前未完成运行引用、启停状态和版本。通知计划另外保存目标绑定及配置版本、批准记录引用。一次性计划登记运行后将下次时间置空，待该运行结束才标完成，不能因没有下次时间提前撤销本次待发通知的授权。首版提供创建、查询、取消；修改时间、正文或动作采用取消旧计划后重新创建，通知计划重新确认，不增加通用编辑与授权继承逻辑。
- `schedule_runs` 保存运行 ID、计划及其版本、原定 UTC 时刻、对应当地时间、实际登记时间、延迟和合并区间、入站事件或发送操作引用、关闭时间。唯一约束覆盖 `(schedule_id, schedule_version, scheduled_for)`；每个计划最多有一个未完成运行。执行结果从关联任务或发送记录读取，不再复制一套任务终态。
- `notification_ops` 保存操作 ID、创建任务/宿主工具操作 ID、宿主来源类别及来源键、固定目标/账号/配置版本、最终正文与摘要、来源引用、状态、创建及发送时间、平台消息 ID、错误类别、取消意图和迟到应答记录。来源类别限 `schedule_run / confirmation / owner_reply`，由宿主入口选择，模型不能自报已授权。`(source_kind, source_key)` 唯一，重复登记返回原操作，同键异参报冲突，不能通过换操作 ID 重试同一来源。
- 为 `schedules(status, next_due_at)`、未完成运行、`notification_ops(status, created_at)` 及来源精确查询建立索引。所有修改带宿主来源、时间和理由，状态与对应事件同一核心事务提交后才广播；查询分页返回，首版不自动删除历史记录。

调度到期时，在一次短事务中核对计划仍有效、创建或合并运行、推进下一触发时间，并登记对应 `inbound_events` 或 `notification_ops`。调用 Store 的事务内方法，不在其中嵌套 `Store.withTx()`，也不在事务中等待网络、模型或应用库查询。

### 3. 明确时间、夏令时与漏过周期的语义

首版规则限一次性、每日、每周，使用 ISO 日历。一次性时间必须带 `Z` 或显式偏移并保留显示用 IANA 时区；每日保存 IANA 时区及 `HH:mm`，每周再保存不重复的 ISO 星期列表（1–7）。非法时区、无偏移的一次性时间和越界日期明确拒绝，不使用服务器本地时区补全。新建周期计划从登记后首次符合规则的时刻开始；登记已过去的一次性时间时，只产生一次标记延迟的触发。

- UTC 时刻统一保存为毫秒精度的 ISO 表示；先严格校验，再复用现有 UTC 规范化口径。每日/每周按当地日期和原定钟点重新构造，不能用固定 `24h/7d` 相加。
- DST 策略固定采用 `compatible`：当地时间不存在时按时间缺口向后移动，重复出现时选较早的那一次。例如纽约春季的 `02:30` 在跳时日变为 `03:30`，次日回到 `02:30`；秋季重复的 `01:30` 只触发第一次。将这一策略保存在规则中并在确认详情展示。[依据：Temporal 的歧义时间规则](https://tc39.es/proposal-temporal/docs/zoneddatetime.html#from)。
- 本地检查未发现已安装的时间库，当前 Node `24.15` 也没有可用的全局 `Temporal`。计划只新增 `@js-temporal/polyfill`，在 `src/scheduler/time.ts` 内集中使用并锁定安装版本；不提升项目 Node `>=22.19` 的要求，不自写 IANA 偏移和 DST 算法。该库提供 ESM 用法并支持 Node 14 及以上。[依据：项目 README](https://github.com/js-temporal/temporal-polyfill#readme)。
- 时间函数返回最近一次应发生时刻和严格晚于扫描截点的下一时刻。以当前当地日期及相邻候选日期计算，不逐分钟扫描，也不逐个枚举多年停机期间的全部周期。测试覆盖非整点偏移、半小时 DST 和日期跨越，不能假设每次时区变化都是一小时。
- 时钟回拨不回退已持久化的处理范围，不重复发生过的周期；时钟前跳和停机共用合并补发规则。已登记运行的时刻与键固定；运行环境时区数据更新后，只重算尚未登记的未来时间，并记录采用的 Node/ICU/tz 版本，避免改写历史发生时刻。

漏过多个周期时，每个计划只补一次，按以下顺序处理：

1. 没有未完成运行时，选择本次扫描截点之前最近的一次应发生时刻，建立一个运行，保存从首次漏过时间到该时刻的合并范围；把 `next_due_at` 推进到扫描截点之后。
2. 已有未完成运行时，保留原运行、原幂等键和原正文，把新增漏过区间追加到合并记录并推进时间，不建立第二个运行。已登记未建任务、已排队或执行中的任务，以及 `pending/sending` 通知，都占用这个位置。
3. 重启时先读取关联记录的真实状态：任务或通知早已终态、只是运行关闭标记未回填的，先补关闭，不能让它吸收结束之后漏过的周期；仍为 registered/queued/running/pending/sending 的才执行合并和时间推进。然后才把重启中断的任务、遗留 `sending` 定为相应终态并释放位置，最后启动正常扫描。原始状态须在通用 `Runtime.recover()` 改写 running 任务之前读取并完成恢复准备。已有待处理运行优先复用，不把它改名为最新周期。

例如周一的通知仍为 `pending`，周四恢复时仍使用周一的原操作，只发送一次，记录合并至周四，下一次为周五；若周一已经 `sent`，仅关闭标记缺失，则补关闭后另生成一次覆盖周二至周四的补发。失败或结果未知的运行不自动重试；后续正常周期是独立的新运行，不能被描述成对旧操作的补发。

### 4. 接入编排与 Runtime 生命周期

- 新增 `src/scheduler/runtime.ts`，采用一个不重入的扫描循环和一个独立发送循环。初始扫描间隔 1 秒、每批最多 50 个到期计划，批次之间让出事件循环；活跃计划上限 1,000。队列积压按稳定顺序继续处理，不丢弃已登记记录。
- `wake_main` 使用 `source: scheduler` 和稳定的运行 ID 作为 `external_id`；入站正文只有有界的触发说明、原定时间、延迟和来源引用，目标角色固定为 main。继续使用 `evt:<eventId>` 提交键创建任务，定时任务采用宿主固定的 `confirm` 模式，正文不能设置角色、任务权限或模型配置。
- 为 Orchestrator 增加宿主专用的有界派发入口：调度事务提交后可以派发已持久化的 `registered` 事件，后续巡检也能按原键补派。当前登记入口只在 `created=true` 时触发派发，且提交失败主要等待重启；本工单不能依赖重复登记自动补派。恢复与正常派发共用原串行链，重复调用不重复建任务，调度来源同键异参须报冲突。
- 取消计划立即停止未来触发，并取消尚未发送的关联 `pending` 操作。尚未派发的运行不得在恢复时重新派发；已排队的关联任务经现有取消入口处理。取消与派发通过同一串行边界核对，覆盖提交任务与回填事件之间的竞争；已运行的任务及在途发送保留真实执行事实，不承诺撤销已发生效果。
- Runtime 启动先打开数据库并完成 issue 02 的存储核实，在通用任务恢复之前核对调度关联记录、补齐已有终态运行的关闭标记、对真实待处理运行合并漏过周期；再执行任务/在途发送恢复、角色引导和运行关闭核实，最后开放调度事件派发与发送。当前 `Orchestrator.start()` 会立即恢复入站事件，需增加明确的启动顺序或恢复前置钩子，保证这些准备和取消记录核对先完成，不能仅在其启动后再补一遍扫描。
- 停止时先拒绝新增计划/发送并停止扫描、领取，再等待调度事务、派发链与在途发送收尾，最后关闭数据库。当前 `Orchestrator.stop()` 只清理定时器，需同时等待已有 `dispatchChain` 并阻止关闭期间新增派发；超时后的发送回调也不得访问已关闭数据库。

SQLite 只执行有索引且有批量上限的短事务。发送、应用数据读取和模型调用均在事务外异步等待，不进入 coding 会话的任务队列，也不占用其工作目录。发送循环首版只允许一个在途操作，避免并发状态和限流调度器；慢发送不会阻止到期登记、控制面请求或 coding 任务推进。

### 5. 固定发送授权、状态转换与恢复规则

本工单只向宿主已配置的 owner 目标发送。目标绑定、账号、配置版本及凭据引用来自可信宿主；模型不能传入 URL、chat/user ID、凭据、授权类型或审批 ID。未配置目标时明确拒绝，不能猜测接收者。

- `wake_main` 计划可以直接登记。首次创建 `notify` 计划时，复用 `Driver.awaitApproval()` 和现有 TUI，新增 `notification` 审批范围，固定完整正文、目标及配置版本、规则、IANA 时区、DST 策略和持续范围；周期计划明确展示“持续至取消”，不能只批准首次时间。
- 获批后在同一个核心事务中重新核实宿主 main 身份、任务/权限版本与目标配置，调用 `Store.consumeApproval()` 并写入计划、批准引用及事件。后续触发依据该有效计划，不重复消费原批准，也不要求最初任务仍在执行。目标配置版本变化或停用使旧授权不再可用，不能自动改发到新目标。
- 一次性 `notification_enqueue` 同样批准固定目标与正文，批准消费、账本插入及事件在同一事务内完成，工具只返回“已排队”和操作 ID。定时器另用内部 `enqueueScheduled(runId)` 读取已批准计划；issue 04 另用内部 `enqueueOwnerReply(eventId, taskId, text)` 验证可信 owner 入站、固定回复路由与任务关联。模型不能调用这两个内部入口，也不能把一次 owner 回复扩展成未来发送授权。
- `auto-review` 对通知审批直接转拥有者。本计划对建立持续发送计划及未预授权的一次发送均要求显式确认，包括 `full_access`；这是 [daily-agent 规格第 6 项](../spec.md) 对未预授权外发的约束，实施时须记录其与 [ADR 0003](../../../docs/adr/0003-enforce-explicit-access-modes.md) 通用模式语义的关系。已批准计划与可信 owner 回复属于明确的自动发送范围，不复用 MCP 的无条件 full_access 放行分支。
- 宿主决定逻辑发送键：定时通知为运行 ID，owner 回复为入站事件 ID 和固定回复槽，一次确认发送为当前任务的通知槽。首版模型每任务只有一个一次通知槽，重复调用只能查询/返回该操作，同键变更正文报冲突；不能通过模型生成新键绕过 `effect_unknown`。内部恢复也不得换键或改正文。

发送状态按事实转换：

1. `pending` 表示尚未领取、没有调用发送函数。发送前重新检查来源授权、计划状态、目标启用/版本和渠道可用性；永久失效转 `canceled` 并记录原因，暂时离线保持 `pending`。领取时以条件更新把 `pending → sending` 与发送开始事件一并提交，只有成功领取者可调用发送函数。
2. 网络调用在事务提交后执行一次，接收固定 `opId/target/text` 和 `AbortSignal`；函数返回平台成功回执或可证明未产生发送的失败。明确成功为 `sent`，明确未发送/平台拒绝为 `failed`；请求发出后的超时、断线、模糊错误为 `effect_unknown`。初始时限 15 秒，具体平台可在宿主配置中收紧，适配器不得隐藏自动重试或自动拆成多条发送。
3. 重启时 `pending` 可继续领取，遗留 `sending` 一律转 `effect_unknown`，包括“已提交 sending，但网络调用前崩溃”的窗口。`sent/failed/effect_unknown/canceled` 均不自动重发。平台已接收但本地结果写入失败时，保留 sending/未知事实，不能回退 pending。
4. 只有确定未发送的 pending 可以直接取消。在途取消或停机发送中止只记录取消意图，并按成功、明确失败或未知事实收尾。迟到回执按原操作 ID 保存，不能触发重发，也不能把已不确定的发送伪装成取消成功。发送函数必须在中止后释放本地资源；关闭屏障隔离未能及时结束的回调。

“同一幂等键最多产生一次可见发送”的可实现保证，是本地只保留一个操作且不重复发起可能已经产生副作用的发送。平台没有幂等支持时，本地事务无法保证远端 exactly-once，也不能同时保证未知窗口必达。验收应同时核对模拟平台接收次数和本地状态；“重启不丢提醒”指计划、触发与发送事实可恢复，未知结果仍需拥有者核实。这与 [ADR 0002](../../../docs/adr/0002-detach-terminal-from-task-runtime.md) 和 [ADR 0008](../../../docs/adr/0008-mcp-write-tools-unified-approval.md) 的不重放原则一致。

### 6. 连接 main 工具、来源快照与查看入口

新增 `src/agent/scheduler-tools.ts`，提供 `schedule_create/schedule_query/schedule_cancel` 和 `notification_enqueue/notification_query/notification_cancel`。独立 `scheduler` 工具类别只赋予可信 main 会话，沿用 issue 02 的装配、发送前检查、执行端身份核实与旧角色清单升级方式；coding/chat/QQ/普通开发会话不能查询 main 的计划、正文或发送记录。查询结果同样受资料范围约束。

- 创建计划使用 main 范围内的稳定创建键，并持久保存规范化参数摘要；同键同参返回原计划，同键异参拒绝。取消带预期版本并幂等，取消后不复活；所有修改带非空理由。宿主操作 ID 同时用于核实工具调用在崩溃前是否已登记，避免恢复把已成功入账误报为需要再执行。
- 正文可以直接提交文本，或从已完成任务结果、可访问产物的明确文本片段、issue 02 应用记录的指定字段解析。复用 `AccessScope`、产物读取和应用库有界查询，拒绝未授权资料、任意文件路径、二进制内容和尚未完成的任务结果；不能从“会话最新回复”推断某个指定任务的结果。
- 在登记/审批前将引用解析成最终文本，保存来源 ID、应用库实例/表/行/schema/行版本、内容摘要及有界快照。记录读取时版本，不宣称应用库和核心库跨库原子；业务记录以后修改或删除不会悄悄改变已批准正文，需要取消旧计划后重新登记。发送前仍核实可撤销的资料授权，撤销后不得利用旧快照继续外发。
- 首版正文限制 2,000 个 Unicode 字符及 8 KiB，以两者和渠道更小限额为准；触发说明最多 4 KiB，来源引用最多 8 个，单次登记参数最多 32 KiB。超限明确拒绝，不在批准后截断、拼接或拆成多次发送。发送正文使用纯文本，平台转义只做无歧义编码。
- `schedule_query` 可按 ID 查看规则、下次时间、批准范围及有界的运行历史；`notification_query` 可按 ID/状态查看目标、来源、状态、错误、延迟和平台回执。列表每页最多 50 条、64 KiB，正文详情按单条读取。首次登记前可通过查询了解是否存在可信 owner 路由，不返回凭据值。
- 为拥有者控制面增加对应的查询/取消操作，CLI 增加薄的列表、详情和取消命令，复用现有认证与错误展示；审批继续用现有 TUI。控制面的查询和取消不获得发送或更改目标的隐含能力，不扩大默认 connect 快照为全量计划或通知历史。

### 7. 实施顺序与验收

1. **先实现时间函数与存储约束。** 新建库及旧库升级保留已有任务、审批和 QQ 记录；验证计划/运行/通知唯一键、同键异参、CAS 取消、事务失败不推进时间也不留下半条触发。时间用例覆盖一次性、每日、每周、跨月/年/闰日、纽约 DST gap/fold、`Australia/Lord_Howe` 半小时变化、`Asia/Kathmandu` 偏移和无效时间。
2. **接通持久触发与编排。** 注入可控时钟调用 `tick(now)`，覆盖重复和并发 tick、建任务后回填前崩溃、派发临时失败后不重启也能补派、取消与派发竞争、时钟回拨以及长期停机只合并一次。检查运行、入站、任务数量和实际模型请求；普通状态事件不得增加模型调用。
3. **完成审批和公共 outbox。** 使用可信 fake 路由和可控发送函数，覆盖批准前零发送、同键重复登记、并发领取只调用一次、目标版本变化、权限模式切换、跨角色伪造授权、凭据不进入模型/日志、未配置目标拒绝与暂时离线保持 pending。
4. **验证每个发送崩溃窗口。** pending 重启后发送一次；sending 在调用前崩溃不重发；模拟平台已接收但应答丢失/本地结果未落库时标未知；sent 重启不重发；明确失败、取消前后竞争、超时和迟到成功均保留真实状态。至少用一次真实后台子进程终止验证“平台已接收、本地未落结果”，其余窗口可通过现有故障注入构造。
5. **验证恢复合并与退出。** 已有周一 pending 到周四恢复仍仅一个操作且下次为周五；分别覆盖已有 sending、registered 入站和 queued/running 任务，证明先合并再释放不会新增补发。另覆盖关联通知已 sent／任务已 completed、运行尚未关闭的跨日崩溃窗口，要求补关闭后新建一次补发，不能吞掉后续漏过周期。发送函数挂起时，控制面和独立 coding 任务继续推进；stop 后不再领取，不在数据库关闭后写入，重启不会接着重放在途发送。
6. **接入 issue 02 快照并收尾。** 验证登记后业务行修改不改变正文、资料授权撤销阻止外发、应用库身份不符或不可用时不伪造快照；检查核心库 `integrity_check/foreign_key_check`。核对计划/发送记录可分页查看、取消及与事件对应，再更新运行文档、术语与 ADR。

新增测试集中在 `test/29-scheduler-outbox.test.ts`，复用现有 mock 模型、临时目录、`Db.faultNextWrite` 和后台子进程测试设施；必要时更新 `test/27-orchestration.test.ts` 的派发/退出检查及 TUI 的审批展示测试。先运行相关定向测试，收尾执行 `npm run typecheck` 与一次 `npm test`。本工单不向真实 Telegram/QQ 账号发送验收消息，模拟平台通过不代表 issue 04 的真实部署已经通过。

代码落点为四个新增模块 `src/scheduler/store.ts`、`src/scheduler/time.ts`、`src/scheduler/runtime.ts`、`src/agent/scheduler-tools.ts`，以及现有核心 schema/类型、Runtime/Driver/Orchestrator、控制面、CLI 和审批展示的必要接线。按 `domain-modeling` 约定补充“调度计划、调度运行、发送操作”的领域定义及相应 ADR，更新 `docs/runtime.md`；最后在本工单记录实现事实、迁移说明和验证结果。首版不引入 Redis、cron 表达式、通用工作流、平台插件系统或自动重试框架。
