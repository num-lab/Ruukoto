# Code：工作区与会话树、会话标签页、对话流

Status: resolved

## 目标与边界

实现[规格 R9](../spec.md)中的浏览与会话创建部分：左栏工作区与会话树、打开工作区、新建会话、中间会话标签页与对话流（正文、思考、工具活动折叠组），数据全部来自 view 投影。提交与控制在 05，审批在 06，右栏在 07。界面文案按 R13 用中文。

## 方案

1. 渲染进程经 `subscribe` 得到快照与事件，交给 `@ruukoto/view` 投影。
2. 会话流恢复沿用 TUI `app.ts` 中 `loadHistory`、`restoreEventFlow`、`readTaskFlow`、`loadEntry` 的协作方式，按 [01](01-view-package.md) 写进 view 文档的安装约定实现：
   - 历史页用 `read_history`；
   - 思考记录与工具操作身份用 `list_tasks`，加 `get_task`（含 seq）与 `read_task_events` 补齐；
   - 超长正文用 `read_history_entry`，按 UTF-8 偏移分页读取；
   - 渲染进程每次安装新快照，代次就加一，同时清空流游标与在途的流请求，旧代次的异步结果到达后直接丢弃。新快照既可能来自重连，也可能来自同一连接内因 seq 缺口发起的重同步（`ControlConnection` 会在原连接上再次握手）。这与 TUI `onSnapshot` 的做法一致。

   只安装快照与历史页，恢复不出思考记录、工具操作身份与完整长正文。全局 seq 缺口检测与重同步由主进程的 `ControlConnection` 负责，渲染进程不另写一套连接恢复。
3. 左栏：工作区与会话来自快照，加上按 `workspace_id` 查询的 `list_session_summaries`；会话归属沿用 `sessionDisplayAttribution`，避免把已映射的旧会话按原 `project_id` 放错位置。SubAgent 会话不出现在树中。
4. 创建操作的幂等与应答丢失恢复。“添加工作区”（先 `pickFolder`，再 `open_workspace`）和“新建会话”（`create_session`）都是本单负责的写操作。`open_workspace` 不带键时，每次调用都会新建一个会话，所以两者都必须带键。做法照搬 TUI 的 `ensureWorkspaceEntry` 与 `verifyWorkspaceEntry`：
   - **键、参数与归属**：用户每次发起一项独立操作，都生成一个新的 `request_id`。它和原参数、连接目标、发起时快照的 `instanceId` 一起，保存为一条待完成的创建记录。结果确认之前，这条记录一直保留；重发时只用原键和原参数。待核实期间重复点击，既不换键，也不另起一项操作。操作成功之后，再对同一目录发起的“添加工作区”是一次新的独立操作：它用新键，后台照旧在已有工作区下新建会话。做法与 `SubmissionGuard` 一致，见 `packages/control/src/submission.ts` 第 49–84 行的实例核对。
   - **按结果分类处理**：用 03 跨 IPC 保留下来的结构化 `outcome` 区分：
     - 成功：打开返回的会话。
     - `rejected`：显示失败原因，丢弃这项操作，不留下任何成功状态。
     - `unknown`（连接还在，应答丢了）：当场在当前状态里按 `Session.createRequestId` 找原会话；找到就打开；找不到，就用原键、原参数重发一次。
     - `disconnected` 或 `not_sent`：先不重发，等重连后装好新快照，再按 `createRequestId` 核实；核实不到，才用原键、原参数重发。

     待完成的创建记录属于用户操作，不是绑定代次的异步结果，所以快照换代时不丢弃。
   - **实例归属**：核实、重发和采纳结果之前，都先确认当前连接目标与 `instanceId` 和记录一致。
     - 同一数据库的后台重启或重同步，`instanceId` 不变，按原键恢复。
     - 新快照的 `instanceId` 与记录不同（`ControlConnection` 的 `onSnapshot` 会报告 `instanceChanged`）时：保留记录，不向新实例重发，界面显示“原操作结果仍未知”，并提示连回原数据实例后再核实。
     - 旧实例的成功应答如果晚于新实例的快照才到，不安装到当前界面。
   - **结果未知**：核实并重发一次之后还不能确认，就显示“结果未知”，并告诉用户去哪里查看会话是否已经建好（左栏工作区树）；不把下一次点击当成一次新的创建。
   - **代码位置**：这段逻辑在渲染进程里，基于 view 的状态实现。`control/workspace.ts` 的 `ensureWorkspaceSession` 所在模块引用了 `node:fs`，渲染进程不能 import，所以不复用它。不需要新增协议，也不需要通用的请求框架。
5. 中间：会话标签页的开合只是界面状态；对话流按 view 的流条目渲染，正文用 `react-markdown` 加 `remark-gfm` 且关闭原始 HTML。
6. 实施交接：`loadHistory` 的向前翻页要保留；`loadEntry` 按 UTF-8 偏移连续读取，要保留它的连续性检查。字节计数用 01 提供的浏览器可用实现，不照搬 `app.ts` 里的 `Buffer` 调用。按 R20，`docs/modules/desktop.md` 同步新增的可观察行为。
7. 放行名单加入本单调用的 op：`list_session_summaries`、`open_workspace`、`create_session`、`read_history`、`read_history_entry`、`list_tasks`、`get_task`、`read_task_events`。

## 验收与证据

工程检查、独立审查与真实 Electron 外部清单均通过；实施、产品验收适用性、检查结果和未覆盖项见[验收证据](../evidence/04-implementation.md)。以下为有效验收要求。

- 放行名单单测随新增 op 一起更新。
- 恢复流程的纯逻辑单测，参照 `test/14-tui-app.test.ts` 的冷重连回归，覆盖以下四种情况：
  - 冷启动后思考记录与工具操作身份完整；
  - 重连后条目不重复、不缺失；
  - 超过单页的长正文经 `read_history_entry` 补全；
  - 旧代次的迟到结果被丢弃，包括同一连接内重同步时，迟到的旧历史请求结果。
- 创建操作的回归测试：用真实 Runtime 与 ControlServer（模型用替身），对 `open_workspace` 和 `create_session` 各跑以下三种情况：
  - 后台已接受，但连接仍在线时应答超时；
  - 后台已落库，随后断线；
  - 后台明确拒绝。

  断言：
  - 前两种情况核实之后，对应的会话恰好只有一条，并且打开的是原会话；
  - 明确拒绝时不留下成功状态；
  - 待核实期间重复点击，发出的请求始终是同一个 `request_id`；
  - 快照换代后，待完成的创建记录仍然保留；
  - 一次操作成功后，对同一目录再发起一次独立操作，用的是新键，同一工作区下多出一个新会话。这是既有的语义。
- 跨实例负例：用两个真实 Runtime 与 ControlServer（A、B 的 `instanceId` 不同）覆盖两种情况：
  - A 已接受 `open_workspace`，随后应答丢失，连接恢复到 B：断言 B 收到的创建请求为零、原记录保留、不会打开 A 的会话，界面显示原结果未知；
  - A 的成功应答晚于 B 的快照到达：断言这个结果不安装到当前界面。

人工检查（外部验收）：
- 打开工作区后，它出现在树中。待核实期间重复点击，或者应答丢失后按原键重试，都不会多出会话；操作成功后再添加同一目录，则按既有语义新建一个会话。
- 新建会话可用。
- 与 TUI 同时连接时，TUI 中的任务在桌面端流式出现，思考计时与工具折叠组和 TUI 语义一致。
- 重启后台、桌面端重连后，条目不重复也不缺失。
- 含 `<script>`、`<img onerror>` 与 `javascript:` 链接的模型输出不执行脚本。
