# Code：提交、模型、会话默认模式、中断／取消／继续、恢复队列

Status: ready-for-agent

## 目标与边界

实现[规格 R9](../spec.md)中的写操作：输入框提交、按会话切换模型、切换会话默认模式、中断／取消／继续、队列暂停横幅与恢复。

## 方案

1. **提交与继续都走持久守护。** `submit` 与 `continue` 都不是普通透传：渲染进程照常经 `request(target, op, params)` 发起，主进程把这两个 op 交给本目标的 `SubmissionGuard`。守护先落盘、后发送，记录里保存完整参数和请求键。`PendingRequestStore` 按目标分别存放在应用数据目录里。
   - `continue` 会新建一个带 `resumesTaskId` 的任务，不是让原任务恢复执行。所以它的记录除了输入和 `model_selection`，还要包含原任务 `task_id` 与所属 `session_id`。
   - 防止重复：同一会话已有待核实的 `submit` 时，渲染进程禁用该会话的发送；同一原任务已有待核实的 `continue` 时，主进程拒绝为它再发起一次，并返回那条待核实记录。重复点击不会产生新的请求键。
2. **核实的触发与回流。** 核实由主进程负责，每个目标各有一个核实调度器。
   - **触发**：某次请求得到 `pending_verification`，且 `outcome` 为 `unknown`（连接仍在）时，当场核实这一条。另外，每次 `ControlConnection` 的 `onSnapshot` 回调装好快照后，都核实全部记录。`onSnapshot` 覆盖首次上线、断线重连，以及同一连接因 seq 缺口发起的重同步；重同步不会再次进入 `online`，所以触发点不能挂在 `onState` 上。记录在磁盘上，应用重启后的首个快照同样会触发核实。
   - **防止并发**：调度器同一时刻只跑一轮核实；运行期间又有新的触发，只记一个标记，本轮结束后再补跑一轮，不会让同一批记录并发核实。
   - **核实方式**：守护内部用 `find_task` 核实，只有明确未接收时，才用原键、原参数重发。

   核实结果经 `subscribe(target)` 以结构化事件交给渲染进程。渲染进程按 `requestId` 维护一份待核实列表，同一条记录无论核实多少次，都只占一项，不重复提示：
   - `linked`、`resent`：关联到对应任务，提示一次。守护随后清除记录，所以不会再次出现。
   - `kept`：查询失败，保留记录，列表中显示“结果未知”。
   - `rejected`：守护已经清除记录。把原文恢复到所属会话的输入框，只恢复这一次。
   - `needs_resubmit`：原请求已确认未被接收，并且缺少模型。守护会保留记录，所以单独处理，见下一条。
   - `foreign_instance`：保留记录，提示连回原数据实例。
   - 损坏的记录：显示数量和文件位置，供人工处理。
   - **`needs_resubmit` 的确认流程**：列表中显示“原请求未被后台接收，且缺少模型”，并提供“恢复输入”与“暂不处理”两个选项。
     - 选“暂不处理”：保留记录，不自动发送；该会话的发送仍然禁用，列表项一直可见。
     - 选“恢复输入”：分两步，经既有的 `request(target, op, params)` 桥接交给主进程。这两个 op 都在主进程本地处理，不转发给后台，也不改变 preload 的四个入口。顺序必须是先交付、后清除：原记录在原文安全进入草稿之前一直保留，是唯一的持久副本。
       1. 渲染进程调用 `desktop_pending_read({ request_id })`。主进程只读出原参数并返回，不删除记录。
       2. 渲染进程把原文合并进所属会话的草稿：草稿为空就直接放入；已有草稿时，把原文放在前面，中间空一行，原有草稿保留。原 op 是 `continue` 时，草稿仍关联原任务，下次发送照旧是对这个任务的继续。渲染进程按会话记下已合并的 `request_id`，同一渲染进程生命周期里，重复点击或重复读取不会再合并一次。
       3. 合并完成后，渲染进程调用 `desktop_pending_clear({ request_id })`，主进程用严格的存储入口处理（见下一段“严格的存储入口”）：
          - 记录存在：先核对可恢复资格，再删除；删除成功才返回成功。
          - 经严格读取确认记录不存在（`ENOENT`）：同样返回成功。这样，清除成功但应答丢失之后，重复确认仍然成功，满足幂等。
          - 读取或删除时出现权限、IO 等任何其他错误：返回 `pending_clear_failed`，界面提示“原记录未能清除，发送仍禁用”，拥有者可以再试一次。已合并的草稿不会重复拼接。
       4. 清除成功后，这个会话的发送解除禁用，拥有者可以先选模型，再发送。

       中途失败的处理：
       - 第 1 步的返回没有送达（IPC 失败、窗口关闭或渲染进程重载）：记录仍在，可以重来。
       - 第 2 步之后、清除之前重载或退出：草稿只在渲染进程内存里，会随之丢失；记录仍在，重开后可以再恢复一次，原文不会丢。
     - **可恢复的范围**：对于现存的记录，两个 op 都只处理同时满足三个条件的记录：属于本目标；记录的 `instanceId` 等于当前连接的 `instanceId`；本次运行中，最近一次核实的结果是 `needs_resubmit`。应用重启后，首个快照的核实会重新得出这个结果。现存但不满足条件的记录（仍待核实的、属于其他实例的），一律返回 `not_restorable`，不读也不删。对于不存在的记录：`desktop_pending_read` 返回 `not_restorable`；`desktop_pending_clear` 按上面第 3 步返回成功，不要求一条已经不存在的记录再提供字段来校验。文件读取失败不算“不存在”。
     - **严格的存储入口**：现有的 `PendingRequestStore.clear` 和 `list` 都会吞掉错误。`list` 在 `readdirSync` 失败时返回空列表，所以不能用来证明“已经不存在”。因此在 `packages/control/src/pending-requests.ts` 新增两个严格方法，供这两个 op 使用：
       - `read(requestId)`：返回记录，或者 `absent`（只在 `ENOENT` 时）；记录无法解析时，返回损坏标记；其他错误照常抛出。
       - `remove(requestId)`：返回 `removed`，或者 `absent`（只在 `ENOENT` 时）；其他错误照常抛出。

       主进程把抛出的错误映射为 `pending_clear_failed`，读取 op 则映射为 `pending_read_failed`。`clear`、`list` 的宽容策略，以及它们现有的调用方（`SubmissionGuard` 与 TUI），都不改。

     渲染进程不直接操作存储。记录清除之后，之后的快照和应用重启都不会再恢复它。
3. **模型。** 模型列表用 `list_models`，按 `nextOffset` 翻页。选择项保留 provider、modelId、thinkingLevel 与可用性。切换模型用 `set_session_model`，带 `expected_version`；每次提交都携带当前会话的 `model_selection`。
4. **会话默认模式。** 模式选择放在模型选择旁，调用 `set_session_mode`，`expected_version` 取 `defaultAccessModeVersion`。它只改会话的默认值，不调用 `switch_mode` 改写已有任务；标签沿用 TUI 的英文名。
5. **设置类写操作的失败处理。** 模型和模式没有提交幂等键，所以不自动重发：
   - 在线应答丢失（`unknown`）或版本冲突时，用 `get_session` 读回实际值并刷新界面。
   - 断线（`disconnected`）时，等新快照恢复实际值。
   - `not_sent` 和明确拒绝时，显示原因，保留原值。
6. **任务控制。**
   - `interrupt` 与 `cancel` 不自动重放。应答丢失分两种：`unknown` 时，当场用 `get_task` 读回任务的实际状态；`disconnected` 时，等同一实例的新快照装好后，按快照里的任务状态核对。查询失败则保留“结果未知”。
   - “继续”只对当前会话里状态为中断的任务开放。如果原任务的 `effectUnknown` 为真，先提示拥有者核实原操作。
7. **队列暂停与恢复。** 暂停横幅由快照里会话的 `queueState`、`queuePauseReason` 和之后的事件共同决定；暂停期间新建的任务如实显示为排队，不说成已经执行。“恢复”沿用 TUI `cmdResumeQueue` 的流程：
   - 先找出当前会话里缺 `modelSelection` 的排队任务。
   - 有这类任务时：会话还没有模型，就先让拥有者选一个；已有模型，就显示要补齐的任务数和具体的模型选择。拥有者确认后调用 `resume_queue({ session_id, model_selection })`；拥有者取消，队列保持暂停。
   - 没有这类任务时，只传 `session_id`。

   `set_session_model` 不会回填旧任务，所以不能用“先改会话模型、再发不带模型的 `resume_queue`”来代替这一步。`resume_queue` 的应答丢失时，不自动重放，而是按会话实际的 `queueState` 核对：在线时用 `get_session` 读取，断线时以新快照为准；查询失败则保留“结果未知”。这段决策写成纯函数，放在桌面端可在 Node 下测试的模块里。
8. **放行名单与文档。** 主进程本地处理 `desktop_pending_read` 与 `desktop_pending_clear`，它们不转发给后台，可处理的范围见第 2 步。放行名单加入本单直接透传的 op：`list_models`、`set_session_model`、`set_session_mode`、`get_session`、`interrupt`、`cancel`、`resume_queue`。`submit` 与 `continue` 由主进程交给守护处理；守护内部用的 `find_task` 只在主进程使用，不对渲染进程开放；`get_task` 已经由 04 加入。按 R20 同步 `docs/modules/desktop.md`。

## 验收与证据

工程待验证。以下单测放在 `test/38-desktop-main.test.ts`，直接调用桌面主进程的处理逻辑，不以单独重跑共享守护作为证据：

- **同一连接重同步时的核实**：首次核实查询失败（`kept`）之后，同一个 transport 出现 seq 缺口；新快照装好时没有第二次 `online` 回调，核实仍会运行，并关联到已被接受的原任务。断言不换键、不新增任务。连续多次触发时，核实不会并发执行；已经关联成功并清除的记录不再核实，成功结果也只呈现一次。本轮结果为 `kept` 的记录，在合并后的补跑中允许再核实一次，测试不能禁止这次必要的重试。
- **`needs_resubmit`**：
  - 选“暂不处理”：记录保留，不发送任何请求，该会话的发送仍然禁用；之后的快照与重启不会重复恢复输入。
  - 选“恢复输入”：原文只恢复一次，已有草稿保留；记录从存储中移除，发送解除禁用；原 op 为 `continue` 时，恢复后的输入仍关联原任务。之后的快照与重启都不会再恢复它。
  - 交付失败：主进程准备返回原文之后、渲染进程收到之前，注入 IPC 失败或渲染进程重载；断言记录仍在，重开后能恢复原输入。
  - 清除确认丢失：恢复已经成功，但 `desktop_pending_clear` 的应答丢了；再次确认成功，草稿不会重复拼接。
  - 清除失败：在临时目录上制造权限失败，让删除与列目录同时失败。断言返回 `pending_clear_failed`、不解除发送禁用。修复权限后，原记录仍能找到，再次清除成功。
  - 不存在的记录，分三种情况：
    - 从未存在的 `request_id`：`desktop_pending_read` 返回 `not_restorable`，`desktop_pending_clear` 返回成功。
    - 刚刚清除成功、但应答丢失：再次 `desktop_pending_clear` 返回成功。
    - 记录仍在但不可恢复（仍待核实，或 `instanceId` 不同）：两个 op 都返回 `not_restorable`，记录不变。
  - 严格存储方法的单测：`read` 与 `remove` 只在 `ENOENT` 时返回 `absent`；权限错误照常抛出；`clear`、`list` 原有的行为不变。
- **continue 应答丢失**：连接在线时超时，当场核实并关联原继续任务；再用新的守护实例读同一个存储目录（模拟应用重启），`reconcileAll` 同样关联到原任务；两种情况下任务数都不增加。同一原任务已有待核实的继续时，再次发起被拒绝，不产生新的请求键。
- **submit 的四种情况**：在线超时；断线后恢复；应用重启；数据实例换了，不重发并返回 `foreign_instance`。`not_sent` 与明确拒绝时，输入回到所属会话。
- **设置类写操作**：`set_session_model` 与 `set_session_mode` 遇到版本冲突或在线应答丢失时，用 `get_session` 读回实际值；断线后由新快照恢复。
- **任务控制**：`interrupt` 在 `unknown` 时用 `get_task` 读回实际状态，在 `disconnected` 时按同一实例的新快照核对，两者都不自动重放；`resume_queue` 应答丢失时按会话的 `queueState` 核对。
- **恢复队列**：恢复队列的纯函数覆盖四种情况：有缺模型的旧任务且会话没有模型时，要求先选模型；拥有者取消时，不发请求；确认后发出的请求带 `model_selection`；没有缺模型的任务时，只传 `session_id`。另用真实 Runtime 与 ControlServer（模型为替身）断言两点：不带模型的 `resume_queue` 返回 `model_selection_required` 且队列保持暂停；带模型时恢复成功，已经有模型的排队任务不被改写。
- **放行名单**：随新增 op 一起更新；渲染进程不能直接调用 `find_task`。

人工检查（外部验收）：
- 提交后，输出流式显示。
- 切换模型与模式后，下一次提交生效，TUI 同步看到变化。
- 中断、取消、继续各做一次。
- 重启后台后出现暂停横幅；有缺模型的旧任务时，先补选模型，恢复后队列继续。
- 提交时后台恰好重启（用 `ruukoto-code stop` 后由“重新连接”拉起）：恢复后输入不重复提交。

   修订要求：明确 `submit`、`continue` 都由主进程持有完整参数和请求键、先落盘后发送，都不能走普通透传；继续记录包含原任务、所属会话、输入和模型选择。同一待核实操作的重复点击不另建请求。验收补一条继续应答丢失的回归，覆盖客户端重启后关联原继续任务、任务数不增加，而不只检查一次正常继续成功。
