# 审批卡片、系统通知与 Dock 角标

Status: ready-for-agent

## 目标与边界

实现[规格 R9 的审批卡片与 R12](../spec.md)。审批卡片两个目标共用；通知与角标由主进程按两个目标的快照与事件计算。

## 方案

1. **审批卡片与失效规则。** 卡片和角标都取 view 的待审批选择器，同时响应实时的解决事件与自动审查事件。任务结束时，后台只会把它的审批写成 `stale`，不会发出解决事件；任务的权限版本变化时，也是这样。所以本单修改共享的 `ViewState.pendingApprovals()`：只有同时满足三个条件的审批才算待处理：自身状态是 `pending`；所属任务不是终态（`TERMINAL_TASK_STATUSES`）；审批的 `permissionVersion` 等于任务当前的 `permissionVersion`。任务的权限版本由 `task.mode_switched` 事件更新，切换模式与授予路径都会发这个事件。这条规则在 01 迁移到 view 之后再改，主进程和渲染进程用的是同一个选择器，TUI 的待审批列表也随之不再显示失效的审批；同步 TUI 回归、`docs/modules/view.md` 与笔记。
   - **终态常量**：`TERMINAL_TASK_STATUSES` 目前在依赖 Node 的 `core/types.ts` 中，选择器不能从那里做值引用。和 01 拆出的 `ACTIVE_TASK_STATUSES` 一样，把它放进同一个无 Node 依赖的状态模块，`types.ts` 改为再导出；R4 的浏览器打包与产物全局检查照旧适用。
   - **模式切换失败**：共享投影同时修改对 `task.mode_switch_failed` 的处理。后台只在 `Store.endTask` 以 `interrupted` 结束任务、且带 `modeSwitchFailure` 时才发这个事件（`store.ts` 第 883–884 行），这时不会另发 `task.interrupted`，权限版本也不变。所以 view 收到它时，除了清除 `pendingAccessMode`，还把任务投影为 `interrupted`。投影只在任务当前不是终态时生效，已知的终态不会被旧事件回滚。界面提示保留事件的 `reason`，例如 `worker_stop_unverified`，不把它说成任务已经安全停止。这一投影依赖“该事件只随中断终态产生”的后台约定；实施时将该依据同步到桌面客户端决策笔记，在 view 的这个分支加 `Note: 见 .agents/notes/<路径>` 锚点指向承载该决定的笔记。将来后台如果在非终态时也发这个事件，这里必须改为用 `get_task` 核实。展示内容沿用 TUI：操作范围、目标、审查状态与转人工原因，不只显示参数 JSON。完整参数用 `get_confirmation_params` 按返回的 UTF-8 字节偏移续读，字节计数用 01 提供的浏览器实现；参数被截断或读取失败时，界面上要看得出来。
2. **审批应答的结果处理。** 每次批准或拒绝，都绑定发起时的目标、`instanceId`、审批 ID 与卡片上展示的权限版本。按 03 跨 IPC 保留下来的结构化 `{ code, outcome, message }` 分别处理，任何情况下都不自动重发 `respond_confirmation`：
   - 成功：卡片按事件移除。
   - `rejected` 且为 `stale_confirmation` 或 `not_found`：审批已经失效（被 TUI 处理、被自动审查处理，或任务已结束），移除卡片并说明原因。
   - `rejected` 且为 `permission_version_mismatch`：重新读取详情，展示新的权限版本，等拥有者重新决定；不会换成新版本后自动批准。
   - 其他 `rejected`：显示原因，卡片保留。
   - `not_sent`：说明请求没有发出，卡片保留，拥有者可以再点一次。
   - `unknown`：用 `get_task` 查询原审批的实际状态。已经处理的，显示查到的结果；仍待处理的，显示“结果未知，审批仍待处理”，由拥有者决定是否再操作；查询失败时，显示“结果未知”，并提示等待新快照或刷新。
   - `disconnected`：先显示“结果未知”，等同一实例的新快照装好后，再按快照核实。实例换了，就丢弃这次的结果，并说明原目标已经变化。
   - 快照换代后才到达的旧详情、旧查询结果，一律丢弃，不复活卡片，也不把原决定带到另一个目标。
3. **通知判定。** 主进程为每个目标维护一份 view 的 `ViewState`（view 不依赖 Node，也能在主进程里运行），以“目标 + `instanceId`”为单位保存观察基线：
   - **基线内容**：已见的待审批 ID 集合、已见的终态任务 ID 集合，以及“观察中任务”集合（任务曾在非终态时被看到过）。所有 ID 都按“目标 + 实例 + ID”区分，所以两个目标的 seq 或对象 ID 相同也互不干扰。
   - **首次观察一个实例**：本次应用运行中首次观察到某个实例（包括 `instanceId` 变化后的新实例）时，这一次同步全程静默：快照，以及随后回调的 `replay` 补发事件（seq 都不超过快照的 `seq`），都只用来建立已见基线，不发通知。新实例快照里每个会话最多只带 20 个终态任务，更早的历史终态仍可能出现在补发里，所以静默范围必须包括补发。`instanceId` 变化时，先丢弃这个目标的旧基线。静默只看事件是 `replay` 还是 `live`，以及它的 seq 是否超过快照的截止点，不以 `onState("online")` 作为解除静默的条件：`ControlConnection.sync` 在进入 `online` 之前，就会派发握手期间缓冲下来的 `live` 事件，这些 seq 大于快照截止点的事件是真正的新事件，照常通知。同步完成后才到的实时事件照常通知；同一实例的正常重连，仍按下面的规则补发通知。
   - **待审批**：每次装好快照、每应用一条事件之后，用当前的待审批集合与已见集合比较，新出现的 ID 发通知并记为已见。
     - 补发不会回滚状态，所以快照已经确认失效的旧审批，不在当前集合里，不会通知。
     - 离线期间创建、至今仍待处理的审批，会出现在集合里，补发一次通知。
     - 同一审批同时出现在快照和补发里，按 ID 去重，只通知一次。
   - **任务终态**：候选来源有三处：快照里的终态任务，补发与实时事件里的终态事件（包括第 1 步投影为 `interrupted` 的 `task.mode_switch_failed`），以及第 4 步查回的结果。只有 `completed`、`failed`、`interrupted` 发通知；`canceled` 是拥有者主动取消，不通知，但同样记为已见，并移出观察中集合。凡是还没记为已见、属于这三种状态的，都发通知并记为已见。
   - **前台不通知，但照常记已见**：窗口在前台时，所有判定照常更新已见集合，只是不发通知；之后切到后台，也不会为前台已经看过的内容补发。
   - **角标**：始终等于两个目标当前待审批集合的大小之和，不靠事件累加。
4. **没有补发时的恢复范围。** 重同步可能没有补发（seq 缺口或游标失效时会退回全量快照），快照里的终态任务也有数量上限。所以每次装好同一实例的新快照后，对“观察中任务”里既不在快照中、也还没有终态记录的任务，用 `get_task` 逐个查询：查到终态的，按第 3 步通知；查询失败的，保留在观察中集合，下次上线再查，不算作已通知。离线期间创建并结束、既没有补发、又超出快照近期范围的任务，不在当前恢复策略的覆盖范围内，不补通知。协议本身可以用 `list_tasks` 分页查询这些历史，本方案选择不扫描全部历史。这一限制，连同第 3 步的首次观察静默规则，写进 desktop 文档，并同步到提案笔记；本单不另建持久的通知服务。
5. **通知点击。** 点击通知后，主进程聚焦窗口，经 `subscribe(target)` 把导航意图 `{ target, sessionId, taskId }` 交给渲染进程。如果是 SubAgent 子会话，04 的会话树里没有它，就打开其父会话，并在右栏打开 07 的 SubAgent 页。切换目标不会改变在途审批的归属。
6. **放行名单与文档。** 放行名单新增 `get_confirmation_params`、`respond_confirmation`；`get_task` 已经由 04 加入。按 R20 同步 `docs/modules/desktop.md`，包括第 4 步的限制。

## 验收与证据

工程待验证。以下单测放在 `test/38-desktop-main.test.ts`，用两个替身目标，直接驱动主进程的通知判定逻辑，断言通知次数、所属目标与会话，以及角标计数：

- **通知判定**：
  - 首个快照里带有历史终态与旧审批：不发通知。
  - 同一个新审批，同时出现在快照和补发里：只通知一次。
  - 离线期间创建、之后被 TUI 处理掉的审批：不通知。
  - 离线期间结束的任务：补发一次通知。
  - 同一连接重同步、没有补发、观察中的任务已经不在快照里：用 `get_task` 查到终态后通知；查询失败时不算已通知，下次上线再查。
  - 两个目标的 seq 或对象 ID 相同：互不干扰。
  - 同一目标的 `instanceId` 换了：重建基线，不为新实例里的历史内容发通知。
  - 前台期间看到的事件：切到后台后不补发。
- **审批失效**（view 选择器单测，加上真实 Runtime、ControlServer 与 ControlConnection）：保持在线，由另一个客户端中断一个正在等待审批的任务，期间没有任何解决事件；断言卡片消失、角标减一。另外覆盖：切换模式或授予路径之后，旧审批不再计入。TUI 的待审批列表同样不再显示这些审批，TUI 回归通过。
- **模式切换失败**：保持在线，任务正在等待审批；另一个客户端请求切换模式，并让可控停止返回失败，复用 `test/94-task-ending.test.ts` 的机制。断言后台只有 `task.mode_switch_failed`、没有 `task.interrupted`；经桌面端使用的共享投影与选择器之后，任务显示为中断，卡片消失，角标减一；窗口不在前台时，收到一次中断通知，提示里保留失败原因。另外断言，前台、重复事件和首次同步时的补发，仍然遵守第 3 步的规则；任务已经是终态时，迟到的这个事件不会改写它。
- **首次观察静默**：旧游标在新实例上仍然有效；某个会话有 21 个已完成任务，快照只带 20 个，第 21 个只在补发里出现。断言这一批历史内容通知数为 0，随后一个真正新的终态只通知一次。握手期间缓冲的 `live` 终态，seq 大于快照截止点，也只通知一次。另外断言 `canceled` 不通知，但会移出观察中集合。
- **审批应答**：批准与拒绝各覆盖在线应答丢失、发送后断线、明确拒绝、未发送和核实失败五种情况。断言：界面能区分“结果未知”与明确失败；`respond_confirmation` 从不自动重发；状态由同一实例的新快照或查询结果核实。另外覆盖：TUI 抢先处理了审批；权限版本不一致时，重新展示详情、等待拥有者重新决定；切换目标或快照换代后，旧查询结果才到达，此时卡片不会复活，原决定也不会被送到另一个目标。

人工检查（外部验收）：
- 批准、拒绝各做一次，TUI 同步看到结果。
- 同一审批在 TUI 中处理后，桌面端的卡片消失。
- 把窗口切到后台后，新的待审批与任务结束都会发出通知；点击通知跳到对应会话，SubAgent 子会话会打开右栏的 SubAgent 页。
- 角标数正确。

1. **P2：通知没有定义快照、补发与实时事件之间的判定规则，现有验收无法排除旧审批误报与断线期间的新事件漏报。** 第 2、3 步只要求按快照与事件计算和通知“新的”待审批；但 [ControlConnection.sync](../../../packages/control/src/connection.ts) 先安装最新快照，再逐条回调 `replay`，[ViewState.applyEvent](../../../packages/tui/src/tui/state.ts) 明确不让补发回滚任务与审批状态。按这个实际顺序，断线期间创建又处理的审批已不在重连快照里，补发中仍有它的 `task.awaiting_confirmation`；直接对这条事件通知，会要求拥有者处理已经失效的审批。对快照新增项和补发分别通知，又会对同一新审批通知两次。反过来，全部忽略补发而只监听 `live`，会漏掉断线期间的任务结束。首次快照还包含近期历史终态，不能把它们都当成刚结束的任务。这些是按当前源码推演的反例，尚无桌面实现可运行。

   修订要求：明确每个连接目标及 `instanceId` 下的观察基线与去重身份，以及首次快照、同实例重连、同连接重同步、实例变化各自如何处理；对断线期间仍待处理的新审批和任务终态规定补通知规则，对快照已确认失效的旧审批不再通知。角标以当前待审批集合为准，不能由补发累加。不能假定重同步总有补发：seq 缺口或游标失效可能退回无 `replay` 的全量快照，且快照中的终态任务有数量上限；方案须写清如何核实原来观察中的任务及恢复范围，不把未恢复的记录算作已通知。只要求完成 R12 的规则，不要求另建持久通知服务。

   验收补充：首次快照带历史终态与旧审批；同一新审批同时出现在快照和补发；离线期间审批创建后已被 TUI 处理；离线期间任务结束；无补发的同连接重同步；两目标具有相同 seq 或相同对象 ID；同目标更换 `instanceId`。分别断言通知次数、目标／会话归属和角标计数，前台事件也更新观察基线，之后切到后台不补发前台已观察的旧消息。

2. **P2：审批应答只覆盖两种业务拒绝，遗漏应答丢失后的结果核实。** 第 1 步只列 `stale_confirmation` 与 `permission_version_mismatch`；批准已被后台接收但应答超时或连接断开时，这两种码都不会出现，客户端不能据此显示“批准失败”或直接让重试代替核实。[控制面失败规则](../../../docs/modules/control.md#不变量与失败处理)要求无幂等键的写请求先查询实际状态，再由拥有者决定。[TUI 审批详情](../../../packages/tui/src/tui/app.ts)已有对应流程：`unknown` 时用 `get_task` 查询原审批，`disconnected` 时等新快照，不自动重放。03 已负责跨 IPC 保留 `outcome`，但 05 负责的是提交与任务控制，本单也没有依赖或引用其失败处理，审批入口仍须明确承担这一步。

   修订要求：使用 03 的结构化 `{ code, outcome, message }` 区分 `rejected`、`not_sent`、`unknown`、`disconnected`；在线应答丢失查询原审批，断线等待同一实例恢复后核实，查询失败保留“结果未知”和安全的下一步，绝不自动重发批准／拒绝。请求及核实结果绑定发起时的目标、实例、审批 ID 与展示的权限版本；快照换代后的旧详情／核实结果不能覆盖当前卡片。权限版本不匹配要重新展示详情并等待拥有者重新决定，不能换成新版本自动批准。补齐 TUI／自动审查已处理或任务结束时卡片失效的路径；现有 `get_task`、`get_confirmation_params` 足够，不需要新增协议。
