# 协议升级后停止仍在运行的旧后台

Status: needs-triage

## 目标与边界

仓库升级、`PROTOCOL_VERSION` 变化之后，旧后台可能还在运行。这时新版本的 CLI `stop`、TUI 和桌面端都无法经控制面停止它：[服务端](../../../packages/control/src/server.ts)在认证之前就拒绝所有版本不等的请求。这个问题对 TUI 早已存在，桌面端规划时才被注意到。桌面端第一阶段只给出人工恢复步骤（[03](03-desktop-skeleton.md) 第 4 步），本单评估是否提供一种不经控制面的受控停止。

这不在拥有者已确认的桌面端范围内。是否要做、做到哪一步，由拥有者在评估后决定；不做时，人工恢复就是现行办法。

## 方案

待评估。03 第三轮方案审查给出了自动停止的前提，任何方案都必须满足：

1. **严格的启动身份。** [probeLockHolder](../../../packages/core/src/instance-lock.ts) 在 owner 没有 `processIdentity` 时，只按命令行特征判定后台存活。这种兼容语义用于保守地阻止第二个实例启动，不能作为发信号的依据。停止路径要有严格的身份核实：可以是新的严格查询，也可以是显式的身份核实字段。不能只凭 `held && !unverifiable` 判断，也不能解析 detail 文本。锁竞争、数据导入等现有调用方的保守语义保持不变；[test/101-instance-lock.test.ts](../../../test/101-instance-lock.test.ts) 的兼容回归也保留。
2. **连接与进程属于同一实例。** DATA 目录与 CONTROL 目录可以分别覆盖，所以拒绝连接的那个 socket 和某个数据目录的持锁进程，不一定是同一个后台。证明不了两者是同一实例，就拒绝自动停止，退回人工指引。
3. **发送前复核。** 拥有者确认之后、发 SIGTERM 之前，再核实一次目标没有换代，以免旧后台已被别处替换，结果停掉了新后台。超时不升级为 SIGKILL。

## 验收与证据

立项后补充。至少要有以下负例，并断言不会向无关进程或新实例发信号：缺少启动标识、但命令行看起来像后台的旧记录；A/B 路径错配；确认期间目标被替换。
