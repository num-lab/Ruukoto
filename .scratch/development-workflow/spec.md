# 跨模型开发流程

本次建立 Ruukoto 的开发方法：拥有者提出需求，与方案角色讨论，交由不同模型实施、整理文档和独立验收。目标是让新会话根据仓库资料接续工作，并能发现偏离需求的成果。依据为 2026-10-12 本会话两轮已确认的建议（Q6–Q12）；实施入口为[工单 01](issues/01-establish-workflow.md)。

## 已确认的决定

- 计划锁定目标、非目标、关键契约和验收标准；实现步骤可以调整。改变拥有者已确认的边界时，说明冲突与理由，重新讨论。
- 独立审查对照需求、项目约束和实际成果，可以否定计划；实施者总结只是导航。
- 轻量改动直接实施并验证；行为、架构、跨模块契约等重流程先有计划，再独立审方案与实现。角色代表职责，模型由拥有者按任务选择。
- 每项工作有一个任务入口，引用长期规范；聊天中新决定及时写回。方案者负责计划与决策，实施者负责实际变化和证据，文档角色据此整理说明。
- 实现问题返实施者，方案问题返方案者；改变确认范围才找拥有者。阻断意见必须有依据，偏好和优化建议不无限阻断交付。
- 工程验收与产品验收分别记录。Agent 证明客观要求，拥有者判断主观体验和产品取舍；必要的真实环境证据缺失时保持待验收。

## 范围

整理开发入口、任务与文档的职责、角色交接、审查和返工方法，复用现有 notes、工单与按改动面选择检查的机制。借鉴 DSH 的权威归属与渐进读取，以及 Magpie 的独立核验和针对实际交付版本的审查。

本次不建设全天候调度或工作流执行器，不修改产品行为、模型配置、CI 和发布授权。`docs/visual/` 只是历史漂移的例子，不为它建立专用门禁，也不在本次删除。历史工单在再次接手时核实，不批量重写历史资料。

## 验收

| 编号 | 要证明的结果 |
| --- | --- |
| A1 | 新会话只需角色和任务路径，就能找到有效目标、约束、阶段、下一步与验收要求 |
| A2 | 实施步骤的合理调整不反复请示；已确认目标或关键契约的改变必须明确提出 |
| A3 | 独立审查能识别“实现符合计划、测试通过，但计划违背需求”的案例，并正确退回 |
| A4 | 工程证据、审查意见和产品验收分别记录；实质改动后不会沿用旧审查结果宣称完成 |
| A5 | 简单改动不被迫填写重流程全部材料；原有 notes、文档和定向检查约定保持一致 |
| A6 | 文档与 skill 格式、链接和静态检查通过；方法的实际作用以独立演练与审查记录证明 |

主观产品验收不适用于本次文档与协作流程改动；跨客户端、跨模型的长期使用效果不由短演练代替。
