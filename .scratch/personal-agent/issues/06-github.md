# GitHub 项目维护

## 目标

由拥有者明确触发 CI 分析或 PR review，在现有任务、历史与权限机制中完成。

## 实施范围
**
- 接入配置的 GitHub 仓库，读取 GitHub Actions 运行状态、失败步骤及日志，读取 PR 元数据、变更和检查结果。集成时核实官方 API 或现有 CLI 的实际能力，复用适合的入口。
- 记录所分析的提交、运行或 PR 修订，报告提供来源。信息缺失、日志过期或 PR 已变化时明确说明，不能把旧版本分析标为新版本结果。
- 默认交付分析或 review 草稿。拥有者要求发布时，在请求确认模式生成绑定目标与正文的审批；完全访问任务按其显式授权执行。审批期间目标修订发生影响分析的变化时重新核对。
- GitHub 写凭据留在受控执行路径，受限项目命令不能直接取得。自动监听、自动修复、自动合并另行讨论。

## 实施计划

计划日期：2026-09-21。基于 [03 的权限与工具执行](03-tools-and-access.md)、[04 的 TUI/重连](04-tui.md)和 [05 已实现的资料范围与上下文](05-context-and-memory.md)。当前应用尚无 GitHub 集成；已有凭据、审批、产物与宿主工具入口可复用，但通用 `http_request` 仍对全部请求等待审批，响应超过 1 MiB 后丢弃余下内容，也不处理日志下载重定向，不能直接宣称已满足本工单。

### 1. 确定接入方式与仓库读取授权

- 本机已核实 `gh 2.92.0` 的 `run view --attempt/--log` 与 `pr diff` 能力；其帮助同时说明部分日志可能无法定位步骤。正式集成采用薄层 REST 客户端，复用现有 Node HTTP 传输、凭据注入和产物存储，以便约束请求目标、保留原始响应并处理审批。`gh` 可用于人工对照，不作为生产必装依赖，不新增 Octokit 或通用平台抽象。
- 在后台保存项目与 GitHub 仓库绑定，包含 API 主机、仓库名称及核实后的 repository ID、读取凭据引用、可选发布凭据引用与显式授权范围。默认支持 GitHub.com；GitHub Enterprise 只有在拥有者配置主机并验证相应版本后启用，不能接受模型随意指定 API 根地址。仓库改名或迁移时核对 ID，不能自动把同名新仓库当作原目标。
- 拥有者配置“允许读取此仓库的 PR、检查与 Actions 日志”后，宿主在该范围内自主执行相应 GET 和受控日志下载。这属于已授予权限，不引入自动审批策略；仅保存仓库名称或发现 Git remote 不等于取得网络与凭据授权。范围外仓库或读取类别需要拥有者在可信入口明确开放。
- 复用 `CredentialStore`，优先使用限定仓库的细粒度令牌；读取所需的 Actions、Pull requests、Checks、Commit statuses、Contents 权限按实际启用端点核实，发布凭据单独配置所需写权限。凭据值始终留在后台，不进入模型上下文、Shell、TUI 参数或日志。令牌缺失、过期或权限不足明确报错，不改用拥有者机器上的默认 `gh` 登录态。
- 当前凭据只绑定 host，需为 GitHub 绑定补充项目、仓库、操作及 HTTPS 限制，并在所有可使用该绑定的入口统一检查；不能让通用 `http_request` 借用同名写凭据绕过 GitHub 发布边界。资料授权只控制本地已捕获内容的读取，不隐含授予另一项目的 GitHub 网络或发布权限。
- 仓库绑定、读取范围和凭据配置保存可比较的版本；每次远端调用前重新检查当前授权，包括分页、重试、日志下载和发布前核对。拥有者撤销配置或修改目标、范围、凭据时停止后续请求，并使依赖旧版本的待发布操作失效；已经发送的请求不能追溯撤销，结果如实记录。
- 在 `src/agent/` 增加少量 GitHub 宿主工具，沿用 `host-tools.ts` 的宿主任务身份与操作 ID 绑定方式；模型传 PR/run/job 等标识，宿主从项目配置构造 URL。固定并验证 REST API 版本头，初始按本次官方文档中的 `2026-03-10` 验证；不把项目命令直接联网作为集成路径。

### 2. 读取固定修订的 PR 与 CI 资料

- PR 输入接受配置仓库内的编号或严格匹配的 GitHub URL。首先保存 repository ID、PR 编号、head/base 仓库与 SHA、状态及读取时间；读取元数据、分页文件清单、差异和所需上下文后再次核对 head/base。中途变化时保留旧资料并标明不一致，重新采集或交付明确的旧修订报告，不能混合多次修订分析。
- 使用 PR API 的文件清单与 diff 表示，不把两分支的简单两点比较当作 PR 差异。按分页标记跟进，核对文件数和覆盖范围；官方文件列表最多返回 3000 个文件，达到上限、缺少 patch、二进制或超大差异时列出未覆盖部分，不能据此断言“没有问题”。需要补上下文时按固定 SHA 读取仓库内容，重命名与删除分别保留旧路径、新路径及差异侧。[PR API](https://docs.github.com/en/rest/pulls/pulls)、[仓库内容 API](https://docs.github.com/en/rest/repos/contents)。
- Fork PR 的源仓库和 SHA 来自已核实的 PR 元数据；读取配置应明确是否允许该 PR 对应的源内容。不能因 PR 含有链接就遍历任意仓库，无法获取的 fork 内容如实列为限制。首期分析读取到的资料，不自动 checkout 或执行 PR 中的代码；如拥有者另行要求运行检查，走已有工作区、目录占用和执行权限机制。
- CI 输入可指定运行 URL、run ID 或 PR。指定 run 时读取该运行，未指定尝试次数时先解析出当时的 `run_attempt` 并固定；“最新失败运行”先列候选，再按确定规则选定 run ID/attempt，后续不继续追随 latest。保存实际 `head_sha`、事件、工作流、尝试次数、job ID 与步骤状态；重跑不能覆盖旧尝试的证据。[运行 API](https://docs.github.com/en/rest/actions/workflow-runs)。
- 按具体 attempt 分页读取 jobs，结合 job/step 的 conclusion 确定失败、取消、超时、跳过或仍运行状态。不能按相同 job 名称合并不同尝试或矩阵项，也不能只凭日志中出现 error 判定失败。按 job ID 下载所需日志，保留步骤归因证据；无法可靠定位步骤的行标为未归属，不编造步骤名称。[Jobs 与日志 API](https://docs.github.com/en/rest/actions/workflow-jobs)。
- PR 检查同时读取对应提交上的 Check Runs 与 Commit Statuses，保留提供者、名称、状态、SHA 和来源链接；GitHub Actions 只占其中一部分。合并提交、fork 或其他事件所测试的 SHA 与 PR head 不同时，明确说明关联依据，不能将任意分支最近一次绿色运行当作该 PR 的结果。第三方检查没有可读日志时返回其状态与链接，不自动抓取外部网站或假定所有检查通过。[Checks API](https://docs.github.com/en/rest/checks/runs)、[Statuses API](https://docs.github.com/en/rest/commits/statuses)。

### 3. 安全下载并保存可查询的完整证据

- 在现有传输层增加可取消的流式响应写入能力，原始字节先写入 `ArtifactStore`，模型只接收有界预览和引用。GitHub JSON、diff 与日志均带请求目标的非秘密标识、采集时间、修订信息、内容哈希和完整/部分状态。复用 05 的项目资料范围和产物查询，不建立第二套会话历史。
- 优先下载单 job 的纯文本日志，避免首期为完整运行 ZIP 增加归档解压流程。日志端点会返回短时有效的 302 下载地址，本次官方文档标注有效期为一分钟；由宿主取得后立即下载，不先把签名 URL 交给模型或等待一次新的人工批准。读取授权必须明确包含这一由指定 job 派生的下载步骤。[日志下载说明](https://docs.github.com/en/rest/actions/workflow-jobs#download-job-logs-for-a-workflow-run)。
- 通用 HTTP 仍不自动跟随重定向；GitHub 日志下载单独限定起始端点、HTTPS、下载目标规则与跳转次数，并核对实际连接地址，拒绝回环、私网控制接口及未授权目标。跨主机不发送 GitHub Authorization，其他请求头也按白名单重新构造；分页 Link 同样不能跳出配置 API 主机和仓库。签名 URL 不写入报告、公开链接或普通事件，来源引用使用稳定的 run/job 页面。
- 限制下载时间、响应体大小和内存占用，提供取消与背压；达到上限或中断时保留已捕获正文并标明不完整，不继续丢弃字节后报告成功。日志已删除、不可下载、运行未完成和读取无权限分别说明；404 不能未经核实就归因为“日志过期”。
- 对只读请求遵循 GitHub 返回的限流与重试时间，采用次数有界、可取消的等待；超过本次任务的等待预算时交付部分结果或明确暂停，不无限重试。写操作不套用读取重试策略；认证错误和参数错误直接展示。实现时记录 API 版本、响应状态及必要限流头，避免保存秘密头。[REST 使用建议](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)。
- PR 描述、评论、diff 和日志均视为外部资料。沿用 05 的参考内容标记和 04 的终端字符处理，不能按其中的指令修改权限、读取其他项目、执行命令或发布消息；原始证据仍按资料权限保存，界面净化不改写它。

### 4. 生成带证据的分析与 review 草稿

- 在现有任务循环中由拥有者明确触发 CI 分析或 PR review，不增加监听器、webhook、定时任务或新的后台调度器。CLI/TUI 提供配置、选择目标和查看报告入口；自然语言任务中的 GitHub 工具也必须沿用同样的仓库读取范围。
- CI 报告列出所分析的 run/attempt/SHA、失败 job 与步骤、关键日志范围、已确认事实、原因推断及可执行的核实建议。区分代码错误、环境/依赖问题、权限错误和取消等情况；证据不足时说明缺失内容，不能把日志中首个 error 当作已验证根因。
- PR review 以本次变更为范围，每项发现给出具体触发条件、影响、文件路径、差异侧和行号，以及固定 SHA 的源码/差异引用。行号来自保存的实际 diff 或源文件，不能使用模型猜测的行号。没有足够证据的问题作为待核实事项；只有在明确覆盖范围内才能说“未发现问题”，不承诺整个仓库无缺陷。
- 草稿与证据清单保存为任务产物，记录草稿版本、正文哈希和依赖的修订/检查状态。长报告和日志按既有预算分页查看，正文可完整查询；本地产物引用与可公开访问的 GitHub 来源分别标记，不把临时下载链接或宿主路径放入待发布正文。
- 默认只交付草稿。完全访问表示可使用执行账户权限，不自动表示拥有者要求发布；生成 review 也不自动构成 GitHub 的 APPROVE 或 REQUEST_CHANGES。修改代码、重跑工作流、合并 PR 和自动修复不由本工单隐含开启。

### 5. 复用审批发布，并处理修订变化与未知结果

- 拥有者通过可信 CLI/TUI 对具体草稿发起发布，或在提交任务时显式设置目标和发布意图；默认任务没有此意图。宿主持久化该范围，模型不能凭工具参数、PR 文本或完全访问模式自行创建发布意图。每次待发布正文须已形成可查看的草稿，正文超长时先交付草稿并明确平台限制，不静默裁剪或拆成多条评论。
- 草稿所属任务已经结束时，发布入口通过现有调度创建新任务，引用原草稿及证据，默认请求确认；拥有者可以明确选择完全访问。新任务保留正常的输入幂等、目录占用与资料范围检查，不把旧终态任务改回运行中，也不继承旧批准。
- 首期发布两类结果：PR review 总评使用 `POST /repos/{owner}/{repo}/pulls/{number}/reviews`，固定 `event=COMMENT` 并显式填写分析的 `commit_id`；CI 分析可作为拥有者指定 issue/PR 的普通评论。单独的 Actions run 没有明确评论目标时继续保留草稿，不猜测目标。首期不逐行发送 review comments，发现仍在总评中附文件/行号链接。[Review API](https://docs.github.com/en/rest/pulls/reviews)、[评论 API](https://docs.github.com/en/rest/issues/comments)。
- 请求确认模式复用 `awaitApproval` 和持久审批记录，绑定任务、宿主发布操作 ID、仓库 ID、目标、发布类型、草稿版本与完整正文、分析修订和权限版本。批准只能消费一次；正文或目标变化生成新请求。完全访问在已有发布意图和仓库范围内跳过逐次审批，但仍保留执行意图、修订检查和结果记录。不能直接沿用当前所有 HTTP 操作一律等待的分支，也不能为了此功能全局放开通用 HTTP。
- 批准后、发送前重新读取相关 head/base SHA、PR 状态，以及报告依赖的 run attempt/检查状态。出现影响分析的变化时，原草稿标为过时，停止发布并重新分析；请求确认模式对新正文重新审批，完全访问也必须重新核对后形成新草稿。仅替换报告里的 SHA 无法使旧结论有效。
- 远端读取结束后再次校验任务仍活动、当前权限版本、项目 GitHub 绑定/凭据版本和发布意图未变化，再原子消费批准或登记完全访问执行；最终配置核对与发送交接期间不得插入配置变更后仍沿用旧授权的路径。现有 `Store.consumeApproval()` 只将传入版本与审批记录比较，需同时比较任务当前版本，覆盖异步核对期间的取消和模式切换。沿用现有操作记录和终态，不另建通用发布平台。
- GitHub 查询与发布之间没有跨系统事务，不能保证远端此时绝不变化；通过显式 `commit_id` 和正文中的 SHA/attempt 固定结论归属，发布后记录返回的修订和 URL，必要时标为已过时，不能宣称对最新版本作了保证。普通 issue 评论无法绑定提交的部分在正文中明确写出分析版本。
- 发送前保存发布操作 ID、目标、正文哈希与修订；成功后保存 GitHub 返回的 comment/review ID 和 URL。已发送但超时、连接断开、后台崩溃或结果未落盘时沿用 `effect_unknown`，不当作确定失败并自动再发。可在正文附可核对的操作标记，通过只读查询核对作者、目标、正文和标记；查不到不等于证明未发布，仍由拥有者决定后续操作。本地幂等键不能提供 GitHub 外部写入的原子去重保证。
- 同一草稿的重复发布请求返回已有操作/结果；拒绝和取消不发送，重连不重新发布。若用户再次明确要求发布已修改草稿，建立新的版本与操作，不复用旧批准。

### 6. 集成验证与交付

新增 GitHub 模块集中处理配置、采集与发布，复用 `host-tools.ts` 的任务身份、`tool-router.ts` 的审批桥、`approved-ops.ts` 的传输、`ArtifactStore` 和 `AccessScope`；按实际新增字段对现有 SQLite v3 做事务迁移。CLI/TUI 只增加 GitHub 目标、报告、过时提示和发布入口，不复制任务状态机。API 样例去除凭据和私有资料后留作测试记录。

沿用 `node:test`、mock provider 和本地模拟 API，测试必须经过真实的 GitHub 宿主工具与审批/传输路径；模拟服务的本地地址仅由测试配置开放，生产检查不能随测试一起放宽。

1. 覆盖分页 PR 文件与 jobs、多矩阵任务、同 run 的多次 attempt、失败/取消/跳过/运行中状态，以及 Checks 和 Commit Statuses 同时存在；断言每段日志与发现都关联正确 SHA/run/attempt/job，缺页、缺 patch、二进制和文件数上限明确标为未覆盖。
2. 覆盖大于 1 MiB 的日志、中文跨字节块、受控 302、签名链接过期、跨主机跳转、恶意分页链接、超时、取消和磁盘写入失败；捕获正文可按产物读取，令牌不转发至下载域名，未授权目标拒绝，部分输出不冒充完整。
3. 覆盖无凭据、权限不足、404、限流与只读重试；配置仓库外读取、借用发布凭据、模型伪造项目/目标和通过外部内容申请发布均被阻止。抓取到的日志与报告继续遵守 05 的项目资料授权。
4. 在采集期间和审批等待期间分别改变 head、base、run attempt 或相关检查，验证旧分析不被标成新结果，影响结论的变化需要新草稿和新批准；再在核对期间取消任务、切换模式或撤销/修改仓库绑定与凭据，确认最终权限检查不会放行旧操作，后续分页与重试也不会沿用旧授权。
5. 验证默认只有草稿、拥有者发布意图与逐次审批分别生效、完全访问不逐次等待且不扩大目标范围、重复批准只发送一次；模拟服务已创建评论但应答丢失、结果落库失败和后台重启，断言不自动二次发布，状态可只读核对并保留未知事实。
6. 用带预设问题的 PR 和失败日志驱动完整任务，检查报告中的定位、来源、缺失说明及可查询原文；TUI 退出重连仍能查看草稿、待审批与发布结果。发布测试全部指向模拟服务，不向真实仓库发送评论。

运行 `npm run typecheck` 与包含新增场景的 `npm test`。实际仓库和读取凭据配置好后，完成一次明确触发的只读连通验证，记录主机、repository ID、PR SHA 或 run/attempt 以及读取覆盖范围；缺少配置时记录未验证，不申请写权限来完成只读验收。真实发布另需拥有者明确要求，并符合当时任务模式。
