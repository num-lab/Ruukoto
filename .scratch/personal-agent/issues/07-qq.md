# QQ 接入阶段设计

## 已明确目标

接入 QQ 群聊，用于活跃气氛和后续群聊工具的入口。复用后台任务；群成员只可触发明确开放的群聊能力，不能提升权限或访问开发项目的历史与凭据。

## 进入本阶段时补齐

- 根据届时可用的官方接口及拥有者现有环境确定接入方式，不提前假定协议。
- 确定允许接入的群和身份范围、首批工具、被提及时回应或主动参与的规则、发言频率和安静时段。
- 明确消息去重、回应目标、群内资料访问范围及管理入口。QQ 消息不作为拥有者的完全访问授权渠道。

## 实施计划

计划日期：2026-09-21。本工单先完成接入与群聊行为的阶段设计，依赖 [06 的交付](06-github.md)，复用 [04 的后台交互](04-tui.md)和 [05 的资料边界](05-context-and-memory.md)。接入协议、目标群、成员范围及主动发言规则尚未确认；以下建议与实施顺序不代表已经取得这些配置或启用授权，当前 `needs-info` 仍适用。

### 1. 核实实际接入条件，选定一条路线

- 先整理拥有者已有环境：是否已有 QQ 机器人应用或正在使用的接入服务、应用可用的群聊权限、测试群及管理权限、Linux 部署方式、是否具备 HTTPS 回调入口。只记录非秘密配置与凭据文件位置，AppSecret、访问令牌及登录材料不写进工单或聊天历史。
- 优先核实官方机器人接口是否覆盖目标群和所需互动方式。官方文档已列出群聊场景、访问凭证以及提及/普通群消息事件，但应用能否实际订阅、添加到目标群和发送相应消息，仍需管理端与测试验证；不能把“QQ 群”“频道”和单聊混用。[接入指南](https://bot.q.qq.com/wiki/)、[启动接入](https://bot.q.qq.com/wiki/develop/api-v2/)、[消息收发概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)。
- 传输方式依据该应用当前可用能力和部署条件选择。腾讯维护的旧 BotGo README 与较新的 QQBot 接入示例对 WebSocket 的描述存在差异，不能据旧公告直接宣布不可用，也不能因示例支持就认定本应用可用。验证事件接收、身份鉴别、重连或回调重投后，只实现选定的 Webhook 或 WebSocket 路线。[BotGo](https://github.com/tencent-connect/botgo)、[QQBot 接入示例](https://github.com/tencent-connect/openclaw-qqbot/blob/main/README.zh.md)。
- 先检查官方 [Node SDK](https://github.com/tencent-connect/bot-node-sdk) 的发布版本、群聊 API、传输支持和许可，再决定直接复用还是以现有 Node 能力实现薄适配层。固定实际验证过的版本或提交，不引入 OpenClaw 整套运行时，也不同时建设多个 QQ 协议后端。
- 官方路线存在实际功能缺口时，记录具体缺口与拥有者现有服务的能力，再决定是否评估其他接入方式；不提前指定 OneBot 或个人 QQ 登录方案。账号注册、应用权限配置与真实群消息测试在实施阶段由拥有者提供条件并明确范围，本次编写计划不执行这些外部操作。

### 2. 收集并记录必须明确的群聊规则

把以下问题集中形成一轮确认，答案按时间追加到 `Comments`。优先用可验证的配置值表达，不把“活跃气氛”直接解释为持续监听或自由主动发言。

| 待确认事项 | 建议起点，尚未确认 | 实施前需记录的内容 |
| --- | --- | --- |
| 群和成员范围 | 一个指定测试群及有限测试成员 | 机器人应用、实际群标识、成员允许范围；是否所有群成员均可触发 |
| 回应触发 | 仅明确 @ 机器人时回应 | 是否接受回复引用、固定命令；非 @ 消息是否接收、留存或进入上下文 |
| 主动参与 | 初期关闭 | 若启用，明确触发条件、允许话题、退出条件、是否需要普通群消息权限；定时发言另列规则 |
| 频率和安静时段 | 单条最终文本回复，排队有上限 | 每群/每成员冷却、群与机器人总量限制、时区和安静时段、最长等待时间；同时满足平台限制 |
| 首批能力 | 文本聊天，不开放额外工具 | 如需娱乐或查询工具，逐项列输入、数据来源、副作用和允许的发送目标；图片、语音、附件是否需要 |
| 历史与记忆 | 只使用本群已接纳交互，不继承个人记忆 | 群内上下文是否共享、不同成员能否查询旧记录、是否启用群记忆、留存及撤回处理规则 |
| 管理入口 | 继续使用可信 CLI/TUI | 谁能启停接入、修改范围、清理队列、查看记录；是否允许群内执行有限的静音操作 |

建议先验证“允许成员 @ → 一次任务 → 原群回复”的闭环，再根据明确规则加入主动参与。这只是实施起点；若拥有者选择首批即包含主动发言或群聊工具，应把相应行为与验收一并补齐，不以建议替代用户决定。没有安静时段、额度等答案时不自行填入看似合理的数字。

### 3. 先封闭 QQ 入口、工具和资料权限

- 复用 Runtime 的排队、任务状态、取消、历史与恢复机制，增加只接收经验证 QQ 事件的窄入口。平台身份来自已验证的连接/回调，宿主据机器人、群和成员标识映射会话；不能把拥有者 token 交给 QQ 适配器调用任意控制面操作，也不能从消息正文取得项目 ID、权限模式或管理身份。
- 群成员的显示名、群管理身份、转发消息中的作者，以及拥有者本人在 QQ 内的发言，都不等同于后台拥有者认证。QQ 入口不得开启完全访问、授予文件路径、响应开发任务审批、管理凭据或给其他任务授权；群内有限管理命令若被选中，另设固定操作范围。
- 按宿主持久化的 QQ 入口配置选择完整工具集合，并在实际执行时再次检查。当前 `Driver.ensureSdk()` 会在 `toolFactory` 之后追加资料和 GitHub 工具，单把编码工具列表设为空仍会开放其他能力。QQ 白名单必须覆盖所有注册来源；首批未确认时按空工具集合设计，不注册 Shell、文件工具、通用 HTTP 或 GitHub 发布。
- 资料范围独立于普通开发项目。当前 `MemoryStore.listActiveFor()` 会包含个人共享记忆，`owner_note` 来源也默认可读；因此仅创建 QQ 项目或禁用历史工具不足以隔离。为 QQ 增加受宿主约束的资料身份，同时用于历史搜索、原文/产物读取、记忆查询、来源跳转及每轮上下文注入，默认排除开发历史、个人共享记忆、项目指令和跨项目授权。
- 建议以“机器人应用 + 群”映射独立会话与群资料范围，在用户确认共享上下文规则后落地。不同群不得因使用同一机器人、相同成员 ID 或重用会话而串用历史；同群多人交互保留发言人及回复关联，不能把 A 的问题与 B 的身份混合。私聊/频道不属于本次默认开放范围。
- 现有会话必须绑定真实目录且任务持有目录锁。首版为独立群会话分配符合保护根限制的专用空工作目录，避免所有群共用目录而全局串行，也不复用开发仓库；沿用既有锁和执行环境检查，不为纯聊天先重构整套无工作区运行时。群工具、项目指令与执行后端的启动校验需在最小验证中一起检查。

### 4. 设计收件去重、会话排队与发送控制

- 按选定传输验证应用身份、事件来源和消息结构；Webhook 按当前协议验签与处理验证请求，WebSocket 按当前协议处理鉴权、心跳与恢复。事件大小、过期规则和重复投递分别校验，平台握手/心跳不生成模型任务。接入凭据只供适配层使用，令牌刷新复用可用 SDK 或最小受控实现。
- 事件在允许范围内且满足触发规则后，持久化机器人、群、发送人、平台消息/事件 ID、时间、正文及回应关联，并生成稳定的 Runtime `request_id`。去重键包含平台规定的标识作用域，不能只按消息文本或显示名去重；接收成功的应答必须晚于可靠登记，重投和后台重启后不会重复创建任务。
- 收件登记与任务创建之间可恢复地关联：若已经登记但尚未入队，恢复时用原请求键核实；不能因事件已被去重就永久漏掉任务，也不能换新键重新提交。复用现有 SQLite 和 FIFO，不新增消息中间件；对达到队列上限、超时或不满足规则的消息记录明确处理结果。
- 消息是否进入模型上下文与是否触发回复分别判断。首期不默认采集全群历史；未开放成员/群的数据不进入任务，机器人自身消息及已识别的回声不重复触发。编辑、撤回、引用不可读原文、非文本消息按确认后的规则处理，不伪造内容或扩大为自动附件下载。
- 回应目标由宿主在收件时固定，模型只产生候选正文，不能自行选择群、成员或消息 API 参数。默认只发送用户可见的最终回复，不把模型中间文本、工具日志、审批正文、系统错误栈或通用事件流转发到群里。长文本是否拆分须受已确认的消息条数和长度限制约束，不能自动把一次回复变成刷屏。
- 群聊发送使用专用的发送入口和授权规则，不复用 GitHub 发布意图，也不让普通群回复逐条等待开发任务审批。拥有者事先配置的群、触发方式和能力范围构成发送授权；平台被动回复所需关联字段由宿主填写。平台的回复时效、次数及去重字段按实际接口验证，借鉴官方 [消息收发规则](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)，不把入站重投序号与出站回复序号未经核实视作同一语义。
- 入队、模型调用前与发送前检查当前群/成员范围、配置版本、静音、配额和消息时效。配置被撤销或回复已过时，停止后续处理；被动回复窗口已过不能自动改为主动消息。安静时段结束后不集中补发积压内容。若确认主动参与，候选发言同样经过发送控制，不能让模型自行绕过限频。
- 每次发送先保存固定目标、正文和本地发送操作 ID，成功后记录平台消息 ID；明确区分模型任务完成与消息已发送。网络超时或后台崩溃导致结果不明时，复用 06 的 `effect_unknown` 原则，不自动换回复序号再次发送；只有平台能验证的幂等/查询语义才可用于恢复，否则由拥有者核实。断线重连不自动发送失效回复或恢复中断任务。

### 5. 明确管理、验证及后续工单交付

- 管理仍通过已有可信 CLI/TUI，提供接入状态、群配置、启停、队列、发送结果和错误查看。QQ 公网入口只暴露选定的事件接收能力，不公开拥有者控制 socket 或开发资料接口；一键停用必须阻止新的接收任务和后续发送，运行中任务按既有取消机制收尾。
- 首轮不预建额外平台框架。用户确认接入路线与群聊规则后，补齐具体模块、协议版本、凭据部署、数据库迁移及运行命令；复用现有 Runtime、AccessScope、会话 JSONL 与产物存储。持久记录只覆盖已决定保留的交互，不把完整平台事件、鉴权头和秘密参数无差别写入历史。
- 先用模拟平台事件与发送服务，经真实适配器、Runtime 和发送控制验证：合法/非法身份、白名单、同消息重投、登记后未入队崩溃、同群排队及跨群并行、机器人回声、回复目标固定、超时积压、静音及撤销配置、平台限流和发送结果未知。测试不得向真实群发送消息。
- 隔离验证同时覆盖工具注册与调用、个人共享记忆自动注入、历史/产物查询、伪造群 ID、跨群及开发资料访问、群消息冒充拥有者或请求完全访问。至少使用一个已有个人共享记忆的后台，证明新建群范围后不会自动带入该记忆；只断言模型没主动调用工具不足以证明隔离。
- 实施后运行 `npm run typecheck` 和包含新增接入场景的 `npm test`，保留既有开发任务、TUI 与 GitHub 回归验证；仅完成模拟事件或本机检查时，不声明真实 QQ 接入和 Linux 部署已通过。
- 仅在拥有者指定测试应用、群和成员并明确授权测试后，执行一次真实“收消息—生成回复—发回原群”闭环；记录事件类型、实际身份字段、回复时效、可用配额和断线恢复结果。该测试是后续实施步骤，本次计划不代表真实群发送授权。主动发言只有规则已经确认且平台支持时另行验证。
- 把用户答案与真实验证事实追加到本工单 `Comments`，区分已确认规则、工程方案和未验证能力；相应更新规格，必要时按领域文档约定记录 ADR。信息齐全后补成可执行的接入工单并按 `docs/agents/triage-labels.md` 更新状态；当前只完成计划，不把建议写成用户答案，也不提前改成 `ready-for-agent`。
