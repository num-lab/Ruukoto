# QQ 接入阶段设计（NapCat）

本工单负责 QQ 群聊。新增私聊交互由 [21：消息平台接口](21-messaging-platforms.md) 跟踪；下文对 QQ 入口的权限限制适用于本工单的群聊范围，私聊身份与控制权限在 Issue 21 中独立定义。

## 已明确目标

接入 QQ 群聊，用于活跃气氛和后续群聊工具的入口。复用后台任务；群成员只可触发明确开放的群聊能力，不能提升权限或访问开发项目的历史与凭据。

接入方式已确定为 NapCat，通过其 OneBot v11 接口连接登录的 QQ 账号。取消此前优先评估官方机器人应用及官方 SDK 的路线，不再将官方机器人应用注册、AppSecret 或群消息订阅权限作为前置条件。

## 已确认规则

- NapCat OneBot v11 正向 WebSocket，ruukoto 主动连接；部署地址和账号属于部署配置，不再比较官方机器人或其他协议路线。
- 首次启用一个指定群，全体成员均可明确 @机器人触发。首版纯文本聊天，不接私聊、频道、主动发言、图片、语音、附件及群管理命令，不开放额外工具。
- 不设置发言频率限制、成员冷却或每小时发言额度，不设安静时段，全天响应明确 @。账号离线、队列资源保护及消息有效期不等于发言配额。
- 按“登录账号 + 群”共享独立会话，每群一次执行一个任务，FIFO 排队；未开始执行的请求等待超过 5 分钟即过期跳过。不同群相互隔离。
- 仅保留已触发任务的交互；不注入开发历史、个人共享记忆、项目指令或跨项目资料，群成员不开放历史查询。引用原文仅在属于本群已接纳交互时进入上下文，不主动抓取其他历史。
- 原始交互保留至拥有者手动清理；收到撤回事件后，该消息不再进入后续上下文，取消尚未发送的相关回复，已发送回复不自动撤回。撤回事件丢失时不能宣称已从平台获知撤回。
- 默认每次任务发送一条最终文本回复，不自动拆成多条；超过已核实的平台长度上限时缩短候选回复或明确失败，不发送中间过程。
- 管理沿用可信 CLI/TUI。QQ 身份不能批准开发任务、修改权限或取得完全访问能力。

## 部署配置与事实验证

实施时查验 NapCat 版本、端点、登录身份和 API 行为；实际账号、测试群、token 通过可信配置入口填写，工单不保存秘密。未配置不启用，不自动猜测群号。真实群收发须另有明确测试范围与发送授权；这些属于部署与验收条件，不再阻塞实现规格。

## 实施计划

计划日期：2026-09-21；2026-09-22 按拥有者要求改为 NapCat。本工单先完成接入与群聊行为的阶段设计，依赖 [06 的交付](06-github.md)，复用 [04 的后台交互](04-tui.md)和 [05 的资料边界](05-context-and-memory.md)。接入路线及群聊规则已确认，以本工单“已确认规则”为准；实际部署参数在启用前填写。GitHub 后续按 [17](17-replace-github-module-with-mcp.md) 退役专用模块，QQ 仅复用公共运行时与发送结果处理原则，不依赖旧 GitHub 业务实现。

### 1. 配置 NapCat 与 OneBot 连接

- 记录 NapCat/QQ 客户端的实际版本、Linux 部署方式、登录 QQ 账号标识、测试群及账号在群内的状态。登录、扫码和会话材料由拥有者在 NapCat 侧管理；本项目仅保存连接配置与受保护的 token 引用，不将 token、二维码或登录材料写入工单、模型上下文和日志。[NapCat 项目](https://github.com/NapNeko/NapCatQQ)。
- 首版使用正向 WebSocket：NapCat 提供 OneBot WebSocket 服务端，ruukoto 主动连接，避免为后台增加公网事件入口。NapCat 文档及配置支持正向/反向 WebSocket；本轮仅实现正向连接，部署须提供可达端点。[接入文档](https://napneko.github.io/use/integration)、[网络配置定义](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/config/config.ts)。
- 默认在本机回环或受控私网连接，启用 token 鉴权；跨主机通过受保护传输连接。区分 OneBot token 与 NapCat WebUI 管理凭据，适配器不获得 WebUI 管理能力。核对登录身份与预期账号一致后才接纳事件；账号离线或身份变化时停止接收新任务和发送。
- 复用现有 Node WebSocket 能力实现薄 OneBot v11 适配器；确有缺口时再选经过验证的小型依赖。固定验证版本，解析结构化消息段，处理动作响应关联、心跳、重连和失败。NapCat 独立部署，应用启动不安装、升级或嵌入另一套机器人运行时。
- 先验证连接鉴权、群消息事件及群消息发送动作的请求和响应；只有实际部署版本支持并经过测试的行为才作为依据。接口不可用时明确报错，不回退到官方机器人接口；首次真实群测试的账号、群和成员范围在实施阶段明确。

### 2. 将已确认群聊规则落为配置与验收

按上方规则实现，不再次征询相同产品决策。群号、账号及端点未配置时保持禁用；允许列表、配置撤销和队列内存上限属于运行保护，不能借此新增成员冷却、每小时额度或安静时段。撤回处理需关联原消息、排队/运行任务与尚未发送的回复。

### 3. 先封闭 QQ 入口、工具和资料权限

- 复用 Runtime 的排队、任务状态、取消、历史与恢复机制，增加只接收经验证 NapCat 连接事件的窄入口。身份依据经鉴权的固定端点、预期登录账号及事件中的 self_id、group_id、user_id，宿主核对后映射会话；不能把拥有者 token 交给 QQ 适配器调用任意控制面操作，也不能从消息正文取得项目 ID、权限模式或管理身份。
- 群成员的显示名、群管理身份、转发消息中的作者，以及拥有者本人在 QQ 内的发言，都不等同于后台拥有者认证。QQ 入口不得开启完全访问、授予文件路径、响应开发任务审批、管理凭据或给其他任务授权；群内有限管理命令若被选中，另设固定操作范围。
- 按宿主持久化的 QQ 入口配置选择完整工具集合，并在实际执行时再次检查。当前 `Driver.ensureSdk()` 会在 `toolFactory` 之后追加宿主工具，单把编码工具列表设为空仍会开放其他能力。QQ 白名单必须覆盖资料工具及后续 MCP 等所有注册来源；首版按空工具集合设计，不注册 Shell、文件工具、通用 HTTP 或 MCP 工具。NapCat 连接仅供群聊适配器收发，不将其全部管理动作暴露给模型。
- 资料范围独立于普通开发项目。当前 `MemoryStore.listActiveFor()` 会包含个人共享记忆，`owner_note` 来源也默认可读；因此仅创建 QQ 项目或禁用历史工具不足以隔离。为 QQ 增加受宿主约束的资料身份，同时用于历史搜索、原文/产物读取、记忆查询、来源跳转及每轮上下文注入，默认排除开发历史、个人共享记忆、项目指令和跨项目授权。
- 以“NapCat 登录账号 + 群”映射独立会话与群资料范围，同群共享上下文。不同群不得因使用同一账号、相同成员 ID 或重用会话而串用历史；同群多人交互保留发言人及回复关联，不能把 A 的问题与 B 的身份混合。私聊/频道不属于本次默认开放范围。
- 现有会话必须绑定真实目录且任务持有目录锁。首版为独立群会话分配符合保护根限制的专用空工作目录，避免所有群共用目录而全局串行，也不复用开发仓库；沿用既有锁和执行环境检查，不为纯聊天先重构整套无工作区运行时。群工具、项目指令与执行后端的启动校验需在最小验证中一起检查。

### 4. 设计收件去重、会话排队与发送控制

- 按固定 NapCat 端点验证连接、账号和 OneBot 事件结构，处理鉴权、心跳、离线及重连。事件大小、过期规则和重复接收分别校验，握手、心跳和动作响应不生成模型任务。结构化消息中的 @ 按目标账号判断，不能仅匹配显示名或正文中的 @ 字符；连接 token 由可信管理入口轮换，不套用官方机器人访问令牌刷新流程。
- 事件在允许范围内且满足触发规则后，持久化登录账号、群、发送人、消息 ID、时间、正文及回应关联，并生成稳定的 Runtime `request_id`。按实际 OneBot 事件核实消息 ID 作用域，以账号、群和消息 ID 等组成稳定去重键，不能只按消息文本或显示名去重。先可靠登记再入队；WebSocket 收到事件不等于平台提供持久投递确认，不假定断线事件会重投，连接中断期间的缺失如实标记。
- 收件登记与任务创建之间可恢复地关联：若已经登记但尚未入队，恢复时用原请求键核实；不能因事件已被去重就永久漏掉任务，也不能换新键重新提交。复用现有 SQLite 和 FIFO，不新增消息中间件；对达到队列上限、超时或不满足规则的消息记录明确处理结果。
- 消息是否进入模型上下文与是否触发回复分别判断。首期不默认采集全群历史；未开放成员/群的数据不进入任务，机器人自身消息及已识别的回声不重复触发。撤回与引用按已确认规则处理；首版忽略不支持的编辑及非文本事件，不伪造原文或自动下载附件。
- 回应目标由宿主在收件时固定，模型只产生候选正文，不能自行选择群、成员或消息 API 参数。默认只发送用户可见的最终回复，不把模型中间文本、工具日志、审批正文、系统错误栈或通用事件流转发到群里。长文本按单条回复及实际长度上限处理，不自动拆分。
- 群聊发送使用受控的 OneBot 群消息动作，由宿主固定目标并构造文本及可选回复消息段。拥有者事先配置的群、触发方式和能力范围构成发送授权，普通群回复不逐条等待开发任务审批。动作响应的关联字段只用于匹配请求与应答，不能当作远端幂等键；按实际版本核实成功状态、错误码和返回消息 ID，不套用官方机器人的被动回复窗口或回复序号规则。
- 入队、模型调用前与发送前检查群/成员范围、配置版本、启停状态和账号在线状态；未开始执行的请求超过 5 分钟即跳过。发送前再次核对原消息是否撤回。无安静时段、主动参与和发言配额。
- 每次发送先保存固定目标、正文和本地发送操作 ID，成功后记录返回的消息 ID；明确区分模型任务完成与消息已发送。网络超时、NapCat 离线或后台崩溃导致结果不明时，复用公共 `effect_unknown` 原则，不自动换动作关联 ID 再次发送；只有实际可验证的幂等/查询语义才可用于恢复，否则由拥有者核实。断线重连不自动发送失效回复或恢复中断任务。

### 5. 明确管理、验证及后续工单交付

- 管理仍通过已有可信 CLI/TUI，提供 NapCat 连接及登录状态、群配置、启停、队列、发送结果和错误查看。正向 WebSocket 方案不增加公网入站接口，NapCat WebUI、OneBot 端点和拥有者控制 socket 分别限制访问；一键停用必须阻止新的接收任务和后续发送，运行中任务按既有取消机制收尾。
- 首轮不预建额外平台框架。基于已确定的 NapCat 路线，按已确认规则补齐具体模块、协议版本、凭据部署、数据库迁移及运行命令；复用现有 Runtime、AccessScope、会话 JSONL 与产物存储。持久记录只覆盖已决定保留的交互，不把完整平台事件、鉴权头和秘密参数无差别写入历史。
- 先用模拟 OneBot WebSocket 事件与动作响应，经真实适配器、Runtime 和发送控制验证：token 错误、登录账号不匹配、账号掉线、白名单、重复消息、登记后未入队崩溃、同群排队及跨群并行、自身消息回声、回复目标固定、响应乱序、超时积压、停用及撤销配置、发送失败和结果未知。测试不得向真实群发送消息。
- 隔离验证同时覆盖工具注册与调用、个人共享记忆自动注入、历史/产物查询、伪造群 ID、跨群及开发资料访问、群消息冒充拥有者或请求完全访问。至少使用一个已有个人共享记忆的后台，证明新建群范围后不会自动带入该记忆；只断言模型没主动调用工具不足以证明隔离。
- 实施后运行 `npm run typecheck` 和包含新增接入场景的 `npm test`，保留既有开发任务、TUI 与通用工具回归验证；仅完成模拟事件或本机检查时，不声明真实 NapCat 接入和 Linux 部署已通过。
- 仅在拥有者指定 NapCat 登录账号、测试群和成员并明确授权测试后，执行一次真实“收消息—生成回复—发回原群”闭环；记录 NapCat 版本、连接方式、事件字段、动作响应及消息 ID，并验证账号掉线和连接恢复。该测试是后续实施步骤，本次调整工单不代表真实群发送授权。主动发言只有规则已经确认时另行验证。
- 将实现与真实验证事实追加到 Comments；模拟测试不代表真实部署已通过。验证纯文本 @、5 分钟排队过期、全天无频率限制、撤回排除与取消待发送回复、跨群与开发资料隔离。
