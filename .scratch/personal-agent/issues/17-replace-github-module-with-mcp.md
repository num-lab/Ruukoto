# 弃用现有 GitHub 模块，用 GitHub MCP 替换并视为普通工具

## 目标

移除现有 GitHub 专用业务模块，通过通用 MCP 接入 GitHub MCP。GitHub 工具与其他 MCP 工具使用同一套配置、发现、调用、审批、结果保存和展示流程。

## 已确认的方向

用户明确要求用 GitHub MCP 替换现有模块，并将其视为普通工具。本工单取代 [16：MCP 支持](16-mcp-github.md) 计划中“长期保留 REST 采集与发布、增加 GitHub 专用授权适配层”的建议，也取代 [06：GitHub 项目维护](06-github.md) 中对应的专用实现方向。

“普通工具”意味着不再为 GitHub 保留独立的仓库绑定、采集、草稿、发布意图或发布状态机。服务启用、凭据使用、工具授权、访问模式与必要审批统一由通用 MCP 和任务机制处理；不能将既有 GitHub 模块改名后作为 MCP 包装层继续保留。

## 实施范围

- 基于 Issue 16 的通用 MCP 能力配置 GitHub MCP，工具通过远端发现并按统一规则启用。GitHub 专属内容限于服务配置示例和使用文档，不在运行时按服务名添加业务分支。
- 移除 `src/agent/github/` 及其在 Runtime、Driver、控制协议、CLI、TUI 中的专用接线，清理只供旧模块使用的类型、事件、配置和测试。仍被其他功能使用的凭据、审批、产物与任务能力继续由公共模块提供。
- PR、issue、仓库内容及 CI 等操作通过可用 MCP 工具完成；分析与报告由 Agent 组合普通工具执行，不预设必须复刻旧模块的全部专用工作流。实施时核实旧功能与 MCP 能力差异，并记录无法覆盖的部分。
- GitHub 写工具按通用 MCP 工具规则处理，不再要求旧模块独有的草稿或发布意图入口。若 Issue 16 首版只支持读取，补齐通用写工具审批及结果不明的处理后再启用写工具，不能为 GitHub 单独增加一条写入路径。
- 通用调用须绑定任务、服务、工具、具体参数和权限版本。取消、权限撤销及配置变化后旧授权不能继续执行；已发送但结果不明的有副作用调用不自动重试。这些规则适用于所有 MCP 服务。
- 制定旧配置和持久数据的退役方案：停用旧入口，提示使用 MCP 配置；旧凭据不能因迁移自动扩大权限或发送到不同主机。保留历史消息和产物的可读性，旧待审批/待发布操作不得在升级后自动转为 MCP 调用或重新发送。
- 更新使用文档、相关领域说明和架构决策，明确专用 GitHub 工作流已退役，验收标准调整为通用 MCP 工具行为。

## 待明确

- 首次开放的 GitHub 工具及所需凭据权限，哪些写工具需要通用审批支持。
- 旧 `/github` 与 CLI 命令采用一次性迁移提示还是直接移除；不保留长期双实现。
- 旧仓库绑定、草稿和发布记录的只读保留或导出方式，以及数据库表的后续清理时机；本工单不默认删除历史数据。
- GitHub MCP 实际无法覆盖的旧功能是否仍有需求；有需求时另行评估，不默认重建专用模块。

### 1. 对齐关联工单与能力边界

- 调整 Issue 16 的计划，删除复用 `GitHubStore`、增加 GitHub 参数适配层、`github_mcp_read` 专用操作类别和长期保留 REST 发布的要求。保留其通用服务配置、工具发现、身份绑定、凭据主机校验、上下文预算与任务生命周期设计。
- Issue 16 负责通用 MCP 连接与首次工具接入，本工单负责通用写工具能力缺口、旧模块替换及数据退役。若两者一起实施，按本计划依赖顺序完成，不先写出随后又删除的 GitHub 适配层。
- 同步 Issue 15：auto-review 接入公共审批桥，移除专门修改 `github/publish.ts` 的最终交付要求。尚未实现 auto-review 时先按现有模式完成，不为本工单增加等待依赖。
- 列出旧模块承担的读取、分析草稿、评论发布能力与实际 MCP 工具对应关系，明确不再由运行时强制固定 PR/CI 修订、维护专用草稿或建立发布意图。需要这些工作步骤时由 Agent 使用工具完成；不能宣称普通 MCP 调用自动提供旧工作流的全部保证。无法覆盖的能力记录为差异，不用 REST 回退隐藏差异。
- 新增 ADR 记录专用模块退役及行为变化；通用控制面身份、访问模式和单次授权仍遵守 ADR 0003/0004。

### 2. 补齐普通 MCP 工具的授权与写入流程

- 在 Issue 16 的 MCP 调用入口统一校验项目服务启用状态、工具允许列表、凭据用途及版本。授权来自拥有者配置，不来自远端工具描述；`readOnlyHint` 等元数据只能作为参考。未确定是否有副作用的工具按需要审批处理，未启用的工具直接拒绝。
- `confirm` 在已授权范围内执行，需逐次批准的调用复用 `Driver.awaitApproval()`；`full_access` 按现有模式跳过逐次审批，仍受服务启用和凭据范围约束。若 auto-review 已落地，通过同一审批桥处理。所有判断与服务名称无关。
- 在 `src/core/types.ts` 增加通用 MCP 审批范围，绑定服务 ID、远端工具名、工具定义版本、配置版本及规范化后不可变参数。TUI 展示服务、工具、完整可查看参数与请求原因；不要求用户先创建 GitHub 草稿。已有任务请求中的操作意图由通用授权规则判断，不再设置 GitHub 专用发布意图字段。
- 批准后重新校验任务状态、权限版本、服务和凭据授权，再用 `Store.consumeApproval()` 单次消费并登记执行开始。发送使用批准时保存的参数；参数、服务或工具定义变化必须重新授权。必要的版本与执行交接检查放在公共入口，不能散落到服务适配器。
- 所有 MCP 调用复用工具意图、结果、产物和历史配对机制。审批未消费时取消属于已知未执行；请求发出后断线、超时、取消或落盘失败可能已经产生效果，按现有 `effect_unknown` 语义记录，不自动重发。SDK 重连不能隐式重试写调用，重复控制请求也不能触发再次发送。

### 3. 配置 GitHub MCP 并验证通用路径

- 使用通用 MCP 配置入口建立 GitHub 服务，凭据按目标主机和服务用途独立配置。远端工具通过正常发现机制启用，GitHub 专属信息只出现在配置示例及工具选择文档中。
- 先验证只读调用，再用模拟 MCP 服务验证一项写调用。真实 GitHub 凭据按实际需要限制仓库与权限；从只读扩展到写入必须显式变更工具及凭据配置，不能自动解除服务端只读设置。
- 旧仓库绑定不自动转成通用 MCP 授权。新的访问范围以通用服务配置、工具策略和远端凭据权限为准；原来限定单仓库的令牌不能被静默换成宽权限令牌。若通用层没有参数级仓库限制，文档如实说明由令牌限制可访问仓库，不保留隐藏的 GitHub 仓库校验分支。
- 使用另一个不同名称的模拟 MCP 服务执行相同发现、读取和审批写入测试，证明无需识别 GitHub 名称或调用旧模块即可完成整条流程。

### 4. 停机迁移与历史资料退役

- 在旧后台退出、相关执行单元确认停止后升级，先备份数据库与产物目录。迁移不得在旧发布进程仍可能发送请求时进行；新版本不能与旧后台同时运行，也不能把新库交给旧程序继续发布。
- 当前 `src/core/db.ts` 的公共建表脚本包含 `github_repo_bindings`、`github_drafts` 和 `github_publish_ops`。新数据库不再创建这些表；升级数据库先保留旧表作为历史归档，停止业务写入与启动恢复调用，不在本轮执行 DROP TABLE。旧版本升级路径显式检测表是否存在，不能因移除建表 SQL 导致迁移失败。
- 提供一次性、可重复执行的归档步骤，将旧草稿各版本正文、证据引用和发布记录导出为原项目/任务可查看的产物，并记录来源 ID、版本及导出清单；旧绑定仅导出无秘密配置。复用现有产物存储和权限归属，保持原历史消息、事件、工具结果与产物 ID 可读取。导出中断可以恢复，未完成不得标记成功或删除原数据。
- 旧 `github_publish` 审批不再具备执行资格；待审批以及已批准未消费的请求均在迁移中失效，并记录退役原因。`Store.stalePendingConfirmations()` 只覆盖 pending，迁移须另外处理 approved 未消费的记录。已消费或可能发送的操作保留真实状态及未知效果，不能一律标记“已取消、未执行”。
- `github_publish_ops` 独立于普通 `tool_ops`，现有任务恢复不会自动处理它的 pending 记录。退役迁移须核对关联审批及执行证据：能证明未执行的标为取消，已消费或无法确认是否发送的标为结果不明，保存原状态和核对信息。完全访问的旧发布可能没有审批，不能用“无审批记录”推断未发送。迁移及重启均不将旧操作转换为 MCP 调用。
- 旧凭据保留原 host 和 scope，不删除限制字段、不自动复制秘密到新主机。`CredentialStore.getForUse()` 对遗留限制继续拒绝不匹配用途；轮换同名凭据不得清空 scope。新 MCP 配置采用新的明确授权。
- 保留最小历史读取兼容：旧事件可显示为归档记录，旧审批可查看但不能响应执行；不再提示 `/github show` 或 `/github publish`。历史兼容仅存在于迁移和只读展示，不保留旧 GitHub 业务对象供新任务调用。

### 5. 删除专用实现并切换界面

- 删除 `src/agent/github/` 下 client、collect、store、tools、publish 的活动实现。在 `src/runtime/runtime.ts` 移除 `GitHubStore` 实例、GitHub API 方法、发布任务创建和 `githubClientFor` 测试注入；在 `src/agent/driver.ts` 移除 GitHub 工具装配、固定工具名分派及专用依赖。
- 删除 `src/control/server.ts` 的 `github_*` 业务接口，CLI 的 GitHub 子命令实现、TUI `/github` 操作及专用审批展示。旧命令仅在迁移期返回“已退役，请配置 MCP”的静态提示，不发网络请求、不映射为自动发布；从补全和新帮助中移除旧入口。按现有协议约定升级版本，旧客户端不能继续调用已移除接口。
- 清理新业务类型和事件中的 GitHub 分支；历史数据解析保留明确的只读兼容或通用回退，不能只删除类型后假设持久化 JSON 已不存在。
- 保留公共 `CredentialStore`、`ArtifactStore`、`AccessScope`、任务状态机、审批消费和受限执行能力。删除只被旧模块使用的辅助函数、配置和依赖前搜索全部调用方，避免误删公共传输或安全校验。
- 更新 `docs/runtime.md`、CLI/TUI 帮助与相关领域说明：用户直接在普通任务中调用 GitHub MCP，结果通过普通工具结果、产物和审批界面查看。说明旧数据归档位置、旧命令退役和权限范围变化。

## 验收标准

- GitHub MCP 与另一模拟 MCP 服务经过同一配置、发现、调用、审批和结果展示路径，运行时不依赖 GitHub 专属业务模块。
- 已移除旧 GitHub 工具注册、专用控制接口和活动业务路径，不存在 REST 与 MCP 两套 GitHub 实现并行承担同一功能。
- 完成已授权仓库的真实只读调用；模拟服务验证写工具批准后执行、拒绝不执行、取消与权限变化使旧授权失效、结果不明不自动重发。真实写操作仅在拥有者明确要求时验证。
- 升级后旧待发布操作不会自动发送，历史消息与产物可读取；旧配置和命令有明确迁移说明，凭据未被隐式扩大用途。
- 运行类型检查及受影响的 MCP、任务、权限、迁移和界面测试；旧 GitHub 专用测试中仍适用的通用保障迁移到公共测试，其余随旧实现删除。
