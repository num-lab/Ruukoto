# 支持普通 MCP 写工具与统一审批

## 已确认范围

本工单由 Q9、Q18 拆出，作为只读 MCP 接入后的后续能力，不阻塞 Issue 17 删除旧 GitHub 模块。GitHub 与其他 MCP 服务走同一执行路径，不设置专用发布意图、仓库适配层或草稿状态机。

- 有副作用或无法确定副作用的工具在 confirm 模式逐次审批；full_access 可跳过逐次审批，仍须满足服务启用、工具允许列表及凭据范围。
- auto-review 已实现时走同一审批桥，遵守 Issue 15 已确认策略；本工单不自行扩大其自动批准范围。
- 远端只读注解不是授权。批准绑定任务、服务、工具、具体不可变参数、权限及配置版本；修改参数或撤销权限后旧批准失效。
- 复用公共审批记录和单次消费；发送前登记执行开始，结果不明使用 effect_unknown，不因超时、重连或重启自动重发。
- 首批不指定真实写工具；先实现通用审批、单次消费、取消和 `effect_unknown` 框架，并使用模拟服务验证。本轮不启用真实写入。
- 未来首次启用的写工具必须使用按服务、项目和操作类别独立绑定的凭据；禁止复用 Tavily、旧 GitHub 或无 scope 的通用凭据。

## 后续实施与验收

在通用 MCP 入口接入 Driver.awaitApproval、Store.consumeApproval 和工具结果记录；补齐通用审批详情。使用两个不同服务的模拟工具验证人工批准、拒绝、模式切换、取消、配置撤销、重复响应、断线及崩溃；断言批准最多发送一次，拒绝零次，效果不明不重发。运行类型检查和受影响测试。真实写操作须由拥有者明确指定目标及范围后验证。
