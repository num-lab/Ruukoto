## 实施计划

本工单当前只做范围确认和预研，不立即改动模型配置或凭据格式。Issue 10 已覆盖已有配置的模型切换；只有完成下面的决策门，才进入实现阶段。

### 1. 盘点现有配置边界

- 核对 `src/agent/model-selection.ts`、`src/runtime/runtime.ts`、`src/control/server.ts`、`src/cli.ts` 及 TUI 当前对 `models.json`、`auth.json`、`ModelRuntime` 和 `list_models`/`set_session_model` 的职责划分。
- 记录可复用的 SDK 能力：提供方注册、模型目录读取、`setRuntimeApiKey`、`removeRuntimeApiKey`、`listCredentials`、`refresh` 和 OAuth 登录接口。确认哪些能力能在后台已初始化的 `ModelRuntime` 上安全调用，哪些会重建模型目录或影响运行中的任务。
- 明确配置文件权限、锁、错误处理和后台重启行为；现有模型选择继续使用任务创建时的固定快照，不因配置刷新改写已排队或运行任务。

### 2. 形成一轮产品决策

由拥有者确认以下范围后再实现：

- 管理入口：只提供可信 CLI、只提供 TUI，或两者都提供；控制 socket 仍需拥有者认证。
- 配置对象：仅 API key 和已登记 provider，还是同时支持 provider URL、模型列表、别名、默认模型和思考档位；首版建议只管理 API key 与显式模型目录。
- 认证方式：先支持环境变量/受保护文件写入，还是同时提供 OAuth；首版建议手动 API key 和现有 SDK 已验证的认证类型，暂不自建 OAuth 回调。
- 刷新语义：修改后立即刷新仅影响后续任务，还是要求重启后台；建议通过后台显式 reload，已接收任务继续使用原快照。
- 配置存储：继续使用 SDK 的 `models.json`/`auth.json`，还是迁移到 SQLite；建议先复用 SDK 文件存储，只有需要版本/CAS 或多客户端事务时才增加元数据表。

### 3. 设计安全和并发约束

- 所有写配置操作只接受可信控制面请求；秘密不出现在命令行参数、模型上下文、事件、历史、TUI 日志或错误消息中。输入使用环境变量、受保护交互或已验证的秘密引用。
- 写入保持 0700 目录和 0600 文件权限，更新采用临时文件加原子替换或 SDK 提供的锁；并发 CLI/TUI 修改返回版本冲突，不静默覆盖。
- provider、模型和凭据在启用前做结构校验与认证检查；缺失、过期或不可用状态明确显示，不能把 provider 目录中不存在的模型当作可用，也不能因配置失败切换到内置未配置 provider。
- 配置版本变化不改变已接收任务的 `ModelSelection`、预算快照或审查模型；新任务在提交时读取并固定最新可用配置。删除或禁用 provider 前检查现有 session 默认值，避免后台启动后找不到默认模型。

### 4. 按决策实现最小入口与验证

- 决策确认后，优先复用 `ModelRuntime` 的注册/认证/刷新 API，新增最少的 Runtime 控制方法、协议分支和 CLI/TUI 表单；不复制一套 provider SDK 或凭据数据库。
- 增加配置读取、写入、版本冲突、权限拒绝、认证失败、刷新失败、后台重启和旧任务快照测试。测试断言秘密不出现在响应或持久事件中，文件损坏时保留旧配置并返回明确错误。
- 验证多客户端并发更新、运行中切换、禁用当前默认 provider、模型目录变化、凭据轮换和重连后的真实状态；运行 `npm run typecheck` 与受影响测试，再运行 `npm test`。
- 若决策仍为“只切换已有配置”，关闭本工单，避免为尚未确认的配置管理继续建设。
