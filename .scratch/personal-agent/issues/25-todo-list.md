# 增加工作清单（`todo_write`）

## 目标

普通开发会话与 coding 在多步任务中用 `todo_write` 维护工作清单（步骤与状态），拥有者在 TUI 常驻面板查看进度。清单跟随会话，不另建存储（术语见 `CONTEXT.md`「工作清单」）。

## 背景

2026-09-25 核对：

- pi 0.85.1 不内置 to-do（README：“No built-in to-dos. They confuse models.”，`node_modules/@earendil-works/pi-coding-agent/README.md:507`）。示例扩展 `examples/extensions/todo.ts` 用带 ID 的 `list/add/toggle/clear` 增量操作，状态存在工具结果 `details` 中、靠回放重建。本项目关闭了 pi 扩展（`src/agent/session-factory.ts:71`），宿主工具经 `customTools` 注册（`:104`），示例不能直接加载，也不沿用它的增量模型。
- 工具装配：角色白名单按类别给出（`src/runtime/orchestrator.ts:82-90`），driver 按类别装配各注册来源（`src/agent/driver.ts:388-480`），编码工具在 `roleAllows("coding")` 下装配（`:469`）。普通开发会话不受角色限制；coding 角色含 `coding` 类别，main 与 chat 没有；QQ 群为空工具集合。GitHub 评审的 coding 任务由 `allowTool` 收窄为 `read`、`read_artifact` 与只读 MCP（`src/github/events.ts:136-140`），新工具在那里自动不可用。
- `RETRY_SAFE_TOOLS`（`src/runtime/orchestrator.ts:107`）决定失败的 analyze 委派子任务能否自动重试一次：工具记录必须全是可证明只读的操作（`:613-617`）。
- 上下文选择（`src/agent/context-selector.ts:8-20`）：必留当前任务原文与最新一批工具调用（`:425-433`）；当前任务更早的批次由近及远纳入，装不下即停（`:592-600`）；以往任务按整轮保留或移出；Jev（默认关闭）可剔除中间批次与旧轮次（`:543`）。长任务预算吃紧时，早先的 `todo_write` 会被挤出模型视图。前缀消息位于视图最前（`:637`），内容每变一次，其后整段历史的提示缓存都会失效，因此不采用每次调用注入清单。
- TUI：事件流对工具统一渲染为一行 `⚙︎ 名称 目标`，只有 edit 另显示增删行数（`src/tui/event-flow-view.ts:153-169`）；目标取参数中第一个字符串值（`src/tui/event-flow.ts:24-29`），`todo_write` 的参数没有这样的值。布局为标题 / 事件流 / 状态栏 / 输入框 / 页脚（`src/tui/app.ts:778-784`）。工具参数 8 KiB 以内原样下发，超出只给预览、数组截到 32 项（`src/core/views.ts:15, 60-62, 75-87`）。
- 拥有者的待办、提醒等业务数据已约定放在 main 的应用数据空间（`.scratch/daily-agent/spec.md:24`），不属于本工单。

## 实施范围

### 1. `todo_write` 宿主工具

- 参数 `todos`：数组，每项 `{ content, status }`，`status` 为 `pending | in_progress | completed`；不设 ID、优先级或其他字段。每次调用提交整张清单并整体替换；空数组表示清空。
- 校验：最多 20 项；`content` 去除首尾空白后非空且不超过 120 字符；`status` 只能取上述三值。不满足时返回明确错误，不截断，当前清单不变。上限保证参数总在 `PARAMS_INLINE_CAP`（8 KiB）以内，TUI 总能拿到完整清单（用 `ponytail:` 注释标明两者的关系）。
- 用法写在工具描述中：3 步以上的工作才使用；同一时间只标一项 `in_progress`；完成一项立即更新。不改系统提示，不做定期提醒；「只有一项进行中」不校验。
- 结果只返回一句摘要（如「已更新：完成 3/7」），不回显清单。
- 无副作用：任何访问模式下都不产生审批；加入 `RETRY_SAFE_TOOLS`。
- 装配：与编码工具同一条件（`roleAllows("coding")`）装配，普通开发会话与 coding 角色可用，含 main 委派的 coding 子任务。不新增 `ToolCategory`，不改已落库的角色配置。main、chat、QQ 群不装配；GitHub 评审任务由现有 `allowTool` 排除。

### 2. 清单状态

- 清单跟随会话：会话中最近一次成功的 `todo_write` 调用参数即当前清单，跨任务延续；校验失败的调用不改变清单；新会话没有清单。
- 不新建表、不另存文件：会话历史（pi JSONL）与工具记录是唯一来源。

### 3. 模型上下文保底

- 选择器把当前任务中最近一次成功 `todo_write` 所在的工具批次列为必留（与最新一批同级），不作为 Jev 候选；其 token 计入 `/context` 的「当前任务」。
- 跨任务沿用整轮保留或移出的现有规则，不单独保底。用 `ponytail:` 注释标明：上一任务整轮被移出时，模型看不到旧清单，需要时自行重写。

### 4. TUI 展示

- 事件流与状态栏之间新增清单面板：`▶` 进行中、`☐` 待做、`☑` 已完成（暗色）。最多 8 行，超出时先省略已完成项，仍超出则截取并显示「…另 N 项」。当前会话没有清单、清单为空或全部完成时隐藏。
- 面板内容取当前会话已加载工具记录中最近一次成功 `todo_write` 的参数；重连与界面重载后按同一来源恢复。不新增控制面事件或接口。
- 事件流中每次更新只占一行，如 `⚙︎ todo_write 3/7`（完成数/总数），不展开清单。

### 5. 文档

- `docs/runtime.md` 记录 `todo_write`：参数与上限、适用会话、清单跟随会话、上下文保底规则。

## 已确认范围

2026-09-25 访谈确认（Q1、Q3–Q8、Q12 均按推荐）：

- todo 指 Agent 自己的工作清单，不是拥有者的个人待办（后者属于应用数据空间）。也不采用 pi 建议的 TODO.md：main 没有文件工具，TUI 也看不到实时进度。
- 与计划模式（[26](26-plan-mode.md)）分为两张独立工单。执行时是否把计划转成清单由模型决定，不写耦合代码。
- 整表替换而不是增量操作：幂等、可安全重试，当前状态直接取最后一次成功调用。
- 只给普通开发会话与 coding：main 经 Telegram/QQ 只发最终回答，拥有者看不到清单，而且每次调用都要多带一份工具定义。main 等真有多步编排需要时再加。
- 清单跟随会话：每条消息都是一个新任务，追问、补充要求与「继续」都能延续清单。
- 上下文只在当前任务内保底；不做每次调用注入，避免清单一改就让整段历史的提示缓存失效。
- TUI 用常驻面板，事件流每次更新只占一行；不做 `/todos`。
- 不写 ADR，取舍记在本工单。

## 验收标准

离线集成测试（mock 模型）覆盖：

- 普通开发会话与 coding 角色（含委派子任务）的工具集含 `todo_write`；main、chat、QQ 群没有；GitHub 评审任务的工具集不变。
- 整表替换：多次调用后当前清单等于最后一次成功调用；空数组清空；超过 20 项、`content` 为空或超过 120 字符、`status` 非法时返回错误且当前清单不变。
- 请求确认、完全访问与自动审查模式下调用均不产生审批；失败的 analyze 委派子任务若工具记录只含可重试操作（含 `todo_write`），仍按现有规则自动重试一次。
- 跨任务：同一会话的下一任务开始时，上一任务的清单仍是当前清单；新会话没有清单。
- 上下文保底：构造当前任务多批工具调用且预算不足的场景，最近一次成功 `todo_write` 所在批次仍在模型视图中，更早的普通批次按原规则移出；开启 Jev 时该批次不在候选中；`/context`「当前任务」计入该批次。
- TUI：面板显示三种状态；超过 8 行时先省略已完成项并显示「…另 N 项」；无清单、空清单或全部完成时隐藏；事件流一行显示完成数/总数；重连后面板恢复。
