# 通用个人 Agent：项目规划

当前阶段：四轮需求讨论已完成，形成首期可执行规划与后续路线。本文区分用户确认的需求、工程默认方案及实施中需要验证的选型；当前未开始应用实现。

## 用户提出的方向

- 基于 pi agent core 开发通用个人 Agent。
- 参考 OpenClaw 与 Hermes。
- 借鉴 DeepSeek Harness 的“everything is a plugin”思想，通过插件补充 pi agent core 原本没有的能力。
- 通过讨论，将初步想法转化为可执行的项目规划。

“个人 Agent”与“插件”的含义见根目录 `CONTEXT.md`。首期范围为后台编码与 TUI、技术权限边界、可定制上下文、历史检索和长期记忆；后续依次扩展 GitHub 项目维护与 QQ 群聊，Jev 单独实验。

## 已确认需求与约束

2026-09-19，用户回答第 1 轮：

- 面向自己的日常使用；选择自建的原因是现有产品不方便深度定制。
- 开发协助最重要，目标是替代 Codex、Claude Code 这样的 agentic coding 工具。第 2 轮进一步明确了起步流程与主要定制点，见下文。
- 项目维护包括分析 GitHub CI 结果与 review PR；默认由拥有者明确指令触发，自动触发与自动修复后续再讨论。
- 需要接入 QQ 群聊，用于活跃气氛，并作为后续群聊工具的接入口；具体响应策略及开放哪些群聊工具尚未定义。
- 插件用于自己添加功能，不需要插件平台。
- 没有开发时长约束；运行于 Linux 服务器；没有特定模型选择；数据保存至本地。

第 2 轮用户进一步确认：

- 主要定制点是上下文组装策略、压缩机制与记忆。初始方案不做有损压缩，全部历史消息持久化并可供 Agent 查阅。
- 后续阶段实验性引入 Jev 清理上下文和记忆；第 3 轮确定了实验边界，见下文。
- 编码起步流程为：接受仓库和需求，理解代码、修改文件、运行检查、根据失败修复，交付可审查的改动。不设置硬性验收门槛。
- 初始交互入口仅做 TUI，体验参考 pi agent；关闭终端后任务仍应继续执行。
- 接受先编码、再 CI/PR 维护、后 QQ 接入的交付顺序。
- 请求确认模式下，工作区内已授权修改与验证自主执行；对外发布、合并、部署需要拥有者确认。第 4 轮另加入拥有者显式启用的完全访问模式。群成员默认只能使用明确开放的群聊能力。
- 会话、配置、记忆及产物保存在 Linux 服务器本地；允许向用户选择的云端模型发送任务所需内容。

上下文与历史的决策见 [ADR 0001](../../docs/adr/0001-preserve-session-history.md)。没有硬性验收门槛不取消必要的功能验证及数据完整性检查；没有开发时长约束不要求首版同时交付全部场景。

第 3 轮用户明确“全部接受建议”，据此确认：

- 初始上下文保留系统与项目指令、当前任务要求和预算内最近的完整交互；更早消息保留原文及可查询索引，预留回答与工具结果空间。
- 默认查询同项目历史，跨项目由拥有者显式开放；QQ 群历史与开发资料分别控制访问。
- Agent 可维护少量长期记忆，包括个人偏好、项目约定、确认后的决策与经验；每条关联来源，可修改或撤销，临时进度保留在会话中。
- Jev 暂按已介绍的 TypeSafe Jev 方案进入后续实验。先用于本轮上下文选择；长期记忆清理独立实验并保留撤销记录；历史原文删除由独立数据保留规则决定。
- 不同会话可以并行，同一会话一次执行一个任务，新消息默认排队，并提供明确中断操作。
- 后台进程持有任务，TUI 可断开重连；后台或服务器异常重启后恢复记录，将未完成任务标为中断，由拥有者决定继续。

后台运行的决策见 [ADR 0002](../../docs/adr/0002-detach-terminal-from-task-runtime.md)。多会话执行不等于首阶段已经要求 Agent 自动创建和协调子代理。

第 4 轮用户确认：

- 权限使用技术约束，首期实现请求确认和完全访问，后续再添加自动审批。
- 当前只操作 Linux 环境；代码托管与 CI 使用 GitHub。

权限模式决策见 [ADR 0003](../../docs/adr/0003-enforce-explicit-access-modes.md)。具体仓库、服务器发行版及运行权限在部署时配置；宿主 Docker、数据库或其他服务的访问不作隐含授权。

## 工程默认方案

以下方案用于把已确认需求变成实现任务，不属于用户逐项指定的技术栈；基础验证发现不合适时，应记录依据后调整：

- 按具体定制需求选择 pi 的复用层级，不预先决定自行重建已有的编码宿主能力。
- 优先复用 coding-agent SDK 的会话、工具与扩展入口；先验证相关 API 足以满足已确认行为，再锁定实际发布版本。
- 同一工作目录限制为单个会话执行可写任务；不同目录可并行，已有独立 Git worktree 视为不同工作目录。自动创建和整合 worktree 暂不作为初始必需能力；worktree 也不作为权限隔离机制。
- 请求确认模式下项目命令在受限执行环境运行，对网络和凭据访问进行控制，对外写操作由明确审批路径执行。不能仅依赖系统提示要求自由 shell 遵守审批，也不能将只隐藏部分凭据等同于阻止全部外部写操作。
- 项目维护先采用明确指令触发，监听 CI 或 PR 事件在实际需要时补充。

## 权限模式与确认流程

请求确认是默认模式。范围内的代码读写、测试和检查自主执行；越出工作区、访问未授权网络或凭据、对外写操作等需要确认。范围内操作直接执行不等于后续的自动审批能力；首期不引入模型判定审批或学习授权规则。

审批请求绑定任务、具体操作、参数和所需权限。批准只放行该请求，不解除其他会话的限制，不给予永久通用权限；参数或权限变化需要重新确认。拒绝则不执行该操作。TUI 不在线时请求保持等待，重连后继续处理；其他会话可以继续执行。

完全访问由拥有者在可信入口显式选择，按任务生效，TUI 持续显示当前模式。它跳过应用内逐次确认，使用运行账户实际具备的权限。模型、普通工具、记忆内容或 QQ 消息不能开启它；不得通过后台自动模式升级完成失败的任务。模式改变只作用于后续操作，不假设可以撤销已经执行的外部效果。

技术实现必须覆盖自由 Shell，不能只拦截 `git push`、`gh` 等命令字符串。需要验证子进程无法未经批准访问其他资料、发布凭据、后台控制接口或外部网络。具体使用容器、系统沙箱还是其他 Linux 机制，由阶段 0 的可用性验证决定；无法满足约束时明确失败。

请求确认模式的项目资料隔离与完全访问模式的保证不同：完全访问任务可能读取该运行账户有权限访问的文件。未来 QQ 执行环境不能拿到该账户的完全访问能力。

两种模式的项目命令均不得冒充拥有者、修改宿主授权状态或给其他任务提升权限。后台授权控制面与任务执行账户的权限必须分开；具体系统身份或等效隔离在阶段 0 验证。不能在项目命令可以任意改写控制面配置的部署中声称满足这一保证。

## 分阶段规划

阶段按可使用的能力组织，不设日期承诺、任务成功率门槛或强制验收关卡。必要的权限与数据完整性验证属于实现工作，不能因为没有产品验收门槛而省略。

### 阶段 0：确定复用基础

交付：依赖版本与 API 边界记录，以及一个最小运行示例。验证所选发布包能够关闭自动压缩、独立保留历史、按轮选择上下文、注册历史查询工具，并从外部驱动任务和订阅事件。先复用上游；只有已确认需求无法通过公开接口实现时，才降低复用层级。

验证目的在于消除依赖选型的不确定性，不增加产品验收门槛。TUI 库、持久化后端和本机通信协议在这个阶段按实际 API 决定。同时验证 Linux 执行隔离是否能覆盖文件、子进程、网络和凭据，给出目标服务器的运行前提。

### 阶段 1：后台编码与 TUI

交付：在 Linux 后台运行的个人 Agent，支持项目、会话、任务、流式交互、基础编码工具、多会话执行、排队、中断、确认操作、断开重连和中断任务的人工继续。TUI 提供会话列表、输入、执行进度与工具结果、确认请求及中断操作。代码工作区和命令权限边界与工具接入同时实现。

直接使用“读取仓库—修改代码—运行检查—继续修复—交付改动”的流程验证。重点检查断开 TUI 不影响任务、重连不重复提交消息、后台重启不自动重放工具、不同会话不会意外同时修改同一份文件。

阶段 1 即开始完整保存历史并关闭有损自动压缩。阶段 2 完成长期任务所需的预算控制；在其完成前，上下文容量不足应明确暂停，不能回退到有损压缩或静默丢弃历史。

### 阶段 2：上下文组装、历史检索与长期记忆

交付：可替换的上下文选取规则、消息原文读取与搜索、项目访问范围、带来源且可修改和撤销的长期记忆。初版按已确认的规则选择近期完整交互，不要求向量数据库或模型驱动筛选。

持久化历史与模型输入分别处理。工具调用及结果保持合法配对；超长工具结果保留可读取的正文，仅将预算内片段和引用交给模型。不能把模型输入截断误当作原始记录完整保存。来源范围过滤在数据读取层执行。

验证包括长会话能够找到已移出上下文的原文、记忆修改可追溯、跨项目或群聊读取受约束，以及上下文预算耗尽时有明确行为。记录每轮上下文选取的消息与原因，供策略调试使用；这不要求重建全部外部环境以实现精确重放。

### 阶段 3：项目维护

交付：通过确定的平台读取 CI 日志与 PR 差异，输出带依据的失败分析与 review 结果。首批维护能力复用编码阶段的工作区、历史、工具与确认机制。

平台为 GitHub，CI 先对接 GitHub Actions，并保留读取 PR 上其他检查结果的能力。首批默认由拥有者明确指令触发。请求确认模式下向外发布评论需要拥有者确认，完全访问模式按显式授权执行；自动修复、自动监听或合并不因具有读取能力而隐含启用，进入该阶段时再确认是否需要。

### 阶段 4：QQ 接入

交付：群聊入口与后续群聊工具的接入能力，复用后台任务系统。群成员仅能触发明确开放的能力，群聊与开发历史分别控制。

接入方式已确定为 NapCat，通过 OneBot v11 接口连接；具体部署和传输配置按 [Issue 07](issues/07-qq.md) 验证。需要在该阶段明确允许的群与成员、主动发言与被动响应规则、频率限制、首批群聊工具，不因接入方式已确定而默认启用主动发言。

### 后续实验：Jev

依赖阶段 2 的上下文机制，可以在其完成后另行安排。以固定历史比较基础规则与 Jev 筛选结果，记录保留和排除的内容、延迟、费用及实际漏检问题。启停实验不修改历史原文；模型服务不可用时使用已确认的基础规则。长期记忆清理作为单独实验处理。

## 插件职责与核心边界

工程默认由项目宿主统一处理任务生命周期、入口身份、确认状态与数据访问范围；通过上游已有扩展机制承载编码工具、上下文策略、记忆及外部服务接入。先提供已知需要的扩展点，不建设插件市场或动态安装平台。权限实施点不能被模型选择某个工具或切换上下文策略绕开。

插件仅按拥有者可信代码使用。插件接口不会自动提供恶意代码隔离；QQ 消息也不因进入同一运行进程而获得拥有者权限。哪些策略能够替换、替换时哪些行为约束必须保留，在阶段 0 结合上游接口记录清楚。
