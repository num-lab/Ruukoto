## 方案

1. 新入口配置独立存于 `telegram.json`，仅持实例锁时修改，含版本、程序生成的配置代次、bot/owner 身份、接管水位和凭据环境变量引用/指纹；不保存 token。向导先验证 getMe，再经明确选择丢弃专用 bot 的旧待收消息，读取真实平台边界；拥有者发送随机配对短语后从显示的私聊身份选择绑定，不输入内部 ID。绑定确认后用整批最后 update_id + 1 完成一次真实平台确认，成功才保存配置；该边界及之前的委托不受理，之后消息留给后台。配对短语随机且一次性，选择须在最近批次收到后 60 秒内确认，过期重走配对。凭据变化必须重新配对，不以旧水位接管另一个 bot。
2. 入站只接受配置 bot 下固定拥有者的私聊文本。每条先在同一 durable commit 保存原始正文、固定来源与回复目标、稳定平台键、后台原生 Task 和诊断水位；重复平台消息只接原记录，同键异参拒绝。运行中的数值水位只用于诊断，不按大小排除消息；每批最多 16 条，为 1 MiB 有界回执留出正文及引用预算；完成持久化后，仅下一次轮询请求使用该批最后 update_id + 1，内存确认值仅在收到响应后 60 秒内有效，请求失败、空批或超期即清空。重启不携带旧 offset，按永久消息键去重，覆盖空闲一周后 update_id 随机重置。Task 使用原键向唯一 main admission，保存 Submission 引用，重启补接 admission 窗口。其他身份、群与非文本不产生模型输入。
3. 每个入站原生 Task 只从自己的完成 Submission.answer 生成一次固定回复正文；中断片段与 unanswered 不发送。发送意图和正文、目标同 commit 保存；领取发送先持久化 started/checkpoint，再发送。进程崩溃/超时/断线/畸形应答/5xx 均保留效果未知，不自动重发；只有确定的 429 限流拒绝延后重试，确定其他 4xx 拒绝记失败。完整回答在 durable 保存，平台显示有界单条文本并标截断。
4. 配置代次变化或停用时，旧未提交输入和待发回复取消，不改发新目标；已提交模型输入保留原生历史但旧目标不再发送。发送开始后的旧操作保持未知，配置变更不能重试它。源、Task、Submission、版本与配置记录在恢复前双向核对，缺失拒绝调度。该扩展固定注册，停用后的入口配置仍可安全处理旧代次收尾；配置记录缺失则拒绝恢复。
5. `startPersonalServer` 持锁读取配置并装配轮询，停止时先中止/收齐轮询和管理接口，再关闭 Harness 并收齐发送，最后释放锁；存储故障也停止 transport。凭据和原生 fetch 错误不进入日志或模型。CLI 状态显示有界收发统计与未知状态，不要求输入内部键。
