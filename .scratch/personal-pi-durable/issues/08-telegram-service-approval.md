## 方案

- 绑定拥有者的普通文本在收件事务内固定当时三模式及权限版本；默认自动审查。可信 API 引用该输入时从原收件取得权限与身份，不接受调用者扩大模式；执行消费再次检查原绑定/配置代次与原 Submission。历史本机可信 API 保持现有语义，不能以 Telegram 字符串冒充本机输入。
- `/权限` 提供回复选择；`/审批` 展示一条原入口待审批服务及精确范围，回复「批准本次」「批准并长期授权」「拒绝」；「下一项」轮询其他待审。`/服务状态` 提供原入口工作结果查询；`/授权` 展示原 bot/owner 的一条授权，回复「撤销授权」或「下一项」。所有选择绑定已发送的宿主回执与配置代次，用户不用输入内部键。转发、引用摘录与非绑定身份不能提供决定；无效控制消息只返回安全指引，不进入模型。
- 控制收件、决定/授权/撤销与固定回复意图同 commit，重投只复用原事实。复用 Telegram 原生 Task 的持久发送阶段，发送未知不重发；管理消息不等待主聊天。命令仅按原始完整文本分类，普通对话中的描述不成为控制指令。
- 长期授权仅由 pending 原审批创建，固定 main、bot/owner/代次、machine/unit/restart、policy/unit 修订，保留来源与行版本。每次宿主请求先 inspect，再在消费事务重读匹配授权；撤销先提交恢复人工，消费先提交只影响后续。普通单次批准独立于其他授权。绑定/部署变化使旧授权失效；未知服务效果同事务撤销同机器/目标的全部授权，重启保留未知占用且不重发。
- 恢复前核实权限记录、Telegram 来源与服务/授权引用、文档版本；缺失或损坏拒绝启动，不补猜旧记录。新字段兼容已验收的本机服务工作，既有 Telegram 收件不自动授予权限；旧 Telegram 来源但无权限快照的未消费服务操作失效，已消费事实仍保留未知核实与占用。
