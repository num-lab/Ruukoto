## 方案

- CLI 分页选择原服务操作，查看原目标、效果/停止状态、诊断及已保存核实说明（每页 1200 字符），选择已生效或未生效并输入最多 8192 字符的非空证据。内部 requestId/TaskId 由程序管理；应答丢失后先刷新原状态，不换键重试。
- Telegram 新增 `/服务核实`，仅列当前 bot/owner/代次的原操作；直接回复已送达原宿主菜单选择原操作、效果，再按提示提交证据。保存决定、原操作引用和控制收件同事务；转发、引用摘录、旧入口、未送达菜单及已核实记录拒绝变更。本机认证入口可管理全档案，包括已失效入口。
- 将现有 resolve 提取为事务内共用函数；Telegram 决定保存控制收件回链。核实只记事实，不触发 restart，不恢复长期授权；效果已核实且原启动器/命令单元退出已证明，才沿既有状态机结束与解除占用。
- 停止重核只登记独立 durable background Task；接纳和执行时均要求原操作已消费且处于可核实的效果未知状态，再重新核实原引用及当前入口，调用原服务 API 的 stop-op，不在 HTTP 应答或 Telegram 接纳事务里等 helper。重启重接原 Task，只重核同一 hostOpId；失败不循环重核。审批前检查或仍执行中的 started 记录拒绝本菜单，检查停止仍从原检查菜单管理。
- 新扩展标记阻止旧程序忽略控制记录；恢复核对所有重核 Task、原操作、菜单、决定和收件回链。服务操作本身的稳定引用及停止证明协议不变。
- 影响面：personal-service-operations、独立 service-controls、Harness 装配/恢复、control/CLI、Telegram records、permissions/收件控制；个人服务操作、CLI、Telegram 窄回归；personal-durable/products/agent-tools/usage 文档及决策笔记。另修正既有子检查强杀用例的列表查询竞态，仅捕获原引用，不改运行时；依据见[验证笔记](../../../.agents/notes/implemented/testing/2026-10-17-inspection-stop-test-reference.md)。无新增依赖、命令、共享包或 exports。
- 验收：仅效果/仅停止均不释放，错误停止证明保持占用；原菜单和入口约束、重投去重及核实不可覆盖；接纳失败零外调；慢停止不阻塞应答/聊天；真实子进程强杀恢复只重核原操作；控制回链破坏拒绝恢复；CLI 选择流程与认证；静态、相关个人回归、构建、两端定向与独立实现审查。真实 Telegram/systemd 和拥有者体验单列待验，不以替身计通过。
