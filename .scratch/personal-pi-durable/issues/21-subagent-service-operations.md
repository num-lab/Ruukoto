## 方案

- 提取服务请求的事务内共用登记。子工具仅接收精确 unit，宿主以工具 Task 派生稳定键；同 commit 保存不可改接纳、原 WorkTask、tool/generation、当前 child inputs 及其拥有者来源、原权限和入口。恢复重接原操作，不从当前默认模式、后续说明或历史上下文扩权。
- 新服务 Task 在 root conversation 中由原 WorkTask 持有，历史宿主操作保持 conversation-owned。执行前复核活动工作、原入口、整项暂停、取消、授权版本及部署修订；自己的已消费操作恢复只核实原效果与停止，不走会阻断自身的来源门禁。子工具等待原 Task，提供同子会话的完整证据分页；审批仍从已有原入口处理。
- 本机来源原来只有可信 API 审批，补齐在线服务详情的批准本次/拒绝选择与认证 POST `/service/decide`，复用已有决定校验；Telegram 仍只能原私聊审批。本机不创建长期授权。服务 Task 在线 faulted 且已消费但结果缺失/started 时，成员收尾将其规范化为 interrupted 未知效果并失效授权，现有恢复菜单即可处理。
- WorkTask 正常收尾先收齐子会话，再等所持服务 Task；取消先保存成员与服务取消事实，再收齐子会话并 abortOwned。释放事务拒绝未结束服务、未知效果及服务审批前检查未核实。即使服务 Task faulted，原效果和停止未核实也不释放；沿现有拥有者菜单恢复，不重发 restart。
- 复用原来源暂停与委托成员归属，使同委托的续派、追加、子请求、外部工具和报告不能绕过未知操作；报告及整项取消沿成员 WorkTask 等待，独立宿主操作不误归组。其他聊天与独立工作继续。
- 新扩展同时登记主/子配置；仅空闲旧档案可原子升级，旧程序缺扩展拒绝。启动前双向核实接纳、原工具调用、来源、权限、输入、服务 Task owner 与工作占用；审批前检查沿原服务 Task 绑定。
- 影响面：service-operations 的登记/恢复、独立子服务工具、work 的配置/取消/收尾、inspection 的成员归属、Harness 装配/升级、模型可见工具与提示；服务/工作/权限/委托/报告回归及 personal-durable/products/agent-tools/usage 文档。无依赖、共享包、exports 或命令变化。
- 验收：三模式及跨轮权限不扩大；接纳失败零外调；原键恢复与消费后实际强杀零重复；审批/检查/restart/未知处取消均保留必要占用；双事实才释放；篡改恢复关系拒绝；同组换方式不能绕过、其他聊天继续；请求快照含实际新工具与结果。运行静态、个人相关回归、构建、产品入口与 Linux 定向；真实模型/IM/systemd、拥有者体验及完整迁移单列待验。
