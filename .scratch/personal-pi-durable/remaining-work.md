## 共同实施与交接规则

- 每单先核实当前代码/依赖/前置的真实状态，再细化必要接口；本次独立方案审查检查范围、依赖和验收覆盖，实施中出现新的跨模块契约仍需审查，已有授权不重复请示。
- 继续使用 durable 的 Task/Submission/Conversation。业务文档可记录来源、授权、接纳、效果、外部结束和占用，不镜像第二份执行状态；不能以文件 journal、旧 Task 表或旧 Runtime 装配补接。
- 各能力在同一实现里交付最小必要配置与控制。35 负责全局可达性、交互一致性和缺口，不让其他能力只剩宿主 API 等待 35 才能验证，也不复制它们的业务规则。
- 每单同步实际影响的模块说明、usage 与必要命令；新重要决定在相应 `.agents/notes/` 记录，沿已有决定更新事实而非为每个工单再造同题笔记。模型可见工具/提示/错误按 agent-facing-text 与 prose-standard 核对。
- 检查遵循 pre-push-checks：静态、最窄回归、实际共享调用方；真实 Linux/模型/IM各记证据。没有新失败或内容变化不重复全量；最终组合范围由 39 核定。缺前提记待验，不将替身/源码检查写成真实通过。
- 37、35 和 39 可分批回写原 ready-for-human 工单，必须注明体验的能力、版本和证据；未覆盖的原项保持待验。工单“工程通过”不自动等于产品或正式迁移通过。
- 既有命令意图到外部认领之间的崩溃窗口仍可能保守占用；MCP 本地关闭也不是远端结束。没有可核实证据不解除占用、重发或降低验收要求。
- 生产切换授权不由建单、方案过审或实现验收隐含获得；新旧原档案只归档，代码回退仍用空白档案，不重放旧积压。
