## 目标与边界

逐项验收[规格 R1–R14](../spec.md)，依赖 01–04 的实现、文档和独立审查。拥有者已确认默认 shell、可编辑角色、源工作区保护与当前内容审查等体验目标。本单与[工作流 11](../../agent-workflow/issues/11-experience-acceptance.md)交叉核实等待/侧栏组合，保留两单各自范围。

## 方案

1. 固定实际检出与未提交内容，对照 R1–R14 收集最窄离线回归、真实 Driver/worker 和必要外部证据；由独立实现审查者核对原始要求、实际代码、调用方和文档，阻断退回对应工单。
2. 两产品分别从普通委派和工作流使用默认 general 执行 shell；普通调用只给 request/key，不被旧资料必填 guard 拒绝；无 target 做目录/材料调查。编辑 reviewer、新增角色、触发坏文件/缺工具并修正，验证已有对象保持旧版本、新对象使用新版本。
3. Git target 含 staged/unstaged/untracked binary，reviewer 在副本运行检查、明确缺依赖、不能写原工作区；general 修改后只汇入子增量。完成冻结→独立验证→汇入→父 Agent 继续检查，核实实际字节与账本而非最终文本。
4. 权限、个人业务和 MCP 来源做正负例；普通与工作流同源一致，撤销、换配置、角色文件修改、冷恢复、旧接口、非 Git 限制及效果未知不产生越权或重放。非 Git 普通写任务等待期间父 Agent 继续聊天，目录占用保持有效。GitHub 宿主固定评审沿旧可信入口，用户角色覆盖不改变其只读限制、终态来源资格和恢复，不能借通用默认新增 shell。
5. 按最终实际改动范围运行所需检查；若跨 core/agent/runtime/control 与业务入口，执行一次完整 npm run check。macOS 与 ssh tx Linux 验证 native 隔离和停止；真实模型用 RUN_MODEL_CHECK=1，使用已配置且获准的模型，测试默认保持离线。
6. 拥有者验收默认 shell 是否能完成原任务、角色文件是否好用、工具/权限/缺依赖错误是否明确、审查是否确实针对当前内容。产品问题返工后只复验受影响内容。
