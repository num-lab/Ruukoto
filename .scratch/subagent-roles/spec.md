# 可配置子代理角色规格

本规格依据 2026-10-14 拥有者在 grill-me 会话中对 Q1–Q14 的逐轮确认及最终整体确认。当前交付是方案；实施入口为[执行计划](implementation-plan.md)，理由与取代关系归[决策笔记](../../.agents/notes/proposed/architecture/2026-10-14-configurable-subagent-roles.md)。问题由工作流 [08](../agent-workflow/issues/08-workflow-sidebar.md)、[10](../agent-workflow/issues/10-agent-wait.md)人工验收发现，不重开这两单；原始现象与现行源码见[事实依据](evidence/source.md)。

## 目标与术语

ruukoto 与 ruukoto-code 共用可配置的子代理角色，普通委派与工作流可选择同一角色，默认子代理能够使用 shell。工作流归属继续决定调度、等待、取消、结果交接和冻结验证，不再独占角色或成为普通委派无法取得同源能力的理由。

本规格的「子代理角色」指具名的职责、工具要求、权限策略与 prompt 定义，不是 SubAgent 身份、一次工作、任务访问模式，也不是旧 `AgentRoleId` 的 main/coding/chat。一个角色可创建多个独立 SubAgent；实现时将该术语补入 CONTEXT.md。配置文件不能赋予拥有者身份、下级委派资格或来源之外的权限。

## 已确认要求

| 编号 | 要求 | 验收依据 |
| --- | --- | --- |
| R1 | 两产品的普通委派与工作流共用角色目录及来源能力规则；工作流只额外持有其编排与成果职责。 | 同一角色在两条入口按相同来源得到相同基础能力；工作流绑定不额外授予业务身份，宿主验证仍可进一步收窄。 |
| R2 | 首版从实例 `<agentDir>/agents/*.md` 加载；角色名取文件名，同名覆盖内置，可新增；不自动扫描仓库。 | 覆盖、新增、未知角色、非法文件和目录均有可定位结果；实例之间不串用配置。 |
| R3 | 内置 `general` 与 `reviewer`，省略角色用 `general`；默认通用角色具备来源允许委派的工具，包含 shell。 | 两产品普通首次委派只给 request/key，工作流默认步骤只给任务正文，均通过真实 Driver 实际调用 bash，不靠模型自述认定可用。 |
| R4 | 文件首版只有描述、工具、权限策略和正文 prompt；模型与推理强度继承来源。 | 不新增模型覆盖、角色继承或模板机制；正文补充宿主指令，不能覆盖身份、授权、记录和成果规则。 |
| R5 | 角色权限继承来源或收紧，不能提高；内置 reviewer 使用受限执行保护原工作区，并允许副本或临时目录中的检查产物。 | 受限来源不能通过选角色变成完全访问；完全访问父任务派发内置 reviewer 后，绝对路径写原源码、索引及宿主文件写旁路仍被拒绝；隔离不可用明确失败。 |
| R6 | 显式工具清单中的工具必须全部可用，否则启动前报缺失项与原因；省略清单才继承当时实际可委派集合。 | 未知工具、来源未授权、产品不支持、MCP 发现失败均无静默删减；实际发送和调用门使用同一钉定集合。 |
| R7 | SubAgent 创建时固定角色版本，工作流启动时固定可用角色版本；编辑文件影响后续新建对象。 | 继续、复用、消息触发及冷恢复不换角色正文；恢复不依赖可被覆盖的配置路径；每次任务实际权限仍受其可信来源约束。 |
| R8 | 普通子代理与工作流统一使用适用的项目指令和技能目录，资料按来源授权读取，不自动复制完整父聊天。 | 两种入口实际模型输入可由角色快照、任务、选择记录和 JSONL/产物重建；撤销资料后不能继续使用旧授权。 |
| R9 | `target` 独立于角色：未指定时使用子代理自己的目录及获准资料；代码修改和代码审查明确给目标。 | 无 target 的 shell、调研、资料处理和个人业务不要求 Git；同一角色可用于不同目标，不能靠角色名取得目录权限。 |
| R10 | 指定 Git target 时使用委派时的工作区快照，包含已暂存、未暂存及非忽略的新文件，默认不复制忽略文件和依赖目录。 | 子代理看到当前内容；原源码与 Git index 不因捕获而改变；新文件与二进制覆盖；汇总只应用子代理相对捕获基线的新改动。 |
| R11 | 普通 general 的非 Git target 保留原地串行执行；独立代码副本审查、工作流修改和冻结验证首版要求 Git。 | 非 Git 普通写入与父任务按目录占用串行，agent_wait 可安全让出；需要副本却缺 Git 时在执行前明确拒绝，无 target 业务仍可运行。 |
| R12 | 工作流验证是宿主操作语义，不是专属角色模式；冻结输入、独立执行、工具账本和最终汇入资格仍由宿主持有。 | reviewer 可用于普通审查；工作流验证即使选别的角色也不能绕过受限验证和冻结绑定；模型的 passed 文本不能覆盖失败或未知效果。 |
| R13 | 直接替换旧 analyze/modify/verify 派发模式接口，旧定义与历史保留；旧工作流需保存为使用新接口的新版本。 | 旧接口得到明确升级说明，不自动解释成权限更大的 general，不自动改写历史、复跑旧步骤或迁移旧 JSONL。 |
| R14 | 实际角色、有效工具、权限与来源、工作区快照及注入内容可追溯；故障遵循已有取消、停止核实与效果未知规则。 | 记录缺失或损坏时拒绝猜测恢复；已产生副作用的失败不自动重放；新角色接入不破坏等待、唯一回报及三个共享并发名额。 |

## 角色文件与执行保证

文件契约采用 YAML frontmatter 与 Markdown 正文：`description` 必填，`tools` 可省略，`permissions` 表达权限策略。其 `mode` 默认 `inherit`，允许 `inherit`、`confirm`、`auto-review`、`full_access`；`protect_source` 默认 false，声明是否必须由执行边界保护原工作区及获准来源目录。这个声明落实 Q4，不能由 reviewer 名字或是否列出 edit/write 猜测。角色名使用仓库的 kebab-case 命名；不另加可与文件名冲突的 name。未知字段、重复工具名、非法值与空描述明确报错。下面是内置 reviewer 的最小定义示意，实际内置正文由实现按本规格写定：

```markdown
---
description: 审查给定代码并运行必要检查，报告发现与验证依据。
tools: [read, bash, read_artifact]
permissions:
  mode: confirm
  protect_source: true
---
在宿主提供的审查副本中检查代码并运行必要测试。报告发现、证据与未验证项；保留检查产物，由主 Agent 处理后续修改与交付。
```

保护来自宿主的受限执行、只读来源与受控副本，不能来自 reviewer 名字或 prompt。protect_source 为 true 时拒绝无沙箱执行及非 Git 原地 target；无 target 仍可在独立目录处理只读资料。来源允许完全访问但该角色指定 confirm 时按 confirm 执行；角色若同时要求完全访问和保护来源则明确冲突，不声称两者都满足。拥有者显式取消保护并改为完全访问后，不再宣称该自定义角色具有原工作区隔离保证；工作流冻结验证的宿主保护不随角色覆盖解除。内置角色与自定义角色使用相同加载及解析契约，不对角色名硬编码权限。

角色明确请求的访问模式若比来源更宽，启动前拒绝；不默默提高，也不把请求完全访问却实际受限的角色伪装为配置成功。可收紧关系为 full_access → auto-review 或 confirm，auto-review → confirm；confirm 不转为 auto-review。宿主冻结验证仍施加其固定受限要求，并在最终执行记录中说明收窄来源。

工具和角色 prompt 不提供子代理再委派、工作流再启动或直接与拥有者交互的资格。个人业务与 MCP 的来源身份、产品能力、服务配置和凭据范围由宿主保存及复核；不能复制主 Agent 身份或只开放工具名。已有 GitHub 宿主固定评审继续由可信入口提供固定执行定义与只读限制，不参与用户角色选择；它不是新增的公开角色或本次 GitHub 功能扩展，覆盖 general/reviewer 不能改变该入口。

## 范围与确认来源

本轮不建设角色配置 TUI、项目级发现、专属模型设置、角色继承、模板变量、非 Git 独立代码副本与回写、嵌套委派或兼容旧模式的双路径。无 target 的获准资料处理不等于针对代码工作区的快照审查；需要审查当前代码必须明确 target。非 Git 自定义角色若要求受保护的目标副本，同样拒绝，不能通过换名字降级到原地写入。
