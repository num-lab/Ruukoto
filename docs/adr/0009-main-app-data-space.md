# main 应用数据空间：独立库、受控工具与破坏性确认例外

日期：2026-09-23

## 背景

main 角色（日常助手）需要按需建立待办、提醒、习惯等个人数据结构。这些数据是 main 自己声明的业务数据，不属于后台运行时元数据，也不属于长期记忆（偏好、约定、决策、经验）。核心 `ruukoto.db` 保存任务、审批、事件与凭据绑定，不能向模型开放 schema 变更。

## 决策

1. **独立应用库**：`<dataDir>/agent-data/main.db`（node:sqlite，WAL + synchronous=FULL + 外键），由 Runtime 管理打开、恢复与关闭；目录权限 0700，在 `protectedRoots()` 数据目录范围内。首次建立后把稳定实例 ID 登记到核心库 `meta` 表；启动恢复先核对文件存在与实例身份。已登记但文件丢失、身份不符或损坏时不自动创建空库、不覆盖既有实例绑定，能力停止并留下 `app_data.unavailable` 事件。两库没有共同事务，不使用 `ATTACH` 拼接。
2. **六个受控工具**：`app_data_define_table / migrate / query / insert / update / delete`，仅 main 角色的会话装配（`ToolCategory` 新增 `app_data`；装配、发送前检查与调用门三层共用同一份白名单，执行入口每次重新核实宿主任务/会话/项目与 main 角色绑定）。名称、类型、大小、关系与版本校验在存储边界执行；SQL 标识符只来自已验证目录，数据值全部绑定参数。
3. **版本与审计**：存储格式版本（宿主维护）独立于 main 管理的 `schema_version` 与每次变更递增的 `revision`。所有写入在单事务内提交业务/schema 变更、版本递增与追加审计回执（`hostOpId` 唯一）；审计失败、约束失败或磁盘写入失败必须回滚业务变更。同操作重复执行先查回执：同参数返回原结果，异参冲突。
4. **破坏性操作确认**：删表、删字段、删唯一索引、多行写与批量重写进入统一审批桥（复用 `Driver.awaitApproval` / `Store.consumeApproval` / 控制面 `respond_confirmation` / TUI），新增 `ApprovalScope.kind = app_data_change` 固定应用库身份、任务与操作 ID、表与操作类别、schema/revision、参数摘要、受影响数量与行版本。批准后重新核实身份与版本，批准单次消费，执行参数取自不可变快照。
5. **full_access 例外**：完全访问模式的任务也不免除破坏性应用数据确认。这是相对 ADR 0003 "完全访问无需逐次确认" 的特定例外：应用数据是 main 的个人结构化数据，删表/删字段/批量重写的破坏面独立于任务执行权限，依据 daily-agent 规格第 9 项明确要求逐次确认。`auto-review` 对此范围直接转拥有者（`classifyForReview` 不覆盖，默认即转人工）。
6. **有界查询与只读子进程**：首版不开放任意 SQL/JOIN/聚合，按 `_id` 主键游标分页，AND 条件限标量比较/空值检查/有限集合匹配；行数（默认 50/硬上限 100）、结果（64 KiB）、候选扫描（1,000 行/1 MiB）与总时限（2 秒）均为宿主常量。每次查询启动固定入口的只读子进程（`node --import tsx query-child.ts`），超时 SIGKILL 并等待退出；子进程只读查询，写事务全部留在宿主。该子进程用于真实终止超时计算，不构成完整的操作系统权限沙箱。
7. **双库恢复**：恢复在现有未知效果判断之前按应用库回执核实未落结果的应用数据写操作——有回执补记已提交结果；批准已消费但无回执且应用库可核实记未提交；应用库丢失/损坏/无法核实保留 `effect_unknown`。只读查询不产生写入效果，不适用。重启只补记结果与事件，不自动重放修改。

## 后果

- 核心库 schema 不因业务数据演进；应用库格式版本独立演进，过新或损坏时明确停止。
- 查询延迟包含子进程启动开销（毫秒级），换取可终止的查询截止。
- coding/chat/QQ 会话与普通开发会话默认无法访问应用数据；资料授权、grantedPaths 与完全访问模式不扩大应用数据 API 范围。
