# 调度器与通知 outbox：单进程 SQLite、固定发送授权、未知结果不重发

日期：2026-09-24

## 背景

daily-agent 规格第 7 项要求单进程 SQLite 调度器与 outbox，不引入 Redis 或消息中间件；第 6 项要求未预先授权的外部发送经拥有者确认。提醒需要跨重启不丢失、跨夏令时不漂移，发送结果未知时不能自动产生第二次外部副作用。

## 决策

1. **核心库三表，数据库为准**：`schedules / schedule_runs / notification_ops` 进入核心 `ruukoto.db`（schema v13），是运行时基础设施而非 main 业务表，应用数据工具不可达。内存定时器只唤醒扫描；重启不靠重建定时器猜测漏过的工作。
2. **时间语义**：一次性 / 每日 / 每周，IANA 时区，ISO 日历；按当地日期与原定钟点重构；DST 固定 `compatible`（缺口顺延，重复取较早）。IANA 偏移与 DST 计算交给 `@js-temporal/polyfill`（Node 24 尚无全局 Temporal），不自写算法，不提升 Node 版本要求。
3. **漏过周期只补一次**：无未完成运行时取截点前最近一次并标延迟；已有未完成运行时并入原运行，保留原键与原正文。恢复准备在通用任务恢复改写 running 之前读取真实状态：已终态未关闭的先补关闭，再合并，最后把遗留 `sending` 定为 `effect_unknown`。
4. **发送状态按事实**：`pending`（未领取）与 `sending`（已领取、可能已发出）分离；只有条件更新领取成功者调用发送函数一次。明确成功 `sent`、可证明未发送 `failed`、其余 `effect_unknown`；`sent/failed/effect_unknown/canceled` 均不自动重发，迟到回执只记录。逻辑发送键由宿主决定（定时 = 运行 ID，一次确认 = 任务通知槽，owner 回复 = 入站事件 + 回复槽，issue 04），模型不能换键绕过未知结果。
5. **固定发送授权**：目标只来自可信宿主渠道配置；`notify` 计划与一次发送都经统一审批（`ApprovalScope.kind = notification`，固定正文、目标及配置版本、规则/时区/DST 与持续范围），获批后同一核心事务内重核并单次消费。目标配置版本变化或停用使旧授权失效，不改发新目标。

## 与 ADR 0003 的关系

ADR 0003 规定完全访问模式无需逐次确认。本 ADR 与 ADR 0009 同样设定特定例外：**建立持续发送计划与未预授权的一次外发，在 full_access 下也须拥有者确认**——外发面向平台上的真实接收者，其授权独立于任务执行权限，依据 daily-agent 规格第 6 项。auto-review 对 `notification` 范围直接转拥有者（ADR 0005 的确定性策略不覆盖）。已批准计划的后续触发与可信 owner 回复（issue 04）属于明确的自动发送范围，不复用 MCP 的 full_access 放行分支。

## 后果

- 本地只能保证"一个逻辑键至多一个操作、不重复发起可能已产生副作用的发送"；平台无幂等支持时无法保证远端 exactly-once，`effect_unknown` 需拥有者核实。
- 调度与发送不进入 coding 会话的任务队列、不占用工作目录；发送一次只有一个在途操作，慢发送不阻塞到期登记、控制面与编码任务。
- 首版不引入 cron 表达式、通用工作流、平台插件系统或自动重试框架；既有 `qq_outbox` 暂不迁移到公共账本。
