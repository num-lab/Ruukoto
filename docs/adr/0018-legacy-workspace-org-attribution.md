# 旧开发数据迁入工作区时保留原 projectId 作为资料与配置来源，组织归属只作展示

日期：2026-10-03

状态：已接受。依据已确认方向规格（agent-direction spec）与 [ADR 0017](0017-two-agent-products.md) 的工作区模型，经四个实施步骤落地（schema v21、只读预览、事务化应用、界面打通）。

工作区是带根目录归属的 Project（ADR 0017；issue 05/06 已交付）。旧架构项目可包含不同目录的会话，而 `sessions.project_id` 同时承担会话的资料身份与配置来源：历史、产物及记忆来源校验通过它定位，项目指令、Web Search、MCP、Jev 和记忆候选也使用它；JSONL 经原 `sessionFile` 与 `piSessionId` 定位，授权按来源/目标项目界定方向。旧项目数据迁入工作区（工单 07）如果把旧会话的 `project_id` 改写为工作区 ID，会在整理展示的同时改变这些边界：一个旧项目含多个目录时，原会话本来能读取同项目其他目录的资料，改写后会静默收窄；多个旧项目使用同一目录时，它们各有不同的资料身份，合并展示后会获得新的默认读取范围；`AccessScope.sourceRefAccessible` 按来源会话当前的项目判定，改写还可能使原授权的撤销不再控制原资料。

因此采用加法迁移：`sessions` 增加可空的 `workspace_project_id` 作为工作区组织归属，仅用于组织查询与展示（显示归属 = `workspace_project_id ?? project_id`）；旧 `project_id` 连同会话/任务/产物 ID、pi 会话 ID、历史文件路径、记忆与授权 ID 全部保留为兼容来源。组织映射不得进入 AccessScope、模型工具身份或凭据范围判定，也不复制、不合并旧配置；历史、产物与记忆继续按原标识定位读取。映射旧会话的后续任务继续使用原项目配置，目标工作区使用其他 Project 身份的新会话不因映射获得源资料与凭据；如需开放其他来源，使用已有的可信配置与授权入口，不建立第二份配置状态。与 ADR 0001 及 [ADR 0016](0016-lossy-context-compaction.md) 的完整历史原则一致：迁移不改写 JSONL、不移动产物文件、不重建会话、不恢复审批、不重放未完成任务，迁移前后原标识与字节可逐项核对。

满足严格条件的单目录完整旧项目可以复用原 ID 认领根目录（后续新会话沿用该身份本来拥有的配置与访问范围——因为身份未变，这不是边界扩大）；其他情况只建立组织映射。迁移由拥有者经只读预览明确选择（列出可映射项、歧义与异常：失效/被替换目录、同目录多旧项目、混合项目、嵌套根、worktree、已认领根外会话等，目录失效或被替换时保留原记录不静默认领），再经单事务应用：预览修订取相关元数据的规范化内容哈希（无关任务输出不使预览过期），应用先查幂等回执再核修订，任一失败整体回滚；成功后的回退只恢复显式组织字段并校验当前值，已确认根目录身份与迁移后产生的执行事实保留。角色绑定与群聊会话不纳入迁移（明确排除），与 ADR 0017 中角色退役与群聊外挂化的边界一致。

## 与既有决策的关系

- ADR 0017 的工作区 → 会话模型本单实现为：展示归属按本 ADR 的组织映射，资料与配置归属保留原项目；跨实例的实际导入、备份与切换由工单 21 负责，不在本单绕过产品目录隔离。
- ADR 0001（完整历史）与 ADR 0016（有损处理只作用于模型上下文）是加法迁移的直接依据：任何迁移方案都不得为了对齐展示而改写或收窄历史资料的可达性。
- issue 05 的目录入口认领保持可信入口语义，但同步收紧：多目录旧项目与混合旧项目不可经 open_workspace 认领，必须走本 ADR 的预览/应用流程，避免在迁移流程之外把多目录项目直接认领到其中一个目录。
- issue 06 的项目配置版本（settingsVersion）继续作为迁移预览修订与并发保存的依据；迁移不建立第二份配置状态。
