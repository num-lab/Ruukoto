# 服务器服务管理经 root 拥有的固定 helper，所有访问模式逐次审批

日期：2026-10-03

状态：已接受（agent-direction issue 09 交付）。阶段边界补充（2026-10-03，issue 10 交付）：逐次审批增加一个明确例外——拥有者可经原 IM 平台的待审批把某次 service restart 审批保存为限定长期授权；命中完全相同范围（main、原入口稳定身份与原目标代次、本机/单元/固定 restart、策略与单元修订）的后续任务经宿主逐次重建核实后自动放行，撤销或失效（修订/绑定变化、目标效果未知）后恢复逐次审批。没有有效授权时，包括 full_access 在内仍逐次审批；应用数据破坏性变更、通知外发、MCP 写操作及其他工具的特殊审批规则不变。

## 背景

main 需要按明确授权管理整台服务器（ADR 0017）。已核实的执行边界是：main 没有 bash；受限编码容器不能管理宿主 systemd；systemd 工作进程启动器只接受完全访问且其执行 UID 无服务管理权限。直接给 main 开放 bash 或向执行账户授予 sudo 都不满足 ADR 0003/0004 的账户隔离。

## 决定

服务管理能力收敛到唯一可信入口：root 拥有的固定 helper（`deploy/systemd/ruukoto-service.mjs`，安装 0700，仅后台账户经 sudoers 固定路径调用）。helper 只接受固定协议（inspect / restart / stop-op），目标限定在 root 拥有的策略文件（固定本机身份、执行 UID/GID、精确单元及允许动作），拒绝别名、模板实例、通配符、选项注入与额外参数，并固定拒绝后台、Docker、执行工作进程及自身操作单元。检查降至策略执行账户运行，重启经 `systemd-run --pipe --wait` 派生的短命命令单元以 root 执行固定的 `systemctl --system restart`；同一宿主操作 ID 以原子 mkdir 持久认领一次执行权，停止协议只作用于由该 ID 派生的命令单元。

`service_manage` 在任何访问模式下都逐次审批——包括完全访问。理由是完全访问模式只代表执行账户已有权限（ADR 0003），而 helper 的 root 分支是后台经 sudoers 获得的新提权能力，不属于执行账户已有权限，必须按 ADR 0017 的「明确授权」单独确认。审批范围固定本机身份、规范单元、动作与修订指纹（策略内容、单元定义内容及已加载配置）；批准后这些修订或 IM 固定身份变化即失效，helper 在请求 systemd 前再次复核。已消费但无确定结果的操作记为效果未知，不自动重发，由拥有者核实后重新申请。

## 与既有决策的关系

- ADR 0003：完全访问不扩大为后台的提权能力；逐次审批与「清晰失败优于静默降级」一致。
- ADR 0004：执行账户不因此获得新的 sudo/Polkit 权限，也不能读取策略之外的部署材料。
- ADR 0017：本记录是「专用账户按明确授权管理整台服务器」的第一个授权形态；后续动作（日志读取、其他管理动作、远程主机）按各自需求以同样的固定协议扩列，不引入通用执行框架。
- ADR 0011/0012 及 issue 08：审批通知、批准消费与效果未知的 IM 路径不变，服务审批复用同一通道，不另建控制面。
