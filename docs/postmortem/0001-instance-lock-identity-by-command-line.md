# 事故复盘 0001：实例锁按命令行判断持有者，独立检出名下会接管仍存活的锁

Status: resolved

## 执行摘要

实例锁用「进程命令行里是否含 `ruukoto`」判断持锁者是不是本产品的后台。这条判断隐含了一个假设：检出名里一定带产品名。当检出目录名不含 `ruukoto` 时，正在运行的后台命令行里就没有这个词，锁被误判为「PID 已被无关进程复用」的遗留锁，于是第二个后台接管了锁并启动——两个后台同时写同一份 SQLite 与 JSONL。根因不在锁的原子性（`mkdir` 是对的），而在**身份核实依赖了一个与产品无关的外部事实**。它在 macOS 与 Linux 上都复现，且逃过了当时的测试，因为测试都在名为 `ruukoto` 的检出里跑，恰好满足那个隐含假设。护栏是把身份换成内核提供的、不可变的进程启动标识，并补上一条用改名子进程验证「不依赖检出名」的用例。

## 影响

两个后台可能同时持锁运行，共写同一份 SQLite 元数据与会话 JSONL。数据损坏不会立即报错，而会在后续读取出错或状态错乱时暴露。实例锁存在的意义正是阻止这种情况，因此这是一条被绕过的安全边界，而不是普通功能缺陷。

未受影响：锁的原子获取语义（`mkdir`）本身正确；单实例场景下的行为一直正常。实际触发需要「检出名不含 `ruukoto`」这一条件，日常在仓库目录下开发不会遇到。

## 时间线

- 锁实现从一开始就用命令行核对进程身份，注释写明「从宽，宁误拒不误放」，包含 `ruukoto`、`cli.ts`、`dev.ts` 三个子串。
- 2026-10-09 建立可复现基线的改动（`4d5379c`）在隔离检出上跑完整检查，Node 24.15 与 24.21 均复现同一问题：锁被错误接管。
- 定位到条件：检出名不含 `ruukoto` 时 `looksLikeBackend` 返回假，持锁的活进程被当成「无关进程复用 PID」。
- 修复改用内核启动标识（Linux 用 `/proc/<pid>/stat` 的启动 tick 加 boot id，macOS 用 `ps -o lstart=`），并把只读探测与获取路径合并到同一个 `probeLockHolder`；旧记录保留命令行兼容路径。
- 同批新增 `test/101-instance-lock.test.ts`，其中一条用例用改名后的真实子进程持锁，断言仍能核实身份。

## 根因

`looksLikeBackend(command)` 把「命令行里含 `ruukoto`」当作「这是本产品的后台进程」。命令行内容由**启动方式**决定，不由**进程身份**决定：

- 检出目录名、`npm link` 的 bin 名、启动脚本的写法都会改变命令行；
- 该函数还接受 `cli.ts` 与 `dev.ts`，任何在类似文件上运行的无关进程也会被误认。

于是判断在两个方向上都错：真后台在改名检出里被误判为无关进程（本次事故），无关进程也可能被误判为后台。正确做法是让内核给出进程启动时刻的标识，它与进程一一对应、不可伪造，也不随命令行变化。

## 为什么没被发现

- **测试全在名为 `ruukoto` 的检出里跑。** 隐含假设恰好被测试环境满足，`looksLikeBackend` 永远返回真，错误分支从未执行。测试与生产环境的差异正好落在被判定的那个变量上。
- **`looksLikeBackend` 的宽匹配被写成了一种保守选择。** 注释说「宁误拒不误放」，把接受更多子串当作安全方向；但该函数的两个返回值都通向危险动作——返回假会接管锁。从宽在这一侧其实是冒险。
- **锁的行为没有端到端用例。** 当时没有测试真的启动第二个进程去竞争锁，只覆盖了单进程内的获取与释放。
- **只在隔离检出上暴露。** 开发实例运行在仓库目录下，检出名天然含 `ruukoto`；问题只在 CI 检出或部署目录等改名场景出现，日常开发看不到。

## 护栏

- **身份改用内核启动标识。** `processIdentity` 读 Linux 的 boot id 与启动 tick、macOS 的 `ps -o lstart=`；核实不到身份时保守拒绝启动，而不是放行。见 `packages/core/src/instance-lock.ts`。
- **获取与只读探测共用同一套核实。** `probeLockHolder` 是唯一判定入口，获取路径改为调用它，消除了两处判断漂移的可能。
- **新增不依赖检出名的不变量测试。** `test/101-instance-lock.test.ts` 用改名后的真实子进程持锁，断言仍能核实身份、退出后允许接管；另有用例覆盖「启动标识不同则判为遗留锁」与「无法核实则保守拒绝」。
- **规则写入常驻约定。** 根 [AGENTS.md](../../AGENTS.md) 的「持久化」一节记录状态与事件同事务的处理方式；本事故的具体教训留在本文件。
