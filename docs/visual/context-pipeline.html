模型上下文是一份每次调用重算的视图

视图的顺序固定：前缀参考块与长期记忆 → 会话历史（压缩摘要、移出标记、[S, C) 清理后的中段、其余原样） → 任务级参考块 → 当前任务。前缀参考块与记忆在任务开始时钉版，任务内不变；任务级参考块与当前任务只属于本任务。任务级参考块按继续来源 → [SubAgent 结果] → [工作内消息] → 计划说明排列（context-assembly.ts · references）；[SubAgent 结果] 与 [工作内消息] 只出现在普通开发会话里，来历见SubAgent 任务的上下文。

「选」由 context-selector.ts · selectContext 的确定性策略 deterministic-v1（context-selector.ts · SELECTOR_STRATEGY）按预算做，不调用模型。「压」只在不做移出的视图估算超过高水位 H′ 时发生，把较早的内容换成占位说明与滚动摘要；超长工具结果的有界替换与预算不够时的整轮移出同样只改视图。系统提示按会话类别（dev / main / subagent；main 是旧架构的逻辑角色，coding 与 chat 已退役、提示已删除）固定为 session-factory.ts · SYSTEM_PROMPTS 之一，pi 自己的 compaction 关闭（session-factory.ts · session_before_compact 一律取消）。

每一段的估算按分类记账（context-selector.ts · CONTEXT_CATEGORIES）；/context 与选择记录的 estimates 用同一张表，按下表顺序展示：

一次调用的流水线

driver 的 context 钩子 driver.ts · handleContext 把当前分支消息交给本任务组装实例的 context-assembly.ts · assemble。assemble 不抛错：pi 会捕获扩展异常并继续运行，所以失败原因记在组装实例上，由发送前的 context-assembly.ts · prepareSend 拒发。

任务开始钉住的内容

每个任务一个组装实例（context-assembly.ts · beginContextAssembly），任务结束时 driver 中止它在途的 Jev 与摘要请求并丢弃实例；下一任务重新读取，这就是拥有者刷新项目指令、技能与记忆的入口。项目指令、Jev 配置与记忆都按会话的原项目（sessions.project_id）读取，工作区组织归属不参与（见工作区配置）。资料受限会话（执行画像的 restricted，tool-availability.ts · executionProfile：SubAgent 子会话）以下各项都为空。

选择规则

  • 必留：系统提示、参考块（各注入一次）、当前任务输入、当前任务最新批次、当前任务最近一次成功 todo_write 所在的批次（与最新批次同级）。长期记忆不是必留项，先按独立预算选入；选入的记忆、摘要块与工具定义再和必留项一起算作固定占用，固定占用超过输入预算即 ok = false。
  • 以完整交互为单位：一轮 user 连同其后的 assistant 与工具消息整体进出；当前任务内以批次为单位（一条 assistant 连同它的全部 toolResult），toolCall 与对应 toolResult 不拆分。
  • 由近及远：先装当前任务的较早批次，再装更早的历史交互，都从最近的开始；某一组装不下就停，更老的组不再尝试，避免挑拣远旧碎片造成因果断裂。
  • 孤儿消息剔除：崩溃恢复留下的缺配对 toolCall/toolResult 只从视图移出，历史原文不动，选择记录以 unpaired_tool_call:<id> 记为排除原因。
  • 有界替换：单条工具结果的某个文本段超过 toolResultViewChars（context-selector.ts · DEFAULT_BUDGET_CONFIG 的 80_000 字符）时，视图里首尾各保留上限的一半并写明省略字符数，附 history_read / read_artifact 指引；skill 结果不截取（context-selector.ts · capToolResultView）。
估算口径

估算不追求与 provider 一致：先用 pi 的 estimateTokens（字符数 / 4），CJK 字符补足到每字 1 token，再乘校准系数 calibration（1.5），意在宁高勿低（context-selector.ts · estimateMessageTokens）。/context 里的数字是这个估算，不能用它反推某一类的精确用量。

预算与水位：数字从哪来

输入预算不是模型窗口，而是扣掉各项预留后的剩余空间（context-selector.ts · inputBudgetFor）：

输入预算 = contextWindow − maxTokens − thinkingBudget − toolResultReserve − safetyMargin
        = 窗口        − 输出上限   − 0              − 8000              − 2000

thinkingBudget 由 model-selection.ts · modelResponseBudget 固定为 0（pi 的响应上限已包含思考）；其余预留取 DEFAULT_BUDGET_CONFIG。高水位 H′ = min(compactionHighWater, 输入预算)，compactionHighWater 为 200_000；低水位 0.5 H′、保护尾部 0.15 H′、最小降幅 0.2 H′ 都写在 context-selector.ts · planCompaction 里，用同一估算口径。

量来源两种窗口下的取值（示例）说明
contextWindowpi 模型目录，经 modelResponseBudget 校验1 000 000 / 200 000不是本项目定义的常量
maxTokens同上；prepareSend 把请求的 maxTokens 显式设为这个值384 000 / 64 000输出预留随模型变化
toolResultReserveDEFAULT_BUDGET_CONFIG8 000 / 8 000为下一批工具结果预留

窗口与输出上限来自模型目录，会随模型变化，表中两组窗口只是示例；本页写死的只有仓库里的预留常量。换模型后请先看 /context 的实际分母，再对照上表。

上下文压缩：压缩点、两层、指纹与提示缓存

压缩点记录覆盖范围 S、C 与摘要正文，并用 compaction.ts · checkpointFingerprint 把前 C 条消息的角色、时间戳、工具调用 id 做成 SHA-256 指纹。每个会话至多一个生效的压缩点，新建时旧行在同一事务里改为 superseded；每次调用读取生效压缩点并核对指纹，消息少于 C 条或指纹不符时当场作废（invalidated），按无压缩点处理。资料受限会话不压缩，也不加移出标记。

  1. 规划：保护尾部是由新到旧累计到 0.15 H′ 的完整单元（至少含最新批次）；当前任务最近一次成功 todo_write 所在的批次也不进覆盖范围。估算不超过 H′、必留项超预算，或预计降幅不到 0.2 H′ 时不建压缩点，也不调用摘要模型。
  2. 第一层（清理）：C 推到保护尾部开头（清单保底批次更早时停在它前面），[S, C) 中正文超过 CLEAR_MIN_CHARS（2_000 字符）或含图片的工具结果整条换成占位说明；skill、todo_write 结果、toolCall 参数与 assistant 文本不清理。toolCallId 与 isError 不变，配对不受影响。
  3. 第二层（滚动摘要）：只做清理的估算仍高于低水位 0.5 H′ 时推进 S，取能压到低水位的最小单元边界（摘要块按 SUMMARY_MAX_CHARS 约 4 000 字的上限估算）。摘要输入是上一版摘要加 [旧 S, 新 S) 的原消息，提示版本 compaction-v2（compaction.ts · COMPACTION_PROMPT_VERSION）。
  4. 落盘后重选：压缩点与 task.context_compaction 的 finished 事件同一事务写入（context-assembly.ts · compactContext），然后重读输入再选一次。此时仍超输入预算，选择器照常由近及远纳入，装不下的更早单元移出，视图在摘要块之后加一条移出标记，写明移出的单元数与时间范围。
压缩点状态含义如何进入选择器怎么用
active当前生效，每个会话至多一行新建时写入（旧的 active 同一事务改为 superseded）前 S 条换成摘要块，[S, C) 按第一层清理
superseded被新的压缩点取代新建压缩点时同一事务内改旧行不再使用；引用它的选择记录仍留着 checkpoint_id
invalidated指纹不符或消息少于 C 条每次调用核对失败即写库（context-assembly.ts · validatedCheckpoint）按无压缩点处理；估算仍超过 H′ 时本次重新规划
摘要模型

配置了摘要模型就用它（每次读取当前配置，不按任务钉版；已配置但解析失败按失败处理，不改用会话模型），否则用任务记录的模型选择。摘要请求经模型运行时直接发出，不经发送前复核那层包装：不带思考参数、单次尝试、超时 180 s（SUMMARY_TIMEOUT_MS）、输出上限 16 384 token（SUMMARY_MAX_TOKENS，模型上限更小时取模型上限），触顶按失败处理；覆盖段估算超过摘要模型的输入预算也按失败处理。phase 为 started 的事件在确定摘要模型后、发出请求前写入。

前缀稳定：提示缓存只在压缩时失效一次

视图顺序的设计目标是让同一会话连续调用的消息序列保持前缀关系（ADR 0016）：记忆按任务钉版、参考块的块头不含版本号（记忆块头带版本，修订时本来就要换内容）、任务级参考块插在当前任务输入之前而不打断其前的历史、同一条消息的清理与有界替换不随后续调用变化。

两类普通错误

「中断 + 暂停队列」只对 checkBeforeSend 与 prepareSend 抛出的 ContextSendBlocked 成立（task_canceled 在这之前抛出，不记下）：driver 把它的原因记下，任务结束时由 driver.ts · consumeBlockedReason 识别。prepareSend 里预算配置无效与选择记录落库失败抛的是普通错误，不会被记下；pi 把它转成 stopReason = "error" 的消息，兜底匹配的四个 context_* 前缀也对不上，于是任务以 failed 结束，队列不暂停。请求同样没有发出，差别只在终态与队列。

被拦下之后：任务状态与队列

consumeBlockedReason 先取发送侧记下的原因，再兜底匹配最后一条 assistant 错误消息里的 context_budget_exceeded、context_selection_failed、context_selection_missing、context_pairing_invalid 前缀。识别到 image_input_unsupported 时直接写 failed 结束标记并失败，不暂停队列；其余已记下的阻断原因写入任务结束标记（types.ts · TASK_END_MARKER），driver.ts · pauseQueue 在同一事务里把会话队列置为 paused（原因即阻断原因）并发出 session.queue_paused，任务以 interrupted 结束。队列恢复与任务状态机见任务生命周期。

provider 返回上下文超限时同样中断并暂停（context_overflow），只是判定在模型循环结束之后，按最后一条 assistant 消息判断（isContextOverflow）。超限不触发压缩、不重试。

资料范围、工作区配置与长期记忆

资料范围由宿主注入的身份决定（access.ts · canAccess）：身份里的项目就是会话的 sessions.project_id（driver.ts · accessor），工具参数里的任何 id 都不改变它。granted_paths 与完全访问模式只作用于文件与命令执行，不扩大资料 API 范围。

默认

本项目的历史 / 产物 / 生效记忆 + 个人共享记忆。记忆的每条来源引用都要当前可访问（sourceRefAccessible）：来源不再可访问的记忆下一次调用即不注入，选择记录记 source_scope_revoked。

资料授权

拥有者在可信入口（CLI ruukoto grant、配置中心的项目详情）创建的 data_grants：来源项目、目标项目、类别 history / artifact / memory，同项目不需要也不能建（access.ts · createGrant）。可查看、可撤销；撤销自后续查询与上下文注入起生效，不撤回已经发给模型的内容。来源与目标都按原项目 ID 判定，会话的工作区组织归属不改变授权端点。

受限身份

访问判定里仍有 qq_group 与 role_restricted 两种受限身份（旧架构的群聊入口与 chat 角色）：只读本项目、不查授权表，owner_note 来源不自动放行。群聊与 chat 角色退役后，驱动器只给出 agent 身份（driver.ts · accessor），已没有会话以这两种身份运行。main（与旧 coding）角色的项目一律不能读取原始 QQ 群项目，这条先于资料授权判定，群资料仍是归档。

受限会话的上下文

资料受限的会话（执行画像的 restricted，executionProfile：只有 subagent 工具类别，即 SubAgent 子会话）不注入任何参考块与记忆、不跑 Jev、不压缩。旧群会话的撤回过滤已随群聊退役删除。SubAgent 的资料身份仍是普通的 agent，限制来自上下文与工具，见下一节。

工作区配置：按原项目读取

工作区就是带根目录归属的项目（项目是旧架构的组织边界），配置仍挂在项目上。旧会话经迁移映射到工作区后只改 sessions.workspace_project_id，这一列只决定会话显示在哪个工作区下（ADR 0018）；下表每一项都按会话的原项目 sessions.project_id 读取，映射前后不变，迁移也不复制配置。迁移流程与两个归属字段见存储布局。

长期记忆

类别限 preference / convention / decision / experience（types.ts · MEMORY_CATEGORIES），每条必须关联至少一个来源（历史条目 / 产物 / owner_note），正文上限 memory.ts · MEMORY_CONTENT_MAX_BYTES（32 KiB），来源引用至多 MEMORY_SOURCE_REFS_MAX（8 条）。

  • 注入哪些：任务开始时钉住当时生效记忆（本项目 + 个人共享）的 id 与顺序：项目优先 → 更新时间倒序 → id（memory.ts · listActiveFor）。每次调用只对这些 id 重读当前内容，按钉住的顺序装入 memoryBudget（2 000 估算 token）；放不下的一条跳过并记 memory_budget，后面更短的仍可能装入。
  • 中途变化：已撤销或来源失效的下一次调用即剔除；拥有者中途修订的按新版本注入；任务中新建的记忆（含 memory_save）从下一任务起注入。选入的记忆在选择之后、发送之前变化，发送前复核以 context_source_changed 拦下。
  • 钉版读取失败：记忆 id 列表记为错误，每次调用都以 context_selection_failed 阻断发送，不静默省略。
  • 选择记录里：选入与未选入的记忆都按 id 与版本记下，未选入的附原因（memory_budget、source_scope_revoked）。
  • 写入与撤销：Agent 经 memory_save / memory_revoke 写入，标记 author=agent，不能冒充拥有者确认；只能写当前项目，个人共享与跨项目写入只有拥有者能做。修改经预期版本号条件更新，冲突明确报错；撤销 = 停用（不删除），恢复旧版本 = 创建一条新修订（memory.ts · restore，只有拥有者入口）。

资料授权的复核

main 委派时，materials 按父会话原项目的资料权限解析（scheduler-tools.ts · createSourceResolver），来源引用存进任务的 read_scope.sourceRefs（types.ts · SubAgentReadScope）。复核的对象不是本次委派的那批来源，而是这个 SubAgent 名下全部历史任务的 sourceRefs 与本次的并集（store.ts · listTasksBySession）——复用保留的子会话上下文里仍可能有旧工作的资料，旧资料撤销后同样要拦。登记事务里核实一次，之后子任务每次发送前由 checkBeforeSend 按子会话全部任务再核实（driver.ts · task_sources_revoked）。核实只看 task_result 与 artifact 两类来源能否经资料授权读到；text 与 app_data 没有可撤销的授权，不复核；chat_result 不能作为委派资料。

快照正文不重新解析。撤销只拦住之后的请求：子任务以 interrupted 结束、子会话队列暂停，编排器把它归为结果未知；已经读进子会话历史的内容留在 JSONL 里。普通开发会话用 read_paths 委派时没有来源引用，读范围由宿主钉定的路径与目录身份约束，在工具执行一侧检查（见编排器）。

可观察：三处各看到什么

/context 分解

取当前会话最近一次调用的选择记录，由后台按 CONTEXT_CATEGORIES 算出各类估算及占输入预算、总窗口的比例（runtime.ts · getContextBreakdown），TUI 画成一条窗口长条，另有「预留」与「尚余输入」两段，并列出本次使用的压缩点（摘要替代条数与截至时间、清理条数、建立它的任务与调用序号、摘要模型或失败原因）与 Jev 实验结果。分母固定为记录创建时的窗口快照；快照与预算不一致按记录损坏报错。

/prompt 查看

模型请求列表（新到旧分页）与某一次的 prompt 详情：systemPrompt / messages / tools 的请求快照；入站图片以 image_ref 及稳定媒体元数据保存（imageReferenceSnapshot），不重复写 base64，按字节分段加载（runtime.ts · readPromptSnapshot）。快照在委托发送函数之前捕获，缺失时如实报错，不重新拼接。文本与工具定义保留发出原文，入站图片正文由引用指向的不可变产物恢复；选择记录描述组成。

选择记录

ruukoto selection-records --task <id> | --session <id>：任务与会话、调用序号、策略与配置版本、模型、项目指令与技能版本、选入与排除的消息序号及原因、记忆 id 与版本、被有界替换的工具结果（序号与原 / 视图字符数）、各项估算与预算、窗口快照、本次使用的压缩点、Jev 实验记录、发送后回填的 usage。排除原因只记序号与原因码，不含消息正文。

Store.getSessionUsage 在 SQLite 按会话汇总实际用量：输入为 input + cacheRead + cacheWrite，输出为 output，缺少 usage 的调用不计入。保存后持久事件 session.usage_updated 通知 TUI 经 get_session_usage 刷新底栏；切换会话与重连也重新查询。底栏用灰体显示输入、输出数量和模型，支持 K、M、B；宽度不足时隐藏统计。

这些记录与压缩点在库里的落点见存储布局；工具可用性与审批见工具调用路径。

Jev 上下文筛选实验（默认关闭）

按项目配置（jev-config.ts · getProjectJevConfig，缺省关闭，损坏配置拒绝使用）。凭据用途须为 JEV_CREDENTIAL_PURPOSE（jev_context），作用范围恰好是本项目的这一项操作，每次调用重读核对。启用后，当前任务与有界的候选历史文本会发送给服务方：模型 jev-1.13.0（JEV_MODEL）、阈值 0.5（JEV_THRESHOLD）、单次超时 2 s（JEV_TIMEOUT_MS）、最多 24 个候选（MAX_CANDIDATES）、任务与每个候选各 8 KiB（TASK_CAP_BYTES / CANDIDATE_CAP_BYTES）、整个请求 24 KiB（REQUEST_CAP_BYTES）、响应 64 KiB（RESPONSE_CAP_BYTES）。候选只取 [S, n) 内的非必留单元；任务文本（含继续来源的原始要求）只作筛选依据，参考块与必留项不作为候选；无效回答、超时或服务失败回退 deterministic-v1，不自动重试。启用从下一任务生效；停用后迟到的结果被丢弃，但已经发送的内容无法撤回。
