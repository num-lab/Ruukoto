控制面协议

拥有者的客户端（TUI、CLI、配置中心）与本机后台之间的全部往来：一条 Unix socket 上的换行分帧 JSON。本页讲连接怎么建（含 ruukoto-dev 建连前先确保后台在运行）、认证怎么做、事件流怎么做到不丢不重、请求失败怎么分类、提交怎么去重，并登记两份随代码更新的目录：op 与持久事件。

传输、帧与认证

控制面是一个 Unix socket 上的请求/应答加单向推送：客户端发请求帧，后台回应答帧；持久事件提交后，后台向发过 connect 的连接推事件帧。没有 TCP 端口，也没有远程协议——远程使用是先登录服务器，再在那台机器上开 TUI。

socket 是控制面目录下的 control.sock（connect.ts · socketPathFor）。控制面目录默认是数据目录的同级目录 control/，可用环境变量覆盖，变量名按产品隔离：ruukoto 读 RUUKOTO_CONTROL_DIR，ruukoto-dev 读 RUUKOTO_DEV_CONTROL_DIR（connect.ts · controlDirFor，product.ts · dirEnvFor）。后台启动时以 mode 0770 建目录（再经 umask，022 时实为 0750；服务器由安装步骤预建 0770，见存储布局），删掉上一个实例遗留的 socket 文件后重新监听，再把 socket 收紧到 0660（server.ts · ControlServer.start）；能安全删除遗留 socket，是因为实例锁已保证本进程是这个数据目录唯一的后台。

服务端按字符串长度（UTF-16 码元数）比较请求行，客户端只核对收到的帧（按 UTF-8 字节数），发送前不核对请求大小。超过服务端上限的请求会让连接被直接销毁，客户端把在途请求当成应答丢失（disconnected）；如果是提交，待确认记录每次重新上线都会被核实：find_task 查不到，就按原参数重发，连接又被销毁，状态机按退避初值 500 ms 重连，如此循环。这是按代码推演的结论（架构工单 07 也有同样推断），未实际运行验证。

认证：先令牌，后一切

socket 所在的控制面目录的权限是第一道门。连接建立后，第一个成功的操作必须是 auth；认证之前，服务端对其他 op 一律回 unauthorized，不返回快照、不执行请求，但连接保留，可以再次认证。

建连之前：确保后台在运行

只有 ruukoto-dev 的任务界面在建连前做这一步（ensure-backend.ts · tuiSpawnsBackendOnDemand，条件是产品为 ruukoto-dev）。tui/index.ts · runTui 在创建 ControlConnection 之前调用 ensureRuukotoDevBackend：ruukoto-dev、ruukoto-dev <路径>、--session 都经过这里，--demo 不连后台也不拉起。ruukoto（个人 Agent）的后台由显式 server 或 systemd 管理，TUI 只连接：后台不在时，只要能取到令牌就直接进入下一节的退避重连；取不到令牌（例如后台从未启动、owner.token 还没生成）就打印指引并以 1 退出。

不变量 · 拉起只在启动时发生一次

拉起只发生在 TUI 启动、首次建连之前。连上之后断线只退避重连，重连只恢复观察，绝不再次拉起后台；后台没了要重新拉起，就重开 TUI。拉起的后台按正常启动做崩溃恢复，拉起与重连都不构成重新执行任何任务的授权。

握手与事件流：快照、补发、实时

认证之后的 connect 同时做三件事：读一张有界快照、补发游标之后漏掉的事件、把这条连接登记为订阅者。首次连接、断线重连、发现缺口后的重新同步都走这一步，恢复的是观察，不是执行。

快照（protocol.ts · ConnectSnapshot）包含：项目、会话、任务（全部活动任务，加每个会话最近结束的 20 个，常量 SNAPSHOT_ENDED_TASKS_PER_SESSION；更早的经 list_tasks 分页）、待决审批（参数为有界预览）、活动任务的产物元数据、输出预览（执行中任务的生成中正文，以及中断、失败、取消任务尚未落为历史条目的残片）、数据实例标识 instanceId、执行后端说明、后台默认模型，以及 roleSessionIds（逻辑角色绑定的会话，旧架构）、subAgentSessionIds、workDelegations、subAgents。后四项对旧后台可缺省。subAgents 的每条身份除了 state（running / idle / unverified）还带独立于 state 的 closedAt / closedBy（关闭后委派拒绝 closed；TUI 显示时关闭优先于 state）。

连接状态机

ControlConnection 把上面的链路包成五个状态（connection.ts · ConnectionState）。判断只看一条：后台是否明确拒绝。认证或同步被明确拒绝（令牌无效、协议版本不符）才停；其余失败——后台还没起来、建连超时、认证或同步超时、连接中途断开——都只是暂时没连上，按有上限的退避重试。

请求结果与去重

「这个请求到底做没做」在控制面只有四个答案（client.ts · RequestOutcome），由产生错误的地方写定一次（架构工单 07），调用方按分类处理，不再各自列错误码表。

分类含义产生处TUI 的通用处理
not_sent未发送（已知未执行）连接不可用 connection_unavailable（含握手前提交）、客户端已关闭 closed、参数无法序列化、建连失败 connect_timeout / connection_error「X 未发送」；提交恢复草稿
rejected后台明确拒绝ok:false 且错误码不在下一行列表里「X 失败」；提交恢复草稿。request_conflict 例外：保留记录，提示核实原任务
unknown应答丢失，连接仍在请求超时 request_timeout；应答码在 UNKNOWN_REPLY_CODES 里：internal_error（异常没带码或带的是系统错误码）、response_too_large（已执行完）、mode_switch_unverified「X 结果未知…先用某命令核实再操作（未自动重发）」；提交、工作区入口、审批应答、/mode、/model 当场查询后台核实
disconnected应答丢失，已断线terminate() 时的在途请求：socket 关闭或出错、坏帧、超长帧、未换行残留、客户端主动关闭通用文案同上；上一行那几处不发注定失败的查询，等重连后的快照或核实

系统错误码（ENOENT、ERR_SQLITE_* 等）不进协议：服务端只原样转发小写蛇形的业务码，其余统一收口为 internal_error，原码写进 message（server.ts · errorReply）。TUI 的通用文案在 commands.ts · writeFailure。

不变量 · 写请求应答丢失不换键

任何 unknown / disconnected 的写请求都不自动换新键重发：有幂等键的（提交、工作区入口）按原键核实，确认未接收才以原键重发；其余先查询后台状态，再由拥有者决定。这与工具调用路径的「效果未知」是同一条纪律的两个位置：「应答丢失」针对控制面请求，「效果未知」针对工具操作，不混称。

提交去重：先落盘，再发送

提交（submit / continue）会真正启动任务，所以它的幂等键要比请求本身活得久：断线、超时、界面重载都不能让同一条输入变成两个任务。submission.ts · SubmissionGuard.submit 的顺序如下。

未发送或被明确拒绝时清除记录、恢复草稿；request_conflict 保留记录。应答丢失时记录留着，进入「接收结果待核实」：unknown 当场核实这一条，disconnected 等连接回到 online 后核实全部记录（每次上线都核实一遍）。核实只问一个问题：后台有没有收到这个 request_id？

后台怎样判定同键：同参与异参

同键同参返回原任务，同键异参回 request_conflict，客户端不换新键、不重发，展示冲突让人处理。键是（会话，request_id）；「参数」是提交摘要：原文、访问模式（未显式指定时取提交瞬间的会话默认模式）、授权范围、继续来源、模型选择与编排字段的 sha256（store.ts · findMatchingSubmission）。schema v11 之前接收的提交没有编排字段，编排字段全空的新提交会另带一份旧格式摘要参与核对；连摘要都没记录的旧任务一律回 request_conflict，请拥有者用 find_task 核实。

缺模型：明确未接收、但记录里没有模型选择（早期版本落盘的）时不能原样重发，转为 needs_resubmit：拥有者确认后把原文恢复进原会话的草稿，用 /model 选好再提交；按 Esc 则保留记录。

记录目录：每个产品自己的档案根下的 pending/（ruukoto 为 ~/.ruukoto/pending，ruukoto-dev 为 ~/.ruukoto-dev-agent/pending），可用 RUUKOTO_PENDING_DIR / RUUKOTO_DEV_PENDING_DIR 覆盖（pending-requests.ts · defaultPendingDir）。目录 0700、记录 0600；解析不了的文件留在磁盘上单独列出，不静默丢弃。令牌等凭据永不写入这里。

工作区入口的幂等键

CONTEXT.md 把「工作区入口」标为旧架构：当前实现里，ruukoto <路径>（ruukoto-dev 同样）打开的工作区实例上是带根目录归属的项目，数据模型与旧数据迁移见存储布局，新方向会再迁移。这里只讲它在协议上怎样做到重试不重建。

  1. 本地解析目录：按客户端当前目录解析路径，取 realpath 与 dev/ino；不存在或不是目录就退出（workspace.ts · resolveWorkspaceDir）。随后生成本次启动唯一的请求标识 boot-<uuid>，本次启动内只用这一个。
  2. 在快照里选目标：先找根目录归属与该目录身份相同的工作区，命中即用它；否则在尚无根目录的旧项目里按会话目录身份找可认领的候选（角色、群聊会话所在的项目和会话分布在多个目录的旧项目不作候选，与后台防御同一判定）；零个候选让后台自动建，一个直接认领，多个让拥有者选，取消则不建任何东西（workspace.ts · findWorkspaceProjects）。
  3. 发 open_workspace：cwd、可选 project_id，request_id 就是启动请求标识（workspace.ts · ensureWorkspaceSession）。后台先重新校验目录身份与保护根，再在一个事务里：同标识已有会话且目录身份相同就返回原会话（不插入、不发事件，也不比对 project_id），目录不同回 request_conflict；否则带 project_id 时认领该项目的根目录，不带时复用已归属该目录的工作区或新建项目（名取目录名，重名加序号），再建会话。失败整体回滚，不留空项目（runtime.ts · openWorkspace）。
  4. 应答丢失：unknown 当场核实一次——先在当前状态里按 createRequestId 等于启动请求标识找会话，找到就进入，找不到才以同一标识重发；仍丢失就回到正常启动。disconnected 或 not_sent 等重连后的新快照再做同样的核实。明确拒绝（如保护根）回到正常启动（app.ts · verifyWorkspaceEntry）。

核实是先找再发：首次请求若已生效，新快照里就有带这个标识的会话，直接进入，不再发请求；即便重发，后台也只按同一标识返回原会话。认领有三道防线：已归属别的目录的项目拒绝改归属；同一目录身份（realpath 相同，或 dev+ino 相同的挂载别名）已归属别的项目回 duplicate；projects.root_real 的部分唯一索引只作兜底。角色或群聊项目、会话分布在多个目录的旧项目，后台都拒绝经目录入口认领，多目录的旧项目走 preview_workspace_migration / apply_workspace_migration。

迁移应用也有自己的幂等键：apply_workspace_migration 必须带 request_id 与当前连接的 instance_id；先查成功回执（核心库 meta 里的 migration_receipt:<request_id>），同键同参返回原成果，同键异参回 request_conflict；无回执时再核对预览修订（过期回 revision_conflict），然后单事务提交（workspace-migration.ts · firstReceiptCheck）。

op 目录

服务端 server.ts · dispatch 的 switch (request.op) 派发下表全部 op；auth 在派发之前单独处理（见认证）。本页是 op 的登记处，代码新增 op 时必须补到这里（visual-docs 检查会报缺）。列含义：写＝会改变后台状态；防重＝幂等键 request_id，或乐观并发的版本/修订号（版本不符回 version_conflict 一类错误，不覆盖别人的修改）；TUI＝在 TuiOps 类型表里。各 op 对任务状态的效果见任务生命周期，审批语义见工具调用路径。

TuiOps：TUI 用到的那一层

ops.ts · TuiOps 是一张类型表（架构工单 07）：上表 TUI 列为「是」的 op，参数与返回形状只在这里定义一次，返回形状直接取服务端 Runtime 方法的返回类型。真实客户端、demo 合成会话与测试替身都按它实现 ControlTransport，于是「TUI 发的 op 服务端认不认得、返回形状对不对」在编译期就能对上。服务端派发、CLI 与配置中心仍按字符串调用任意 op，不经这张表。TUI 收到的错误统一按 RequestOutcome 处理（见请求结果）。

事件目录

持久事件（types.ts · PersistentEventBody）是后台状态的变更流：与状态变化同一事务写入事件表，提交成功才广播，回滚的事务不产生事件。本页是事件类型的登记处，代码新增类型时必须补到这里。「详见」列指向讲了该事件或其机制的页面小节；「—」表示没有别的页面专门讲它，本行即全部说明。

流式输出

正文不是一条消息一个事件，而是按「显示段」持续追加的增量（driver.ts · flushOutput）。三个字段：contentIndex 是后台分配的连续段序号（不等于 SDK 的块索引），offset 是本片在段内的 UTF-8 字节偏移，totalBytes 是到本片末尾为止段内的字节数。

模型流（Driver）事件表客户端
text_delta：累积到当前段，距上次冲刷满 250 ms 才冲刷
一次冲刷在一个事务里写一到多条 task.output_fragment，每片不超过 FRAGMENT_TEXT_CAP（8 KiB），切在 UTF-8 字符边界上。
thinking_start / thinking_delta：冲刷并结束当前正文段，写 task.thinking（开始时立即写，之后同样 250 ms 节流）
toolcall_*：冲刷正文、结束当前段与思考
message_end：补齐尾部，冲刷，结束思考
此后这条消息的正文在事件流里已完整，但最终正文仍以历史 JSONL 为准。
turn_end 的下一拍：task.output_entry {entryId, sessionFile, role, messageId}
  • 段：思考与工具调用会结束当前正文段，下一段正文取新的 contentIndex；同一段的片段共享 startedAt，即该段首次出现正文的时间。节流间隔 driver.ts · FRAGMENT_INTERVAL_MS。
  • 思考：task.thinking 带 thinkingId、startedAt / endedAt 与尾部有界的最新文本；TUI 默认只显示最后 4 行（可展开），结束后标题换成耗时（event-flow-view.ts）。
  • 最终正文：事件只是实时投影与恢复来源。消息正文经 read_history_entry 读取；点开工具结果行时经 read_tool_result 读取工具正文与补丁。重连时用 read_task_events 按任务分页补事件，用输出预览补生成中或中断前的尾巴。
  • 兼容：没有 offset 的旧片段按「累计文本的尾部」解释。

有界视图：线上载荷不带完整大参数

事件表、审批请求、工具操作在库里保存完整参数；只有发往客户端的载荷经有界视图转换（views.ts · paramsToView）。实时推送与补发都会对 task.tool_intent 与 task.awaiting_confirmation 做这一步，快照里的待决审批也是。

常量取值行为
PARAMS_INLINE_CAP8 KiB（序列化字节）不超过上限的参数原样内联；超限换成保留结构的预览
PARAMS_PREVIEW_STRING_CAP256 字符预览里的长字符串截断，并标注原始字节数
FRAGMENT_TEXT_CAP8 KiB正文增量与思考文本在源头（Driver）就有界（思考取尾部）
SEGMENT_DEFAULT_BYTES / SEGMENT_MAX_BYTES64 KiB / 256 KiB分段读取的默认页大小与单页上限

换成预览的参数带 paramsBytes（完整序列化字节数）与 paramsTruncated: true，完整正文经 get_confirmation_params / get_tool_op_params 按 ID 分段读取。输出预览的 state 区分生成中（generating）与中断前捕获的部分（captured_partial）。

协议版本演进

每一帧的 v 都是协议版本，当前 PROTOCOL_VERSION = v12（types.ts · PROTOCOL_VERSION）。服务端只服务完全相同的一版：不一致就回 protocol_version，连接状态机进 failed，按需拉起的探测也按「后台在运行、需要升级」报错，都不静默重试。持久事件里的旧格式兼容（没有偏移的片段、旧格式幂等摘要、旧决定来源）不代表线上协议向后兼容。

版本变化（据 protocol.ts 头注释）
v2拥有者认证（ADR 0003）：连接后首个操作必须是 auth，认证前不返回快照、不执行请求；令牌只经控制面目录的令牌文件或拥有者环境变量传递
v3快照有界化（活动任务 + 每会话近期结束任务，更早的经 list_tasks 分页）；握手返回数据实例标识与执行后端说明；活动与中断任务带输出预览；审批与工具操作经有界参数视图传输；新增历史读取与 request_id 核实接口
v8专用 GitHub 模块退役：github_* 业务接口移除，旧客户端因版本不一致被拒，旧命令只保留静态迁移提示
v9正文按连续显示段发送 UTF-8 增量；新增持久思考阶段、read_task_events 分页与 get_task 快照水位；持久旧事件的累计尾部格式仍可读
v10长期操作授权（agent-direction 工单 10）：批准新增可空的授权 ID 与版本关联，以及新决定来源 standing_permission；新增 standing_permission.* 事件与 service_grant_list / service_grant_get / service_grant_revoke，控制面不获得创建或扩大授权的能力
v11通用 SubAgent 委派（agent-direction 工单 11，ADR 0020）：快照新增 workDelegations、subAgents 与 subAgentSessionIds；新增 work_delegation.created 与 subagent_task.* 事件，只读 op work_list / work_get
v12SubAgent 继续、复用与显式关闭（agent-direction 工单 12）：subAgents 身份另带 closedAt / closedBy；新增 subagent.closed 事件与 op subagent_close（工作委托与工作 / SubAgent 的只读列表照旧）；委派复用经模型工具的 sub_agent_id 参数

头注释只记了这六段变化，其余中间版本没有说明。工作区（open_workspace）、迁移 op 与 list_session_summaries 的 workspace_id 参数是 v9 期间（agent-direction 工单 05–07）加入的，当时没有升协议版本，注释里也没有记录：同为 v9 的旧客户端仍能通过版本检查。
