控制面协议

拥有者的客户端（TUI、CLI、配置中心）与本机后台之间的全部往来：一条 Unix socket 上的换行分帧 JSON。这一页讲清楚连接怎么建、认证怎么做、事件流怎么保证不丢不重、请求失败怎么分类、提交怎么去重，以及两个必须随代码更新的登记处——op 目录与事件目录。

传输与帧

控制面是一个 Unix socket 上的请求/应答加单向推送：客户端发请求帧，服务端回应答帧，后台产生持久事件时向所有已订阅连接推事件帧。房间里的空位只有一个——后台对本机只有这一个入口，没有 TCP 端口，也没有远程协议。

帧的大小口径阈值 / 行为源码锚点
单帧上限MAX_FRAME_BYTES = 1 MiBprotocol.ts · MAX_FRAME_BYTES
请求超限断开该连接（不回应答）server.ts · 行超限断开
应答超限回 response_too_large，请缩小分页范围重试（请求已执行）server.ts · response_too_large
客户端收到超限帧按断线处理：frame_too_large，不再使用该连接client.ts · frame_too_large
版本不匹配回 protocol_version 并说明双方版本（认证前后都先查版本）server.ts · protocol_version
非法 JSON回 bad_frame；客户端收到非法帧则断开server.ts · bad_frame
未知 op回 unknown_opserver.ts · unknown_op
已知限制 · 帧大小口径

服务端按 UTF-16 字符数比较请求行（line.length），客户端按 UTF-8 字节数比较（Buffer.byteLength）。含非 ASCII 的长参数（中文输入约占 3 字节/字）在请求侧可能先被服务端判超限断开，而客户端仍以为在限额内。架构工单 07 已记录该差异及其对提交核实的影响。

请求的 id 由客户端生成（req-1、req-2…）；应答回来后按 id 唤醒等待者，超时之后的迟到应答被静默丢弃，不会串到别的请求上。

认证：先令牌，后一切

socket 文件位于控制面目录，该目录的权限是访问控制的第一道门。连接建立之后，第一个操作必须是 auth；认证成功之前，服务端不返回快照、不执行任何请求。

环节规则源码锚点
生成与复用后台启动时确保控制面目录存在（0770）；令牌缺失则生成 32 字节随机 hex、文件 0600，已存在则复用owner-token.ts · ensureOwnerToken owner-token.ts · TOKEN_FILE_NAME
客户端解析优先级环境变量 → RUUKOTO_OWNER_TOKEN_FILE → 控制面目录的 owner.token；都取不到就抛含修复指引的错误（不发请求）connect.ts · resolveOwnerToken

多用户部署配置步骤把令牌以 0400、属主为拥有者放入其可读位置；控制面目录对拥有者开放连接权限owner-token.ts · 部署约束

握手与事件流：快照、补发、实时

连接建立的最后一步是 connect：它同时完成三件事——读一张有界快照、补发漏掉的事件、把这台连接注册为订阅者。上一页提到的「后台重启」「断线」都靠这一步恢复，而恢复的是观察，不是执行。

客户端后台执行事件存储
connect {since: 上次应对齐的序号}
getMaxSeq() → N；snapshot()（项目/会话/有界任务/未决审批/产物/输出预览/instanceId/执行后端/默认模型）
getEventLog(since, 5001)：读 (since, N] 的补发事件
快照读取与 this.subscribers.add(socket) 在同一个同步段内完成（Node 单线程）。这两步之间没有 await，因此不会出现「快照已经含 seq N、订阅却从 N+1 之后才开始」的缺口。
应答 {seq: N, replay: (since, N] 的事件, snapshot}；此后实时推送自 seq > N 开始
快照就位（客户端）
实时推送 {push:"event", event.seq = N+1, N+2, …}
补发事件按 kind="replay" 应用：只补齐显示记录，不得把最新状态回滚到旧状态；实时事件按 kind="live" 应用，可以改状态。
去重两层：ControlClient 丢弃 seq ≤ lastSeq 的帧；ControlConnection 丢弃 seq ≤ appliedSeq 的重复事件，并只在事件应用之后前进游标。

三条恢复路径都指向同一个动作——重新取快照，而不是重放任务：事件序号出现缺口、invalid_cursor、cursor_too_old。重新同步只替换观察到的最新状态，不发送 resume_queue、不批准任何审批、不继续任何任务。

连接状态机

ControlConnection 把上面那条链路包成五个状态。判断标准只有一条：后台是否明确拒绝。明确拒绝（令牌无效、协议版本不符）才停止；其余一切失败——后台还没起来、建连超时、认证或同步超时、连接中途断开——都只是暂时没连上，按有上限的退避重试。

请求结果分类

界面上「这请求到底做没做」这个问题，在控制面只有四个答案，而且由产生错误的地方写定一次（架构工单 07）。调用方按分类处理，不再各列一份错误码表。

分类含义产生处调用方处理（TUI）
not_sent未发送（已知未执行）连接层拒绝 connection_unavailable、closed、握手前提交、建连失败、参数无法序列化「X 未发送」；提交恢复草稿
rejected后台明确拒绝ok:false 的服务端错误应答「X 失败」；提交清记录并恢复草稿，request_conflict 例外
unknown应答丢失，连接仍在请求超时；应答为 internal_error、response_too_large、mode_switch_unverified当场查询后台状态核实，不重发；提交按原键核实
disconnected应答丢失，已断线terminate() 时的在途请求：socket 关闭/出错、坏帧、超长帧、未换行残留、主动关闭「结果未知，重连后按后台状态显示（未自动重发）」；不发必然失败的查询
不变量 · 写请求应答丢失不换键

任何 unknown / disconnected 的写请求都不自动换新键重发：有幂等键的（提交、工作区入口）按原键核实，确认未接收才以原键原参数重发；其余先查询后台状态，再由拥有者决定。这与 工具调用路径 的「效果未知」是同一条纪律的两个位置——一个针对控制面请求，一个针对工具操作，不要混称。

提交去重：先落盘，再发送

提交（submit / continue）是唯一会真正启动任务的控制面写操作，因此它的幂等键必须比请求本身活得更久：断线、超时、界面重载都不能让同一条输入变成两个任务。

输入与界面提交守护待确认记录（~/.ruukoto/pending）后台
randomId("req") → request_id
save()：临时文件 + rename，0600；含 op、完整参数、数据实例标识、创建时间
落盘失败不得发送：请求根本没发出去，按「未发送」处理（已知未执行）。
submit / continue：原样发送已落盘的参数
应答带任务 ID
clear(request_id)：删除记录
从这一刻起，这条输入由任务的生命周期负责，记录不再存在——它只代表「尚未确认接收」的请求，不是会话历史的副本。

应答丢失时记录留着，进入「接收结果待核实」。核实只问一个问题：后台有没有收到这个 request_id？

同键异参与旧格式：两种不重发的例外

同键异参：后台的幂等键比较含提交原文、访问模式、授权范围、继续来源与模型选择（submissionDigest 为这些字段的 sha256）。同键同参重试返回原任务；同键异参回 request_conflict，客户端不换新键、不重发，展示冲突让人处理。升级前落盘的提交（schema v11 之前）另带一份旧格式摘要参与核对；连旧格式都缺的任务，一律请拥有者用 find_task 核实。

旧格式缺模型：明确未接收、但记录里没有模型选择（早期版本）时不能原样重发——needs_resubmit：把原文恢复进原会话的草稿，让拥有者用 /model 选好再提交。

记录目录：~/.ruukoto/pending/（RUUKOTO_PENDING_DIR 可覆盖），目录 0700、记录文件 0600；损坏的文件保留在磁盘上并单独列出，不静默丢弃。令牌等凭据永不写入这里。

工作区入口的幂等键

ruukoto <路径> 每次启动都带一个稳定的启动请求标识（startupRequestId），它同时是 create_project / create_session 的 request_id。

  • 同键同参（项目 + 规范化目录 + 确认工具集合）返回已存在记录，不重复插入、不产生事件；同键异参回 request_conflict。
  • Project 的幂等键比较项目名；Session 的比较项目、cwdReal 与确认工具集合。
  • 应答丢失且连接仍在：当场核实一次；已断线：重连完成新握手后，先在新快照里按 createRequestId === startupRequestId 找会话，找不到才以同一标识重发。标识只在本次启动内复用，不生成第二个。
  • 目录校验（存在性、realpath、dev/ino、保护根）在写入之前；项目与会话在同一事务，失败不留空项目。

TuiOps：TUI 用到的那一层

TuiOps 是 src/control/ops.ts 里的一张类型表（架构工单 07）：35 个 op 的参数与返回形状只在这里定义一次，返回形状取服务端 Runtime 方法的实际返回类型。真实客户端、demo 合成会话与测试替身都按它实现 ControlTransport，因此「TUI 请求的 op 名与服务端是否认得」「返回形状对不对」在编译期就能对上。服务端 dispatch、CLI 与配置中心仍按字符串调用，不经这张表。

TUI 收到的错误也统一按 RequestOutcome 处理（writeFailure 把四类翻成「未发送 / 失败 / 结果未知」），不再各处列错误码表。

流式输出（本页负责）

正文不是一条消息一条事件，而是按「显示段」持续追加的增量。理解三个字段就够了：contentIndex 是后台分配的连续段序号（不等同 SDK 的块索引），offset 是该段内的 UTF-8 字节偏移，totalBytes 是段内已累计的字节数。

模型流（Driver）事件流客户端
thinking_delta（节流 250ms 一条）
text_delta
task.output_fragment {contentIndex, offset, text, totalBytes}：每段按 offset 拼接，单片不超过 FRAGMENT_TEXT_CAP（8 KiB），节流间隔 FRAGMENT_INTERVAL_MS = 250ms。
thinking_start / thinking_delta：携带最新内容（尾部截断）
toolcall_start / text_end：段边界，冲刷尾块
message_end：冲刷 tail 并结束思考段
message_end 会冲刷所有段：此后该条消息的正文在事件流里已经完整，但最终正文仍以 task.output_entry 关联的 JSONL 为准。
task.output_entry {entryId, sessionFile, messageId}
  • 段序号：正文段由消息内的位置推进（思考、工具调用会结束当前段）；一个 contentIndex 内的片段共享 startedAt，即该段首次产生正文的时间。
  • 思考：task.thinking 带 thinkingId、startedAt / endedAt 与最新文本（尾部有界），客户端据此显示单行滚动的最新部分，结束后原位保留耗时。
  • 最终正文：事件只是实时投影与恢复来源；消息正文经 read_history_entry / task.output_entry 关联的 JSONL 读取。点击工具结果行时经 read_tool_result 读取 JSONL 工具结果与补丁，在事件流内以代码和红绿 diff 展示，再次点击收起。仅返回文本、实际 patch 和对应 Write 原文，不公开其他 details。重连时用 read_task_events 按任务分页补事件，用输出预览补生成中或被中断的尾巴。
  • 兼容：没有 offset 的旧片段按「累计文本尾部」解释。

有界视图：线上载荷不携带完整大参数

持久化层（事件表、确认请求、工具操作）保存完整正文，只有发往客户端的载荷经有界视图转换。

上限取值行为
PARAMS_INLINE_CAP8 KiB（序列化字节）小于上限的参数原样内联；超限替换为结构保留的预览
PARAMS_PREVIEW_STRING_CAP256 字符预览中的单个字符串截断并标注原始字节数
FRAGMENT_TEXT_CAP8 KiB输出增量与思考文本在源头（Driver）就有界（思考取尾部）
SEGMENT_DEFAULT_BYTES / SEGMENT_MAX_BYTES64 KiB / 256 KiB历史、参数、事件分页的默认页大小与单页上限

被替换为预览的参数带 paramsBytes（完整序列化字节数）与 paramsTruncated: true，完整正文经 get_confirmation_params / get_tool_op_params 按 ID 分段读取；任务输出预览同理，state 区分生成中与中断前捕获的部分。

协议版本演进

协议版本写在每一帧的 v 里。服务端只服务与它完全相同的一版：不匹配就回 protocol_version，客户端提示升级而不是静默重试。当前值 PROTOCOL_VERSION = v9。持久事件中的旧格式兼容（缺少偏移的片段、旧格式幂等摘要）不代表线上协议向后兼容。

版本变化
v2拥有者认证：连接建立后首个操作必须是 auth，认证成功前不返回快照、不执行请求；令牌只经控制面目录的令牌文件或拥有者环境变量传递
v3快照有界化（活动任务 + 每会话近期结束任务，更早经 list_tasks 分页）；握手返回数据实例标识与执行后端说明；活动 / 中断任务携带输出预览；确认请求与工具操作经有界参数视图传输；新增历史读取与 request_id 核实接口
v8专用 GitHub 模块退役：github_* 业务接口移除，旧客户端因版本不匹配被拒绝，旧命令只保留静态迁移提示
v9正文按连续显示段发送 UTF-8 增量；新增持久思考阶段、read_task_events 分页与 get_task 快照水位；持久旧事件的累计尾部格式仍可读

源码注释里只有 v2、v3、v8、v9 四段变化记录；这四段之外的中间版本没有留下说明。
