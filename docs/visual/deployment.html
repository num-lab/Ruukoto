边界总图

生产部署把一台机器切成五个嵌套的范围：主机、拥有者账户、后台账户、执行账户、每任务容器；外面是外部网络。后台进程的每一个跨边界动作都只有下面这几条通道，通道之外没有别的路：容器里没有网络，执行账户读不到控制面，容器里也没有数据目录。本图描述服务器生产部署；开发机（ruukoto-dev，macOS/Linux）的受限执行复用同一每任务容器边界——macOS 上容器跑在 Docker Desktop 的 Linux VM 里，宿主路径按原样挂载（agent-direction 工单 03 冒烟 16/16，含孙进程逃逸回收与停止核实）；macOS 内置 sandbox-exec 的文件规则在 macOS 27 静默不执行，不能作为边界（探针见 macos-sbx-probe.sh）。开发机的完全访问同样需要独立的执行账户身份（同 uid 会持有控制面令牌、可冒充拥有者），macOS 上该本机账户与 sudo 包装属部署前置、尚未验证。工单 04 已把验证后的边界接入产品：ruukoto-dev 默认以容器边界执行受限任务（后端缺失或失效时执行前明确拒绝、不回退；local 须显式选择并带无隔离警告），完全访问缺执行账户入口时提交按 execution_unavailable 拒绝；产品级冒烟（代码修改与检查、外网/宿主文件/只读根约束、越界审批、中断回收执行单元，含启动窗口竞争的修复）在 Docker Desktop 与原生 Linux 各 6/6，注册占位后的 03 边界结论与上述部署前提不变。

秘密放在哪，谁读得到

秘密全部落在后台账户自己的两个目录里，执行账户、容器与工具工作进程都拿不到；审批与事件里只出现凭据的名称与用途，不出现值。

秘密位置与权限谁持有怎么用
模型 API key<agentDir>/auth.json，0600，属主后台账户后台进程（ModelRuntime）只用于模型调用；不进命令行、不进工具环境
服务凭据<agentDir>/credentials.json，0600（目录 0700）后台进程（CredentialStore）按名称引用；执行器核对目标 host 与绑定 host 一致后才注入请求头，带 scope 的绑定通用 HTTP 不得借用
拥有者令牌<controlDir>/owner.token，0600，由后台生成（32 字节随机 hex）后台进程；部署时 0400 复制一份给拥有者控制面 auth 的凭据；客户端按环境变量 → 令牌文件 → 控制面目录的顺序解析
各适配器 token不单独存放，一律是 credentials.json 里的绑定各适配器按 purpose 取Telegram telegram_bot（token 拼在 URL 路径里）、QQ qq_onebot（Bearer 头）、GitHub webhook github_webhook（HMAC 秘密）、Web Search tavily_search、MCP mcp
不变量

工具工作进程的环境变量只保留 PATH、HOME、LANG、LC_ALL、TMPDIR；容器额外只给 PATH。凭据值不进入工作进程环境、审批记录、事件与日志，因此「读走凭据」不是工具能做出来的动作，只能经批准的单次 HTTP 请求带着注入的头发出。

两处要记牢的边界

backend 在 docker 组里，成员等于事实上的 root —— 这条边界保护的是「执行账户与任务代码不能冒充拥有者或后台」，不是「后台不能提权」。另外完全访问下容器 uid/gid 常按拥有者设定（原生 Linux 不做 uid 映射），此时容器里的进程和拥有者同 UID：工作区里能读到的东西它都能读，包括同名 UID 可读的令牌副本 —— 所以「把主目录整个当工作区」这种授权在隔离上并不便宜。

三个系统身份，各自能碰什么

拥有者

日常登录账户，用 TUI / CLI / 配置中心经 socket + 令牌连接；持有 0400 的令牌副本与工作区里的文件。不运行后台进程，也不运行工具。

后台 ruukoto-backend

运行控制面，持有数据目录、模型凭据与服务凭据；可调用容器（docker 组）与受保护的提权入口。任务运行期间是唯一能读凭据的身份。

执行账户 ruukoto-exec

完全访问任务的工作进程以它运行。不属于拥有者/后台的组，读不到两者的认证材料，不能改服务代码、配置或容器管理接口。

容器内进程

请求确认与自动审查任务的工作进程，uid/gid 由 RUUKOTO_CONTAINER_UID/GID 固定（默认 1000），非 root、无 capabilities、无网络。

为什么要第三个身份：授权控制面与项目命令必须分别保护，这一点对完全访问同样成立。如果执行身份能读到 CLI 的授权材料，就能冒充拥有者；如果直接用后台账户跑工具，任务读到的就是全部凭据。因此完全访问提供的只是执行账户已有的系统权限，不承诺拥有者账户的全部文件，也不提供账户内部的文件隔离。

保护根：无论怎么授权都排除

runtime.ts · protectedRoots 返回四个 realpath 规范化后的根：数据目录、agent 目录、控制面目录与服务代码目录（CODE_ROOT 由模块位置推出）。它们在三个位置被强制：创建会话时不得作为工作区（runtime.ts · validateGrantedPaths 校验每个授予路径）、申请文件操作时不得作为目标（approved-ops.ts · assertGrantNotProtected 双向排除：既不能在里面，也不能是它们的父级），以及执行已批准的文件操作前再查一次。这也是容器里看不到数据库、凭据与服务代码的原因：能被挂载的路径本来就只能是保护根之外的东西。

编排器的角色工作目录与 QQ 群工作目录因此被放在数据目录的兄弟位置（agent-work/、qq-work/），而不是数据目录里面。

实例锁与配置锁

同一数据目录只允许一个后台，同一 agent 目录只允许一个在线后台或离线配置写入方。锁用 mkdir 的原子性实现：遇到已存在的锁目录，必须读出 owner.json 并核实该 pid 仍然存活、且用 ps 完整命令行确认它确实是本后台；进程已死或 PID 被无关进程回收才接管，无法核实进程身份时保留锁并要求人工处理，不做静默删除。启动时顺带删掉遗留的 socket 文件再重新绑定 —— 实例锁已经保证那不是活着的后台。

一个 systemd 服务里跑整个后台，组件都在同一个进程内，各自只做自己的事。

启动与停止的顺序

cli.ts · runServer 只做三件事：解析参数与执行后端、Runtime.start、然后才 ControlServer.start —— 恢复与所有入口就绪之前，客户端连不上也拿不到快照。产品身份（ruukoto / ruukoto-dev）由 bin 入口经 RUUKOTO_PRODUCT 固定注入：ruukoto-dev 不创建 QQ/Telegram 适配器与调度器，路径环境变量只认 RUUKOTO_DEV_*_DIR（详见存储布局的归属与根目录）。

  1. 建目录（data/、agent/、会话目录，0700）并取实例锁与配置锁；锁冲突时启动失败。
  2. 打开元数据库、核对并登记产品归属（已归属另一产品的目录直接拒绝）、登记 GitHub webhook 签名凭据、创建模型运行时；models.json 里找不到可用模型即以 no_model 失败。
  3. 应用数据空间与调度器各自准备恢复（ruukoto-dev 无调度器，只做应用数据空间）；recover 在一个事务里把遗留的 running / awaiting_confirmation 任务转 interrupted、失效未决审批、标记遗留占用并按原因暂停会话（见任务生命周期）。
  4. 按配置创建 QQ、Telegram 适配器（ruukoto-dev 与 dev 实例跳过）与编排器，依次启动编排器、QQ、Telegram、调度器（仅个人 Agent 产品）。
  5. 需要时打开 webhook 监听（启动失败会先停止整个后台再抛错）。
  6. 写 backend.started（带执行后端与产品身份）后 ControlServer 绑定 socket：先确保 owner.token（缺失则生成 0600，已存在则复用），删掉遗留 socket 文件，监听后把 socket 设为 0660。

停止走 SIGTERM → backend_stop：先停各入口（webhook、调度器、Telegram 轮询、编排器、QQ 适配器），再把 running / awaiting_confirmation 的任务按停止路径中断（排队任务保持排队），释放驱动器、关库、释放两把锁并删除 socket。

ruukoto-dev：没有服务单元，TUI 按需拉起

Coding Agent 一般不装 systemd 单元：第一次打开 TUI 时，tui/index.ts · runTui 在连接前先探测控制面（socket 可连、令牌认证与握手都通过才算在运行；探测令牌与客户端同一来源：环境变量 → 令牌文件 → owner.token，取不到视为未运行），后台不在才经 ensure-backend.ts · ensureBackend 拉起一个 detached + unref 的 server 子进程（默认复用当前入口脚本；npm start 的 TypeScript 入口换用 bin/ruukoto-dev.mjs 固定服务入口）——这是一次正常的后台启动，上面的启动顺序与 重启恢复 规则一条不差。子进程的 stdout/stderr 追加到 <controlDir>/spawn.log，拉起方轮询探测到就绪为止；拉起成功打印一行提示，失败打印错误并以退出码 1 退出（socket 可连但令牌认证不通过＝后台其实在运行，报令牌核对指引、不再拉起；服务进程以非实例锁原因提前退出报「后台启动失败」并附日志尾部；等待超时另行标注且不杀子进程）。

两个终端同时打开会各自拉起一次：实例锁 <dataDir>/runtime.lock 只放行一个后台（instance-lock.ts · InstanceLockError），败者进程退出，拉起侧不误判为启动失败，继续探测并连上胜者，结果仍是恰好一个实例。关闭 TUI 不停止后台、也不取消任务（quit 不发送任何停止请求），重开 TUI 探测到它即复用同一份任务；显式停止用 ruukoto-dev stop——各产品的 stop 只打自己产品的 socket。升级（checkout 换成新代码）之后先 stop，下一次打开 TUI 拉起的即是新代码。

「明确失败」发生在三个时点：提交时（runtime.ts · 执行入口不可用 与切换模式时都先试建启动器），启动工作进程时，以及重建工作进程时。三者都不回退到后台账户执行。

已知限制

直连 systemd-run 的分支只在程序化配置下可达（CLI 不接受 systemd 后端），此时执行账户 uid/gid 默认取到 0，与「固定执行账户」的意图不符；生产请始终经受保护包装入口。另外 systemd 的 Restart=on-failure 默认允许 5 次 / 10 秒，启动失败的后台会重启几次才停在失败态，看日志时不要当成崩溃循环。

开发实例与生产的差别

npm run dev 启动的开发实例是同一份代码的隔离运行：档案固定在仓库外，进程环境在派生前被清洗，因此即使复用同一份数据库也不会连上真实的消息通道。

启动前它会探测控制面：socket 可连且令牌认证通过就报错退出，不接管、不停止外来进程；进程内的实例锁与配置锁同样生效。生命周期上，界面退出或 Ctrl+C（含关终端触发的 SIGHUP）会停后台（SIGTERM，10 s 升级 SIGKILL）、关监听并退出，源码变更则按影响范围只重启后台或只重启界面。

不是同一个东西

开发实例不是 ruukoto-dev 产品：ruukoto-dev 是装在开发机器上的 Coding Agent（ruukoto-dev 命令，档案根 ~/.ruukoto-dev-agent；不装服务单元，后台由 TUI 按需拉起、ruukoto-dev stop 显式停止，见「进程拓扑」），开发实例只是开发本项目用的隔离环境（npm run dev，档案根 ~/.ruukoto-dev，运行的是默认产品 ruukoto 并监听源码重启）。两者的目录、锁与控制面互不相同；新产品不会读写开发实例的档案。

部署与验证

完整步骤在 deploy/systemd/README.md 与 deploy/worker-image/README.md，这里只列顺序与关键约束。

  1. 建三个身份与目录：ruukoto-backend（/var/lib/ruukoto/{data,agent,agent-work} 0700、control 0770）、ruukoto-exec（建议 uid/gid 1002，HOME 0700 且 git config --global --add safe.directory '*'）。
  2. 代码放 /opt/ruukoto（属主 root，后台与执行账户只读，npm ci --omit=dev），再用 esbuild 打包宿主工作进程入口 /opt/ruukoto/worker/worker.mjs（完全访问包装脚本的固定入口）。
  3. 放置 models.json 与 auth.json（0600，属主后台账户）—— 出厂默认模型是第一个 provider 的第一个模型，网络不可达时用 drop-in 指定。
  4. deploy/worker-image/build.sh 构建镜像（可信身份执行，打 ruukoto-worker:<pi 版本> 与 :latest），并把后台账户加入 docker 组（容器管理权限只给可信后台）。
  5. 安装 root 拥有的 /usr/local/libexec/ruukoto/ruukoto-exec-launch 与 -stop（0700）以及 /etc/sudoers.d/ruukoto（0440）。
  6. 安装 ruukoto-backend.service 并 enable --now；执行账户 uid/gid 或容器 uid/gid 与默认不同时用 drop-in 覆盖（RUUKOTO_EXEC_UID/GID、RUUKOTO_CONTAINER_UID/GID）。
  7. 把 control/owner.token 以 0400 复制给拥有者，把拥有者加入 ruukoto-backend 组，再给主目录配穿越 --x（后台与执行账户各一条），并给要用完全访问的工作区配 rwX ACL。
三个容易踩的点

原生 Linux 的 bind mount 不做 uid 映射（Docker Desktop 会），所以容器内进程必须能写任务工作区 —— 单拥有者服务器把容器 uid/gid 设为拥有者值最简单。没配 ACL 的工作区在完全访问下会 EACCES。后台启动时会用到 agent-work 目录，缺失即启动失败。另外镜像里的 git 段：这个仓库的开发机访问不了 apt 源，目标服务器构建时按 Dockerfile 顶部的说明恢复 —— 文件里那段安装已经是启用状态，而 deploy/worker-image/README.md 仍写着「git 未装入」，以 Dockerfile 为准。

验证到了哪一步

两份报告都在 verification/foundation/results/：linux-isolation-report-tx.md（2026-09-21，Ubuntu 24.04 + Docker 29.5.2 原生 Linux）与 linux-isolation-report.md（Docker Desktop 的 Linux VM）。两者都是 32 行探针、逐项一致，判定条件也一致：探针缺失或结果与预期不符即失败，容器引擎不可用按「未验证」退出而不是通过。

验证怎么做的结论
容器边界探针（32 项） bash verification/foundation/scripts/linux-isolation/run-probes.sh；用 python:3.13-slim 镜像跑 plain / restricted / identity 三个变体与一个回环 TCP 对照 宿主路径（/Users、/home、/root/.pi、/var/run/docker.sock）在容器内不可见；环境无凭据；容器内无 pi 配置；mount 被拒；非 root 下容器层写不进去；restricted 变体 CapEff 全零、--network none 无出网；宿主回环端口不可达；真实存在于宿主的秘密文件在容器内不存在；另一 uid 读/写 root 的 0600 状态文件都是 EACCES
真实启动器冒烟 container-worker-smoke.mts 经应用自己的容器启动器与工作进程宿主跑真实路由 非 root、只读根、cap 清零、无外网、宿主绝对路径与只读授予路径按原路径挂载、整容器回收核实；Docker Desktop 9/9，tx 13/13（含同路径挂载新增项，容器 uid 固定为拥有者 1003）
systemd 执行账户入口 tx 上经 sudo 链路跑完全访问任务（含 uid 986 经 env_keep 传递、参数注入与非授权调用拒绝、stop 幂等） 通过：id -un 为 ruukoto-exec、按 ACL 写工作区、读拥有者令牌被拒、结束后单元 inactive（曾修复 exec-stop 包装退出码与启动器约定相反的问题）
未覆盖的部分 探针用的是 python:3.13-slim 与固定 /workspace 挂载，不跑真实镜像，也不含只读根与 tmpfs 项 镜像与 --read-only/tmpfs/同路径挂载由启动器冒烟覆盖；TUI 断开重连、Git worktree 共享 Git 元数据、真实 NapCat 与真实 Tavily 连通均未在目标机验证
