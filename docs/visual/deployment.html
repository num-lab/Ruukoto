两个产品，一份代码

代码库产出两个产品（ADR 0017）：ruukoto 是装在专用 Linux 服务器上的个人 Agent，IM 是主入口；ruukoto-code 是装在开发机上的 Coding Agent，TUI 是主入口。两者跑同一份 src/cli.ts 与同一套运行时，差别全部来自启动时确定的产品身份（product.ts · PRODUCT_TYPES）。

ruukoto（个人 Agent）ruukoto-code（Coding Agent）
入口bin/ruukoto.mjs；服务器上由 systemd 单元直接运行 src/cli.ts serverbin/ruukoto-code.mjs（npm link 或把 bin/ 加入 PATH）
档案根~/.ruukoto（product.ts · productRootDir）；生产部署 /var/lib/ruukoto~/.ruukoto-code（避开开发实例的 ~/.ruukoto-dev）
路径环境变量RUUKOTO_DATA_DIR / AGENT / CONTROL / PENDING（product.ts · dirEnvFor）只读 RUUKOTO_CODE_DATA_DIR 等同名一组，不读对方的变量
默认执行后端local（CLI 默认）；生产单元写定 containercontainer（cli.ts · runServer）
消息入口与调度QQ、Telegram 适配器按各自配置连接（RUUKOTO_DISABLE_QQ / RUUKOTO_DISABLE_TELEGRAM 可停用）；调度器随后台启动强制停用 QQ / Telegram，不创建调度器（runtime.ts · start）
服务管理工具Linux 且部署配置齐备时装配给 main不装配
后台怎样启动systemd（ruukoto-backend.service）或显式 ruukoto server；TUI 只连接打开 TUI 时按需拉起（见下文「按需拉起」）；也可显式 ruukoto-code server

产品身份只有一个来源：环境变量 RUUKOTO_PRODUCT。两个 bin 入口在加载 cli.ts 之前把它写死，外部设置的同名变量被覆盖；systemd 单元不设它，按缺省 ruukoto。取值不在 PRODUCT_TYPES 里时，product.ts · productFromEnv 抛错，cli.ts 在分发任何入口之前以退出码 1 结束，不会用错误的产品碰数据目录。

数据目录的归属登记在核心库 meta 的 product.type（product.ts · PRODUCT_META_KEY）：旧库没有这个键，首次启动按当前产品补记；之后用另一个产品打开同一个数据目录，Runtime.start 在取得锁、打开库之后立刻以 product_mismatch 拒绝并释放两把锁，模型运行时、恢复与各个入口都不会启动（runtime.ts · product_mismatch）。

离线管理命令 legacy-import：把旧 ruukoto 实例迁入新档案，两个方向按产品分流——ruukoto-code legacy-import 迁开发资料（agent-direction 工单 21，ADR 0022），ruukoto legacy-import 迁个人资料到全新实例（工单 22，ADR 0023）；四个子命令 preview / apply / revert / list 不走控制面、各自持目标实例锁运行（cli.ts · runLegacyImport）；机制归入存储布局 · 实例导入与· 个人方向。

同一台机器可以同时装两个产品：档案根与路径变量都分开，所以实例锁、配置锁、control.sock 与 owner.token 各是各的，停一个不影响另一个；stop 只连自己产品的 socket。

共用的令牌变量

RUUKOTO_OWNER_TOKEN / RUUKOTO_OWNER_TOKEN_FILE 两个产品都读，而且优先于各自控制面目录里的 owner.token（connect.ts · resolveOwnerToken）。两个后台各自生成随机令牌，所以在导出了某个产品令牌的 shell 里使用另一个产品会认证失败：后台已在运行时报令牌核对指引；按需拉起时新后台能起来，但探测一直认证不过，60 s 后报等待超时。

信任边界总图

服务器上的生产部署（ruukoto）把一台主机分成五个范围：拥有者账户、后台账户、root、执行账户、每任务容器，外面是外部网络。后台进程的每个跨边界动作只走下图的通道。开发机的情况见「系统身份」与「执行边界」两节。

通道载体与方向准入挡住的失败
控制面 socket Unix socket，客户端 → 后台 目录 0770、socket 0660（server.ts · chmodSync）；任何连接先 auth，令牌常数时间比较（owner-token.ts · tokenMatches），认证前不返回快照、不执行请求 执行账户与容器不在该组、也读不到令牌；同组进程没有令牌同样被拒（unauthorized）
执行包装入口 sudo，后台 → root sudoers 只放行后台账户调用三个固定入口（NOPASSWD）；两个执行包装只接受任务 id / ruukoto-exec-* 单元名，否则 exit 64；env_keep 额外保留 RUUKOTO_EXEC_UID / GID 执行账户不能调用；附加选项、改单元名、多给参数都被拒

工作进程帧协议 换行分帧 JSON over stdin/stdout，双向；容器经 docker run -i、完全访问经 systemd-run --pipe 透传 单帧上限 MAX_FRAME_BYTES 4 MiB，正文分块 DATA_CHUNK_BYTES 512 KiB；工作进程只接受 init / tool_call / abort / shutdown，只执行 WORKER_TOOL_NAMES 里的 read / edit / write / bash，拿不到审批、模式或控制面凭据 超限帧断开并停止整个执行单元；进程退出时在途调用按结果缺失处理（见工具调用路径）

秘密放在哪，谁读得到

秘密的原件都在后台账户自己的目录里（拥有者另持一份 0400 令牌副本），执行账户与容器读不到；local 后端的工具进程就是后台账户，能直接读（见下方「三处要记牢的边界」）。审批与事件里只出现凭据的名称与用途，不出现值。

秘密位置与权限谁持有怎么用
模型 API key<agentDir>/auth.json，0600，属主后台账户；models.json 里 provider 的 apiKey 与 headers 值同样是秘密（model-config.ts · isSecretKey），部署时同为 0600后台进程（模型运行时）只用于模型调用；不进命令行、不进工具环境
服务凭据<agentDir>/credentials.json，0600（目录 0700）后台进程（CredentialStore）按名称引用；执行器核对目标 host 与绑定 host 一致后才注入请求头；带 scope 的绑定通用 HTTP 不得借用（credentials.ts · getForUse）
拥有者令牌<controlDir>/owner.token，0600，后台生成（32 字节随机 hex）后台进程；部署时 0400 复制一份给拥有者控制面 auth 的凭据；客户端按 RUUKOTO_OWNER_TOKEN → RUUKOTO_OWNER_TOKEN_FILE → 控制面目录的 owner.token 解析
各适配器 token不单独存放，都是 credentials.json 里的绑定各适配器按 purpose 取Telegram telegram_bot（拼在 URL 路径里）、QQ qq_onebot（Bearer 头）、GitHub webhook github_webhook（HMAC 秘密）、Web Search tavily_search、MCP mcp
不变量

工具工作进程的环境里没有秘密：local 工作进程的环境只保留 PATH、HOME、LANG、LC_ALL、TMPDIR（launchers.ts · filteredEnv）；容器启动器只传 PATH；完全访问经 sudo 重置环境，单元环境由 systemd 设定，包装脚本不带入调用方环境。凭据值不进入工作进程环境、审批记录、事件与日志；在容器与执行账户里，「读走凭据」不是工具能做出来的动作，只能经批准的单次 HTTP 请求带着注入的头发出。local 后端例外：工具进程与后台同账户，bash 能直接读 agent/ 下的文件。

保护根：无论怎么授权都排除

runtime.ts · protectedRoots 返回四个 realpath 规范化后的根：数据目录、agent 目录、控制面目录与服务代码目录（CODE_ROOT 由模块位置推出，生产即 /opt/ruukoto）。approved-ops.ts · assertGrantNotProtected 做双向排除，路径既不能在保护根里，也不能是保护根的祖先。它用在打开工作区（runtime.ts · resolveUsableDir）、登记授予路径（runtime.ts · validateGrantedPaths）和钉定 SubAgent 只读根（subagents.ts）三处。执行已批准的文件操作之前另做单向检查（assertNotProtected）：目标是文件，只需排除落在保护根内。

为什么没有例外：容器能看到的宿主路径只有工作区、授予路径与只读根三类，三类都要过双向检查，所以数据库、凭据、令牌与服务代码不会被挂进任何容器；祖先方向也要排除，否则把 / 或 /var/lib 授出去就等于把整棵子树挂进去。批准、完全访问与资料授权都不改变这组根。也因为这条规则，编排器的角色工作目录与 QQ 群工作目录（旧架构的现行实现）、SubAgent 工作目录都放在数据目录的兄弟位置（agent-work/、qq-work/），而不是数据目录里面。

三处要记牢的边界

ruukoto-backend 在 docker 组里，组成员等于事实上的 root：这套边界保护的是「执行账户与任务代码不能冒充拥有者或后台」，不是「后台不能提权」。容器 uid 常按拥有者设定（原生 Linux 不做 uid 映射），此时容器里的进程与拥有者同 UID，挂进来的工作区里拥有者能读的东西它都能读，「把主目录整个当工作区」在隔离上并不便宜。local 执行后端下工具进程就是后台账户本身，保护根只约束工作区与批准路径，挡不住 bash 直接读后台文件。

系统身份，各自能碰什么

拥有者

日常登录账户，用 TUI / CLI / 配置中心经 socket + 令牌连接；持有 0400 的令牌副本、工作区与待核实提交。不运行后台，也不运行工具。

后台 ruukoto-backend

运行控制面与全部宿主组件，持有数据目录、模型凭据与服务凭据；是 docker 组成员，可经 sudo 调用三个固定入口。任务运行期间唯一能读凭据的身份。

执行账户 ruukoto-exec

完全访问任务的工作进程以它运行（单元默认 uid/gid 1002，可用 drop-in 覆盖）。不在拥有者 / 后台的组，读不到两者的认证材料，不能改服务代码、配置或容器管理接口，也没有 sudo / Polkit 权限。

容器内进程

请求确认与自动审查任务的工作进程，uid/gid 取 RUUKOTO_CONTAINER_UID / GID（默认 1000，单拥有者服务器建议设成拥有者），无 capabilities、无网络。非 root 靠这个取值：启动器不拒绝 0。

为什么要第三个身份（ADR 0003 / 0004）：授权控制面与项目命令必须分开保护，完全访问也不例外。执行身份能读到 CLI 的授权材料，就能冒充拥有者；直接用后台账户跑工具，任务就能读到全部凭据。所以完全访问提供的只是执行账户已有的系统权限，不承诺拥有者账户的全部文件，也不提供账户内部的文件隔离。

服务器（ruukoto）开发机（ruukoto-code）

进程拓扑：服务器上的 ruukoto

一个 systemd 服务里跑整个后台，宿主组件都在同一个 node 进程内；真正分出去的是工具工作进程与按需调用的服务 helper。

启动与停止的顺序

cli.ts · runServer 先完成 Runtime.start，再 ControlServer.start：恢复与各入口就绪之前，客户端连不上，也拿不到快照。

  1. cli.ts 先解析产品身份（非法值退出 1）；runServer 校验 --execution（未指定时取 RUUKOTO_EXECUTION_BACKEND，再按产品默认），local 生效时打印无隔离警告；两个 service 变量只设一个则退出 1。
  2. 建 data/、agent/、会话目录（0700），取实例锁 <dataDir>/runtime.lock 与配置锁 <agentDir>/config.lock。锁冲突抛 InstanceLockError，cli.ts 以 INSTANCE_LOCK_EXIT_CODE（42）退出；无法核实持锁进程身份时退出 1 并保留锁。
  3. 打开核心库、核对产品归属（不符即 product_mismatch）、有 webhook 配置时核实其签名凭据并把凭据范围收紧到 github_webhook、创建模型运行时；models.json 里找不到可用模型即 no_model。
  4. 恢复：先打开应用数据空间，调度器做恢复准备（仅 ruukoto），创建 SubAgent 管理器，再由 recover 把遗留的执行中任务转 interrupted、失效未决审批（见任务生命周期）。
  5. 创建并启动编排器，再启动 QQ、Telegram、调度器（QQ、Telegram 适配器在构造 Runtime 时已创建；是否连接看各自配置，ruukoto-code 或 RUUKOTO_DISABLE_QQ=1 / RUUKOTO_DISABLE_TELEGRAM=1 时启动为空操作，不连接、不轮询）；有 webhook 配置时打开监听，失败则先停止整个后台再抛错。
  6. 写 backend.started（带执行后端与产品），然后 ControlServer 绑定 socket：确保 owner.token（缺失则生成 0600，已有则复用），删掉遗留 socket 文件，监听后把 socket 设为 0660。

停止（SIGTERM / SIGINT，或控制面 stop）走同一条路（runtime.ts · doStop）：先停 webhook、调度器、Telegram 轮询、编排器、QQ 适配器，再把 running / awaiting_confirmation 的任务以 backend_stop 中断（排队任务保持排队），释放驱动器、关闭控制面与应用数据查询子进程，写 backend.stopped，关库、释放两把锁、删除 socket。

实例锁与配置锁

同一数据目录只允许一个后台，同一 agent 目录只允许一个在线后台或离线配置写入方。锁用 mkdir 的原子性实现（instance-lock.ts · acquireInstanceLock）：遇到已存在的锁目录，读出 owner.json，核实记录的 pid 仍然存活、并用 ps 的完整命令行确认它像本后台；进程已死、PID 被无关进程回收或 owner.json 缺失才接管，无法核实进程身份时保留锁并要求人工处理。启动时顺带删掉遗留的 socket 文件再重新绑定，实例锁已经保证那不是活着的后台。

一般启动之外的只读探测用 instance-lock.ts · probeLockHolder：不建锁、不接管，只把 owner.json 与存活核对的结果说成「锁持有」「遗留锁」或「无法核实身份」。跨实例导入用它核实源后台已停止（见存储布局 · 实例导入）；它既不是抢锁，也不会因为探测改写锁目录。

已知限制

单元只写了 Restart=on-failure 与 RestartSec=3，没有设置 StartLimitIntervalSec / StartLimitBurst。启动必然失败的后台（如没有可用模型）会每隔 3 s 被重启；这个节奏是否会触发 systemd 的默认启动限速、最终停在失败态，没有在目标机核实。

按需拉起：开发机上的 ruukoto-code 后台

日常 Coding Agent 不装服务单元。打开任务界面（ruukoto-code、ruukoto-code <路径>、--session）时，tui/index.ts · runTui 在连接之前调用 ensure-backend.ts · ensureBackend：后台在就复用，不在才拉起。门控只放行 ruukoto-code（tuiSpawnsBackendOnDemand），并排除有开发重载状态标记的前端；ruukoto 仍由 systemd 或显式 server 管理，TUI 只连接。

npm run code 的后台由开发启动器管理，TUI 只连接，退出界面后整组进程停止（runTui · 开发前端）。下面的拉起与退出规则属于日常入口；开发规则见开发实例。

探测怎样判定「后台在运行」、什么情况下拉起、怎样轮询到就绪、各时限（首次探测、轮询间隔、退出宽限、总截止）与报错分类，归控制面协议 · 建连之前讲，本页不重复。和部署相关的只有下面几点：拉起参数是 <入口> server --data-dir … --agent-dir …（ensure-backend.ts · defaultServerArgv），入口默认复用当前脚本，npm start 的 TypeScript 入口换成固定的 bin/ruukoto-code.mjs；环境整份继承 TUI 的环境。不传 --execution，所以执行后端取继承来的 RUUKOTO_EXECUTION_BACKEND，没设时才是产品默认的 container。子进程输出追加到控制面目录下的 spawn.log。

  • 两个终端同时打开：各自拉起一次，由后台实例锁 <dataDir>/runtime.lock 收敛为一个实例（仲裁细节见控制面协议）。
  • 关闭 TUI：后台是 detached + unref 的子进程，比 TUI 活得久；TUI 退出时不发送 stop、不取消任务。重开 TUI 探测到它即复用同一份任务。运行中断线只重连观察，不会再拉起后台。
  • 显式停止：ruukoto-code stop 走控制面 stop，后台按上一节的停止顺序收尾。升级（替换检出）后先 stop，下一次打开 TUI 拉起的就是新代码。
  • 拉起即正常启动：上一节的启动顺序与重启恢复规则一条不差；拉起与重连都不构成重新执行的授权。

「明确失败」发生在哪一步

  • 完全访问：提交与切换模式时都先试建启动器（runtime.ts · 执行入口不可用）。没设 RUUKOTO_EXEC_LAUNCH_SCRIPT / STOP_SCRIPT 就直接拒绝，任务不创建；设了但脚本文件不存在，要到启动工作进程时才报 execution_unavailable。
  • 请求确认 / 自动审查：容器启动器的构造不会失败，任务照常入队并开始；边界缺失在第一个编码工具启动工作进程时暴露：docker CLI 路径含 / 且不存在报 execution_unavailable（裸命令 docker 找不到的情况见下方限制）；CLI 在但容器起不来（dockerd 不可用、镜像缺失），进程退出不会让等待提前结束，等不到 ready 帧，30 s 后 worker_timeout（host.ts · start）。工具返回「执行环境不可用 …（不回退到其他执行方式）」，命令不执行。
  • 重建工作进程：模式或授予集变化时旧单元核实不了退出，报 mode_switch_unverified，拒绝建立新环境。

三种情况都不回退到后台账户执行。

开发机：受限与完全访问

ADR 0017 要求 ruukoto-code 在 macOS 与 Linux 上都有技术约束的受限模式，缺边界时不静默降级。工单 03 先验证可行方式，工单 04 把它接成产品默认：受限任务复用服务器同一套每任务容器启动器，ruukoto-code 的默认执行后端就是 container。

原生替换的第一阶段尚未通过，未接入 WorkerLauncher。2026-10-08 的规范化路径更正撤回了旧探针对 Seatbelt 文件机制的否决；新的进程组策略与临时 launchd job 均未停止逃离进程组的后代，tx 的 bubblewrap 在 namespace 建立时被拒。脚本、有效对照与具体限制见原生探针说明，候选失败不能替代完整验收。

  • macOS 受限：容器跑在 Docker Desktop 的 Linux VM 里，宿主路径按原样挂载；容器 uid 1000 写挂载的工作区不受宿主权限位约束（VM 代管）。前提是装好并运行 Docker Desktop、工作区在它的文件共享范围内、镜像由可信身份用 build.sh 构建。工单 03 的冒烟 16/16（含逃逸孙进程的回收与停止核实），sandbox-exec 的探针见 macos-sbx-probe.sh。
  • Linux 开发机受限：原生 docker，bind mount 不做 uid 映射，要用 RUUKOTO_CONTAINER_UID / GID 把容器 uid 设成能写工作区的值（通常是拥有者）。
  • 完全访问：必须是独立的执行账户。同 uid 的进程能读 ~/.ruukoto-code/control/owner.token，等于持有控制面拥有者身份。仓库里的包装脚本调用 /usr/bin/systemd-run，只适用于 Linux；macOS 尚未提供经过验证的本机执行账户入口，不能直接使用这套 Linux 包装。没有设置 RUUKOTO_EXEC_LAUNCH_SCRIPT / STOP_SCRIPT 时，提交即 execution_unavailable。
  • Linux 完全访问复验：本次在 tx 上用 ruukoto-code 的真实 Runtime，经临时 root 固定包装与 sudoers 运行当前 worker：uid:gid=986:986，修前检查失败、修后通过，读取后台 owner.token 与核心库被拒；模型为桩，日常实例不参与（release-24-linux-full-access.mts）。该临时入口在演练后清理，新部署仍需配置自己的执行账户与固定入口。
  • 产品级验证：工单 04 的冒烟（代码修改与检查、外网 / 宿主文件 / 只读根约束、越界审批单次消费、完全访问缺入口拒绝、中断回收容器含启动窗口）在 Docker Desktop 与原生 Linux 各 6/6，见 04-desktop-execution.md。
已知限制

当前 ToolWorkerHost.start 在 ready 失败时丢弃停止失败的返回值，starting 占位再把启动失败返回为已回收；stop 首次返回 false 后会因句柄已置空而在第二次返回 true。worktree 临时执行入口忽略停止失败且未登记受管单元（createWorktreeInContainer）。这些分支仍待停止核实工单修正。local 的 killProcessGroup 只检查主 PID，不能证明组内或脱离进程组的后代全部退出。

直连 systemd-run 的分支只在程序化配置下可达（CLI 不接受 systemd 后端），此时执行账户 uid/gid 缺省取到 0，与「固定执行账户」的意图不符；生产始终经受保护包装入口。另外 docker CLI 默认是裸命令 docker（RUUKOTO_DOCKER_PATH 可改）：它不在 PATH 上时，容器启动器 spawn 出的子进程会发出 error 事件，而启动器没有监听它，后台进程也没有注册 uncaughtException 兜底。按 Node 的语义（单独用 Node 24 验证过），未监听的 error 会让后台进程以退出码 1 结束，而不是报 execution_unavailable。这一点没有在产品里复现。

受控服务 helper：服务器服务管理的唯一通道

main 的 service_inspect / service_manage（ADR 0019）只经 root 拥有的 helper 触达 systemd。装配要三个条件同时成立：产品是 ruukoto、平台是 Linux、RUUKOTO_SERVICE_HELPER 与 RUUKOTO_SERVICE_POLICY 都已注入（runtime.ts · 构造）；缺一个就不装配，不是静默放行。只有 main 拿到这两个工具，main 也不因此获得 bash。模型只给白名单服务名与固定动作，本机身份、宿主操作 ID、执行身份与策略都由宿主注入。

后台调用 helper 的方式固定（service-tools.ts · callHelper）：sudo -n <helper> <动词> …，结构化 argv、环境只留 PATH、stdin 不接、独立进程组；超时或任务停止时整组 SIGKILL。应答只认 stderr 上唯一一行 RUUKOTO_SERVICE_REPLY 前缀的 JSON（v: 1），stdout / stderr 的全部字节原样存为任务产物（保存失败即不采信结果），模型只看有界视图。不用 fd3，是因为 sudo 默认关闭 fd ≥ 3。三个动词的调用上限：inspect 20 s、restart 150 s、stop-op 15 s。

修订指纹从哪来

  • 策略修订 = services.json 原始字节的 sha256（ruukoto-service.mjs · loadPolicy）。helper 每次调用都重算；后台在批准消费的事务里也读同一文件重算比对（文件 0644，后台可读）；保存长期授权时再读一次，与审批范围不符就不保存（im-approvals.ts · servicePolicyRevision）。
  • 单元修订 = 单元 fragment 与全部 drop-in 的路径和内容 sha256（排序后）加上 NeedDaemonReload，再整体取 sha256（computeUnitRevision）。只有 helper 计算，来源文件读不到即 revision_unreadable。
  • 两项修订从 inspect 应答进入审批快照与 service_operation 范围；长期授权行也保存这两项（db.ts · standing_permissions）。之后的任务按 main、来源入口、本机、单元与动作找候选授权，再与本次 inspect 拿到的修订比对，不符的旧授权同事务失效（revision_changed）。改策略文件或改单元文件都会改变修订，让已有批准与授权失效；改了单元没 daemon-reload 时，helper 还会以 reload_required 拒绝执行。

部署件

sudoers 条目

sudoers.d.ruukoto 的同一行里放行后台账户调用三个固定入口：两个执行包装与 /usr/local/libexec/ruukoto/ruukoto-service（root 0700）。执行账户不在其中。

策略与认领目录

/etc/ruukoto/services.json（root 0644）固定本机 machineId、执行 uid/gid、精确单元及允许动作，默认只列测试服务，由拥有者在可信部署流程修改。/var/lib/ruukoto/service-ops（root 0700）存认领标记。

可控测试服务

ruukoto-service-test.service 以执行账户运行 root 拥有的 ruukoto-service-test.sh：Restart=no、无网络、空 capability 集、ProtectSystem=strict 下只放开 /var/lib/ruukoto-service-test 可写（另有私有 /tmp）。脚本每次启动记一行 InvocationID 并递增计数后常驻；这个文件执行账户可写，只作辅助观察，systemd 的 InvocationID 才是证据。

后台单元 drop-in

同时注入 RUUKOTO_SERVICE_HELPER（helper 路径）与 RUUKOTO_SERVICE_POLICY（策略路径）；只设一个时后台拒绝启动，都不设则 main 没有服务管理工具。

首期场景与验证边界

开发实例、部署与验证

npm run dev 启动 ruukoto 开发后台，npm run code 启动 ruukoto-code 开发后台并默认打开 TUI；两个入口的 --config 分别打开本产品开发实例的配置中心，均不再接受 --tui（dev.ts · parseDevArgs）。code.ts 调用共享的 dev.ts · runDev，档案固定在仓库外，派生后台前清洗进程环境；即使开发库里保存着 QQ / Telegram 配置，也不会连上消息通道。

npm run code -- <路径> 接受一个已存在的目录，创建或复用工作区并进入新会话；相对路径按 npm 脚本的当前目录解析，路径含空格时加引号，目录与 CLI 命令同名也可使用。路径不能与 --config 同用，dev 不接受路径（parseDevArgs）。开发启动器只在首次 TUI 启动时传入路径，源码重载后恢复原会话和草稿，不重复创建（spawnFrontend）。工作区目录身份与保护根校验沿用日常入口，不新建目标目录（runtime.ts · openWorkspace），详见工作区根目录。

各实例独立运行

两个开发入口的档案、锁、socket 与日常 ~/.ruukoto / ~/.ruukoto-code 分开。code 创建自己的开发档案，不自动迁入 dev 历史，--import-models 只显式复制模型配置。日常 ruukoto-code 退出 TUI 后后台继续运行，开发 npm run code 退出 TUI 后整组进程停止。

部署步骤

完整命令在 deploy/systemd/README.md 与 deploy/worker-image/README.md，这里只列顺序与关键约束。

  1. 建身份与目录：ruukoto-backend（/var/lib/ruukoto/{data,agent,agent-work} 0700、control 0770）与 ruukoto-exec（建议 uid/gid 1002；HOME 0700，并 git config --global --add safe.directory '*'）。
  2. 代码放 /opt/ruukoto（属主 root，npm ci --omit=dev），再用 esbuild 打出宿主工作进程入口 /opt/ruukoto/worker/worker.mjs（执行包装的固定入口）。
  3. 放 models.json 与 auth.json（0600，属主后台账户）；缺失时后台以 no_model 启动失败。
  4. deploy/worker-image/build.sh 构建镜像（可信身份执行，打 ruukoto-worker:<pi 版本> 与 :latest），把后台账户加入 docker 组。Dockerfile 在构建阶段复制 src/agent/tool-worker 与 src/core（worker 经 ../../core/* 引用宿主侧工具与类型），再经 esbuild 打成单文件 worker.mjs——修改这两处任一路径都要重建镜像，运行时容器内见到的才是新代码。
  5. 安装 root 拥有的 ruukoto-exec-launch / -stop（0700）与 /etc/sudoers.d/ruukoto（0440）。
  6. 安装 ruukoto-backend.service 并 enable --now；执行账户或容器 uid/gid 与默认不同时用 drop-in 覆盖。
  7. 把 control/owner.token 以 0400 复制给拥有者，拥有者加入 ruukoto-backend 组；主目录给后台与执行账户各配一条 --x，要用完全访问的工作区配 rwX ACL。
  8. （可选）服务管理：装 helper、策略、认领目录与可控测试服务，再用 drop-in 注入两个 service 变量（见上一节）。

ruukoto-code 不走这些步骤：在开发机检出仓库并装依赖，把 bin/ruukoto-code.mjs 放进 PATH（npm link 或直接加 bin/），装好容器运行时并用 build.sh 构建 ruukoto-worker 镜像，用 ruukoto-code config 配好模型（否则拉起失败并提示 no_model），之后打开 TUI 即可。升级时替换检出，ruukoto-code stop 后重开 TUI。

容易踩的点

原生 Linux 的 bind mount 不做 uid 映射（Docker Desktop 会），容器内进程必须能写任务工作区，单拥有者服务器把容器 uid/gid 设为拥有者最简单。没配 ACL 的工作区在完全访问下会 EACCES。后台启动时要建 agent-work/ 下的角色目录，/var/lib/ruukoto 本身由 root 创建、后台建不了，缺了 agent-work 即启动失败。qq-work/ 已随核心群聊退役不再需要（旧目录保留为归档）。也不要为此把 /var/lib/ruukoto 改归后台账户：服务 helper 逐级核对认领目录 /var/lib/ruukoto/service-ops 的父目录必须属 root、组与他人不可写，否则报 deployment_invalid。镜像的运行阶段通过 apt 安装 git 与 ca-certificates，worktree 创建与汇总使用容器里的 git（Dockerfile · git 安装段）。
