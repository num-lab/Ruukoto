入站事件

Telegram 与 QQ 的消息、调度器的定时唤醒、GitHub 的 PR 事件，都先登记成一条持久的入站事件，再由编排器建任务。本页讲每个来源怎样取外部 ID、核对身份、在什么情况下被拒或跳过，派发与启动前的门怎样决定放行、等待或丢弃，任务结束后怎样登记 owner 回复，以及重启后怎样不换键地接着做。绑定拥有者在私聊里发的整条审批命令是另一条路：同样先落库（类别 event_kind = im_approval），但不派发、不建任务，宿主在一个同步事务里直接处理到终态并回执。

先落库，再建任务

入站事件是外部消息、定时器与其他来源进入编排器的持久记录，存在 inbound_events 表（db.ts · inbound_events）。(source, external_id) 上有唯一约束，就是幂等键：同一条消息无论平台重投几次、恢复路径重提几次，都只落一行、只建一个任务。事件行记下来源、外部 ID、触发者（actor）、目标角色、正文、回复目标与收到时刻；任务建好后回填 task_id。行的类别由宿主在登记时写定为 event_kind（types.ts · InboundEventKind，schema v22 起，旧记录默认 task）：task 是普通任务入站，走下面这张状态机；im_approval 是 IM 审批控制消息，不派发模型任务、登记所在的事务里直接到终态（见 IM 审批控制消息）。类别不能由消息正文或模型参数决定。

登记在 store.ts · registerInboundEvent：INSERT … ON CONFLICT (source, external_id) DO NOTHING，插入成功才发 inbound.registered，键已存在时返回原事件（created = false），不发事件、不建任务。经编排器登记的来源还会校验目标角色有效、source 与 external_id 非空，并把正文截到 orchestrator.ts · INPUT_TEXT_CAP 字符（orchestrator.ts · registerInboundEvent）。登记与派发分开：先提交登记事务，再在编排器的串行链上建任务，两者之间崩溃由启动恢复补上。

转换触发者条件与位置事件
新键 → registered Telegram、QQ 私聊、QQ 群经编排器；调度器到期事务；GitHub 登记事务 插入成功即生效，与调用方的其他写入同一事务（调度运行、GitHub 旧结果的失效标记）。
store.ts · registerInboundEvent		 inbound.registered
已有键 → 原事件 平台重投、恢复重提、Telegram 偏移未推进时的重读 返回已存在的行，状态不变。编排器入口只在 created 时触发派发；QQ 群入口不看 created，照常排一次派发（派发前复读状态，不会重复建任务）。 无
registered 保持 编排器派发 门返回 wait；建任务抛错（后台停止中、会话不存在、提交冲突等）；目标角色尚未引导。事件留在 registered，等下一次派发（见派发与门控）。 无
registered → queued 编排器派发 任务已提交（或按原请求键找回既有任务）后，一个事务里回填 task_id；QQ 群另在同一事务里回填任务的 agent_id 与 source_event_id、关联收件。若回填时任务已经记了结果（崩溃窗口），同一事务里接着定终态。

不变量

没有登记就没有任务：每个入站任务的 source_event_id 都指向一条已提交的事件，建任务用的请求键由事件或收件派生（evt:<事件>、qq:<收件键>、evt:<事件>:main），同键重提由提交幂等返回原任务。已建任务的事件（queued → done / failed）只由编排器写终态：通常在结果事务里，与任务结果、child_task.* 事件和 owner 回复登记一起提交；任务在回填 task_id 之前就已记了结果时（崩溃窗口），由派发的回填事务补写终态，owner 回复早已随那次结果事务登记。还没建任务的事件（registered → failed）另有调度器取消计划与 Runtime 复核 QQ 私聊 / Telegram 入口三处会作废；以上都是 event_kind = task 的普通事件，im_approval 控制消息登记即终态，只有崩溃遗留的 registered 控制事件由派发作废。

各来源的入口

每个来源自己决定外部 ID 怎么取、身份怎么核对、什么消息根本不登记。下表是对照，后面逐个展开。来源取值来自各模块的常量：TELEGRAM_SOURCE、QQ_PRIVATE_SOURCE、QQ_GROUP_SOURCE、GITHUB_SOURCE；调度器的 scheduler 是登记处的字面量（scheduler/runtime.ts · fire）。

source外部 ID身份与范围核对角色与会话入站时固定不登记或跳过
telegram <botId>:<chatId>:<messageId>，botId 是 token 冒号前一段 chat.type 为 private，from.id 与 chat.id 等于配置的 owner，text 是字符串，非转发消息 main 角色会话，请求键 evt:<事件> 回复目标：平台、bot（由收件时捕获的凭据派生）、owner chat、配置版本；原始发送文本另交宿主识别审批命令 不登记，记 telegram.rejected
qq_private <登录账号>:<owner>:<message_id> 连接核实的登录号与事件 self_id 都等于配置；账号在线；friend 私聊、发送者是配置的 owner main 角色会话，evt:<事件> 回复目标：平台、登录账号、owner、配置版本 不登记，不记事件
qq_group 收件键 <account>:<group>:<message_id> 同上的连接与 self_id 核对；群在允许列表；有指向登录号的结构化 at 段 该「登录账号 + 群」的 qq_group 会话，qq:<收件键> 回复目标：群、登录账号、收件时的配置版本；收件原文与引用消息 ID 不触发的消息不登记；超大或过期的登记收件后记 skipped
scheduler 调度运行 ID 没有外部身份；只由到期事务写入，actor 固定为 scheduler main 角色会话，evt:<事件> 无回复目标 计划取消时未派发的事件作废
github delivery ID（小写） 原始字节的 HMAC 签名；仓库 ID 在允许列表；PR 字段逐项校验 main 父任务 evt:<事件>:main 与 coding 子任务 deleg:<父任务>:review 归一化 PR 快照；所选渠道的 owner 目标与配置版本 非 PR 事件与未支持的 action 返回 202 忽略；校验失败返回 4xx

Telegram 私聊

telegram/adapter.ts · poll 用 long polling 调 getUpdates：offset 取持久的 last_update_id + 1，只收 message，长轮询 pollTimeoutSec ?? 25 秒。每条 update 先处理（登记或记拒绝），成功后才在独立事务里推进偏移（setLastUpdateId，只增不减）；推进前先核对当前配置与本轮捕获的仍是同一代次（配置版本与凭据绑定名都未变），否则不写回旧偏移，重投由外部 ID 去重。登记抛错时偏移不动，本轮退出、按退避等待，下一轮平台重投同一批 update，已登记的命中原外部 ID。轮询失败标离线，退避从 1 秒翻倍到 30 秒封顶（adapter.ts · poll），429 按 retry_after。

  • 身份：handleUpdate 依次判定 unsupported_update（不是 message）、not_private、not_owner（from.id 或 chat.id 与配置不符）、non_text。命中任何一条都只记 telegram.rejected，带 update / chat / user id 与原因，不含正文，不建任务；偏移照常推进。转发消息（forward_origin/forward_date）照常登记建任务，但其内容不解释为审批命令（不入 commandText）。登记前还再核对本轮捕获的配置与凭据仍是当前代次，轮换/重绑期间的消息不登记。
  • 登记：外部 ID 由 telegramExternalId 拼成，message_id 只在 bot + chat 内唯一，带上 botId 后换 bot 不会撞键。actor 为 telegram:<user_id>。正文是固定模板（inboundBody）：平台、chat、user、message id、原消息时间，回复某条消息时附被回复消息的摘录（≤ QUOTE_CAP 字符），最后是原文。回复目标按该次轮询捕获的配置与凭据钉版（targetFor，与 QQ 私聊同款），存进事件的 reply_target，不用后来的配置重新包装旧消息；原始发送文本（未加模板与摘录）另作为 commandText 交给宿主，供识别审批命令。
  • 凭据：bot token 只在 CredentialStore，按 purpose telegram_bot 取用（TELEGRAM_CREDENTIAL_PURPOSE）；telegram_config 只存 API 地址、绑定名、owner 的 user_id 与 chat_id、启停、配置版本与偏移。取不到 token 时轮询直接退出、保持未连接。token 位于请求 URL，错误信息写日志与状态前先用该次请求捕获的 token 脱敏（redact），凭据轮换后旧请求的迟到错误也不会泄露旧 token。
  • 派发门与配置变化：Telegram 与 QQ 私聊一样有入站门（gatePrivate）：来源、actor（配置的 owner user_id，不能由 chatId 推断）与收件时钉版的目标及配置版本逐项核对（sameTarget）；不符即以 telegram_target_changed 丢弃，配置未变只是暂时离线则等待恢复。重新配置或启停把偏移归零并重连——凭据内容变化或删除还会先单调递增配置版本（TelegramStore.bumpConfigVersion，重置偏移），平台重投的旧 update 由外部 ID 去重。配置或凭据变化后 Runtime 逐条复核在途事件（reconcileTelegram，与 reconcileQqPrivate 对齐）：registered 的作废，活动任务取消，未消费的 IM 审批授权一并失效。

QQ 私聊

QQ 私聊与群聊共用一条 NapCat OneBot v11 正向 WebSocket 连接（onebot.ts · OneBotClient）。连接打开后并行调 get_login_info 与 get_status，之后每 probeIntervalMs ?? 30_000 毫秒再探一次；心跳事件的 status 也参与判断。拿到有效登录号、且状态同时是 online 与 good（isOnlineStatus）才算在线；WebSocket 还连着、账号离线时同样算不在线。

  • 公共核对（qq/adapter.ts · handleEvent，私聊与群聊都走）：适配器已启动、QQ 入口已启用、连接在线、连接核实的登录号等于配置的 self_id、连接代次仍是当前配置、事件 self_id 等于配置。连接代次由连接键决定（connectionKey：端点、凭据名与值、登录号、配置版本）——任何配置或凭据变化都要求重建连接，旧连接上的事件不再接纳。任何一条不满足，事件直接丢弃。
  • 私聊接纳（handlePrivateMessage）：私聊入口可用（配了 owner、取得到 token）；sub_type 为 friend，发送者等于配置的 owner 且不是登录号本身，没有 group_id，sender 与 user_id 一致；消息段只能是 text 与 reply，出现其他段整条忽略；拼出的文本非空且不超过 MAX_INBOUND_TEXT_CHARS 字符。不满足的一律静默忽略，不记事件。引用只记被回复消息的 ID，不读原文；拼出的原始发送文本另作为 commandText 交给宿主（引用内容不进这个字段），供识别审批命令。
  • 入站时固定：外部 ID 由 qqPrivateExternalId 拼成，actor 为 qq_private:<owner>，回复目标取接收那一刻的 target()：平台 qq_private、登录账号、owner、配置版本，存进事件的 reply_target。之后派发、任务启动与 owner 回复都拿它与当前配置逐字段比对（两平台共用 notify-target.ts · sameTarget），配置换了就不改发给新目标。
接收不是投递确认

QQ 私聊登记失败（编排器未就绪、后台正在停止）只记诊断日志，这条消息不会重试。连接断开或账号离线再恢复时，适配器记一条 qq.receive_gap，带离线的起止时刻；这段时间的私聊与群消息都不补抓、不假定平台会重投。Telegram 靠持久偏移让平台重投，没有这类缺口。

QQ 群

群消息先登记到 QQ 自己的收件表 qq_inbox（db.ts · qq_inbox），再登记 qq_group 入站事件。收件是群入口的宿主记录：会话、原文、发言人、配置版本都从这里取，入站事件和派发时的核对都以它为准。

  • 触发（handleGroupMessage）：群号、发言人、消息 ID 齐全；发言人不是登录号（自身消息与 message_sent 回声不触发）；群在允许列表；消息是结构化段数组，只含 at、text、reply，出现图片、语音、转发等任何其他段整条忽略；必须有一个 at 段的 qq 等于登录号，不按显示名或正文里的 @ 字符匹配；去掉首尾空白后文本非空。
  • 收件键与原文：qqDedupKey 拼成 account:group:message_id，请求键固定为 qq: 加收件键（qq/store.ts · registerInbox）。任务输入以消息标记 qqMessageTag 开头，接发言人与正文；被引用的消息只有在本群收件里、且没被撤回时才附上前 QUOTE_TEXT_CAP 个字符，并记下引用消息 ID。
  • 超大与过期：正文超过 MAX_INBOUND_TEXT_CHARS 字符，或消息时间早于排队有效期（配置里固定 queueTtlMs: 300_000 毫秒，不能经配置修改），照样登记收件，随即记 skipped，不登记入站事件。这样断线期间积压、重连后被重投的旧消息有明确结局。
  • 会话：首次触发时建项目 qq-<账号>-<群>、数据目录旁 qq-work/ 下的专用空目录和 qq_group 类别会话（ensureGroupSession），不同群互相隔离。群会话的角色能力归编排器。
  • 撤回（handleRecall）：group_recall 通知按收件键条件标记 recalled（未登记或已标记的不处理，撤回事件丢失时不宣称已知撤回）。该消息与引用它的消息里尚未完成的收件：未结束的任务取消，已登记在途的群回复记 unknown、收件记 reply_unknown；随后触发一次派发，还没建任务的事件在门上以 qq_recalled 丢弃。撤回的消息在之后的模型调用前从上下文视图移出，不改写历史（见上下文组装）。

收件状态（qq/store.ts · QqInboxStatus）记的是「这条群消息最后怎样了」，包括回复发没发出去；群回复的发送账本 qq_outbox 见通知 outbox。

收件状态含义谁写、什么时候
registered已登记，还没关联任务登记收件时；入队失败时保持
queued已关联任务派发的回填事务，只从 registered 转入（qq/store.ts · linkInboxTask）
done回复已发出send_group_msg 回执带有效 message_id，群回复记为 sent（sendReply）
reply_failed回复明确没发出平台明确失败；没有入站事件的旧收件在发送时未连接。任务完成但读不到回答文本时也会先写这个值，随即被第二次 sendReply 覆盖为 skipped（见下）
reply_unknown回复结果不明动作超时、断线或回执无效；撤回、停用或移出群时回复在途；启动时遗留 pending（reconcilePendingOutboxOnBoot）；平台在别处定态后才返回
skipped不回复超大或过期；门丢弃；任务以 failed、canceled、interrupted 结束；发送前复核不通过（不在线、停用、账号或群变化、撤回、收件已不是 queued）；读不到回答文本（见下）；恢复时配置已不允许该群
收件状态写入不带条件

setInboxStatus 直接覆盖（linkInboxTask 与启动核对里的更新另带起点条件）。群任务完成时 task.completed 与随后的 child_task.completed 各触发一次 sendReply，已登记群回复的第二次直接返回；但第一次若因读不到回答文本记了 reply_failed、没有登记群回复，第二次看到收件已不是 queued，会改记 skipped。

调度器 wake_main

wake_main 计划到期时，scheduler/runtime.ts · fire 在一个事务里建调度运行、推进下一时刻，并直接用 Store 登记入站事件：source scheduler、外部 ID 为运行 ID、actor 为 scheduler、目标 main，正文是宿主模板（计划 ID、原定时间、延迟与合并区间、触发说明、来源引用，末行声明本次唤醒不继承外发授权，wakeBody）。本轮扫描登记过新事件就请编排器派发。这类事件没有派发门，也没有回复目标；计划取消时，还是 registered 的事件作废为 failed，已建的任务仍在排队则取消。调度运行本身怎样合并漏过的周期见通知 outbox。

GitHub webhook

webhook.ts · receive 只接受 POST /github/webhook，默认监听 127.0.0.1。它先查请求头（签名格式、UUID 形式的 delivery ID、事件名、JSON 且无压缩、Content-Length），读正文时超过 GITHUB_WEBHOOK_MAX_BYTES（1 MiB）即 413，再对原始字节验 HMAC-SHA256（verifyGitHubSignature，等长常量时间比较）。签名通过后：ping 回 200；非 pull_request 事件、不在 GITHUB_PR_ACTIONS 里的 action 回 202 忽略；PR 字段归一化失败回 400，仓库 ID 不在允许列表回 403。

  • 登记（events.ts · register）：先再核一次仓库在允许列表，再在一个事务里登记 source github、外部 ID 为小写 delivery ID、actor 为 PR 发送者、目标 main 的事件，正文是归一化 JSON 快照（PR body 只存前 4000 字符并标记截断，不经 INPUT_TEXT_CAP），回复目标取所选 notifyChannel 当时的 owner 目标。首次登记时，同一事务里给同一 PR 修订或状态已变的旧事件结果写 staleReason，并取消它们未发送的通知。
  • 应答：首次登记 202，重复 delivery 200，登记失败或后台停止中 503。应答不等模型与任务：派发放到下一轮事件循环（setImmediate）。父子任务的编排、只读工具与通知见编排器。

派发与门控

派发在编排器的串行链上做：新登记和外部的补派请求（orchestrator.ts · dispatchRegisteredEvents）排进同一条链；启动恢复不经这条链，但它在各入口开始接收之前跑完。都按 received_at, rowid 的顺序逐条处理 registered 事件（store.ts · listInboundByStatus），不会并发重提同一条。入站任务一律用宿主固定的 confirm 模式（ADR 0011）：dispatchEvent 的三条建任务路径都显式传 accessMode: "confirm"，不继承会话默认模式；拥有者把 main 会话默认设为完全访问后，入站任务照样在需要审批的操作处停下。

各来源的门

inboundGate 按来源分派：qq_group 交 gateGroup，github 交 events.ts · gate，telegram 交 telegramGate（适配器的 gatePrivate），其余交 qqPrivateGate，它对非 qq_private 来源直接放行。QQ 适配器不存在（dev 实例停用 QQ）时两个 QQ 门都返回 wait；Telegram 适配器未启动时 Telegram 门以 telegram_unavailable 丢弃。QQ 门的丢弃原因以代码前缀开头、后接说明，GitHub 门直接写说明；原因写进 inbound.skipped 或任务的 error_message。

门说「等」之后谁来重试

保持 registered 的事件

  • 调度器每轮扫描发现还有 registered 的普通任务事件时（hasUndispatched 只数 event_kind = 'task'，所有来源都算，IM 审批控制消息不算），按 SCHEDULER_LIMITS.redispatchMs（30 秒）的间隔补派。
  • QQ 连接恢复在线、收到撤回、配置变化后，适配器请编排器派发一次。
  • 任何新登记都会排一次派发，顺带处理积压的事件；后台启动时编排器先重提一遍。

留在 queued 的任务

  • QQ 适配器每 sweepIntervalMs ?? 15_000 毫秒唤醒所有群会话与 main 会话，过期的在门上丢弃，恢复在线的开始执行。
  • QQ 连接恢复在线、配置变化时同样唤醒；私聊授权复核后唤醒 main。
  • 其余唤醒（新提交、占用释放）照常触发一次调度循环。

启动前的 drop 有两种落法：来源门判定丢弃时调用 runtime.ts · cancelTask，任务从 queued 取消、原因写进 error_message；群会话门判定丢弃时，调度循环自己条件更新 queued → canceled 并记 task.canceled。两种都随后由编排器回传结果，事件转 failed。

IM 审批控制消息（event_kind = im_approval）

绑定拥有者在 QQ 私聊或 Telegram 私聊里发的整条文本命令，由宿主模块 im-approvals.ts · ImApprovals 直接处理（agent-direction issue 08），两个平台同一套命令：/approvals [页码]、/approval <审批ID> [偏移]、/approve <审批ID> <权限版本>、/reject <审批ID> <权限版本>；issue 10 增加长期授权命令：/approve-standing <审批ID> <权限版本>、/service-grants [页码]、/service-grant <授权ID> [偏移]、/revoke-service-grant <授权ID> <版本>。解析只认完整匹配（parseImApprovalCommand），输入是适配器提交的原始发送文本（commandText，正文模板与引用摘录之前的原文）：命令动词已出现但参数不合法时宿主直接回用法说明，不交给模型；自然语言、引用中的命令、转发内容、群消息与模型输出都不会被解释为批准，照常走普通入站。宿主入口是 runtime.ts · registerImInbound：整条匹配即进审批路径，其余按普通事件登记派发。

收件
适配器核身份后提交 externalId、actor、收件时钉版的 replyTarget 与原始文本。
整条命令匹配
不匹配走普通入站；匹配则先按幂等键查重，重投读取原记录与原回执。
身份逐项核实
平台 actor 等于当前配置的 owner、当前目标与钉版目标相同（含配置版本）；不符只留控制记录，不执行。
一个同步事务到终态
控制事件 done / failed、审计事件与回执写入同一事务；提交成功后由发送循环按原键送达。
  • 不派发、不排队：控制消息持久化为 event_kind = im_approval 的入站事件（同一 (source, external_id) 幂等键），在处理事务内直接到 done / failed，task_id 恒为 null——不建任务、不调用模型、不经编排器派发，也不排在等待审批的普通任务后面。崩溃遗留仍 registered 的控制事件（正常路径不会产生）由派发明确作废：inbound.skipped 原因 control_event_not_dispatched，不作为普通提示或新的批准重放；补派扫描也只数普通事件（hasUndispatched 只认 event_kind = 'task'）。
  • 归属核实：审批是否可由本命令操作，先从审批的任务沿 parentTaskId 走到根任务、再取它的来源入站事件（imSourceEvent，断链、循环或无来源一律拒绝，不从会话最近消息推断），然后平台、actor 与收件时钉版的目标及配置版本逐项相同才放行（sameTarget）。决定只作用于原请求与原权限版本，不开放新参数或修改范围。
  • 决定与回执同一事务：批准 / 拒绝经活动 Driver 的审批闸门提交（approval-gate.ts · resolve 的 txExtra 挂钩）：决定、审计事件、控制事件终态与回执在同一事务提交，任何一步写失败整笔回滚（决定未记录），等待者在提交之后才唤醒。回执区分已接受（执行前仍复核）、已拒绝与已失效/竞态落败。
  • 回执走公共 outbox：回执是 sourceKind = inbound_event、键 = 控制事件 id 的发送操作，目标是命令收件时钉版的目标；限流只按原键延后，结果未知不换键重发（见 通知 outbox）。同幂等键的平台重投读取原回执、不重复执行；同键异命令或身份不一致记 im_approval.redelivery_rejected，不覆盖既有事实。
  • 分页有界：列表每页 5 条（LIST_PAGE_SIZE）；详情把参数按字节分段（history.ts · sliceTextByBytes），单条回执不超过平台回复上限（QQ 按配置 max_reply_chars、Telegram 4000 字符），看完再决定。
  • 失效纪律：入口停用、重新绑定或凭据内容变化使该平台代次递增，未消费的待决与已批准确认失效并定向解除等待；配置未变只是暂时离线的确认保留。已接受的批准在执行前一刻还有一次消费前复核（见 工具调用路径），身份已变即批准失效、操作按已知未执行记。同一事务内，该入口稳定身份已死的长期授权（issue 10）一并明确失效（entry_changed，递增版本、保留记录），另一平台原本独立的授权不受影响。
  • 长期授权命令（issue 10）：/approve-standing 明确表示「保存持续授权并批准这一次」——只接受当前 pending 的服务 restart 审批，范围完全来自原不可变审批记录（本机/单元/固定 restart/策略与单元修订），模型、子任务消息与自然语言不能创建或扩大；授权创建、当前决定与授权关联、审计事件、控制事件终态与回执在同一事务（同一 txExtra 挂钩），任何一步失败整笔回滚。原 /approve 仍只批准一次，绝不隐式保存长期授权。目录与撤销只核实入口稳定身份（channel/account/chat/actor），可对旧配置代次的记录操作并明确标注入口已失效；使用放行的代次一致性与修订在执行侧每次执行前核实（见 只执行一次）。
不变量

平台身份不会变成任意控制面访问权：命令只能看到并决定「由同一钉版身份委托出去的任务」产生的审批；决定与回执要么同一事务全部提交，要么全部回滚，不存在「已记录决定但回执丢失登记」或「回了执但决定没落实」的中间态（中途写失败时如实回「未记录决定，请重试」）。

任务结束之后

入站任务到达终态后，编排器照常记录结果、写事件终态（见编排器）。在同一个结果事务里，它调用 Runtime 注入的回调：github 来源交 GitHub 模块登记评审摘要通知，其余来源交 runtime.ts · enqueueOwnerReply。owner 回复只对 telegram 与 qq_private 两个来源登记（ADR 0011、0012）；scheduler 与 qq_group 来源直接返回，子任务唤醒与定时唤醒的任务没有私聊来源事件，也就不会自动外发。

目标、正文与跳过

  • 目标：必须是登记该消息的同一 bot / 账号加同一 owner。两个平台一致：拿事件里收件时钉版的回复目标与当前目标逐字段比对（含配置版本），并要求外部 ID 以钉版的 <账号>:<chat>: 前缀开头。升级前登记、没有钉版目标的旧 Telegram 事件无法证明接收时的版本，明确按 target_unavailable 跳过，不拿当前配置重新包装。
  • 正文：completed 时取本任务历史条目里的最终回答（readTaskReplyText：只看该任务最后 20 条历史条目，倒序找第一条有内容的 assistant 条目，不取会话最新一条），为空时发「（无文本输出）」；失败或取消、超时、结果未知只发宿主固定提示，未知时说「被后台重启中断，结果未知」。Telegram 超过 REPLY_CAP 字符截短并注明原长度；QQ 私聊按配置的 max_reply_chars（缺省 maxReplyChars ?? 1500）截短加省略号。
情况结果

跳过判定的原因码见 enqueueOwnerReply。两个平台的比对都含配置版本，所以入站之后、任务结束之前的任何 IM 配置或凭据变化（代次递增）都会让这条消息的回复记 target_changed，不改发给新目标（发送时的目标核对见通知 outbox）。

另外两类回复

QQ 群回复

不走 owner 回复，也不走公共 outbox。QQ 适配器收到群任务的 task.completed 或 chat 的 child_task.completed 后调用 sendReply：已登记过群回复就返回；否则用同一个 gateGroup 与收件状态复核，通过才写 qq_outbox 并调用 send_group_msg，引用原消息，每个任务一条，超长截短不拆分。任务以 failed、canceled、interrupted 结束时不发送，收件记 skipped。账本与结果分类见通知 outbox。

GitHub 评审摘要

只有本事件 coding 子任务结果唤醒出的 main 摘要任务结束时，才以 inbound_event 加事件 ID 登记一次通知，目标是入站时固定的 owner 目标；事件已失效、webhook 停用、入站时没有目标或目标已变化时改记 inbound.skipped（events.ts · terminal）。编排细节见编排器。

重启恢复与停止

崩溃可能落在任何两步之间：登记之后、建任务之前；建任务之后、回填之前；任务结束之后、结果登记之前；群回复登记之后、平台回执之前。恢复不换新键，也不重放外部效果，每个窗口都按原键核实后接着做。后台启动时的相关顺序：

  1. 任务层恢复：running 与 awaiting_confirmation 转 interrupted，见任务生命周期。
  2. 编排器启动（runtime.ts · Runtime.start）。先按 received_at, rowid 的顺序逐条重提仍为 registered 的事件（recoverInbound），经过同样的门，用同样的请求键：任务已在上次提交时落库的，提交幂等返回原任务再回填；回填时发现任务已有结果的，同一事务补写事件终态。这时 QQ 适配器还没启动，仍然有效的 QQ 事件在门上等待（适配器未启动即 wait），留给第 4 步；已经失效的照常丢弃；类别不是 task 的控制事件（正常不会有遗留）一律以 control_event_not_dispatched 作废，不重放。
  3. 编排器补记结果（sweepPendingResults）：重启窗口里已到终态、结果还没写的角色任务走同一个结果事务，owner 回复随之补登；interrupted 一律按结果未知，回复只发固定提示。结果只写一次，已记录结果的任务不会再登记回复。
  4. QQ 适配器启动（startOnce）：遗留 pending 的群回复一律记 unknown，收件记 reply_unknown，不重发；按 created_at, rowid 的顺序（qq/store.ts · listPendingInbox）逐条接管 registered 与 queued 的收件（recoverInbox）：配置已不允许该群的记 skipped，其余按原收件键重新登记入站事件（已有则不变），升级前只有收件、没有事件的旧任务先核实原键原文再补关联；自动恢复暂停的群会话队列；最后连接 NapCat。每次连上都派发一次积压的 QQ 事件；首次连上时还补齐「任务已完成、群回复还没登记」的收件（recoverCompletedInbox，每个进程一次；已有群回复记录的只同步收件状态，从不重发）。
  5. Telegram 开始轮询，从持久偏移继续；停机期间积压的 update 全部处理，重投的命中原外部 ID。
  6. 调度器启动，之后每 30 秒补派仍为 registered 的普通任务事件（控制消息不算未派发）；GitHub webhook 最后开始监听。
同毫秒的平局按登记顺序

入站事件、群收件与会话队列都按「时间，再 rowid」排序（事件按 received_at，群事件的 received_at 就是收件的 created_at；队列见 store.ts · listQueuedTasksFifo）。rowid 随插入递增，所以同一毫秒登记的两条群消息，恢复与执行都保持到达顺序（ADR 0014）。

停止

runtime.ts · doStop 按顺序停入口：GitHub webhook（排空在途的登记回调）→ 调度器 → Telegram（中止长轮询、等循环退出，之后不再写偏移）→ 编排器（停止派发，等当前派发链收尾）→ QQ 适配器（断开连接、等收件链收尾），然后才中断活动任务。停止期间到达的消息：QQ 的登记入口直接拒绝，GitHub 回 503，已登记的事件因提交被拒而保持 registered，留给下次启动。编排器停止后才中断的任务不在本进程回传结果，由下次启动的第 3 步补记，结局为未知。

不补抓

恢复只处理已经落库的记录。没登记上的消息（QQ 断线期间、QQ 私聊登记失败、GitHub 没送达的 webhook）不会被补抓，QQ 的缺口只以 qq.receive_gap 如实记下。群消息收件已登记、入站事件没登记上的，要等下次适配器启动才重提。
