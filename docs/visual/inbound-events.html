入站事件

Telegram 与 QQ 的消息、调度器的定时唤醒、GitHub 的 PR 事件，都先登记成一条持久的入站事件，再由编排器建任务。本页讲每个来源怎样取外部 ID、核对身份、在什么情况下被拒或跳过，派发与启动前的门怎样决定放行、等待或丢弃，任务结束后怎样登记 owner 回复——还有一种把 IM 发起的工作的最终汇报发回同一入口的 owner_reply，以及重启后怎样不换键地接着做。绑定拥有者在私聊里发的整条审批命令是另一条路：同样先落库（类别 event_kind = im_approval），但不派发、不建任务，宿主在一个同步事务里直接处理到终态并回执。

先落库，再建任务

入站事件是外部消息、定时器与其他来源进入编排器的持久记录，存在 inbound_events 表（db.ts · inbound_events）。(source, external_id) 上有唯一约束，就是幂等键：同一条消息无论平台重投几次、恢复路径重提几次，都只落一行、只建一个任务。事件行记下来源、外部 ID、触发者（actor）、目标角色、正文、回复目标与收到时刻；任务建好后回填 task_id。行的类别由宿主在登记时写定为 event_kind（types.ts · InboundEventKind，schema v22 起，旧记录默认 task）：task 是普通任务入站，走下面这张状态机；im_approval 是 IM 审批控制消息，不派发模型任务、登记所在的事务里直接到终态（见 IM 审批控制消息）。类别不能由消息正文或模型参数决定。

登记在 store.ts · registerInboundEvent：INSERT … ON CONFLICT (source, external_id) DO NOTHING，插入成功才发 inbound.registered，键已存在时返回原事件（created = false），不发事件、不建任务。经编排器登记的来源还会校验目标角色有效、source 与 external_id 非空，并把正文截到 orchestrator.ts · INPUT_TEXT_CAP 字符（orchestrator.ts · registerInboundEvent）。登记与派发分开：先提交登记事务，再在编排器的串行链上建任务，两者之间崩溃由启动恢复补上。

新键 → done / failed（im_approval） IM 审批命令（im-approvals.ts · persistTx） 登记、回执与 im_approval.processed 审计事件同一事务；决定类命令还与审批决定同一事务。插入时 status 即终态，task_id 恒为 null。done 表示命令已处理，包括身份不符、版本不符、已失效这些只回执、不执行的情况。failed 只有两种：命令收件时没有钉版目标（只留记录、无回执），或决定事务写失败整笔回滚后另记的失败回执。见IM 审批控制消息。

已有键 → 原事件 平台重投、恢复重提、Telegram 偏移未推进时的重读 返回已存在的行，状态不变。编排器入口只在 created 时触发派发；退役前的 QQ 群入口不看 created，照常排一次派发（派发前复读状态，不会重复建任务；该入口已随退役删除）。IM 审批命令的重投在插入之前就按原键读出原记录（见IM 审批控制消息），不靠这条约束。 无
registered 保持 编排器派发 门返回 wait；建任务抛错（后台停止中、会话不存在、提交冲突等）；目标角色尚未引导。事件留在 registered，等下一次派发（见派发与门控）。 无
registered → queued 编排器派发 任务已提交（或按原请求键找回既有任务）后，一个事务里回填 task_id。若回填时任务已经记了结果（崩溃窗口），同一事务里接着定终态。退役前的 QQ 群路径另在同一事务里关联收件；该路径已删除。

不变量

没有登记就没有任务：每个入站任务的 source_event_id 都指向一条已提交的事件，建任务用的请求键由事件或收件派生（evt:<事件>，退役前的 QQ 群为 qq:<收件键>（归档键，不再有新增），evt:<事件>:main 与评审工作的 sdelegate:<工作>:ghreview-<事件>），同键重提由提交幂等返回原任务。已建任务的事件（queued → done / failed）只由编排器写终态：通常在结果事务里，与任务结果、child_task.* 事件和 owner 回复登记一起提交；任务在回填 task_id 之前就已记了结果时（崩溃窗口），由派发的回填事务补写终态，owner 回复早已随那次结果事务登记。还没建任务的事件（registered → failed）另有调度器取消计划与 Runtime 复核 QQ 私聊 / Telegram 入口三处会作废；以上都是 event_kind = task 的普通事件，im_approval 控制消息登记即终态；万一出现 registered 的控制事件（正常路径不会产生），由派发作废。

Telegram 私聊

telegram/adapter.ts · poll 用 long polling 调 getUpdates：offset 取持久的 last_update_id + 1，只收 message，长轮询 pollTimeoutSec ?? 25 秒。每条 update 先处理（登记或记拒绝），成功后才在独立事务里推进偏移（setLastUpdateId，只增不减）；推进前先核对当前配置与本轮捕获的仍是同一代次（配置版本与凭据绑定名都未变），否则不写回旧偏移，重投由外部 ID 去重。登记抛错时偏移不动，本轮退出、按退避等待，下一轮平台重投同一批 update，已登记的命中原外部 ID。轮询失败标离线，退避从 1 秒翻倍到 30 秒封顶（adapter.ts · poll），平台回应带 retry_after（如 429）时按它等待。

  • 身份：handleUpdate 依次判定 unsupported_update（不是 message）、not_private、not_owner（from.id 或 chat.id 与配置不符）、non_text。命中任何一条都只记 telegram.rejected，带 update / chat / user id 与原因，不含正文，不建任务；偏移照常推进。转发消息（forward_origin/forward_date）照常登记建任务，但其内容不解释为审批命令（不入 commandText）。登记前还再核对本轮捕获的配置与凭据仍是当前代次，轮换/重绑期间的消息不登记。
  • 登记：外部 ID 由 telegramExternalId 拼成，message_id 只在 bot + chat 内唯一，带上 botId 后换 bot 不会撞键。actor 为 telegram:<user_id>。正文是固定模板（inboundBody）：平台、chat、user、message id、原消息时间，回复某条消息时附被回复消息的摘录（≤ QUOTE_CAP 字符），最后是原文。回复目标按该次轮询捕获的配置与凭据钉版（targetFor，与 QQ 私聊同款），存进事件的 reply_target，不用后来的配置重新包装旧消息；原始发送文本（未加模板与摘录）另作为 commandText 交给宿主，供识别审批命令。
  • 凭据：bot token 只在 CredentialStore，按 purpose telegram_bot 取用（TELEGRAM_CREDENTIAL_PURPOSE）；telegram_config 只存 API 地址、绑定名、owner 的 user_id 与 chat_id、启停、配置版本与偏移。取不到 token 时轮询直接退出、保持未连接。token 位于请求 URL，错误信息写日志与状态前先用该次请求捕获的 token 脱敏（redact），凭据轮换后旧请求的迟到错误也不会泄露旧 token。
  • 派发门与配置变化：Telegram 与 QQ 私聊一样有入站门（gatePrivate）：来源、actor（配置的 owner user_id，不能由 chatId 推断）与收件时钉版的目标及配置版本逐项核对（sameTarget）；不符即以 telegram_target_changed 丢弃，配置未变只是暂时离线则等待恢复。配置版本是代次：重新配置递增版本并把偏移归零，启停只递增版本，两者都让适配器重连；凭据同名修改或删除在写入前也单调递增版本并归零偏移（TelegramStore.bumpConfigVersion），平台重投的旧 update 由外部 ID 去重。配置或凭据变化后拥有者 IM 入口表按来源逐条复核在途事件（im-entries.ts · reconcile，QQ 私聊共用同一段）：registered 的作废，活动任务取消，该平台未消费的审批与入口已失效的长期授权一并失效（见IM 审批控制消息）。ruukoto-dev 与设了 RUUKOTO_DISABLE_TELEGRAM=1 的进程（开发实例固定注入）照常创建适配器，但它不轮询、目标为 null，门以 telegram_unavailable 丢弃。

QQ 私聊

QQ 私聊与群聊共用一条 NapCat OneBot v11 正向 WebSocket 连接（onebot.ts · OneBotClient）。连接打开后并行调 get_login_info 与 get_status，之后每 probeIntervalMs ?? 30_000 毫秒再探一次；心跳事件的 status 也参与判断。拿到有效登录号、且状态同时是 online 与 good（isOnlineStatus）才算在线；WebSocket 还连着、账号离线时同样算不在线。

  • 公共核对（qq/adapter.ts · handleEvent，私聊与撤回通知都走）：适配器已启动、QQ 入口已启用、连接在线、连接核实的登录号等于配置的 self_id、连接代次仍是当前配置、事件 self_id 等于配置。连接代次由连接键决定（connectionKey：端点、凭据名与值、登录号、配置版本）——任何配置或凭据变化都要求重建连接，旧连接上的事件不再接纳。任何一条不满足，事件直接丢弃。群消息不在这条核对之后分流：群分支已随退役删除，群消息到达即忽略。
  • 私聊接纳（handlePrivateMessage）：私聊入口可用（配了 owner、取得到 token）；sub_type 为 friend，发送者等于配置的 owner 且不是登录号本身，没有 group_id，sender 与 user_id 一致；消息段只能是 text 与 reply，出现其他段整条忽略；拼出的文本非空且不超过 MAX_INBOUND_TEXT_CHARS 字符。不满足的一律静默忽略，不记事件。引用只记被回复消息的 ID，不读原文；拼出的原始发送文本另作为 commandText 交给宿主（引用内容不进这个字段），供识别审批命令。
  • 入站时固定：外部 ID 由 qqPrivateExternalId 拼成，actor 为 qq_private:<owner>，回复目标取接收那一刻的 target()：平台 qq_private、登录账号、owner、配置版本，存进事件的 reply_target。之后派发、任务启动与 owner 回复都拿它与当前配置逐字段比对（两平台共用 notify-target.ts · sameTarget），配置换了就不改发给新目标。
接收不是投递确认

QQ 私聊登记失败（编排器未就绪、后台正在停止）只记诊断日志，这条消息不会重试。连接断开或账号离线再恢复时，适配器记一条 qq.receive_gap，带离线的起止时刻；这段时间的私聊消息不补抓、不假定平台会重投（群消息退役后直接忽略）。Telegram 靠持久偏移让平台重投，只要平台还保留着这些 update，就没有这类缺口。

QQ 群（已退役）

核心群聊已退役（agent-direction 工单 20，ADR 0017 修订 ADR 0014）：适配器 handleEvent 没有群分支，群消息直接忽略——不登记收件、不建会话、不建任务、不回复，也不逐条记日志。旧群资料保留为只读归档：qq_inbox / qq_outbox / qq_sessions 不再有新增（见 存储布局），可经 ruukoto qq inbox 与 qq outbox 查阅；正式群聊外挂在后续阶段交付。

退役前（旧架构）群消息先登记到 QQ 自己的收件表 qq_inbox（db.ts · qq_inbox），再登记 qq_group 入站事件：收件是群入口的宿主记录，会话、原文、发言人、配置版本都从这里取。升级遗留的非终态行由每次启动的退役收尾（runtime.ts · retireLegacyRoles）按状态幂等地终结，不会重新处理（见 重启恢复）；仍 registered 的旧 qq_group 事件由派发补上作废（见 派发与门控）。

  • 触发、会话与回复链路已删除：原 handleGroupMessage、ensureGroupSession、registerQqGroup、gateGroup、gate、sendReply、recoverInbox、recoverCompletedInbox、cancelInvalidGroupWork、cancelQqWork、onGroupRemoved、reconcilePendingOutboxOnBoot 都不复存在；QqStore 的群写入方法（登记收件、关联任务、绑定会话、建群会话、建待发群回复等）与驱动器的撤回过滤也已删除（agent-direction 工单 23），三张表只剩读取与退役收尾用到的定态方法。归档中的收件键是退役前格式：qqDedupKey 拼成 account:group:message_id，请求键为 qq: 加收件键，记在收件行的 request_id 列。
  • 撤回仍打标记（handleRecall）：group_recall 通知照旧走公共核对，但只做一件事——qq/store.ts · markRecalled 按收件键给已登记的旧收件打 recalled 标记（未登记或已标记的不处理，撤回事件丢失时不宣称已知撤回）。不再取消任务、不补发回复、不再触发派发。标记仍支撑已接收群结果的撤回复核（见 编排器 · 群聊结果）。

收件状态（qq/store.ts · QqInboxStatus）记的是「这条群消息最后怎样了」，包括回复发没发出去；群回复账本 qq_outbox 见 通知 outbox。退役后不再有新收件，registered 与 queued 也不再产生：升级遗留的这两类行由退役收尾一次性清理（queued 且回复在途的记 reply_unknown，其余未终态记 skipped）。下表第三列的退役前写法仅解释归档中已有的行。

收件状态含义谁写、什么时候
registered已登记，还没关联任务退役前：登记收件时，入队失败时保持；升级遗留的一律经退役收尾记 skipped
queued已关联任务退役前：派发的回填事务，只从 registered 转入（写入方法已删除）；遗留行若回复在途记 reply_unknown，否则 skipped
done回复已发出退役前：send_group_msg 回执带有效 message_id，群回复记为 sent
reply_failed回复明确没发出退役前：平台明确失败；旧收件在发送时未连接等
reply_unknown回复结果不明退役收尾把退役时遗留的 pending 群回复定 unknown，对应仍在 queued 的收件记本值；退役前：动作超时、断线或回执无效，撤回或停用时回复在途
skipped不回复退役收尾：剩余未终态收件一律记本值；退役遗留的 qq_group 门丢弃同一事务里也记本值；退役前：超大或过期、门丢弃、任务非正常结束、发送前复核不通过
收件状态写入不带条件

setInboxStatus 直接覆盖（退役收尾里的回复定态另带起点条件 status = 'queued'）。退役收尾依赖这条让重复启动幂等：先把回复在途的收件定 reply_unknown，再对剩余 registered/queued 收件一律记 skipped，已到终态的行一律不动。

调度器 wake_main

wake_main 计划到期时，scheduler/runtime.ts · fire 在一个事务里建调度运行、推进下一时刻，并直接用 Store 登记入站事件：source scheduler、外部 ID 为运行 ID、actor 为 scheduler、目标 main，正文是宿主模板（计划 ID、原定时间、延迟与合并区间、触发说明、来源引用，末行声明本次唤醒不继承外发授权，wakeBody）。本轮扫描登记过新事件就请编排器派发。这类事件在门上总是放行（inboundGate 落到拥有者 IM 入口表的 gate，不是 qq_private / telegram 的来源直接 run），也没有回复目标；计划取消时，还是 registered 的事件作废为 failed，已建的任务仍在排队则取消。调度运行本身怎样合并漏过的周期见通知 outbox。

GitHub webhook

评审本身由宿主固定登记的 SubAgent 完成（见编排器 · GitHub PR 评审编排）。webhook.ts · receive 只接受 POST /github/webhook，默认监听 127.0.0.1。它先查请求头（签名格式、UUID 形式的 delivery ID、事件名、JSON 且无压缩、Content-Length），读正文时超过 GITHUB_WEBHOOK_MAX_BYTES（1 MiB）即 413，再对原始字节验 HMAC-SHA256（verifyGitHubSignature，等长常量时间比较）。签名通过后：ping 回 200；非 pull_request 事件、不在 GITHUB_PR_ACTIONS 里的 action 回 202 忽略；PR 字段归一化失败回 400，仓库 ID 不在允许列表回 403。

  • 登记（events.ts · register）：先再核一次仓库在允许列表，再在一个事务里登记 source github、外部 ID 为小写 delivery ID、actor 为 PR 发送者、目标 main 的事件，正文是归一化 JSON 快照（PR body 只存前 4000 字符并标记截断，不经 INPUT_TEXT_CAP），回复目标取所选 notifyChannel 当时的 owner 目标。首次登记时，同一事务里给同一 PR 修订或状态已变的旧事件结果写 staleReason，并取消它们未发送的通知。
  • 应答：首次登记 202，重复 delivery 200，登记失败或后台停止中 503。应答不等模型与任务：派发放到下一轮事件循环（setImmediate）。父子任务的编排、只读工具与通知见编排器。

派发与门控

派发在编排器的串行链上做：新登记和外部的补派请求（orchestrator.ts · dispatchRegisteredEvents）排进同一条链；启动恢复不经这条链，但它在各入口开始接收之前跑完。都按 received_at, rowid 的顺序逐条处理 registered 事件（store.ts · listInboundByStatus），不会并发重提同一条。入站任务一律用宿主固定的 confirm 模式（ADR 0011）：dispatchEvent 的三条建任务路径都显式传 accessMode: "confirm"，不继承会话默认模式；拥有者把 main 会话默认设为完全访问后，入站任务照样在需要审批的操作处停下（命中长期授权的服务 restart 由宿主核实后放行，见工具调用路径）。

门说「等」之后谁来重试

保持 registered 的事件

  • 调度器每轮扫描发现还有 registered 的普通任务事件时（hasUndispatched 只数 event_kind = 'task'，所有来源都算，IM 审批控制消息不算），按 SCHEDULER_LIMITS.redispatchMs（30 秒）的间隔补派。
  • QQ 连接恢复在线、配置变化后，适配器请编排器派发一次（退役前的撤回促发已随群分支删除）。
  • 新登记的普通任务事件都会排一次派发，顺带处理积压的事件（IM 审批控制消息不触发派发）；后台启动时编排器先重提一遍。

留在 queued 的任务

  • QQ 适配器每 sweepIntervalMs ?? 15_000 毫秒唤醒 main 会话，Telegram 轮询未连上时等待的 main 任务也靠这次唤醒重试（退役前同样唤醒各群会话）。QQ 由启动配置停用的实例（适配器的 start 为空操作）没有这项巡检。
  • QQ 连接恢复在线、配置变化时同样唤醒；私聊授权复核后唤醒 main。
  • 其余唤醒（新提交、占用释放）照常触发一次调度循环。

启动前的 drop 与退役兜底走同一条路：来源门判定丢弃时调用 runtime.ts · cancelTask，任务从 queued 取消、原因写进 error_message；qq_group 会话的退役兜底由调度循环自己条件更新 queued → canceled 并记 task.canceled。两种随后都由编排器回传结果（有来源事件的转 failed）。

IM 审批控制消息

绑定拥有者在 QQ 私聊或 Telegram 私聊里发的整条文本命令不是任务。宿主模块 im-approvals.ts · ImApprovals 直接处理它：查看审批与长期授权，对一条已有审批作出决定，或撤销本入口的长期授权。入口在 runtime.ts · registerImInbound：适配器提交了原始发送文本 commandText 时先交给 handleCommand，返回 null（不是命令）才按普通事件交编排器登记。控制消息同样落在 inbound_events，用同一个 (source, external_id) 幂等键，类别写定为 im_approval，在一个同步事务里直接到 done / failed，task_id 恒为 null：不建任务、不调用模型、不经派发，也不排在等审批的普通任务后面。审批请求怎样登记、批准怎样单次消费、长期授权怎样放行，见工具调用路径。

命令集

解析以 parseImApprovalCommand 为准：去掉首尾空白后，整条必须是「/动词」加至多两个参数。动词对、参数个数或格式不对时解析为 usage，宿主回用法说明，不交给模型；未知动词、命令出现在句中等其余文本返回 null，照常走普通入站。数字参数只收十进制整数，上限 PAGE_ARG_MAX，两种版本参数还要 ≥ 1。审批 ID 与授权 ID 要写全，查不到就按不存在处理。

从收到私聊到作出决定

  • 识别：commandText 是原始发送文本。Telegram 取 message.text，转发消息（forward_origin / forward_date）不提供这个字段；QQ 取全部 text 段拼接，reply 段只留消息 ID。正文模板、被引用消息的摘录、群消息与模型输出都进不了这个字段，所以引用里、转发来的命令不会被执行。
  • 入口身份：命令收件时必须有钉版目标；当前目标（适配器的 target()）与钉版目标 sameTarget，发送者 actor 等于当前配置期望的 owner（各适配器的 expectedActor，经入口表按来源取：入口须启用，QQ 还须绑定了 owner）。适配器已先滤掉非 owner 的消息，这一步拦的是收件之后配置或凭据已经换代的命令。
  • 审批归属：审批必须来自同一钉版身份委托出去的任务。imSourceEvent 从审批所属任务沿 parentTaskId 找到根任务（最多 CHAIN_WALK_LIMIT 层，断链或循环即拒绝），根任务的来源事件必须是 telegram 或 qq_private 的普通任务入站，平台、actor 与钉版目标都与命令相同，不从会话最近消息推断。列表只列通过这项核实的审批；不属于本入口的审批与不存在的审批回同样的 not_found，不给详情。
  • 决定与回执同一事务：决定经活动驱动器的审批闸门提交（approval-gate.ts · resolve）：条件更新 pending → approved / rejected、task.confirmation_resolved，以及作为 txExtra 传入的控制事件终态、回执与审计事件，一起提交，等待者在提交之后才被唤醒。任何一步写失败整笔回滚，决定没有记录；宿主另开事务记一条 failed 控制事件和失败回执，请拥有者恢复后重发（新消息有新的外部 ID）。这条也写不进去时异常抛回适配器：Telegram 不推进偏移、等平台重投，QQ 只记日志。批准回执写明「已接受」，执行前仍要复核，不说操作已成功。
  • 回执怎么发回：回执是一条发送操作，sourceKind = inbound_event，键是控制事件 ID，目标是命令收件时钉版的目标，正文由宿主模板写定，按平台上限截短（QQ 按 max_reply_chars，Telegram 4000 字符）。经 persist 落库的回执（查看、用法、身份不符、各种只回执的结局与失败回执）和撤销成功的回执，提交后宿主立即唤醒发送循环；/approve、/reject、/approve-standing 成功提交的回执随决定事务落库，宿主不另行唤醒，由调度器下一轮扫描末尾的唤醒带起（每轮间隔 tickMs ?? 1_000 毫秒）。发送循环正在跑时唤醒不另起一轮，新回执同样等下一轮。发送前 outbox 核对渠道当前目标与操作目标完全相同，不同即取消（target_changed），不改发到新目标；来源核对只确认控制事件仍带 actor 与相同的钉版目标。所以 identity_failed 的回执在入口已换代时其实发不出去。限流与 effect_unknown 的处理见通知 outbox。
  • 重投：同一 (source, external_id) 再到达时，handleRedelivery 先于身份核实比对原记录的类别、规范命令、actor 与钉版目标：一致就只读原回执（待发的由 outbox 按原键送达，已终态的不重发），不重新执行；不一致记 im_approval.redelivery_rejected，不覆盖原记录。
  • 不派发：补派扫描（hasUndispatched）只数 event_kind = 'task'；万一遗留 registered 的控制事件（正常路径不会产生），派发时以 control_event_not_dispatched 作废，不当作普通提示或新的批准重放。

与审批通知、长期授权的关系

  • 初始通知：IM 来源任务的审批登记时，ImApprovals 在同一事务里给原委托入口登记一条通知（im-approvals.ts · notifyCreated，sourceKind = confirmation，键 im-approval:<审批ID>，目标是原委托收件时钉版的目标），写明审批 ID、权限版本和 /approve、/reject、/approval 的完整命令，服务 restart 审批另附 /approve-standing。发送前审批已决定或失效就不再发。通知发不出去不会让操作获批。
  • 长期授权：/approve-standing 是创建长期授权的唯一入口（handleApproveStanding）。范围全部取自原审批记录，入口取自这条命令；控制事件终态、授权创建、回执与审计事件作为 txExtra，与本次批准、批准与授权的关联在闸门的同一事务里提交。原 /approve 只批准一次，从不顺带保存授权。/service-grants、/service-grant、/revoke-service-grant 按入口的稳定身份（平台、账号、chat、actor）选授权，不看配置代次，所以旧代次建的授权也能查看和撤销，目录里标「入口已失效」；命令本身照样先过当前入口身份核实。撤销与回执同一事务。授权怎样逐次核实后放行、何时失效，见工具调用路径 · 长期操作授权。
  • 失效：入口停用、重新绑定、凭据变化或其他使配置版本递增的改动之后，ImApprovals 的复核（invalidate）让该平台来源的未消费审批失效并解除等待，入口已失效的长期授权记 entry_changed。批准已接受、还没消费时，消费前另有一次固定身份复核（consumeRecheck）。暂时离线不作废；另一平台在共享 main 会话里的审批不受影响。
不变量

平台身份不会变成任意控制面访问权：命令只能看到并决定「由同一钉版身份委托出去的任务」产生的审批，只能查看和撤销本入口建立的长期授权。决定与回执要么同一事务全部提交，要么全部回滚，不存在「决定已记录、回执没登记」或「回执已登记、决定没落实」的中间态；中途写失败时如实回「未记录决定，请重发」。

任务结束之后

入站任务到达终态后，编排器照常记录结果、写事件终态（见编排器）。在同一个结果事务里，它调用 Runtime 注入的回调：github 来源交 GitHub 模块登记评审摘要通知，其余来源交 im-entries.ts · enqueueOwnerReply。owner 回复只对 telegram 与 qq_private 两个来源登记（ADR 0011、0012）；scheduler 与 qq_group 来源直接返回。子任务与唤醒任务没有来源事件，同一条结果事务也就没有 owner 回复可登记；IM 发起的工作的例外是另一条与来源事件无关的链路——收尾的唤醒任务终态时，宿主在唤醒的结果事务内把工作最终汇报登记到发起事件的回复槽（见本节下文）。

目标、正文与跳过

  • 目标：必须是登记该消息的同一 bot / 账号加同一 owner。两个平台一致：拿事件里收件时钉版的回复目标与当前目标逐字段比对（含配置版本），并要求外部 ID 以钉版的 <账号>:<chat>: 前缀开头。升级前登记、没有钉版目标的旧 Telegram 事件无法证明接收时的版本，明确按 target_unavailable 跳过，不拿当前配置重新包装。
  • 正文：completed 时取本任务历史条目里的最终回答（readTaskReplyText：只看该任务最后 20 条历史条目，倒序找第一条有内容的 assistant 条目，不取会话最新一条），为空时发「（无文本输出）」；失败或取消、超时、结果未知只发宿主固定提示，未知时说「被后台重启中断，结果未知」。Telegram 超过 REPLY_CAP 字符截短并注明原长度；QQ 私聊按配置的 max_reply_chars（缺省 maxReplyChars ?? 1500）截短加省略号。

跳过判定的原因码见 im-entries.ts · enqueueReply。两个平台的比对都含配置版本，所以入站之后、任务结束之前的任何 IM 配置或凭据变化（代次递增）都会让这条消息的回复记 target_changed，不改发给新目标（发送时的目标核对见通知 outbox）。

工作最终汇报发回发起入口

IM 私聊发起的工作（通用 SubAgent 委派）完成多个子任务后，最终结果由宿主守着收尾、发回最初那条私聊——拥有者不等在会话边上，也知道这项异步工作有了结论。main 处理该工作子任务结果的唤醒任务（wake:<子任务>，由父级送达在子任务的结果事务之后有界提交，输入尾部附宿主固定的最终汇报说明，见编排器 · 结果怎样回到主 Agent）到达终态时，编排器除了照常记录结果与 child_task.* 之外，在同一结果事务里调用父级送达的 parent-delivery.ts · wakeTerminal。到期判定、发送键与正文由父级送达决定，IM 机制（目标核对、按平台截短、写发送操作）经回调交拥有者 IM 入口表（im-entries.ts · sendWorkReport）。宿主判定全部满足才登记工作最终汇报，模型不能选择不汇报：

  • 唤醒对应的执行属于一项未取消的工作（work_delegations 的取消三列为空）。已取消的工作不汇报：整项取消处理所在轮次已有 owner 回复。
  • 发起事件存在且是 telegram 或 qq_private 的普通任务入站：经工作发起任务（origin_task_id）的 source_event_id 派生（workOriginEvent），不从会话最新回答推断。TUI、定时、群与 GitHub 发起的工作一律不发。
  • 收尾判定两条：该工作没有 queued / running / awaiting_confirmation 的执行任务（listActiveTasksByWork）；且其他每条执行任务的 wake:<执行> 在唤醒会话里已存在并已记录结果（findTaskByRequest）。main 本轮续派会产生活动任务，汇报自然推迟到下一个收尾的唤醒；两条执行并发收尾时，先终态的唤醒看到对方唤醒还没有结果，只有后终态的汇报一次。唤醒任务本身经来源门核实（回报唤醒轮次不允许再委派，见工具调用路径），续派只发生在拥有者与 IM 任务轮次。

另外两类回复

QQ 群回复（已退役）

核心群聊退役后不再产生：qq_group 来源的任务不再建出，owner 回复也不登记；sendReply 与事件监听已删除，旧账本 qq_outbox 为只读归档（账本与结果分类见通知 outbox）。退役前：不走 owner 回复、不走公共 outbox，群任务完成后适配器把回复写进自己的 qq_outbox 再调 send_group_msg，每个任务一条。

GitHub 评审摘要

只有本事件评审 SubAgent 执行任务的结果唤醒出的 main 摘要任务结束时，才以 inbound_event 加事件 ID 登记一次通知，目标是入站时固定的 owner 目标；事件已失效、webhook 停用、入站时没有目标或目标已变化时改记 inbound.skipped（events.ts · terminal）。编排细节见编排器。

重启恢复与停止

崩溃可能落在任何两步之间：登记之后、建任务之前；建任务之后、回填之前；任务结束之后、结果登记之前。恢复不换新键，也不重放外部效果，每个窗口都按原键核实后接着做。后台启动时的相关顺序：

  1. 任务层恢复：running 与 awaiting_confirmation 转 interrupted，见任务生命周期。
  2. 固定角色退役收尾（runtime.ts · retireLegacyRoles，每次启动执行、按状态幂等，一个事务）：遗留 pending 的群回复一律定 unknown（错误注明 core_group_chat_retired，不重发），对应仍在 queued 的收件记 reply_unknown；各旧群会话（qq/store.ts · listGroupSessions）里排队的任务条件更新 queued → canceled（error_message 为 core_group_chat_retired），同一事务发 task.canceled；旧 coding 角色会话里排队的任务同样取消（error_message 为 coding_role_retired:…）；剩余 registered/queued 的收件（qq/store.ts · listPendingInbox）一律记 skipped。运行中的群任务不在此处理：第 1 步的通用恢复已定 interrupted，由编排器启动时的结果巡检补记（见下）。
  3. 编排器启动（runtime.ts · Runtime.start）。先按 received_at, rowid 的顺序逐条重提仍为 registered 的事件（recoverInbound），经过同样的门，用同样的请求键：任务已在上次提交时落库的，提交幂等返回原任务再回填；回填时发现任务已有结果的，同一事务补写事件终态。退役遗留的 qq_group 事件在这一步被入站门固定丢弃（core_group_chat_retired），同一事务作废并发 inbound.skipped，关联的群收件记 skipped、同键未结束的旧群任务随后被取消。这时 QQ 适配器还没启动、Telegram 也还没开始轮询，仍然有效的 QQ 私聊与 Telegram 事件在门上等待（未启动、未在线即 wait），留给第 5 步的 QQ 派发与第 7 步的补派；已经失效的照常丢弃；类别不是 task 的控制事件（正常不会有遗留）一律以 control_event_not_dispatched 作废，不重放。
  4. 编排器补记结果（sweepPendingResults）：重启窗口里已到终态、结果还没写的角色任务走同一个结果事务，owner 回复随之补登，工作最终汇报也在这条事务里按同一条结果补登；运行中的旧群任务由第 1 步定为 interrupted，同样在这里按结果未知补记（child_task.result_unknown）。结果只写一次，已记录结果的任务不会再登记回复或汇报。
  5. QQ 适配器启动（startOnce）：只服务私聊——按配置连接 NapCat、每 15 秒唤醒一次 main 会话；群侧收尾已由第 2 步完成。每次连上都派发一次积压的入站事件（所有来源）。
  6. Telegram 开始轮询（入口启用时），从持久偏移继续；平台仍保留的积压 update 依次处理，重投的命中原外部 ID。轮询上线本身不触发派发，第 3 步留下的 Telegram 事件等下一条新登记、QQ 连上时的那次派发或第 7 步的补派。
  7. 调度器启动（只有 ruukoto 产品创建调度器）。首轮扫描发现仍为 registered 的普通任务事件就补派一次，之后距上次派发满 30 秒（redispatchMs）再补派（控制消息不算未派发）；GitHub webhook 最后开始监听。
同毫秒的平局按登记顺序

入站事件、群收件与会话队列都按「时间，再 rowid」排序（事件按 received_at，群事件的 received_at 就是收件的 created_at；队列见 store.ts · listQueuedTasksFifo）。rowid 随插入递增，所以同一毫秒登记的两条群消息，恢复与执行都保持到达顺序（ADR 0014）。

停止

runtime.ts · doStop 按顺序停入口：GitHub webhook（排空在途的登记回调）→ 调度器 → Telegram（中止长轮询、等循环退出，之后不再写偏移）→ 编排器（停止派发，等当前派发链收尾）→ QQ 适配器（断开连接、等收件链收尾），然后才中断活动任务。停止期间到达的消息：QQ 的登记入口直接拒绝，GitHub 回 503，已登记的事件因提交被拒而保持 registered，留给下次启动。Telegram 的登记入口不看停止标志，在轮询停下之前照常登记：普通消息同样留在 registered，审批命令照常同步处理，回执因调度器已先停而留在 pending，下次启动再发。编排器停止后才中断的任务不在本进程回传结果，由下次启动的第 3 步补记，结局为未知。

不补抓

恢复只处理已经落库的记录。没登记上的消息（QQ 断线期间、QQ 私聊登记失败、GitHub 没送达的 webhook）不会被补抓，QQ 的缺口只以 qq.receive_gap 如实记下；退役后的群消息直接忽略，也不产生任何记录。退役前遗留的未终态群行由启动收尾一次性了结，不再重提为任务。
