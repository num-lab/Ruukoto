跨模块模式

只执行一次

工具操作、审批与 IM 审批命令、长期操作授权、服务操作、通知、群回复、入站事件、控制面提交、应用数据、调度与委派各自实现了同一个模式：先落盘意图，再条件领取或消费，然后只执行一次，结果不明不重发。这一页把各处的键、条件与后果并排放，便于横向对照；每处的细节在对应页面。

同一个模式的四步

① 先落盘意图

执行之前把「要做什么」持久化：工具操作、审批请求、发送操作、收件登记、入站事件写进数据库，控制面客户端的待确认提交写进本地文件。崩溃在这一步之前，什么都还没执行。

② 条件领取或消费

执行前用一次条件更新或唯一键取得资格：状态仍是指定值、版本一致、尚未被消费，或同一个键还没有记录；服务 helper 用一次原子 mkdir。条件更新影响 0 行说明别人抢先了或已失效，放弃执行。

③ 执行一次

拿到资格的一方执行一次。执行内容在落盘或审批时就已固定（审批记录的参数、发送操作的目标与正文、待确认提交的原参数），执行时不按当前状态重新构造。

④ 结果分类

成功、失败照实记；结果无法确认时记「效果未知」或「应答丢失」，不自动换键重发：效果未知由拥有者核实，应答丢失先按原键核实。
不变量

本地能保证的只有一件事：一个逻辑键最多产生一次可能带副作用的执行。远端平台没有幂等支持时，本地无法保证端到端只发生一次——所以未知结果一律交回拥有者，而不是赌一次重发。

工具操作
tool-op-ledger.ts · recordResult		 tool_ops 行，工具调用门在执行前写入执行意图（driver.ts · handleToolCall）；主键是宿主操作 id，与模型的调用 id 分开 按任务当前访问模式放行；需要审批的操作先经审批闸门消费批准，消费成功才执行 停止或重启时，结果缺失的操作按同一个分类器补记：审批全部未消费 → 已知未执行；无写入效果的工具 → 无写入效果；工具族能按宿主操作 id 核实 → 已提交或已知未提交；其余记效果未知（markEffectUnknown）
批准消费
store.ts · consumeApproval		 confirmations 行，登记审批请求时写入，与任务转 awaiting_confirmation 同一事务；主键是审批 id，行上记宿主操作 id、权限版本与参数快照，执行参数只取这份快照 决定是一次条件更新 pending → approved / rejected（store.ts · respondConfirmation）：TUI、IM 命令与自动审查谁先提交谁生效。获批后在同一事务内先复核：工具族复核；IM 来源再核固定身份，当前平台目标与收件时钉版目标逐项相同，含配置版本（consumeRecheck）；关联长期授权的批准重读授权版本与未撤销状态。然后条件更新写 consumed_at：状态为 approved、consumed_at 为空、审批与任务的权限版本都等于预期、任务仍是 running 或 awaiting_confirmation 复核或消费失败 → 批准失效（stale），按已知未执行记。消费即执行开始：停止或重启时已消费、结果缺失的操作，除非工具族能按宿主操作 id 核实，都记效果未知；HTTP 以 Node ClientRequest 的 finish 事件为界（approved-ops.ts），之前的失败（凭据不符、主机解析失败、连接被拒）是已知错误，之后拿不到状态码的超时、连接重置、中止记效果未知（TLS 握手错误可能落在 finish 之后，同样记效果未知），GET/HEAD 除外（无写入效果）；MCP 写与副作用不明工具的超时、连接失败、取消也记效果未知
IM 审批命令
im-approvals.ts · handleCommand		 控制消息落 inbound_events（event_kind = im_approval），沿用 (source, external_id) 唯一；在处理它的同步事务里直接写终态 done / failed，task_id 为 null，不建任务、不派发。回执是 (inbound_event, 控制事件 id) 的发送操作；收件时没有钉版目标的只记一条 failed 控制事件，没有回执（persistNoReceipt） 先按幂等键查原记录，有就按重投处理。新键依次核实：入口身份（平台、actor、钉版目标含配置版本）；审批归属同一入口；审批仍 pending、命令里的权限版本等于审批记录、任务仍 awaiting_confirmation。都通过才交审批闸门 resolve：决定、审计事件、控制事件终态与回执作为 txExtra 同一事务提交；决定的条件更新落空、或已没有活动的等待者，就回执 race_lost。批准只选中原请求与原权限版本 本地一个事务完成，没有决定已写、记录未写的中间态：写失败整笔回滚，另记一条 failed 回执请拥有者重发命令。平台按同键重投只读原记录与原回执，不再执行（handleRedelivery）；同键异命令或身份不一致记 im_approval.redelivery_rejected。回执本身按通知发送的规则送达
长期操作授权
approval-gate.ts · requestStanding		 standing_permissions 行：授权 ID + 行级版本，范围创建后不改。部分唯一索引保证同一 main、同一入口（渠道、账号、chat、actor）、同一目标（本机、单元、动作）至多一条未撤销授权；approval_id 唯一，一条来源审批只能建一次授权（store.ts · createStandingPermission）。创建与这次批准、授权关联、控制事件终态和回执同一事务提交，撞上唯一约束整笔回滚，决定也不记录 授权本身从不被消费。每次使用在一个同步事务里重读授权版本与未撤销状态，逐项比对本次的本机、单元、动作与两项修订，核实任务仍 running、未请求取消、权限版本未变，过一遍与人工路径相同的复核，再为本次宿主操作 id 新建一条已批准记录并照常 consumeApproval；任一不符整笔回滚，回落人工审批。撤销与失效都是条件更新（期望版本 + 未撤销），版本加一、保留记录 撤销先提交，放行事务重读即不符，回落人工。已消费的服务操作一旦记效果未知，同一 main、本机、单元与动作的所有入口有效授权在同一事务里失效（invalidateStandingForTarget，原因 effect_unknown，事件带触发操作 ID），阻止换操作 ID 自动重试；重新建立要拥有者再次 /approve-standing
服务 restart
service-tools.ts · service_manage		 宿主侧：tool_ops 意图 + 一条审批记录（人工决定或长期授权新建），执行参数取自审批快照。helper 侧：以宿主操作 id 命名的认领目录（ruukoto-service.mjs · OPS_DIR），持久保留，只证明已认领、不证明已重启 先在核心库消费批准（消费事务内复核 main 身份与策略修订），再调 helper。helper 先 mkdir 认领执行权，目录已存在即拒绝（already_claimed）；再核对策略与已加载单元修订，才经 systemd-run 派发 systemctl restart（cmdRestart）。两道关卡分别在 sqlite 与文件系统，之间没有跨系统事务 helper 证明还没请求 systemd（launched: false，含已认领、修订不符）→ 已知未执行，但批准已消费，再做要新审批；有退出码就照实记，非零可能已有部分效果。超时、中止、应答不可信或操作 id 不符、原始输出未保全、派发后失败 → 效果未知，不重发，并使同目标长期授权失效
通知发送

群聊回复（已退役 · 只读归档）

SubAgent 委派

串起来：一次服务 restart 过几道单次关卡

上表里 IM 审批命令、批准消费、长期操作授权与服务 restart 四行，在一次 service_manage 调用里首尾相接：IM 命令给出决定，或长期授权代为建一条批准；批准被消费一次；helper 再按宿主操作 id 认领一次。每道关卡各自只放行一次，但它们分在两个系统里：决定、长期授权与消费在核心库的 sqlite 事务内，认领在 root helper 的文件系统上。中间没有跨系统事务，所以派发之后的结论只认 helper 的可信应答，拿不到就记效果未知。审批与长期授权的完整流程见工具调用路径，IM 命令的识别与持久化见入站事件。

这条链上的每道关卡都对应源码里一处条件：决定 respondConfirmation，长期授权 requestStanding，消费 consumeApproval，认领 cmdRestart，效果未知与授权失效 markEffectUnknown。只有 IM 来源的任务有授权候选（standingCandidate）；TUI 提交、调度、GitHub 与子任务消息恒无候选，走人工审批。

三种「没有结果」要分开

这套模式里最容易写错的是把这几件事混成一件。CONTEXT.md 把它们定成不同术语，代码里也是不同的记录与文案。失败落在哪一段，决定了记哪一种。

已知未执行

能证明没有执行：审批被拒绝、取消或失效；获批后复核或消费失败；请求没交出（HTTP 未发出、渠道抛 NotSentError、控制面请求未送出、服务 helper 在请求 systemd 前拒绝）；发送操作在领取前被取消。服务 helper 那一种批准已经消费，再做要新审批。发送操作里可证明未发送的记 failed。只读操作中止另记「无写入效果」，也不算效果未知。要再做一次，由模型或拥有者重新发起；系统自己再试的只有下一节两处。

approval-gate.ts · notExecutedText runtime.ts · NotSentError

效果未知

工具操作已经开始，却无法确认是否产生了效果：停止或重启时已消费批准、结果缺失的操作；写请求交出后的超时、断线、中止；服务 restart 派发后拿不到可信应答。发送操作的 effect_unknown 语义相同、分开记录（旧架构 QQ 群回复记 unknown；核心群聊退役后只剩退役收尾给遗留 pending 定 unknown）。不自动重发，由拥有者核实；能从已提交记录证明时（应用数据回执，调度、委派、群聊结果接收与 SubAgent 登记），以核实结果为准。服务操作记效果未知时，同目标的长期授权随之失效。

types.ts · task.tool_effect_unknown

应答丢失

拥有者经控制面发出的请求已经送出，却拿不到能说明结果的应答：超时、断线，或 internal_error、response_too_large 这类不能说明未执行的错误应答。不换新键重发：提交与工作区入口按原键核实，确认未接收才以原键重发；其余查询后台状态后由拥有者决定。它针对控制面请求，不与工具操作的效果未知混称。

client.ts · UNKNOWN_REPLY_CODES

未知结果不重发是默认规则。系统自己再做一次的只有下面两处，共同点是能证明上一次没有产生写入效果：

例外条件怎样再试
平台限流退回（ADR 0011）渠道抛 scheduler/runtime.ts · RetryLaterError：平台明确限流拒绝、可证明未发送。目前只有 Telegram 渠道在 HTTP 429 时抛出，等待时间取平台的 retry_after发送操作从 sending 退回 pending 并写 not_before（store.ts · release），到时用原目标、原正文、原键再领取；领取期间已请求取消的直接 canceled。其他明确拒绝仍是 failed，超时、5xx 与断线仍是 effect_unknown，都不重发。
控制面同键重发应答丢失后按原键核实，后台没有这条请求（提交：find_task 查不到；工作区入口：客户端状态里没有同一 create_request_id 的会话）以原键和落盘的原参数重发；撞上 request_conflict 先再核实一次，查到就关联。不换新键绕过。

按原键重提不在此列：入站事件补派、子任务唤醒补发、SubAgent 同键重放都用原请求键提交，已有任务就返回它（异参冲突），不会产生第二次执行。IM 审批命令的平台重投也只读原记录，不再执行。

已知限制

平台没有幂等支持时，远端可能已经执行而本地无法确认，这种情况只能由拥有者核实。系统不因为「大概没成功」而重发，也不把结果未知显示成取消成功。
