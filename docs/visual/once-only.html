跨模块模式

只执行一次

工具操作、审批、通知、群回复、入站事件、控制面提交、应用数据、调度与子任务各自实现了同一个模式：先落盘意图，再条件领取或消费，然后只执行一次，结果不明不重发。这一页把各处的键、条件与后果并排放，便于横向对照。

同一个模式的四步

① 先落盘意图

执行之前把「要做什么」持久化：工具操作、审批请求、发送操作、收件登记、入站事件写进数据库，控制面客户端的待确认提交写进本地文件。崩溃在这一步之前，什么都还没执行。

② 条件领取或消费

执行前用一次条件更新或唯一键取得资格：状态仍是指定值、版本一致、尚未被消费，或同一个键还没有记录。条件更新影响 0 行说明别人抢先了或已失效，放弃执行。

③ 执行一次

拿到资格的一方执行一次。执行内容在落盘或审批时就已固定（审批记录的参数、发送操作的目标与正文、待确认提交的原参数），执行时不按当前状态重新构造。

④ 结果分类

成功、失败照实记；结果无法确认时记「效果未知」或「应答丢失」，不自动换键重发：效果未知由拥有者核实，应答丢失先按原键核实。
不变量

本地能保证的只有一件事：一个逻辑键最多产生一次可能带副作用的执行。远端平台没有幂等支持时，本地无法保证端到端只发生一次——所以未知结果一律交回拥有者，而不是赌一次重发。

tool-op-ledger.ts · recordResult		 tool_ops 行，工具调用门在执行前写入执行意图（driver.ts · handleToolCall）；主键是宿主操作 id，与模型的调用 id 分开 按任务当前访问模式放行；需要审批的操作先经审批闸门消费批准，消费成功才执行 停止或重启时，结果缺失的操作按同一个分类器补记：审批全部未消费 → 已知未执行；无写入效果的工具 → 无写入效果；工具族能按宿主操作 id 核实 → 已提交或已知未提交；其余记效果未知
批准消费
store.ts · consumeApproval		 confirmations 行（status 与 consumed_at），登记审批请求时写入；主键是审批 id，行上记宿主操作 id 与权限版本 获批后在同一事务内先复核，再做一次条件更新：状态为 approved、consumed_at 为空、审批与任务的权限版本都等于预期、任务仍是 running 或 awaiting_confirmation。IM 来源的审批在条件更新之前还要过一次宿主固定身份复核（consumeRecheck）：当前平台目标与收件时钉版目标逐项相同（含配置版本），不符即批准失效、不消费——批准接受之后、执行开始之前的重新绑定与凭据变化在这里拦截。关联长期授权的批准（standing_permission_id/version，issue 10）在公共消费处重读授权版本与未撤销状态：撤销先提交则本次放行失效，不能成为独立批准 复核或消费失败 → 批准失效（stale），按已知未执行记。消费即执行开始：停止或重启时已消费、结果缺失的操作记效果未知；HTTP 以请求头与正文交给操作系统为界，之前的失败是已知错误，之后的超时、连接重置、中止记效果未知，GET/HEAD 除外（无写入效果）；MCP 写与副作用不明工具的超时、连接失败、取消也记效果未知
长期操作授权
approval-gate.ts · requestStanding		 standing_permissions 行（issue 10）：授权 ID + 行级版本，范围创建后不修改（main、入口稳定身份与钉版目标、机器/单元/固定 restart、策略与单元修订）；同一 main、稳定入口与目标至多一条未撤销授权（部分唯一索引），来源审批唯一 每次执行都在单个同步事务内重读授权版本与未撤销状态、对执行快照逐项核实完整范围、核实活动任务与取消状态，然后为本次 taskId/hostOpId 创建独立的初始已批准记录并公共消费：命中即整笔提交，核实不再成立整笔回滚并回落人工审批，不使用旧候选执行；授权本身不被消费，原单次批准也不被重复使用 已消费的服务操作效果未知（派发后失败/协议错误/应答不符/产物未保全/超时/中止）在工具操作账本的统一事务路径里使同一 main、本机、单元与动作的所有入口有效授权失效（reason = effect_unknown，事件携带触发操作 ID）；重新建立授权需要拥有者显式决定，旧未知记录不改写

orchestrator.ts · delegateCoding		 子任务是 tasks 行，请求键由编排器拼出：deleg:<父任务>:<幂等键>（幂等键来自委派工具参数）；唤醒父任务用 wake:<子任务> 委派在编排器串行链上查重：同键同参返回原子任务，异参冲突；结果以条件更新写一次（result_summary 为空才写），写成的一方才唤醒父任务 后台重启中断的子任务记结果未知（child_task.result_unknown），不重放；结果已写而唤醒缺失时，启动巡检按原键补发唤醒，不会建第二个唤醒任务。可证明无写入效果的失败 analyze 子任务会被自动重试一次（见下文）

三种「没有结果」要分开

这套模式里最容易写错的是把这几件事混成一件。CONTEXT.md 把它们定成不同术语，代码里也是不同的记录与文案。失败落在哪一段，决定了记哪一种。

已知未执行

能证明没有执行：审批被拒绝、取消或失效；获批后复核或消费失败；请求没交出（HTTP 未发出、渠道抛 NotSentError、控制面请求未送出）；发送操作在领取前被取消。发送操作里可证明未发送的记 failed。只读操作中止另记「无写入效果」，也不算效果未知。要再做一次，由模型或拥有者重新发起；系统自己再试的只有下一节三处。

approval-gate.ts · notExecutedText runtime.ts · NotSentError

效果未知

工具操作已经开始，却无法确认是否产生了效果：停止或重启时已消费批准、结果缺失的操作；写请求交出后的超时、断线、中止。发送操作的 effect_unknown 语义相同、分开记录（QQ 群回复记 unknown）。不自动重发，由拥有者核实；能从已提交记录证明时（应用数据回执、调度与委派记录），以核实结果为准。

types.ts · task.tool_effect_unknown

应答丢失

拥有者经控制面发出的请求已经送出，却拿不到能说明结果的应答：超时、断线，或 internal_error、response_too_large 这类不能说明未执行的错误应答。不换新键重发：提交与工作区入口按原键核实，确认未接收才以原键重发；其余查询后台状态后由拥有者决定。它针对控制面请求，不与工具操作的效果未知混称。

client.ts · UNKNOWN_REPLY_CODES

只重试「证明没产生效果」的那一次

未知结果不重发是默认规则。系统自己再做一次的只有下面三处，共同点是能证明上一次没有产生写入效果：

例外条件怎样再试
平台限流退回（ADR 0011）渠道抛 scheduler/runtime.ts · RetryLaterError：平台明确限流拒绝、可证明未发送。目前只有 Telegram 渠道在 HTTP 429 时抛出，等待时间取平台的 retry_after发送操作从 sending 退回 pending 并写 not_before（store.ts · release），到时用原目标、原正文、原键再领取；领取期间已请求取消的直接 canceled。其他明确拒绝仍是 failed，超时、5xx 与断线仍是 effect_unknown，都不重发。
控制面同键重发应答丢失后按原键核实，后台没有这条请求（提交：find_task 查不到；工作区入口：客户端状态里没有同一 create_request_id 的会话）以原键和落盘的原参数重发；撞上 request_conflict 先再核实一次，查到就关联。不换新键绕过。
编排器自动重试analyze 模式的委派子任务状态为 failed；不是入站事件派生、本身不是重试；没有效果未知；没有已批准或已消费的审批；每个工具操作都有结果且属无写入效果（tool-op-ledger.ts · hasNoWriteEffect）以 <原请求键>:retry 再委派一次，不计入委派上限；首次结果标注由谁重试，只由重试的结果唤醒父任务；重试再失败不再重试（orchestrator.ts · handleTerminal）。

按原键重提不在此列：入站事件补派、群收件恢复、子任务唤醒补发都用原请求键提交，已有任务就返回它（异参冲突），不会产生第二次执行。

已知限制

平台没有幂等支持时，远端可能已经执行而本地无法确认，这种情况只能由拥有者核实。系统不因为「大概没成功」而重发，也不把结果未知显示成取消成功。
