编排

编排器

编排器是后台内的宿主组件：派发入站事件，在委派出去的任务到达终态时记录结果、发出事件并回报父会话。现行代码里两套委派并存：旧架构的 main、coding、chat 三个固定逻辑角色（main 把修改草稿委派给共享的 coding 会话，结果发 child_task.*），以及新方向的通用 SubAgent（主 Agent 登记工作委托，由独立的只读 SubAgent 执行，结果与 SubAgent 的状态变更（idle 或 unverified）同一事务登记，发 subagent_task.*；空闲的 SubAgent 可沿原工作继续或复用承接新工作，关闭由主 Agent 或拥有者显式发起，发 subagent.closed）。超时、重启和 PR 事件都沿用宿主写定的请求键，不换键、不重放。

逻辑角色与引导（旧架构）

旧架构的现行实现

本节与下文「窄接口」「main 委派 coding」「子任务结果与异常路径」「GitHub PR 评审编排」「群聊结果」描述的固定角色机制仍在运行，但属于旧架构：新方向取消固定 coding 与 chat，由主 Agent 派发通用 SubAgent（ADR 0017、ADR 0020）。GitHub 评审迁到 SubAgent、核心退出群聊、迁移旧实例与清理固定角色分别是 agent-direction 工单 19、20、21–22、23，都还没有实施。新机制见工作委托与 SubAgent。

逻辑角色只有三个（types.ts · AgentRoleId）。后台启动时，orchestrator.ts · ensureRoles 按 ROLE_DEFINITIONS 逐个检查：agent_roles 已有该角色的行就跳过；没有就找到或创建项目 agent-<角色>，建工作目录 <dataDir>/../agent-work/<角色>（权限 0700，放在数据目录之外以避开保护根），经桥接创建会话，再写一行角色配置（store.ts · insertAgentRole）。

角色项目 · 会话工具类别资料身份任务从哪来
main agent-main，一个持久会话 host_data web_search app_data scheduler delegation chat_results service skills subagent；没有编码工具（service 的装配另要求部署配置，见工具调用路径） agent：本项目加有效的资料授权；不能读原始 QQ 群项目 拥有者直接提交；Telegram 与 QQ 私聊入站；调度唤醒；子任务唤醒；GitHub 评审父任务
coding agent-coding，一个持久会话 coding host_data web_search mcp skills agent：同 main，也不能读原始 QQ 群项目 main 的 draft 委派；GitHub 评审子任务。analyze 委派已改由 SubAgent 执行（见下文）
chat agent-chat 会话之外，每个「登录账号 + 群」一个 qq_group 会话 空集合 群会话为 qq_group，其他 chat 会话为 role_restricted：只读本项目，不查资料授权，owner_note 来源不自动可读 QQ 群入站事件，进各群会话；agent-chat 会话本身没有宿主来源

角色能力与资料范围都由宿主决定，互不替代：

  • 工具：会话类别到工具类别是一张静态表 tool-availability.ts · SESSION_TOOL_CATEGORIES。角色行里的 tools 列只是引导时写入的副本，运行时不读回；sessionToolClass 把 qq_group 会话一律归入 chat，其余角色会话按角色绑定。装配、激活与调用门的细节见工具调用路径。
  • 资料：驱动器按会话给出资料身份（driver.ts · accessor），access.ts · canAccess 判定。main 与 coding 所在项目读取任何 qq_group 项目一律拒绝，且优先于资料授权，coding 因此不能成为读取群资料的旁路（ADR 0012）。
  • 模型：引导时 model_selection 写 null，Store 也没有改写它的方法，所以编排器提交的角色任务用后台默认模型；群任务依次取群会话、角色、后台默认的模型配置。拥有者直接提交到角色会话时用自己给的模型。

chat 共用一份角色工具策略，群与群之间的资料却是隔离的：QQ 适配器在某群首次触发时建项目 qq-<账号>-<群>、专用空目录 <dataDir>/../qq-work/<账号>_<群> 与 qq_group 会话，并登记到 qq_sessions，主键为（账号，群）（qq/adapter.ts · ensureGroupSession）。按会话反查角色时，store.ts · getAgentRoleBySession 把这些群会话合成为 chat 角色，项目、会话与工作目录取群绑定，工具取 chat 行。

通用 SubAgent 不进这张角色表，也不进 agent_roles：AgentRoleId 与 tasks.agent_id 保持三个固定角色的语义（列上有 CHECK 约束），动态身份记在 sub_agents 表，宿主按会话反查识别（store.ts · getSubAgentBySession）。驱动器先查这张表：命中的会话归 subagent 工具类别（driver.ts · toolClass），不会因为没有角色绑定落进默认的 dev 类别。见工作委托与 SubAgent。

角色配置只由编排器写

Store 对 agent_roles 只有 insertAgentRole 一个写方法（INSERT，同 id 已存在即冲突，不覆盖），调用方只有 ensureRoles。控制面的 create_session 不带角色身份，输入正文、项目指令与模型结果都没有入口改动角色的项目、会话、工作目录、模型或工具类别。

窄接口

编排器只经 orchestrator.ts · OrchestratorBridge 调用 Runtime，接口由 Runtime 在启动时注入。它不持有拥有者 token，也不是模型工具：模型工具直接调用的编排器方法只有 coding_delegate（mode=draft）背后的 delegateCoding；调度工具只经调度器间接用到编排器的派发与串行链（scheduler/runtime.ts · cancelSchedule）。subagent_delegate 与 coding_delegate（mode=analyze）进的是另一个宿主组件 SubAgentManager，它自己登记任务，不经编排器，也不经 Runtime 的提交入口；编排器只在这些执行任务到达终态时登记结果。subagent_close 同样直接落在 SubAgentManager 的核实与写入上（subagents.ts · close）。coding_result、subagent_result 与群聊结果工具直接读 Store。窄接口只约束编排器能调用的 Runtime 方法：它自己的持久记录（结果、入站事件、角色行、子任务事件、SubAgent 状态、群收件状态）直接写 Store 与 QqStore。旧架构的部分是角色任务的提交与唤醒；入站派发与结果登记在新方向里继续使用。

编排字段只来自宿主

控制面 server.ts · submit 只把 session_id、request_id、model_selection、input、access_mode、granted_paths 交给 Runtime，拥有者也不能借控制面伪造子任务。编排器提交的任务一律使用 confirm（请求确认模式），不继承目标会话的默认模式，也就不会继承 main 会话的完全访问模式；桥接里没有审批、切换访问模式（switchTaskMode、setSessionDefaultMode）或建资料授权（createDataGrant）的方法。SubAgent 执行任务同样固定 confirm，Runtime 另外拒绝三件事：向 SubAgent 子会话提交（runtime.ts · submit）、切换 SubAgent 任务的模式（switchTaskMode）、改子会话的默认模式（setSessionDefaultMode）。

工作委托与 SubAgent

新方向的委派入口是 subagent_delegate：主 Agent（拥有者的普通开发会话或 main）为一项工作登记工作委托，宿主为它创建一个动态 SubAgent，再派出一次只读执行任务（ADR 0020）；空闲后可沿原工作继续（work_id）或复用承接新工作（sub_agent_id），不再需要时显式关闭（subagent_close 或控制面 / CLI，见继续、复用与关闭）。登记由 subagents.ts · SubAgentManager.delegate 集中完成；执行沿用普通的会话队列与驱动器；终态由编排器登记（见下一节）。main 的 coding_delegate 在 mode=analyze 时也转进这条链路（runtime.ts · analyzeDelegate），硬只读、不自动重试。

三层记录

一项工作、承接它的 Agent、每一次执行，分三处记录。核心库 schema v24 新增 sub_agents 与 work_delegations 两张表（db.ts · work_delegations），并给 tasks 补四个可空列；v25（当前版本，db.ts · SCHEMA_VERSION）再给 sub_agents 补 closed_at / closed_by 两个可空列。旧任务的四个关联列、旧 Agent 的两个关闭列都是空的。

层记录记什么谁写、何时写为什么单独存
工作 work_delegations
types.ts · WorkDelegation		 所属父会话、发起任务 origin_task_id、首次委派的键 request_key 与参数摘要 params_digest、承接的 sub_agent_id。（父会话，键）唯一。 首次委派的登记事务（store.ts · insertWorkDelegation），之后不再改。 一项工作可以跨多轮对话、包含多次执行；某次执行结束不等于工作结束。
身份 sub_agents
types.ts · SubAgent		 所属父会话、独立子会话 session_id（唯一）、宿主生成的 work_dir、状态 state、当前工作 active_work_id 与当前任务 current_task_id，以及独立于 state 的关闭两列 closed_at / closed_by（见继续、复用与关闭）。 首次委派建行（insertSubAgent）；之后只改状态与两个指针（setSubAgentState），另有一次条件写入的关闭（closeSubAgent）。 身份、目录与上下文在执行结束后保留，供同一工作继续派活；动态 ID 不能进 agent_roles 或 tasks.agent_id，后者的 CHECK 只允许三个固定角色。
执行 tasks 的一行 新列：work_id、sub_agent_id、钉定的读范围 read_scope、结果注入时刻 result_delivered_at。沿用的列：直接父任务 parent_task_id、请求键、截止时间、访问模式 confirm、result_summary 与 result_ref。 登记事务插入排队任务；终态后编排器写结果；dev 父会话注入结果时写 result_delivered_at。 每次执行有自己的状态、截止、审批与读范围，复用现有队列、驱动器、工具操作账本、历史与产物。

幂等、限额与截止

  • 两级幂等：新工作路径（省略 work_id 与 sub_agent_id，或带 sub_agent_id 复用）以（父会话，key）查工作（dedupNewKey，登记事务内的竞争仲裁同一条）；工作内每次执行的请求键是 sdelegate:<工作>:<key>（subAgentTaskRequestId），在子会话里唯一。工具的参数摘要（canonicalParamsDigest）只在给 sub_agent_id 时纳入它，省略时摘要与此前相同，重放不因此冲突。任务的提交摘要（taskSubmissionDigest）只覆盖参数摘要、工作与身份，不含本次调用的父任务 ID、模型选择与截止时间，所以下一轮对话用同一个键重放会拿回首次记录，而不是误报冲突；查重排在限额与可用性之前，同键同参命中即返回原记录，即使目标已关闭或忙碌，也不新建执行。
  • 限额：同一父会话的活动执行任务（queued、running、awaiting_confirmation）至多 SUBAGENT_LIMITS.perParentSession = 3 个（store.ts · countActiveSubAgentTasks）。空闲的身份不占名额。
  • 截止：直接父任务的开始时刻（尚未开始取创建时刻）加 deadlineMs（60 分钟），包含排队与审批等待；到期由编排器的截止巡检取消，与旧委派同一套（见子任务结果与异常路径）。
  • 继续原工作：带 work_id 时沿原工作派一次新执行（dedupExistingWork 查重）：同一个 SubAgent、同一个子会话与目录，上下文接着原 JSONL；不新建工作，不发 work_delegation.created；读范围与资料按本次新的任务重新确定，前次批准不延续。
  • 复用 SubAgent：带 sub_agent_id（与 work_id 互斥）时，让本会话名下另一个空闲且未关闭的 SubAgent 承接一项全新工作：登记事务里新插入一行 work_delegations 指向它（发 work_delegation.created），子会话上下文延续（ JSONL 接着旧工作），只读路径与资料按本次重新钉定，任务正文里另有一句「此前承接过其他工作，旧范围不延续」（taskInput）；快照文件按工作加执行键命名（materials-<workId>-<key>.txt），不覆写旧工作的快照。
  • 资料快照命名：materialsFileFor 按 (workId, key) 命名；v25 之前的旧目录里呈 materials-<key>.txt 的快照仍在磁盘与个人产物登记里有效，只是新的委派不再产生这个名字。

继续、复用与关闭

首次委派之后，同一个 SubAgent（独立子会话与目录都保留）可以被主 Agent 继续沿原工作派活（work_id）、复用承接新工作（sub_agent_id），或显式关闭。继续与复用都经 subagent_delegate 走同一登记与幂等链路（见上「一次委派怎样登记」），且都要先过可用性核查（subagents.ts · assertAvailable）——准备前与登记事务内各核一次；关闭是 subagent_close（主 Agent 的工具调用）或控制面 subagent_close 操作 / CLI ruukoto work close（拥有者，见下一节）。

可用性核查结果
目标 SubAgent 的 parent_session_id 是当前父用户会话不属于本父会话拒绝 forbidden（关闭由拥有者发起时不受这条限制）
closed_at 为空（未关闭）已关闭拒绝 closed，提示「请新建 SubAgent」
state 是 idle 且没有活动任务（queued / running / awaiting_confirmation，store.ts · findActiveSubAgentTask）忙碌或待核实拒绝 busy，给出任务 id，不排队（堵住「running 时再委派覆盖当前任务指针、在跑任务显示空闲」的缺口）
工作目录必须仍存在，且 realpath 与目录身份（realpath、dev、ino）与子会话登记的 cwd_real / cwd_dev / cwd_ino 一致目录不存在、被替换或不符拒绝 workdir_gone，提示「请新建 SubAgent」

复用时生效上下文是延续的（同一子会话 JSONL 接着旧工作），资料与读范围按新的任务重新钉定：旧资料若已被撤销会先在登记事务的并集复核里被拦掉；子任务正文里另有一句告知模型旧范围不延续。快照文件命名为 materials-<workId>-<key>.txt，复用同一 Agent 时不会覆写旧工作的快照。

subagent_close(sub_agent_id) 或 subagent_close {sub_agent_id}
核实：存在、归属（agent 发起必须本父会话）、未关闭、无活动任务

条件写入 closeSubAgent，并发 subagent.closed
返回：不再接受新委派；历史与产物保留
  • 两个入口：主 Agent 的工具 subagent_close（普通 dev 与 main 装配；回报唤醒轮次也允许，因为关闭只收窄能力；subagent-tools.ts · subagentClose）；拥有者经控制面 subagent_close（runtime.ts · closeSubAgent，CLI ruukoto work close）。主 Agent 的 closedBy 记为 agent:<发起任务 ID>，拥有者记为 owner（types.ts · SubAgentClosedBy）。
  • 幂等与并发：关闭在一个同步事务里核实与写入；有活动任务报 busy 并给出任务 id，已关闭幂等返回（不再发事件），竞争与委派由条件写入（store.ts · closeSubAgent）与登记事务的可用性重核二选一胜负——不存在「已关闭且有活动任务」的中间态。关闭后新委派拒绝 closed。
  • 不自动关闭：任务终态（idle）、TUI 退出与空闲都不自动关闭；关闭不改 state，历史、子目录与 JSONL 保留可查。
  • 事件：每次核实通过写一条 subagent.closed（types.ts · subagent.closed：subAgentId、parentSessionId、closedBy，主 Agent 发起时另带 taskId，拥有者关闭为 null），事件归父会话，TUI 在父会话线里显示（tui/state.ts · subagent.closed）。

执行范围由宿主钉定

模型只给正文、键、可选的 work_id / sub_agent_id 与资料；身份、目录、模式、工具与读范围都由宿主写定，其中读范围（钉定路径与来源引用）存进任务的 read_scope（types.ts · SubAgentReadScope）。

范围宿主怎样固定在哪里核实
工具 只有 read 与 read_artifact（tool-availability.ts · SUBAGENT_READONLY_TOOL_NAMES）；subagent 类别的清单为空，编码、委派与其他宿主工具都不装配，SubAgent 也就不能再委派下级。 装配时过滤，发送前按载荷核对，调用门用同一白名单收窄（driver.ts · checkBeforeSend）。read_artifact 只读本任务自产的产物，拒绝 prompt-snapshot:*。

访问模式 固定 confirm，不继承父任务或父会话的模式、单次批准与长期授权。 见上文「编排字段只来自宿主」。
上下文 按资料受限会话装配：不注入项目指令、长期记忆与技能目录，也不做上下文压缩（driver.ts · dataScopeRestricted）。 细节见上下文组装。

SubAgent 状态与结果回报

SubAgent 的状态写在 sub_agents.state 上，取值见 types.ts · SubAgentState：running 表示有活动执行任务；idle 表示执行任务已到终态、目录占用已回收；unverified 表示执行任务已到终态，但旧执行单元是否退出没有核实，目录占用还在。只有两处代码改它：委派登记置 running，编排器登记终态时置 idle 或 unverified。空闲时子会话的驱动器已释放，不跑模型，也没有 worker 进程；身份、子会话、JSONL 与产物都保留。

结果怎样回到主 Agent

执行任务到达终态后，编排器的事件监听或启动巡检把它交给 handleSubAgentTerminal，不走旧角色任务的重试门，也不发 child_task.*。一个事务里：setTaskResult 条件写入摘要与结果引用（重复终态只有先到的一次生效）；改 SubAgent 状态；追加一条 subagent_task.* 事件，事件归到父会话名下，TUI 在父会话里显示。结果引用 result_ref 记 sessionId、taskId、workId、subAgentId、parentSessionId、parentTaskId、outcome、artifactIds（不含 prompt-snapshot:*）与 failure；结局按任务终态归类，规则与旧子任务相同（见终态怎样归类）。之后按父会话的类别回报：

main 父会话：唤醒

沿用旧链路的 wakeParent：以 wake:<子任务>、confirm 向 main 会话提交唤醒任务，不带来源事件，所以没有自动外发授权。唤醒正文只有固定字段与截断后的摘要，并提示用 subagent_result 按 work_id 读完整结果。提交失败由启动巡检 ② 按原键补发。

dev 父会话：下一个任务开始时注入

不产生唤醒任务，也不进唤醒巡检。父会话下一个任务开始时，驱动器取出还没送达的结果（store.ts · listUndeliveredSubAgentResults），同一事务标记 result_delivered_at，再作为 [SubAgent 结果] 参考块放进模型上下文（context-assembly.ts）。标记后若崩溃，结果仍可从事件与 subagent_result 查到。参考块的写法与位置见上下文组装 · SubAgent 任务的上下文。

  • 读结果：subagent_result 只读工作登记在当前会话的记录：省略 work_id 时返回本会话 SubAgent 的总览（状态或已关闭、当前工作、名下工作、最近任务状态，供挑选继续或复用对象，store.ts · listSubAgentsBySession）；指定时 part=result（默认）给工作、SubAgent 是否已关闭 / 状态与每次执行的摘要；part=reply 按 UTF-8 字节分页读最终回答，每页至多 READ_LIMITS.replyBytes（16 KiB）；part=artifact 读该次执行自己的产物，每页至多 artifactBytes（64 KiB）。不给 task_id 时取最近一个已有结果的执行，都还没有结果时取最近一个。已关闭后历史与产物仍按原窄口可读。main 的 coding_result 也能读这些执行任务（见main 委派 coding）。
  • 拥有者查看与关闭：控制面只读操作 work_list / work_get（CLI ruukoto work list / ruukoto work show）列出工作、SubAgent（含关闭两列）与执行任务；拥有者经 subagent_close（runtime.ts · closeSubAgent，CLI ruukoto work close，cli.ts）随时显式关闭——有活动任务报 busy 并给任务 id，等任务结束或先 ruukoto cancel 再关，已关闭幂等；停止中（stopping）拒绝。普通的提交、继续、切换模式与会话默认模式都不能作用于子会话。协议见控制面协议。

停止与重启时

  • 执行中的任务：后台停止（runtime.ts · doStop）或崩溃后恢复（runtime.ts · recover）时把它转为 interrupted，这时编排器已经停下或还没启动，没人监听；编排器启动时由巡检 ① 补记（listRoleTasksPendingResult 同时选带 sub_agent_id 的任务），结局为结果未知，发 subagent_task.result_unknown。留下了占用的（崩溃，或停止时没能回收工具进程），恢复时子会话被暂停为 occupancy_unverified，SubAgent 记 unverified；停止时工具进程已回收的记 idle。main 父会话随后被唤醒，dev 父会话等它下一个任务开始时注入。
  • 排队中的任务：Runtime 恢复时把子会话队列暂停为 backend_restart。编排器只自动恢复三个角色会话的队列，SubAgent 子会话不在其中：任务留在 queued，身份仍是 running，直到拥有者对该会话 resume_queue，或截止巡检按 deadline_exceeded 取消它（结局 timeout，身份按占用情况转 idle 或 unverified）。
  • 不重放、不重试：结果未知的执行不自动重发，也没有自动重试。
  • 关闭与重启：关闭只写 closed_at / closed_by 两列并记一条 subagent.closed（归父会话的持久事件）；不取消在途任务——有活动任务报 busy 并给任务 id，等任务结束或由拥有者 ruukoto cancel 后再关；不撤销既有产物、子目录、JSONL 与工作记录。

首版限制

首版只做只读分析。已有：首次委派、沿原工作继续（work_id）、复用承接新工作（sub_agent_id）、结果回报与查询（含总览）、主 Agent 与拥有者两侧的显式关闭（subagent_close 与 subagent_close op / ruukoto work close）。还没有实现：同项工作的 SubAgent 互发消息（13）；取消整项工作（14）；后台重启后的 SubAgent 恢复状态机（15）；并行 worktree 与汇总改动（16、17）；GitHub 评审迁到 SubAgent（19）。代码里已知的缺口（不作新派遣之外的口径）：unverified 没有回到 idle 的路径；重启时排队的执行任务不会自动恢复。此前「执行中再委派同一工作覆盖当前任务指针」的缺口已堵死——继续与复用要求 idle，忙碌明确拒绝不排队。

main 委派 coding（旧架构）

main 有两组委派工具：旧的 delegation 类别 coding_delegate 与 coding_result（delegation-tools.ts · createDelegationTools），只有 main 的清单里有；新的 subagent 类别 subagent_delegate 与 subagent_result，见工作委托与 SubAgent。coding_delegate 的模型参数是正文、模式（analyze / draft）、幂等键和可选资料；按模式分两路：

  • mode=analyze：转进通用只读 SubAgent 链路（delegation-tools.ts · analyzeDelegate），硬只读、不自动重试；登记、请求键与终态回报都走 SubAgent 那一套，结果仍可用 coding_result 读。它从不带 work_id，所以每个新键都新建一项工作与一个 SubAgent；查重按（main 会话，key），同一个键在后面的对话轮次里也会命中，而 draft 的键只在父任务内有效。Runtime 总是装配这条链路，所以后台里新的 analyze 委派不再产生 coding 子任务。
  • mode=draft：留在本节的旧路径。目标角色、会话、工作目录、权限模式与截止时间都由 orchestrator.ts · delegateCoding 写定。GitHub 评审子任务也走 coding 角色（见下文）。

谁能委派、委派什么

  • 来源：只有拥有者发起的 main 任务能委派（delegation-tools.ts · ownerOriginated）：拥有者直接提交（任务不带角色来源），或来源事件是 Telegram / QQ 私聊入站。调度唤醒、子任务唤醒与其他入站任务调用时报错，外部内容不能借此连环建任务。
  • 幂等键：key 为 1–64 位字母、数字、_ 或 -（KEY_RE），请求键 deleg:<父任务>:<key>。工具先比对原始参数的规范化摘要；编排器在串行链上再核一次（角色、正文或摘要、截止时间、来源事件），同键异参抛冲突，不产生第二个子任务。
  • 资料：materials 在委派时按 main 的可读范围解析成文本快照，追加在请求后面；coding 拿不到原始引用 ID。已接收的群聊结果（chat_result）不能作为委派资料。
  • 固定参数：每个父任务至多 DELEGATION_LIMITS.perParent = 3 个首次委派（store.ts · countDelegations 不计 :retry）；截止时间 = 父任务开始时刻（尚未开始取创建时刻）+ deadlineMs（60 分钟），是确定值，同键重试不会因时间变化而冲突；宿主模板加请求加资料合计超过 INPUT_TEXT_CAP（8192 字符）直接拒绝，不截断。
  • 不继承来源事件：委派不把父任务的来源事件传给子任务，子任务终态不会回写 Telegram / QQ 私聊事件，子任务和它的唤醒任务都不产生 owner 回复（owner 回复的登记见 runtime.ts · enqueueOwnerReply 与入站事件）。
  • 停止或重启时：未落结果的 draft 调用按原请求键核实子任务是否存在（delegationOpCheck），存在即已委派，不存在即已知未委派，不记效果未知；analyze 调用改按 SubAgent 族核实（见上文的登记失败表）。

子任务结果与异常路径

子任务本身的状态机见任务生命周期。这里画的是编排器这一侧：一个角色任务或 SubAgent 执行任务到达终态之后，结果怎样被记录一次、父会话怎样被唤醒一次，以及超时、自动重试和重启时走哪条边。结果只写一次、截止巡检、按原键唤醒与启动巡检对两类任务都适用；自动重试、DelegationResult 与 child_task.* 只属于旧架构的角色任务，SubAgent 一侧的差别见SubAgent 状态与结果回报。

终态怎样归类

归类在 onRuntimeEvents 与 outcomeFromStatus 里各写一份，前者按事件类型，后者按持久状态（启动巡检与群任务派发用），结论相同。

任务终态结局事件摘要
completedcompletedchild_task.completed，带摘要与 result_ref最终回答，截断到 1000 字符；没有文本时写「无文本输出」。
failedfailedchild_task.failed，带错误信息「子任务失败：」加错误信息。
canceled，原因 deadline_exceededtimeoutchild_task.timeout，带截止时间超过截止时间、已取消。
canceled，其他原因failedchild_task.failed「子任务失败：」加 error_message（排队中取消的原因写在这里，如入站门丢弃）；没有时写「已取消」。执行中取消的原因在 interrupt_reason，不进摘要，只进委派结果的 failure。
interrupted，任何原因unknownchild_task.result_unknown，带中断原因固定文本：结果未知，未自动重放任何外部副作用。

child_task.* 事件对每个带 agent_id 的任务都会发，不只是子任务：入站建的 main 任务、群任务与唤醒任务本身也会发，它们的 parentTaskId 为 null。

带 sub_agent_id 的执行任务走同一张状态图，只是没有「由重试接替」这条边，事件换成 subagent_task.completed / subagent_task.failed / subagent_task.timeout / subagent_task.result_unknown，唤醒只发给 main 父会话；dev 父会话不唤醒，也不进巡检 ②（listRoleTasksPendingWake 要求父会话绑定角色），结果在父会话下一个任务开始时注入（见上文）。

自动重试门

重试门在 handleTerminal 里，只作用于旧 coding 委派链的 analyze 子任务。新的 analyze 委派已由 SubAgent 执行、不自动重试，所以这道门如今只对接入 SubAgent 链路之前登记、之后才结束的 analyze 子任务起作用。下列条件全部成立才自动重试一次：

  • 子任务模式为 analyze；draft 不重试。
  • 有父任务且没有来源事件：GitHub 评审子任务不重试。
  • 任务状态是 failed；超时、其他取消与中断（结果未知）都不重试。
  • 任务没有效果未知标记，请求键不以 :retry 结尾。
  • 本任务没有已批准或已消费的审批请求。
  • 工具操作账本里的每个操作都满足：规则表判为无写入效果（tool-op-ledger.ts · hasNoWriteEffect），没有效果未知，结果已记录。bash、edit、write、记忆写入、MCP 与未登记的工具一律按需要审批判定，出现一次就不重试（包括经 bash 执行的 git clone）。

重启恢复

Runtime 先跑自己的恢复（执行中的任务转 interrupted、未决审批失效，见任务生命周期），再启动编排器。Runtime 恢复时编排器还没创建，这时产生的 task.interrupted 没人监听；重启窗口内到达终态的任务全靠巡检补记。orchestrator.ts · start 按顺序执行：

  1. 引导角色：已有的角色行原样保留。
  2. 已登记、未建任务的入站事件按原请求键串行重提（派发细节见入站事件）；类别不是 task 的控制事件（正常路径不会有遗留）不派发为模型任务，一律以 inbound.skipped（control_event_not_dispatched）作废（dispatchEvent）。
  3. 巡检 ①：已终态但结果未记录的角色任务与 SubAgent 执行任务补记结果与事件（store.ts · listRoleTasksPendingResult）；interrupted 记为结果未知，不重放。
  4. 巡检 ②：结果已记录但缺唤醒的子任务，按 wake:<子任务> 补发（sweepPendingResults）。
  5. 三个角色会话中，只有因 backend_restart 暂停的队列自动恢复；occupancy_unverified 等涉及未核实旧执行的暂停留给拥有者核实。SubAgent 子会话不在自动恢复之列（见停止与重启时）。
  6. 开始截止巡检。

后台停止时，编排器在 GitHub webhook、调度器与 Telegram 之后，QQ 适配器与中断活动任务之前停下（runtime.ts · doStop）：清掉巡检定时器，等派发串行链收尾，此后不再产生取消或唤醒。停止路径随后中断的角色任务没人监听，由下次启动的巡检 ① 按结果未知补记。

恢复靠原键

编排器提交的每个任务都有宿主写定的请求键，Runtime 按「同会话 + request_id + 提交摘要」幂等：同键同参返回原任务，同键异参冲突。SubAgentManager 不经 Runtime 提交，但依赖同一个（会话，request_id）唯一约束，并在登记事务里自己比对提交摘要。任何恢复路径都只用原键，不另起新键。

GitHub PR 评审编排（旧架构）

拥有者启用 webhook 后，每个有效的 PR 事件由宿主固定委派一次只读评审（ADR 0013）。评审子任务仍由固定的 coding 角色执行，没有接入 SubAgent；迁移是 agent-direction 工单 19，尚未实施。签名校验、入站登记与去重见入站事件；通知的发送账本见通知 outbox。这里只讲编排：派发不经模型，模型也不能改变任务的工具、目标或发送。

报告与修订有效性

  • 报告：子任务完成时，events.ts · resultData 把最终回答逐页写进产物 review-draft:<事件>，读满记录的总字节数才标记完整。分页缺失或写入失败时产物保持 partial，结果记 captureError 并要求拥有者核实。
  • 有效性：result_ref.review 保存事件 ID、PR URL、仓库 ID、PR 编号、head/base SHA、产物 ID 与 staleReason。events.ts · staleReason 在 PR 已关闭或为 draft，或同一 PR 有 updatedAt 不早于本事件、但 head、base、状态或 draft 不同的事件时返回原因。
  • 失效：新事件登记时（events.ts · register）在同一事务里给旧事件的评审结果写 staleReason，并取消旧事件尚未发送的通知（发送中的只记取消请求）；旧事件还没派发或还没开始的任务被入站门丢弃（events.ts · gate）。旧产物保留为不可变记录。
  • 通知：events.ts · terminal 只接受「本事件 coding 子任务」的唤醒任务；事件已失效、webhook 停用、owner 目标未配置或已变化时改记 inbound.skipped，不发送。

群聊结果（旧架构）

本节是旧架构的核心群聊入口：chat 角色与 QQ 群会话由核心运行时处理。新方向把群聊移到可独立停用的 QQ 群聊外挂，核心退出群聊是 agent-direction 工单 20，尚未实施。QQ 群任务完成后，编排器照常记录摘要与 child_task.completed，但群任务没有父任务，所以不唤醒 main；它的来源事件是 qq_group，owner 回复登记直接跳过。群内的普通回复走独立的 qq_outbox（见入站事件）。main 想用群里的结果，必须显式接收（ADR 0014）。

通知引用
{kind:'chat_result', task_id} 作为通知来源；每次解析再复核，仍经拥有者审批。
  • 能接收什么：chat-result-tools.ts · sourceOf 只放行已完成且已记录结果的 chat 任务，并核对会话类别为 qq_group、收件记录、群绑定、入站事件（done、目标 chat、actor 与收件一致）彼此对应。两个工具都只在宿主绑定的 main 任务里可用。
  • 快照：接收保存 result_summary 的前 SUMMARY_CHARS = 1000 个 Unicode 字符、来源任务、接收任务、宿主操作 ID 与理由（1–1024 字节）。（main 项目，任务）为主键，首次快照固定，重复接收不改写，只有首次写入发 chat_result.accepted（store.ts · acceptChatResult）。列表每页 1–50 条，默认 20（chat_result_list）。
  • 撤回使摘要失效：该群任何一条在任务结束前收到、并在任务开始后（或时间未记）被撤回的消息，都会让这次结果不可接收，已接收的快照也不能再被解析或外发。这是按时间窗的保守判定，可能拒掉其实没引用被撤回消息的摘要。已经进入 main 历史或已发送的副本不追溯清除。
  • 接收不是外发授权：通知与通知计划引用快照时经 resolveAcceptedChatResult 核对 main 项目与撤回，登记仍要拥有者审批（通知 outbox）。快照也不开放原始群历史、产物或带群来源的记忆，coding_delegate 与 subagent_delegate 都不能把它当委派资料。
  • 停止或重启时：未落结果的 chat_result_accept 按接收账本核实（chatResultOpCheck），不记效果未知。
