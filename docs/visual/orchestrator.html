编排器

编排器是后台内的宿主组件：派发入站事件，在委派出去的任务到达终态时记录结果、发出事件并回报父会话。固定角色已退役：旧架构的 main、coding、chat 三个逻辑角色里，宿主只引导 main，coding 与 chat 的角色行保留为只读归档，升级前在途的旧 coding 子任务在启动时收尾一次，结果按 child_task.* 记录、可用 coding_result 查阅。委派一律走新方向的通用 SubAgent（主 Agent 登记工作委托，由独立的 SubAgent 执行只读分析或按工作隔离的修改——修改工作时 Git 仓库建宿主 worktree 副本、非 Git 目录直接写入并串行，结果事务经 SubAgentManager 核实当前任务后更新状态（idle 或 unverified），发 subagent_task.*；worktree 副本的改动由主 Agent 经 subagent_integrate 汇入父工作区待提交区，预检通过才写入、冲突零写入双方保留，发 work_delegation.integrated，main 的修改委派走同一条通用链路；空闲的 SubAgent 可沿原工作继续或复用承接新工作，关闭由主 Agent 或拥有者显式发起，发 subagent.closed；整项工作可取消，取消三个独立列不改写已结束任务的结果，发 work_delegation.canceled，不关闭 SubAgent；同一项只读工作的参与者（主 Agent 与当前承接它的各 SubAgent）之间可以互发带宿主标注来源的工作内消息，登记与投递发 subagent_message.sent、明确未投递发 subagent_message.dropped；IM 发起的工作在收尾的 main 唤醒结果事务里由宿主登记工作最终汇报，发回发起入口）。超时、重启和 PR 事件都沿用宿主写定的请求键，不换键、不重放。

逻辑角色与引导（旧架构）

旧架构的现行实现

逻辑角色属于旧架构。新方向取消固定 coding 与 chat，由主 Agent 派发通用 SubAgent（ADR 0017、ADR 0020），代码已按此收口：核心群聊由 agent-direction 工单 20 退役，固定 coding 角色由工单 23 退役，两者都不再引导、不接受新任务，旧行与旧会话保留为只读归档。现行代码里 main 仍以角色会话的形式运行（项目 agent-main）。本节、「子任务结果与异常路径」与「群聊结果」里关于 coding / chat 的内容只描述归档与升级收尾。新机制见工作委托与 SubAgent。

逻辑角色的类型仍是三个取值（types.ts · AgentRoleId），旧行仍带这些值，库表的 CHECK 约束也照旧；引导定义只剩 main：coding 与 chat 已退役，旧安装的 agent-coding、agent-chat 行保留为归档标识（见下文角色表）。后台启动时，orchestrator.ts · ensureRoles 按 ROLE_DEFINITIONS 逐个检查：agent_roles 已有该角色的行就跳过；没有就找到或创建项目 agent-<角色>，建工作目录 <dataDir>/../agent-work/<角色>（权限 0700，放在数据目录之外以避开保护根），经桥接创建会话，再写一行角色配置（store.ts · insertAgentRole）。

角色能力与资料范围都由宿主决定，互不替代：

  • 工具：会话类别到工具类别是一张静态表 tool-availability.ts · SESSION_TOOL_CATEGORIES。角色行里的 tools 列只是引导时写入的副本，运行时不读回；会话类别即会话身份（classifySession）：SubAgent 会话归 subagent，main 角色会话归 main，其余普通会话归 dev；qq_group 会话与 chat / coding 角色会话是已退役归档，不归任何类别，驱动器被要求运行这类会话时，算执行画像即报错（tool-availability.ts · executionProfile）。装配、激活与调用门的细节见工具调用路径。
  • 资料：驱动器按会话给出资料身份（driver.ts · accessor），access.ts · canAccess 判定。main（与旧 coding）角色所在项目读取任何 qq_group 项目一律拒绝，且优先于资料授权（ADR 0012，access.ts · isQqGroupProject）；这条边界在群聊退役后保留，旧群资料仍是归档。
  • 模型：引导时 model_selection 写 null，Store 也没有改写它的方法，所以编排器提交的 main 任务用后台默认模型。拥有者直接提交到 main 会话时用自己给的模型。

退役前 QQ 适配器在某群首次触发时建项目 qq-<账号>-<群>、专用空目录 <dataDir>/../qq-work/<账号>_<群> 与 qq_group 会话，并登记到 qq_sessions（主键为账号、群）；退役后这些旧绑定保留为归档，QqStore 已没有写 qq_sessions 的方法。按会话反查角色时，store.ts · getAgentRoleBySession 把这些群会话合成为 chat 角色，项目、会话与工作目录取群绑定，工具取 chat 行。

通用 SubAgent 不进这张角色表，也不进 agent_roles：AgentRoleId 与 tasks.agent_id 保持三个固定角色的语义（列上有 CHECK 约束），动态身份记在 sub_agents 表，宿主按会话反查识别（store.ts · getSubAgentBySession）。会话身份先查这张表：命中的会话是 SubAgent 会话、归 subagent 工具类别（session-identity.ts · classifySession），不会因为没有角色绑定落进默认的 dev 类别。见工作委托与 SubAgent。

角色配置只由编排器写

Store 对 agent_roles 只有 insertAgentRole 一个写方法（INSERT，同 id 已存在即冲突，不覆盖），调用方只有 ensureRoles。控制面的 create_session 不带角色身份，输入正文、项目指令与模型结果都没有入口改动角色的项目、会话、工作目录、模型或工具类别。chat 与 coding 退役后不再引导：引导定义只剩 main，旧安装的 chat、coding 行原样保留，不删除也不改写。

窄接口

编排器只经 orchestrator.ts · OrchestratorBridge 调用 Runtime，接口由 Runtime 在启动时注入。它不持有拥有者 token，也不是模型工具：没有模型工具直接调用编排器（coding_delegate 已删除），调度工具只经调度器间接用到编排器的派发与串行链（scheduler/runtime.ts · cancelSchedule）。subagent_delegate 进的是另一个宿主组件 SubAgentManager，它自己登记任务，不经编排器，也不经 Runtime 的提交入口；编排器只在这些执行任务到达终态时登记结果。subagent_close 同样直接落在 SubAgentManager 的核实与写入上（subagents.ts · close）。coding_result、subagent_result 与群聊结果工具直接读 Store。窄接口只约束编排器能调用的 Runtime 方法：它自己的持久记录（结果、入站事件、角色行、子任务事件、群收件状态）直接写 Store 与 QqStore；在线 SubAgent 状态与工作 / 任务指针统一经 SubAgentManager 更新，Store 保留 SQL 原语（离线导入另行收尾）。入站派发、结果登记与 main 唤醒在新方向里继续使用。

工作委托与 SubAgent

新方向的委派入口是 subagent_delegate：主 Agent（拥有者的普通开发会话或 main）为一项工作登记工作委托，宿主为它创建一个动态 SubAgent，再派出一次执行任务——只读分析（ADR 0020），或经 mode=modify + target 发起的修改委派（dev 与 main 均可，agent-direction issue 16/17，ADR 0021，见修改委派：worktree 隔离与非 Git 串行）；worktree 副本的改动用 subagent_integrate 汇回父工作区待提交区（见改动汇总）；空闲后可沿原工作继续（work_id）或复用承接新工作（sub_agent_id），不再需要的工作整项取消（见整项取消），不再需要的 SubAgent 显式关闭（subagent_close 或控制面 / CLI，见继续、复用与关闭）。登记由 subagents.ts · SubAgentManager.delegate 集中完成；执行沿用普通的会话队列与驱动器；终态由编排器登记（见下一节）。旧的 coding_delegate 已删除，这是 dev 与 main 唯一的委派入口。

三层记录

一项工作、承接它的 Agent、每一次执行，分三处记录。核心库 schema v24 新增 sub_agents 与 work_delegations 两张表（db.ts · work_delegations），并给 tasks 补四个可空列；v25 再给 sub_agents 补 closed_at / closed_by 两个可空列；v26 再给 work_delegations 补 canceled_at / canceled_by / cancel_reason 三个可空列（见整项取消）；v27 再给 work_delegations 补 write_target 一个可空列（见修改委派）；v29 新增 subagent_messages（工作内协作消息，见协作加入与工作内消息）。旧任务的四个关联列、旧 Agent 的两个关闭列、旧工作的三个取消列与一个写入目标列都是空的；旧库新增的消息表同样为空。

幂等、限额与截止

  • 两级幂等：新工作路径（省略 work_id 与 sub_agent_id，或带 sub_agent_id 复用）以（父会话，key）查工作（dedupNewKey，登记事务内的竞争仲裁同一条）；工作内每次执行的请求键是 sdelegate:<工作>:<key>（subAgentTaskRequestId），在子会话里唯一。工具的参数摘要（canonicalParamsDigest）只在给 sub_agent_id 时纳入它，省略时摘要与此前相同，重放不因此冲突；修改委派把 mode 与 target 纳入摘要，旧分析委派的重放摘要不变。任务的提交摘要（taskSubmissionDigest）只覆盖参数摘要、工作与身份，不含本次调用的父任务 ID、模型选择与截止时间，所以下一轮对话用同一个键重放会拿回首次记录，而不是误报冲突；查重排在限额与可用性之前，同键同参命中即返回原记录，即使目标已关闭或忙碌，也不新建执行。
  • 限额：同一父会话的活动执行任务（queued、running、awaiting_confirmation）至多 SUBAGENT_LIMITS.perParentSession = 3 个（store.ts · countActiveSubAgentTasks）。空闲的身份不占名额。
  • 截止：直接父任务的开始时刻（尚未开始取创建时刻）加 deadlineMs（60 分钟），包含排队与审批等待；到期由编排器的截止巡检取消，与旧委派同一套（见子任务结果与异常路径）。
  • 继续原工作：带 work_id 时沿原工作派一次新执行（dedupWorkTask 查重：按目标 Agent 的会话、sdelegate:<工作>:<key> 与工作 ID 核对，继续与协作加入共用）：同一个 SubAgent、同一个子会话与目录，上下文接着原 JSONL；不新建工作，不发 work_delegation.created；读范围与资料按本次新的任务重新确定，前次批准不延续。
  • 复用 SubAgent：带 sub_agent_id（与 work_id 互斥）时，让本会话名下另一个空闲且未关闭的 SubAgent 承接一项全新工作：登记事务里新插入一行 work_delegations 指向它（发 work_delegation.created），子会话上下文延续（ JSONL 接着旧工作），只读路径与资料按本次重新钉定，任务正文里另有一句「此前承接过其他工作，旧范围不延续」（taskInput）；快照文件按工作加执行键命名（materials-<workId>-<key>.txt），不覆写旧工作的快照。
  • 资料快照命名：materialsFileFor 按 (workId, key) 命名；v25 之前的旧目录里呈 materials-<key>.txt 的快照仍在磁盘与个人产物登记里有效，只是新的委派不再产生这个名字。

继续、复用与关闭

首次委派之后，同一个 SubAgent（独立子会话与目录都保留）可以被主 Agent 继续沿原工作派活（work_id）、复用承接新工作（sub_agent_id），或显式关闭。继续与复用都经 subagent_delegate 走同一登记与幂等链路（见上「一次委派怎样登记」），且都要先过可用性核查（subagents.ts · assertAvailable）——准备前与登记事务内各核一次；关闭是 subagent_close（主 Agent 的工具调用）或控制面 subagent_close 操作 / CLI ruukoto work close（拥有者，见下一节）。

可用性核查结果
目标 SubAgent 的 parent_session_id 是当前父用户会话不属于本父会话拒绝 forbidden（关闭由拥有者发起时不受这条限制）
closed_at 为空（未关闭）已关闭拒绝 closed，提示「请新建 SubAgent」
state 是 idle 且没有活动任务（queued / running / awaiting_confirmation，store.ts · findActiveSubAgentTask）忙碌或待核实拒绝 busy，给出任务 id，不排队（堵住「running 时再委派覆盖当前任务指针、在跑任务显示空闲」的缺口）
工作目录必须仍存在，且 realpath 与目录身份（realpath、dev、ino）与子会话登记的 cwd_real / cwd_dev / cwd_ino 一致；继续（work_id）修改工作时另核 worktree 的钉定目录身份与 .git 指向的 gitdir目录不存在、被替换或不符拒绝 workdir_gone；worktree 被替换或 .git 指向变化拒绝 worktree_gone，都提示「请新建 SubAgent」，不自动重建

复用时生效上下文是延续的（同一子会话 JSONL 接着旧工作），资料与读范围按新的任务重新钉定：旧资料若已被撤销会先在登记事务的并集复核里被拦掉；子任务正文里另有一句告知模型旧范围不延续。快照文件命名为 materials-<workId>-<key>.txt，复用同一 Agent 时不会覆写旧工作的快照。

整项取消

不再需要的整项工作可以取消：主 Agent 的工具 subagent_cancel(work_id, reason?)（普通 dev 与 main 装配，回报唤醒轮次也允许，因为取消只收窄能力；subagent-tools.ts · subagentCancel），或拥有者经控制面 work_cancel / CLI ruukoto work cancel <工作ID> [--reason R]（runtime.ts · cancelWork）。取消只作用于这一项工作的活动与排队任务，SubAgent 名下的其他工作不受影响；SubAgent 自身（没有该工具，verifyHost 拒绝）与其他父会话的工作一律拒绝（主 Agent 发起时核对 parentSessionId）。取消不关闭 SubAgent、不删除工作目录、会话、JSONL、产物与工作记录；旧 coding 子任务没有 work_id，不纳入工作取消。

修改委派：worktree 隔离与非 Git 串行

普通开发会话与 main（不含固定 coding / chat 角色会话、计划模式任务与 SubAgent 自身）发起委派时可以带 mode=modify + target（父工作区内的目录）：管理器从父 Task 的固定 planMode 判定计划模式，拒绝显式 modify 及沿已有 writeTarget 继续，不接收 planMode 入参（subagents.ts · delegate）。模型工具名单 PLAN_TOOL_NAMES 未开放 subagent_delegate。宿主在事务外解析目标并钉定写入目标（work-copy.ts · prepareWriteTarget），与工作一起经同一登记事务提交，之后继续委派沿用、只读分析工作不能升级为写入。目标分两种：

  • Git 目标：每项工作一个宿主生成的 worktree 副本。位置 <dataDir>/../agent-work/worktrees/<workId>（保护根与父工作区之外），分支 ruukoto/work-<workId>，基线为委派时仓库 HEAD 指向的提交——父工作区未提交的改动不进副本，父工作区字节不变。仓库根从目标向上纯文件系统查找（宿主不运行 git，不越出父工作区）；共享 Git 目录必须位于父工作区内，否则拒绝。副本在受限 confirm 容器里创建：宿主先把副本目录预建为空目录（0700；挂载源必须先存在于宿主，否则 Docker 会以 root 自动创建它、容器内 uid 写 .git 被拒），runtime.ts · createWorktreeInContainer 复用 ToolWorkerHost.start 执行一条宿主固定的 bash（git -c core.fsmonitor=false rev-parse --verify HEAD + git -c core.fsmonitor=false -c core.hooksPath=/dev/null worktree add）——宿主进程本身绝不执行 git，因为仓库的 hooks/config 可能被父任务的容器写入，宿主以后台账户运行 git 会执行其中植入的 fsmonitor / filter（hooks 用 /dev/null 跳过，fsmonitor 显式关）；基线提交按 40 位十六进制从容器输出提取。容器另带 safe.directory=* 环境。创建失败一律保留现场（错误含副本路径与分支），副本不提供删除入口；子任务不能 git add / commit / 推送，改动留在工作树由主 Agent 汇总。
  • 非 Git 目标：直接写入父工作区内的目标目录（不建副本，写预检执行身份可写）。子任务的执行目录与占用键都是这个写入根，与父会话按目录占用串行——目录占用对祖先/子孙前缀判定冲突（见任务生命周期 · 会话队列与目录占用），父任务本轮结束才释放；subagent_result 在本会话自己的占用仍挡着排队中的非 Git 子任务时提示「等待本会话释放目录，请结束本轮」（store.ts · findBlockingOccupancy）。

两种写入目标都经得起替换检查：钉定的 path/dev/ino（worktree 另加 gitdir）在继续委派时逐项复核（worktree_gone），队列启动前与工作进程 init 时再各核一次，被替换即失败、不自动重建。首次钉定后，子会话 cwd 对齐到写入根（store.ts · setSubAgentCwd）；容器按 LaunchSpec 把写入根作为可读写工作区挂载，修改委派任务的共享 Git 目录按只读 readRoots 挂载并注入 GIT_CONFIG_COUNT/KEY_0/VALUE_0=safe.directory=*（见工具调用路径 · LaunchSpec）。覆盖 agent-work/worktrees 或其下位置的读写授予会被 validateGrantedPaths 拒绝（只读仍允许），副本不能经授予路径被旁路写入。复用（sub_agent_id）承接新工作时另建副本，旧工作的改动不进入新工作。任务首行写明工作目录、分支、基线与「不要 git add / commit」，并要求修改工作在副本内完成相关检查、在结论里如实报告（见改动汇总）；TUI 工作摘要标「worktree 分支 X」或「直接写入」。副本改动由主 Agent 经 subagent_integrate 汇回父工作区待提交区（不代提交），见下一节。

改动汇总：副本差异汇入父工作区，冲突不覆盖

主 Agent 用 subagent-tools.ts · subagent_integrate(work_id)（dev 与 main 均装配，回报唤醒轮次也允许——汇总只作用于本会话自己登记的成果；SubAgent、群与固定角色会话经宿主身份重核拒绝）把本会话登记的 worktree 副本「相对基线的完整差异」套用到父工作区待提交区：不代提交、不强制覆盖。宿主只按工作 id 取首次钉定的写入目标——Agent 复用承接新工作（另建副本）后，汇总旧工作仍只落旧工作的副本。非 Git 直接写入工作没有副本（改动本就就地落盘）只如实告知；只读分析工作明确拒绝。

  1. 核实（subagents.ts · integrate）：工作有活动任务拒绝（busy，副本可能仍在被改写）；副本目录 realpath/dev/ino 与 .git 指向的 gitdir 逐项复核（与继续委派同一判定，被替换或消失明确失败 worktree_gone，不自动重建、不凭钉定记录套用）；原工作区的仓库根仍在父会话工作区内且 .git 可读。
  2. 容器内取差异与预检：宿主容器（与创建副本同一入口 createWorktreeInContainer，宿主永不执行 git）在副本里 git add -N --all 把未跟踪文件纳入索引，对基线取完整二进制 diff 与 numstat，再对父仓库 apply --check 预检；fsmonitor 显式关、hooks 走 /dev/null，父仓库本身是 worktree 时共享 Git 目录按钉定记录补一枚读写挂载。
  3. 三套结论：预检过 → git apply 写入待提交区（applied），并在一个事务内追加 work_delegation.integrated 事件（工作 / SubAgent / 发起汇总的主任务 / 分支 / 基线 / 父 HEAD / 文件清单 INTEGRATE_FILE_LIST_CAP 条 / numstat / patch 字节数）；完整差异已在工作区（apply --check --reverse 命中）→ already，幂等返回，不重复写入、不重复登记；两向预检都失败 → conflict（integrate_conflict）：零写入，父工作区原改动与副本成果都保留，错误点名冲突文件与待处理说明。空差异为 empty，不登记。
  • 与取消 / 关闭的关系：整项取消与显式关闭本就不删副本与成果，汇总不按取消 / 关闭状态拦截——取消后、关闭后的成果仍可按工作找回；汇总与关闭同为「读副本 + 写父工作区待提交区」，竞争保持可恢复记录（副本保留 + 事件钉定基线与文件清单）。
  • 展示与核实：TUI 经 work_delegation.integrated 在会话提示汇总规模与来源（tui/state.ts）；工具操作账本按事件存在与否核实（见上文登记失败表）。
  • 后续验证由主 Agent 自己完成：汇总落成待提交改动后，主 Agent 用自己的工具继续检查（类型、测试等），验证不过的待处理内容如实告诉拥有者；SubAgent 的任务输入同样要求其在副本内完成相关检查并报告结果。
已知上限

套用的是副本此刻对基线的全差异——汇总后继续委派产生新改动时，再次汇总会命中冲突（已套用的 hunks 挡路），按冲突如实报告双方保留，不引入增量汇总状态；busy 检查与容器套用之间登记的新执行可能让副本继续变化，副本保留与事件钉定使现场可核对，不加锁。汇总后又遭取消或关闭的副本仍可再次汇总。

SubAgent 状态与结果回报

结果怎样回到主 Agent

执行任务到达终态后，编排器的事件监听或启动巡检把它交给 handleSubAgentTerminal，不走旧角色任务的重试门，也不发 child_task.*。一个事务里：setTaskResult 条件写入摘要与结果引用（重复终态只有先到的一次生效）；调用管理器 resultRecorded(task)，只在当前任务仍匹配时按占用改 SubAgent 状态；追加一条 subagent_task.* 事件，事件归到父会话名下，TUI 在父会话里显示。结果引用 result_ref 记 sessionId、taskId、workId、subAgentId、parentSessionId、parentTaskId、outcome、artifactIds（不含 prompt-snapshot:*）与 failure；结局按任务终态归类，规则与旧子任务相同（见终态怎样归类）。之后交给父级送达（parent-delivery.ts · ParentDelivery）调用一次 resultRecorded，按父会话的会话身份回报。送达指结果进入主 Agent 的一次模型调用：main 是承载它的唤醒任务开始运行时，dev 是下一次任务开始时的注入；此前只是待送达，所属工作被取消即截住（见整项取消）。

main 父会话：唤醒

父级送达以 wake:<子任务>、confirm 经 Runtime 的 submit（模型门闩与执行入口检查）向 main 会话提交唤醒任务；工作已取消就不建，不带来源事件，所以没有自动外发授权。唤醒正文只有固定字段与截断后的摘要，并提示用 subagent_result 按 work_id 读完整结果；IM 发起的工作另在末尾附一段宿主固定的最终汇报说明（parent-delivery.ts · workReportNotice，与 GitHub notice 一起附在唤醒输入尾部）：没有其他进行中任务时这轮最终回答会作为工作最终汇报发回发起入口。main 本轮续派就得在拥有者轮次或下一条 IM 消息里继续——这个唤醒轮次本身经来源门核实不允许再委派（见工具调用路径）——汇报因此自然推迟到真正收尾的唤醒轮次。提交失败由启动巡检 ② 按原键补发（parent-delivery.ts · sweep）。

dev 父会话：下一个任务开始时注入

不产生唤醒任务，也不进唤醒巡检。父会话下一个任务开始时，驱动器经父级送达（parent-delivery.ts · takeInjection）取出还没送达的结果（store.ts · listUndeliveredSubAgentResults），同一事务标记 result_delivered_at，再作为 [SubAgent 结果] 参考块放进模型上下文（context-assembly.ts）。标记后若崩溃，结果仍可从事件与 subagent_result 查到。参考块的写法与位置见上下文组装 · SubAgent 任务的上下文。

  • 读结果：subagent_result 只读工作登记在当前会话的记录：省略 work_id 时返回本会话 SubAgent 的总览（状态或已关闭、当前工作、名下工作、最近任务状态，供挑选继续或复用对象，store.ts · listSubAgentsBySession）；指定时 part=result（默认）给工作、SubAgent 是否已关闭 / 状态与每次执行的摘要；part=reply 按 UTF-8 字节分页读最终回答，每页至多 READ_LIMITS.replyBytes（16 KiB）；part=artifact 读该次执行自己的产物，每页至多 artifactBytes（64 KiB）。不给 task_id 时取最近一个已有结果的执行，都还没有结果时取最近一个。已关闭后历史与产物仍按原窄口可读。main 的 coding_result 也能读这些执行任务（见旧 coding 子任务）。
  • 唤醒终态后由宿主判定收尾，向发起入口登记工作最终汇报：main 唤醒任务到达终态时，编排器在结果事务内除照常写结果与 child_task.* 之外，只要这条结果首次写入，就在同一事务里调用父级送达的 wakeTerminal（只处理 requestId 以 wake: 开头的唤醒；与 onInboundTerminal 并列，都是结果事务的一部分；重启巡检补记结果时一并补登）。到期判定、发送键与正文由父级送达决定，IM 机制经回调交拥有者 IM 入口表（im-entries.ts · sendWorkReport）：宿主判定满足才登记 owner_reply——工作未取消、发起事件是 IM 私聊的普通任务、没有活动执行任务、其余执行的唤醒都已记录结果——满足即发回 work 的发起入口，内容与目标规则见入站事件 · 工作最终汇报发回发起入口。旧 coding 子任务的唤醒（见旧 coding 子任务）不属于任何工作，wakeTerminal 判定不满足，不外发。
  • 拥有者查看与关闭：控制面只读操作 work_list / work_get（CLI ruukoto work list / ruukoto work show）列出工作、SubAgent（含关闭两列）与执行任务；拥有者经 subagent_close（runtime.ts · closeSubAgent，CLI ruukoto work close，cli.ts）随时显式关闭——有活动任务报 busy 并给任务 id，等任务结束或先 ruukoto cancel 再关，已关闭幂等；停止中（stopping）拒绝。普通的提交、继续、切换模式与会话默认模式都不能作用于子会话。协议见控制面协议。

停止与重启时

  • 执行中的任务：后台停止（runtime.ts · doStop）或崩溃后恢复（runtime.ts · recover）时把它转为 interrupted，这时编排器已经停下或还没启动，没人监听；编排器启动时由巡检 ① 补记（listRoleTasksPendingResult 同时选带 sub_agent_id 的任务），结局为结果未知，发 subagent_task.result_unknown。留下了占用的（崩溃，或停止时没能回收工具进程），恢复时子会话被暂停为 occupancy_unverified，SubAgent 记 unverified；停止时工具进程已回收的记 idle。main 父会话随后被唤醒，dev 父会话等它下一个任务开始时注入。
  • 排队中的任务：重启时仍排队的拥有者 / 主 Agent 委派任务（没有来源事件）由 Runtime 恢复事务调用管理器 recoverQueuedTasks 转为 interrupted（backend_restart，从未启动）：不自动继续、也不当作成功或新委派；编排器巡检 ① 补记结果（store.ts · listQueuedSubAgentTasks），当前任务仍匹配时身份按占用情况记 idle 或 unverified，main 父会话被唤醒、dev 父会话注入，是否重新委派由拥有者 / 父 Agent 决定。宿主固定评审（带来源事件）的排队任务不中断：子会话队列被暂停为 backend_restart 后，由管理器 start 在无遗留占用时自动解除（角色队列归编排器，见重启恢复），继续执行。
  • 不重放、不重试：结果未知的执行不自动重发，也没有自动重试。
  • 关闭与重启：关闭同步写 closed_at / closed_by 两列与 subagent.closed，同事务仅清理发给该 Agent 的 pending 消息（归父会话的持久事件）；不取消在途任务——有活动任务报 busy 并给任务 id，等任务结束或由拥有者 ruukoto cancel 后再关；不撤销既有产物、子目录、JSONL 与工作记录。

协作加入

work_id 与 sub_agent_id 同现且目标不是该工作的当前承接者时，delegate 把一个既有空闲且未关闭的 SubAgent 拉入同一项只读工作协作（subagents.ts · delegate）：登记的事务、可用性核查、限额与请求键 sdelegate:<工作>:<key> 与继续原工作完全相同，只是不新建工作、不发 work_delegation.created（任务输入由 taskInput 固定生成，含「你加入了既有工作作为协作方」的说明）。查重按目标 Agent 的会话核实同键（dedupWorkTask，不同协作方的键按各自 Agent 的目标 Agent 的会话独立，不与其它 Agent 冲突）；登记事务内 竞争仲裁 仍按目标 Agent 会话的同键核实提交摘要：同参返回、异参冲突。修改工作与宿主评审工作拒绝加入：WorkDelegation.subAgentId 只记首次承接者，协作加入的其他 SubAgent 经 tasks 关联列记录（work_get 的 tasks 列表带全部执行）。加入后彼此可用 subagent_message 通信。

工作内消息

主 Agent 与当前承接同项工作的 SubAgent 可互发带来源的消息（宿主固定评审不参与）。subagent_message 的发送方由发起任务核实，不接受身份参数：子任务须属于本工作，父任务须属于本父会话；主 Agent 必须指定 to_sub_agent_id。正文上限 MESSAGE_TEXT_CAP = 4096 字符，投递输入仍受 INPUT_TEXT_CAP 限制。

message 先按（工作, 发送方, 键）查重：同键同参返回原记录，即使此后已关闭 / 已取消；异参报 request_conflict。新消息异步准备（prepareMessageDelivery）：发给子会话或 main 唤醒时，在事务外核实模型配置与受限执行入口，登记事务内再次查重、调用预检返回的 check 并重核当前资格与模型选择（checkMessageDelivery）。model_config_busy 等预检失败或模型选择变动，零新增消息、任务与事件；忙碌 / 名额满也不能绕过预检。纯 dev 父会话注入不创建新执行，无需执行预检。

继续、复用、加入、消息登记与冲刷共用管理器私有 eligibility 判断。目标须属于本父会话、未关闭、当前仍承接本工作；工作取消、跨父会话、宿主评审、已转做其他工作均明确拒绝或记未投递。异步准备期间可能登记新委派，投递事务必须重核 active_work_id；旧消息不能进入新工作。忙碌或名额满只让消息保持待投递，限额仍为 SUBAGENT_LIMITS.perParentSession = 3；不增加锁。

发给 SubAgent 的消息由 deliverAsTask 登记本工作的一次 confirm 执行（请求键 smsg:<消息ID>），读范围沿用其本工作最近任务，模型选择使用已经核实的 selection。发给主 Agent 的消息在同一事务交给 ParentDelivery.messageRecorded(msg, work, selection)：main 只用已核实的 selection 插入消息唤醒（confirm、无截止），dev 待下一次任务开始时注入。消息不扩大工具或资料范围。

flushPendingMessages 异步冲刷已登记消息：先经 pendingMessageContext 核资格，忙碌 / 满额保留待投递并跳过预检；具备投递条件才经 prepareMessageDelivery 预检，再在投递事务内重核当前资格、模型选择与投递标记。任意预检失败保留待投递并输出诊断。触发点为结果事务之后、启动、取消、resume-queue 核实完成和模型配置应用结束（applyModelConfigChange 的 finally 等待冲刷，成功与回滚都覆盖）。关闭保持同步，只在关闭事务内清理目标 Agent 的 pending 消息；资格已失则由 dropMessage 记 undelivered_reason 并发 subagent_message.dropped，例如 work_canceled、closed:…、moved_work、agent_missing。消息登记发一次 subagent_message.sent，冲刷成功只更新消息与任务，不补发 sent。

重启恢复

Runtime 先跑自己的恢复（执行中的任务转 interrupted、未决审批失效，见任务生命周期），再启动编排器。Runtime 恢复时编排器还没创建，这时产生的 task.interrupted 没人监听；重启窗口内到达终态的任务全靠巡检补记。orchestrator.ts · start 按顺序执行：

  1. 引导角色：只引导 main，已有的角色行（含已退役的 coding、chat）原样保留。
  2. 已登记、未建任务的入站事件按原请求键串行重提（派发细节见入站事件）；类别不是 task 的控制事件（正常路径不会有遗留）不派发为模型任务，一律以 inbound.skipped（control_event_not_dispatched）作废（dispatchEvent）。
  3. 巡检 ①：已终态但结果未记录的角色任务与 SubAgent 执行任务补记结果与事件（store.ts · listRoleTasksPendingResult）；interrupted 记为结果未知，不重放。旧 coding 子任务的升级收尾也在这一步（见旧 coding 子任务）。
  4. 巡检 ②：父级送达为结果已记录但缺唤醒的子任务按 wake:<子任务> 补建，消息唤醒补建交给下一步的管理器冲刷（sweepPendingResults → parent-delivery.ts · sweep）。
  5. 管理器 start 先等待冲刷消息，再自动恢复无遗留占用的 backend_restart 子会话；编排器只恢复角色队列（resumeRestartPausedQueue）。恢复保留的 SubAgent 排队任务属于宿主固定评审；冲刷还可能登记新的消息投递任务。重启时的拥有者 / 主 Agent 委派排队任务已由 Runtime 恢复定 interrupted（见停止与重启时）；occupancy_unverified 等涉及未核实旧执行的暂停留给拥有者核实。
  6. 开始截止巡检。

后台停止时，编排器在 GitHub webhook、调度器与 Telegram 之后，QQ 适配器与中断活动任务之前停下（runtime.ts · doStop）：清掉巡检定时器，等派发串行链收尾，此后不再产生取消或唤醒。停止路径随后中断的角色任务没人监听，由下次启动的巡检 ① 按结果未知补记。

  • 报告：子任务终态登记时（orchestrator.ts · handleSubAgentTerminal），events.ts · resultData 把最终回答逐页写进产物 review-draft:<事件>，读满记录的总字节数才标记完整。分页缺失或写入失败时产物保持 partial，结果记 captureError 并要求拥有者核实。
  • 有效性：result_ref.review 保存事件 ID、PR URL、仓库 ID、PR 编号、head/base SHA、产物 ID 与 staleReason。events.ts · staleReason 在 PR 已关闭或为 draft，或同一 PR 有 updatedAt 不早于本事件、但 head、base、状态或 draft 不同的事件时返回原因。
  • 失效：新事件登记时（events.ts · register）在同一事务里给旧事件的评审结果写 staleReason，并取消旧事件尚未发送的通知（发送中的只记取消请求）；旧事件还没派发或还没开始的任务被入站门丢弃（events.ts · gate）。旧产物保留为不可变记录。
  • 通知：events.ts · terminal 只接受「本事件评审 SubAgent 执行任务」的唤醒任务；事件已失效、webhook 停用、owner 目标未配置或已变化时改记 inbound.skipped，不发送。

  • 快照：接收保存 result_summary 的前 SUMMARY_CHARS = 1000 个 Unicode 字符、来源任务、接收任务、宿主操作 ID 与理由（1–1024 字节）。（main 项目，任务）为主键，首次快照固定，重复接收不改写，只有首次写入发 chat_result.accepted（store.ts · acceptChatResult）。列表每页 1–50 条，默认 20（chat_result_list）。
  • 撤回使摘要失效：该群任何一条在任务结束前收到、并在任务开始后（或时间未记）被撤回的消息，都会让这次结果不可接收，已接收的快照也不能再被解析或外发。这是按时间窗的保守判定，可能拒掉其实没引用被撤回消息的摘要。退役后撤回仍打标记（见入站事件），这项复核继续生效；撤回事件只在 NapCat 连接期间观察到，缺口如实记录（见qq.receive_gap）。已经进入 main 历史或已发送的副本不追溯清除。
  • 接收不是外发授权：通知与通知计划引用快照时经 resolveAcceptedChatResult 核对 main 项目与撤回，登记仍要拥有者审批（通知 outbox）。快照也不开放原始群历史、产物或带群来源的记忆，subagent_delegate 不能把它当委派资料。
