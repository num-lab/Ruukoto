发送操作的状态与转换

每条外发通知是 notification_ops 里的一行发送操作：目标、正文与操作 ID 在登记时写定，之后不再改。pending 是未领取，sending 是已领取、请求可能已经发出；sent、failed、effect_unknown、canceled 是终态，进入后不再转换，也都不自动重发（store.ts · NotificationStatus）。

转换触发者条件与位置事件
新行 → pending 宿主登记方，见逻辑发送键 按 (source_kind, source_key) 查重：不存在才插入；已存在且正文摘要与目标都相同，返回原行、不写新事件；否则抛冲突。

runtime.ts · finishNews		 notification.changed，reason 为错误类型
pending 保持，写等待原因 发送循环 发送器未加载（sender_unavailable）或渠道离线（channel_offline）：不领取，只在原因变化时写 wait_reason，下一轮再查。

不变量

每次转换都是条件更新（WHERE status = …），状态与 notification.changed 同一事务提交、提交后才广播。本地保证的是「一个逻辑发送键至多一行、一行至多一次可能产生副作用的调用」（限流退回后同一行会再调用一次，但被退回的那次可证明没有发出）；平台没有幂等支持，远端是否恰好一次无法保证，effect_unknown 由拥有者核实（notification_query、ruukoto notify show）。

扫描循环与发送循环

调度器是宿主组件，不进入任何会话的任务队列、不占用工作目录。内存定时器只负责唤醒扫描，规则、下一触发时间、运行与发送状态都以数据库为准。

扫描循环 runtime.ts · tick

每 1 s 一次（runtime.ts · tickMs ?? 1_000），不重入：上一轮没结束时返回同一轮。一轮依次做：关闭已结束的运行 → 取到期计划（每批 batch: 50，每轮至多 batchesPerTick: 20 批）逐个做到期事务 → 本轮新登记了 wake_main 事件，或距上次派发满 redispatchMs: 30_000 且库里仍有 registered 的普通任务入站事件（任何来源；hasUndispatched 只数 event_kind = 'task'）时，请编排器派发 → 唤醒采集循环与发送循环。

发送循环 runtime.ts · drainSends

独立于扫描循环，kickSender 已在跑或正在停止时不另起一轮。唤醒来自每轮扫描末尾、调度器启动、每次新闻采集收尾、notification_enqueue 登记后、IM 初始通知与多数 IM 命令回执提交后，以及 IM 配置变化后的复核。每轮按渠道各取最早的至多 batch 条可领取 pending（store.ts · listPending，遵守 not_before），逐条串行处理：一次只有一个在途操作；离线渠道的积压只写等待原因，挡不住另一渠道。慢发送不阻塞到期登记与控制面。

本地写入失败时

收尾事务本身失败（例如数据库异常）时，操作保留 sending，不回退 pending；下次重启由恢复准备定为 effect_unknown。停止时（runtime.ts · stop）先拒绝扫描与领取，再中止在途发送与采集并等待收尾，最后关闭屏障，之后迟到的回调不再写库。

ruukoto-dev 没有调度器

调度器只在个人 Agent 产品 ruukoto 里创建（runtime.ts · 创建条件）。Coding Agent ruukoto-dev 启动时跳过创建、恢复准备与启动，所以没有扫描、采集与发送三个循环，各处的 scheduler?.kickSender() 都是空操作；会话不装配 schedule_* 与 notification_* 工具。QQ 与 Telegram 适配器被强制停用（runtime.ts · qqDisabled），所以也没有 owner 回复、IM 审批命令与初始通知的来源；即使配置了 GitHub webhook，事件入站时取不到通知目标，结束时只记 inbound.skipped（events.ts · terminal）。控制面的计划与发送记录照常可查，notification_cancel 照常改库；schedule_cancel 返回 unavailable（runtime.ts · scheduleCancel）。

逻辑发送键与固定发送授权

发送键由宿主按来源决定，模型只能提供正文来源，不能传入发送键、接收者、URL、chat/user ID、凭据或审批 ID。数据库上 UNIQUE (source_kind, source_key)（db.ts · notification_ops）；同键同正文同目标返回原记录，同键异参冲突，所以模型无法换一个键绕过一次 effect_unknown（效果未知）的发送。

图片拒绝的固定文本回执

宿主 runtime.ts · enqueueMediaReceipt 把图片永久拒绝、重试耗尽与模型不支持登记为 inbound_event 发送操作，键固定为 media:<消息暂存ID>；该 ID 由媒体消息账本的 (source, external_id) 唯一约束确定，不冒充普通入站事件 ID。图片拒绝不建普通模型任务；模型不支持在入站已登记后的派发前判定时作废该事件，仍不建任务。下载拒绝已落盘但回执未登记的窗口，启动恢复补登同一个键，不因重投重复发送。

拒绝类别固定回执来源记录
MIME、magic、大小、数量或图片不可取得提示只支持 JPEG、PNG、WebP，每条 4 张、每张 8 MiB，并说明消息未执行媒体账本的永久拒绝事实；上限与原因见图片入站
download_failed / download_interrupted提示图片下载未完成、消息未执行，请稍后重新发送有界重试耗尽或重启时缺完整文件；不发送平台错误正文或下载 URL
image_input_unsupported提示当前模型不支持图片、消息未执行，请配置视觉模型后重新发送模型能力不含 image；已建任务或继续任务的防御复核失败用既有 owner_reply 槽发送相同固定提示（im-entries.ts · enqueueOwnerReply）

回执目标固定为原收件入口；发送前 Runtime · verifySources 重读媒体消息，要求状态 rejected 或 expired、actor 是该入口的预期拥有者、消息钉版目标和操作目标、当前目标一致。入口换代后取消发送，不改发；发出结果未知照常保留 effect_unknown 并停止自动重发。模型自由生成内容不会成为错误回执。

固定发送授权

统一审批，完全访问也不例外

notify 与 news 计划、一次通知都经审批闸门，审批范围 kind 为 notification，mode 分别是 schedule、news、once，固定目标及配置版本、正文摘要与长度、规则描述、持续范围（single / until_canceled）与来源引用。调度工具直接调用审批闸门，不看访问模式，完全访问模式也要拥有者确认；自动审查模式下 notification 范围不属于可审查类别，直接转拥有者（review.ts · classifyForReview）。这是 ADR 0010 对 ADR 0003 的例外。

scheduler-tools.ts · approveThenCommit

获批后同事务重核

批准消费的事务里先重核身份（按调用开始时捕获的上下文）、目标是否仍与审批时相同、来源资料是否仍可读；IM 来源任务的审批另核 IM 固定身份（im-approvals.ts · consumeRecheck）。全部通过才消费批准并写入计划或发送操作；任一失败即作废批准、不登记。闸门细节与单次消费见工具调用路径。

目标只来自可信渠道配置

工具拿到的目标由宿主给：来源是 QQ 私聊的任务绑定该消息登记时的 QQ 目标（须与当前配置相同），其余沿用 Telegram 默认目标（im-entries.ts · notificationTarget）。未配置目标即拒绝创建外发。目标配置版本变化或停用后，未领取的旧操作在发送前复核时取消，已领取的由适配器记 failed，都不改发到新目标或另一平台（见固定目标）。

调度计划与调度运行

main 经 schedule_create 登记调度计划（scheduler-tools.ts · schedule_create）。创建键在 main 范围内唯一（存为 main: + 键），同键同参返回原计划、异参冲突；活跃计划上限 maxActive: 1000。首版不支持编辑：改时间、正文、动作或新闻范围都是取消后重建，外发计划重新确认。

动作到期事务里登记创建时
wake_main入站事件（source scheduler，external_id = 运行 ID），提交后由编排器派发为 main 任务；派发见入站事件不需审批；触发说明 ≤ noteBytes: 4 * 1024 字节。唤醒任务不继承外发授权
notify发送操作（schedule_run，键 = 运行 ID），正文是批准的原文正文来源登记前解析为最终文本（≤ textChars: 2000 字符且 ≤ textBytes: 8 * 1024 字节，超限拒绝、不截断），经审批
news运行上的采集快照（状态 pending），此时还没有发送操作固定关键词、来源域名与窗口，经审批；main 项目须启用 Web Search

规则只有一次性、每日、每周三种（time.ts · parseRule）：一次性时间必须带 Z 或显式偏移；每日、每周是当地 HH:mm，每周用 ISO 星期 1–7；时区必须是 IANA 名，不接受裸偏移。每日、每周按当地日期加原定钟点重新构造，不做固定 24 h / 7 d 相加。DST 固定 compatible：不存在的当地时间按缺口向后移，重复时间取较早一次。偏移与 DST 计算交给 time.ts · Temporal polyfill；计划上记录计算所用的 Node/ICU/tz 版本（time.ts · tzDataVersion）。首次到期：一次性取原定时刻（已过去就在登记后的下一轮扫描延迟触发一次），周期取登记后第一个时刻；外发计划在批准提交时重算，等待确认期间错过的时刻不算漏过。

计划状态怎样进入事件
active登记即 active，version 为 1schedule.changed（created）
completed只有一次性计划：它唯一一次运行关闭、next_due_at 为空后标完成（store.ts · completeSchedule）。周期计划持续到取消schedule.changed（completed）
canceledschedule_cancel（main 工具或拥有者控制面），带预期版本：已取消的幂等返回原记录，已完成或版本不符报冲突；取消后不复活schedule.changed（canceled）

到期事务

每个到期计划一个短事务（runtime.ts · fire），事务内只读写核心库，不等网络、模型或应用库：

  1. 重读计划：仍是 active 且 next_due_at 已到，否则跳过。
  2. 取截点前最近一次应发生时刻作为原定时刻（time.ts · latestAtOrBefore），但不早于持久化的 next_due_at：时钟回拨或时区数据更新不回退处理范围。
  3. 算下一触发：一次性为空，周期取原定时刻与现在两者较晚者之后的下一次（time.ts · nextAfter）。
  4. 计划已有未关闭运行：把漏过区间并入它（store.ts · coalesceRun），推进下一触发，结束。不登记新事件或操作，原键、原正文不变。
  5. 否则新建运行：写原定时刻、当地时间、delay_ms；原定时刻不等于 next_due_at 时写合并区间 coalesced_from / coalesced_to；按动作登记入站事件、发送操作或采集快照；推进下一触发并把它设为当前运行。
  6. 提交后才派发 wake_main 的入站事件；派发失败的事件保持 registered，按补派间隔重试同一事件。

运行按 (schedule_id, schedule_version, scheduled_for) 唯一，部分唯一索引保证每个计划至多一个未关闭运行（db.ts · idx_schedule_runs_open）。运行在关联记录结束后关闭（runtime.ts · closeFinished）：有发送操作的看它离开 pending/sending（新闻运行采集完成后也有发送操作，要等它发完）；还没有发送操作的新闻运行看采集离开 pending/searching；wake_main 看入站事件 done/failed 或关联任务到达终态。结果是 failed 或 effect_unknown 的运行照样关闭，不自动重试。

取消计划

runtime.ts · cancelSchedule 在编排器串行链上执行，覆盖与派发的竞争。一个事务里：计划转 canceled、清空 next_due_at、版本加一；当前运行的 pending 发送操作取消（sending 只记取消意图）；未完成的新闻采集标 canceled；还没派发的入站事件作废。事务提交后先中止在途采集，再经现有取消入口取消仍在排队的关联任务。已经开始运行的任务与在途发送保留真实结果。

新闻计划复用调度计划、调度运行与公共 outbox（ADR 0015），但采集由宿主完成：不创建模型任务，不装配会话历史、项目资料、应用数据或记忆工具。采集在独立循环里串行进行，不占用 main 会话或发送循环（runtime.ts · drainNews）。

渠道与两本账

公共 outbox 按发送操作上持久的 target.channel 选发送器（im-entries.ts · channel）：qq_private 交 QQ 适配器，telegram 交 Telegram 适配器；其他取值，或对应入口由启动配置停用（适配器照常创建，但不算已加载的发送器），都没有发送器，操作保持 pending。测试可经配置注入模拟渠道（QQ 私聊之外的渠道都交给它）。QQ 群的普通回复（旧架构 QQ 群聊入口）不走公共 outbox，而是 QQ 适配器自己的 qq_outbox；核心群聊已退役（agent-direction 工单 20），qq_outbox 不再有新增，保留为只读归档。QQ 连接的代次键含配置版本（connectionKey）：任何配置或凭据变化都重建连接，旧连接上的事件不再接纳，断开时旧连接上还没应答的动作按结果不明拒绝（私聊发送记 effect_unknown；退役前的群回复记 unknown）。两个平台的配置变化对公共 outbox 的影响都靠目标比对拦截，见固定目标。

重启恢复与停止

本节按个人 Agent 产品 ruukoto 的启动顺序写。Coding Agent ruukoto-dev 不创建调度器，QQ 与 Telegram 适配器照常创建但按启动配置停用、不连接（agent-direction issue 01，架构工单 10），下面第 1、2、6、7 步对它都不发生。启动顺序里，调度器的恢复准备排在通用任务恢复之前（runtime.ts · prepareRecovery 调用处）：它要先按关联记录的真实状态决定运行开着还是关着，再让通用恢复把 running 任务改写为 interrupted。

  1. 创建调度器（runtime.ts · initScheduler；仅个人 Agent 产品），此时不启动定时器、不派发、不发送。
  2. 恢复准备（runtime.ts · prepareRecovery）：① 关联记录早已终态、只是关闭标记没写上的运行先补关闭；② 到期计划按正常到期事务处理，仍在 registered/queued/running/pending/sending/searching 的运行吸收漏过区间，没有未完成运行的计划补一次；③ 一个事务里把遗留 sending 全部定为 effect_unknown（backend_restart）；④ 停在 searching 的采集定为 unknown，登记 news_backend_restart 的 failed 发送操作，同一窗口不重搜。
  3. 通用任务恢复：running 与 awaiting_confirmation 转 interrupted，见任务生命周期。
  4. 固定角色退役收尾（runtime.ts · retireLegacyRoles，通用任务恢复之后、编排器启动之前）：遗留 pending 的群回复一律定为 unknown，对应仍在 queued 的收件记 reply_unknown；群会话排队任务取消（原因 core_group_chat_retired），旧 coding 角色会话的排队任务取消（原因 coding_role_retired:…）；剩余未终态收件记 skipped。
  5. 编排器启动：先恢复图片暂存并补登固定拒绝回执（见图片入站），再按原请求键重提已登记未建任务的入站事件，补记重启窗口内结束的任务结果；owner 回复与 GitHub 评审通知随这次结果事务补登。结果只写一次，已记录结果的任务不再登记。
  6. QQ 适配器启动（只为私聊），Telegram 开始轮询。
  7. 然后 scheduler.start()（仅个人 Agent 产品）：开定时器，唤醒发送循环与采集循环，到期扫描从这里开始。GitHub webhook 在它之后才开始监听。
为什么必须在通用恢复之前

如果先改写，停机时仍在执行的唤醒任务会先变成 interrupted，它的运行被当作已结束而关闭，漏过的周期就会另建一次运行、再唤醒一次 main。先做恢复准备，这类运行还开着，漏过的周期并入它。遗留 sending 同理放在补关闭与合并之后才定为未知：发送中断的运行在这次恢复里仍算未完成，漏过的周期不会另发一次；它在之后的正常关闭中释放。

后台停止时，调度器在 GitHub webhook 之后、Telegram 轮询、编排器与 QQ 适配器之前停止（runtime.ts · doStop）：停止扫描与领取，中止在途发送（记 timeout_or_abort 的 effect_unknown）与在途采集（采集记 unknown，登记 news_canceled 的 failed 发送操作）并等待收尾。退役后不再有新的群回复；停止前的在途群回复假如仍有 pending，也由下次启动的退役收尾定为 unknown。
