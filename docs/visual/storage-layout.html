存储布局

每份数据在哪、谁写谁读、哪份是权威、崩溃后怎么对齐。两个产品各有一棵档案目录；会话历史以 pi JSONL 为唯一权威，ruukoto.db 存元数据、事件与可重建的索引，产物正文在产物文件，入站图片在任务创建前另有安全暂存，main 的应用数据另有一个独立库。这几份之间没有跨文件事务，靠写入顺序与重启恢复对齐。

目录与文件：按产品分开

产品身份只来自环境变量 RUUKOTO_PRODUCT（两条 bin 入口固定注入；缺省为 ruukoto，非法取值直接报错，product.ts · productFromEnv）。档案根按产品分开（product.ts · productRootDir）：个人 Agent 是 ~/.ruukoto，Coding Agent 是 ~/.ruukoto-code。数据、agent、pending 三个目录默认在根下（data/、agent/、pending/），控制面目录默认是数据目录的兄弟目录 control/（connect.ts · controlDirFor）；server 的 --data-dir / --agent-dir 参数优先于默认值。

路径环境变量同样按产品隔离（product.ts · dirEnvFor）：ruukoto 只读 RUUKOTO_DATA_DIR / RUUKOTO_AGENT_DIR / RUUKOTO_CONTROL_DIR / RUUKOTO_PENDING_DIR，ruukoto-code 只读 RUUKOTO_CODE_DATA_DIR / RUUKOTO_CODE_AGENT_DIR / RUUKOTO_CODE_CONTROL_DIR / RUUKOTO_CODE_PENDING_DIR。拥有者令牌的 RUUKOTO_OWNER_TOKEN / RUUKOTO_OWNER_TOKEN_FILE 不分产品，两边同名。各类工作目录（qq-work/、agent-work/）由 dirname(dataDir) 推出，跟着数据目录走，而不是跟着档案根走。

开发本项目时，npm run dev 以 ruukoto 身份继续使用 ~/.ruukoto-dev/<仓库名>-<realpath 哈希前 8 位>/，npm run code 以 ruukoto-code 身份使用独立的 ~/.ruukoto-code-dev/<仓库名>-<realpath 哈希前 8 位>/（dev.ts · devProfileFor，哈希长度来自 slice(0, 8)）。各档案下有 data/ agent/ control/ pending/ logs/ 与 reload-state.json，与日常产品档案分开，不自动迁移历史。后台直接以 src/cli.ts 启动；子进程先清除两产品目录变量、外部产品身份与生产认证和执行配置，再显式注入 RUUKOTO_PRODUCT 与本产品的 RUUKOTO_*_DIR 或 RUUKOTO_CODE_*_DIR（dev.ts · buildChildEnv），各库按本产品登记 product.type。入口、执行后端与停用消息通道的规则见开发实例。

不变量

两个产品的默认数据、锁、socket 与令牌路径互不重叠；即使有人把两个产品指向同一个数据目录，库里登记的 product.type 也会让后来的产品拒绝启动（见 schema 与迁移）。保护根之外的目录只放客户端记录和工作目录，后台自己的数据、凭据与控制面全在保护根内。

三份权威来源，没有跨文件事务

db.ts 开头写明：SQLite 与 JSONL 没有跨文件事务，实现不得声称两者原子。各份数据的权威划分如下：

  • 会话历史：pi JSONL 是唯一权威副本，SQLite 不重复存会话消息正文；入站信封与任务输入另有宿主记录。读取严格解析（history.ts · parseSessionFileStrict）：完整行损坏即报 history_corrupt，不静默跳过；尾部没有换行的行视为正在写入，不算完整消息。但 pi SDK 下次打开这个文件时会先给尾部补一个换行，崩溃留下的半行由此变成完整的坏行，之后严格解析就报 history_corrupt。
  • 任务状态、审批、事件与其余元数据：ruukoto.db 是权威。JSONL 里的任务结束标记只是「历史已写完」的证据，不决定任务状态。
  • 产物正文：artifacts/<id>.bin 是权威；artifacts 表存归属、字节计数与 partial / complete，图片另有 mime_type 与 content_hash（SHA-256）。暂存尚不属于产物；提升、崩溃恢复与无任务暂存清理见图片入站。
  • 可重建的派生数据：history_index 记录每条 JSONL 条目的字节位置，history_index_state 记录文件身份（路径 + dev + ino）与已处理字节数。检索时按需增量同步；文件被替换、截断或状态缺失时删掉该会话的索引从头重建，只动索引、不碰源文件（history-index.ts · sync）。

本项目代码里没有删除或改写 JSONL 与产物文件的路径；上下文压缩只作用于模型上下文（ADR 0016），迁移也不搬动这些文件（ADR 0018）。改动 JSONL 的只有 pi SDK 打开会话文件时的修复：尾部补换行、空文件写入会话头、旧格式版本整文件重写。

窗口两次写入崩溃在中间时重启后怎样对齐
1 会话文件路径SDK 会话建好后、发 prompt 之前，Driver 在独立事务里把 sdk.sessionFile 写进 sessions.session_file（「尽早落库」）；完成核对时若登记值不同再写一次。新会话的文件要到首条助手消息才由 pi 创建，之前的条目只在内存里，所以登记总是先于文件出现。
driver.ts · runInner		库里已登记路径，文件还不存在（崩溃在首条助手消息落盘之前）；或登记的文件丢失、目录里另有同 piSessionId 的文件runtime.ts · recover 第 4 步：登记的文件不存在（或未登记）时，在 sessions/ 找 *_<piSessionId>.jsonl，取排序最后一份（文件名以创建时间开头）写回，保证继续写同一份历史。原先登记过路径的，改用或找不到都记 session.history_unreadable；从未登记过的静默写回。登记的文件仍不存在时，下次执行以同一 piSessionId 新建文件并重新尽早落库（session-factory.ts · openPiSessionManager）。
2 结束标记与核对自然结束时先向 JSONL 写 ruukoto_task_end 标记（types.ts · TASK_END_MARKER），再严格解析 JSONL、找到本任务的开始与结束标记，在一个事务里写 history_entry_ids，最后在另一个事务里条件更新为 completed。
driver.ts · verifyAndLinkHistory		JSONL 里有 status=completed 的结束标记，tasks 仍是 runningrecover 以库为准，把 running / awaiting_confirmation 一律转 interrupted（backend_restart）。核对本身失败时：标记缺失 → history_unverified:…；JSONL 解析失败 → history_corrupted:…，记 session.history_unreadable，原文件保留待人工处理。
3 位置索引索引只在检索时同步：按已完整落盘的换行记录追加，写完再更新 processed_bytes。索引落后于 JSONL，或状态行比部分已写条目旧下次同步从 processed_bytes 续扫，已存在的条目 ON CONFLICT DO NOTHING；文件身份变了或文件比已处理位置短，就删掉该会话索引从 0 重建。索引坏了不影响历史本身。
4 产物字节先 appendFileSync 正文，再 addArtifactBytes 累加计数；只有结果回收后才定稿为 complete。文件比 byte_count 多一段；状态停在 partial读取按文件实际长度切片；元数据仍是 partial，如实表示未定稿。磁盘写失败时停止捕获并保留已写部分（ArtifactWriteError）。

schema 版本与迁移

当前版本 v32（db.ts · SCHEMA_VERSION），写在核心库 meta 的 schema_version 键里。Db 构造时读这个键，按下表处理；迁移只在后台启动打开库时发生。

文件里的版本行为
无版本记录（全新库）一个 BEGIN IMMEDIATE 事务内建全部表、补列、写版本。
高于程序抛「schema 版本过新：文件 N，程序 32（需升级程序）」，后台启动失败，文件不动。
等于程序幂等执行建表语句与补列，只补齐缺失对象。
1 到 31一个事务内：建表（IF NOT EXISTS）→ db.ts · migrateFrom → ensureColumns 补列 → 必要的重建 → 写版本。任何一步抛错整笔 ROLLBACK，报「schema 迁移失败（vN → v32）」，旧库保持原样。从 v1 迁移另把旧的 pending 审批全部置 stale。
其他（如 0）「不支持从 schema vN 迁移」，同样回滚。

SQLite 改不了 CHECK 约束，涉及 CHECK 的旧版本用 *_new 临时表重建：版本低于 6 时重建 tasks_new / sessions_new（访问模式加 auto-review，db.ts · rebuildModeCheckedTables），13 到 15 重建 notification_ops_new（来源类别加 inbound_event），13 到 17 重建 schedules_new（动作加 news），28 / 29 重建 instance_import_items_new（导入账本类别扩展）；低于 32 时重建 sessions_new（会话默认值加入 plan，rebuildSessionModeCheck）。步骤是建新表 → 按显式列清单 INSERT … SELECT → 删旧表 → 改名 → 重建索引。外键开关在事务内无效，所以在事务外先关 foreign_keys，提交前跑 PRAGMA foreign_key_check，有违规就抛错回滚，最后在 finally 里重新打开。

提交 d139561 时库是 v18；v19 至 v29 通过建表语句（IF NOT EXISTS）增加表与 ensureColumns 补列。v30 重建导入账本的 CHECK 并保留行，v31 增加入站媒体两表与图片产物元数据，v32 增加任务计划字段并扩展会话默认模式。

产品归属

Runtime 启动时打开核心库之后读 product.type（runtime.ts · start）：记录的产品与当前产品不同，就关库、释放配置锁与实例锁，以 product_mismatch 拒绝启动；没有记录（全新库，或工单 01 之前的旧库）就在事务外直接补记当前产品。

已知限制

产品核对排在 new Db() 之后，所以用错误的产品打开一个版本较旧的数据目录时，schema 迁移会先完成，然后才被拒绝。登记了 product.type 的目录至少是 v18（工单 01 时的版本），之后的迁移在事务内保留旧行（v30 重建导入账本 CHECK）；但原产品若仍在用旧版本程序，之后再打开这个目录会因版本过新被拒。原产品的后台正在运行时不会出现：实例锁在 new Db() 之前取得，后来者先在锁上失败。

从 v5 或更早迁移时，sessions_new 的列清单里没有 workspace_project_id：重建排在 ensureColumns 之后，所以迁移完成的那次启动里 sessions 缺这一列，下次以同版本打开时 ensureColumns 才补回（用当前代码对一个改成 v5 的库实测如此）。

工作区与旧数据迁移

工作区和会话怎样归属

工作区就是带根目录归属的 projects 行。目录身份是 realpath 加 dev / ino（dir-identity.ts · resolveDirIdentity），realpath 相同或 dev+ino 相同即视为同一目录（sameDirIdentity），符号链接与挂载别名因此不会各成一个工作区。store.ts · findProjectByRoot 按这两条查找；部分唯一索引只能兜住 realpath，挂载别名只能靠这次查询拦住。

open_workspace（runtime.ts · openWorkspace）先在事务外核对目录存在、取得身份、确认不落入保护根，再在一个事务里：同一 createRequestId 重发返回原会话（目录不同报 request_conflict）；指定旧项目时拒绝角色或群聊项目、拒绝会话分布在多个目录的项目（legacyProjectClaimableFromDir），没有根目录就认领；否则按身份复用工作区，或以目录名新建（重名加「 (2)」等序号，同名不同目录绝不合并）；最后建会话，project_id 就是这个工作区。

会话的两个归属字段含义不同：sessions.project_id 是资料身份与配置来源，历史、产物、记忆、指令、MCP、Jev、授权与凭据都按它定位；sessions.workspace_project_id 只决定组织查询和列表里显示在哪个工作区下（显示归属 = workspace_project_id ?? project_id），AccessScope、模型工具身份与凭据范围都不读它（ADR 0018）。项目指令列表与 Web Search 开关由 settings_version 保护（store.ts · updateProjectSettings）：带预期版本的保存在同一事务里核对，不符报 version_conflict；省略版本的旧入口同样递增这个版本；同值保存不递增、不发事件。

把旧数据迁到工作区

全部推断集中在 workspace-migration.ts · previewWorkspaceMigration 与 applyWorkspaceMigration，Runtime 只做接线，CLI 经控制面 op preview_workspace_migration / apply_workspace_migration 调用。迁移只改组织字段与根目录归属（必要时新建带根目录的工作区），不改写 JSONL、不移动产物、不重建会话、不复制或合并旧配置。

预览只处理「普通 dev 会话」：角色绑定会话、SubAgent 的内部子会话与 QQ 群会话都被明确排除。它先把这些会话的登记目录按 distinctDirIdentities 归并成目录组，再逐组核实（workspace-migration.ts · checkRegisteredDir）：

目录组状态判定（对登记的 realpath 重新 realpath + stat）后果
valid仍是目录，realpath、dev、ino 都与登记一致组内会话可以映射；全部有效且只有一个组时才可能安全认领
missingrealpath 或 stat 报 ENOENT / ENOTDIR保留原记录；组内会话不能映射，安全认领不成立；目录恢复后重新预览
replaced该位置已不是目录，或 realpath、dev、ino 任一与登记不同同上；同路径的新目录不被当成旧目录
unverifiable其他错误（如无权限）同上，预览里报「无权核实」
  • 上限：预览核查的会话数默认 500（PREVIEW_DEFAULT_LIMIT），可调到 5000（PREVIEW_MAX_LIMIT）。超出即截断并如实报告，截断的预览不能生成修订、不能认领；应用时总按 5000 重扫，仍截断就报 revision_conflict。
  • 修订：r1. 加规范化 JSON 的 sha256（revisionOf），输入是源项目根目录与 settings_version、核查到的每个会话（类别、是否角色绑定、组织映射、目录身份）、角色绑定、目标根身份和规范化后的计划。无关任务的输出不在输入里，不会让预览过期。
  • 两种计划：map_sessions 逐会话指定目标（已有工作区的根必须仍有效且包含会话目录；新根要通过目录与保护根校验，同一真实目录已有工作区时必须复用其 ID）；claim_source 让旧项目以原 ID 认领根目录，条件是项目尚无根、会话集合未截断且全是普通 dev、全部目录有效且是同一个真实目录、该目录没被别的工作区占用、没有已映射的会话（computeSafeClaim，事务内再算一次）。
  • 事务与幂等：应用要求连接的 instance_id 与当前库一致；回执键 migration_receipt:<request_id> 存在核心库 meta，摘要覆盖项目、实例、计划与预期修订。单事务内写项目创建（project.created）、根认领（project.root_attached）、组织映射（session.workspace_mapped）与回执，任一失败整体回滚。
  • 回退：action: revert 指向一次成功的 map_sessions 回执，逐个核对会话当前的 workspace_project_id 仍等于当时写入的值（否则 revision_conflict），再在一个事务里恢复原值并写新回执（applyRevert）。claim_source 不可回退，回退不能再回退；新建的工作区、已认领的根与迁移后产生的执行事实都保留。

「把旧数据迁到工作区」在同一个实例里只改组织归属；跨实例的迁入不经过控制面，由目标侧离线 CLI 执行，两个方向按产品分流、共用同一副骨架：ruukoto-code legacy-import 迁开发资料（agent-direction 工单 21，ADR 0022，本节）；ruukoto legacy-import 迁个人资料（工单 22，ADR 0023，下节）。CLI 们持目标实例锁（instance-lock.ts · acquireInstanceLock）运行，要求目标后台已停止；预览对目标零写入，目标库也经只读副本核对（legacy-import.ts · openTargetReadonlyCopy）。开发方向的全部判断集中在 src/runtime/legacy-import.ts。目标必须已在当前 schema：库版本不等于程序版本时报 target_schema，先启动一次目标产品后台完成迁移再导入（checkTargetProduct）。

源全程只读。源库不能用 SQLite 读连接或 VACUUM 直读——只读连接会恢复 WAL、在源目录生成 -shm / -wal 来写侧车；改为把 ruukoto.db 及其侧车逐文件复制到 mkdtemp 临时目录（0700），在副本上迁到当前 schema 再核对完整性（openSourceSnapshot）。动手之前先经只读探测核实源已停止（已核实同一进程持锁 → source_active；身份无法核实 → source_unverifiable；instance-lock.ts · probeLockHolder，启动身份与旧记录兼容规则见 部署与信任边界 · 实例锁）；源已登记为别的产品报 product_mismatch。导入只读源目录与 agent 目录的名称清单，任何路径都不修改源资料。

表级 TABLE_POLICY：快照与目标库的每张表都必须逐张登记为「导入」或「排除 + 理由」，哪边出现未登记的表都以 table_policy 拒绝（checkTablePolicy），新加的表不会被默认漏判或默认复制。subagent_messages 按「import」登记，但行不独立搬运：预览按纳入导入的工作收集其消息（legacy-import.ts）、apply 时随所属工作同批插入、revert 时先于工作按 work_id 删除（见下「工作区迁移与实例导入」的列表）。

导入单位是源项目内普通 dev 会话（含其一层 SubAgent），行 ID 原样保留。角色绑定会话、QQ 群会话与 main 资料一律排除并逐项列出；目标已有同 ID 且不属于本源此前导入的行以 id_conflict 拒绝，不覆盖未核实的目标数据；同一源续跑时按账本领跳过。会话文件改写为目标 sessions/ 下同名文件，按 sha256 逐文件复制（目标已有同 sha 跳过、内容不同报 file_conflict）；源文件缺失或损坏照常导入并在报告列出，不补空文件。

  • 不重放的收尾：queued 任务改 canceled、running / awaiting_confirmation 改 interrupted（原因 migration；结果未登记且可能已开始执行的工具操作与任务置 effect_unknown——被未消费审批挡住的操作属已知未执行，与运行时恢复同口径），未消费审批一律 stale，full_access 会话默认降为 confirm，导入的 SubAgent 以独立 closed_at / closed_by 记录为已关闭。
  • 不完整的历史如实保留：项目根四列只在本机严格核实身份一致且目标无同根占用时保留，其余清空成旧来源项目并把原值记入回执；会话 cwd 在本机无法核实身份时导入成只读仅查阅（继续执行由既有目录身份核查拒绝）；组织映射按 07 规则保留、改指同根目标工作区或置空待重新组织。
  • 凭据与边界 fail-closed：项目记忆只在全部版本来源落在导入范围或为 owner_note 时导入；personal 记忆只导入计划显式选中的条目，其余正文留在源实例、列入待处理；跨实例授权只记回执不生效；MCP 与 Jev 配置导入，目标缺同名凭据绑定时以停用状态导入并列出，不与源凭据值接触。
  • 回退按账本（legacy-import.ts · revertLegacyImport）：单事务内删除导入的行、事件区间（先核实整段都属于本次导入）与账本条目，回执保留并标 reverted；提交后才删经 sha256 核对的复制文件。导入的项目 / 会话 / 记忆在导入后有新任务、会话、事件、授权、组织映射或新版本，逐项列为阻挡项并拒绝回退；此时返回 ok: false、status: applied，回执与已导入资料保持原状，不能显示为已回退。成功回退才返回 status: reverted。
  • 整库恢复的手工路径：VACUUM INTO 在导入事务之前把目标库完整备份到 <dataDir>/migration/<导入ID>/target-before.db：停止后台后以备份库恢复（步骤见 docs/runtime.md「数据布局」）；代码不回滚这份备份，也不自动恢复它。
首版与首版限制

不做增量同步——源侧在导入后新增的条目只在报告列出，可再次按同一源导入；不做在线 / 控制面导入；agentDir 文件（models / auth / default-model / credentials / skills）与 qq / telegram 表一律不复制，预览只列名称与差异、不读凭据值。canonicalJson / sha256 / historyStatusOf 由 workspace-migration.ts 导出复用，本工单不改其行为。

两个导入方向都排除 inbound_media_messages / inbound_media 及暂存文件、拒绝账本，避免目标启动重放半接收消息；已绑定任务的图片作为既有 ArtifactStore 产物复制，MIME 与内容哈希随元数据行保留（legacy-import.ts · TABLE_POLICY、personal-import.ts · TABLE_POLICY）。

实例导入 · 个人方向：迁入全新 ruukoto，平台与调度归属显式交接

镜像方向（agent-direction 工单 22，ADR 0023）在 src/runtime/personal-import.ts，机制骨架复用 legacy-import.ts 的导出，不建通用框架。导入单位反转：main / coding / chat 角色行及其项目与会话（含 main 一层 SubAgent）、QQ 群会话与群归档四表全量导入，普通 dev 会话一律排除（经开发方向迁移，预览列出并指过去）。目标必须是全新实例：目标后台启动过（有自有角色行与 main 会话）即拒绝，源与目标同一路径或同一实例 ID 也拒绝（personal-import.ts · checkNotSelf）；角色工作目录在目标 agent-work/<角色> 重建并取目标身份，ensureRoles 幂等跳过导入角色行。应用数据是文件级迁移：agent-data/main.db（+WAL）与 github-archive-manifest.json 同 JSONL、产物一样按 sha256 核对复制，绑定 meta 与退役 meta 随行；v9 前遗留的 github_* 三表在全新目标按快照自身 DDL 重建。main 会话访问模式原样保留（同产品延续，不做开发方向的降级）；personal 记忆同产品延续、不做计划选中，只用来源规则（全部版本来源落在导入范围或为 owner_note 才导入，引用 dev 的列待处理）。

不重放收尾与开发方向同口径并扩到交接面：未关闭调度运行置 closed_at；发送账本 pending → canceled（error_kind = migration，已知未发送不当作新请求重发）、sending → effect_unknown；入站 registered / queued → failed。执行归属显式交接：qq_config / telegram_config 原样随迁（含 config_version 与 telegram last_update_id）、入站去重表全量随行——目标以偏移继续消费、钉版目标不换代；活动调度原样接管，逾期按启动恢复语义在目标各触发一次（合并进未完成运行，旧 pending 已取消、无双发）；长期授权原样导入，身份链在使用侧逐次核实、不符即 fail-closed。必要凭据——平台配置引用的绑定与 purpose 为 github_webhook 的绑定——从源 credentials.json 合并进目标（同名同值跳过、异值报 credential_conflict；personal-import.ts · mergeCredentials，报告只记 sha256）；MCP / Jev 凭据不复制、缺绑定停用导入。旧实例侧不改一字：导入完成后拥有者不得再启动旧实例消费平台入站或调度。

易变行按回执 manifest 管理（不走逐项账本）：调度运行、发送账本、入站事件、群归档与 GitHub 归档按导入行 id 列表 + 整行 sha256 记入回执报告（按其写入目标的转换后行计算）；续跑时同源此前（applied）回执的 manifest 是唯一「目标行确为本源导入所写」的证据——同键同 sha 跳过、其余同键报 id_conflict。回退（personal-import.ts · revertPersonalImport）在开发方向阻挡项之外另拦交接事实：目标启动后的新入站事件、新发送操作、新调度 / 运行、新长期授权，导入行被运行时改写（已发送、已 advance、已消费偏移、撤回标记）、应用数据文件被写、导入凭据被轮换——逐项 sha256 核对、逐项列出并拒绝，切换期间新增的执行及发送事实不抹掉；阻挡时返回 ok: false、status: applied，回执仍为 applied，成功回退才返回 status: reverted。凭据摘除同样经 sha 核对。v30 账本扩五类（agent_role / schedule / platform_config / standing_permission / credential，见上表），开发方向不受影响。

首版限制

不做增量同步、不在线导入；不做源侧写入（含「停用旧平台」的源侧写入——旧实例的停用是拥有者的部署动作，见运行文档）；外部平台重配置（GitHub webhook URL、新的监听地址由启动参数重新给出）不在导入范围。与开发方向不互相预抽象：两模块共享快照 / 账本 / 行工具导出，各自的预览 / 应用 / 回退判断独立。

事务纪律、锁与令牌

核心库的状态写入经 store.ts · withTx（少数写入在事务外自动提交：history_index 同步、product.type 补记、GitHub 退役完成标记）：底层 db.ts · tx 以 BEGIN IMMEDIATE 开事务，函数体抛错即 ROLLBACK。appendEvent 在事务里插入 events 行并把事件暂存；提交成功后才交给 onCommitted 广播给客户端与宿主内监听者，回滚则丢弃。所以状态、占用与对应事件要么一起出现，要么都不出现，客户端看不到未提交的变化。

  • 事务不能嵌套：事务里再 BEGIN 会被 SQLite 拒绝。窄存储层（SchedulerStore、mapSessionToWorkspace、updateProjectSettings 等）的写方法因此约定在调用方的 withTx 里执行，自己不开事务。
  • 条件更新做并发仲裁：任务转换 WHERE status IN (…)（transitionTask），长期授权撤销 WHERE version = ? AND revoked_at IS NULL，根目录认领 WHERE root_real IS NULL，调度与发送状态同样按当前状态更新。竞争的两条路径只有先提交的生效，后到的看到 0 行就退出。
  • 同步驱动：node:sqlite 是同步 API，事务函数体里没有 await，同一进程内不会有别的逻辑插进一个事务中间；实例锁保证同一数据目录只有一个进程在写。
机制位置保证什么
实例锁（instance-lock.ts · acquireInstanceLock）<dataDir>/runtime.lock/同一数据目录只有一个后台。mkdir 原子创建，owner.json 记录 pid、诊断命令、登记时间与进程启动身份 processIdentity。获取与只读探测共用身份核实：确认持锁时拒绝，无法核实时保留锁，确认遗留后接管；旧记录继续兼容。来源与分支见实例锁与配置锁。确认的锁竞争仍以 42 退出。
配置锁（acquireConfigLock）<agentDir>/config.lock/同一 agentDir 只允许一个在线后台或离线配置写入方，覆盖两个数据目录共用一个 agentDir 的情况；socket 连不上不能证明后台已停，必须走锁。
拥有者令牌<controlDir>/owner.token控制面认证，常数时间比较。多用户部署时由配置步骤以 0400 复制给拥有者，或用 RUUKOTO_OWNER_TOKEN_FILE 指向拷贝（见 部署与信任边界）。
产品归属meta 的 product.type另一产品打开同一数据目录被拒绝（product_mismatch）。
迁移回执meta 的 migration_receipt:<request_id>迁移应用同键重放返回原成果、异参 request_conflict；回退按回执核对当前值。
导入回执（legacy-import.ts · applyLegacyImport）instance_imports（与条目账本 instance_import_items）跨实例导入同请求键重放返回原回执、同键异参 request_conflict；同一资料 (kind, item_id) 至多归属一次导入（续跑识别、回退范围）；回执持久保留。
schema 版本meta 的 schema_version比程序新的库拒绝打开；迁移失败整笔回滚。

后台停止时先关控制面服务（断开连接、删 socket），再关应用库，记 backend.stopped 后关核心库（关闭前做 PRAGMA wal_checkpoint(TRUNCATE)，db.ts · close），然后释放实例锁与配置锁，最后再删一次 socket。
