状态与转换

queued、running、awaiting_confirmation 是活动状态（types.ts · ACTIVE_TASK_STATUSES）；completed、failed、canceled、interrupted 是终态，进入后不再转换。同一会话一次只执行一个任务，不同会话在工作目录不同时可以并行。

转换触发者条件与位置事件

每次转换都是 store.ts · transitionTask 的条件更新：WHERE id = ? AND status IN (起点集合)。取消与自然完成、人工中断与后台停止同时发生时，只有先提交的那一次生效，后到的路径看到更新 0 行就退出，不会写出第二个终态（例外：调度循环的兜底 catch 照写 task.failed 事件）。状态、占用与对应事件在同一事务里提交，提交成功后才广播给客户端。

一次运行的结局怎样判定

driver.ts · runInner 在 sdk.prompt() 返回后按下列顺序判定，前面的条件优先。发送前复核拦截与上下文超限都会暂停该会话的队列，排队中的下一个任务不会自动开始。

  1. 已请求停止：终态由停止路径决定，这里只做清理。
  2. 发送前复核拦下了某次模型调用：interrupted，原因即拦截码，暂停队列。
  3. 模型调用以 aborted 结束：interrupted（aborted）。
  4. provider 报告上下文超限：interrupted（context_overflow），暂停队列。不自动摘要、不缩短输入重试。
  5. 模型返回错误：failed。
  6. 其余情况：写任务结束标记，再核对最终历史确已落盘。核对通过为 completed，否则 interrupted（history_unverified:… 或 history_corrupted:…）。

停止路径

拥有者中断、拥有者取消、编排器超时取消、QQ 等后台内部取消与后台停止共用 driver.ts · requestStop。它先把「要停」写下来，再解除所有等待，最后才定终态和释放占用。驱动器当前执行的不是该任务时，它直接返回、什么也不做。另一条更窄的路经与此分开：IM 入口绑定失效（停用、重新绑定或凭据变化）不停止任务，只把受影响审批的等待定向解除（supersedeConfirmations，与 runtime 侧 invalidateImApprovals 配套），同会话其他审批照常。

回收失败时

无法确认工具进程组已经退出时，任务照常进入终态，但目录占用保留，同一目录的新任务不会启动（task.tool_process_unreaped）。拥有者核实容器或子进程确已停止后，用 resume_queue 释放遗留占用。

会话队列与目录占用

会话队列有 active 与 paused 两种状态（types.ts · SessionQueueState）。暂停只影响「是否自动开始下一个排队任务」，不改变已排队任务本身。目录占用以工作目录身份为键，保证同一工作目录同一时间只有一个任务处于 running 或 awaiting_confirmation。

暂停原因谁暂停什么时候谁恢复
backend_restart重启恢复重启时会话里还有排队任务，且会话此前是 active。编排器（角色会话）；QQ 适配器（群会话）；其余等拥有者
occupancy_unverified重启恢复旧后台留下占用行，且会话此前是 active。遗留占用一律视为无法确认旧执行已停止（正常部署下 systemd 会随服务回收子进程，不会出现）。拥有者；QQ 群会话由适配器启动时恢复
context_overflow驱动器provider 报告上下文超限，任务已中断。拥有者；QQ 群会话由适配器启动时恢复
发送前复核的拦截码驱动器某次模型调用在发送前被拦下，任务已中断。拥有者；QQ 群会话由适配器启动时恢复

恢复都经 runtime.ts · resumeQueue：拥有者调用 resume_queue，或后台启动时的两处自动调用——编排器恢复角色会话里以 backend_restart 暂停的队列（orchestrator.ts · start），QQ 适配器不论原因恢复所有暂停的 QQ 群会话，群会话没有工具执行（qq/adapter.ts · startOnce）。它只释放本会话所属任务已经结束的遗留占用，本会话有活动任务持有占用时整个请求被拒（occupancy_active）；旧版本留下的排队任务没有记录模型配置时，要求显式给出 model_selection 并写回（tasks.model_selection_recorded）；最后置 active、发 session.queue_resumed 并唤醒本会话的调度循环。暂停时发的是 session.queue_paused。

后台停止与重启恢复

后台停止 runtime.ts · doStop

  1. 记 backend.stopping，先停所有入口：GitHub webhook、调度器（等在途发送收尾）、Telegram 轮询、编排器、QQ 适配器。
  2. 对 running 与 awaiting_confirmation 的任务走停止路径，原因 backend_stop；驱动器缺失的任务直接条件更新为 interrupted，占用保留。排队任务保持 queued，停止开始后不再转入 running。
  3. 释放各会话驱动器，等调度循环全部退出。
  4. 关闭控制面与应用数据库，记 backend.stopped，关核心库、释放实例锁与配置锁、删除 socket。

重启恢复 runtime.ts · recover

启动时打开应用库、做完调度器的恢复准备后，在编排器与各入口启动之前，用一个事务完成：

  1. 按工具操作账本的分类器补记所有结果缺失的操作；running 与 awaiting_confirmation 一律转 interrupted（backend_restart），未决与已批准未消费的审批一律失效（stalePendingConfirmations：consumed_at 为空即随任务终结，已消费的不动）。
  2. 遗留占用记 occupancy.stale、保留不删，所属会话仍为 active 时以 occupancy_unverified 暂停。
  3. 有排队任务、仍为 active 的会话以 backend_restart 暂停；上一步已暂停的会话保留原因。
  4. 会话登记的 JSONL 缺失时改用同 pi session id 的最新文件；改用与找不到都记 session.history_unreadable。

事务末尾记 backend.recovered，列出被中断的任务与被暂停的会话。编排器、QQ、Telegram、调度器与 GitHub webhook 都启动之后才记 backend.started（QQ、Telegram 与调度器只有个人 Agent 产品启动；Coding Agent 不创建，backend.started 一并记录产品身份）。

ruukoto-dev 的 TUI 按需拉起（ensure-backend.ts · ensureBackend）只是通往同一条重启路径的又一个入口：拉起的进程就是 server，实例锁照常仲裁成单个后台，上面这张 recover 事务一条不差地执行。它改变的只是谁来发起启动，不改变启动之后发生什么：界面重新打开沿握手快照复现任务（见控制面协议），连接丢失永远不构成重新执行的授权——恢复语义照下，不重放。

不重放

重启不重新调用模型、不重放工具操作。想继续中断的任务，拥有者用 continue 提交一个带 resumesTaskId 的新任务：它沿用会话默认访问模式（提交时可显式指定），旧任务的批准不继承，也不补造工具结果。

访问模式切换

任务携带访问模式与权限版本。只有拥有者能切换（runtime.ts · switchTaskMode），切换只在没有工具正在执行的边界生效，并递增权限版本，使等待中的审批失效。各模式的含义见工具调用路径。

切换时任务处于行为事件
queued 或 awaiting_confirmation立即应用：停止本会话驱动器当前的执行单元并核实已退出（没有驱动器视为已退出），写入新模式与权限版本；等待中的审批全部失效。task.mode_switched
同上，但无法核实旧执行单元退出任务中断（mode_switch_unverified），不释放占用，请求以同名错误码失败。task.mode_switch_failed
running登记待生效模式；执行中的调用沿用开始时的范围，下一次工具调用前在边界应用（tool-router.ts · prepareToolBoundary）。任务先到终态时待生效模式随之清除。要立刻停下请用中断。task.mode_switch_requested，应用时 task.mode_switched
边界应用失败任务中断（mode_switch_failed:…），回收失败时保留占用。task.interrupted；回收失败另发 task.tool_process_unreaped
终态拒绝（invalid_state）。无
