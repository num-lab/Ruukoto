状态与转换

queued、running、awaiting_confirmation 是活动状态（types.ts · ACTIVE_TASK_STATUSES）；completed、failed、canceled、interrupted 是终态（TERMINAL_TASK_STATUSES），进入后不再转换。同一会话一次只执行一个任务，不同会话在工作目录不同时可以并行。

一次运行的结局怎样判定

driver.ts · runInner 按下列顺序判定，前面的条件优先。发送前复核拦截与上下文超限都会暂停该会话的队列，排队中的下一个任务不会自动开始。

  1. 任务已带取消意图（cancel_requested=1，来自落在「已转 running、Driver 尚未接管」窗口的取消）：canceled（interrupt_reason=cancel_requested），不建 SDK 会话、不调用模型。该窗口不保留原始取消原因（超时取消落在此窗口记 canceled 而非 timeout，见 runInner 内的 ponytail: 注释）。
  2. 任务没有记录模型配置、模型解析失败或 SDK 会话创建失败：failed。
  3. prompt 之前已请求停止：interrupted（aborted）。它与停止路径各自尝试条件更新，先提交的生效，所以开始前到达的取消也可能以 aborted 中断收场。
  4. 技能展开失败：failed。prompt 抛错：未请求停止时 failed。
  5. prompt 返回后已请求停止：终态由停止路径决定，这里只做清理。
  6. 发送前复核拦下了某次模型调用：interrupted，原因即拦截码，暂停队列。
  7. 模型调用以 aborted 结束：interrupted（aborted）。
  8. provider 报告上下文超限：interrupted（context_overflow），暂停队列。不自动摘要、不缩短输入重试。
  9. 模型返回错误：failed。
  10. 其余情况：写任务结束标记，再核对最终历史确已落盘。核对通过为 completed，否则 interrupted（history_unverified:… 或 history_corrupted:…）。

停止路径

拥有者中断、拥有者取消、编排器截止巡检、整项工作取消、QQ 与 IM 配置变化等后台内部取消，以及后台停止，共用 driver.ts · requestStop。它先把「要停」写下来，再解除所有等待，最后才定终态和释放占用。驱动器当前执行的不是该任务时，它直接返回；对取消而言这一支不再吞掉请求——runtime.ts · cancelTask 在 requestStop 之前已把 cancel_requested=1 落库（独立事务，所有取消调用方共享，含整项取消的事务内写入），runInner 开头读到该标记直接定态 canceled、不调用模型。

回收失败时

无法确认执行单元已经退出时，任务照常进入终态，但目录占用保留，同一目录的新任务不会启动（task.tool_process_unreaped）。拥有者核实容器或子进程确已停止后，用 resume_queue 释放遗留占用。若是 SubAgent 执行任务，结果补记事务核实它仍是当前任务时，管理器才按占用仍在记为 unverified；resume_queue 同时是它的出口：释放占用的事务内调用管理器 executionVerified，无活动任务且当前终态结果已登记时回 idle；结果缺失报 invalid_state，连同遗留占用释放一起回滚。提交后等待冲刷待投递消息（见编排器）。

IM 入口配置变化

QQ 私聊或 Telegram 入口的配置变化（停用、重新绑定、凭据变化）由拥有者 IM 入口表按来源处理（im-entries.ts · reconcile），暂时离线（门控为 wait）不算变化；入口由启动配置停用与入口停用同义，门控为丢弃。分两层：

  • 直接由该入口消息建立、仍在活动的任务按取消处理：排队的条件更新为 canceled，执行中的走上面的停止路径；原因是门控丢弃码。
  • 沿父任务链追溯到该入口的其他任务（如委派出的子任务）不停止：归属该入口、尚未消费的审批（待决与已批准）作废，再只解除这些审批的等待（invalidate → supersedeConfirmations）。工具按已知未执行返回，同会话其他审批照常，已消费的不动。同一事务里，该入口身份已变的长期授权记 entry_changed 失效。

会话队列与目录占用

会话队列有 active 与 paused 两种状态（types.ts · SessionQueueState）。暂停只影响「是否自动开始下一个排队任务」，不改变已排队任务本身。目录占用以任务的工作区根（taskWorkspaceFor：SubAgent 修改任务的工作副本或直接写入根，其余任务为会话工作目录）的身份为键，保证同一目录及其祖先/子孙同一时间只有一个任务处于 running 或 awaiting_confirmation。

后台停止与重启恢复

后台停止 runtime.ts · doStop

由控制面 stop 操作、进程收到 SIGINT / SIGTERM，或启动时 GitHub webhook 起不来触发（server.ts · stop）。

  1. 记 backend.stopping，先停所有入口：GitHub webhook、调度器（等在途发送收尾）、Telegram 轮询、编排器、QQ 适配器。ruukoto-code 没有调度器；QQ 与 Telegram 适配器仍存在，但按产品停用连接与轮询。
  2. 对 running 与 awaiting_confirmation 的任务走停止路径，原因 backend_stop；驱动器缺失的任务经 Store.endTask 转 interrupted，清除待生效模式、失效未消费审批并保留占用，事件读实际取消意图与效果未知标记。排队任务保持 queued，停止开始后不再转入 running。
  3. 释放各会话驱动器，等调度循环全部退出。
  4. 关闭控制面与应用数据库，记 backend.stopped，关核心库、释放实例锁与配置锁、删除 socket。

重启恢复 runtime.ts · recover

启动时先核对数据目录登记的产品归属，属于另一产品即拒绝启动（product_mismatch）。打开应用库（个人 Agent 还先做调度器的恢复准备）后，在编排器与各入口启动之前，用一个事务完成：

  1. 按工具操作账本的分类器补记所有结果缺失的操作（settleAll），已消费的服务操作被标效果未知时同目标的长期授权一并失效；running 与 awaiting_confirmation 经 Store.endTask 转 interrupted（backend_restart），清待生效模式并保留占用，未决与已批准未消费的审批一律失效（stalePendingConfirmations：consumed_at 为空即随任务终结，已消费的不动）。
  2. 仍排队的 SubAgent 执行任务（拥有者 / 主 Agent 委派，没有来源事件）由恢复事务调用 SubAgentManager.recoverQueuedTasks 转 interrupted（backend_restart，从未启动）：不自动继续也不当作新委派（store.ts · listQueuedSubAgentTasks）；宿主固定评审（带来源事件）的排队任务保持，由管理器 start 在无遗留占用时恢复继续。
  3. 遗留占用记 occupancy.stale、保留不删，所属会话仍为 active 时以 occupancy_unverified 暂停。
  4. 有排队任务、仍为 active 的会话以 backend_restart 暂停；上一步已暂停的会话保留原因。
  5. 会话登记的 JSONL 缺失时改用同 pi session id 的最新文件；改用与找不到都记 session.history_unreadable。

事务末尾记 backend.recovered，列出被中断的任务与被暂停的会话。编排器、QQ、Telegram、调度器与 GitHub webhook 的启动步骤完成之后才记 backend.started（调度器只在个人 Agent 产品创建；QQ 与 Telegram 适配器始终创建，ruukoto-code 按产品停用；webhook 仅在显式配置后监听；backend.started 带产品身份）。随恢复失效的审批，尚未发出的 IM 通知在发送前核对审批已不是 pending，不再发出；入口未变的长期授权不因重启失效。

日常 ruukoto-code 的后台可以由 TUI 按需拉起（ensure-backend.ts · ensureBackend，只属 ruukoto-code：tuiSpawnsBackendOnDemand；ruukoto 仍显式启动）。它先探测控制面，认证与握手通过即复用；socket 可连但被拒（令牌或协议版本）也不拉起。拉起的进程就是 server，启动后照常执行上面的恢复；多个终端同时拉起由实例锁仲裁成单个后台，败者以 INSTANCE_LOCK_EXIT_CODE 退出。子进程 detached 并 unref：关闭 TUI 不停止后台、不取消任务，后台只按上面的停止路径结束。界面重新打开沿握手快照复现任务（见控制面协议），连接丢失不触发任何重新执行。

开发入口 npm run code 的 TUI 只连接启动器管理的后台（runTui · 开发前端），退出 TUI 后由启动器停止整组进程。两个开发入口的源码重载与退出规则见开发实例。

不重放

重启不重放已中断任务的模型调用或工具操作；宿主固定评审尚未启动的排队任务可自动继续（见SubAgent 执行任务）。想继续普通开发会话的中断任务，拥有者用 continue 提交一个带 resumesTaskId 的新任务：采用本次提交时的会话默认模式，显式模式优先。Plan 同样按本次选择决定，不从源任务输入或继续链继承；旧任务的批准不继承，也不补造工具结果（runtime.ts · continueTask）。

会话默认模式与任务模式切换

会话默认模式（types.ts · SESSION_DEFAULT_MODES）包含 confirm、full_access、auto-review；普通开发会话另可选择 plan。拥有者经 set_session_mode 带 expected_version 条件保存，发出 session.default_mode_changed；旧版本请求返回 default_mode_conflict，不覆盖现值（runtime.ts · setSessionDefaultMode、store.ts · setSessionDefaultMode）。TUI 的 /mode 与 Shift+Tab 沿用此入口；切换普通开发会话时，把源会话选择同步到目标会话并保存。

默认值只影响后续新任务，提交时保存任务的 planMode 与 accessMode。Plan 固定为 planMode=true、accessMode=auto-review，持续到拥有者手动更换默认值；计划完成和“开始实现”消息不自动退出。排队、执行或等待审批中的任务保留提交时选择，底栏显示任务模式；与后续任务默认值不同时，另显示会话默认模式。计划说明与工具收窄的边界见工具调用路径。

任务级 switch_mode 只接受原访问模式。Plan 任务拒绝改变权限模式；请求 plan 也会被拒绝，不能在任务内部进入或退出 Plan。拒绝不改写任务、权限版本或审批；需要转换时先中断，再按当前会话选择继续。非 Plan 任务仍携带访问模式与权限版本，只有拥有者能切换（runtime.ts · switchTaskMode），在没有工具正在执行的边界生效，递增权限版本并使未消费的审批失效（store.ts · applyModeSwitch）。访问策略含义见工具调用路径。
