一次调用走完整条路径

可用性：会话类别定清单，任务再收窄

静态清单在 tool-availability.ts · SESSION_TOOL_CATEGORIES：普通开发会话与 coding 角色拿到 coding（含共享的待办工具）、host_data、web_search、mcp、skills；main 在此基础上换成 app_data、scheduler、delegation、chat_results、service（没有 coding）；chat 为空清单。ruukoto-dev（Coding Agent）不创建调度器，main 的 scheduler 工具不装配（agent-direction issue 01）。service（types.ts · ToolCategory，service_inspect / service_manage，服务器服务管理）进了 main 的清单只是可见的前提：实际装配另要求产品 ruukoto + Linux + 显式部署配置齐备（缺一则不装配，不是静默放行）。

装配之外还有逐任务收窄：计划模式只留只读；项目关掉 Web Search 时 web_search 整类不装；宿主可按任务钉一份更小的工具集。收窄只减不增——任务不能拿到清单外的类别。

访问模式决定执行边界

访问模式含义执行边界越界操作
confirm
请求确认模式		 权限内自主执行；会话默认模式缺省于此 受限执行环境（当前为容器工作进程） 登记审批请求，等拥有者批准
full_access
完全访问模式		 拥有者明确允许任务使用执行账户已有的系统权限 专用执行账户（systemd 临时服务范围） 仍需列明的范围外操作照常审批；不额外授予系统权限
auto-review
自动审查模式		 与请求确认模式同一受限环境 同 confirm 越界的外部文件读取与无凭据 HTTP 读取先经独立无工具审查调用放行，其余转拥有者

模式到启动器的映射在 launchers.ts · createLauncherFor：受理任务前先探测所选边界可用，缺失就直接拒绝，不静默降级。IM 来源的任务固定 confirm。

审批：状态机与批准消费

审批请求的状态（types.ts · ConfirmationStatus）：pending 待拥有者决定；approved 已批准、待消费一次；rejected 已拒绝，操作按已知未执行记；stale 已失效（复核或消费失败、任务终态等），该批准不能再消费。

决定的两个入口：控制面与 IM 私聊

拥有者的应答既可以从控制面 respond_confirmation 来，也可以从 QQ / Telegram 私聊的整条审批命令来（绑定拥有者专用，命令识别与归属核实见入站事件）。两条入口汇到同一个 approval-gate.ts · resolve：条件更新 pending → approved / rejected 与 task.confirmation_resolved 审计事件在同一事务提交，失效应答返回 false；IM 命令另把控制事件终态与回执作为 txExtra 并入这个事务——回执登记写失败会让决定整笔回滚（决定未记录，回执如实说「请重试」），不存在已记录决定但没留回执的中间态。任何入口都是提交成功后才唤醒等待的任务；已被其他入口（TUI、自动审查或另一条命令）处理的审批，后到的应答不生效。IM 决定只作用于原请求与原权限版本：命令必须带完整审批 ID 与当前权限版本，不开放新参数。

审批范围按操作类别固定

登记请求时把范围结构化冻结，展示与复核都用同一份快照（types.ts · ApprovalScope）：

kind冻结内容
tool工作进程内工具操作；标注是否限工作区
file_operation路径、读写类别、原文件版本指纹与待写内容的字节数/指纹
http_request方法、URL 与凭据引用名（只有名称与用途，不含原值）
mcp_tool服务身份与配置版本、远端工具名、参数摘要、副作用类别
app_data_change应用库身份、任务与操作 ID、表与破坏性类别、版本与受影响数量
notification通知外发：完整正文指纹、目标与配置版本、时间规则与持续范围；单次消费，完全访问模式下也须确认
service_operation服务器服务管理（root 提权 helper）：本机身份、精确单元名、固定动作、策略与单元定义修订指纹、任务与宿主操作 ID；任何访问模式都逐次审批（例外：issue 10 限定长期授权逐项核实成立时自动放行——见下节），参数快照含 unit/action/machine_id/policy_revision/unit_revision/state_before/note，消费事务内复核策略修订，helper 在请求 systemd 前再复核单元修订
github_publish已退役范围：旧 GitHub 发布模块的审批记录只读展示，新任务不再产生

自动审查不扩大授权

auto-review 下越界的外部读取先经一次独立的无工具调用（review.ts · ReviewDecision），结论只有三种：approve（放行该操作）、reject（拒绝）、ask_owner（转拥有者确认）；无法确认或审查失败一律按 ask_owner 处理。审查的输入不构成授权依据，结论也不升级为完全访问。

长期操作授权：窄服务范围的有效授权（agent-direction issue 10）

ADR 0019 的逐次审批有一个明确例外：拥有者经原 IM 平台的待审批把某次 service restart 审批保存为限定长期授权（/approve-standing，见入站事件）。授权行存 standing_permissions（scope 不可变 + 行级版本；同一 main、入口稳定身份与目标至多一条未撤销授权，来源审批唯一，见 存储布局）。模型、子任务消息、TUI 提交与各平台文本都不能创建或扩大。

service_manage 每次执行都重新核实：宿主按当前 main、任务来源入口身份、钉版目标代次、本机/单元/动作与两项修订查找候选（候选不是执行依据；观察到失配的旧授权同事务明确失效）。命中时经闸门的窄路径（approval-gate.ts · requestStanding）在单个同步事务内重读授权版本与未撤销状态、对执行快照逐项核实完整范围、核实活动任务与取消状态，创建独立的初始已批准记录（不发布等待事件、任务保持 running、不启动自动审查），经公共消费边界单次消费；决定来源记 standing_permission 并关联授权 ID/版本（事件与 TUI 详情如实标注）。候选读取后撤销/取消/版本变化即整笔回滚并回落人工审批。效果未知另使同目标所有入口的有效授权失效（见 只执行一次）。

结果落账：三类的「没有结果」

执行前意图已落 tool_ops（tool-op-ledger.ts · recordResult），所以停止、重启或渠道中断后每个操作都能归入一类：明确的成功或失败照实记；审批未消费或请求未交出是已知未执行；只读中止记无写入效果；其余一律效果未知，不自动重做，由拥有者核实。详见 只执行一次 页的对照表。

不变量

同一个批准最多消费一次、宿主操作最多执行一次；结果无法确认时停在不放大副作用的一侧（效果未知），而不是赌一次重发。
