工具调用路径

Runtime 提供静态宿主工具族，驱动器按执行画像构建工具集合，每次宿主调用持有独立上下文。模型发出的 tool_call 先过本任务的工具集合，再记意图、按名字分派；越界操作经审批闸门单次消费，执行边界由访问模式决定。各族声明账本分类，结果、产物引用与效果未知由工具操作账本记录，结果不明不自动重做。

分派：一次调用先记意图，再按名字分路

SDK 每发出一次 tool_call，都先进 driver.ts · handleToolCall。它按顺序做四件事：查本任务的允许集合；读取当前任务（模式、权限版本、授予路径都不用缓存），在工具边界应用待生效的模式切换；确认没有停止请求；分配宿主操作 id 并在一个事务里写入执行意图。之后才按工具名分到四条路。

静态宿主族与独立调用上下文

Runtime 先初始化应用库、资料解析器和个人产品的调度器，创建 SubAgentManager，再建立全局静态族清单及工具操作账本，随后恢复遗留操作；管理器在恢复前创建，编排器在恢复后创建（runtime.ts · start、initHostToolFamilies）。同一份清单捕获各族的资料、凭据与存储依赖，并交给驱动器。驱动器按执行画像筛选族，构建工具时向族提供身份复核、审批、产物登记、效果未知登记与读取任务钉版技能的闭包；每次执行再按 SDK 调用 id 取得独立 HostCall（driver.ts · ensureSdk）。buildHostToolSet 核对族声明的名称集合与构建结果一致，并拒绝族间重名；返回的名称集合用于宿主分派。编码、结构化审批、产物读取与 MCP 继续走上图各自的执行路径。

HostCall 的上下文由宿主记录取得，driver.ts · bindHostCall 只释放对应 SDK 调用 id 的记录，工具包装在 finally 释放句柄（hostCallFor）。没有绑定器的模块测试可直接提供 taskContext。调度通知目标也使用本次调用的 taskId 读取来源事件，再由拥有者 IM 入口确定（initHostToolFamilies）。

执行期间按宿主操作编号登记产物引用；例如 web_search 保存超限或畸形响应时，先创建 web-search-response 产物并登记引用，再写正文（web-search.ts · saveRawResponse）。正常回收 tool_execution_end 时，驱动器把这些引用并入 task.tool_result 的 artifactIds；正文写入不完整时，已登记的引用仍可随错误结果返回，创建失败时没有引用。

可用性：会话类别定清单，任务再收窄

「这个会话、这个任务能用哪些工具」只有一个答案来源：tool-availability.ts · SESSION_TOOL_CATEGORIES，一张会话类别 → 工具类别的静态表。会话类别（SessionToolClass）取自会话身份（store.ts · getSessionIdentity），由驱动器在任务开始算出的执行画像钉定（tool-availability.ts · executionProfile）：绑定了 SubAgent 的子会话是 subagent；main 角色会话是 main（旧架构的逻辑角色）；其余是普通开发会话 dev。QQ 群会话与 chat、coding 角色会话已退役，是只读归档，不归任何类别（会话身份为已退役归档，session-identity.ts · classifySession）：提交入口与队列兜底先行拒绝，驱动器被要求运行这类会话时直接报错。新工具族默认对所有会话不可见，写进哪份清单才出现。

清单含某类别只是装配的前提。全局清单包含各宿主族，应用库、调度器或服务管理不可用时，对应族提供空的名称与构建结果，恢复规则仍保留（账本分类）；驱动器按类别构建工具。SubAgent 的编码工具按执行画像单独筛选，协作消息由对应宿主族提供，之后仍过任务收窄（装配与调用上下文，driver.ts · ensureSdk）：

  • scheduler：调度器只在个人 Agent（ruukoto）启动；ruukoto-dev 不创建调度器，main 的调度与通知工具不装配。
  • service：后台构造时要求产品为 ruukoto、平台为 Linux、显式部署配置（helper 与策略路径）齐备，缺一项 runtime.ts · serviceManager 就是 null，工具不装配，不会静默放行。普通开发会话、SubAgent 与 ruukoto-dev 都没有这两个工具；main 也不因此拿到 bash。
  • subagent：委派、结果、关闭、取消与汇总工具每次调用都核实会话是普通开发会话或 main（driver.ts · verifyDelegationHost）；subagent_delegate 另要求任务由拥有者发起（直接提交，或已核实身份的 Telegram / QQ 私聊入站；subagent-tools.ts · ownerOriginated），调度唤醒、子任务回报与 SubAgent 自己的任务都被拒绝；subagent_close / subagent_cancel / subagent_integrate 没有这道来源门（关闭与取消只收窄能力；汇总只作用于本会话登记的成果），回报唤醒轮次也允许。SubAgent 本身怎样登记与执行见编排器。
  • SubAgent 子会话的清单为空：驱动器只从编码工具里按执行画像的 SubAgent 工具集挑出静态白名单装配——只读分析工作 read、read_artifact；修改委派的工作额外给 edit、write、bash（装配、发送前与调用门三处经 subAgentAllows 取同一结论，工具集按本任务 work_delegations.write_target 与是否宿主评审在任务开始钉定）。工具集进 SDK 会话签名，与 MCP 清单签名拼在一起（driver.ts · runInner）：同一 SubAgent 从只读工作复用到修改工作时签名变化，SDK 会话重建，装配拿到写入工具；这不依赖 Runtime 每任务释放 SubAgent 的驱动器（那只是回收 SDK 缓存与 MCP 连接）。写任务仍固定 confirm，不给 request_file_access、http_request、MCP 或委派工具，也没有网络；任务的访问模式由宿主固定为 confirm，不能切换。唯一的例外是宿主评审任务（GitHub PR，工单 19）：driver.ts · taskMcp 依赖为真时画像的 planMcp 为真，按本会话项目规划 MCP，收窄为静态白名单 ∪ effect=read 的 MCP（GitHub MCP 配在 main 项目；owner 委派的 SubAgent 拿不到）。
  • 同一 SubAgent 宿主族为 dev / main 构建委派工具与 subagent_message，为 SubAgent 子会话只构建协作消息工具（subagent-tools.ts · createSubAgentFamily；发送方身份由发起任务核实、不接受参数）。tool-availability.ts · subAgentAllows 对 subagent_message 放行：SubAgent 任务里允许向主 Agent 或当前承接本工作的其他 SubAgent 发送；宿主评审任务（GitHub PR，taskMcp）除外——同一收窄不放行（管理器侧同样拒绝评审 SubAgent 收发）。工作内消息的登记、投递与冲刷见编排器 · 协作加入与工作内消息。

同一个集合，三处使用

任务开始时 taskToolSet 算一次本任务允许的工具：已装配的工具（含本任务的 MCP 工具），减去三类收窄。每个任务都从完整注册表重算，宿主对上一个任务的收窄不带进下一个任务。收窄只减不增。

  • 计划模式：只留 plan-mode.ts · PLAN_TOOL_NAMES 与只读 MCP 工具，今后新增的工具默认不可用。这个名单含 bash、request_file_access、http_request，后两者照常逐次审批；未开放 subagent_delegate。管理器的计划模式校验不增加模型工具，不能据此发起分析委派。
  • 宿主按任务收窄：SubAgent 任务按执行画像的工具集收窄（subAgentAllows，与装配同一结论）——写入目标白名单兜底一次，GitHub 评审 SubAgent 收窄为静态白名单 ∪ 本任务 effect=read 的 MCP；其他任务经 github/events.ts · allowTool：评审对应的 main 唤醒任务只留 subagent_result 与只读的 coding_result，带 GitHub 来源事件的其他任务（评审父任务）一律不放行任何工具。
  • 项目关闭 Web Search：web_search 不进集合，模型看不到。任务进行中才关闭时，由工具在调用时自行检查并拒绝，这不属于可用性。

算出的集合在三处共用，结论一致：激活（setActiveToolsByName，决定模型看到哪些工具）；每次模型调用发送前，载荷里的每个工具都必须在集合内，否则以 task_tools_forbidden 阻断发送、中断任务并暂停会话队列（driver.ts · checkBeforeSend，发送前复核的其余检查见上下文组装）；以及上图的可用性门。

访问模式矩阵：哪些操作要谁点头

任务带一个访问模式（types.ts · AccessMode）：confirm 请求确认、full_access 完全访问、auto-review 自动审查。模式只由拥有者选择；入站事件、子任务回报唤醒、委派出的子任务与 SubAgent 任务都由宿主固定为 confirm，不继承会话默认模式。「是否要审批」不由一处统一决定，而是写在各工具族里，下表逐格对照了代码；自动审查只在闸门内部生效。

「完全访问也须确认」的四个例外

ADR 0003 说完全访问无需逐次确认，指的是执行账户已有的系统权限。下面四类授权独立于任务执行权限，full_access 也照样审批：应用数据破坏性变更（ADR 0009）、建立外发计划与一次外发（ADR 0010）、新闻推送计划（ADR 0015）、服务操作（ADR 0019，root 分支是后台经 sudoers 的提权能力，不属于执行账户权限）。另外，request_file_access 与 http_request 在 tool-router.ts · executeApprovalOp 里不看模式、始终审批；完全访问下的编码工具本来就按执行账户权限读写，不必经过它们。代码里唯一按 full_access 跳过审批的是 MCP 写工具。

自动审查不覆盖的范围

review.ts · classifyForReview 是确定性策略：只有越界文件读、无凭据的 GET / HEAD 能交给审查调用（ADR 0005）。其余范围——写文件、带凭据或其他方法的请求、mcp_tool（ADR 0008）、app_data_change、notification、service_operation、通用 tool 门、历史 github_publish——都不发起模型调用，直接转拥有者。

长期授权放行只在 service_manage 的请求路径上尝试，不看访问模式；候选要求任务沿父任务链追溯到绑定拥有者的 IM 私聊入站（见长期操作授权）。这类任务提交时由宿主固定为 confirm，拥有者事后切换模式不影响候选判定。

审批闸门：登记、决定、单次消费

审批请求的全程只在 approval-gate.ts · ApprovalGate 里（每个驱动器一个实例）：登记请求并把任务转入等待、auto-review 任务先经一次自动审查、等决定、未批准时记已知未执行、获批后在同一事务里复核并消费一次。工具族只交给它三样东西：审批范围、获批后的同步复核 recheck、需要与消费同事务提交的本地效果 commit。service_manage 在走这条路之前，先试一次长期授权的窄路径。

审批请求的状态

状态取值见 types.ts · ConfirmationStatus：pending 待决定；approved 已批准，consumed_at 为空即尚未执行；rejected 已拒绝；stale 已失效，再也不能消费。消费不改状态，只写 consumed_at；已消费的批准不会再被标 stale。

决定的两个入口

拥有者从 TUI / CLI 经控制面 respond_confirmation 回应（可带 permission_version，版本不符返回 permission_version_mismatch）；也可以在 Telegram 或 QQ 私聊发整条审批命令。IM 命令怎样识别、怎样作为 im_approval 控制事件持久化，见入站事件。两个入口汇到同一个 approval-gate.ts · resolve：只有仍为 pending 的第一次条件更新生效，后到的应答（另一入口、自动审查、另一条命令）返回 false，不再执行。

IM 命令在进闸门之前逐项核实：第 1 步由 im-approvals.ts · handleCommand 对所有命令先做，其余由 handleDecide 做。任一不符都只回执、不决定（没有钉版目标时连回执渠道都没有，只留控制记录）：

  1. 入口身份：当前绑定目标与命令收件时钉版的目标逐项相同（渠道、账号、chat、配置版本），发送者 actor 是当前绑定的拥有者。
  2. 归属：从审批所属任务沿 parent_task_id 找到根任务的入站事件（imSourceEvent，最多追溯 CHAIN_WALK_LIMIT 层，断链或循环即拒绝），它必须是同一平台、同一 actor、同一钉版目标的普通 IM 委托。TUI 发起、没有 IM 来源的审批不对 IM 开放。
  3. 审批仍是 pending，命令中的权限版本等于审批记录的版本（否则回执 version_mismatch），任务仍在 awaiting_confirmation。
  4. 交给活动驱动器的闸门：决定、task.confirmation_resolved、控制事件终态与回执作为 txExtra 在同一事务提交。任一写失败整笔回滚，决定不记录，另记一条失败回执请拥有者重发。

批准接受不等于操作成功。消费前，闸门经宿主挂钩再做一次 IM 固定身份复核（im-approvals.ts · consumeRecheck）：批准接受之后、消费之前若入口重绑、停用或配置代次变化，批准失效、操作不执行。IM 入口失效时，ImApprovals 另把该平台来源的未消费审批全部失效并定向放开等待，另一平台在共享主会话里的审批不受影响。

自动审查：一次有时限的无工具调用

auto-review 任务的审批照常登记、照常进入 awaiting_confirmation，闸门在注册好等待者之后才启动审查（approval-gate.ts · runAutoReview），所以拥有者随时可以抢先决定。审查复用任务创建时固定的模型配置；任务没有审查器或模型配置时退化为纯人工。

确定性策略

classifyForReview：只有越界文件读、无凭据 GET / HEAD 返回 reviewable；其余直接 ask_owner，不发模型调用。

输入检查

拥有者原始请求为空，或请求、参数任一超过 REVIEW_INPUT_CAP_BYTES（8 KiB）：转人工，不凭截断后的摘要批准。

审查调用

无工具、独立输入，时限 REVIEW_TIMEOUT_MS（30 s），输出上限 REVIEW_MAX_TOKENS（1024），策略版本 REVIEW_POLICY_VERSION（auto-review-v1）随审批记录落盘。每个审批最多一次，不重试。

结论

严格解析 JSON（只容忍外层代码围栏）：decision 必须是下表三者之一且理由非空，否则转人工。

结论（ReviewDecision）审批记录事件任务
approve条件更新 pending → approved，要求权限版本未变、任务仍活动；decision_source = auto_review，review_status = done，理由落盘task.confirmation_resolved（source auto_review，带 reason）唤醒等待者，进入消费
reject同上，状态 rejected同上账本记「自动审查拒绝执行 X：理由」
ask_owner只改 review_status = asked_owner 与理由，状态仍 pending；人工已抢先则不覆盖task.confirmation_reviewed继续等拥有者

审查失败的各种情形——模型不可用、超时、调用失败、输出格式错误、输入超限——一律转 ask_owner，不因失败放宽。外部中止（人工抢先、停止、模式切换）抛 ReviewAbortedError：只把 review_status 标 superseded，不碰审批状态。审查输入里的网页、文件与参数都是待审查数据，其中的指令不构成授权；结论也不会让任务升级为完全访问。

已知限制

approve / reject 的条件更新与随后的 task.confirmation_resolved 事件在代码里是两个相邻事务，而函数注释写「决定、理由、来源与事件在同一事务落盘」。两次写之间崩溃会留下已决定、无事件的审批；重启恢复会把未消费的批准一并标 stale，不会因此多执行。

长期操作授权：逐次重建核实后自动放行

ADR 0019 的逐次审批有一个例外：拥有者可以在原 IM 平台把某次服务 restart 审批保存为限定的长期授权（首版只覆盖本机白名单服务的 restart）。之后独立任务命中完全相同的范围时，宿主每次都重新核实，再为这一次单独建一条已批准记录并消费；授权本身不被消费，也不会被扩大。授权行存在核心库 standing_permissions（types.ts · StandingPermission，存储细节见存储布局）。

创建：/approve-standing <审批ID> <权限版本>

只能经原 IM 平台、针对一条 pending 的 service_manage restart 审批（im-approvals.ts · handleApproveStanding）。在 IM 决定的全部核实之外，再要求会话绑定 main、同步重读部署策略且修订与审批范围相同。范围完全取自原审批记录：本机、单元、动作、两项修订；入口取自命令：渠道、账号、chat、actor 与钉版目标。授权创建（版本 1）、这次批准与授权关联、审计事件、控制事件终态与回执同一事务提交。原 /approve 只批准一次，从不隐式保存授权。模型、子任务消息、TUI 提交与其他平台都不能创建授权。

使用：先找候选，再在消费事务里核实

service_manage 先经 helper 拿到本次真实修订，再调 approval-gate.ts · requestStanding。ImApprovals 按当前 main、任务来源入口的稳定身份、本机、单元与动作找候选（im-approvals.ts · standingCandidate）：钉版目标或 actor 与当前不符记 entry_changed 失效，修订不符记 revision_changed 失效。候选不是执行依据，消费事务内还要按授权行逐项重核（上方时序图 ①）。没有 IM 来源的任务（TUI 提交、调度、GitHub、子任务消息）恒无候选。

记录：审批与账本怎样写

每次放行都有一条独立的审批记录：状态一开始就是 approved，decision_source = standing_permission，并钉版授权 ID 与版本；随后照常写 consumed_at，发 task.confirmation_resolved 与 task.approval_consumed，两者都带授权 ID 与版本。restart 以退出码 0 完成时，工具结果第一行写明「授权依据：长期授权 <ID> v<版本>」。账本一侧与人工批准完全相同，这条记录已消费，所以中断时归入效果未知。

失效原因（revoked_reason）触发位置
owner_revoked/revoke-service-grant <授权ID> <版本>、控制面 service_grant_revoke、ruukoto service-grant revoke，都带期望版本；重复撤销幂等store.ts · revokeStandingPermission

执行边界：谁在哪个身份下真正动手

访问模式在执行时选边界，只影响编码工具的工作进程。其余操作——越界文件与单次 HTTP、MCP、宿主工具——都由后台进程自己执行，服务操作再经 root helper。容器参数、系统账户与 sudoers 属于部署与信任边界，这里只讲调用路径上的分工。

操作执行者与身份要点
编码工具工具工作进程。启动器由 launchers.ts · createLauncherFor 按后端与模式选：container 后端下 confirm / auto-review → 按任务容器，full_access → systemd 执行账户（缺执行账户入口即 execution_unavailable）；local 后端任何模式都以后台账户运行工作进程按「任务 + 模式 + 授予路径」复用，任一变化先停旧单元并核实退出，核实不了就拒绝建新环境。单次调用上限 WORKER_CALL_TIMEOUT_MS（10 分钟）。ROUTED_TOOL_NAMES 的工具定义声明顺序执行（executionMode: "sequential"），避免同名调用的输出串流；MCP 动态工具不在此列
越界文件、单次 HTTP后台受信执行器，后台账户（approved-ops.ts · executeApprovedHttpRequest）文件：逐段 lstat 拒绝符号链接、打开后核对 dev/ino、写前核对原文指纹，保护根目录始终排除，写入上限 MAX_FILE_CONTENT_BYTES（8 MiB）。HTTP：不跟随重定向、不重试，连接到登记审批前解析出的地址，响应超过 MAX_HTTP_RESPONSE_BYTES（1 MiB）的部分截断。凭据只按名称引用，主机与绑定一致才注入，限定了使用范围的凭据不能被 http_request 借用（credentials.ts · scope）
MCP后台进程，任务开始建立的钉版连接每次调用前重读服务配置与凭据绑定（mcpConfigBlock）；凭据值不进审批视图或事件
宿主工具后台进程身份由宿主注入；应用数据在独立的 main.db，调度与通知写核心库的计划与 outbox
服务操作后台经 sudo -n 调 root 拥有的 helper（deploy/systemd/ruukoto-service.mjs），环境只留 PATH、绝对路径、固定 argv检查以策略里的执行账户运行；restart 由每个宿主操作派生的命令单元执行，派生单元先登记到受管单元表，停止时只停它，已提交给 PID 1 的重启作业不撤回

LaunchSpec：宿主钉定工作区、只读根与环境

每次启动工作进程的挂载与环境单由宿主算好（tool-router.ts · launchSpecFor），模型参数进不了这张图。工作区由 taskWorkspaceFor 钉定：普通任务是会话工作目录；SubAgent 修改任务（工作带 write_target）是该工作的副本或写入目录。数值目录身份（workspaceIdentity 与 readRoots 条目的 dev/ino）只在 Linux 下发——原生 bind mount 按宿主原样呈现目录身份；macOS Docker Desktop 经 VM 重新编号 inode（已实测：容器侧 dev/ino 与宿主恒不一致），darwin 不下发数值身份，worker init 只按路径钉定（worker.ts），目录身份复核由宿主队列回路在任务启动前按 taskWorkspaceFor 承担（runtime.ts）。worktree 修改任务再加两样：仓库的共享 Git 目录作为只读 readRoots 挂载（可 status/diff/log，写不了 refs/hooks/config），以及环境包 GIT_CONFIG_COUNT=1、GIT_CONFIG_KEY_0=safe.directory、GIT_CONFIG_VALUE_0=*（容器 uid 与仓库属主不同时 git 仍能运行）；这些键只在需要时注入，不进 worker 复用键。git 会把副本路径字串写进共享 Git 目录的 worktrees/<name>/gitdir 并据此回核，所以修改委派的创建命令、挂载与 write_target.path 一律用 copyDirReal = fs.realpathSync(copyDir)（macOS TMPDIR 的符号链接会让字串与 realpath 不一致）。

工作进程协议与产物

后台与工作进程之间是 stdio 上的换行分帧 JSON（protocol.ts · WorkerRequest）：后台发 init、tool_call（以宿主操作 id 关联）、abort、shutdown；工作进程回 ready、data、result、fatal。单帧上限 MAX_FRAME_BYTES（4 MiB），正文按 DATA_CHUNK_BYTES（512 KiB）分块、base64 传输，写入侧有背压。等 ready 超过 30 秒即启动失败并回收执行单元（host.ts · 启动超时）；停止时先发 shutdown，给 3 秒优雅退出，再停整个执行单元并核实退出。

工作进程把未截断的 stdout、stderr 与文件正文以 data 帧流回，路由器先写进产物文件，再在模型视图里附「完整正文已捕获：artifact …」引用（tool-router.ts · executeCodingTool）。结果帧回来即产物定稿为 complete；写盘失败立即中止执行，保留已捕获部分与原因，不报告完整成功。模型用 read_artifact 按偏移续读，单次最多 64 KiB，同项目旧任务的产物按资料范围判定，SubAgent 只能读本任务自产的产物。

ruukoto-dev 开发机的受限与完全访问

  • 默认执行后端按产品区分（cli.ts · 执行后端默认值）：ruukoto-dev 为 container，受限任务进本机容器运行时里的每任务容器；ruukoto 的 CLI 默认仍是 local，生产部署显式启用 container。--execution local 或 RUUKOTO_EXECUTION_BACKEND=local 可显式选 local，两个产品都打印同一条无隔离警告。
  • 完全访问需要专用执行账户入口（RUUKOTO_EXEC_LAUNCH_SCRIPT 与 RUUKOTO_EXEC_STOP_SCRIPT）。没配置时，提交和切换模式就以 execution_unavailable 拒绝（Runtime 受理前先构造一次启动器），不静默降级。受限任务提交时不检查容器边界，照常入队，到第一个编码工具启动工作进程时才失败：带路径的 RUUKOTO_DOCKER_PATH 不存在报 execution_unavailable；CLI 在而 dockerd 或镜像不可用，等不到 ready，30 秒后报 worker_timeout。都不换执行方式，各情形见部署与信任边界 · 执行边界。
  • 启动窗口：执行意图落库早于工作进程 ready。路由器在启动前先登记一个 starting 占位单元（managed-processes.ts · starting），停止路径也能回收仍在启动的容器；驱动器读受管单元表前先让出一个宏任务，使已记意图的派发先完成登记（driver.ts · killManagedProcesses）。停止路径本身见任务生命周期。

工具操作账本：结果、效果未知与停止时的分类

工具操作的已知结果与「效果未知」只在 tool-op-ledger.ts · ToolOpLedger 里写。recordResult 把 tool_ops 的结果列与 task.tool_result 事件成对写入，条件是结果仍为空，所以先写者为准，重复补记不重复发事件。markEffectUnknown 一次写三处：操作标记、task.tool_effect_unknown 事件、任务的效果未知标记，已标过就跳过；被标的若是已消费的 service_operation，同一事务里让同目标的长期授权全部失效。事务由调用方开，账本自己不开。

停止与重启的分类器

停止（settleTask）与重启（settleAll）对结果缺失、尚未标未知的操作用同一棵决策树；前一级的证据强于后一级。停止多一步：中止之前先快照「按审批判定、且审批并非全部未消费」的操作，这些一律效果未知，中止期间才落下的结果（如 bash 的「已中止」）不改变结论。

结论条件账本写入（结果文案 · isError）
停止快照停止路径中止之前，规则为 approval 且不是「有审批且全部未消费」交给终态事务标效果未知；终态被竞争路径抢先时放弃标记
已知未执行操作有审批记录，且每一条的 consumed_at 都为空停止：「已知未执行：审批未消费即停止」；重启：「…即发生后台重启（批准不跨重启执行）」· true
无写入效果规则为 no_effect「未完成：只读操作在停止前中止，无写入效果」（重启为「后台重启前」）· true
已提交 / 已知未提交规则指向工具族，族核实给出 committed / not_committed族自己的证据文案，如「已提交：应用库存在该操作回执（停止前已生效）」· 已提交为 false，未提交为 true

各族声明与账本分类

宿主工具的名称与分类规则由各族模块声明，能核实提交结果的族另提供核实入口（HostToolLedger）。Runtime 从同一份全局族清单派生账本声明（initHostToolFamilies）。应用库、调度器或服务管理停用时，对应族的工具名与构建结果为空，账本声明仍保留完整规则，恢复不依赖当前会话是否装配该族；应用库无法核实时仍定效果未知。编码、结构化审批、产物读取与模拟工具保留固定规则，只有已删除的 coding_delegate 另保留 delegation / subagent 核实映射，处理升级前在途调用。

MCP 动态工具与未登记名字按 approval 判定。该分类表示结果缺失时按审批证据判断，并不表示工具一定产生审批：记忆写入就是没有审批的例子。工具路由器判定已发出的 HTTP 调用是否效果未知时，也复用「无写入效果」规则（hasNoWriteEffect，tool-router.ts）。

消费之后失败怎样定性

停止与重启之外，执行中的失败由各工具族当场定性：能证明没发出去、或远端已经应答的，是已知结果；请求可能已送达却拿不到可信结论的，当场标效果未知，不自动重发。

操作已知结果效果未知
http_requestGET / HEAD 的任何失败；请求写完（Node ClientRequest 的 finish 事件）之前的失败，如凭据不符、主机解析失败、连接被拒；有 HTTP 状态码的应答其他方法在 finish 之后失败、拿不到状态码：超时、连接重置、任务停止中止
MCP 写 / 副作用不明远端已应答的错误（isError、HTTP 状态、JSON-RPC 错误）；发送前失败；结构化结果与声明的 outputSchema 不符（远端已执行，记错误）传输类失败：timeout、connect_failed、canceled
service_managehelper 明确证明还没请求 systemd（launched: false）：已知未执行，批准已消费，再操作要新审批；命令已执行的非零退出码如实报告，可能有部分效果helper 超时或被中止、应答不可信或操作 id 不符、原始输出没保存成功、派发后失败
不变量

每个记过意图的操作最终都落在一类结论上：有结果，或效果未知。同一批准最多消费一次，同一宿主操作最多执行一次；结果确认不了时停在不放大副作用的一侧，由拥有者核实，而不是赌一次重发。跨模块的对照见只执行一次。
